CubeSandbox 增量内存快照演进：从 Full/Incremental 到 SoftDirty 逐周期增量

本文回答一个版本演进问题：CubeSandbox 从提交 A 到提交 B，内存快照的增量 捕获机制发生了什么变化，为什么变，影响与代价是什么？

先行结论：B 在不破坏既有 full/incremental 语义的前提下，新增了 第三种快照类型 soft-dirty——用内核 soft-dirty PTE 位（clear_refs 布防 + pagemap bit 55 读取）替代 pagemap+ kpageflags 的"生命周期单调累积"判定， 使长期运行 VM 的重复增量快照从"单调增长的差集"变为"逐周期真差集"，并在 Cubelet 侧配三层退化（soft-dirty → incremental → full）保证 base 血缘断裂 时仍能产出正确镜像。机制对宿主架构不条件编译，可用性由内核 CONFIG_MEM_SOFT_DIRTY 决定；页大小硬编码 4096 在 A 的 pagemap_anon 已 存在、B 的 soft_dirty 复制了同一缺陷，在 64 KiB base page 的 ARM64 宿主上 会错误索引 pagemap（6 周后由后续提交统一修复）。

范围与边界（集中声明）：读者问题与两端身份见下节；架构适用范围为 x86_64 与 ARM64（不条件编译，按内核配置与页大小分化，见"架构边界"节）； 不做事项：不运行任何 build/runtime/快照/benchmark 验证，不覆盖 23d3126 之后的机制状态（该修复只作延伸边界），不讨论 Template/rootfs 特性。 本文全部行为结论来自 A/B 两端源码；作者声明的动机单独标注为 author evidence，未经运行验证。

背景与术语

  • full 快照：写全部 guest RAM，自包含，代价与内存同阶。
  • incremental（pagemap_anon）：只写 CoW 匿名页——通过 /proc/self/pagemap + /proc/kpageflags 判定自原始 MAP_PRIVATE mmap 建立以来被写过的页。关键性质：保存集随 VM 生命周期单调增长（每个被碰 过的页都进差集）。
  • soft-dirty：Linux 内核 PTE 的软件脏位（CONFIG_MEM_SOFT_DIRTY）。向 /proc/self/clear_refs 写 "4" 清零全部 PTE 脏位（"布防"），此后 guest 写内存会重新置位；/proc/self/pagemap 的 bit 55 即该位。由此得到的保存集 是自上次布防以来的真差集。
  • 组件链（按真实调用方向）：Cubelet 决策 → CubeShim/cube-runtime → VMM。 prepareCommitMemoryArtifact 在 Cubelet 先决定类型与 base （template_ops.go:158），再经 executeCubeRuntimeSnapshot 以 exec.CommandContext 调 cube-runtime 把类型送进 CubeShim （template_ops.go:191-196、appsnapshot.go:621-642），最终由 VMM memory_manager 分派（:3041）。CubeShim 的 --snapshot-type CLI 与 hypervisor ch-remote --snapshot-type 是同一取值集合的两个用户入口。

A 端旧机制（local fact）

  • 快照类型只有两种：hypervisor/vm-migration/src/lib.rs:108-116 enum SnapshotType { #[default] Full, Incremental }；Incremental 的文档 注释即"only saves CoW anonymous pages via pagemap + kpageflags"。
  • 不存在 hypervisor/vmm/src/soft_dirty.rs（git cat-file -e 在 A 处报对象 不存在），CLI 也没有 soft-dirty 取值。
  • hypervisor/docs/snapshot_restore.md 在 A 处没有 ## Snapshot types 章节（grep 计数为 0），类型语义只散落在枚举注释中。

也就是说：A 已能做增量快照，但增量语义是"自 restore 以来碰过的所有匿名页" ——对重复做增量快照的长运行 VM，每次快照要写的差集只增不减。

B 端新机制（local fact）

1. 类型入口：SnapshotType::SoftDirty

vm-migration/src/lib.rs:110-149（变体 :110-123、Display :125-133、 FromStr :135-149，"soft-dirty" 分支在 :142）：新变体的文档注释明确语义边界——"only saves pages written since the previous soft-dirty snapshot (true delta)"， 并写明内核不支持时静默降级为 Incremental。serde rename 保证线上 序列化值是 "soft-dirty"。

2. VMM 侧：soft_dirty.rs 的布防-读取-过滤原语

决定行为的最小片段（hypervisor/vmm/src/soft_dirty.rs）：

pub const PAGE_SIZE: u64 = 4096;              // :36  ← B 端隐患，见 ARM64 节
pub fn probe_soft_dirty_support() -> bool     // :133 写 clear_refs 探测内核支持
pub fn clear_soft_dirty() -> Result<()>       // :150 写 "4" 重新布防
pub fn get_soft_dirty_pages(...) -> Vec<bool> // :193 读 pagemap bit 55
pub fn filter_memory_ranges_by_anon_and_soft_dirty(...)  // :371 anon ∩ soft-dirty

保存集取 anon ∩ soft-dirty 的交集（:371），而不是单用 soft-dirty 位： 只有"是匿名页且本周期被写过"的页进入 memory-ranges。交集是最小且安全的 保存集——排除了非匿名映射上的脏位噪声。

3. 周期状态机：首扫写完整 anon 集、后续真差、写后重布防

memory_manager.rs 的 send_soft_dirty_memory（:2413 起）按 soft_dirty_armed 原子标志分两态：

  • 未布防（首扫或降级后）：memory_manager.rs:2421-2443——先执行 send_pagemap_anon_memory 写一个完整 anon 集快照（叠加在 Cubelet 预置 的 base 文件上，不是 SnapshotType::Full 的全 RAM 语义），再调 probe_soft_dirty_support() 布防（该探测本身就是向 clear_refs 写 "4"，成功即完成布防）。失败则 soft_dirty_armed 保持 false，下周期重试。
  • 已布防（稳态）：要求目标 memory 文件已存在有效 base，否则直接返回 硬错误"Base snapshot file not found … take a full snapshot first" （memory_manager.rs:2490-2496）；随后 open_read_write() 打开该文件并 就地叠加 filter_memory_ranges_by_anon_and_soft_dirty 过滤出的真差页 （:2463、:2497-2512），写完调 clear_soft_dirty() 重布防 （:2525-2532）。若重布防失败（如 seccomp 拦截 clear_refs 写），disarm 并降级到 pagemap_anon 路径，只记 warning 不向调用方报错。

Cubelet 侧把同一前置写进常量注释：soft-dirty 的目标文件"MUST already contain a valid base image … otherwise pages untouched-since-last-clear would read back as zero on restore"，Cubelet 通过先 reflink base 保证该前提 （appsnapshot.go:555-562）。

分派点在类型 match（memory_manager.rs:3041-3047）： SnapshotType::SoftDirty => self.send_soft_dirty_memory(...)。

4. Cubelet 三层退化：base 血缘选择

Cubelet/services/cubebox/snapshot_base_memory.go:188 的 prepareCommitMemoryArtifact 是统一入口，按 base 血缘可用性退化：

Tier 条件 快照类型 base 来源
1 上一快照 base 可解析 soft-dirty reflink 上一快照 base（resolveBaseMemoryObject）
2 上一快照 base 缺失、上次 restore base 可解析 incremental（pagemap_anon） reflink 上次 restore base（resolveRestoreBaseMemoryObject:114）
3 两条血缘都断 full 全新空卷（CreateTemplateMemoryVolume）

Tier 2 为什么必须换类型：soft-dirty 位图在上次 commit 时被重置，与更早 的 last-restore 文件不一致；而 pagemap_anon 的"当前匿名脏页"集恰好在 VM 上 次 restore 时归零——与 restore-base 标签记录的时刻一致（源码注释 snapshot_base_memory.go:205-216）。类型选择与 base 血缘时刻必须匹配， 这是正确性不变量，不是风格偏好。

前置（Tier 0）：opaque restore 使两条血缘同时失效。UpdateWithResume （pause/resume 路径）调用 invalidateRuntimeSnapshotBindingsAfterOpaqueRestore 把 runtime-snapshot 与 restore-base 两条标签同时置为 runtimeSnapshotBindingInvalidID，强制下一次 commit 走 Tier 3 full 重新锚定（update.go:225-231；无效 ID 常量与作废函数见 snapshot_runtime_binding.go:14,85-99；守卫测试 snapshot_base_memory_fallback_test.go:262-291）。这是已实现并有测试的 local fact：CubeShim 从内部 full 快照 resume 不经过 cubecow catalog，旧标签 必然失真，因此主动作废。

两条标签的维护规则不同（核心不变量，local fact）：

  • runtime-snapshot 标签在每次成功 commit 后推进 （template_ops.go:208 setRuntimeSnapshotBindingLabels；Rollback 同样 推进，rollback.go:186）。
  • restore-base 标签只在 Create 的 restore 路径 （cube_container_create.go:197）与 Rollback（rollback.go:190）更新； commit 有意不推进——snapshot_base_memory.go:76-81 注释明确 "intentionally NOT updated by Commit"，因为 pagemap_anon 的脏页集恰以 上次 restore 为零点。守卫测试 TestRestoreBaseLabelDoesNotAdvanceOnCommit （snapshot_base_memory_fallback_test.go:183-246）把"commit 误推进 restore-base 标签"判定为会静默损坏镜像的回归。
  • 注意：B 提交信息中的 "Update binding labels on every successful commit" 是作者意图陈述，且实际只覆盖 runtime-snapshot 标签；本文以源码与守卫测试 为准（见"作者动机"节的 author evidence 边界）。

5. CLI 与文档链

  • CLI（两处入口）：CubeShim/shim/src/snapshot/cmd.rs:86-93 的 --snapshot-type 帮助扩展为 'full', 'incremental' or 'soft-dirty' （默认 full）；hypervisor ch-remote.rs 的 snapshot 与 pause2snapshot 两处 --snapshot-type help 同步扩展（默认 incremental，与 CubeShim 的 默认值不同——两个入口的默认语义有差异，使用时需显式指定）。
  • 文档：hypervisor/docs/snapshot_restore.md:100-124 的 Snapshot types 表 逐行区分三种类型保存什么、何时用，并明确 incremental"单调增长"与 soft-dirty"真差集"的语义差别；### Soft-dirty details 补充三条边界—— 其原文写法 "writes a full base image"（snapshot_restore.md:114）是对 上述完整 anon 集快照的描述措辞，不对应 SnapshotType::Full 枚举语义； 另两条为内核不支持降级与 seccomp 失败降级。

不变量（跨 A/B 保持）

  1. full 与 incremental 的行为、序列化值、恢复路径在 B 完全不变（枚举 纯新增变体；diff 中两类型的发送/恢复代码零改动）。
  2. 快照工件结构不变：--snapshot-type 只影响 memory-ranges 的内容选择， config.json/state.json 等其余工件不受影响（B 端文档表第一段即此 声明，且分派只发生在内存发送路径）。
  3. soft-dirty 稳态的目标文件契约：稳态写入是就地叠加——目标 memory 文件必须已含有效 base，否则 VMM 直接硬错误 （memory_manager.rs:2490-2496）；写入只叠加过滤页（:2497-2512）。 Cubelet 以 reflink 预置 base 保证该前提（appsnapshot.go:555-562）。 违反该前提的后果是"上次 clear 以来未触碰的页读回为零"，不是格式错误。
  4. 恢复端不感知快照类型：git grep snapshot_type 62e0d56 -- hypervisor/ 的命中分布为——CLI 入口（ch-remote.rs）、协议字段定义 （vm-migration/src/lib.rs:156,166）、类型分派 memory_manager.rs:3041-3047 与快照元数据写入 vm.rs:2855-2877； 即除 CLI 与协议字段定义外，snapshot_type 只在发送侧被读取/分派。 restore 读的是完整 memory-ranges 文件 + base 血缘，增量语义完全由发送 端决定（local fact：该 grep 范围为 hypervisor/ 子树，无 restore 侧 读取点）。
  5. base 血缘一致性约束在两端等价存在：A 的 incremental 隐含要求 base 来自 上次 restore；B 把它显式化为三层退化、双标签差异化维护 （runtime-snapshot 随 commit 推进 / restore-base 钉在最近 VM 重启点）与 opaque-restore 失效（见上文 Tier 0 与标签规则）。

兼容与迁移影响

  • 序列化兼容：新增 serde rename 值 "soft-dirty"，旧值 "full"/ "incremental" 不变；旧快照与旧请求不受影响（local fact）。
  • 内核依赖：宿主需要 CONFIG_MEM_SOFT_DIRTY=y；不支持时请求被静默降级 为 incremental（memory_manager.rs:2405-2411 注释、文档 snapshot_restore.md:119-120）。降级只记 debug/warning 日志，调用方不 会收到错误——运维上需要靠日志识别"实际生效类型 ≠ 请求类型"。
  • Cubelet 运维前提：三层退化依赖两条血缘标签，但二者维护规则不同—— runtime-snapshot 标签随每次成功 commit 推进（template_ops.go:208）， restore-base 标签只在 Create-restore / Rollback 更新、commit 有意不推进 （snapshot_base_memory.go:76-81，守卫测试 snapshot_base_memory_fallback_test.go:183-246）。标签丢失或被 opaque restore 作废（update.go:225-231）只触发降级（Tier 2/3）， 不产生错误镜像。
  • 稳态 base 缺失是硬错误：若绕过 Cubelet 直接请求 VMM soft-dirty 而目标 文件无 base，VMM 拒绝并要求先做 full（memory_manager.rs:2490-2496）； 该失败路径不会静默产出坏镜像，但会把错误暴露给调用方（与内核降级路径 的"静默"形成对比）。
  • 无迁移动作：对已存在的快照/模板无需任何转换。

优点与代价

优点（local fact 层面）：

  • 保存集语义从"生命周期单调累积"变为"逐周期真差集"，重复增量快照的 数据量上界从"曾被写过的全部匿名页"变为"本周期写过的页"。
  • 三层退化保证任意血缘状态下都能产出正确（可能更大）的镜像，失败模式是 退化而非损坏。
  • 类型、CLI、文档向后兼容。

代价（local fact + 标注 inference）：

  • 首次 soft-dirty 快照仍要写完整 anon 集（memory_manager.rs:2421-2443， 叠加在 Cubelet 预置 base 上），不能跳过（local fact）。
  • 稳态依赖目标文件已有有效 base：base 缺失即硬错误、opaque restore 后必须 回到 Tier 3 full 重锚（memory_manager.rs:2490-2496、update.go:225-231， local fact）；这把"base 存在性"变成了每个稳态周期的正确性前提。
  • 每周期 clear_soft_dirty() 要求内核遍历所有 PTE 重布防；源码注释将其 标注为大 guest 上的主要暂停停顿来源（local fact：注释存在；停顿幅度 本身未经测量）。
  • Cubelet 必须维护两条血缘标签，状态面比 A 增大（local fact）。
  • 作者声称 soft-dirty "typically much smaller"、能"cut snapshot-induced pause-time spikes"——这是作者动机声明（author evidence），本文不作为 性能结论（未运行验证）。

失败/反例与错误矩阵

观察到的现象（判错指引） 说明什么假设不成立 处置
请求 soft-dirty 但日志出现 "tracker not yet armed" 且多个周期连续出现 内核无 CONFIG_MEM_SOFT_DIRTY（probe 失败），"实际生效类型 = incremental" 的假设未成立——实际一直在走 pagemap_anon 换内核或接受 incremental 语义；靠日志识别降级，调用方无错误
VMM 返回 "Base snapshot file not found … take a full snapshot first" "目标文件已含有效 base"的稳态前提被绕过（未经 Cubelet reflink 预置） 先做一次 full/Tier 3 重建 base；不要重试 soft-dirty
commit 后发现 restore-base 标签被推进 违反"commit 有意不推进 restore-base"守卫不变量（snapshot_base_memory_fallback_test.go:183-246 判此类回归为静默损坏镜像） 回滚该改动；该行为会使 Tier 2 选错 base 时刻
pause/resume（opaque restore）后第一次 commit 产出 full 而非 soft-dirty 不是 bug：update.go:225-231 有意作废两条血缘强制 Tier 3 重锚 预期行为；下一次 commit 恢复 soft-dirty
64 KiB base page 宿主上快照尺寸异常或恢复后数据错乱 命中 PAGE_SIZE=4096 硬编码缺陷（A 的 pagemap_anon 与 B 的 soft_dirty 均有） 升级到 23d3126 之后状态；不要在 B 状态的 64K 宿主上信任快照
反例（限制场景）：增量快照差集不减反增 该 VM 的访问模式使匿名页持续新增——incremental 的"单调累积"性质与此无关，soft-dirty 的真差集才按周期归零 长运行重复快照选 soft-dirty；偶发第二次快照用 incremental 已够

判错总则：soft-dirty 的两类静默行为（内核不支持降级、重布防失败降级）都不 向调用方报错，运维判断"实际生效类型"只能依赖日志中 "Soft-dirty:" 前缀的 info/warn 行；唯一的硬错误路径是稳态 base 缺失。

x86_64 与 ARM64 边界

  • soft-dirty 机制不按 target_arch 条件编译（soft_dirty.rs 全文件无 cfg(target_arch)）；可用性只由宿主内核 CONFIG_MEM_SOFT_DIRTY 决定 （local fact）。x86_64 与按 4 KiB base page 配置的 ARM64 宿主上，B 的 索引计算正确。
  • 页大小硬编码缺陷（inference，后续提交作者证据确认）：该缺陷在 A 已存在——pagemap_anon.rs:27 的 pub const PAGE_SIZE: u64 = 4096; 两端 相同；B 的 soft-dirty 路径在 soft_dirty.rs:36 复制了同一硬编码，使 新路径继承同一问题。/proc/self/pagemap 与 /proc/kpageflags 按内核真实 页大小索引，在 64 KiB base page 的 ARM64 宿主上会错位索引，可能静默 损坏快照。
  • 后续修复（延伸边界，不属于 A/B 主差异）：提交 23d31267e5234f2dd05e6f0a854efccbbacb0519（2026-07-13， fix(vmm): index snapshot pagemap by the host's real page size）改为经 sysconf(_SC_PAGESIZE) 探测并缓存宿主真实页大小，统一 pagemap_anon/soft-dirty 的页索引、偏移与长度计算。其提交信息确认了上述 硬编码缺陷（"could silently corrupt snapshots"）。
  • 因此描述 ARM64 行为时必须区分版本：B 状态仅对 4 KiB 页内核可靠； 64 KiB 场景须以 23d3126 之后的状态为准。
