CubeSandbox CubeShim ↔ Hypervisor 通信与 I/O 演进：v0.5.1 → v0.7.1

本文回答：从 v0.5.1 到 v0.7.1，CubeShim 与 VMM 的控制关系、host↔guest socket、TAP/virtio-net 和 container stdio 到底改变了什么，哪些核心契约保持 不变？

先行结论：三版都没有把 CubeShim 常规 VM 控制改成 socket RPC； VmmInstance/VMM_SERVICE 的进程内 mpsc + eventfd + response 核心在三个 tag 上是同一 blob。v0.6.0 的相关变化主要是可选 ivshmem 与 restore backend 扩展。真正显著的 transport/I/O 变化集中在 v0.7.1：新增 opt-in container stdio passfd、改变 TAP slow path 的 IP 配置、把 TAP TX EIO 从 VM-fatal 错误改为丢帧计数，并移除 virtio-net restore 期 driver_awake 强制中断 workaround；同时 pause/resume 生命周期从同 shim 恢复收敛为 pause-to-snapshot 后重新 create。上述都是源码行为；本次没有运行验证，不能 据此声称性能或稳定性提升。

范围与边界：A=v0.5.1，中间里程碑=v0.6.0，B=v0.7.1；覆盖 CubeShim、内嵌 CubeHypervisor、virtio-vsock、TAP/virtio-net、container stdio 与相关生命周期。无 build/runtime/benchmark；不把 commit title 当作 实现证据。

当前机制先读 CubeShim、VMM 与 guest 通信分层。

背景与术语

  • 主控制通道：CubeHypervisor wrapper 调 VmmInstance::send_request()； request 走 mpsc，eventfd 唤醒 VMM thread，response 同步返回。
  • chapi：同进程 VMM 的 HTTP/Unix socket 旁路，主要供 snapshot 工具。
  • cube.sock：virtio-vsock 的 host AF_UNIX 入口，映射到 guest AF_VSOCK。
  • cubetap.sock：VMM 向 Cubelet TAP pool 请求 donated TAP fd 的 Unix socket。
  • passfd：v0.7.1 新增的 container stdio 路线；CubeShim 用 SCM_RIGHTS 把 FIFO/socket fd 交给 vsock muxer，再映射为 guest vsock stream。它不是 VM control，也不是 TAP fd 路线。

旧机制（A 端）

A.1 控制面已经是内嵌 VMM thread

A 端 CubeHypervisor::launch_vmm() 创建 VmmInstance；wrapper 方法直接发 ApiRequest。VmmInstance::new() 建 request/response channel 与 eventfd， 启动 VMM thread；VmmServiceInner::send_request() 执行 send→eventfd→recv。

关键证据：

  • A CubeShim/shim/src/hypervisor/cube_hypervisor.rs:75-181；
  • A hypervisor/src/lib.rs:179-187,228-278；
  • A hypervisor/vmm/src/api/service.rs:14-16,66-89。

这三个核心文件中的后两个在 A、中间、B 上分别是相同 blob：

文件 A / v0.6.0 / B blob
hypervisor/src/lib.rs c4acfbfb746ed11c3dd5811099d67c1acf8da846
hypervisor/vmm/src/api/service.rs 744267e946f12dcb71e2f892360cfdeaf52c2447

这是“主控制 transport 未变化”的直接证据，不是根据接口名推断。

A.2 chapi、cube.sock 与 TAP pool 已经分层

  • A 端 SandBox::new() 已设置 ch_http_api，app snapshot 已通过 Snapshot::request_ch() 访问 pause/snapshot/resume；A 与 v0.6.0 的 CubeShim/shim/src/snapshot/mod.rs 是相同 blob fc2b69edf2f391ef42192ddac1b9ecc0845bf6f4。
  • A 端 AsyncUtils::connect_agent() 已连接 cube.sock、发送 CONNECT 1024 并把 dup fd 交给 ttrpc（ CubeShim/shim/src/common/utils.rs:335-368）。
  • A 端 TAP pool 已由 Tap::lookup_from_pool() 获取 fd； hypervisor/net_util/src/tap.rs 在 A、中间、B 上都是 blob 2240299a75664215a8d7c51c02cf72ab9e7866b5。
  • A 端 virtio-net RX/TX 已是 guest descriptor ↔ TAP 的 readv/writev 热路径。

因此 v0.7.1 不是从“CubeShim 通过一个 socket 控制外部 hypervisor”迁移而来； 这些分层在 A 已存在。

A.3 A 端没有 container stdio passfd

在 A 与 v0.6.0 的 CubeShim、agent、hypervisor 范围内， git grep passfd 均无匹配；proto 没有 stdin/stdout/stderr port，vsock muxer 只有传统 UnixStream backend。container stdio 由 agent ttrpc 的 read/write stream 路线转发。

v0.5.1 → v0.6.0：I/O backend 扩展，但 transport 不换轨

CubeHypervisor wrapper、VmmInstance、VMM_SERVICE、TAP、virtio-net、 virtio-block 与 virtio-fs 的关键 blob 在这两个 tag 上相同。可见变化是：

  • SandBox 新增 cube.master.enable_ivshmem，创建 /dev/shm/ivshmem-<sandbox-id>，普通创建和 restore 都可绑定它（ v0.6.0 CubeShim/shim/src/sandbox/sb.rs:50-51,773-812,889-951）；
  • RestoreConfig 增加 ivshmem，VMM restore 调 update_ivshmem()（ v0.6.0 hypervisor/vmm/src/lib.rs:676-684）；
  • ivshmem device 实现本身在 A 已存在且未变化，所以这里是 shim/config/restore 接入，不是新造一条 CubeShim↔VMM socket。

另一个与 ARM64 snapshot 正确性相关的变化，是 soft-dirty/pagemap 子路径从 固定 PAGE_SIZE=4096 改为 host_page_size()：A hypervisor/vmm/src/soft_dirty.rs:36 使用固定值；v0.6.0 hypervisor/vmm/src/pagemap_anon.rs:36-46 通过 _SC_PAGESIZE 缓存 host 页 大小，并被 soft_dirty.rs:193,271,353 等路径使用。memory_manager 在 A 端 已经有运行时 sysconf 探测，因此这里不能写成整个内存管理层首次支持 host page size。该变化不改变本文的控制、vsock 或 TAP transport。

v0.6.0 → v0.7.1：stdio passfd

B 端新增：

  • Config.use_passfd_io，默认 false，annotation 为大小写不敏感的 true 才启用 （B CubeShim/shim/src/sandbox/config.rs:74,79-105,185-190）；
  • AsyncUtils::passfd_connect_many() 一次 sendmsg 发送文本命令和最多三个 fd，解析带 label 的 ACK（B common/utils.rs:562-681）；
  • VsockMuxer::read_local_stream_port() 用 recvmsg 收 SCM_RIGHTS，校验 同 UID、fd 类型、非阻塞属性，再构造 PassFdStream（B hypervisor/virtio-devices/src/vsock/unix/muxer.rs:495-667,851-939）；
  • guest agent 在 AF_VSOCK 1027 接收 stream，并由 ttrpc request 中的动态 port 与具体 container/exec 绑定（B agent/src/passfd_io.rs:13-18,84-195、 agent/src/rpc.rs:150-215,430-496）。

提交 2aec7dd7f3d19cf7aff3a8caa8d3fa5d98cd45da 的标题把它称为 “high-performance passfd IO”；这只是 author evidence。固定 tag 源码能证明 数据路径减少了一层 UnixStream payload 转发，但没有 benchmark，不能把 “高性能”写成已验证结果。

v0.6.0 → v0.7.1：网络错误语义与 restore workaround

  1. named TAP 配置：v0.6.0 slow path 对 ip_addr/netmask 无条件调用 setter （open_tap.rs:101-113）；B 先检查 /sys/class/net/<name>，只有接口不存在 才写 IP/netmask（B open_tap.rs:76-103,105-145）。同时 B DeviceManager 把 net_cfg.ip/mask 传入 Net::new()（B device_manager.rs:2441-2461）。
  2. TX EIO：v0.6.0 在 writev 返回非 EAGAIN 时直接返回 NetQueuePairError::WriteTap（queue_pair.rs:96-116）；B 对 EIO 改为 丢帧、used length=0，并累计 tx_dropped_frames，其他错误仍失败（B queue_pair.rs:109-166,445-479）。
  3. driver_awake 删除：v0.6.0 在 restore 后、guest 尚未发 queue event 时 无条件触发 RX/TX used queue IRQ（net.rs:167-180,222-263,317-329,745-773）； B 删除字段与 || !driver_awake，只在 needs_notification() 为真时触发 （B net.rs:167-257,302-344,735-774）。

第 3 项是明确的机制删除，但没有本次运行数据支撑“更稳定”或“会回归”。若 restore 后第一包只在旧版成功、新版失败，这一变化是应优先验证的候选，而非 已确认根因。

v0.6.0 → v0.7.1：pause/resume 生命周期收敛

v0.5.1/v0.6.0 的 SandBox::pause_vm() 把 snapshot 写到本地固定路径，保留 shim 后由 resume_vm_with_config(None) 恢复（v0.6.0 CubeShim/shim/src/sandbox/sb.rs:1256-1288,1356-1375）。B 中 legacy pause_vm/resume_vm 直接报错；新 pause_vm_to_snapshot() 使用调用方提供的 spec dir/memory volume/snapshot type，写完后等待 VmShutdown 并保存 metadata， 恢复改为 Master create from snapshot（B sb.rs:1346-1462）。

底层仍发 ApiRequest::VmPauseToSnapshot / VmResumeFromSnapshot，所以这是 产品生命周期和 artifact 所有权变化，不是 VMM control transport 变化。

新机制（B 端）

B 端可以按五条彼此独立的路径理解：

普通 boot/restore 的主控制仍走实线第一条；stdio passfd 和 TAP fd 都用 SCM_RIGHTS，但 socket、fd 类型、所有者和目标完全不同。

不变量（跨 A/B 保持）

  1. CubeHypervisor 内嵌库 + VMM thread；没有新增独立管理 VM。
  2. 常规 VM action 都经 ApiRequest，同步 response 与异步 NotifyEvent 分离。
  3. chapi 是 HTTP/UDS 旁路，不是 wrapper 的默认调用路径。
  4. cube.sock 将 host Unix stream 映射为 guest vsock connection。
  5. CubeShim 网络配置传 TAP name；VMM 内 Tap::lookup_from_pool() 取得 fd。
  6. virtio-net steady-state 数据在 guest ring 与 TAP 之间搬运；控制请求不承载帧。
  7. restore 必须重新绑定当前 host 的 net/fs/disk/vsock backend；snapshot 不保存 可跨 host 复用的开放 TAP fd。

兼容与迁移影响

  • passfd 是可选协议扩展：旧配置继续走 ttrpc；只有 shim、VMM muxer、agent proto/实现同时支持且 annotation 开启时才能工作。部分升级会在 ACK、port 或 RPC 字段处失败。
  • passfd 不能跨 restore 自动存活：B 用 ReconnectContainerIO 重建；恢复 后仍持有旧 fd/port 的假设不成立。
  • TAP 既有配置保护：B slow path 不再覆盖既有 interface 的 IP/netmask； 依赖 VMM 重写既有 TAP 地址的环境需要显式复核。
  • TX EIO 语义变化：旧版把它传播为 device error；B 丢帧并计数。监控若 只看 VM 是否退出，会漏掉持续丢包，必须读取 tx_dropped_frames。
  • pause/resume API 行为变化：依赖旧 Task::Pause/Resume 原地恢复的调用方在 B 会收到明确错误，必须走 PauseToSnapshot + create-from-snapshot。
  • snapshot/设备格式兼容：本文证明的是代码路径变化，没有证明 A 快照可以由 B 无条件恢复；CPU/中断、ivshmem、独立 agent image 与设备 state 仍需各自 compatibility gate。

优点与代价

  • 工程判断：保持进程内控制降低了版本迁移时的 transport 变量，但全局 VMM_SERVICE 与阻塞 response 仍是单点卡住风险。
  • 工程判断：passfd 把 stdio fd 所有权显式送入 vsock muxer，减少 legacy stream relay 层；同时增加同 UID 校验、批次原子性、动态 port、timeout 与 restore reconnect 的复杂度。
  • 工程判断：TAP EIO 丢帧更接近链路暂时 down 时的容错，但把故障从 fail-fast 改成可持续数据丢失，必须依赖计数器与上层健康检查。
  • 工程判断：移除 driver_awake 简化中断语义，却也删掉了一个明确针对 restore 首轮通知的保护；没有实测不能判断净收益。

架构边界（x86_64 / ARM64）

三个版本的控制 service、vsock muxer、TAP pool 与 virtio-net queue worker 都 不是按目标架构分叉的。架构差异位于外围：

  • A/B 的 wrapper 分别为 x86_64 与 ARM64 添加不同 seccomp syscall；
  • guest cmdline 分别使用 x86 hvc0/no_timer_check 与 ARM64 ttyAMA0；
  • used-ring interrupt 下游进入 x86 APIC/IOAPIC/MSI 或 ARM GIC/MSI；
  • v0.6.0 的 host-page-size 修正会影响 64 KiB ARM64 host 的 snapshot dirty-page 解释，但没有新增一条 ARM64 专属 socket。

B 的 passfd、TAP EIO 与 driver_awake 变化是共享源码变化；“ARM64 更受益或 更易回归”均属未确认，需要同场景运行证据。

未确认项与运行验证边界

  • 未确认任何版本的吞吐、延迟或 CPU 收益；perf(passfd) 只是提交作者命名。
  • 未确认 B 的标准部署是否设置 cube.use_passfd_io=true。
  • 未确认 driver_awake 删除对 ARM64/x86 restore 第一包的真实影响；不得把它 自动并入已 deferred 的 ARM64 2-vCPU restore 根因调查。
  • 未确认 A snapshot 到 B 的跨版本兼容；本报告不是 snapshot format compatibility 声明。
  • 未确认生产 chapi/cube.sock/cubetap.sock 的权限、SELinux、namespace 与 systemd/containerd 配置；源码路径不是部署事实。
  • 未运行 benchmark、KVM、远端或网络实验；因此所有收益/风险只保持为工程判断 或待验证候选。
