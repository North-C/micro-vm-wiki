AgentENV 架构层级与运行时边界

问题与结论

问题：AgentENV 在 Micro-VM、runtime 与沙箱平台的层级中是什么，它负责哪些状态，哪些能力仍属于底层 VMM 或宿主机？

结论：在固定提交 00ba6cb74f309a0cbd65f6ec415640e9e674a371 中，AgentENV 是组织 API、sandbox orchestration、snapshot/template、Firecracker backend、ublk/OverlayBD 和可选分布式服务的沙箱平台。它消费 Firecracker/KVM 等底层能力，但不是与 Firecracker、Cloud Hypervisor 同层的 VMM。

本文只确认固定源码中的组件装配、接口和检查逻辑。没有运行 AgentENV、Firecracker、ublk 或 OverlayBD，也没有重新验证整个来源工作树当前是否 clean，因此页面状态保持 unconfirmed。

一、平台层如何装配

server 启动入口按依赖顺序建立 P2P/OverlayBD runtime、全局 ublk manager、Firecracker pool、SnapshotManager、TemplateBuilder、FirecrackerSandboxFactory、Orchestrator、observability 与 Axum API。这个顺序说明 API 并不直接创建 microVM；API 之下还有编排、持久化状态解析和具体 backend。

证据：src/bin/server.rs:70-141。

关停则按 reporter、orchestrator、Firecracker pool、ublk daemon、OverlayBD P2P、P2P transport 的顺序收敛。这里的工程含义是：上层先停止产生新工作，再关闭下层共享资源；它不是“进程退出即可保证所有远端 artifact durable”的证明。

证据：src/bin/server.rs:145-195。

二、状态所有权分层

API 与 Orchestrator

API 负责协议入口和请求转换；Orchestrator 管 sandbox 生命周期状态、并发操作和失败收敛。具体 microVM start/pause/resume/snapshot/fork 则通过 SandboxBackend contract 下沉到 Firecracker 实现。

这一层次在 Sandbox 生命周期与 E2B-shaped API 链路 中展开。

Snapshot、Template 与 repository

SnapshotManager 把 backend 捕获结果发布为 committed snapshot；repository 是 durable truth，runtime resolver 将 committed record 解析成节点本地可运行路径。Template 是 committed snapshot 之上的用户接口与构建流程，而不是另一种独立 VM 状态格式。

证据：

  • SnapshotManager::publish_captured, src/snapshot/manager.rs:87-128
  • repository interfaces, src/snapshot/repository/interfaces.rs:80-200
  • TemplateBuilder, src/template/builder.rs:20-145

Firecracker、OverlayBD 与 ublk

Firecracker backend拥有 microVM 生命周期；OverlayBD承载可提交的分层 artifact；ublk manager把相应块设备暴露给运行时。三者是协作关系，不能把 OverlayBD/ublk 的存储状态当作 Firecracker 完整设备状态，也不能把 VMM snapshot 文件当作已经发布的 Template。

详见 Snapshot、Template、OverlayBD 与 ublk 链路。

三、虚拟化模式与架构边界

Virtualization 是 node-wide 的 Kvm | Pvm 枚举，默认值是 KVM。dependency resolver 只接受 x86_64 与 aarch64；PVM 分支明确限制为 x86_64。host check 同时检查 /dev/kvm 可访问性，以及 PVM mode 与 kvm_pvm module 是否匹配。

证据：

  • src/virtualization.rs:3-30
  • src/setup/deps.rs:74-99
  • src/setup/kvm.rs:44-80

这些是 Local source fact：源码存在分支和 fail-closed check。它们不是“本文在 ARM64 或 PVM 上运行通过”的 runtime evidence。

四、多节点控制面放在哪里

Gateway 对已有 sandbox 查询 node，对新请求请求 schedule，再把请求代理到选定节点；Scheduler 先按 observed node/resource limit 过滤，再用 strategy 选择节点。binding 由 assignment 与 heartbeat roster 协调。

证据：

  • services/gateway/internal/server.go:92-230
  • services/scheduler/internal/service.go:81-242

工程判断：多节点 gateway/scheduler 是平台扩展面，不是理解单节点 sandbox create 的前置条件，因此本轮只在总览中定位，不另建公开页面。
