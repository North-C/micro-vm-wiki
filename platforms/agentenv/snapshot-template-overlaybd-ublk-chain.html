AgentENV Snapshot、Template、OverlayBD 与 ublk 链路

问题与结论

问题：AgentENV 的 snapshot/template 保存什么，memory、rootfs 与 attached drive 如何分层、提交、解析和恢复？

结论：固定提交 00ba6cb74f309a0cbd65f6ec415640e9e674a371 把 backend capture、committed repository record 与 node-local runnable state明确分层。Firecracker捕获 VM state/memory，AgentENV把 sparse/dirty memory转换成 sealed OverlayBD layer，并通过 repository记录 rootfs、drive、memory和runtime版本；ublk负责节点块设备。P2P只是 artifact 获取加速，不是 committed truth。Template则是 committed snapshot之上的用户接口与构建流程。

本文没有执行 snapshot、restore、ublk、OverlayBD、P2P 或 object-storage测试，页面保持 unconfirmed。

一、三个不同状态层

这四个对象不能混为“snapshot”：

  1. live sandbox 包含运行时 fd、worker 和设备对象；
  2. captured handle 是 backend交给上层的 opaque捕获结果；
  3. committed record 是repository中的持久化真相；
  4. runnable snapshot 是resolver在当前节点物化的路径和配置。

SnapshotManager::publish_captured 只接受可 downcast为 FirecrackerCapturedSnapshot 的 handle，先向repository发布，再best-effort发布P2P artifacts。

证据：src/snapshot/manager.rs:87-128。

二、Firecracker 捕获与 memory layer

Firecracker client创建 diff snapshot；memory可以落到 sparse mem.bin，也可以把 dirty ranges直接交给 AgentENV 打包。Restore路径支持 file-backed memory backend。

证据：src/sandbox/firecracker/instance.rs:455-550。

convert_sparse_mem_to_overlaybd 与 convert_dirty_memory_to_overlaybd 把 memory变成 sealed OverlayBD layer；实现对 range做 4 KiB alignment/segment mapping检查。

证据：

  • 4 KiB dirty-page 与 OverlayBD alignment 常量，src/sandbox/firecracker/overlaybd_snapshot.rs:40-41
  • sparse/dirty memory 转换与 range/segment 校验，src/sandbox/firecracker/overlaybd_snapshot.rs:670-844

合理推断：memory layer与rootfs layer都可由repository管理，不表示两者使用相同dirty tracking语义；页面不会把“存储层格式相似”外推成“写入来源相同”。

三、committed snapshot 记录什么

Committed snapshot结构包含runtime versions、virtualization mode、image configs、rootfs layers、attached-drive layers、memory layers，以及可选publication/custom-extension metadata。

证据：src/snapshot/types/snapshot.rs:284-337。

Repository interface明确区分 durable record与runtime resolution：resolver把committed snapshot转换为node-local runnable paths，但不得反向修改repository truth。

证据：src/snapshot/repository/interfaces.rs:80-200。

四、POSIX、OSS 与 P2P

POSIX resolver物化memory、rootfs和attached-drive runtime config，再hydrate Firecracker manifest。

证据：

  • src/snapshot/repository/backends/posixfs/runtime.rs:54-110
  • src/snapshot/repository/backends/posixfs/runtime.rs:288-324

OSS resolver对fixed artifacts可先尝试P2P，失败后回退object storage，并从committed layers物化memory/rootfs。

证据：src/snapshot/repository/backends/oss/resolver.rs:98-180。

因此“P2P是加速路径而不是提交真相”是由resolver fallback和repository contract支持的 inference；本文没有测试P2P故障或remote consistency。

五、ublk 与 live runtime 修改

ublk device manager通过daemon创建和管理block device。Restack snapshot若已经改变live runtime，失败会被分类为terminal，而不是假设原backend仍安全可用。

证据：src/sandbox/ublk/device.rs:391-439。

这个边界说明rollback不能只看repository metadata：一旦节点的live block stack发生不可逆变化，上层状态也必须按terminal failure收敛。

六、Template 是 committed snapshot 的上层语义

TemplateBuilder在committed snapshot之上组织build/publish。固定提交的upstream concepts文档也把template解释为committed snapshot的用户侧wrapper。

证据：

  • src/template/builder.rs:20-145
  • docs/src/concepts/templates.md:1-17
  • docs/src/concepts/templates.md:130-139

第一条是 Local source fact，后两条是 upstream-doc observation。本文不复制上游quickstart或完整template命令。

七、virtualization mode compatibility

Committed snapshot记录capture时的virtualization mode。Create、resume与Firecracker config会拒绝跨KVM/PVM mode恢复；仓内单测覆盖不匹配情况。

证据：

  • src/orchestrator/service.rs:359-371
  • src/orchestrator/service.rs:1270-1277
  • src/sandbox/firecracker/config.rs:471-489
  • src/orchestrator/tests.rs:3549-3605
  • src/sandbox/firecracker/config.rs:946-966

测试代码存在不等于本任务执行通过。
