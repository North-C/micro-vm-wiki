E2B-infra Template：NBD Rootfs、UFFD Memory 与发布完成点

问题与结论

问题：E2B-infra 的Template如何分别处理rootfs和memory，save时哪些动作构成一致性边界，本地ready与远端publish完成又有什么不同？

结论：稳定版 2026.29@557445ffddda8d9a27f6f529a3f4d7732cf81a13 中，rootfs通过readonly Template base、per-sandbox sparse Cache和block.Overlay组成NBD路径；memory由独立UFFD lazy-fault与dirty/empty状态管理。Save需要pause并drain/flush disk，再移交cache ownership、关闭/等待NBD、导出diff。Local Template可用不等于远端artifact upload完成；只有upload流程成功返回才能证明该次远端发布完成。

本文没有执行NBD、UFFD、save、filesystem-only、upload或故障注入测试，状态保持 unconfirmed。

一、rootfs 与 memory 分账

NewNBDProvider建立readonly Template base与per-sandbox sparse mmap Cache，再通过block.Overlay暴露host NBD路径。这里的overlay是E2B block abstraction，不是Linux OverlayFS，也不能推断成whole-file FICLONE。

证据：

  • packages/orchestrator/pkg/sandbox/rootfs/nbd.go:22-170
  • packages/orchestrator/pkg/sandbox/block/overlay.go:14-100

Memory由独立UFFD路径处理lazy fault与page状态，不经过rootfs Cache/Tracker。

证据：packages/orchestrator/pkg/sandbox/uffd/uffd.go:38-228。

工程判断：把rootfs和memory统称为“snapshot cache”会掩盖不同的读写来源、同步点与失败语义，应在性能/一致性分析中分开建模。

二、Cache 与 Tracker 的语义

Read miss从base满足读取，不会仅因读取就copy-up整个block。Write/zero修改per-sandbox Cache，并由tracker区分NotPresent、Dirty、Zero等状态；导出时只处理相应diff状态。

证据：

  • packages/orchestrator/pkg/sandbox/block/cache.go:51-204
  • packages/orchestrator/pkg/sandbox/block/cache.go:348-550
  • packages/orchestrator/pkg/sandbox/block/tracker.go:1-117

copy_file_range具有fallback，因此源码只能支持“优先尝试内核copy路径并可回退”的结论，不能写成“必然reflink”或“零拷贝”。

三、Save 的一致性边界

Save主路径不是单独调用EjectCache：

  1. pause microVM；
  2. drain并flush disk I/O；
  3. EjectCache移交cache ownership；
  4. 关闭NBD并等待provider退出；
  5. ExportDiff生成rootfs diff；
  6. 组织Template metadata与后续publish/upload。

证据：

  • packages/orchestrator/pkg/sandbox/sandbox.go:1316-1495
  • packages/orchestrator/pkg/sandbox/sandbox.go:1660-1698

合理推断：一致性依赖pause与disk drain/flush先于cache ownership handoff；只看到EjectCache调用不能证明前序写入已经静止。

四、filesystem-only 与 DirectProvider

Filesystem-only路径跳过memory snapshot，但仍执行disk drain/flush与rootfs diff。DirectProvider是独立实现，不拥有NBD Cache/Tracker，因此不能把NBD的copy-on-write与tracker结论直接套用到DirectProvider。

证据：

  • packages/orchestrator/pkg/sandbox/sandbox.go:1316-1495，save/filesystem-only分支；
  • DirectProvider, packages/orchestrator/pkg/sandbox/rootfs/direct.go:23-168。

本文没有对不同provider运行A/B或故障注入，因此实际性能、crash consistency和回退行为均未确认。

五、本地 ready 与远端 durable publication

Local Template cache可以在本地artifact就绪后供节点使用；remote upload则由独立upload流程异步完成。只有Upload.Run成功，才能说明该次remote artifact upload完成。Local ready较早不应被描述为“所有远端副本已durable”。

证据：

  • Upload.Run/Wait/Finish, packages/orchestrator/pkg/sandbox/build_upload.go:121-173；
  • packages/orchestrator/pkg/sandbox/sandbox.go:1660-1698 — save/publish衔接。

这里的完成点是 Local source fact + inference：源码区分local cache与upload流程；“系统在任意故障下达到某种分布式durability级别”仍需运行证据。
