E2B-infra 架构与 Sandbox 创建、恢复链路

问题与结论

问题：E2B-infra 的 API、placement、node orchestrator、Firecracker 与 envd 如何协作，把请求变成可路由的 sandbox？

结论：在稳定版 2026.29、固定提交 557445ffddda8d9a27f6f529a3f4d7732cf81a13 中，请求由 API handler进入 API orchestrator与placement，再通过node manager RPC到node orchestrator。Node侧组合Template配置、NBD rootfs、UFFD memory、network slot、Firecracker与envd；根据可用artifact选择snapshot resume、filesystem-only reboot或cold build，最后才进入ready/routing阶段。

本文是固定源码与已审查研究的纵向整理。没有在本任务中启动E2B、Firecracker或envd，也没有执行云部署、ARM64交付或API E2E，因此状态保持 unconfirmed。

一、控制面分层

API create handler负责解析请求、并发/模板输入与上层错误；API orchestrator负责create instance流程；placement实现Best-of-K候选选择。它们与node-side sandbox状态机是不同所有权域。

证据：

  • packages/api/internal/handlers/sandbox_create.go:59-336
  • packages/api/internal/orchestrator/create_instance.go:138-394
  • packages/api/internal/orchestrator/placement/placement_best_of_K.go:15-190

工程判断：E2B-infra 应归入沙箱基础设施层，而不是第六个VMM。Placement、catalog和API语义属于平台控制面；Firecracker仍负责microVM边界。

二、node create 与启动来源选择

Node manager server接收sandbox请求并进入node orchestrator；后者根据Template/artifact状态选择恢复或构建路径。

证据：packages/orchestrator/pkg/server/sandboxes.go:75-280。

Sandbox实现中可见三类主要路径：

  1. memory与VM state齐备时走snapshot resume；
  2. filesystem-only条件下走reboot语义，不恢复memory snapshot；
  3. 缺少可恢复artifact时进入cold build/create。

证据：

  • packages/orchestrator/pkg/sandbox/sandbox.go:446-699
  • packages/orchestrator/pkg/sandbox/sandbox.go:753-1165
  • packages/orchestrator/pkg/sandbox/reboot.go:33-155

这里的“选择”不表示三条路径行为完全等价：filesystem-only不会恢复memory，但仍需维护rootfs与设备状态边界。

三、rootfs、memory 与 network 不是同一种缓存

Node侧使用NBD provider构造rootfs链，用UFFD处理memory lazy fault，并从network pool取得网络slot。三个subsystem服务不同数据和生命周期：

  • NBD/rootfs：只读Template base + per-sandbox sparse cache/overlay；
  • UFFD/memory：按page fault加载memory，并独立跟踪dirty/empty状态；
  • network slot：分配node侧network资源，供Firecracker/guest路径使用。

证据：

  • packages/orchestrator/pkg/sandbox/rootfs/nbd.go:22-170
  • packages/orchestrator/pkg/sandbox/uffd/uffd.go:38-228
  • packages/orchestrator/pkg/sandbox/network/pool.go:24-233

Local source fact是三套实现与状态结构彼此独立；“不能把它们统称为一个snapshot cache”是避免所有权混淆的 engineering judgment。

四、Firecracker 与 envd readiness

E2B-infra封装Firecracker process/client，负责配置、启动、pause/resume与snapshot API交互；envd初始化发生在VM恢复/启动之后，并参与sandbox ready语义。

证据：

  • packages/orchestrator/pkg/sandbox/fc/process.go:159-667
  • packages/orchestrator/pkg/sandbox/fc/client.go:42-166
  • packages/orchestrator/pkg/sandbox/fc/client.go:215-240
  • packages/orchestrator/pkg/sandbox/fc/client.go:319-435
  • packages/orchestrator/pkg/sandbox/envd.go:259-335

Catalog在Redis中维护sandbox routing记录，供后续请求找到node；它不等于Firecracker内部VM state。

证据：packages/shared/pkg/sandbox-catalog/catalog_redis.go:26-113。

五、部署配置和运行事实的边界

固定仓库包含AWS/GCP Terraform与Nomad交付配置。这证明上游维护了相应IaC路径，但本文没有读取或复制Secret-adjacent变量值，也没有执行部署。

证据：

  • iac/provider-aws/main.tf:1-41
  • iac/provider-gcp/main.tf:1-33

“固定仓库存在云IaC配置”是 Local source fact；“本任务验证过云部署、容量与ARM64交付”仍是 unconfirmed。本文没有使用upstream文档声明支撑运行结论，因此没有把 upstream-doc observation 列为本页证据类别。
