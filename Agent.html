    Micro-VM Agent Instructions

    本文档约束后续在 /home/lyq/Projects/Micro-VM 中进行 Micro-VM 源码阅读、架构解析、功能对比、ARM64 适配分析和图表生成的工作方式。

    目标范围

    主要关注以下五个项目：

    • firecracker: 极简 Rust/KVM VMM，面向 serverless/container microVM。
    • CubeSandbox: 基于 RustVMM/KVM 的 AI Agent sandbox 系统，包含控制面、VMM、guest agent、网络和部署链路。
    • cloud-hypervisor: RustVMM 系 VMM，面向现代 cloud workload，支持热插拔和迁移等能力。
    • crosvm: ChromeOS/Android 生态 VMM，强调进程级设备隔离、sandbox 和多后端。
    • kata-containers: 轻量 VM 容器运行时系统，重点是 runtime、agent、shim、hypervisor 集成和容器编排接口。

    其他目录只作为背景或验证辅助引用，例如：

    • kernel: 仅在解释 KVM、virtio、guest kernel config、ARM64/x86 内核机制时引用。
    • E2B-infra、e2b-infra-openeuler-arm64: 仅在解释 CubeSandbox/E2B 兼容接口或部署背景时引用。

    不要把上述辅助项目纳入主线横向比较，除非用户明确要求。

    工作原则

    • 默认使用中文输出；代码符号、文件名、配置项和命令保持原文。
    • 结论必须从当前工作区源码、配置、测试或项目文档出发。不要只凭外部常识判断功能是否支持。
    • 每个关键结论都要给出依据，优先引用 文件路径:行号、函数/类型/trait 名、配置项、测试用例或构建脚本。
    • 区分事实、源码推断和工程判断。无法从源码确认时明确写“未在当前源码中确认”，不要补全想象中的实现。
    • 面向用户的解释要聚焦“机制如何工作”和“为什么不同”，避免只罗列目录或 README 摘要。
    • 不默认修改源码。除非用户明确要求实现、修复、重构或补测试，否则以分析、文档和图表输出为主。
    • 尊重各子项目已有 AGENTS.md、贡献规范和工作区脏状态；不得回滚用户已有改动。

    Claude Code 协作方式

    后续研究以主线程规划和审阅为主，Claude Code 作为源码阅读和文档材料生产的主要执行者。

    主线程职责：

    • 选择研究路线，拆分问题，限定项目、目录、文件和符号范围。
    • 给 Claude Code 下发只读源码解析、文档初稿或文档审阅任务。
    • 交叉核验 Claude Code 输出，只采纳能被当前源码、配置、测试或项目文档支撑的结论。
    • 组织最终文档结构，修正逻辑顺序、术语、证据索引、图表和能力边界。
    • 运行 Markdown、链接、未完成标记和关键源码锚点校验。

    Claude Code 职责：

    • 执行限定范围内的代码阅读，输出入口函数、关键结构、调用链、状态机、架构差异和能力边界。
    • 为专题文档提供中文材料、草稿或审阅意见。
    • 每个重要判断必须给出文件、行号、符号名和明确结论。
    • 不做无边界的全仓库泛读；不修改源码；是否写入最终文档由主线程决定。

    当前暂缓范围：

    • Kata Containers 的 CoCo、confidential guest、TDX、SEV、SNP、CCA 等机密计算路径暂不安排深入分析。
    • 已有跨项目或其他项目的受保护 VM 文档可以保留，但后续不要把 Kata CoCo 作为新专题推进，除非用户重新要求。
    • 该暂缓只针对 Kata Containers；Cloud Hypervisor 与 crosvm 已有的 CoCo、protected VM、pVM 路线不受此限制。

    根目录没有统一 CodeGraph 索引，各主项目通常有各自 .codegraph/。进行结构性源码分析时必须优先使用 CodeGraph，并显式传入 projectPath：

    • /home/lyq/Projects/Micro-VM/firecracker
    • /home/lyq/Projects/Micro-VM/CubeSandbox
    • /home/lyq/Projects/Micro-VM/cloud-hypervisor
    • /home/lyq/Projects/Micro-VM/crosvm
    • /home/lyq/Projects/Micro-VM/kata-containers

    使用规则：

    • 架构、调用链、符号定义、影响面问题：先用 codegraph_context、codegraph_trace、codegraph_callers、codegraph_callees、codegraph_impact。
    • 查看多个相关符号源码：用一次 codegraph_explore，不要循环读取许多文件。
    • 查文件树：用 codegraph_files。
    • 查字面量、日志文本、文档段落、配置字符串：使用 rg 或直接读取具体文件。
    • 如果某项目 CodeGraph 未初始化，先告知用户并询问是否运行 codegraph init -i，不要静默初始化。
    • 写入文件后不要立即依赖 CodeGraph 读取同一变更，文件 watcher 可能有短暂延迟。

    分析流程

    处理任何 Micro-VM 架构或功能问题时，按以下顺序推进：

    1. 明确问题涉及的项目、组件、功能和架构范围，默认比较 arm64/aarch64 与 x86_64。
    2. 用 CodeGraph 找入口点、核心类型、调用链和影响面。
    3. 阅读必要的源码、配置、测试和设计文档，记录证据位置。
    4. 还原关键流程，例如 VM 创建、内存初始化、vCPU 启动、设备注册、virtio 队列处理、API 请求、snapshot/restore、网络接入、容器生命周期。
    5. 对比 ARM64 与 x86 的分歧点，只写能由源码或文档支撑的差异。
    6. 输出结论、图表、证据表和未确认点。

    ARM64 与 x86 对比维度

    比较不同 Micro-VM 时，优先检查以下维度：

    • 架构入口：aarch64、x86_64 目录、build tags、Cargo features、target triples、条件编译。
    • 启动方式：direct kernel boot、PVH/bzImage、PE/EFI、FDT、ACPI、kernel cmdline、initrd/rootfs 装载。
    • CPU 模型：CPUID/MSR、CPU template、AArch64 feature register、PMU、cache topology、SMT/NUMA 暴露。
    • vCPU 初始化：KVM vCPU 创建、寄存器设置、reset state、MP boot、PSCI、interrupt injection。
    • 中断模型：x86 APIC/IOAPIC/MSI/MSI-X 与 ARM GIC/GICv3/ITS、irq routing、virtio interrupt 映射。
    • 内存模型：guest physical address layout、MMIO hole、dirty bitmap page size、balloon/hotplug、snapshot 内存恢复。
    • 设备模型：virtio-mmio、virtio-pci、vhost-user、vfio、vsock、block、net、fs、rng、pmem、console。
    • 安全隔离：seccomp、jailer/minijail、namespace、capability、device process、Kata sandbox 边界。
    • 生命周期能力：create/start/pause/resume/shutdown、snapshot/restore、live migration、clone/fork、hotplug。
    • 网络路径：tap、vhost-net、slirp、eBPF/CubeVS、policy/egress、guest agent ready 信号。
    • 容器集成：OCI/runtime/shim/agent、containerd、Kata agent 协议、E2B 兼容 API。
    • 性能路径：启动延迟、内存开销、page fault/CoW、I/O datapath、vCPU pinning、NUMA、perf/PMU 可观测性。
    • 构建部署：native/交叉编译、镜像资产、kernel config、one-click 包、目标宿主机要求。

    • arch、vmm、hypervisor、virtio-devices、vm-migration。

    • ARM64 与 x86 在设备暴露、boot、interrupt、sandbox 规则上的差异。

    kata-containers

    重点关注：

    • runtime、shim、agent、virtcontainers、hypervisor driver、配置模板和 OCI/containerd 集成。
    • src/runtime、src/agent、src/runtime/virtcontainers、src/runtime/virtcontainers/pkg/*。
    • 与 Firecracker、Cloud Hypervisor、QEMU、crosvm 等 hypervisor 的适配层差异。
    • ARM64 与 x86 在 hypervisor 配置、kernel/image、machine type、virtio transport 和 host capability check 上的差异。

    图表输出规范

    用户要求架构图、流程图、组件图时，优先使用 Mermaid。图表必须来自源码分析结果，而不是抽象想象。

    常用图类型：

    • 架构图：flowchart TB 或 flowchart LR，展示控制面、VMM、guest、host kernel、设备、网络和存储。
    • 关键流程图：sequenceDiagram，展示 API 调用、VM 创建、vCPU 启动、设备 I/O、snapshot/restore、sandbox 创建等时序。
    • 组件图：flowchart 或 classDiagram，展示模块职责、核心类型和调用关系。
    • 状态机：stateDiagram-v2，展示 VM/container 生命周期。
    • 对比表：用于横向比较功能支持、架构差异、证据路径和限制。

    每张图后必须附上“证据索引”，列出支撑图中关键节点/边的文件、函数、类型或配置。没有证据的边不要画成确定调用关系，可标注为“推断”。

    证据标准

    优先级从高到低：

    1. 当前源码中的函数、类型、trait、接口实现、条件编译和测试。
    2. 当前仓库内配置、构建脚本、CI、文档。
    3. 当前仓库内 benchmark、实验报告和日志。
    4. 外部官方文档或上游 issue，仅作为背景或版本信息，不能覆盖本地源码事实。

    引用本地文件时使用可点击路径和行号。若同一结论跨多个项目，分别给出每个项目的证据，不要用一个项目的实现推断另一个项目。

    验证与命令

    执行命令前说明目的。优先使用只读命令：

    • git status --short --branch
    • rg
    • sed -n
    • find
    • CodeGraph 工具

    需要构建或测试时，先根据项目选择最小可验证命令；涉及 root、KVM、网络、远端 ARM64 机器、长时间 benchmark 或大量下载时，先说明影响和前置条件。

    禁止事项

    • 不要把 README 宣称直接当作实现事实。
    • 不要在没有源码证据时断言某功能“支持”或“不支持”。
    • 不要混淆 arm64、aarch64、x86_64、amd64 的命名上下文。
    • 不要把 QEMU/KVM/Linux 通用机制直接套到 Firecracker、crosvm、Cloud Hypervisor 或 CubeSandbox 的具体实现。
    • 不要为图表美观补充不存在的组件或调用边。
    • 不要提交 Signed-off-by。CubeSandbox 内提交或 PR 必须遵守其 AGENTS.md 的 AI attribution 要求。
