    Cloud Hypervisor 存储 / rootfs / share-fs 边界链路

    本文承接 I/O 设备数据面、设备创建矩阵 和 DeviceTree/热插拔/Restore，收成一个问题：CH 的存储、rootfs、share-fs 边界在哪。

    源码基线：当前工作树。

    相关：横向 存储/rootfs/share-fs、资源管理与 QoS。

    0. 术语与背景

    CH 存储是 VMM 级设备暴露，不是 runtime 级 rootfs

    CH 的存储语义比 Firecracker 宽，但仍是 VMM 级设备暴露语义，不是 container runtime 级 rootfs 语义。它保证"设备被暴露给 guest"，不负责 guest 内 mount 完成，也不负责 container rootfs 语义。

    三类存储设备，配置对象不同

    设备 配置对象 rootfs? share-fs?
    block DiskConfig（path/readonly/num_queues/vhost_user/image_type...） 是（最常见 rootfs 载体） 否
    fs FsConfig（tag/socket/num_queues） 否 是（vhost-user + virtio-fs）
    pmem PmemConfig（file/size/discard_writes） 是（memory-backed） 否

    关键边界概念

    • share-fs 不是内建 host 目录扫描——CH 通过 FsConfig.socket 连外部 backend（如 virtiofsd），把 virtio-fs 设备暴露给 guest。无 socket 就无此能力。
    • 运行期 add 不是裸热插——disk/fs/pmem 都先 clone VmConfig + 加设备 + config.validate() 校验通过才进 Vm.add_*()。
    • 运行期 add 会回写 VmConfig——确保 reboot/restore 后设备继续存在。
    • pmem ≠ 另一块磁盘——它是 memory-mapped 设备，restore 时复用既有 MMIO 区间。

    1. 核心结论

    CH 把 disk/fs/pmem 都建模成可校验、可热插、可恢复的 VMM 设备，但不把 guest 内 mount 与容器 rootfs 语义纳入自身责任。

    2. 整体链路

    flowchart LR API["vm_add_disk / vm_add_fs / vm_add_pmem"] --> VMM["Vmm"] VMM --> Config["clone + validate VmConfig"] Config --> VM["Vm.add_*"] VM --> DM["DeviceManager"] DM --> Virtio["virtio-block / virtio-fs / virtio-pmem"] Virtio --> Guest["guest sees storage device"]

    3. rootfs：disk 与 pmem（配置对象）

    rootfs 表达本质是不同设备配置对象，不是统一的 guest mount 协议。

    4. share-fs：FsConfig（外部 backend 协议）

    // vmm/src/vm_config.rs:461
pub struct FsConfig {
    pub tag: String, pub socket: PathBuf,
    pub num_queues: usize, pub queue_size: u16,
    pub id: Option<String>, pub pci_segment: u16,
}

    CH 的 share-fs 不自己扫 host 目录——通过 socket 连外部 backend，再把 virtio-fs 暴露给 guest。无 socket 就无 share-fs 能力。

    5. 运行期 add：disk/fs/pmem（先校验再热插）

    vm_add_disk/vm_add_fs/vm_add_pmem 三者模式一致——clone VmConfig + 加设备 + validate，校验通过才进 Vm.add_*()：

    // vmm/src/lib.rs:2257
fn vm_add_disk(&mut self, disk_cfg: DiskConfig) -> result::Result<Option<Vec<u8>>, VmError> {
    self.vm_config.as_ref().ok_or(VmError::VmNotCreated)?;
    {
        let mut config = self.vm_config.as_ref().unwrap().lock().unwrap().clone();  // clone
        add_to_config(&mut config.disks, disk_cfg.clone());
        config.validate().map_err(VmError::ConfigValidation)?;                      // 先校验
    }
    if let Some(ref mut vm) = self.vm {
        let info = vm.add_disk(disk_cfg)?;                                          // 校验过才热插
        serde_json::to_vec(&info).map(Some)
    } else {
        let mut config = self.vm_config.as_ref().unwrap().lock().unwrap();          // VM 未建 → 只更新 config
        add_to_config(&mut config.disks, disk_cfg);
        Ok(None)
    }
}

    运行期存储能力不是裸热插——先经一层完整配置校验。vm_add_fs/vm_add_pmem（:2282/2340）同构。

    6. Vm.add_* 的边界（创建 + 回写 config + 通知）

    Vm::add_disk() 做两件事：DeviceManager 创建并热插设备 + 把设备回写 VmConfig：

    // vmm/src/vm.rs:2092
pub fn add_disk(&mut self, mut disk_cfg: DiskConfig) -> Result<PciDeviceInfo> {
    let pci_device_info = self.device_manager.lock().unwrap().add_disk(&mut disk_cfg)?;  // 创建+热插
    // Update VmConfig by adding the new device. This is important to ensure the device would be created in case of a reboot.
    { add_to_config(&mut self.config.lock().unwrap().disks, disk_cfg); }                 // 回写 config
    self.device_manager.lock().unwrap().notify_hotplug(AcpiNotificationFlags::PCI_DEVICES_CHANGED)?;  // ACPI 通知
    Ok(pci_device_info)
}

    回写 config 很关键——运行期 add 不是临时状态，reboot/restore 后设备继续存在。

    7. DeviceManager 三条设备构造路径

    make_virtio_block_device/make_virtio_fs_device/make_virtio_pmem_device 明确分开（device_manager.rs:2600）——存储面不是"大 storage 设备"抽象，是三种不同设备能力面，最终都走统一 PCI hotplug，但构造逻辑不同。

    share-fs 边界很清楚：没有 socket 就没有这条能力——不是内建 host directory walker，是外部 backend 协议。

    pmem ≠ 另一块磁盘——和 block 边界不同，尤其在 restore 路径（复用 MMIO 区间）和 memory-mapped 语义上更接近持久内存。

    8. 与 Firecracker / Kata 的差异

    维度 Firecracker Cloud Hypervisor Kata
    运行期 add 只改已有设备字段 disk/fs/pmem 显式 add（校验后） runtime + agent
    share-fs 无 FsConfig + vhost-user share_rootfs/share_volume → agent
    设备矩阵 精简 宽 hypervisor 设备
    guest mount 语义 设备暴露 设备暴露 guest 挂载/runtime 语义

    CH 边界恰好在中间：比 Firecracker 更通用，比 Kata 更底层（缺 guest agent Storage 翻译层）。

    9. ARM64 与 x86_64

    DiskConfig/FsConfig/PmemConfig 模型本身不按架构分叉。分叉在 PCI/MMIO 暴露、ACPI/FDT 设备描述、guest firmware/kernel 如何理解这些设备。ARM64 上要额外注意：guest 是否真能按 ARM64 路径发现并使用这些设备。

    10. 结论

    CH 把 disk/fs/pmem 都建模成可校验、可热插、可恢复的 VMM 设备，但不把 guest 内 mount 与容器 rootfs 语义纳入自身责任。后续应把 disk/fs/pmem 各自的运行期与 restore 边界、ARM64 guest 发现与使用证据压得更实。
