    Cloud Hypervisor ARM64 网络观测指南

    本文承接 ARM64 网络能力边界矩阵。

    前一篇回答“ARM64 网络边界在哪里”。

    本文继续回答“Cloud Hypervisor ARM64 网络出问题时，最先会在哪一层暴露，以及该看哪些源码锚点”。

    源码基线：当前工作树。

    1. 核心结论

    Cloud Hypervisor ARM64 网络问题通常会在四层里的某一层先暴露：

    1. host 配置与 vm_add_net() 校验层。
    2. TAP/backend 打开与启用层。
    3. ARM64 FDT/GIC/ITS 描述层。
    4. guest 枚举与 virtio-net 实际激活层。

    它不是“一上来就看 guest 网卡”的问题。

    如果排查顺序反过来，很容易把 host 配置错误误判成 guest driver 问题，或者把 GIC/ITS 中断问题误判成 net device 创建失败。

    2. 总体观测图

    flowchart TB Config["vm_add_net / DeviceManager::add_net"] --> Tap["tap/backend open + enable"] Tap --> FDT["FDT + PCI host bridge + GIC"] FDT --> Guest["guest virtio-net visible"] Guest --> Activated["virtio-device activated / queue path"]

    这四层是单向依赖。

    前一层没过，后一层大多只会留下连带症状。

    3. 第一层：vm_add_net() 最早会暴露什么

    运行期新增网卡统一从 vm_add_net() 进入。

    如果 VmConfig 克隆校验失败，它会在 ConfigValidation 阶段直接返回。

    源码依据：lib.rs。

    如果 VM 已存在，但真正加设备失败，会打：

    Error when adding new network device to the VM: ...

    源码依据：lib.rs。

    这类错误说明问题还停留在 host 配置或设备创建层。

    还不需要先怀疑 guest 内枚举。

    4. 第二层：IOMMU segment 问题在这里最先暴露

    DeviceManager::add_net() 对 net_cfg.iommu 有最直接的架构无关校验。

    如果配置要求 IOMMU，但当前 pci_segment 不是 IOMMU segment，就返回：

    InvalidIommuHotplug

    源码依据：device_manager.rs。

    在 ARM64 上，这类错误尤其值得优先看。

    因为它说明根本还没到 FDT/GIC/guest 枚举阶段，先是设备组合就越界了。

    如果这里已经报错，再去盯 guest driver 没意义。

    5. 第三层：TAP/backend 失败会怎样暴露

    Cloud Hypervisor 普通 net 路径最终要打开并启用 tap。

    open_tap() 相关错误已经细分成：

    1. MultiQueueNoTapSupport
    2. MultiQueueNoDeviceSupport
    3. TapOpen
    4. TapSetIpNetmask
    5. TapSetMac
    6. TapSetMtu
    7. TapEnable

    源码依据：open_tap.rs。

    其中最有诊断价值的是：

    1. multiqueue 期望与 tap 实际能力不一致。
    2. tap 接口已存在但 IP 不会被覆盖。
    3. tap.enable() 失败。

    源码依据：open_tap.rs。

    Tap::enable() 自己的语义也很清楚。

    它通过 SIOCGIFFLAGS/SIOCSIFFLAGS 拉起接口；若 tap 已经是 UP，就直接返回成功。

    源码依据：tap.rs。

    因此这层的正确判断是：

    如果报的是 tap open/enable/multiqueue 错误，那还是 host backend 问题，不是 ARM64 FDT 或 guest 问题。

    6. 第四层：ARM64 FDT/GIC 描述问题会先暴露在哪里

    ARM64 的 guest 描述主轴是 create_fdt()。

    这里会写 root interrupt-parent，再写 CPU、memory、chosen、GIC、timer、PMU、PSCI、devices、PCI nodes。

    源码依据：fdt.rs。

    interrupt-parent 直接指向 GIC_PHANDLE。

    源码依据：fdt.rs。

    这意味着 ARM64 网络的一类失败，其实不在 add_net()。

    而在“net device 已创建，但 FDT/GIC/PCI host bridge 描述没有让 guest 正确理解它”。

    这种问题通常不会表现成设备创建报错。

    更可能表现成 guest 内网卡不出现，或者设备在 guest 内存在但中断不通。

    7. 第五层：GIC/ITS 中断路径的问题如何识别

    Gic::new() 在 ARM64 路径下会创建 VGIC，并立刻 enable()。

    源码依据：devices/src/gic.rs。

    enable() 会先启用 interrupt source group，再为 legacy IRQ 写 irq routing，最后 set_gsi()。

    源码依据：devices/src/gic.rs。

    restore 路径还会显式调用 restore_vgic() 和 set_gicr_typers()。

    源码依据：devices/src/gic.rs。

    这给了 ARM64 网络两类典型问题：

    1. 启动期 GIC/GSI 路径没真正建好，guest 枚举或中断异常。
    2. restore 后 GIC state 没真正闭环，设备存在但网络中断唤醒异常。

    如果问题只在 restore 后出现，应优先怀疑 GIC state 恢复，不应先回头怀疑 NetConfig。

    8. 第六层：guest 侧的最小成功信号是什么

    Cloud Hypervisor 自身不负责 guest 内 IP/route 配置。

    所以它的“最小成功信号”不是 agent RPC，而是 guest 至少能稳定看到并驱动 virtio-net。

    在设备层，virtio-net 激活后会打：

    virtio-device activated

    源码依据：virtio-devices/src/net.rs。

    这条信号非常重要，但也不能过度解读。

    它说明：

    1. guest driver 已完成到 activate() 的关键阶段。
    2. queue/thread 已启动。

    但它不能证明：

    1. guest 内已经配置了 IP/route。
    2. 网络中断一定在所有场景都能稳定工作。
    3. vhost-user/vDPA 等外部 backend 一定无误。

    9. 第七层：测试侧有什么现成观测点

    Cloud Hypervisor 测试基础设施里已经保留了一些 ARM64 相关 guest 观测点。

    例如：

    grep -c 'GICv3.*uart-pl011' /proc/interrupts

    以及：

    grep -c 'GICv3.*arm-pmu' /proc/interrupts

    源码依据：tests/common/utils.rs。

    虽然这两条命令不是专门给网络准备的，但它们说明了一个重要事实：

    Cloud Hypervisor 的 ARM64 验证思路本来就强调 guest 侧 /proc/interrupts 这类观测，而不是只看 host 返回值。

    同理，网络验证也应该延续这个思路：

    不仅看 add_net() 是否成功，还要看 guest 是否真的把相关中断和设备跑起来。

    10. 推荐的排查顺序

    建议把 Cloud Hypervisor ARM64 网络问题固定按下面四步排查。

    第一步：先看 vm_add_net() / DeviceManager::add_net()。

    重点看是否有 ConfigValidation、InvalidIommuHotplug、Error when adding new network device。

    第二步：再看 tap/backend。

    重点看是否有 multiqueue、tap open、tap enable 一类错误。

    第三步：再看 ARM64 FDT/GIC 路径。

    重点确认这是不是一个“设备创建成功但 guest 不理解”的问题。

    第四步：最后看 guest 侧。

    重点看是否真正出现 virtio-device activated，以及 guest 是否已经稳定看到该设备。

    11. 最小观测表

    层级 优先信号 常见失败锚点
    host config vm_add_net() 通过 Error when adding new network device
    IOMMU/segment segment 组合有效 InvalidIommuHotplug
    tap/backend tap 打开并 enable TapOpen / TapEnable / MQ mismatch
    ARM64 描述 FDT/GIC/PCI host bridge 正常 设备存在但 guest 不可见
    device activation virtio-device activated 无 activation 或后续队列不起
    restore GIC state 恢复正常 restore 后网络中断异常

    12. 结论

    Cloud Hypervisor ARM64 网络排查的关键，不是再看一遍 NetConfig 字段。

    真正重要的是知道：

    错误最早会卡在 host 配置、tap/backend、FDT/GIC 描述，还是 guest 设备激活。

    只有按这个顺序排查，ARM64 网络问题才不会被误判成“加网卡 API 失败”或者“guest 驱动有问题”这种过粗的结论。
