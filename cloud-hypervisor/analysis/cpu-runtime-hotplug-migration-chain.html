    Cloud Hypervisor CPU 运行期控制与迁移状态链路

    本文从源码追踪 Cloud Hypervisor CpuManager 在 VM boot 后的 vCPU resize、hotplug、pause/resume、snapshot 和 restore。

    源码基线：当前仓库工作树。

    相关：CPU 启动链路、运行期控制与热插拔、横向 资源管理与 QoS。

    0. 术语与背景

    CpuManager 的双重身份

    CpuManager 不只是启动期建 vCPU——它同时是：① vCPU 线程/状态/snapshot 的持有者；② guest 可见的 CPU hotplug 控制设备（实现 BusDevice）。

    CPU 热插拔是 host↔guest 协议

    方向 谁做
    插入（resize 变大） host 建/配置/启动 vCPU + ACPI/GED 通知 guest；guest ACPI driver ACK inserting 才算完成
    移除（resize 变小） host 只标记 removing + pending_removal；guest 写 eject flag 后 host 才真正 join 线程

    resize() 返回 ≠ 热插拔完成。删除是异步协作语义，不是 host 一次调用立即完成。

    三个全局 vCPU 信号 + per-vCPU 状态

    • 全局 atomic flag：vcpus_kill_signalled/vcpus_pause_signalled/vcpus_kick_signalled——vCPU 线程据此决定退出/park/注入 NMI。
    • per-vCPU VcpuState：inserting/removing/pending_removal/kill/paused ACK。

    pause 为何是 snapshot/migration 前置

    Vm::pause() 先暂停 CPU 再暂停设备/hypervisor VM；snapshot 只能在 Paused 执行。pause 时 vCPU 用 immediate_exit 再进一次 KVM_RUN 完成未完成的 PIO/MMIO exit，保证 guest state 一致——没有 pause 成功就没有一致的 vCPU state snapshot。

    1. 核心结论

    • CpuManager 既是启动期 vCPU 构造器，也是 guest 可见 CPU hotplug 设备 + vCPU 线程/状态/snapshot 持有者。
    • /vm.resize 的 CPU 部分进 Vm::resize() → CpuManager::resize()：变大建+配置+启动 vCPU 并 ACPI/GED 通知；变小只标记，等 guest eject。
    • CPU 下线不是立即杀线程：先标记 removing + pending_removal，guest 写 eject 后 host 才 stop+join。
    • pause/resume 是迁移/snapshot 前置；snapshot 只能在 Paused 执行。
    • CPU snapshot 是每 vCPU 的 hypervisor CpuState 集合；VM snapshot 聚合 CPU+memory+device。

    2. 总体链路

    flowchart LR API["/vm.resize"] --> VMM["Vmm::vm_resize"] VMM --> VM["Vm::resize"] VM --> CPU["CpuManager::resize"] CPU --> Create["create_vcpus + configure_vcpu"] CPU --> Threads["activate_vcpus / vcpu threads"] VM --> Notify["DeviceManager.notify_hotplug"] Guest["guest ACPI CPU device"] --> CPUDev["CpuManager BusDevice"]

    4. Guest 可见 CPU hotplug 设备（BusDevice）

    CpuManager 实现 BusDevice——guest 读 selection/status、写 selection/status/eject 完成热插拔协议：

    // vmm/src/cpu.rs:773  (write)
fn write(&mut self, _base: u64, offset: u64, data: &[u8]) -> Option<Arc<Barrier>> {
    match offset {
        CPU_SELECTION_OFFSET => { self.selected_cpu = /* 选 CPU id */ }
        CPU_STATUS_OFFSET => {
            // guest ACPI 写回 1 ACK inserting/removing
            if (data[0] & (1 << CPU_INSERTING_FLAG) != 0) && state.inserting { state.inserting = false; }
            if (data[0] & (1 << CPU_REMOVING_FLAG) != 0)  && state.removing  { state.removing = false; }
            // guest 写 eject flag → 触发真正删除
            if data[0] & (1 << CPU_EJECT_FLAG) != 0 { self.remove_vcpu(self.selected_cpu)?; }
        }
    }
}

    CPU hotplug completion 不在 resize() 返回时完成——guest ACPI CPU driver 要读写这个设备完成协议。CPU hotplug AML 在 x86_64 由 _SB_.PRES 设备承载（:2538）。

    5. Resize 入口

    Vm::resize() 收到 desired_vcpus 调 cpu_manager.resize()，返回 true 则 ACPI 通知 + 更新 boot_vcpus：

    // vmm/src/vm.rs:1892
pub fn resize(&mut self, desired_vcpus: Option<u32>, desired_memory: Option<u64>, desired_balloon: Option<u64>) -> Result<()> {
    if let Some(desired_vcpus) = desired_vcpus {
        if self.cpu_manager.lock().unwrap().resize(desired_vcpus)? {  // CPU resize
            self.device_manager.lock().unwrap()
                .notify_hotplug(AcpiNotificationFlags::CPU_DEVICES_CHANGED)?;  // ACPI/GED 通知 guest
        }
        self.config.lock().unwrap().cpus.boot_vcpus = desired_vcpus;  // 成功后才更新 config
    }
    // ...
}

    pending CPU removal 映射成 HTTP 429（http_endpoint.rs:462）——不是普通失败，而是 guest 尚未完成 eject 协议。vm_resize() VM 未 boot 时只更新 config（lib.rs:2120）。

    6. CpuManager::resize（变大/变小分流）

    // vmm/src/cpu.rs:1594
pub fn resize(&mut self, desired_vcpus: u32) -> Result<bool> {
    if desired_vcpus == self.present_vcpus() { return Ok(false); }   // 无变化
    if !self.dynamic { return Ok(false); }                           // 未开热插拔
    if desired_vcpus < 1 { return Err(Error::DesiredVCpuCountIsZero); }
    if self.check_pending_removed_vcpu() { return Err(Error::VcpuPendingRemovedVcpu); }  // 有未完成 eject
    match desired_vcpus.cmp(&self.present_vcpus()) {
        cmp::Ordering::Greater => {
            let vcpus = self.create_vcpus(desired_vcpus, None)?;
            for vcpu in &vcpus { self.configure_vcpu(&mut vcpu.lock().unwrap(), None)?; }
            self.activate_vcpus(desired_vcpus, true, None)?;         // inserting=true
            Ok(true)
        }
        cmp::Ordering::Less => { self.mark_vcpus_for_removal(desired_vcpus); Ok(true) }
        _ => Ok(false),
    }
}

    create_vcpu() x86_64 用 topology 算 x2APIC id，ARM64/RISC-V 直接用 cpu id（:1002）；configure_vcpu() x86_64 写 CPUID/Hyper-V/topology/nested，ARM64 调 vcpu.configure(vm, boot_setup)（:1048）。

    7. vCPU 下线（标记 → guest eject → 真删）

    变小走 mark_vcpus_for_removal() 只标记，不删线程：

    // vmm/src/cpu.rs:1517
fn mark_vcpus_for_removal(&mut self, desired_vcpus: u32) {
    for cpu_id in desired_vcpus..self.present_vcpus() {
        self.vcpu_states[cpu_id].removing = true;
        self.vcpu_states[cpu_id].pending_removal.store(true, Ordering::SeqCst);  // 阻止新 resize
    }
}

    真正删除在 guest 写 eject（§4）触发的 remove_vcpu()：

    // vmm/src/cpu.rs:1536
fn remove_vcpu(&mut self, cpu_id: u32) -> Result<()> {
    let state = &mut self.vcpu_states[cpu_id];
    state.kill.store(true, Ordering::SeqCst);    // 设 per-vCPU kill
    state.signal_thread();                        // signal 线程
    state.wait_until_signal_acknowledged()?;
    state.join_thread()?;                         // join
    state.kill.store(false, Ordering::SeqCst);    // 清理，便于复用
    state.pending_removal.store(false, Ordering::SeqCst);
    Ok(())
}

    boot_vcpus 只在 resize + hotplug notify 成功后更新（vm.rs:1900）。源码未见对 create/configure/activate 中途失败的统一 rollback，错误向上冒泡。

    8. vCPU 线程模型与 pause 的 immediate_exit

    start_vcpu() 建 vcpu{n} 线程，设 affinity/seccomp/signal/barrier（:1161）。主循环先处理 pause/kick/kill 再 vcpu.run()。pause 时用 immediate_exit 再进一次 KVM_RUN 是关键：

    // vmm/src/cpu.rs:1320  (vCPU 线程主循环)
if vcpus_pause_signalled.load(Ordering::SeqCst) {
    #[cfg(feature = "kvm")]
    if matches!(hypervisor_type, HypervisorType::Kvm) {
        vcpu.vcpu.set_immediate_exit(true);                       // 让下次 KVM_RUN 立即返回
        if !matches!(vcpu.run(), Ok(VmExit::Ignore)) { break; }    // 完成未完成的 PIO/MMIO exit
        vcpu.vcpu.set_immediate_exit(false);
    }
    vcpu_run_interrupted.store(true, Ordering::SeqCst);
    vcpu_paused.store(true, Ordering::SeqCst);                     // pause ACK
    while vcpus_pause_signalled.load(Ordering::SeqCst) { thread::park(); }  // park 等 resume
    vcpu_paused.store(false, Ordering::SeqCst);
}
// ... kick → NMI(x86) ...
if vcpus_kill_signalled.load(Ordering::SeqCst) || vcpu_kill.load(Ordering::SeqCst) { break; }  // kill/remove
match vcpu.run() { /* KVM_RUN exit 分发 */ }

    为什么 pause 要再进一次 KVM_RUN？ pause 可能由 PIO/MMIO exit 触发，内核侧这些操作要 re-enter KVM_RUN 才算完成（guest state 才一致）。KVM 文档明确：未完成操作状态不对用户态可见，迁移前必须完成。immediate_exit 让这次 re-entry 不再执行任何指令、只完成 pending 操作（:1334）。

    9. Pause / Resume（VM 级）

    Vm::pause() 状态转换检查 + x86 存 clock + 激活 pending virtio + 依次暂停 CpuManager/DeviceManager/hypervisor VM：

    // vmm/src/vm.rs:3068
fn pause(&mut self) -> Result<(), MigratableError> {
    self.state.valid_transition(VmState::Paused)?;
    #[cfg(target_arch = "x86_64")] { self.saved_clock = Some(self.vm.get_clock()?); }  // x86 存 clock
    self.activate_virtio_devices()?;                  // 先激活 pending virtio
    self.cpu_manager.lock().unwrap().pause()?;        // 再 CPU
    self.device_manager.lock().unwrap().pause()?;     // 再设备
    self.vm.pause()?;                                  // 再 hypervisor VM
    self.state = VmState::Paused;
}

    CpuManager::pause() 设全局 pause flag + signal 所有 vCPU + 等所有 active vCPU 的 paused ACK（保证 vCPU 已 park，适合 snapshot/migration，cpu.rs:2632/2652）。resume() 清 pause flag + unpark + 等 paused 清除（:2667）。

    10. Snapshot 与 Restore

    Vcpu 实现 Snapshottable，调底层 hypervisor vCPU state() 存 CpuState（:649）；CpuManager::snapshot() 是所有 vCPU snapshot 集合，不存 memory dirty log 也不存 device tree：

    // vmm/src/cpu.rs:2693
fn snapshot(&mut self) -> Result<Snapshot, MigratableError> {
    let mut cpu_manager_snapshot = Snapshot::default();
    for vcpu in &self.vcpus {
        cpu_manager_snapshot.add_snapshot(vcpu.id(), vcpu.lock().unwrap().snapshot()?);
    }
    Ok(cpu_manager_snapshot)
}

    KVM x86_64 state() 保存 CPUID/MP state/regs/sregs/xsave/LAPIC/FPU/nested/MSRs/events/TSC/Hyper-V（hypervisor/kvm/mod.rs:2344）；ARM64 保存 MP state/core regs + KVM_GET_REG_LIST 收集系统寄存器（:2440）。Vm::snapshot() 要求 Paused，聚合 CPU+memory+device（vm.rs:3153）。restore 时 create_vcpu() 从 per-vCPU snapshot 取 CpuState 调 set_state()（ARM64 先 init，cpu.rs:1025），VM restore 完设备/磁盘锁后 start_restored_vcpus() 用 paused=true 启动（vm.rs:2789）。

    11. 与 Memory Migration 的边界

    CPU snapshot 只存 vCPU state；memory range table/dirty log/UFFD 归 MemoryManager（vm.rs:3207）。Vm 的 Migratable dirty log 只聚合 memory + device manager——CpuManager 不参与 dirty page tracking（:3283）。live migration memory 阶段：先启 dirty log → 多轮发送内存 → VM pause 后发最后一轮 dirty pages（lib.rs:1392）。

    12. ARM64 与 x86_64 差异

    维度 x86_64 ARM64
    vCPU id topology 算 x2APIC id cpu id 直接用
    配置 CPUID/Hyper-V/topology/nested vcpu.configure(vm, boot_setup)
    snapshot VM state common CPUID + clock（vm.rs:3139） 据 vCPU state 构造 MPIDR 列表
    restore 直接 set_state 先 init vCPU 再 set_state（cpu.rs:1700）
    guest CPU 描述 ACPI CPU device FDT /cpus（reg 来自 MPIDR 编码，fdt.rs:238）
    vGIC restore — 依赖 CpuManager::get_saved_states()（device_manager.rs:1726）

    13. 能力边界

    • CPU runtime control 是 manager 级能力，不只是启动期构造。
    • 支持在线增 vCPU，也支持启动 guest eject 协议完成删——删除是异步协作语义。
    • CPU pause/resume 为 snapshot/migration 服务：没 pause 成功就没一致 vCPU state snapshot。
    • CPU snapshot 只覆盖 CPU state；完整 VM snapshot 必须含 memory + device manager。
    • ARM64/x86_64 差异不在 /vm.resize API，而在 vCPU 配置/guest CPU 描述/interrupt controller/restore state。
