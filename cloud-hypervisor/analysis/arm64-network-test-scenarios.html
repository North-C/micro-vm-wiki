    Cloud Hypervisor ARM64 网络测试场景

    本文承接 ARM64 网络观测指南 和 ARM64 网络失败原型。

    目标不是再总结能力边界。

    目标是把仓库里已经存在的 Cloud Hypervisor 网络测试包装代码，整理成一组可直接引用的 ARM64 网络场景。

    这些场景虽然不等于“真实线上事故样本”，但它们已经具备：

    1. 触发配置
    2. host 侧命令
    3. guest 侧命令
    4. 断言条件

    因此它们是从源码原型迈向实样记录的最好中间层。

    源码基线：当前工作树。

    1. 核心结论

    Cloud Hypervisor 当前最有价值的 ARM64 网络测试场景，至少有三类：

    1. 多网卡场景
    2. MSI 中断场景
    3. virtio-net control queue / MTU 场景

    此外，运行期 add-net hotplug 场景也已经有现成包装。

    这些场景的价值不在于“它们是完整测试套件”。

    而在于它们已经把：

    host ip link、guest ip link、guest /proc/interrupts、guest ethtool

    这些关键观测点串在同一个测试里。

    2. 场景一：多网卡场景

    _test_multiple_network_interfaces() 会启动一个 VM，并传入三块网络接口：

    1. 默认网卡
    2. 一块匿名 tap 网卡
    3. 一块显式命名为 mytap1 的网卡

    源码依据：tests_wrappers.rs。

    它在 host 侧直接检查：

    ip link | grep -c mytap1

    断言结果为 1。

    源码依据：tests_wrappers.rs。

    然后它在 guest 侧执行：

    ip -o link | wc -l

    并断言为 4，也就是：

    3 块网络接口 + localhost

    源码依据：tests_wrappers.rs。

    这个场景的意义非常直接：

    它同时验证了：

    1. host tap 确实创建出来
    2. guest 确实看到了新增网卡

    对 ARM64 来说，这是验证 FDT/PCI host bridge 描述是否真正落地的一个很实用场景。

    3. 场景二：MSI 中断场景

    _test_pci_msi() 会启动带默认网卡的 guest，然后在 guest 里执行：

    grep -c <msi_pattern> /proc/interrupts

    并断言结果为 12。

    源码依据：tests_wrappers.rs。

    这说明网络验证在 Cloud Hypervisor 这里，本来就不仅看设备是否出现。

    还直接看 guest 里中断条目是否符合预期。

    对于 ARM64，这类场景特别有意义。

    因为它能帮助区分两类问题：

    1. 设备已创建，但 guest 中断路径不通
    2. 设备和中断都已经被 guest 识别

    如果后续要写真实失败样本，这条命令几乎一定要保留。

    4. 场景三：virtio-net control queue / MTU 场景

    _test_virtio_net_ctrl_queue() 会启动一台带指定 MTU 的 guest。

    在 ARM64 下，它显式把接口名设成：

    enp0s4

    源码依据：tests_wrappers.rs。

    然后它在 guest 内执行：

    1. sudo ethtool -K <iface> rx-gro-hw off && echo success
    2. cat /sys/class/net/<iface>/mtu

    并断言：

    1. ethtool 调整成功
    2. MTU 等于 3000

    源码依据：tests_wrappers.rs。

    这个场景的价值在于，它不只证明 guest 看见了网卡。

    它进一步证明：

    guest 已经可以通过 control queue 和 sysfs 交互网卡参数。

    对 ARM64 网络来说，这比单纯 ip link 更强。

    5. 场景四：运行期 net hotplug

    _test_net_hotplug() 先启动一台没有额外网卡的 VM。

    然后通过 API socket 执行：

    add-net

    把新网卡热插进去。

    源码依据：tests_wrappers.rs。

    在 integration.rs 中，这个场景在 ARM64 下会使用：

    edk2_path()

    作为 kernel/firmware 路径。

    源码依据：integration.rs。

    这点很重要。

    它说明：

    Cloud Hypervisor ARM64 的网络 hotplug 测试，并不是拿 x86 启动路径硬套过来的。

    而是明确承认 ARM64 的 firmware/boot 描述前提。

    因此如果后续有 ARM64 hotplug 样本，它应该优先回对这一组测试包装，而不是只看 vm_add_net API 成功。

    6. 场景与失败原型的对应关系

    可以把上面这些场景，直接映射回已经写好的失败原型。

    场景 更容易发现的失败原型
    多网卡 tap/backend 设置失败、guest 枚举未完成
    MSI 中断 FDT/GIC 路径未闭环
    ctrl queue / MTU 设备已可见但功能交互不完整
    运行期 hotplug vm_add_net() 失败、IOMMU segment 失败、guest 枚举未完成

    这样做的好处是：

    后续碰到一条失败日志时，可以直接反推“应该套用哪一组现成测试场景做复核”。

    7. 推荐如何使用这些场景

    如果目标是补一份真实 ARM64 失败样本，建议顺序如下。

    第一步，优先复用 _test_multiple_network_interfaces()。

    理由：

    它同时覆盖 host tap 和 guest 设备可见性，是最容易形成首份样本的场景。

    第二步，再复用 _test_pci_msi()。

    理由：

    它把 ARM64 guest /proc/interrupts 直接拉进验证链，对定位 GIC 路径问题非常有帮助。

    第三步，再复用 _test_virtio_net_ctrl_queue()。

    理由：

    它能补“设备可见之后，功能交互是否真的成立”这一层。

    最后才去补热插拔场景。

    因为 add-net hotplug 的变量更多，最适合在前面三类场景已经稳定后再做。

    8. 结论

    Cloud Hypervisor 这里其实已经离“真实样本”很近了。

    因为仓库里已经有成型的测试包装代码，把 host 命令、guest 命令和断言都写好了。

    后续如果真要补第一份 ARM64 网络失败样本，最优先不该从头设计场景。

    应该直接从这几组现成测试包装里挑一组，替换成失败配置或失败环境，再把输出固化成样本记录。
