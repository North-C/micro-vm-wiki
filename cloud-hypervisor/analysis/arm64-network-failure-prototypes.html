    Cloud Hypervisor ARM64 网络失败原型

    本文承接 ARM64 网络能力边界矩阵 和 ARM64 网络观测指南。

    当前工作树里没有一份现成的 Cloud Hypervisor ARM64 网络失败样本日志集。

    因此这篇文档不冒充真实事故回放。

    它只做一件更稳妥的事：

    把源码里已经明确暴露出来的 Cloud Hypervisor ARM64 网络失败路径，整理成一组可复用的失败原型。

    源码基线：当前工作树。

    1. 核心结论

    Cloud Hypervisor ARM64 网络当前至少能稳定抽出五个失败原型：

    1. vm_add_net()/配置校验失败
    2. IOMMU segment 组合失败
    3. tap/backend 打开或启用失败
    4. guest 枚举没有真正完成
    5. restore 后 GIC state 与网络设备状态没闭环

    这些原型的价值不在于“已经有现成样本”。

    而在于以后遇到真实日志时，可以直接把错误文本映射到一个已知原型，而不用重新从头解释。

    2. 原型一：vm_add_net() 直接失败

    触发条件

    运行期新增网卡统一从 vm_add_net() 进入。

    如果 VmConfig 校验失败，或者后续 vm.add_net() 失败，会直接在这一层返回错误。

    源码依据：vmm/src/lib.rs。

    典型签名

    Error when adding new network device to the VM: ...

    应归类的层级

    host configuration / device creation

    容易误判的地方

    这类失败还停留在 host 配置和设备构造层。

    它还没有进入 ARM64 FDT/GIC 或 guest 枚举阶段。

    因此看到它时，不该先去怀疑 guest driver。

    3. 原型二：IOMMU segment 组合失败

    触发条件

    DeviceManager::add_net() 对 net_cfg.iommu 有统一校验。

    如果设备要求 IOMMU，但当前 pci_segment 不是 IOMMU segment，就直接返回错误。

    源码依据：device_manager.rs。

    典型签名

    InvalidIommuHotplug

    应归类的层级

    device-model composition

    容易误判的地方

    它不是“guest 看不到网卡”的问题。

    它说明设备模型组合本身越界了，guest 枚举根本不该成为首要排查方向。

    4. 原型三：multiqueue 与 tap 能力不匹配

    触发条件

    open_tap() 在真正打开 TAP 前，会检查 multiqueue 期望与接口实际能力是否匹配。

    源码依据：open_tap.rs。

    典型签名

    1. MultiQueueNoTapSupport
    2. MultiQueueNoDeviceSupport

    应归类的层级

    host backend capability

    容易误判的地方

    这类错误不是 ARM64 FDT/GIC 问题。

    它说明 host tap 与 queue 数配置不匹配，问题发生在更早一层。

    5. 原型四：tap/backend 打开与启用失败

    触发条件

    Cloud Hypervisor 普通 net 路径最终会：

    1. 打开 tap
    2. 设置 IP/netmask
    3. 设置 MAC
    4. 设置 MTU
    5. enable 接口
    6. 设置 vnet header size

    源码依据：open_tap.rs。

    典型签名

    1. TapOpen
    2. TapSetIpNetmask
    3. TapSetMac
    4. TapSetMtu
    5. TapEnable
    6. TapSetVnetHdrSize

    应归类的层级

    host backend / tap setup

    容易误判的地方

    这些错误都还发生在 guest 可见之前。

    因此如果看到它们，不该把问题先归给 ARM64 FDT 或 GIC。

    6. 原型五：设备已创建，但 guest 枚举未真正完成

    触发条件

    ARM64 guest 描述主轴是 create_fdt()。

    这里显式写入 interrupt-parent、GIC、devices 和 PCI nodes。

    源码依据：fdt.rs。

    与此同时，net 设备在真正被 guest 驱动后会打：

    virtio-device activated

    源码依据：virtio-devices/src/net.rs。

    典型签名

    1. host 侧看不到明显错误
    2. guest 侧迟迟没有对应 virtio-device activated
    3. 设备创建成功，但 guest 仍不可用

    应归类的层级

    guest discovery / FDT-GIC path

    容易误判的地方

    这类原型最容易被误判成：

    “既然 vm_add_net() 成功，网络就没问题”。

    实际上，这正是 ARM64 Cloud Hypervisor 最典型的中间层失败。

    7. 原型六：restore 后网络异常

    触发条件

    ARM64 restore 时，Gic 会显式执行：

    1. set_gicr_typers()
    2. restore_vgic()
    3. enable()

    源码依据：devices/src/gic.rs。

    典型签名

    1. 启动期网络正常
    2. restore 后设备仍在
    3. 但网络中断或可用性异常

    应归类的层级

    restore / GIC-state coordination

    容易误判的地方

    如果问题只在 restore 后出现，就不应先回头怀疑 NetConfig。

    应优先怀疑 GIC state 与 guest 枚举状态的恢复闭环。

    8. 失败原型总表

    原型 典型签名 所属层级 首选回看代码
    vm_add_net() 失败 Error when adding new network device to the VM host config vmm/src/lib.rs
    IOMMU segment 失败 InvalidIommuHotplug device-model composition vmm/src/device_manager.rs
    MQ 与 tap 不匹配 MultiQueueNoTapSupport / MultiQueueNoDeviceSupport host backend net_util/src/open_tap.rs
    tap/backend 设置失败 TapOpen / TapEnable / TapSet* host backend net_util/src/open_tap.rs
    guest 枚举未完成 无 virtio-device activated guest discovery arch/src/aarch64/fdt.rs + virtio-devices/src/net.rs
