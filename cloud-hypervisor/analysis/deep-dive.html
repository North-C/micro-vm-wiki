    Cloud Hypervisor 深入探索文档

    本文档从当前仓库源码出发，建立对 Cloud Hypervisor 的系统性理解：它与 Firecracker/crosvm 的边界差异、VMM 控制面如何组织、设备和 snapshot/migration 如何扩展，以及 ARM64 与 x86_64 路径如何分叉。

    当前版本：第 2 版
    源码基线：cloud-hypervisor 仓库，commit ea0a0393b
    阅读方式：先看定位和总架构，再沿 CLI/API -> VMM thread -> Vm -> Cpu/Memory/DeviceManager -> migration/snapshot 展开。

    0. 问题地图

    1. Cloud Hypervisor 是不是 microVM？它和 Firecracker 的定位差在哪里？
    2. 进程入口、API thread、VMM thread、VM 对象之间如何传递控制？
    3. VmCreate、VmBoot、VmRestore、VmSnapshot 如何进入 VMM 内部？
    4. DeviceManager 为什么是理解 Cloud Hypervisor 的核心？
    5. 它支持哪些热插拔设备，为什么比 Firecracker 的设备面更宽？
    6. snapshot/restore 和 live migration 保存的是哪些层级的状态？
    7. seccomp 与 Landlock 分别限制什么？
    8. ARM64 与 x86_64 在 boot、interrupt、memory layout、ACPI/FDT 上有什么差异？
    9. 与 Firecracker、crosvm、Kata/CubeSandbox 的关系应如何理解？

    1. 一句话定位

    Cloud Hypervisor 是面向现代云工作负载的通用 Rust VMM。它运行在 KVM/MSHV 之上，避免 legacy 设备，强调 paravirtualized I/O、热插拔、迁移、VFIO/vDPA/vhost-user，以及 Rust VMM 生态复用。

    源码和文档依据：

    • README 明确它是运行在 KVM/MSHV 之上的开源 VMM，面向 modern cloud workloads，不要求 legacy devices，并基于 Rust VMM crates：README.md。
    • README 说明 Cloud Hypervisor 与 Firecracker/crosvm 的差异：它目标是 general purpose VMM for cloud workloads，不局限于 container/serverless 或 client workloads：README.md。
    • arch/src/lib.rs 顶层注释列出 supported platforms: x86_64、aarch64、riscv64：arch/src/lib.rs。

    2. 能力边界

    能力 Cloud Hypervisor 状态 与 Firecracker 的差异
    VM 生命周期 CLI、HTTP API、DBus API、ch-remote Firecracker 更偏单 microVM API；Cloud Hypervisor 更偏长期可管理 VM
    设备模型 virtio-pci、vhost-user、VFIO、vDPA、virtio-fs、pmem、vsock、memory hotplug 设备面显著更宽
    热插拔 CPU、VFIO、virtio-net/block/pmem/fs/vsock、memory resize Firecracker 热插拔能力更有限
    snapshot/restore vm_migration::Snapshot 聚合 VM、CPU、Memory、DeviceManager、device state 目标更贴近迁移/管理能力
    兼容性 snapshot/restore 与 live migration 不保证跨版本兼容 与 Firecracker 类似，都需要同版本/兼容状态边界
    隔离 seccomp + Landlock + Rust 内存安全 Firecracker 重点是 jailer/seccomp/cgroup/namespace
    架构 x86_64、aarch64、riscv64 源码支持 Firecracker 主要关注 x86_64/aarch64

    README 的 hotplug 小节列出 CPU、VFIO、virtio-{net,block,pmem,fs,vsock} 和 memory resizing：README.md。README 同时说明 snapshot/restore、live migration 不保证跨版本支持：README.md。

    3. 顶层架构

    flowchart TB CLI["cloud-hypervisor CLI"] --> MAIN["cloud-hypervisor/src/main.rs"] REMOTE["ch-remote / HTTP / DBus"] --> API["API endpoint layer"] MAIN --> HV["hypervisor::new()\nKVM/MSHV"] MAIN --> VMMT["start_vmm_thread"] API --> REQ["ApiRequest closure"] REQ --> VMM["Vmm"] VMM --> VM["Vm"] VM --> CPU["CpuManager"] VM --> MEM["MemoryManager"] VM --> DEV["DeviceManager"] DEV --> PCI["virtio-pci transport"] DEV --> VHOST["vhost-user / vDPA / VFIO"] CPU --> VCPU["vCPU threads"]

    Cloud Hypervisor 的关键不是“一个 VM 对象”，而是 Vmm 作为控制中心，持有/创建 Vm，再由 Vm 组合 CpuManager、MemoryManager、DeviceManager。API 层把外部请求变成 ApiRequest，交给 VMM thread 串行处理。

    入口路径在 cloud-hypervisor/src/main.rs 中很集中：创建 API channel 和 EventFd，解析 seccomp/landlock，创建 hypervisor backend，启动 VMM thread，然后根据命令行发送 VmCreate/VmBoot 或 VmRestore：cloud-hypervisor/src/main.rs。

    4. 启动与控制面流程

    sequenceDiagram participant CLI as main.rs participant HV as hypervisor backend participant VMM as VMM thread participant API as ApiRequest participant VM as Vm CLI->>CLI: parse args / seccomp / landlock CLI->>HV: hypervisor::new() CLI->>VMM: start_vmm_thread(...) alt direct boot CLI->>API: VmCreate(vm_config) API->>VMM: vmm.vm_create() VMM->>VM: Vm::new(...) CLI->>API: VmBoot API->>VMM: vmm.vm_boot() else restore CLI->>API: VmRestore(restore_config) API->>VMM: vmm.vm_restore() end

    main.rs 在有 kernel/firmware payload 时先构造 VmConfig，再发送 VmCreate 和 VmBoot；如果命令行传入 --restore，则发送 VmRestore：cloud-hypervisor/src/main.rs。

    API action 的实现模式是统一的。VmRestore、VmSnapshot 等类型实现 ApiAction，request() 返回一个闭包，这个闭包在 VMM thread 内调用 vmm.vm_restore() 或 vmm.vm_snapshot()，再把响应通过 channel 送回：vmm/src/api/mod.rs。

    5. VMM thread：控制面如何串行化

    Cloud Hypervisor 的控制面有一个很关键的设计：外部 API 线程不直接操作 VM，而是把请求包装为 ApiRequest 闭包，通过 channel 和 EventFd 送入 VMM thread。真正修改 VM 状态的代码在 VMM thread 里执行。

    flowchart TB API["HTTP/DBus/ch-remote/API action"] --> REQ["ApiRequest closure"] REQ --> CH["api_sender/api_receiver"] API --> EVT["api_event EventFd"] EVT --> EPOLL["Vmm EpollContext"] CH --> EPOLL EPOLL --> VMM["Vmm::control_loop"] VMM --> HANDLER["RequestHandler for Vmm"] HANDLER --> VMCREATE["vm_create"] HANDLER --> VMBOOT["vm_boot"] HANDLER --> SNAP["vm_snapshot"] HANDLER --> RESTORE["vm_restore"]

    源码依据：

    • start_vmm_thread() 创建名为 vmm 的线程，在线程内先应用 VMM thread 的 seccomp filter，然后构造 Vmm::new()，安装 signal handler，再进入 vmm.control_loop()：vmm/src/lib.rs。
    • HTTP API 线程在 VMM thread 启动之后创建，持有 api_event_clone 和 api_sender，因此它的职责是发送请求，不是执行请求：vmm/src/lib.rs。
    • Vmm::new() 创建 EpollContext，把 exit/reset/activate/api/debug 等 event fd 注册到 epoll 中：vmm/src/lib.rs。
    • 控制循环收到 EpollDispatch::Api 后读取 api_evt，再从 channel 取出 ApiRequest，调用闭包 api_request(self)：vmm/src/lib.rs。

    这个模型解释了 Cloud Hypervisor 的并发边界：API thread 可以并发接收请求，但 VM 生命周期变更被收敛到 VMM thread 的 event loop 中。相比把每个请求直接打到共享对象上，这种模型更容易维持 VM 状态机的一致性。

    6. vm_create 并不真正创建 VM

    容易误解的一点是：API 名字叫 VmCreate，但 Vmm::vm_create() 只保存配置并预创建 console 相关设备，真正的 Vm 对象在 vm_boot() 中创建。

    sequenceDiagram participant API as ApiRequest participant VMM as Vmm participant VM as Vm participant CM as CpuManager participant MM as MemoryManager participant DM as DeviceManager API->>VMM: vm_create(config) VMM->>VMM: store vm_config VMM->>VMM: pre_create_console_devices() API->>VMM: vm_boot() VMM->>VM: Vm::new(...) VM->>MM: MemoryManager::new(...) VM->>CM: CpuManager::new(...) VM->>DM: DeviceManager::new(...) VMM->>VM: vm.boot()

    源码依据：

    • vm_create() 在 self.vm_config 已存在时返回 VmAlreadyCreated，否则只把 VmConfig 存入 self.vm_config，随后调用 pre_create_console_devices()；如果启用 Landlock，则在配置上应用路径限制：vmm/src/lib.rs。
    • vm_boot() 才判断 self.vm.is_none()，并调用 Vm::new(...) 创建 VM 对象，然后调用 vm.boot()：vmm/src/lib.rs。
    • vm_snapshot() 要求 self.vm 存在；它先释放 console fd，再调用 vm.snapshot() 和 vm.send()：vmm/src/lib.rs。
    • vm_restore() 反过来要求当前不能已有 VM/config；它从 snapshot 目录读取 config，校验 restore config，然后走 self.vm_restore(...)，必要时再 vm_resume()：vmm/src/lib.rs。

    这个延迟创建策略的直接后果是：VmCreate 更像“提交 VM 配置”，VmBoot 才是资源分配和 hypervisor 对象创建的主入口。分析能力边界时应该以 vm_boot() 和 Vm::new() 为准，而不是只看 API 名字。

    7. Vm::new_from_memory_manager：VM 组装主路径

    Vm 是 Cloud Hypervisor 内部的核心聚合对象。它持有 payload、thread handle、DeviceManager、CpuManager、MemoryManager、hypervisor VM handle、NUMA nodes 和当前 VmState：vmm/src/vm.rs。

    Vm::new_from_memory_manager() 展示了 VM 创建的真实顺序：

    1. 校验 VmConfig，建立 boot id list 和 NUMA node 信息。
    2. 根据 IOMMU、TDX、restore 等条件决定动态能力和 stop_on_boot。
    3. 创建 guest memory、I/O bus、MMIO bus、VmOpsHandler。
    4. 创建 CpuManager。
    5. 创建 DeviceManager。
    6. 执行 hypervisor-specific 初始化。
    7. 加载 kernel/initramfs 或在 restore 时恢复状态。
    8. 初始化 VmState：普通新建为 Created，从 snapshot 恢复为 Paused。

    源码依据：

    • Vm::new_from_memory_manager() 的主线包含 config 校验、NUMA 创建、guest memory/bus 创建、CPU manager 创建、DeviceManager 创建和 payload 加载：vmm/src/vm.rs。
    • create_device_manager() 把 bus、hypervisor VM、config、memory manager、CPU manager、event fd、NUMA、activate event、snapshot 等全部传给 DeviceManager::new()：vmm/src/vm.rs。
    • hypervisor_specific_init() 处理 MSHV、SEV-SNP、TDX、地址空间分配、aarch64 UEFI flash、payload 异步加载、boot vCPU 创建和 KVM 初始化：vmm/src/vm.rs。

    可以把 Vm 理解为一个“依赖装配器”：它自身不直接实现所有虚拟化细节，而是按顺序装配 hypervisor VM、memory、CPU、device 三大 manager，再在 boot 阶段把它们推进到可运行状态。

    8. Boot 流程：从 Created 到 Running

    Vm::boot() 不是简单地启动 vCPU。它在真正运行 vCPU 前要完成磁盘锁、ACPI/FDT、payload entry point、vCPU 配置、平台系统配置、TDX finalize 等工作。

    flowchart TB START["Vm::boot()"] --> LOCK["try_lock_disks()"] LOCK --> STATE["Created -> Running/BreakPoint"] STATE --> ACPIX["x86_64: create ACPI tables early"] STATE --> ENTRY["entry_point() / wait payload load"] ENTRY --> VCPUCFG["configure_vcpu() for each vCPU"] VCPUCFG --> A64GIC["aarch64: set GIC redistributor addr"] A64GIC --> A64ACPI["aarch64: create ACPI tables after MPIDR known"] VCPUCFG --> SYS["configure_system()"] SYS --> RESUME["hypervisor VM resume if Created"] RESUME --> RUN["CpuManager::start_boot_vcpus()"]

    源码依据：

    • Vm::boot() 首先对磁盘做 advisory lock，然后计算新状态：普通运行是 Running，stop_on_boot 则进入 BreakPoint：vmm/src/vm.rs。
    • x86_64 上 ACPI tables 可以在 vCPU configure 前创建；aarch64 上代码注释明确指出 ACPI 依赖 vCPU MPIDR，因此要在 vCPU configure 之后创建：vmm/src/vm.rs 和 vmm/src/vm.rs。
    • 每个 vCPU 都调用 cpu_manager.configure_vcpu()；aarch64 还会把 GIC redistributor 地址写入 vCPU：vmm/src/vm.rs。
    • 最后 self.vm.resume()，再调用 cpu_manager.start_boot_vcpus()，把 vCPU thread 跑起来：vmm/src/vm.rs。

    这说明 Cloud Hypervisor 的 boot 边界包含三类工作：guest 描述构造、vCPU 初始状态配置、hypervisor run loop 启动。只看 start_boot_vcpus() 会漏掉大部分平台初始化。

    9. CpuManager 与 vCPU run loop

    CpuManager 管理的是 vCPU 生命周期，不只是“创建几个线程”。它保存 CPU 配置、interrupt controller、x86 CPUID、pause/kick/kill 原子变量、vCPU 状态、thread handle、NUMA affinity、dynamic hotplug 标记、hypervisor handle，以及 core scheduling leader 等：vmm/src/cpu.rs。

    关键路径：

    1. CpuManager::new() 检查 max_vcpus 是否超过 hypervisor 能力，准备 vCPU 状态数组，x86_64 上读取 CPU vendor/CPUID 相关信息，处理 AMX/NUMA affinity/dynamic hotplug：vmm/src/cpu.rs。
    2. create_vcpu() 调用 hypervisor VM 创建 vCPU。x86_64 使用 topology 计算 x2APIC id；aarch64/riscv64 直接用 cpu id，并在 snapshot restore 场景加载 vCPU 状态：vmm/src/cpu.rs。
    3. configure_vcpu() 在 x86_64 上传入 CPUID、Hyper-V emulation、topology、nested virtualization 标志；在 aarch64 上调用 vcpu.configure(self.vm.as_ref(), boot_setup)：vmm/src/cpu.rs。
    4. vCPU thread 启动时应用 vCPU seccomp filter、设置 affinity/core scheduling，随后进入循环处理 pause/kick/kill，再调用 vcpu.run()：vmm/src/cpu.rs 和 vmm/src/cpu.rs。
    5. pause 时，CPU manager 通过原子变量和信号中断 KVM_RUN，并等待 active vCPU 都进入 paused 状态；snapshot 中 CPU manager 聚合所有 vCPU snapshot：vmm/src/cpu.rs 和 vmm/src/cpu.rs。

    vCPU thread 的 run loop 特别说明了迁移场景的严格性：当 pause 由 PIO/MMIO exit 触发时，代码会通过 immediate_exit 重新进入一次 KVM_RUN，确保内核完成未完成的 I/O/MMIO 操作，然后再认为 guest state 可迁移：vmm/src/cpu.rs。这是 snapshot/migration 正确性的关键细节。

    10. MemoryManager：guest RAM、hotplug 与 dirty log

    MemoryManager 保存 guest memory 的全局视图：boot/current RAM、memory zones、hotplug slots、device area、arch memory regions、guest RAM mappings、userfaultfd handler、ACPI 地址，以及 aarch64/riscv64 UEFI flash 等：vmm/src/memory_manager.rs。

    flowchart LR CFG["MemoryConfig"] --> MM["MemoryManager"] MM --> ZONE["Memory zones"] MM --> GM["GuestMemoryAtomic"] MM --> MAP["guest_ram_mappings"] MM --> HOT["hotplug slots"] MM --> DIRTY["hypervisor dirty log + VMM bitmap"] MM --> SNAP["MemoryManagerSnapshotData"]

    源码依据：

    • MemoryManager::new() 先校验 memory config。restore 场景走 restore_memory_regions_and_zones() 并从 snapshot data 恢复 device area、RAM 大小、slot、hotplug 等状态；非 restore 场景则按架构内存布局创建 memory regions：vmm/src/memory_manager.rs。
    • memory_range_table(snapshot=true) 遍历 memory zones 和 region。对于特定共享文件映射且可由用户文件保存的区域，会跳过内存内容复制：vmm/src/memory_manager.rs。
    • snapshot_data() 保存 memory ranges、guest RAM mappings、device area、boot/current RAM、arch memory regions、hotplug slots、memory slot 等恢复所需元数据：vmm/src/memory_manager.rs。
    • Snapshottable for MemoryManager 生成 snapshot memory range table 后，把 MemoryManagerSnapshotData 写入 snapshot：vmm/src/memory_manager.rs。
    • Transportable for MemoryManager 把 guest memory ranges 写到 snapshot 目录中的内存文件；Migratable 则通过 hypervisor dirty log 和 VMM bitmap 合并生成 dirty range table：vmm/src/memory_manager.rs 和 vmm/src/memory_manager.rs。

    因此 Cloud Hypervisor 的 memory snapshot 不是单纯 dump RAM。它同时保存“哪些 GPA 范围需要保存”和“这些范围如何映射、属于哪些 slot/zone/hotplug 状态”。这也是 restore 能重新建立同等内存拓扑的基础。

    11. DeviceManager 与设备模型

    Cloud Hypervisor 的设备面比 Firecracker 宽，核心在 DeviceManager。它不是单个 virtio bus，而是一个包含地址分配、PCI segment、interrupt manager、device tree、virtio/vhost/VFIO/vDPA/pmem/fs/net/vsock 等对象的设备编排器。

    DeviceManager 关键成员包括：

    • address_manager：统一管理 IO/MMIO bus、地址分配器和 PCI MMIO aperture。
    • interrupt_controller：x86_64 是 IOAPIC，aarch64 是 GIC，riscv64 是 AIA：vmm/src/device_manager.rs。
    • virtio_devices、block_devices、bus_devices：保存设备和 bus 侧强引用。
    • pci_segments、MSI/legacy interrupt manager、VFIO ops、virtio IOMMU、device tree。
    • activate_evt 和 pending_activations：把 virtio device activation 收敛回 VMM thread。
    • aarch64 特有的 gpio_device 和 id_to_dev_info。

    设备创建路径：

    flowchart TB NEW["DeviceManager::new"] --> ADDR["create mmio allocators / AddressManager"] ADDR --> IRQ["MSI -> IOAPIC/GIC -> legacy interrupt chain"] IRQ --> PCI["create PCI segments"] PCI --> CFG["consume VmConfig device lists"] CFG --> ADD["add_* device"] ADD --> PCIDEV["add_pci_device / allocate BARs"] PCIDEV --> TREE["device_tree"] TREE --> ACT["pending activation / activate_evt"]

    源码依据：

    • DeviceManager::new() 在 restore 时从 snapshot 恢复 device_tree 和 device_id_cnt，否则创建新的 device tree：vmm/src/device_manager.rs。
    • 它按 PCI segment 权重创建 32-bit/64-bit MMIO allocator，然后构造 AddressManager：vmm/src/device_manager.rs。
    • 中断管理上先创建 MSI interrupt manager，再创建 IOAPIC/legacy 相关链路；源码注释明确说明依赖链是 msi_interrupt_manager <- IOAPIC <- legacy_interrupt_manager：vmm/src/device_manager.rs。
    • add_pci_device() 为 PCI 设备分配 BAR，然后挂入对应 segment：vmm/src/device_manager.rs。
    • VFIO-user 设备创建时会建立 client、DMA mapping，并把内存 zone 的 region 映射给 VFIO-user PCI device：vmm/src/device_manager.rs。
    • DeviceManager::snapshot() 先保存自身 state，再遍历 device tree，把每个 migratable device 的 snapshot 聚合进去：vmm/src/device_manager.rs。

    公开热插拔函数包括 add_disk()、add_fs()、add_generic_vhost_user()、add_pmem()、add_net()、add_vdpa()、add_vsock()：vmm/src/device_manager.rs。这解释了为什么 Cloud Hypervisor 更像“现代云 VM 管理器”，而 Firecracker 更像刻意收窄的 microVM building block。

    12. Snapshot、restore 与 migration

    Cloud Hypervisor 使用 vm_migration::Snapshot 作为分层聚合容器。VM snapshot 顶层保存 VM 自身状态，再加入 CPU、Memory、DeviceManager 的子 snapshot。

    flowchart TB SNAP["Vm::snapshot()"] --> CHECK["must be Paused"] CHECK --> VMS["VmSnapshot\nclock/common_cpuid on x86_64"] VMS --> CPU["CpuManager snapshot\nall vCPU states"] VMS --> MEM["MemoryManager snapshot\nranges/mappings/slots"] VMS --> DEV["DeviceManager snapshot\ndevice tree + device snapshots"] MEM --> FILE["guest memory file"] DEV --> D1["virtio/vhost/VFIO migratable devices"]

    源码依据：

    • Vm::pause() 先保存 x86_64 VM clock，再激活 pending virtio devices，然后依次 pause CPU manager、DeviceManager 和 hypervisor VM：vmm/src/vm.rs。
    • Vm::snapshot() 明确拒绝 TDX VM snapshot，且要求当前 VM 状态必须是 Paused；x86_64/KVM 下还会生成 common CPUID 以便 restore 兼容性检查：vmm/src/vm.rs。
    • Vm::snapshot() 依次加入 CpuManager、MemoryManager、DeviceManager 的 snapshot：vmm/src/vm.rs。
    • Vm::send() 把 VM config 写到 SNAPSHOT_CONFIG_FILE，把 snapshot state 序列化写到 SNAPSHOT_STATE_FILE；MemoryManager 的 transport 负责写 guest memory 内容：vmm/src/vm.rs。
    • restore 时 vm_restore() 读取 snapshot state。x86_64/KVM 下先用 common CPUID 做兼容性检查，再构造带 snapshot 的 Vm::new(...)，最后调用 vm.restore()：vmm/src/lib.rs。
    • Vm::restore() 重新加锁磁盘，然后调用 cpu_manager.start_restored_vcpus() 启动恢复出来的 vCPU：vmm/src/vm.rs。

    和 Firecracker 相比，Cloud Hypervisor 的 snapshot/migration 需要面对更复杂的 device tree、更宽的设备集合、hotplug 状态、memory zone/slot 状态和可能的 live migration dirty log。README 也明确说明 snapshot/restore 与 live migration 不保证跨版本兼容：README.md。

    13. 隔离机制：seccomp + Landlock 的分层位置

    Cloud Hypervisor 的隔离不是一个单独模块，而是分散在不同线程创建点和 VM 配置应用点。

    flowchart TB MAIN["main.rs parse seccomp/landlock"] --> VMMT["VMM thread seccomp"] MAIN --> API["HTTP/DBus API thread seccomp"] MAIN --> EVT["event monitor seccomp"] VMMT --> SIG["signal handler seccomp"] VMMT --> VCPU["vCPU thread seccomp"] VMMT --> LL["apply_landlock(config paths)"]

    源码依据：

    • main.rs 未指定 seccomp action 时使用 SeccompAction::Trap，并把 landlock_enable 传入 VMM thread、API thread 和 event monitor thread：cloud-hypervisor/src/main.rs。
    • start_vmm_thread() 根据 Thread::Vmm 和 hypervisor type 取 seccomp filter，并在线程启动后立即应用：vmm/src/lib.rs。
    • event monitor thread 和 signal handler thread 也分别获取并应用自己的 seccomp filter；signal handler 在 Landlock 启用时也会应用 Landlock 规则：vmm/src/lib.rs 和 vmm/src/lib.rs。
    • vCPU thread 启动路径中会获取 vCPU seccomp filter，并在线程内应用后才进入 vCPU run loop：vmm/src/cpu.rs。
    • vm_create() 在保存配置后，如果 landlock_enable 为 true，会调用 apply_landlock(&mut config)；restore 路径在构造 VM 前也会再次应用 Landlock：vmm/src/lib.rs 和 vmm/src/lib.rs。
    • Landlock::new() 创建 ruleset 并设置 hard requirement 兼容级别，后续由 apply_landlock() 按 VM 配置中的磁盘、fs、vhost-user socket、VFIO、payload 等路径添加允许规则：vmm/src/landlock.rs。

    因此它的隔离模型可以概括为：seccomp 限制线程可用 syscall，Landlock 限制进程可访问路径。它没有 Firecracker jailer 那种外部进程包装形态，隔离边界更集中在 VMM 自身的线程和路径权限收缩上。

    14. ARM64 与 x86_64 差异

    Cloud Hypervisor 的架构差异不是只在 arch/ 目录里，也贯穿 VM boot、CPU configure、DeviceManager interrupt controller、ACPI/FDT 生成、snapshot pause 等路径。

    arch/src/lib.rs 按 target_arch 导出平台模块。x86_64 导出 CPUID、zero page、ram ranges、cmdline start 等；aarch64 导出 FDT device info、IRQ base、UEFI、arch memory regions、vcpu configure 等：arch/src/lib.rs。

    维度 x86_64 aarch64
    guest 描述 ACPI、zero page、HVM start info、E820 FDT、UEFI、GIC 信息，也存在 ACPI 表生成路径
    vCPU identity topology -> x2APIC id vCPU configure 后读取 MPIDR_EL1
    CPU 配置 CPUID、MSR、regs、Hyper-V emulation、nested 标志 setup_regs(id, entry, FDT_START)，读取 MPIDR
    中断控制器 IOAPIC/LAPIC/MSI，legacy interrupt manager GIC，pause 时需要 flush GIC pending/ITS tables 到 guest RAM
    内存布局 x86_64 layout/PCI/ACPI 习惯 0-256MiB reserved，256-768MiB MMIO，1GiB 起 RAM，4GiB 后高端 RAM
    boot 描述时机 ACPI 可早于 vCPU configure 创建 ACPI/FDT 依赖 MPIDR，需在 vCPU configure 后补齐
    snapshot 细节 保存 VM clock、common CPUID 兼容性数据 DeviceManager pause 额外触发 GIC pause

    源码依据：

    • x86_64 EntryPoint 包含 setup_header，并定义 CPUID feature bit、KVM feature bit、x2APIC topology 计算等逻辑：arch/src/x86_64/mod.rs 和 arch/src/x86_64/mod.rs。
    • aarch64 configure_vcpu() 在有 boot setup 时调用 setup_regs(id, kernel_entry, FDT_START)，然后读取 MPIDR_EL1 返回给上层：arch/src/aarch64/mod.rs。
    • aarch64 arch_memory_regions() 明确划分 UEFI/GIC/legacy reserved、MMIO、PCI MMCONFIG、低端 RAM、高端 RAM 和 32-bit reserved hole：arch/src/aarch64/mod.rs。
    • CpuManager::configure_vcpu() 在 x86_64 和 aarch64 的分支完全不同：x86_64 传 CPUID/topology/nested，aarch64 传 hypervisor VM 和 boot setup：vmm/src/cpu.rs。
    • DeviceManager 的 interrupt_controller 类型按架构切换：x86_64 是 ioapic::Ioapic，aarch64 是 gic::Gic：vmm/src/device_manager.rs。
    • aarch64 上 DeviceManager::pause() 需要 pause GIC，把 GIC pending tables 和 ITS tables flush 到 guest RAM：vmm/src/device_manager.rs。

    结论：Cloud Hypervisor 在 ARM64 上不是“复用 x86 模型的小改版”。CPU 身份、guest 描述、interrupt controller、memory layout、pause/snapshot 边界都有显式架构分叉。与 x86_64 相比，ARM64 路径更依赖 FDT/GIC/MPIDR 这些 ARM 平台构件。

    15. 与 Firecracker 的关键差异

    1. Firecracker 追求极简单 microVM；Cloud Hypervisor 追求现代 cloud workload 的通用 VM 管理能力。
    2. Firecracker 的设备集合刻意小；Cloud Hypervisor 设备集合包含 VFIO、vDPA、vhost-user、virtio-fs、hotplug 等更宽场景。
    3. Firecracker 的隔离重点包含 jailer；Cloud Hypervisor 更依赖进程内 VMM、seccomp、Landlock 和 Rust 安全。
    4. Firecracker 的 snapshot 更像 microVM 克隆/恢复原语；Cloud Hypervisor 的 snapshot 与 migration 抽象联系更强。
    5. Cloud Hypervisor 与 Firecracker/crosvm 同属 Rust VMM 生态，README 明确提到大量代码借鉴了 Firecracker 或 crosvm：README.md。
