Cloud Hypervisor 可观测性与诊断链路

本文回答：CH 出故障时证据从哪里来，能证明到哪一层。

源码基线：当前仓库工作树。

相关：API/VMM thread 控制面、DeviceManager 设备链路。

0. 术语与背景

CH 可观测四类输出

输出 来源 内容
API response VMM thread request 执行结果（成功/错误码）
event monitor EventMonitor thread 事件流（设备激活/热插拔/错误）
seccomp/Landlock 日志 线程启动 filter apply 失败 → exit event
metrics 可选 Prometheus/serial 设备统计/性能指标

关键边界

  • API response 只说明请求执行完，不说明 guest ready——需要 event monitor + guest 自身信号判断。
  • EventMonitor thread 有自己的 seccomp + Landlock（lib.rs:454）——先 apply filter 再运行监控循环。
  • CH 不像 Kata 有 OpenTelemetry katatrace——tracing 靠 trace_scoped! 宏（本地 span，不导出到远端）。

1. EventMonitor thread

// vmm/src/lib.rs:454
pub fn start_event_monitor_thread(monitor, seccomp_action, landlock_enable, hypervisor_type, exit_event) -> Result<JoinHandle<Result<()>>> {
    let seccomp_filter = get_seccomp_filter(seccomp_action, Thread::EventMonitor, hypervisor_type)?;
    thread::spawn(move || {
        if !seccomp_filter.is_empty() { apply_filter(&seccomp_filter)?; }    // 先 seccomp
        if landlock_enable { Landlock::new()?.restrict_self()?; }             // 再 Landlock
        // 运行 event monitor 循环
    })
}

2. 诊断证据分层

故障层 证据来源
API 请求失败 API error response
设备创建/激活失败 activate() 返回 ActivateError + 日志
热插拔失败 notify_hotplug 返回错误 + 日志
vCPU panic/exit vCPU exit eventfd + shutdown_exit_code
snapshot/restore 失败 MigratableError + 日志
guest 异常 serial 输出 + event monitor 事件

CH 可观测全部在 host VMM 进程——API response/event monitor/seccomp 日志/metrics/serial。无内置 guest agent（不同于 Kata/CubeSandbox）。guest 内诊断靠 serial 输出 + guest 自身工具。

3. 能力边界

问题 CH 表现
日志 有（logger，API 配置 level）
指标 有（可选 Prometheus endpoint 或 serial）
事件监控 有（EventMonitor thread）
tracing/span 有 trace_scoped!（本地 span，不导出远端，不同于 Kata katatrace）
guest agent 无固定 agent
snapshot 保存 metrics 保存设备 Migratable state（含 dirty log state），不保存全局 metrics
