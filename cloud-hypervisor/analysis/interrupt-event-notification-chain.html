Cloud Hypervisor 中断与事件通知链路

本文展开 guest virtio driver 如何经 queue notify 唤醒 host backend，host backend 又如何经 InterruptManager/MSI-X/IOAPIC/GIC 把中断送回 guest。

源码基线：当前仓库工作树。

相关：I/O 设备数据面、CPU 运行期/热插拔/迁移。

0. 术语与背景

三层中断抽象

层 职责
VirtioInterrupt（设备侧） 只区分 Config/Queue(index)，不碰 APIC/GIC
VirtioInterruptMsix（transport） 解析 vector + mask/PBA
InterruptManager/InterruptSourceGroup（VMM） GSI + irqfd + KVM route

两半方向

  • guest → host：VirtioTransport::ioeventfds() → DeviceManager 注册 PCI notification BAR 为 KVM ioeventfd（不经 write_bar 主路径）。
  • host → guest：VirtioInterruptMsix::trigger() → InterruptSourceGroup::trigger() → 写 irqfd → KVM 按 GSI route 注入。

关键：InterruptSourceGroup 不只写 eventfd

它还 update() route、set_gsi_routes() 提交 KVM routing table、notifier() 给 vhost-user/vDPA backend。

1. InterruptRoute + MsiInterruptGroup

// vmm/src/interrupt.rs:22
struct InterruptRoute { gsi: u32, irq_fd: Option<EventFd>, registered: bool }
impl InterruptRoute {
    pub fn enable(&mut self, vm: &dyn hypervisor::Vm) -> Result<()> {
        if !self.registered { if let Some(irq_fd) = &self.irq_fd { vm.register_irqfd(irq_fd, self.gsi)?; } self.registered = true; } Ok(())
    }
    pub fn trigger(&self) -> Result<()> { self.irq_fd.as_ref().unwrap().write(1) }   // 写 irqfd
}
// vmm/src/interrupt.rs:122
pub struct MsiInterruptGroup { vm: Arc<dyn hypervisor::Vm>, gsi_msi_routes: Arc<Mutex<HashMap<u32, RoutingEntry>>>, irq_routes: HashMap<InterruptIndex, Mutex<InterruptRoute>> }
// update: make_routing_entry + masked 过滤 set_gsi_routes + enable/disable
fn update(&self, index, config, masked, set_gsi) -> Result<()> {
    let entry = RoutingEntry { route: self.vm.make_routing_entry(route.gsi, &config), masked };
    if masked { route.disable(self.vm.as_ref())?; }
    routes.insert(route.gsi, entry);
    if set_gsi { self.set_gsi_routes(&routes)?; }   // set_gsi_routes 过滤 masked route 再 KVM_SET_GSI_ROUTING
    if !masked { route.enable(self.vm.as_ref())?; }
}

2. DeviceManager 依赖顺序（MSI manager 先于 IOAPIC/GIC）

// vmm/src/device_manager.rs:1248
// msi_interrupt_manager <- IOAPIC <- legacy_interrupt_manager（线性依赖链）
let msi_interrupt_manager = Arc::new(MsiInterruptManager::new(Arc::clone(&address_manager.allocator), vm));

x86_64 controller = IOAPIC（MMIO bus device）；aarch64 = GIC（Gic 对象不插 device tree）。两者都复用 MSI interrupt manager，但 snapshot/restore 状态完全不同。

3. ARM64 restore 边界 / 与 Firecracker 差异

aarch64 restore 顺序：interrupt controller creation → set_gicr_typers(saved_vcpu_states) → restore_vgic(vgic_state)——GIC 必须在设备 restore 前完成。与 Firecracker 差异：CH 多一层 InterruptManager/InterruptSourceGroup（设备经 group trigger index，route/eventfd/controller 由 manager 统一管）；FC 设备直接持 VirtioInterrupt，transport 直接写 eventfd，VM 直接维护 GSI route——CH 适合热插拔/vhost-user/VFIO/vDPA/迁移，FC 适合固定设备集 + 低开销。
