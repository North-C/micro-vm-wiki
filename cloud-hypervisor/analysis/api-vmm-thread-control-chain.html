Cloud Hypervisor API / VMM Thread 控制面链路

本文从源码解释 Cloud Hypervisor 的控制面：API 入口不直接修改 VM，而是把请求封装成闭包，写入 channel，再用 EventFd 唤醒 VMM thread。

源码基线：当前仓库工作树。本文不展开 TDX/SEV-SNP 等 CoCo 路线；相关内容已有独立专题。

1. 结论先行

Cloud Hypervisor 的控制面可以概括为：

mpsc::Sender<ApiRequest> 承载请求数据，EventFd 承载唤醒通知。VMM thread 在 EpollDispatch::Api 分支中读取 eventfd 计数，再从 channel 取出同等数量的闭包。

这意味着 HTTP thread、DBus thread 和主线程 CLI 只是请求生产者。真正改变 Vmm、VmConfig、Vm、CPU、memory、device 状态的代码，仍在 VMM thread 中串行运行。

2. 启动阶段

cloud-hypervisor/src/main.rs 的 start_vmm() 创建 API channel 和 api_evt。随后解析 seccomp、block VM/VMM 相关 signal，并创建 hypervisor 后端。

源码依据：

  • channel() 和 EventFd::new(EFD_NONBLOCK)：main.rs。
  • seccomp Trap 和 SIGSYS handler：main.rs。
  • signal mask：main.rs。
  • start_vmm_thread() 调用：main.rs。

普通 CLI 启动不是直接调用 Vmm::vm_create()。它先通过 VmCreate.send() 投递请求，再通过 VmBoot.send() 投递启动请求。

对应源码：

  • VmCreate.send(...)：main.rs。
  • VmBoot.send(...)：main.rs。
  • --restore 路径发送 VmRestore：main.rs。

3. VMM Thread

vmm::start_vmm_thread() 负责创建真正的 VMM thread。线程入口先应用 VMM thread 的 seccomp filter，然后构造 Vmm，安装 signal handler，最后进入 control_loop()。

源码依据：

  • start_vmm_thread() 参数包含 API eventfd、sender、receiver：vmm/src/lib.rs。
  • VMM thread 内应用 seccomp：vmm/src/lib.rs。
  • 构造 Vmm::new()：vmm/src/lib.rs。
  • 进入 control_loop()：vmm/src/lib.rs。
  • VMM thread 启动后才启动 DBus/HTTP：vmm/src/lib.rs。

这个顺序很关键：API 服务线程可以并发接收外部请求，但请求执行点已经被收束到 VMM thread。

4. ApiRequest

ApiRequest 不是枚举，而是一个闭包类型：

Box<dyn FnOnce(&mut dyn RequestHandler) -> Result<bool, VmmError> + Send + 'static>

源码注释解释了原因：带泛型 action 和 body 的请求对象不适合作为 trait object 传递，于是用闭包把 action、body、response sender 一起捕获。

源码依据：

  • ApiRequest 定义和注释：vmm/src/api/mod.rs。
  • ApiAction trait：vmm/src/api/mod.rs。
  • get_response() 创建 response channel：vmm/src/api/mod.rs。
  • api_sender.send(request)：vmm/src/api/mod.rs。
  • api_evt.write(1)：vmm/src/api/mod.rs。

因此一次 API 调用包含三步：构造闭包、发送闭包、写 eventfd。调用方随后阻塞在 response receiver 上，直到 VMM thread 执行闭包并回传结果。

5. API 入口

HTTP、DBus 和 CLI 都收敛到同一套 ApiAction::send()。入口层负责解析参数、JSON 或 DBus body，不负责直接调用 Vmm 方法。

HTTP 路由把 /vm.create、/vm.boot、/vm.restore、/vm.snapshot 等 endpoint 映射到 action handler。handler 再调用对应 ApiAction::send()。

源码依据：

  • HTTP endpoint trait 说明会发送 API request 并等待响应：http/mod.rs。
  • /vm.create endpoint 反序列化 VmConfig：http_endpoint.rs。
  • VmCreate.send(...)：http_endpoint.rs。
  • DBus 通用 vm_action() 调用 action.send()：dbus/mod.rs。
  • DBus vm_boot() 使用 VmBoot：dbus/mod.rs。

6. Epoll 注册

Vmm::new() 创建 EpollContext，并把 exit_evt、reset_evt、activate_evt、api_evt 注册进去。api_evt 的 token 是 EpollDispatch::Api。

源码依据：

  • EpollDispatch::Api = 2：vmm/src/lib.rs。
  • Vmm::new() 创建 epoll：vmm/src/lib.rs。
  • 注册 api_evt 为 EpollDispatch::Api：vmm/src/lib.rs。

VMM thread 的主循环不是只服务 API。exit、reset、virtio device activation、guest debug 等事件也通过同一个 epoll loop 进入。

7. API 分发

control_loop() 阻塞在 epoll::wait()。当 token 是 EpollDispatch::Api 时，它先读取 api_evt 的计数，再循环从 api_receiver 接收请求闭包。

源码依据：

  • epoll::wait() 主循环：vmm/src/lib.rs。
  • EpollDispatch::Api 分支：vmm/src/lib.rs。
  • api_evt.read()：vmm/src/lib.rs。
  • api_receiver.recv()：vmm/src/lib.rs。
  • 执行闭包 api_request(self)：vmm/src/lib.rs。

闭包参数是 &mut dyn RequestHandler，而 Vmm 实现了 RequestHandler。这让 API 层只依赖 trait，不直接暴露 Vmm 的完整内部结构。

8. Create 与 Boot

VmCreate 的闭包只调用 vmm.vm_create(config)。VmBoot 的闭包只调用 vmm.vm_boot()。二者在 API 层已经是两个独立动作。

源码依据：

  • VmBoot action 调用 vmm.vm_boot()：api/mod.rs。
  • VmCreate action 调用 vmm.vm_create(config)：api/mod.rs。

Vmm::vm_create() 的边界非常清楚：它只保存 VmConfig，预创建 console devices，并按配置应用 Landlock。源码注释明确说 VM 会在 boot 时创建。

源码依据：

  • vm_create() 注释和 vm_config 保存：vmm/src/lib.rs。
  • 重复 create 返回 VmAlreadyCreated：vmm/src/lib.rs。
  • 预创建 console devices：vmm/src/lib.rs。

Vmm::vm_boot() 才进入真实 VM 创建。它要求 vm_config 存在；如果 self.vm 为空，克隆 eventfd，调用 Vm::new(...)，然后执行 vm.boot()。

源码依据：

  • 缺少 config 返回 VmMissingConfig：vmm/src/lib.rs。
  • Vm::new(...)：vmm/src/lib.rs。
  • vm.boot()：vmm/src/lib.rs。

因此，Cloud Hypervisor 的生命周期不是“create 时创建所有 VM 对象”。当前源码下，它是“create 提交配置，boot 创建 VM 并运行”。

9. Snapshot 与 Restore

VmSnapshot action 调用 vmm.vm_snapshot(destination_url)。外层 vm_snapshot() 要求 self.vm 存在，然后调用 vm.snapshot() 并发送 snapshot。

源码依据：

  • VmSnapshot action：api/mod.rs。
  • 外层 vm_snapshot()：vmm/src/lib.rs。

内层 Vm::snapshot() 对状态更严格。Claude Code 交叉阅读确认，它要求 VM 处于 Paused，运行态 snapshot 会返回错误；TDX VM 也禁止 snapshot。

源码依据：

  • Vm::snapshot() 状态检查：vmm/src/vm.rs。

VmRestore action 调用 vmm.vm_restore(config)。外层 vm_restore() 要求当前没有 self.vm 和 self.vm_config，否则返回 VmAlreadyCreated。

源码依据：

  • VmRestore action：api/mod.rs。
  • restore 前状态约束：vmm/src/lib.rs。
  • 读取 snapshot config 并 validate：vmm/src/lib.rs。

内层 restore 读取 VM state snapshot，设置 self.vm_config，用 snapshot 参数调用 Vm::new(...)，再执行 vm.restore()。

源码依据：

  • 内层 vm_restore()：vmm/src/lib.rs。
  • snapshot 参数传入 Vm::new(...)：vmm/src/lib.rs。

10. 隔离边界

控制面隔离有三层：

层次 机制 源码落点
执行串行化 VMM thread 执行闭包 control_loop()
syscall 限制 seccomp filter start_vmm_thread()
文件访问限制 Landlock main/API/signal/VMM 路径

main.rs 在启动阶段解析 seccomp，并在 Trap 模式注册 SIGSYS 提示。start_vmm_thread() 又为 VMM thread 获取并应用专用 seccomp filter。

Landlock 的位置更分散：主线程在发出启动请求后对自身 restrict；HTTP thread 和 signal handler thread 也有对应限制；VM config 中的 Landlock 会影响设备路径。

这说明 Cloud Hypervisor 的隔离不是单点开关。它把 API thread、VMM thread、signal handler、设备路径约束拆在不同执行上下文中处理。

11. ARM64 与 x86_64

API/VMM thread 控制面本身没有明显 ARM64/x86_64 分叉。ApiAction::send()、ApiRequest、EventFd、mpsc channel、epoll dispatch 是共享代码。

架构差异从闭包进入具体 VM 操作后开始：

位置 x86_64 ARM64
restore 校验 KVM 下检查 CPUID compatibility 无同等 CPUID 路径
vCPU 配置 CPUID、Hyper-V、topology、nested vCPU init、MPIDR、GIC 语义
snapshot 元数据 可带 clock/common CPUID 不走 x86 CPUID 元数据
API 扩展 coredump 仅 x86_64 + guest_debug 无该 action

源码依据：

  • restore CPUID compatibility 仅 x86_64/KVM：vmm/src/lib.rs。
  • Vcpu::configure() 架构分流：vmm/src/cpu.rs。
  • x86_64 CPUID populate：vmm/src/cpu.rs。
  • snapshot x86_64 元数据：vmm/src/vm.rs。
  • x86_64 guest debug coredump action：api/mod.rs。

结论是：控制面调度机制跨架构一致，能力差异从 Vm::new()、Vm::boot()、CPU manager、memory/device manager 和 snapshot/restore 元数据开始体现。

12. 能力边界

问题 结论
API 线程会直接改 VM 吗 不会，API 线程发送闭包并等待响应
vm_create 是否创建 VM 不创建，只保存配置和预处理 console/Landlock
vm_boot 是否可无配置启动 不可，无 vm_config 返回 VmMissingConfig
snapshot 是否可在 running 态执行 外层只要求 VM 存在，内层要求 Paused
restore 是否可覆盖已有 VM 不可，已有 VM 或 config 都报 VmAlreadyCreated
ARM64 控制面是否另有路径 没有，差异在 VM/CPU/设备实现层

这条链路给后续阅读一个明确边界：研究 API 能力时看 ApiAction 和 RequestHandler；研究虚拟化机制时必须继续进入 Vm::new()、Vm::boot() 和各 manager。
