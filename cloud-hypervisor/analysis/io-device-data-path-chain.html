    Cloud Hypervisor I/O 设备数据面链路

    本文从源码追踪 Cloud Hypervisor 非机密计算路径下的 block、net、fs、vhost-user 和 vDPA I/O 设备数据面。

    源码基线：当前仓库工作树。

    相关：DeviceManager 设备链路、运行期控制与热插拔、横向 Virtio data path cross-project。

    0. 术语与背景

    virtio 设备生命周期的两个阶段

    Cloud Hypervisor 的 I/O 数据面分配置阶段和运行阶段，中间靠 activate() 衔接：

    阶段 做什么 启动 worker？
    配置阶段 make_virtio_devices 建 VirtioDevice + MetaVirtioDevice，包成 VirtioPciDevice，注册 ioeventfd/MSI-X 否
    运行阶段 guest driver 配完 queue + DRIVER_OK → transport 触发 activate() → 设备起 worker 线程 是

    关键：配置阶段看不到 worker——worker 只能在 guest 完成 feature ack、queue 配置、DRIVER_OK 后启动。activate() 是数据面真正开始的边界。

    三类后端，数据面落点不同

    后端 数据面在哪 例子
    普通 virtio VMM 进程内（每 queue 一个 epoll 线程） block BlockEpollHandler、net NetEpollHandler
    vhost-user 外部 backend 进程（VMM 只持 frontend + 控制面） virtiofsd、vhost-user-net
    vDPA 内核 vhost-vDPA / 硬件 厂商 vDPA 设备

    三者共享 virtio-PCI 暴露与 activation 模型，区别是"谁消费 vring"。

    MetaVirtioDevice / ActivationContext / ioeventfd·irqfd

    • MetaVirtioDevice：DeviceManager 内部统一包装（virtio device + iommu 标志 + id + PCI segment + 可选 DMA handler）。
    • ActivationContext：activate 时一次性把 guest memory、interrupt callback、queues、device status 交给设备。
    • ioeventfd / irqfd：见 中断与事件通知——ioeventfd 处理 guest→device 的 notify（写 notification BAR），irqfd/MSI-X 处理 device→guest 的完成中断。

    1. 核心结论

    • 配置阶段创建 VirtioDevice/MetaVirtioDevice；运行阶段等 guest ready 后 PCI transport 触发 activate()。
    • 普通 block/net 数据面在 VMM 进程内（block 每 queue 一个 BlockEpollHandler，net 每 queue pair 一个 NetEpollHandler）。
    • vhost-user 把 vring/memory table/eventfd 交给外部 backend；vDPA 把 vring + DMA mapping 交给内核 vhost-vDPA。
    • 所有 virtio 设备统一经 VirtioPciDevice 暴露；ARM64/x86_64 差异在 PCI/ACPI/FDT/GIC/IOAPIC/MSI 暴露层，不在 queue handler 核心逻辑。

    2. 总体链路

    flowchart LR Config["VmConfig disks/net/fs/vdpa"] --> DM["DeviceManager"] DM --> Make["make_virtio_devices"] Make --> Meta["MetaVirtioDevice"] Meta --> PCI["VirtioPciDevice"] PCI --> Ready["guest driver ready"] Ready --> Activate["activate event"] Activate --> Device["VirtioDevice.activate"] Device --> Worker["epoll worker/backend"]

    MetaVirtioDevice 是 DeviceManager 内部统一包装（device_manager.rs:915）。device_tree 被注释为用于 introspection/snapshot/restore——设备数据面不是孤立线程，必须能回到 device tree 做状态保存恢复（:1047）。

    3. 设备创建顺序

    make_virtio_devices() 是启动期创建 virtio 设备的总入口，顺序固定：

    // vmm/src/device_manager.rs:2547
fn make_virtio_devices(&mut self) -> DeviceManagerResult<()> {
    self.make_virtio_block_devices()?;       // block
    self.make_virtio_net_devices()?;         // net
    self.make_virtio_rng_devices()?;         // rng
    self.make_generic_vhost_user_devices()?; // generic vhost-user
    self.make_virtio_fs_devices()?;          // fs
    self.make_virtio_pmem_devices()?;        // pmem
    self.make_virtio_vsock_devices()?;       // vsock
    self.make_virtio_mem_devices()?;         // mem
    self.make_virtio_balloon_devices()?;     // balloon
    self.make_virtio_watchdog_devices()?;    // watchdog
    self.make_vdpa_devices()?;               // vDPA
    Ok(())
}

    DeviceManager::new() 添加 legacy/ACPI/console 后调它，再 add_pci_devices()（:1496）。此入口只建设备对象放入 self.virtio_devices，不起数据面线程。block 按 DiskConfig 分 vhost-user block 与普通 Block（开 disk image、检测 image type、选 raw/qcow2/vhd/vhdx，:2611）；net 按 NetConfig 分 vhost-user net / tap fd / tap name / 自动 tap（:2917）；fs 走 vhost-user fs（从 FsConfig.socket，:3196）；vDPA 从 VdpaConfig.path 建 Vdpa + VdpaDmaMapping（:3695）。

    4. PCI Transport 与 Activation 分界

    add_virtio_pci_device() 把 MetaVirtioDevice 包成 VirtioPciDevice：分配 BDF/BAR、算 MSI-X 向量数（queue 数 + 1，多的 1 个给 config change）、注册 ioeventfd：

    // vmm/src/device_manager.rs:4191
fn add_virtio_pci_device(&mut self, virtio_device, iommu_mapping, virtio_device_id, pci_segment_id, dma_handler)
    -> DeviceManagerResult<PciBdf> {
    // ...
    // MSI-X 向量 = queue 数 + 1（多的 1 个给 config change 通知）
    let msix_num = (virtio_device.lock().unwrap().queue_max_sizes().len() + 1) as u16;
    let virtio_pci_device = VirtioPciDevice::new(id, memory, virtio_device, msix_num,
        access_platform, self.msi_interrupt_manager.as_ref(), pci_device_bdf.into(),
        self.activate_evt.try_clone()?, /*...*/)?;
    // ...
    let bar_addr = virtio_pci_device.lock().unwrap().config_bar_addr();
    for (event, addr) in virtio_pci_device.lock().unwrap().ioeventfds(bar_addr) {  // 为每个 queue 注册 ioeventfd
        self.address_manager.vm.register_ioevent(event, &IoEventAddress::Mmio(addr), None)?;
    }
    Ok(pci_device_bdf)
}
    sequenceDiagram participant DM as DeviceManager participant PCI as VirtioPciDevice participant Guest as guest driver participant VMM as VMM epoll participant Dev as VirtioDevice DM->>PCI: add_virtio_pci_device DM->>Guest: expose PCI BAR/MSI-X/ioeventfd Guest->>PCI: set DRIVER_OK PCI->>VMM: activate_evt VMM->>DM: activate_virtio_devices DM->>PCI: VirtioPciDeviceActivator.activate PCI->>Dev: activate(context)

    本文覆盖的 block/net/fs/vhost-user/vDPA 主路径是 virtio-pci，不是 virtio-mmio（add_pci_devices 统一调 add_virtio_pci_device，:1648）。guest driver ready 时 VirtioPciDevice 把 activator 推入 pending_activations、写 activate_evt（pci_device.rs:1234）；VMM epoll 收 ActivateVirtioDevices → vm.activate_virtio_devices() → drain pending → activate()（lib.rs:1718、vm.rs:2925）。

    5. ActivationContext（activate 的边界）

    VirtioDevice trait：设备先移入 transport，guest 配置完后 transport 调 activate()，把事件/memory/queues 移交（device.rs:70）。VirtioPciDeviceActivator::activate() 构造 ActivationContext：

    // virtio-devices/src/transport/pci_device.rs:314
pub fn activate(mut self) -> ActivateResult {
    let mut locked_device = self.device.lock().unwrap();
    locked_device.activate(crate::device::ActivationContext {
        mem: self.memory.take().unwrap(),
        interrupt_cb: self.interrupt.take().unwrap(),
        queues: self.queues.take().unwrap(),
        device_status: self.status,
    })?;                                       // 一次性交给具体设备
    self.device_activated.store(true, Ordering::SeqCst);
    // ... barrier ...
}

    VirtioCommon::activate() 做通用准备（kill eventfd、pause eventfd、interrupt callback、queue 数检查，device.rs:241）。

    6. Block 数据面

    flowchart LR Notify["queue eventfd"] --> Handler["BlockEpollHandler"] Handler --> Queue["virtqueue descriptors"] Queue --> Request["blk request parse/check"] Request --> Backend["DiskBackend async/sync"] Backend --> Used["used ring"] Used --> IRQ["virtio queue interrupt"]

    Block::activate() 为每个 queue 建 BlockEpollHandler 并 spawn_virtio_thread 启动线程（block.rs:1079/1151）：

    // virtio-devices/src/block.rs:1079
fn activate(&mut self, context: ActivationContext) -> ActivateResult {
    let ActivationContext { mem, interrupt_cb, mut queues, device_status } = context;
    self.common.activate(&queues, interrupt_cb.clone())?;     // 通用准备
    // ...
    for i in 0..queues.len() {
        let (_, mut queue, queue_evt) = queues.remove(0);
        // ...
        let mut handler = BlockEpollHandler {
            queue, mem: mem.clone(),
            disk_image: self.disk_image.new_async_io(queue_size)?,  // async I/O
            interrupt_cb: interrupt_cb.clone(),
            rate_limiter: self.rate_limiter.as_ref().map(|r| r.new_handle())?,
            // ...
        };
        spawn_virtio_thread(&format!("{}_q{}", self.id, i), &self.seccomp_action,
            Thread::VirtioBlock, &mut epoll_threads, &self.exit_evt,
            move || handler.run(&paused, paused_sync.as_ref().unwrap()))?;   // 每 queue 一线程
    }
    // ...
}

    请求处理从 descriptor chain 解析 virtio-blk request、检查读写类型/限速/sector0 写保护、调 execute_async()（block.rs:260）。后端在创建阶段选：raw 可走 io_uring/AIO/sync，qcow2 走 sync，vhost-user block 绕过本地 backend（device_manager.rs:2711）。

    7. Net 数据面

    flowchart LR Tap["TAP fd"] --> RxTx["NetQueuePair"] GuestQ["RX/TX queues"] --> Handler["NetEpollHandler"] Handler --> Tap Handler --> Used["used ring"] Used --> IRQ["queue interrupt"]

    Net::activate() 先判断有无 control queue（单独 VirtioNetCtl 线程），再按 queue pair 启动 VirtioNet 线程（net.rs:743/797）：

    // virtio-devices/src/net.rs:743
fn activate(&mut self, context: ActivationContext) -> ActivateResult {
    // ...
    let has_ctrl_queue = self.common.feature_acked(VIRTIO_NET_F_CTRL_VQ) && !num_queues.is_multiple_of(2);
    if has_ctrl_queue {
        // control queue 单独线程 NetCtrlEpollHandler
        spawn_virtio_thread(/* ... VirtioNetCtl ... move || ctrl_handler.run_ctrl(...) */)?;
    }
    for i in 0..queues.len() / 2 {
        // 每个 RX/TX queue pair: RxVirtio/TxVirtio + tap + rate limiter + NetEpollHandler
        tap.set_offload(virtio_features_to_tap_offload(self.common.acked_features))?;
        let handler = NetEpollHandler { net: NetQueuePair { tap, rx, tx, /*...*/ }, /*...*/ };
        spawn_virtio_thread(/* ... VirtioNet ... move || handler.run(...) */)?;
    }
}

    handler 在 rate limit 未阻塞时监听 TAP fd 的 EPOLLIN，TX 完成后按条件触发 used queue interrupt（net.rs:210）。普通 net 数据面在 VMM 内直接处理 TAP 与 virtqueue，不需要 guest agent。

    8. vhost-user 与 fs

    vhost-user block/net/fs 仍暴露为 virtio PCI 设备，但 vring 实际消费在外部 backend。VhostUserCommon::activate() 调 setup_vhost_user() 把 guest memory/queues/interrupt/features/backend handler/inflight 交给 backend（vhost_user/mod.rs:351）：

    // virtio-devices/src/vhost_user/mod.rs:351
pub fn activate<T: VhostUserFrontendReqHandler>(&mut self, mem, queues, interrupt_cb,
    acked_features, backend_req_handler, kill_evt, pause_evt) -> Result<VhostUserEpollHandler<T>, ActivateError> {
    let mut inflight = /* 若协商 INFLIGHT_SHMFD 则 Some，支持迁移日志 */;
    let vu = self.vu.as_ref().unwrap();
    vu.lock().unwrap().setup_vhost_user(
        &mem.memory(), &queues, interrupt_cb.as_ref(), acked_features,
        &backend_req_handler, inflight.as_mut(), vring_bases.as_deref())?;   // vring/memory/eventfd 交给 backend
    // ...
}

    vhost-user fs 的 activate() 先 common activate 再 vu_common.activate()，fs 自己不起本地 FUSE worker，依赖 vhost-user backend（vhost_user/fs.rs:255）；vhost-user net 类似，control queue 在 VMM 内、数据 queue 交 backend（vhost_user/net.rs:284）。vhost-user snapshot 可含 backend state + vring bases（前提 backend 支持 device state，mod.rs:486）。

    9. vDPA 数据面

    vDPA 数据面主要在内核 vhost-vDPA + 硬件 backend。CH 负责配 vring 地址、kick/call eventfd、DMA mapping。Vdpa::activate_vdpa() 对每 queue 设 vring num/addr/base/call eventfd/kick eventfd（vdpa.rs:218），再设 config call、enable vrings、置 status 为 ACKNOWLEDGE|DRIVER|DRIVER_OK|FEATURES_OK（:300）。DeviceManager 创建时建 VdpaDmaMapping，设备不在 virtual IOMMU 后面时把 guest memory zones 映射给 DMA handler（device_manager.rs:3726/3695）。

    10. 中断与 ioeventfd

    • guest→device：queue eventfd。CH 在 virtio PCI notification BAR 注册 ioeventfd，guest 写 BAR 不走普通 MMIO exit（pci_device.rs:850；SEV-SNP 下还有显式 fallback，:1202）。
    • device→guest：VirtioInterrupt。worker 更新 used ring 后触发 queue interrupt；config 变化触发 config interrupt。PCI 下实现是 VirtioInterruptMsix：
    // virtio-devices/src/transport/pci_device.rs:885
fn trigger(&self, int_type: VirtioInterruptType) -> std::result::Result<(), std::io::Error> {
    let vector = match int_type {
        VirtioInterruptType::Config => self.config_vector.load(Ordering::Acquire),
        VirtioInterruptType::Queue(i) => self.queues_vectors.lock().unwrap()[i as usize],
    };
    if vector == VIRTQ_MSI_NO_VECTOR { return Ok(()); }
    let config = &mut self.msix_config.lock().unwrap();
    let entry = &config.table_entries[vector as usize];
    if config.masked() || entry.masked() {            // masked → 只记 PBA pending
        config.set_pba_bit(vector, false);
        return Ok(());
    }
    self.interrupt_source_group.trigger(vector as InterruptIndex)   // 否则触发 MSI-X
}

    vhost-user 和 vDPA 通过 VirtioInterrupt::notifier() 把 call/config eventfd 交给 backend；backend 写 eventfd 后仍走同一 MSI-X interrupt group（:913）。net handler 检测坏 virtqueue 时设 DEVICE_NEEDS_RESET 并经 config interrupt 通知 guest（net.rs:227）。

    11. Snapshot 与 Restore 边界

    DeviceManager 的 device_tree 是 snapshot/restore 的依赖来源：virtio device node、virtio-pci parent node、PCI BDF、BAR resources 都写入（device_manager.rs:4324）。普通 block/net 由本地 migratable state 保存；vhost-user 还可存 backend state + vring bases（vhost_user/mod.rs:500）。virtio-pci transport 自身存 VirtioPciDeviceState + PCI config + common config + MSI-X（pci_device.rs:1305）。vDPA snapshot 只在 live migration 期间允许，否则报错；迁移开始要求 backend 支持 suspend（vdpa.rs:491）。Vm::device_tree() 直接返回 tree 供 migration/snapshot 读（vm.rs:2906）。磁盘锁非创建时统一获取——Vm::boot() 启动前获取 advisory disk image locks 以支持 live migration（vm.rs:2606）。

    12. ARM64 与 x86_64 差异

    I/O worker 核心路径基本不分架构（block/net/vhost-user/vDPA queue handler 是通用 Rust）。差异在设备枚举与中断路由：

    维度 x86_64 ARM64/RISC-V
    设备描述 ACPI/PCI id_to_dev_info + FDT/平台描述（device_manager.rs:1055）
    PCI config 传统 I/O port + MMCONFIG（pci_segment.rs:119） 只走 MMCONFIG（:69）
    中断控制器 local x2APIC + IOAPIC（cpu.rs:1733） GICC/GICD/GICR + ITS/MSI frame（:1775）
    MSI IOVA APIC MSI range 从 GIC config 取（device_manager.rs:1575）
    FDT — GIC node + PCIe controller node（fdt.rs:660/926）

    对 I/O 性能与兼容性，ARM64/x86_64 差异主要来自 guest kernel、PCIe/GIC/MSI 支持、IOMMU、设备枚举——不是 virtqueue worker 算法。

    13. 能力边界

    • CH 是 VMM 级 I/O 数据面——不理解容器 rootfs/pod 网络，普通 block/net 不需 guest agent。
    • 普通 virtio 后端在 VMM 进程内；vhost-user 把数据面移到外部进程；vDPA 推到内核/硬件。三者共享 virtio-PCI 暴露与 activation 模型。
    • runtime hotplug 与启动期创建共享 MetaVirtioDevice + add_virtio_pci_device()，但 hotplug 还要通知 guest ACPI/GED。
    • snapshot/restore 需同时恢复 device state、transport state、PCI resources、queue state、外部 backend state。vhost-user 是否可迁移取决于 backend capability。

    14. 对比提示

    • vs Firecracker：CH 设备模型覆盖面更宽，PCI 和 vhost-user/vDPA 是一等路径；Firecracker 强调最小设备集 + 单进程。
    • vs Kata：CH 只提供 VM I/O 能力；Kata 要把 container rootfs/volume/network 翻译成 hypervisor 设备 + guest agent 请求。
    • vs CubeSandbox：CH 的 I/O 数据面是底层 VMM 能力；CubeSandbox 在其上叠加 snapshot catalog、CubeCoW、network-agent、产品级 ready/rollback 语义。
