    Cloud Hypervisor VM Create / Boot 构建链路

    本文解释 CH 整机创建与启动路径：vm_create → vm_boot → Vm::new → Vm::boot 如何把 hypervisor VM、guest memory、vCPU、设备和机器描述连成可运行 VM。

    源码基线：当前仓库工作树。聚焦普通 VM 主路径；TDX/SEV-SNP 只作能力边界提示。

    相关：CPU 运行期/热插拔/迁移、I/O 设备数据面、横向 启动路径与控制面。

    0. 术语与背景

    vm_create 不是"创建虚拟机"

    vm_create 只保存 VmConfig + 预创建 console + Landlock。真正的 VM 对象在 vm_boot 内 Vm::new(...) 时才创建。

    常见误解：vm_create 后并没有 Vm、没有 vCPU、没有 guest memory slot、没有设备树——只把 boot 所需配置和少量宿主侧资源准备好。

    两层构建：Vm::new（静态对象图）+ Vm::boot（推进到可运行）

    阶段 做什么
    Vm::new 建静态对象图：hypervisor VM、MemoryManager、CpuManager、DeviceManager、bus、interrupt controller、devices、boot vCPU、payload loader
    Vm::boot 推进到可运行：锁磁盘、等 kernel/firmware load、配置 ACPI/FDT/boot params、配置 vCPU、resume hypervisor VM、启动 boot vCPU

    关键边界

    • vm_create ≠ 资源冻结点——真正资源对象在 vm_boot（Vm::new）创建，看能力边界必须看 Vm::new 和各 manager。
    • 设备不在 Vm::boot 才创建——多数设备在 Vm::new 的 hypervisor_specific_init 创建；Vm::boot 偏向启动参数/vCPU 配置/运行态切换。
    • pending virtio activation 是延后 activation 的补充机制（VMM epoll activate event / pause 前 drain），非设备创建主入口。

    控制面：并发 API 收束到单 VMM thread

    API 请求封装成 ApiRequest 闭包经 channel + api_evt 唤醒 VMM thread。外部 HTTP/DBus/CLI 不直接持有修改 Vm，而是提交闭包等响应。

    1. 结论先行

    • vm_create 只存 VmConfig（+console/Landlock）；vm_boot 才 Vm::new() 构造 VM，Vm::boot() 完成系统配置 + hypervisor resume + start_boot_vcpus()。
    • Vm::new() 建静态对象图；Vm::boot() 推进到可运行。
    flowchart LR API["API / CLI / DBus"] --> Create["vm_create"] Create --> Config["保存 VmConfig\n预创建 console/Landlock"] Config --> BootReq["vm_boot"] --> New["Vm::new"] New --> MM["MemoryManager"]; New --> CPU["CpuManager"]; New --> DEV["DeviceManager"] New --> Loader["payload_loader"]; New --> BootVcpu["create_boot_vcpus"] BootReq --> Boot["Vm::boot"] Boot --> Sys["ACPI/FDT/boot params"]; Boot --> ConfigVcpu["configure_vcpu"]; Boot --> Run["start_boot_vcpus"]

    2. vm_create / vm_boot 边界

    // vmm/src/lib.rs:1783
fn vm_create(&mut self, config: Box<VmConfig>) -> Result<(), VmError> {
    // We only store the passed VM config. The VM will be created when being asked to boot it.
    if self.vm_config.is_some() { return Err(VmError::VmAlreadyCreated); }
    self.vm_config = Some(Arc::new(Mutex::new(*config)));
    self.console_info = Some(pre_create_console_devices(self)?);    // 预创建 console
    if /* landlock_enable */ { apply_landlock(&mut config)?; }      // Landlock
    Ok(())
}
// :1805
fn vm_boot(&mut self) -> Result<(), VmError> {
    if self.vm_config.is_none() { return Err(VmError::VmMissingConfig); }
    if self.console_info.is_none() { self.console_info = Some(pre_create_console_devices(self)?); }  // shutdown 后重建
    if self.vm.is_none() {
        let vm = Vm::new(/* vm_config, exit_evt, reset_evt, hypervisor, ... */)?;   // 此时才建 VM
        self.vm = Some(vm);
    }
    self.vm.as_mut().unwrap().boot()                                // boot 拆两层：vm_boot 建 Vm，Vm::boot 推进运行
}

    5. hypervisor_specific_init（new→boot 桥梁）

    // vmm/src/vm.rs:835
fn hypervisor_specific_init(/*...*/) -> Result<Option<thread::JoinHandle<Result<EntryPoint>>>> {
    // ... mshv/sev_snp 特定 ...
    memory_manager.lock().unwrap().allocate_address_space()?;                 // 地址空间分配
    #[cfg(target_arch="aarch64")] memory_manager.lock().unwrap().add_uefi_flash()?;  // ARM64 UEFI flash
    let load_payload_handle = if snapshot.is_none() {                         // 非恢复：异步加载 payload
        Self::load_payload_async(memory_manager, config, /*...*/)?
    } else { None };
    cpu_manager.lock().unwrap().create_boot_vcpus(/*cpu snapshot*/)?;         // 创建 boot vCPU
    #[cfg(feature="kvm")] if is_kvm { Self::init_kvm(vm, device_manager, /*...*/)?; }  // KVM init + interrupt controller + create_devices
    Ok(load_payload_handle)
}

    payload 加载拆异步线程，Vm::boot 后续 entry_point() join 获 EntryPoint，让启动准备与 kernel load 并行。x86_64 load_kernel 先试 ELF PVH 再 bzImage；aarch64 firmware 加载到 UEFI flash，kernel 先按 PE 再按 UEFI binary（vm.rs:1484/1546/1402）。

    6. Vm::boot 启动阶段

    // vmm/src/vm.rs:2599
pub fn boot(&mut self) -> Result<()> {
    if self.state == VmState::Paused { return self.resume(); }                // Paused 直接 resume
    self.device_manager.lock().unwrap().try_lock_disks()?;                    // 磁盘 advisory locks（支持迁移）
    let new_state = if self.stop_on_boot { VmState::BreakPoint } else { VmState::Running };
    self.state.valid_transition(new_state)?;
    #[cfg(target_arch="x86_64")] let rsdp_addr = self.create_acpi_tables();   // x86 早建 ACPI（与 kernel load 并行）
    let entry_point = self.entry_point()?;                                    // join payload_loader
    for vcpu in self.cpu_manager.lock().unwrap().vcpus() {
        self.cpu_manager.lock().unwrap().configure_vcpu(&mut vcpu, boot_setup)?;  // 配置 vCPU
        #[cfg(target_arch="aarch64")] vcpu.set_gic_redistributor_addr(/*...*/)?;
    }
    #[cfg(target_arch="aarch64")] let rsdp_addr = self.create_acpi_tables();  // ARM64 配置后建 ACPI（依赖 MPIDR）
    self.configure_system(rsdp_addr, entry_point)?;                           // boot params/FDT/cmdline/RSDP
    if self.state == VmState::Created { self.vm.resume()?; }                  // resume hypervisor VM
    self.cpu_manager.lock().unwrap().start_boot_vcpus(/*breakpoint*/)?;       // 启动 boot vCPU
    self.state = new_state;
}

    7. 系统描述与启动参数（架构差异）

    x86_64 在 Vm::boot 较早建 ACPI tables（与 kernel loading 并行），configure_system 写 boot params/cmdline/initramfs/RSDP/serial/UUID/OEM strings/topology（vm.rs:1644）。aarch64 ACPI 创建更晚（依赖 vCPU 配置后的 MPIDR），configure_system 主要生成 FDT（输入 MPIDR/topology/device info/PCI space/VGIC/NUMA/PMU，:1705）。

    x86_64 启动材料更像 PC boot params + ACPI RSDP；aarch64 更像 FDT + GIC/MPIDR/UEFI 生态（也可生成 ACPI 表）。

    8. ARM64 与 x86_64 差异 / 能力边界

    维度 x86_64 aarch64
    hypervisor VM init identity map/TSS/split IRQ 无 x86 PC 兼容初始化
    CPU 身份 populate_cpuid/CPUID/topology MPIDR/GIC redistributor
    kernel 格式 ELF PVH 或 bzImage PE kernel 或 UEFI binary fallback
    firmware x86 load kernel 路径 UEFI flash 显式内存对象
    机器描述 boot params + ACPI RSDP FDT 为核心（也可 ACPI）
    中断控制器 IOAPIC/MSI GIC/VGIC/redist
    ACPI 创建时机 boot 早期（并行 kernel load） vCPU 配置后（依赖 MPIDR）

    能力边界：CH 支持通用 cloud VM（多后端 hypervisor/热插拔/snapshot/restore/migration/NUMA/PCI/多种 virtio/vhost/vfio）。但 vm_create 不是资源冻结点；设备多在 Vm::new 的 hypervisor_specific_init 创建（非 Vm::boot）；pending virtio activation 是补充机制（VMM epoll ActivateVirtioDevices + pause 前 drain，lib.rs:1722/vm.rs:2925/3086）。

    9. 与 Firecracker 对照

    Firecracker build_microvm_for_boot 更像一次性 builder：消费 VmResources 创建 guest memory/KVM VM-vCPU/DeviceManager/kernel-initrd/设备/arch boot config，得 paused microVM。CH 边界不同：vm_create 只存配置，vm_boot 才 Vm::new()，Vm::boot() 自己完成系统配置 + hypervisor resume + start_boot_vcpus()。

    这解释两者架构气质：Firecracker 强调 pre-boot 配置冻结 + 最小设备面；CH 强调 manager 化对象图 + 运行期控制 + 热插拔 + 迁移。
