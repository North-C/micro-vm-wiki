    Cloud Hypervisor ARM64 网络准样本：Restore 后网络异常

    本文承接 ARM64 网络失败原型 和 DeviceTree / 热插拔 / Restore 链路。

    前面的 Cloud Hypervisor 准样本已经覆盖了：

    1. 启动期多网卡枚举
    2. ARM64 MSI 可见性
    3. 运行期 add-net / hotplug 失败

    这一篇继续补当前最明显的剩余空洞：

    restore 后网络异常

    这不是一份真实故障回放。

    它是一份把 restore / GIC-state 协同问题整理成可直接套用结构的准样本。

    源码基线：当前工作树。

    1. 样本定位

    Cloud Hypervisor 的 ARM64 网络在启动期和热插阶段已经有比较好的准样本覆盖。

    但这还不够。

    因为还有一类问题只会在 restore 之后暴露：

    设备看起来还在，但网络中断或可用性不再闭环。

    这类问题不属于：

    1. vm_add_net() 配置失败
    2. tap/backend 打开失败
    3. guest 启动期枚举未完成

    它更像 restore 边界上的状态协同问题。

    2. 为什么 restore 必须单独建样本

    ARM64 restore 路径里，Gic 会显式执行三步：

    1. set_gicr_typers(saved_vcpu_states)
    2. restore_vgic(state, saved_vcpu_states)
    3. enable()

    源码依据：gic.rs。

    这意味着 restore 后的网络可用性，不只依赖 net device 自己还在。

    它还依赖：

    ARM64 GIC state 是否真的恢复到能继续承接设备中断的状态。

    所以这类样本不能和普通启动期样本混写。

    3. 最小触发现象

    这类样本最少应满足三段现象：

    1. restore 前网络正常
    2. restore 流程完成
    3. restore 后网络异常

    如果缺第一段，就不能证明这是回归。

    如果缺第二段，就不能证明故障真的发生在 restore 边界。

    如果缺第三段，就不能构成失败样本。

    4. 准样本结构

    建议最小结构如下：

    [Scenario]
arch = arm64
stage = snapshot -> restore
pre_restore_network = healthy

[Pre-Restore Evidence]
evidence = guest network usable
evidence = device path previously healthy

[Restore Evidence]
evidence = restore completed
evidence = GIC restore path executed

[Post-Restore Failure]
symptom = device still present but network unavailable
or
symptom = restore after interrupt/network regression

[Classification]
layer = restore / GIC-state coordination
not = pure vm_add_net failure
not = pure tap/backend failure
not = pure startup guest discovery failure

    5. 它实际证明了什么

    如果一份样本能满足上面的结构，它至少证明两件事。

    第一，问题已经晚于启动期设备构造和启动期 guest 枚举。

    第二，问题更接近：

    restore 后 GIC state 与网络设备状态之间的协同缺口

    这正是 Cloud Hypervisor ARM64 和普通启动期样本最不同的地方。

    6. 为什么它和 hotplug 样本不同

    hotplug 样本关注的是：

    add-net API -> BDF -> guest convergence

    而 restore 样本关注的是：

    已有设备在恢复后是否还能继续工作

    它们对应的是两条完全不同的时间轴。

    因此后续做真实样本时，不能把 hotplug 失败和 restore 回归合并成一类。

    7. 为什么它和 PCI MSI 样本不同

    PCI MSI 样本更像“启动期的 interrupt visibility 证据”。

    restore 样本则更像“恢复后的 interrupt continuity 证据”。

    即便两者都和中断有关，关注的也不是同一个问题。

    前者问：

    guest 有没有看到它

    后者问：

    restore 之后它还能不能继续正常工作

    8. 建议保留的关键证据

    如果后续把它升级成真实 ARM64 样本，建议至少保留：

    1. scenario.md
    2. pre-restore.txt
    3. restore.txt
    4. post-restore.txt
    5. classification.md

    其中 classification.md 至少要明确回答：

    1. 为什么认定 restore 前网络是好的
    2. 为什么认定 restore 本身完成了
    3. 为什么判断问题落在 restore / GIC-state coordination

    9. 当前最缺的证据是什么

    这类样本当前最缺的不是框架。

    而是一份真正把：

    pre-restore success -> restore complete -> post-restore network regression

    串起来的 ARM64 失败日志包。

    所以这篇准样本的价值不是替代真实样本。

    而是给未来的真实日志一个明确的归档口径。

    10. 结论

    restore 后网络异常 是 Cloud Hypervisor ARM64 网络线上当前最值得补齐的下一块准样本。

    它补上的不是一个新概念。

    而是把 Gic::restore_vgic()、set_gicr_typers()、enable() 之后的网络可用性问题单独固定下来。
