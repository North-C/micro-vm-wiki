1. API / VMM thread 控制面

研究目标：确认 API 请求如何进入 VMM thread，以及 vm_create、vm_boot 的真实生命周期边界。

入口路径：

关键源码：

  • ApiRequest 是闭包类型，由 API 入口发送到 channel，并通过 api_evt.write(1) 唤醒 VMM thread：vmm/src/api/mod.rs。
  • Vmm::new() 把 api_evt 注册为 EpollDispatch::Api：vmm/src/lib.rs。
  • control_loop() 在 EpollDispatch::Api 分支读取 eventfd、接收闭包并执行 api_request(self)：vmm/src/lib.rs。
  • vm_create() 只保存 VmConfig，预创建 console devices，并按需应用 Landlock：vmm/src/lib.rs。
  • vm_boot() 要求已有 vm_config，然后调用 Vm::new(...) 并执行 vm.boot()：vmm/src/lib.rs。

机制结论：

  1. API thread 不直接修改 VM；它只提交闭包并等待 response。
  2. vm_create 不创建 Vm，只提交配置和预处理 console/Landlock。
  3. vm_boot 才创建 Vm，并继续进入 CPU、memory、device manager 的启动路径。
  4. ARM64/x86_64 差异不在 API/VMM thread 调度层，而在 Vm::new()、Vm::boot() 和各 manager 内部。

验证建议：

  1. 用 codegraph_trace 跟踪 VmCreate -> vm_create 与 VmBoot -> vm_boot。
  2. 对比 CLI、HTTP、DBus 三个入口是否都走 ApiAction::send()。
  3. 用日志或断点确认 vm_create 后 self.vm 仍为空，vm_boot 后才出现 Vm。

专题进展：

  • 已完成 API / VMM thread 控制面链路，覆盖线程启动、ApiRequest 闭包、epoll 分发、create/boot/restore/snapshot 边界和 ARM64/x86_64 差异起点。
  • 已完成 VM create / boot 构建链路，覆盖 vm_create、vm_boot、Vm::new、MemoryManager、CpuManager、DeviceManager、payload loader、Vm::boot 和 ARM64/x86_64 启动分叉。

2. CpuManager：vCPU 生命周期与热插拔

研究目标：理解 vCPU 如何创建、配置、运行、暂停、恢复、snapshot，以及 ARM64/x86 的差异入口。

核心结构：

  • CpuManager 保存 CPU config、interrupt controller、hypervisor VM、vCPU 状态数组、vCPU 对象、pause/kill/kick 信号、seccomp action、VM ops、NUMA/affinity、dynamic 等字段：vmm/src/cpu.rs。
  • Vcpu::configure() 在架构上分流：ARM64 调 self.init(vm) 后通过 arch::configure_vcpu() 得到 MPIDR；x86_64 把 CPUID、Hyper-V、topology、nested 等参数传给 arch::configure_vcpu()：vmm/src/cpu.rs。

机制结论：

  1. CPU 热插拔通过 CpuManager 暴露的 CPU selection/status 设备与 ACPI/guest 协作。
  2. x86_64 的 vCPU 配置核心是 CPUID/topology/nested/Hyper-V 语义。
  3. ARM64 的 vCPU 配置核心是 KVM init、MPIDR、GIC redistributor 等 ARM CPU/interrupt 语义。
  4. CpuManager 实现迁移相关 trait，说明 vCPU 状态必须参与 pause/snapshot/transport/migration。

继续深入点：

  • 已完成 CPU 运行期控制与迁移状态链路，覆盖 /vm.resize、vCPU hotplug、guest eject、pause/resume、snapshot/restore 和 ARM64/x86_64 差异。

3. MemoryManager：RAM、hotplug、dirty log 与迁移

研究目标：理解 guest RAM 如何映射到 hypervisor、热插拔内存如何建模、dirty page 如何用于 migration。

核心结构：

  • MemoryManager 保存 boot guest memory、atomic guest memory、memory slot 分配、device/RAM address area、hotplug slots、allocator、hotplug method、memory zones 和 dirty log 等字段。
  • 它还保存 guest RAM mappings、userfaultfd handler 和 UEFI flash 等恢复相关状态：vmm/src/memory_manager.rs。
  • Snapshottable::snapshot() 先构造 memory range table，并把它保存在 snapshot_memory_ranges，供后续 Transportable::send() 发送真实内存内容：vmm/src/memory_manager.rs。
  • Migratable 实现中 dirty log 被用于迁移前后追踪变化页：vmm/src/memory_manager.rs。

机制结论：

  1. snapshot 不是立即复制所有内存，而是先形成 range table，再由 transport 阶段发送需要复制的 range。
  2. dirty log 是 migration 的关键，而不是普通 snapshot 的唯一机制。
  3. ARM64/RISC-V 额外携带 UEFI flash 相关字段；x86_64 更依赖 ACPI 和传统 PC memory map。

继续深入点：

  • 已完成 Memory Address / Hotplug Topology 链路分析，覆盖 memory zones、RAM/device area、create_userspace_mapping()、guest_ram_mappings、ACPI hotplug、virtio-mem、zone resize、restore topology 和 ARM64/x86_64 边界。

专题进展：

  • 已完成 Migration Memory Transport 链路分析，覆盖 range table、memory-ranges、copy restore、on-demand UFFD、dirty log 聚合和 ARM64/x86_64 边界。

4. DeviceManager：设备树、bus、hotplug 和恢复

研究目标：理解 virtio-pci/VFIO/vhost-user/vDPA 等设备如何被建模，以及 snapshot/restore 如何依赖设备树。

核心结构：

  • DeviceManager 持有 address manager、console/serial、interrupt controller、VM config、memory manager、CPU manager、virtio devices、block devices 和 bus devices。
  • 它还持有 PCI segments、interrupt managers、VFIO/IOMMU、device tree、exit/reset event 和 seccomp action 等：vmm/src/device_manager.rs。
  • device_tree 明确被注释为用于 introspection、snapshot 和 restore：vmm/src/device_manager.rs。
  • 中断控制器按架构分流：x86_64 是 IOAPIC，aarch64 是 GIC，riscv64 是 AIA：vmm/src/device_manager.rs。

机制结论：

  1. Cloud Hypervisor 的设备恢复依赖 device tree 记录依赖关系。
  2. 设备热插拔不只是 bus 插入，还要处理 IRQ、IOMMU、ACPI/GED 通知和失败回滚。
  3. ARM64 设备配置更多走 MMIO/FDT/GIC 语义；x86_64 更依赖 PCI/ACPI/IOAPIC。

5. ARM64 路线：GIC、FDT、UEFI、ACPI

研究目标：确认 ARM64 下 VM boot 和设备枚举与 x86 的差异。

专题进展：

  • 已完成 ARM64 与 x86_64 架构差异链路，覆盖 VM boot、vCPU、IOAPIC/GIC、FDT/ACPI、legacy device、UEFI 和 CoCo feature 边界。
  • 已完成 ACPI / FDT 机器描述生成链路，覆盖 ACPI 表聚合、DSDT AML 来源、GED hotplug、aarch64 FDT 和 x86_64 RSDP 消费路径。

已确认差异：

维度 ARM64 x86_64
vCPU 配置 init VM vCPU，返回 MPIDR 设置 CPUID/topology/nested
interrupt controller GIC IOAPIC + MSI
device description FDT 为主，可有 ACPI/GIC 表 ACPI/PCI/IOAPIC 为主
firmware UEFI flash 字段存在 PC BIOS/firmware/ACPI 路径
CPU hotplug 受 GIC/MPIDR/FDT/ACPI 表影响 受 ACPI CPU device/CPUID topology 影响

验证建议：

  • 追踪 arch::configure_vcpu 的 ARM64 实现。
  • 追踪 ARM64 FDT 生成和 ACPI MADT/GIC 表生成路径。
  • 对照 DeviceManager 的 id_to_dev_info、MMIO device info 与 x86 PCI BDF 路径。
  • 沿 Cloud Hypervisor API/VMM/device logs 继续补 ARM64 网络观测点与失败样本。
  • 继续补一份 ARM64 网络失败样本记录，把这些观测点落到具体案例。
  • 如果后续拿到真实日志，优先按失败原型回填样本而不是重搭分类。
  • 优先基于现成测试场景补第一份 ARM64 网络失败样本，而不是从零设计复现场景。
  • 先从多网卡场景补第一份样本，再补 MSI 中断场景。

6. x86_64 路线：CPUID、ACPI、PCI、CoCo

研究目标：理解 x86_64 为什么是 Cloud Hypervisor 功能最完整的架构路径。

已确认差异：

  1. CpuManager 持有 cpuid: Vec<CpuIdEntry>，x86_64 Vcpu::configure() 显式传入 CPUID、Hyper-V、topology、nested。
  2. DeviceManager 使用 IOAPIC 和 legacy/MSI interrupt manager，PCI segments 和 ACPI GED 是热插拔主路径。
  3. TDX/SEV-SNP 等 confidential computing 路径主要落在 x86_64 feature cfg 中。

继续深入点：

  • CPUID topology 如何和 hotplug CPU 数量保持一致。
  • ACPI DSDT/MADT/SRAT/VIOT 如何从 manager 状态生成。

专题进展：

  • 已完成 ACPI / FDT 机器描述生成链路，确认 x86_64 早期 ACPI、PVH/Linux boot params RSDP 注入、CPU/MEM/PCI GED 通知和 aarch64 FDT/ACPI 并存边界。
  • TDX/SEV-SNP 如何改变 IOMMU、payload 加载、memory shared/private 属性。

专题进展：

  • 已完成 CoCo：TDX 与 SEV-SNP 函数级链路，覆盖配置入口、KVM protected VM、TDVF/HOB、IGVM/VMSA、isolated page import、设备 DMA 代理和生命周期限制。
  • 已完成 TDX lifecycle 限制链路，覆盖配置校验、CPU/Memory dynamic 关闭、snapshot、live migration、local migration 前提、coredump 和 ARM64 边界。
  • 已完成 TDX TDVF / HOB 启动链路，覆盖 TDVF metadata、section 类型处理、HOB memory/MMIO/ACPI/payload、TDX vCPU init 和 measurement。
  • 已完成 TDX vCPU exit / VMCALL 边界链路，覆盖 KVM_EXIT_TDX 映射、GetQuote、SetupEventNotifyInterrupt、InvalidOperand 回写和 ARM64 边界。
  • 已完成 SEV-SNP IGVM / VMSA / isolated page 链路，覆盖 MSHV SNP VM、IGVM directive、VMSA、isolated page import、complete import、设备 page access 和 ARM64 边界。
