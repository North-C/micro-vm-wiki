    Cloud Hypervisor ARM64 网络能力边界矩阵

    本文承接 I/O 设备数据面链路 和 ARM64 与 x86_64 架构差异链路。

    目标不是重复解释 NetConfig -> virtio-net 路径。

    目标是把 Cloud Hypervisor 在 ARM64 与 x86_64 上，与网络能力直接相关的边界压成一张矩阵。

    源码基线：当前工作树。

    1. 核心结论

    Cloud Hypervisor 的网络配置结构 NetConfig 本身几乎是架构中立的。

    真正的 ARM64 差异，不在字段表面，而在后面的四层约束：

    1. virtio-net 设备是如何被枚举给 guest 的。
    2. MSI/中断最终是走 IOAPIC 还是 GICv3/ITS。
    3. guest 看到的是 ACPI/PCI 语义还是 FDT/GIC/PCI host bridge 语义。
    4. 网络热插拔虽然走统一的 add_net()，但其“真正确认成功”的条件在 ARM64 上更依赖 guest 枚举与中断路径。

    因此，Cloud Hypervisor ARM64 网络不能只看 vm_add_net() 返回成功。

    更准确的说法是：

    host 侧配置共享，guest 可见性与中断控制器语义不同。

    2. 总体矩阵

    维度 x86_64 ARM64 关键源码依据
    NetConfig 字段 共享 共享 vm_config.rs
    运行期加网卡 vm_add_net -> vm.add_net -> DeviceManager::add_net 同一路径 lib.rs，device_manager.rs
    transport 统一 virtio-pci 主路径 同一路径 io-device-data-path-chain.md
    guest 系统描述 ACPI/PVH/PCI FDT + GIC + PCI host bridge aarch64/mod.rs，fdt.rs
    中断控制器 IOAPIC/MSI GICv3/ITS/MSI devices/src/gic.rs
    IOMMU 热插拔校验 按 segment/IOMMU 规则校验 同规则，但 guest 侧含义不同 device_manager.rs
    “成功”判定 设备可见 + MSI/ACPI/PCI 路径成立 设备可见 + FDT/GIC/PCI 路径成立 本文综合

    3. 控制面：NetConfig 与 vm_add_net() 是共享的

    NetConfig 包含 tap、IP、mask、mac、host_mac、mtu、iommu、queue 数、vhost-user、fds、rate limiter、PCI segment 和 offload 开关。

    源码依据：vm_config.rs。

    运行期新增网卡统一从 vm_add_net() 进入。

    它先在克隆后的 VmConfig 上做一次校验，然后在 VM 已存在时调用 vm.add_net()，否则只更新配置。

    源码依据：lib.rs。

    vm.add_net() 再进入 DeviceManager::add_net()。

    这里先校验 identifier 与 IOMMU segment，再调用 make_virtio_net_device()，最后统一走 hotplug_virtio_pci_device()。

    源码依据：device_manager.rs。

    所以如果只看 API 与 DeviceManager 入口，ARM64 和 x86_64 基本没有区别。

    这也是 Cloud Hypervisor 网络最容易让人误判的地方。

    4. 设备模型：网络主路径仍是 virtio-pci

    DeviceManager::add_net() 不会为 ARM64 单独走另一套 net 设备类型。

    它最终还是把网络设备包装成 virtio-pci。

    源码依据：device_manager.rs。

    这一点与 Cloud Hypervisor 的 I/O 数据面结论一致：

    普通 net 数据面在 VMM 内由 NetEpollHandler 处理，主要差异不在 queue worker 逻辑本身。

    因此 ARM64 与 x86_64 的关键区别，不在 virtio-net handler 内部。

    而在“guest 如何发现它”和“完成后中断如何回到 guest”。

    5. guest 可见性：ARM64 依赖 FDT/GIC/PCI host bridge

    ARM64 的 configure_system() 不是写 ACPI/PVH 启动信息。

    它会把 cmdline、MPIDR、device info、initrd、PCI space、virtio-iommu BDF、GIC、NUMA 和 PMU 状态一起交给 create_fdt()。

    源码依据：aarch64/mod.rs。

    create_fdt() 会写：

    1. CPU nodes
    2. memory
    3. chosen
    4. GIC
    5. timer
    6. PMU
    7. PSCI
    8. devices
    9. PCI nodes

    源码依据：fdt.rs。

    这意味着 ARM64 上 vm_add_net() 成功后，真正的 guest 可见性还要再过一层：

    NetConfig 生成的 virtio-net 必须最终被 FDT/PCI host bridge 正确描述，guest 才能稳定枚举到它。

    而 x86_64 更多依赖 ACPI/PCI/PVH 语义。

    6. 中断控制器：ARM64 走 GICv3/ITS，不是 IOAPIC

    Cloud Hypervisor ARM64 的中断控制器是 Gic。

    它在创建时会基于 VgicConfig 调 vm.create_vgic()，并立即 enable()。

    源码依据：devices/src/gic.rs。

    ARM64 Gic 还会在 restore 时调用 set_gicr_typers() 并恢复 VGIC state。

    源码依据：devices/src/gic.rs。

    这会直接影响网络中断路径的判断口径。

    x86_64 侧更容易把问题归到 IOAPIC/MSI/ACPI 枚举。

    ARM64 侧则必须同时考虑：

    1. GICv3/ITS 是否被创建并启用。
    2. guest 是否按 FDT 正确理解 interrupt-parent 与 PCI MSI。
    3. 网络设备完成后，中断是否真的通过 GIC 送回 guest。

    因此 ARM64 网络的一类特有失败，并不是“网卡不存在”。

    而是网卡已存在，但中断路径没真正闭环。

    7. IOMMU 与 segment：代码共享，语义不完全相同

    DeviceManager::add_net() 对 net_cfg.iommu 有统一校验：

    如果该设备要求 IOMMU，但 pci_segment 不是 IOMMU segment，就返回 InvalidIommuHotplug。

    源码依据：device_manager.rs。

    从代码表面看，这条规则与架构无关。

    但从系统语义看，ARM64 更容易把问题放大。

    原因是 ARM64 guest 还要同时穿过：

    1. FDT/PCI host bridge 描述
    2. GICv3/ITS 的 MSI 语义
    3. 可能存在的 virtio-iommu BDF 描述

    因此同样一条 InvalidIommuHotplug，在 ARM64 上更值得被看作“设备模型组合越界”，而不是仅仅一个配置 typo。

    8. vhost-user、FD 和多队列：ARM64 也共享入口，但要更重视 guest 端确认

    NetConfig 的 fds 字段注释已经写明：

    真正有效的 FD 不是从普通配置序列化恢复，而是通过独立通道传入。

    源码依据：vm_config.rs。

    num_queues 和 queue_size 也没有架构专属字段。

    源码依据：vm_config.rs。

    这说明 ARM64 与 x86_64 在 host 侧“接入哪类 backend”上没有第一层差异。

    但 ARM64 上更不能止步于 host 成功打开 tap/vhost-user/fds。

    因为最终仍要回到 guest 端：

    1. 设备能否被正确枚举。
    2. 中断是否通过 GIC/ITS 到达。
    3. guest driver 是否真正把队列跑起来。

    9. Cloud Hypervisor ARM64 网络的正确判断顺序

    建议把 ARM64 网络判断固定成下面四步。

    第一步：先看 vm_add_net() 与 DeviceManager::add_net() 是否通过配置校验。

    第二步：再看是否正确生成了 ARM64 FDT 中的 devices/PCI/GIC 描述。

    第三步：再看 GICv3/ITS 是否承担了网络设备中断返回路径。

    第四步：最后才判断 guest 内是否真正看到并驱动了 virtio-net。

    如果把第三、第四步省掉，只凭 vm_add_net() 成功就下结论，误判概率很高。

    10. 最小边界表

    flowchart LR NetCfg["NetConfig"] --> AddNet["DeviceManager::add_net"] AddNet --> PCI["virtio-pci"] PCI --> FDT["ARM64 FDT / PCI host bridge"] FDT --> GIC["GICv3 / ITS / MSI"] GIC --> Guest["guest virtio-net visible and usable"]

    可以把 Cloud Hypervisor ARM64 网络能力压成下面这张表：

    问题 x86_64 ARM64
    host 配置入口 共享 共享
    设备创建入口 共享 共享
    guest 描述主轴 ACPI/PCI/PVH FDT/GIC/PCI host bridge
    中断返回主轴 IOAPIC/MSI GICv3/ITS/MSI
    热插拔成功判断 设备可见 + ACPI/PCI 成立 设备可见 + FDT/GIC/PCI 成立
    易漏判位置 只看 config success 只看 vm_add_net() success

    11. 结论

    Cloud Hypervisor ARM64 网络的难点，不在 NetConfig 本身。

    而在于它让一个看起来完全共享的 host 配置入口，最终落到了一条和 x86_64 不同的 guest 描述与中断路径。

    所以研究和验证都应当把“FDT/GIC/ITS 之后 guest 是否真正可用”当成主判据，而不是把 add_net() 返回成功当成终态。
