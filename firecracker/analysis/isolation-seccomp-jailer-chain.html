Firecracker 隔离机制链路

本文展开 Firecracker 的安全边界如何由 jailer、chroot/pivot_root、cgroup、resource limit、netns、seccomp 和单 VM 进程模型共同形成。

源码基线：当前仓库工作树。

相关：vCPU/KVM_RUN、snapshot/restore、横向 安全隔离边界。

0. 术语与背景

两层隔离

层 在哪 做什么
jailer 进程（第一层） exec Firecracker 前 受限文件系统（chroot/pivot_root）+ cgroup + resource limit + 可选 netns/PID ns
Firecracker 进程内（第二层） 各线程 按线程类别加载 seccomp filter（api/vmm/vcpu 分开收紧 syscall 面）

jailer 不负责虚拟化——KVM VM/vCPU/guest memory/设备模型仍由 Firecracker VMM 进程创建。一个 Firecracker 进程构建一个 Vmm（持一个 KVM VM + vCPU handles + DeviceManager）。

关键顺序约束

  • cgroup 必须在 chroot 前完成（chroot 后不能再访问宿主 cgroupfs）。
  • binary 复制而非 hard link（避免多进程共享可执行文件内存映射）。
  • seccomp filter 反序列化 100KB 上限（防异常 filter 内存分配攻击）。

1. 核心结论

隔离两层：jailer 缩小进程所在宿主环境（fs/cgroup/rlimit/netns），Firecracker 缩小各线程内核接口（seccomp）。ARM64 jailer 额外复制 cache topology + midr_el1。

2. Jailer CLI 与 Run 顺序

jailer 必填 id/exec-file/uid/gid，可选 chroot-base-dir/netns/daemonize/new-pid-ns/cgroup/resource-limit/parent-cgroup（main.rs:162）。main_exec() 先 sanitize_process()（关继承 fd + 清空环境变量，:341），Env::new() 校验参数（:137），chroot_dir = <chroot-base>/<exec-file-name>/<id>/root（每实例独立 jail root）。

Env::run()（:644）：复制 binary → 可选 join netns → 安装 rlimit → chroot 前设 cgroup（先写全部属性再 attach pid，cgroup.rs:488）→ aarch64 复制 cache topology + midr_el1（env.rs:552/617）→ pivot_root/chroot → 创建 /dev/kvm + /dev/net/tun → exec firecracker。

3. chroot/pivot_root

// src/jailer/src/chroot.rs:17
pub fn chroot(path: &Path) -> Result<(), JailerError> {
    SyscallReturnCode(unsafe { libc::unshare(libc::CLONE_NEWNS) }).into_empty_result()?;   // 新 mount namespace
    // 递归改传播类型为 SLAVE（才能 pivot_root）
    SyscallReturnCode(unsafe { libc::mount(null(), ROOT_DIR.as_ptr(), null(), libc::MS_SLAVE|libc::MS_REC, null()) })?;
    // ... bind mount jail root → pivot_root → umount old root ...
}

不是普通 chroot——先 unshare(CLONE_NEWNS) + slave propagation + bind mount + pivot_root + umount old root。

4. seccomp（线程级 syscall 限制）

// src/firecracker/src/seccomp.rs:10
const THREAD_CATEGORIES: [&str; 3] = ["vmm", "api", "vcpu"];   // 只接受这三类 filter
// src/vmm/src/seccomp.rs:8  filter 反序列化 100KB 上限
// :93  apply_filter
pub fn apply_filter(bpf_filter: BpfProgramRef) -> Result<(), InstallationError> {
    if bpf_filter.is_empty() { return Ok(()); }
    if BPF_MAX_LEN < bpf_filter.len() { return Err(InstallationError::FilterTooLarge); }
    unsafe {
        libc::prctl(libc::PR_SET_NO_NEW_PRIVS, 1, 0, 0, 0);                       // 先 PR_SET_NO_NEW_PRIVS
        libc::syscall(libc::SYS_seccomp, libc::SECCOMP_SET_MODE_FILTER, 0, &bpf_prog);  // 再 seccomp SET_MODE_FILTER
    }
}

seccomp 按线程类别划分（vmm/api/vcpu 各自 filter），安装顺序：先 PR_SET_NO_NEW_PRIVS 再 seccomp(SET_MODE_FILTER)。

5. 进程模型 / ARM64 差异 / 能力边界

一个 Firecracker 进程 = 一个 Vmm = 一个 KVM VM + vCPU handles + DeviceManager。jailer 可加入 netns（setns(CLONE_NEWNET)，env.rs:520）。ARM64 jailer 额外复制 cache topology + midr_el1 到 jail 内 /sys/devices/system/cpu/...（x86_64 无此步）。

能力 Firecracker 表现
完整 PC 设备模型 不追求，设备面刻意收窄
外部 jailer 有（jailer 进程做 chroot/cgroup/netns）
线程级 seccomp 有（vmm/api/vcpu 三类）
设备进程隔离 无（普通 virtio 在 VMM 进程内，vhost-user block 可外置）
1000 实例密度 实测支持（见 sandbox-bench）

Firecracker 的安全来自"少 + 关 + 限"三层：少设备面 + jailer 关押进程 + 线程级 seccomp 限 syscall。
