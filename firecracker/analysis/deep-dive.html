    Firecracker 深入探索文档

    本文档用于从当前仓库源码出发，逐步建立对 Firecracker 的系统性理解：它是什么、能力边界在哪里、虚拟化机制如何实现，以及 ARM64 与 x86_64 路径有什么结构性差异。

    当前版本：第 12 版
    源码基线：firecracker 仓库 main 分支，commit 37d2b74b7
    阅读方式：先建立全局概念，再逐章深入 KVM/vCPU、设备模型、启动流程、snapshot、隔离机制和架构差异。

    0. 问题地图

    我们要解决的不是“Firecracker 是什么”这种表层问题，而是下面这些更具体的问题：

    1. Firecracker 在虚拟化系统里的定位是什么？
    2. 它的能力边界是什么，哪些能力是刻意不做的？
    3. 一个 Firecracker 进程内部有哪些线程和组件？
    4. API 请求如何变成 VMM 内部动作？
    5. InstanceStart 到 guest Linux 跑起来，中间发生了什么？
    6. 它如何使用 KVM 创建 VM、vCPU 和 guest memory？
    7. vCPU 线程里的 KVM_RUN 循环如何处理 VM-exit？
    8. 设备模型为什么主要围绕 virtio，设备 I/O 如何进入 VMM？
    9. block、net、vsock、balloon、pmem、rng、virtio-mem、MMDS 分别解决什么问题？
    10. snapshot/restore 保存了哪些状态，哪些资源不属于 snapshot？
    11. seccomp、jailer、cgroup、namespace 分别在哪一层提供隔离？
    12. ARM64 与 x86_64 在 boot、CPU、interrupt、memory layout、snapshot 上有什么差异？
    13. Firecracker 与更“完整”的 VMM，例如 QEMU、crosvm、Cloud Hypervisor，边界和设计取舍有什么不同？

    后续章节会围绕这张问题地图展开。本文第 12 版已经建立整体架构，并深入到 KVM/VM/vCPU 执行链路、API/配置模型、启动机制、设备模型、snapshot/restore 主路径、隔离机制、ARM64/x86_64 架构差异、常见 virtio 设备细节、block I/O、UFFD 辅助 restore、aarch64/x86_64 interrupt state 保存恢复差异，以及与 CubeSandbox、Cloud Hypervisor、crosvm、Kata Containers 的源码级横向比较。

    1. 一句话定位

    Firecracker 是一个“单进程单 microVM”的极简 VMM。它不追求完整 PC 设备兼容，而是围绕 Linux/KVM、Linux guest、少量 virtio 设备、Unix socket API、强隔离和快速启动来构建一个适合多租户 serverless/container workload 的 microVM 运行单元。

    源码和文档依据：

    • 设计文档明确说每个 Firecracker 进程只封装一个 microVM，并包含 API、VMM、vCPU 线程：docs/design.md。
    • VMM crate 顶层注释说明它基于 Linux KVM 运行单个 lightweight microVM：src/vmm/src/lib.rs。
    • 公开 API 通过 Unix Domain Socket 上的 HTTP 暴露：src/firecracker/swagger/firecracker.yaml。

    2.2 它刻意不做什么

    这些边界对理解 Firecracker 很重要：

    • 不做完整 PC 设备模拟。设计文档强调 minimal legacy device model，guest 主要通过 virtio net/block/vsock 访问外部资源：docs/design.md。
    • 不内置复杂网络方案。net 设备背后是 host TAP，实际网络连通、路由、安全策略交给宿主侧方案处理：docs/design.md。
    • 不管理磁盘镜像文件系统。block backing file 需要预先格式化为 guest kernel 能识别的文件系统：docs/design.md。
    • 不在一个进程里跑多个 VM。一个 Firecracker 进程对应一个 microVM，这是隔离、资源限制和故障边界的基础：docs/design.md。
    • 不把 API 线程放在 VM fast path。API 线程只做控制面；VMM 和 vCPU/device 事件路径处理运行期行为：docs/design.md。

    4. API 到 VMM 的控制链路

    Firecracker 的控制面分两段：

    1. pre-boot 阶段：API 请求不断积累配置，直到 StartMicroVm 或 LoadSnapshot。
    2. runtime 阶段：microVM 已经构建，API 请求转给 RuntimeApiController，处理 pause/resume/snapshot/device update 等运行期动作。
    sequenceDiagram participant C as Client participant A as API thread participant P as PrebootApiController participant B as builder participant V as VMM/EventManager participant CPU as vCPU threads C->>A: PUT /boot-source, /machine-config, /drives, /network-interfaces...     • API server 接收请求后调用 ParsedRequest::try_from，再把解析出来的 VmmAction 发送给 VMM：src/firecracker/src/api_server/mod.rs。
    • API 路由和 HTTP 方法到内部 action 的映射在 ParsedRequest::try_from 中：src/firecracker/src/api_server/parsed_request.rs。
    • PUT /actions 被解析为 action 请求：src/firecracker/src/api_server/parsed_request.rs。

    • runtime 阶段由 RuntimeApiController 处理 post-boot action：src/vmm/src/rpc_interface.rs。

    5. StartMicroVm 的构建主路径

    StartMicroVm 是从“配置对象”跨到“真实 VM”的边界。核心函数是 build_microvm_for_boot 和 build_and_boot_microvm。

    构建路径：

    1. 从 VmResources 取 boot source、machine config、设备配置。
    2. 分配 guest memory。
    3. 创建 Kvm 对象。
    4. 创建 KVM VM。
    5. 创建 vCPU fd 和 vCPU 对象。
    6. 向 KVM 注册 guest memory region。
    7. 创建 DeviceManager。
    8. 加载 kernel 和 initrd。
    9. attach 设备：balloon、block、net、pmem、vsock、rng、virtio-mem、legacy/arch 设备。
    10. 调用架构相关 configure_system_for_boot。
    11. 创建 Vmm 对象。
    12. 启动 vCPU 线程，初始状态为 Paused。
    13. 给 VMM 线程加载 seccomp。
    14. 把 VMM 注册到 EventManager。
    15. build_and_boot_microvm 调用 resume_vm，让 vCPU 进入 running。

    证据：

    • build_microvm_for_boot 注释说明构建出的 microVM 和 vCPU 初始处于 paused，需要 Vmm::resume_vm() 才真正运行：src/vmm/src/builder.rs。
    • 取 boot source、分配内存、创建 KVM/VM/vCPU、注册内存：src/vmm/src/builder.rs。
    • 创建设备管理器、加载 kernel/initrd、处理 PCI 开关：src/vmm/src/builder.rs。
    • attach 各类 virtio 设备：src/vmm/src/builder.rs。
    • 架构启动配置入口是 configure_system_for_boot：src/vmm/src/builder.rs。
    • vCPU 线程启动并加载 vCPU seccomp：src/vmm/src/builder.rs。
    • VMM seccomp 在构建最后加载：src/vmm/src/builder.rs。
    • build_and_boot_microvm 在构建后调用 resume_vm：src/vmm/src/builder.rs。

    6. 虚拟化机制的第一层理解

    Firecracker 自己不是 hypervisor。真正执行 guest CPU 指令的是 Linux KVM。Firecracker 的核心职责是：

    • 创建 KVM VM 和 vCPU。
    • 准备 guest physical memory，并注册给 KVM。
    • 把 kernel/initrd/cmdline/FDT/ACPI/boot params 写入 guest memory。
    • 提供最小 machine model 和 virtio 设备。
    • 在 vCPU 线程里循环调用 KVM_RUN。
    • 当 KVM 因 MMIO、PIO、system event、错误等 VM-exit 返回时，由 Firecracker 做必要的软件模拟或转发。

    vCPU 主循环的关键点：

    • vCPU 被移动到独立线程，线程名形如 fc_vcpu <index>：src/vmm/src/vstate/vcpu.rs。
    • vCPU 线程启动后先加载 seccomp，再进入状态机，初始是 paused：src/vmm/src/vstate/vcpu.rs。
    • running 状态下不断执行 run_emulation()，无外部事件时不频繁切状态机：src/vmm/src/vstate/vcpu.rs。
    • run_emulation() 直接调用 self.kvm_vcpu.fd.run()，这就是 KVM_RUN 路径：src/vmm/src/vstate/vcpu.rs。
    • MMIO read/write exit 会交给 mmio_bus，这就是 guest 访问 MMIO virtio transport 时进入 VMM 的路径之一：src/vmm/src/vstate/vcpu.rs。
    • system reset/shutdown event 会让 vCPU 进入 stopped，进而触发 VMM 停机：src/vmm/src/vstate/vcpu.rs。

    8. KVM / VM / vCPU 执行链路

    8.1 Kvm::new: 进入 KVM 世界前的门禁

    Kvm::new 是 Firecracker 和宿主 KVM 子系统建立连接的入口。它做三件事：

    1. 通过 kvm_ioctls::Kvm::new() 创建 KVM fd。这个 wrapper 背后对应打开 /dev/kvm 并建立 KVM ioctl 入口。
    2. 检查 KVM API version 是否等于 KVM_API_VERSION。
    3. 合并默认能力和 CPU template 修改器，再用 check_extension_raw 逐个确认宿主 KVM 支持这些能力。

    源码依据：

    8.4 guest memory 如何交给 KVM

    Firecracker 先在用户态创建 guest memory mmap 区域，再把这些区域注册给 KVM。KVM 看到的是 guest physical address 到 host userspace virtual address 的映射，也就是 KVM memslot。

    关键路径：

    1. VmResources::allocate_guest_memory() 分配架构布局下的 guest memory。
    2. vm.register_dram_memory_regions(guest_memory) 遍历每个 region。
    3. 每个 region 分配一个 KVM slot。
    4. region 被包装成 GuestRegionMmapExt。
    5. register_memory_region 把 region 插入 Firecracker 的 GuestMemoryMmap。
    6. 对 plugged slot 调 set_user_memory_region，最终进入 KVM_SET_USER_MEMORY_REGION。

    源码依据：

    • builder 调用 allocate_guest_memory 和 register_dram_memory_regions：src/vmm/src/builder.rs。
    • register_dram_memory_regions 分配 KVM slot 并注册 region：src/vmm/src/vstate/vm.rs。
    • plugged slot 调 set_user_memory_region：src/vmm/src/vstate/vm.rs。
    • set_user_memory_region 是对 KVM fd 的 unsafe ioctl wrapper 调用：src/vmm/src/vstate/vm.rs。

    这一步是理解 microVM 内存隔离的关键：guest 看到的是自己的 guest physical memory，KVM 根据 memslot 映射到 Firecracker 进程持有的 host userspace memory。Firecracker 进程边界、KVM 二阶段地址转换、jailer/seccomp/cgroup 一起构成隔离面。

    8.7 configure_system_for_boot: 把 KVM 对象变成可启动 Linux

    创建 KVM VM/vCPU 还不等于 guest 能启动。Firecracker 还要把 vCPU register、boot protocol、cmdline、设备描述和中断模型都设置到 Linux guest 能理解的形态。

    x86_64 路径：

    • 基于 KVM supported CPUID 和 CPU template 构造 CPU config。
    • 对每个 vCPU 调 kvm_vcpu.configure。
    • cmdline 写入 guest memory。
    • 写 MP table。
    • 按 kernel entry protocol 配置 PVH boot 或 Linux boot params。
    • 创建 ACPI 表。

    证据：src/vmm/src/arch/x86_64/mod.rs。

    aarch64 路径：

    • 基于 AArch64 CPU template 构造寄存器配置。

    aarch64 boot register 中还有两个特别重要的细节：

    证据：src/vmm/src/arch/aarch64/vcpu.rs。

    8.8 vCPU 线程、状态机和 KVM_RUN

    Firecracker 启动 vCPU 时，不是直接在 VMM 线程里跑 guest，而是把每个 vCPU 移入独立线程：

    1. Vcpu::start_threaded clone VcpuFd。
    2. 创建线程 fc_vcpu <index>。
    3. 在线程内注册 kick signal handler。
    4. 等待 barrier，确保线程本地数据初始化完成。
    5. 调 self.run(filter)。
    6. vCPU 线程加载自己的 seccomp filter。
    7. 进入状态机，初始状态是 Paused。
    8. 收到 VcpuEvent::Resume 后进入 Running。
    9. Running 状态不断调用 run_emulation()。
    10. run_emulation() 调 VcpuFd::run()，进入 KVM_RUN。

    证据：

    • vCPU 线程创建和 barrier：src/vmm/src/vstate/vcpu.rs。
    • vCPU 线程加载 seccomp 并从 paused 状态启动：src/vmm/src/vstate/vcpu.rs。
    • Paused 收到 Resume 后进入 Running：src/vmm/src/vstate/vcpu.rs。
    • Running 循环调用 run_emulation：src/vmm/src/vstate/vcpu.rs。
    • run_emulation 调 KVM_RUN：src/vmm/src/vstate/vcpu.rs。

    8.9 VM-exit 如何进入设备模型

    KVM_RUN 返回后，Firecracker 只处理一小组 exit：

    • MmioRead: 通过 mmio_bus.read(addr, data) 找到对应 MMIO device。
    • MmioWrite: 通过 mmio_bus.write(addr, data) 写入对应 MMIO device。
    • SystemEvent RESET/SHUTDOWN: 认为 guest 请求停机或重启，转为 stopped。
    • x86_64 额外处理 IoIn 和 IoOut，通过 PIO bus 路由到 legacy 设备。
    • 其他 unexpected exit 视为错误。

    证据：

    • 通用 MMIO 和 system event 处理：src/vmm/src/vstate/vcpu.rs。
    • x86 PIO exit 处理：src/vmm/src/arch/x86_64/vcpu.rs。
    • aarch64 架构特定 exit 当前不处理，unexpected exit 直接报错：src/vmm/src/arch/aarch64/vcpu.rs。

    Bus 的职责很克制：它只维护一张地址范围到设备的映射。VM-exit 带来的地址会被 resolve 到某个设备，再调用设备的 read/write。

    证据：

    • BusDevice/BusDeviceSync 抽象：src/vmm/src/vstate/bus.rs。
    • Bus 用 BTreeMap<BusRange, Weak<dyn BusDeviceSync>> 维护设备范围：src/vmm/src/vstate/bus.rs。
    • Bus::resolve/read/write 路由地址：src/vmm/src/vstate/bus.rs。

    这一层说明了 Firecracker 为什么能保持小：它不模拟一整台传统 PC，而是让 KVM 跑 CPU 和内存，让极少数 MMIO/PIO exit 回到用户态设备模型。设备模型再尽量围绕 virtio 和少量 legacy 设备展开。

    8.10 本章小结

    理解 Firecracker 的虚拟化机制，可以抓住这几个对象：

    对象 所在层 作用
    Kvm Firecracker wrapper over KVM fd 检查 KVM API、capability，保存架构 KVM 状态
    Vm / VmFd KVM VM 创建 VM、注册 guest memory、维护 irqchip/resource/mmio bus
    GuestMemoryMmap userspace memory Firecracker 持有的 guest memory 视图
    KVM memslot KVM 映射单元 把 guest physical address 映射到 host userspace memory
    Vcpu 公共 vCPU wrapper 管理线程、状态机、事件通道、响应通道
    KvmVcpu 架构 vCPU wrapper 管理 VcpuFd、CPUID/register/MSR/one-reg、架构状态
    VcpuFd::run KVM_RUN 进入内核执行 guest 指令
    Bus 用户态设备路由 把 MMIO/PIO exit 分发给设备模型

    这也解释了 Firecracker 的边界：它的核心复杂度不在“实现 CPU 虚拟化”，而在“正确、最小、可隔离地组织 KVM、guest memory、vCPU 状态和设备模型”。

    9. API 与配置模型

    这一章回答一个关键问题：curl --unix-socket ... PUT /machine-config 这种请求，如何变成 Firecracker 内部的虚拟机状态？

    先给结论：Firecracker 的 API 是一个很薄的控制面。它把 HTTP 请求解析成 VmmAction，再通过 channel 和 eventfd 交给 VMM 线程。pre-boot 阶段主要写入 VmResources；runtime 阶段才操作已经构建好的 Vmm。

    9.1 三层控制链路

    9.2 路由如何变成 VmmAction

    VmmAction 是 Firecracker 的内部控制面接口。枚举定义里已经标明很多动作只能 pre-boot 或 post-boot 调用：src/vmm/src/rpc_interface.rs。

    各解析函数只做三类事：校验路径 ID 与 body ID 是否一致、反序列化 JSON、构造 ParsedRequest::new_sync(VmmAction::...)。

    例如 block 设备的 PUT /drives/{id} 会校验 path id 与 drive_id 一致，然后生成 InsertBlockDevice：src/firecracker/src/api_server/request/drive.rs。

    net 设备也采用同样模式，PUT 生成 InsertNetworkDevice，PATCH 生成 UpdateNetworkInterface：src/firecracker/src/api_server/request/net.rs。

    9.3 pre-boot 阶段：构建计划，不是 VM 本体

    pre-boot 阶段最容易误解。此时还没有完整的 Vmm 在跑，API 请求主要是在填一份“启动计划”。

    这份计划就是 VmResources。它包含 machine config、boot source、block/net/vsock/balloon/pmem/rng/virtio-mem/MMDS 等待构建资源：src/vmm/src/resources.rs。

    flowchart TB VmResources[VmResources] VmResources --> MachineConfig[MachineConfig
    vcpu_count, mem_size_mib, smt, cpu_template] VmResources --> BootSource[BootSource
    kernel, initrd, boot_args] VmResources --> BlockBuilder[BlockBuilder
    virtio-block configs] VmResources --> NetBuilder[NetBuilder
    TAP backed net devices] VmResources --> VsockBuilder[VsockBuilder] VmResources --> BalloonBuilder[BalloonBuilder] VmResources --> PmemBuilder[PmemBuilder] VmResources --> EntropyBuilder[EntropyDeviceBuilder] VmResources --> MemoryHotplug[MemoryHotplugConfig] VmResources --> Mmds[MMDS datastore and network stack] VmResources --> Serial[serial output path and limiter]

    PrebootApiController::handle_preboot_request 明确列出哪些动作 pre-boot 合法：src/vmm/src/rpc_interface.rs。

    合法动作主要是配置类动作：

    • ConfigureBootSource 写入 boot_source。
    • UpdateMachineConfiguration 更新 machine_config。
    • InsertBlockDevice 写入 block builder。
    • InsertNetworkDevice 写入 net_builder。
    • SetVsockDevice、SetBalloonDevice、SetEntropyDevice、SetMemoryHotplugDevice 写入对应 builder/config。
    • PutMMDS、PatchMMDS、SetMmdsConfiguration 操作 MMDS 数据与网络入口。

    真正结束 pre-boot 的只有两类动作：

    动作 结果
    StartMicroVm 调 build_and_boot_microvm，用 VmResources 创建 KVM VM、guest memory、设备和 vCPU 线程
    LoadSnapshot 调 restore_from_snapshot，从 snapshot 恢复出 Vmm，可选恢复后 resume

    start_microvm 成功后把 built_vmm 填上，pre-boot controller 被 runtime controller 替代：src/vmm/src/rpc_interface.rs。

    load_snapshot 也会结束 pre-boot，但它有一个关键限制：如果此前已经走过普通 boot 配置路径，boot_path 为真，则拒绝 load snapshot：src/vmm/src/rpc_interface.rs。

    这说明 Firecracker 把“从配置启动”和“从 snapshot 恢复”视为两条互斥路径。

    9.4 VmResources 的几个约束

    VmResources 不是被动的数据包。它的 setter 会做启动前一致性检查。

    setter 约束或效果 源码
    update_machine_config 新内存不能小于已配置 balloon target src/vmm/src/resources.rs
    set_balloon_device balloon target 不能大于 guest memory src/vmm/src/resources.rs
    build_boot_source 根据 boot-source 生成 BootConfig builder src/vmm/src/resources.rs
    set_block_device 检查 pmem root 与 block root 冲突 src/vmm/src/resources.rs
    build_net_device 构建 net device builder，后续启动时 attach src/vmm/src/resources.rs
    build_pmem_device 检查 block root 与 pmem root 冲突 src/vmm/src/resources.rs
    set_memory_hotplug_config 校验 virtio-mem 配置 src/vmm/src/resources.rs
    set_mmds_config 校验 MMDS 绑定的网络接口已存在 src/vmm/src/resources.rs

    MMDS 的配置顺序值得注意。set_mmds_network_stack_config 会检查 network_interfaces 非空，并且每个 ID 都能在 net_builder 中找到：src/vmm/src/resources.rs。

    也就是说，想让 guest 通过网卡访问 MMDS，必须先配置对应的 network interface，再配置 /mmds/config。

    9.5 runtime 阶段：只允许很窄的动态变更

    runtime 阶段已经有 Vmm，所以控制器不再写 VmResources，而是拿 Arc<Mutex<Vmm>> 调运行期方法：src/vmm/src/rpc_interface.rs。

    stateDiagram-v2 [*] --> Preboot Preboot --> Running: StartMicroVm Preboot --> Paused: LoadSnapshot resume_vm=false Preboot --> Running: LoadSnapshot resume_vm=true Running --> Paused: PATCH /vm Paused Paused --> Running: PATCH /vm Resumed Paused --> Snapshot: PUT /snapshot/create Snapshot --> Paused

    RuntimeApiController::handle_request 允许的动作集中在运行期控制和小范围设备更新：src/vmm/src/rpc_interface.rs。

    runtime 动作 实际含义
    Pause / Resume 暂停或恢复 vCPU
    CreateSnapshot 创建 full 或 diff snapshot；实际保存 vCPU state 要求 VM 已暂停
    FlushMetrics 立即写 metrics
    GetFullVmConfig / Get* 查询运行中 VM 配置或状态
    PutMMDS / PatchMMDS 更新 MMDS 数据
    UpdateBalloon / UpdateBalloonStatistics / hinting 调整 balloon 和 page hinting
    UpdateBlockDevice 更新 block backing path 或 rate limiter；特殊情况下刷新 vhost-user-block 配置
    UpdateNetworkInterface 更新 net RX/TX rate limiter
    UpdatePmemDevice 更新 pmem rate limiter
    UpdateMemoryHotplugSize 调整 virtio-mem 请求大小

    runtime 明确拒绝大部分“结构性配置”动作：ConfigureBootSource、InsertBlockDevice、InsertNetworkDevice、SetVsockDevice、SetEntropyDevice、SetMemoryHotplugDevice、StartMicroVm、UpdateMachineConfiguration 等都会返回 OperationNotSupportedPostBoot：src/vmm/src/rpc_interface.rs。

    因此，Firecracker 的“热更新”能力边界很清楚：它支持部分设备参数和状态控制，不支持运行后随意热插入完整设备，也不支持运行后改变 vCPU 数、基础内存大小、boot source 或 CPU template。

    运行期 block/net/pmem 的更新最终进入 Vmm 的设备方法。例如 block 更新会分别处理 backing path、rate limiter 和 vhost-user-block 刷新：src/vmm/src/rpc_interface.rs。

    snapshot 是一个典型例子：CreateSnapshot 是 runtime action，但不等于 running 状态下可以直接保存。create_snapshot 会先调用 Vmm::save_state：src/vmm/src/persist.rs；保存 vCPU state 时，如果 vCPU 仍处于 running 状态，会返回 NotAllowed("save/restore unavailable while running")：src/vmm/src/vstate/vcpu.rs。

    9.6 配置文件模式复用同一套资源模型

    Firecracker 不只支持逐个 API 配置，也支持从 JSON 配置启动。这个路径不是另起一套模型，而是把 VmmConfig 反序列化后填到 VmResources。

    VmResources::from_json 会依次应用 logger、metrics、machine config、cpu config、boot source、drive、net、vsock、balloon、MMDS、entropy、pmem、serial、memory hotplug：src/vmm/src/resources.rs。

    区别是：logger 和 metrics 在读取配置文件时会立即初始化；其他 VM 资源仍然进入 VmResources，后续再由启动路径消费。

    这解释了 API 模式和配置文件模式的一致性：它们的入口不同，但最终都在准备同一份 VmResources。

    9.7 API 响应模型

    API 响应也很直接：VmmData::Empty 返回 204 No Content；查询类数据返回 200 加 JSON；错误大多返回 400 Bad Request，MMDS payload 超限返回 413 Payload Too Large：src/firecracker/src/api_server/parsed_request.rs。

    这意味着很多“能力不支持”不是 HTTP 路由层直接挡掉，而是路由层先生成 VmmAction，再由 pre-boot/runtime controller 根据阶段返回错误。

    例如 PUT /actions {"action_type":"FlushMetrics"} 在解析层是合法的 VmmAction::FlushMetrics，但 pre-boot controller 会拒绝它，runtime controller 才允许它。

    9.8 ARM64 与 x86_64 在 API 层的差异

    API 表面上跨架构统一，但有几个地方已经体现架构差异。

    第一，SendCtrlAltDel 只在 x86_64 存在。parse_put_actions 在 aarch64 下直接对这个 action 返回 bad request；x86_64 才会生成 VmmAction::SendCtrlAltDel：src/firecracker/src/api_server/request/actions.rs。

    runtime controller 中 SendCtrlAltDel 的处理函数也被 #[cfg(target_arch = "x86_64")] 包住：src/vmm/src/rpc_interface.rs。

    第二，SMT 的 machine config 在 aarch64 下不支持。MachineConfig::update 中如果目标架构是 aarch64 且 smt 为真，会返回 SmtNotSupported：src/vmm/src/vmm_config/machine_config.rs。

    第三，CPU template 的静态模板集合不同。x86_64 有 C3/T2/T2S/T2CL/T2A，aarch64 有自己的 V1N1；测试也明确验证了 "T2" 在 x86_64 可解析，在 aarch64 会失败：src/firecracker/src/api_server/request/machine_configuration.rs。

    第四，snapshot 的某些配置项带架构语义。例如 clock_realtime 在配置结构注释里标注为 x86_64 only：src/vmm/src/vmm_config/snapshot.rs。

    这几个点说明：Firecracker 尽量维持同一套 HTTP API，但不会把架构差异隐藏成完全一致的语义。架构相关能力会在解析、配置校验或 runtime controller 中被显式限制。

    9.9 本章小结

    理解 Firecracker API，不应该把它看成“管理服务”。更准确的模型是：

    1. pre-boot API 是一组构建 VM 的 declarative inputs。
    2. VmResources 是启动前的资源图。
    3. StartMicroVm 是从资源图到真实 KVM/VMM/vCPU/设备线程的分界线。
    4. runtime API 是有限的状态控制和设备参数更新，不是完整热重配置系统。
    5. ARM64 与 x86_64 共享控制面形状，但 CPU、SMT、Ctrl-Alt-Del、snapshot 字段语义等处有实际差异。

    这条主线会直接连接到下一章：StartMicroVm 到底如何消费 VmResources，并创建 guest memory、KVM VM、irqchip、设备和 vCPU 线程。

    10. 启动机制：从 VmResources 到 Running microVM

    上一章已经说明：pre-boot API 最终是在填 VmResources。这一章继续追问：StartMicroVm 到底如何消费这份资源图，把它变成一个真正运行的 guest Linux？

    核心结论：Firecracker 的启动不是一步完成的。它先构建一个完整但处于 Paused 状态的 microVM，再统一 resume_vm。这样可以确保 KVM、guest memory、设备、vCPU register、boot 数据结构、seccomp 和 EventManager 都就绪后，guest 才开始执行。

    10.1 启动主链路

    StartMicroVm 在 pre-boot controller 中进入 start_microvm，再调用 build_and_boot_microvm。后者先 build_microvm_for_boot，再 resume_vm：src/vmm/src/rpc_interface.rs，src/vmm/src/builder.rs。

    flowchart TB Start[StartMicroVm] --> BuildAndBoot[build_and_boot_microvm] BuildAndBoot --> Build[build_microvm_for_boot] Build --> BootConfig[read BootConfig from VmResources] Build --> GuestMemory[allocate guest memory] Build --> Kvm[Kvm::new] Kvm --> Vm[Vm::new / KVM_CREATE_VM] Vm --> VcpuCreate[create_vcpus] Vm --> Memslots[register DRAM memory regions] Build --> Kernel[load_kernel] Build --> Initrd[load initrd] Build --> Devices[attach virtio and platform devices] Devices --> ArchBoot[configure_system_for_boot] ArchBoot --> VmmObj[Vmm object] VmmObj --> StartVcpus[start_vcpus in Paused state] StartVcpus --> Seccomp[apply VMM seccomp] Seccomp --> EventManager[add VMM subscriber] EventManager --> Resume[resume_vm] Resume --> Running[guest starts running]

    源码顺序集中在 build_microvm_for_boot：src/vmm/src/builder.rs。

    顺序 源码动作 作用
    1 取 vm_resources.boot_source.builder 没有 kernel config 就返回 MissingKernelConfig
    2 vm_resources.allocate_guest_memory() 按架构 memory layout 分配 guest memory
    3 cpu_template.get_cpu_template() 展开静态/自定义 CPU template
    4 Kvm::new(...) 打开 /dev/kvm、检查 KVM API/capability、初始化架构 KVM wrapper
    5 Vm::new(&kvm) 创建 KVM VM
    6 vm.create_vcpus(vcpu_count) 创建 KVM vCPU fd 与 Firecracker vCPU wrapper
    7 vm.register_dram_memory_regions(...) 把 guest memory 注册为 KVM memslot
    8 load_kernel / InitrdConfig::from_config 把 kernel/initrd 写入 guest memory
    9 attach devices 注册 virtio/platform devices 到 MMIO/PCI、EventManager 和 boot 描述
    10 configure_system_for_boot 架构相关 boot 数据结构、vCPU register、ACPI/FDT
    11 start_vcpus 创建 vCPU 线程，但初始状态是 Paused
    12 apply_filter("vmm") + add_subscriber VMM 线程进入 seccomp 限制，接入 EventManager
    13 resume_vm 发送 VcpuEvent::Resume，guest 开始执行

    这条链路可以看出一个关键设计：启动前半段是“构建世界”，最后一步才是“让 CPU 跑起来”。

    10.2 guest memory 与 KVM VM

    guest memory 的第一步不是 KVM ioctl，而是由 VmResources 根据架构 layout 计算内存区域：src/vmm/src/resources.rs。

    allocate_guest_memory 调 crate::arch::arch_memory_regions(mem_size)。如果配置了 vhost-user-blk，Firecracker 用 memfd-backed shared memory；否则默认用 anonymous private memory：src/vmm/src/resources.rs。

    内存区域分配后，Vm::register_dram_memory_regions 会为每个 region 申请 KVM slot，并最终调用 set_user_memory_region 注册到 KVM：src/vmm/src/vstate/vm.rs。

    flowchart LR MachineConfig[mem_size_mib / huge_pages / track_dirty_pages] --> ArchRegions[arch_memory_regions] ArchRegions --> Alloc[anonymous or memfd-backed allocation] Alloc --> GuestMemory[GuestMemoryMmap regions] GuestMemory --> Register[Vm::register_dram_memory_regions] Register --> Slot[next_kvm_slot] Slot --> KvmMemslot[KVM_SET_USER_MEMORY_REGION] KvmMemslot --> GuestPhys[guest physical address maps to host userspace memory]

    x86_64 和 aarch64 的 memory layout 从这一层就开始分叉：

    维度 x86_64 aarch64
    arch_memory_regions 从 0 开始，避开 32-bit MMIO gap 和 64-bit MMIO gap 从 DRAM_MEM_START 开始，避开 MMIO64 区域
    kernel load address layout::HIMEM_START SYSTEM_MEM_START + SYSTEM_MEM_SIZE
    initrd 位置 在低内存区域向下对齐 放在 FDT 之前、向下对齐
    boot 描述结构 cmdline + boot params/PVH start info + MP table + ACPI vCPU registers + FDT

    源码依据：x86_64 memory regions 和 kernel start 在 src/vmm/src/arch/x86_64/mod.rs，aarch64 对应逻辑在 src/vmm/src/arch/aarch64/mod.rs。

    10.3 KVM wrapper 与 vCPU 创建

    Kvm::new 是 Firecracker 对 /dev/kvm 的第一层封装。它打开 KVM fd，检查 KVM API version，再把默认 capability 和 CPU template 要求的 capability 合并检查：src/vmm/src/vstate/kvm.rs。

    x86_64 的 Kvm wrapper 还会保存 supported_cpuid，因为后续 CPU template 和 vCPU 配置要基于 KVM 支持的 CPUID 集合做过滤：src/vmm/src/arch/x86_64/kvm.rs。

    aarch64 的 Kvm wrapper 更薄，主要保存 KVM fd 和 capability modifiers，同时提供 optional_capabilities，例如 KVM_CAP_COUNTER_OFFSET：src/vmm/src/arch/aarch64/kvm.rs。

    Vm::create_vcpus 创建 vCPU 时会先做架构 pre hook，再创建一个共享 exit eventfd，然后循环创建每个 Vcpu：src/vmm/src/vstate/vm.rs。

    这时 vCPU 还没有运行 guest。它只是拥有 KVM vCPU fd、事件通道、响应通道和退出 eventfd。真正的线程启动在后面的 Vmm::start_vcpus。

    10.4 设备 attach：进入 MMIO/PCI、EventManager 和 boot 描述

    设备 attach 是启动机制里最容易混淆的部分。Firecracker 的设备不是在 API 请求时就挂到 VM 里，而是在 build_microvm_for_boot 中按固定顺序 attach。

    build_microvm_for_boot 会依次处理 boot timer、balloon、block、net、pmem、vsock、entropy、virtio-mem、aarch64 legacy devices、vmgenid、vmclock：src/vmm/src/builder.rs。

    virtio 设备最终都会进入 DeviceManager::attach_virtio_device。如果 PCI 已启用，就走 PCI transport；否则走 MMIO transport：src/vmm/src/device_manager/mod.rs。

    flowchart TB Builder[build_microvm_for_boot] --> Block[attach_block_devices] Builder --> Net[attach_net_devices] Builder --> Pmem[attach_pmem_devices] Builder --> Vsock[attach_unixsock_vsock_device] Builder --> Balloon[attach_balloon_device] Builder --> Entropy[attach_entropy_device] Builder --> Mem[attach_virtio_mem_device] Block --> Attach[DeviceManager::attach_virtio_device] Net --> Attach Pmem --> Attach Vsock --> Attach Balloon --> Attach Entropy --> Attach Mem --> Attach Attach -->|pci_enabled| Pci[PCI virtio transport] Attach -->|pci disabled| Mmio[MMIO virtio transport] Mmio --> Cmdline[kernel cmdline virtio_mmio.device entries] Attach --> EventManager[device EventManager subscribers]

    block 和 pmem 还会改 kernel cmdline。root block device 会写入 root=/dev/vda 或 root=PARTUUID=...，并追加 ro/rw；root pmem 会写入 root=/dev/pmem{i}：src/vmm/src/builder.rs，src/vmm/src/builder.rs。

    这解释了为什么 API 配置的 is_root_device 会影响 guest Linux 的 rootfs，而不是只影响设备模型。

    10.5 架构 boot 配置：x86_64 与 aarch64 的分叉点

    所有通用构建完成后，代码进入 configure_system_for_boot。这个函数名相同，但由目标架构选择不同实现。

    flowchart TB Common[Common builder path] --> Configure[configure_system_for_boot] Configure --> X86[x86_64 implementation] Configure --> Arm[aarch64 implementation] X86 --> X86Cpu[build CPUID-based CpuConfiguration] X86 --> X86Vcpu[configure each vCPU] X86 --> Cmdline[write command line at CMDLINE_START] X86 --> MpTable[write MP table] X86 --> BootParams{entry protocol} BootParams --> PVH[PVH hvm_start_info] BootParams --> LinuxBoot[Linux boot_params zero page] X86 --> Acpi[create ACPI tables] Arm --> ArmCpu[build register-based CpuConfiguration] Arm --> ArmVcpu[configure each vCPU] Arm --> Clidr[override CLIDR_EL1 from host cache topology] Arm --> Mpidr[collect MPIDR values] Arm --> Fdt[create FDT with cmdline, devices, irqchip, initrd] Fdt --> WriteFdt[write FDT near top of DRAM]

    x86_64 的实现做这些事：src/vmm/src/arch/x86_64/mod.rs

    • 基于 KVM supported_cpuid 和 CPU template 生成 CPU config。
    • 配置每个 vCPU。
    • 把 kernel cmdline 写到 CMDLINE_START。
    • 写 MP table。
    • 按 kernel entry protocol 选择 PVH 或 legacy 64-bit boot params。
    • 创建 ACPI tables 并写入 guest memory。

    aarch64 的实现做这些事：src/vmm/src/arch/aarch64/mod.rs

    • 基于 aarch64 register template 生成 CPU config。
    • 配置每个 vCPU。
    • 覆盖 CLIDR_EL1 的 cache topology 相关字段，避免 guest 看到与 host sysfs 不一致的 cache 信息。
    • 收集每个 vCPU 的 MPIDR。
    • 创建 FDT，把 cmdline、设备、irqchip、initrd 等描述放入 device tree。
    • 把 FDT 写到 guest memory 顶部附近。

    这个分叉是 Firecracker 架构差异的核心之一：x86_64 更依赖 ACPI/MP table/boot params/PVH，aarch64 更依赖 FDT 和 one-reg 风格的 vCPU register 配置。

    10.6 vCPU 为什么先 Paused 再 Running

    build_microvm_for_boot 的注释已经说明：构建好的 microVM 和 vCPU 初始都是 paused，要启动必须调用 Vmm::resume_vm()：src/vmm/src/builder.rs。

    Vmm::start_vcpus 会启动每个 vCPU 线程，并把 instance_info.state 设为 Paused：src/vmm/src/lib.rs。

    vCPU 线程里的 run 也明确从 Paused 状态机开始：src/vmm/src/vstate/vcpu.rs。

    sequenceDiagram participant VMM as VMM thread participant VCPU as vCPU thread participant KVM as KVM VMM->>VCPU: spawn thread VCPU->>VCPU: apply vCPU seccomp VCPU->>VCPU: enter Paused state VMM->>VMM: apply VMM seccomp VMM->>VMM: add VMM to EventManager VMM->>VCPU: VcpuEvent::Resume VCPU-->>VMM: VcpuResponse::Resumed VCPU->>KVM: KVM_RUN loop

    resume_vm 会先 kick virtio devices，再给所有 vCPU 发送 VcpuEvent::Resume，等待每个 vCPU 返回 Resumed，最后把实例状态改为 Running：src/vmm/src/lib.rs。

    这个顺序保证 guest 开始执行前，设备 eventfd、boot 参数、内存映射、vCPU register、seccomp 和 VMM event loop 都已经准备好。

    10.7 启动机制小结

    StartMicroVm 可以压缩成一句话：把 pre-boot 阶段积累的 VmResources 消费掉，构建一个 paused 的 KVM microVM，然后一次性 resume vCPU。

    更细地说，启动边界有五层：

    1. 资源层：VmResources 提供 boot source、machine config、设备 builder。
    2. KVM 层：创建 KVM、VM、vCPU fd、memslot。
    3. 设备层：把 virtio/platform devices attach 到 MMIO/PCI、EventManager 和 boot 描述。
    4. 架构层：x86_64 写 boot params/ACPI，aarch64 写 FDT。
    5. 执行层：vCPU 线程先 paused，resume_vm 后进入 KVM_RUN。

    这也解释了 Firecracker 的能力边界：启动后不能任意改变 machine config、boot source 或设备拓扑，因为这些输入已经被消费成 KVM VM、guest memory layout、设备地址、boot 描述结构和 vCPU 初始状态。

    11. 设备模型：DeviceManager、virtio transport 与队列事件

    Firecracker 的设备模型可以用一句话概括：控制面只创建设备配置，启动阶段把设备 attach 到 transport，运行期由 EventManager 分发 eventfd/TAP/rate limiter 等事件，设备再通过 virtio queue 读写 guest memory。

    这里的重点不是“Firecracker 实现了多少设备”，而是所有 virtio 设备共享的骨架：VirtioDevice trait、MMIO/PCI transport、queue eventfd、interrupt、EventManager subscriber。

    11.1 设备对象的层次

    flowchart TB VmResources[VmResources builders] --> Builder[build_microvm_for_boot] Builder --> DeviceManager[DeviceManager] DeviceManager --> MmioMgr[MMIODeviceManager] DeviceManager --> PciMgr[PciDevices] DeviceManager --> AcpiMgr[ACPIDeviceManager] DeviceManager --> Legacy[legacy serial / i8042 on x86_64] Builder --> Block[Block] Builder --> Net[Net] Builder --> Vsock[Vsock] Builder --> Balloon[Balloon] Builder --> Pmem[Pmem] Builder --> Rng[Entropy] Builder --> VirtioMem[VirtioMem] Block --> VirtioDevice[VirtioDevice trait] Net --> VirtioDevice Vsock --> VirtioDevice Balloon --> VirtioDevice Pmem --> VirtioDevice Rng --> VirtioDevice VirtioMem --> VirtioDevice VirtioDevice --> Transport{transport} Transport -->|default| Mmio[MmioTransport] Transport -->|--enable-pci| Pci[VirtioPciDevice]

    DeviceManager 持有四类设备管理器：MMIO virtio、x86_64 legacy、ACPI、PCIe：src/vmm/src/device_manager/mod.rs。

    每个 virtio 设备都实现 VirtioDevice。这个 trait 要求设备暴露 feature、queue、queue eventfd、interrupt、config space 和 activate 生命周期：src/vmm/src/devices/virtio/device.rs。

    关键点：具体设备负责“业务语义”，transport 负责“guest 如何看见这个设备”。同一个 block/net 设备可以挂到 MMIO transport，也可以挂到 PCI transport。

    11.2 MMIO 与 PCI transport 如何选择

    transport 的选择只看 DeviceManager::is_pci_enabled()。如果启用了 PCI，就调用 attach_pci_virtio_device；否则调用 attach_mmio_virtio_device：src/vmm/src/device_manager/mod.rs。

    --enable-pci 来自 Firecracker 进程参数，在 main 中设置为 pci_enabled，最终写入 VmResources.pci_enabled：src/firecracker/src/main.rs，src/firecracker/src/main.rs。

    启动时，如果 vm_resources.pci_enabled 为真，builder 先调用 device_manager.enable_pci(&vm)；否则向 kernel cmdline 插入 pci=off：src/vmm/src/builder.rs。

    flowchart LR CLI[--enable-pci] --> Main[pci_enabled] Main --> VmResources[VmResources.pci_enabled] VmResources --> Builder[build_microvm_for_boot] Builder --> Decision{pci_enabled?} Decision -->|yes| EnablePci[DeviceManager::enable_pci] EnablePci --> PciSegment[PciDevices::attach_pci_segment] Decision -->|no| Cmdline[pci=off] Builder --> Attach[attach_virtio_device] Attach -->|PCI enabled| PciDevice[attach_pci_virtio_device] Attach -->|PCI disabled| MmioDevice[attach_mmio_virtio_device]

    MMIO 路径会做四件事：

    步骤 源码动作 作用
    1 allocate_mmio_resources 分配 MMIO 地址和 GSI
    2 register_ioevent guest 写 notify register 时触发对应 queue eventfd
    3 register_irq 把设备 interrupt eventfd 绑定到 GSI
    4 mmio_bus.insert + add_subscriber 把 MMIO region 放入 bus，并把设备加入 EventManager

    这些都集中在 MMIODeviceManager::register_mmio_virtio：src/vmm/src/device_manager/mmio.rs。

    x86_64 的 MMIO 设备还会被追加到 kernel cmdline 和 ACPI DSDT data 中：src/vmm/src/device_manager/mmio.rs。

    PCI 路径会创建 VirtioPciDevice，分配 SBDF、MSI-X vectors 和 BAR，然后把 BAR 注册进 MMIO bus，并注册 notification ioevent：src/vmm/src/device_manager/pci_mngr.rs。

    因此，MMIO/PCI 的差异主要在“guest 发现和配置设备的 transport 形态”，而不是 block/net 的核心处理逻辑。

    11.3 MMIO transport 如何激活设备

    MmioTransport 是 guest driver 看到的 virtio-mmio register 面。它包装一个 Arc<Mutex<dyn VirtioDevice>>，并保存 queue select、features select、device status、guest memory 和 interrupt：src/vmm/src/devices/virtio/transport/mmio.rs。

    guest driver 会按 virtio 状态机写 MMIO status register。当状态变成 DRIVER_OK，MmioTransport::set_device_status 调用 inner device 的 activate(mem, interrupt)：src/vmm/src/devices/virtio/transport/mmio.rs。

    sequenceDiagram participant G as Guest virtio driver participant T as MmioTransport participant D as VirtioDevice participant E as EventManager G->>T: negotiate features G->>T: write queue addresses G->>T: set FEATURES_OK G->>T: set DRIVER_OK T->>D: activate(GuestMemoryMmap, interrupt) D->>D: initialize queues D->>D: write activate_evt E->>D: process activate event D->>E: register queue/rate/backend events

    具体设备的 activate 都会初始化 queue 指针。以 block 为例，它遍历 queues 调 q.initialize(&mem)，启用 event idx notification suppression，并写 activate_evt，最后保存 ActiveState { mem, interrupt }：src/vmm/src/devices/virtio/block/virtio/device.rs。

    net 的 activate 同样初始化 queue，设置 TAP offload，初始化 RX buffer size，写 activate_evt：src/vmm/src/devices/virtio/net/device.rs。

    activate_evt 的作用是把“设备已激活”这个状态变化送回 EventManager，让设备 subscriber 从只监听 activate event，切换为监听运行期事件。

    11.4 virtio queue 的事件路径

    virtio queue 是 guest 和 VMM 之间共享的 descriptor/ring 结构。Firecracker 的 Queue 保存 descriptor table、available ring、used ring 的 guest physical address 和 host virtual pointer：src/vmm/src/devices/virtio/queue.rs。

    设备激活时，Queue::initialize 会校验 queue ready、size、地址对齐，并把 guest memory 中的 queue 三段映射成可访问指针：src/vmm/src/devices/virtio/queue.rs。

    运行期的关键路径是：

    flowchart TB Guest[Guest driver] -->|write descriptors| Avail[Avail ring in guest memory] Guest -->|write notify register| IoEvent[KVM ioeventfd] IoEvent --> QueueEvt[device queue EventFd] QueueEvt --> EventManager[EventManager epoll] EventManager --> Subscriber[device MutEventSubscriber::process] Subscriber --> QueuePop[Queue::pop_or_enable_notification] QueuePop --> Desc[DescriptorChain] Desc --> Backend[device backend: file/TAP/vsock/balloon] Backend --> Used[write used ring] Used --> Kick[interrupt.trigger] Kick --> Guest

    Queue::pop_or_enable_notification 会从 avail ring 取 descriptor chain；如果启用了 notification suppression，则会先尝试设置 used ring 的 avail_event，减少不必要通知：src/vmm/src/devices/virtio/queue.rs。

    处理完成后，设备调用 Queue::add_used/advance_used_ring_idx 更新 used ring；Queue::prepare_kick 决定是否需要中断 guest：src/vmm/src/devices/virtio/queue.rs。

    这条路径回答了“guest 写 queue eventfd 后哪个 subscriber 被唤醒”：KVM ioeventfd 先写设备的 queue eventfd，EventManager 监听该 fd，最终调用对应设备的 MutEventSubscriber::process。

    11.5 block 设备：host file、异步 I/O 与 rate limiter

    virtio-block 的核心对象是 VirtioBlock。它有一个 queue、一个 queue eventfd、一个 activate eventfd、host disk properties、rate limiter、metrics 和设备状态：src/vmm/src/devices/virtio/block/virtio/device.rs。

    block 的 EventManager 事件分四类：src/vmm/src/devices/virtio/block/virtio/event_handler.rs

    事件 来源 处理
    PROCESS_ACTIVATE activate_evt 注册运行期事件，移除 activate 事件
    PROCESS_QUEUE guest kick queue 读取 queue eventfd，处理 virtio queue
    PROCESS_RATE_LIMITER rate limiter fd 补充 token 后继续处理 queue
    PROCESS_ASYNC_COMPLETION async file engine completion fd 处理异步 I/O 完成

    process_queue_event 先读 queue eventfd，再检查 rate limiter 和 async I/O engine 是否阻塞，最后进入 process_virtio_queues：src/vmm/src/devices/virtio/block/virtio/device.rs。

    process_queue 会循环从 queue 中取 descriptor chain，解析成 block request，再执行 rate limit 检查；如果通过，就调用 request 的 process：src/vmm/src/devices/virtio/block/virtio/device.rs。

    block request 的 process 按 request type 分发到 host file engine：In 读、Out 写、Flush flush、GetDeviceID 写 image id 到 guest memory：src/vmm/src/devices/virtio/block/virtio/request.rs。

    所以 block 的本质路径是：guest descriptor chain -> request parser -> rate limiter -> file engine -> used ring/interrupt。异步 I/O 只是 file engine 的一种执行方式，完成事件再回到 EventManager。

    11.6 net 设备：TAP、MMDS 与 RX/TX rate limiter

    virtio-net 的核心对象是 Net。它持有 host TAP、RX/TX queues、queue eventfds、RX/TX rate limiter、activate eventfd、可选 MMDS network stack、metrics 和 buffer：src/vmm/src/devices/virtio/net/device.rs。

    net 的运行期事件比 block 更多：src/vmm/src/devices/virtio/net/event_handler.rs

    事件 来源 处理
    PROCESS_VIRTQ_RX guest 提供 RX buffer 解析 RX descriptors，尝试从 TAP/MMDS 收包
    PROCESS_VIRTQ_TX guest 提供 TX frame 从 TX queue 取 frame，写到 MMDS 或 TAP
    PROCESS_TAP_RX TAP 可读 从 host TAP 读包写入 guest RX buffer
    PROCESS_RX_RATE_LIMITER RX limiter fd 补充 RX token 后继续 RX
    PROCESS_TX_RATE_LIMITER TX limiter fd 补充 TX token 后继续 TX

    RX 方向：guest 先把可写 buffer 放进 RX queue。process_rx_queue_event 读取 RX queue eventfd，调用 parse_rx_descriptors 把 descriptor chain 收集进 RX buffer；如果 RX limiter 未阻塞，调用 resume_rx：src/vmm/src/devices/virtio/net/device.rs。

    resume_rx 优先处理 deferred frame，再进入 process_rx。read_from_mmds_or_tap 会优先从 MMDS network stack 取 frame，若没有 MMDS frame，再从 TAP 读包：src/vmm/src/devices/virtio/net/device.rs。

    TX 方向：process_tx_queue_event 读 TX queue eventfd，如果 TX limiter 未阻塞，调用 process_tx：src/vmm/src/devices/virtio/net/device.rs。

    process_tx 从 TX queue 弹出 descriptor chain，构造成 IoVecBuffer。如果 frame 是 MMDS frame，就 detour 到 MMDS；否则写 host TAP：src/vmm/src/devices/virtio/net/device.rs。

    MMDS 不单独进 EventManager。它被 net 设备作为同步状态机调用：TX frame 命中 MMDS 后，net 设备会立即尝试 process_rx，把 MMDS 响应放回 guest RX queue。

    11.7 设备模型的能力边界

    设备模型解释了 Firecracker 的多项边界：

    1. 设备拓扑基本是启动时固定的。运行后可更新的是 rate limiter、block backing path、balloon target、virtio-mem size 等有限参数，不是任意热插拔。
    2. MMIO/PCI 是 transport 选择，不是两套设备实现。block/net/vsock/balloon 等业务逻辑复用同一个 VirtioDevice。
    3. guest I/O 的核心成本在 eventfd/epoll、virtio queue 解析、guest memory 读写和 host backend I/O，而不是传统 PC 设备模拟。
    4. MMDS 被压进 net 设备路径，不是一个独立虚拟网卡或独立线程。
    5. snapshot 需要额外处理 virtio queue memory dirty，因为 queue 对象在运行期可能不会通过普通 dirty tracking 捕获；DeviceManager::mark_virtio_queue_memory_dirty 会遍历 MMIO/PCI virtio 设备并标记 queue memory：src/vmm/src/device_manager/mod.rs。

    这一章覆盖了当前未展开问题里的三项：MMIO/PCI transport 选择、virtio queue 事件处理路径、block/net 设备与 rate limiter/MMDS 的主流程。vsock、balloon、pmem、rng、virtio-mem 的设备细节在第 15 章继续展开。

    12. Snapshot/restore：状态、内存与恢复边界

    Firecracker 的 snapshot 不是“把整个进程冻住”。它把 microVM 拆成两类文件：一个状态文件保存 KVM/VM/vCPU/device 的结构化状态，一个内存文件保存 guest memory 内容。恢复时再重新创建 KVM VM、vCPU、guest memory 和设备对象，并把状态灌回去。

    这也解释了它的边界：snapshot 捕获的是 Firecracker 认为可序列化、可重建的虚拟机状态，不是任意 host 资源、任意外部 fd 或任意设备后端状态。

    12.1 Snapshot 的状态对象

    核心结构是 MicrovmState：src/vmm/src/persist.rs。

    flowchart TB MicrovmState[MicrovmState] --> VmInfo[vm_info] MicrovmState --> KvmState[kvm_state] MicrovmState --> VmState[vm_state] MicrovmState --> VcpuStates[vcpu_states] MicrovmState --> DeviceStates[device_states] VmInfo --> Config[vcpu/mem/smt/cpu_template/boot_source/huge_pages] KvmState --> CapMods[kvm_cap_modifiers] VmState --> Memory[guest memory layout] VmState --> ArchVm[x86 PIT/PIC/IOAPIC/clock or arm64 GIC] VcpuStates --> CpuRegs[arch-specific vCPU registers] DeviceStates --> Devices[MMIO + PCI + ACPI + serial/device states]

    字段含义：

    字段 保存内容 作用
    vm_info microVM 元信息、内存大小、CPU 模板、boot source、huge page 等 恢复时重建 machine config
    kvm_state KVM capability modifiers 用同样 KVM capability 创建 VM
    vm_state guest memory layout、resource allocator、架构 VM 状态 恢复内存区域、IRQ chip、clock/timer
    vcpu_states 每个 vCPU 的架构状态 恢复寄存器、MSR/CPUID/GIC 关联信息等

    SNAPSHOT_VERSION 当前是 10.0.0：src/vmm/src/persist.rs。snapshot 文件本身有架构相关 magic：x86_64 是 0x0710_1984_8664_0000，aarch64 是 0x0710_1984_AAAA_0000：src/vmm/src/snapshot/mod.rs。

    这意味着 snapshot 天然带架构边界。x86_64 snapshot 不会被 aarch64 按同一种格式接受，反过来也一样。

    12.2 创建 snapshot 的控制流

    API 层的 CreateSnapshot 只在 runtime controller 中支持；LoadSnapshot 在 post-boot 会被拒绝：src/vmm/src/rpc_interface.rs。创建入口会记录耗时并调用 persist::create_snapshot：src/vmm/src/rpc_interface.rs。

    sequenceDiagram participant API as RuntimeApiController participant VMM as Vmm participant Dev as DeviceManager participant VCPU as vCPU threads participant VM as Vm/GuestMemory participant File as snapshot files API->>VMM: create_snapshot(params) VMM->>Dev: check_unsnapshottable_devices VMM->>Dev: save device states VMM->>VCPU: VcpuEvent::SaveState VCPU-->>VMM: VcpuResponse::SavedState VMM->>VMM: save KVM + VM arch state VMM-->>API: MicrovmState API->>File: write state file API->>VM: snapshot_memory_to_file VM->>File: full dump or dirty pages API->>Dev: mark_virtio_queue_memory_dirty

    persist::create_snapshot 的顺序很明确：src/vmm/src/persist.rs。

    1. vmm.save_state(vm_info) 生成 MicrovmState。
    2. snapshot_state_to_file 写状态文件。
    3. vm.snapshot_memory_to_file 写 guest memory 文件。
    4. DeviceManager::mark_virtio_queue_memory_dirty 重新标记 virtio queue memory。

    Vmm::save_state 先检查不支持 snapshot 的设备，再保存 device state，然后保存 vCPU state、KVM state 和 VM state：src/vmm/src/lib.rs。

    这里有一个重要顺序：设备状态必须先于 KVM 状态保存。源码注释说明，某些设备在保存时可能修改 virtio transport 并向 guest 注入 interrupt；如果先保存 KVM 状态，这个 interrupt 恢复后可能丢失：src/vmm/src/lib.rs。

    snapshot 要求 vCPU 处于 paused 状态。VcpuEvent::SaveState 在 running 状态会返回 NotAllowed("save/restore unavailable while running")；只有 paused 状态才会调用 kvm_vcpu.save_state()：src/vmm/src/vstate/vcpu.rs，src/vmm/src/vstate/vcpu.rs。

    所以用户侧正确流程通常是：Pause -> CreateSnapshot -> Resume。Firecracker 不会为了 snapshot 自动暂停正在运行的 vCPU。

    12.3 状态文件格式与版本边界

    状态文件由 Snapshot<MicrovmState> 写出。Snapshot::new 写入 header：magic 和 SNAPSHOT_VERSION；Snapshot::save 用 bitcode 序列化，然后追加 CRC64：src/vmm/src/snapshot/mod.rs，src/vmm/src/snapshot/mod.rs。

    加载时，Snapshot::load 会：

    1. 限制最大反序列化大小为 10MB。
    2. 分离最后 8 字节 CRC。
    3. 反序列化 Snapshot<Data>。
    4. 校验 magic 是否匹配当前架构。
    5. 校验版本：major 必须相同，minor 不能高于当前版本。
    6. 校验 CRC64：src/vmm/src/snapshot/mod.rs。
    flowchart LR State[MicrovmState] --> Wrap[Snapshot header] Wrap --> Bitcode[bitcode serialize] Bitcode --> Crc[append CRC64] Crc --> File[state snapshot file] File --> Read[read with 10MB limit] Read --> Split[split data and CRC] Split --> Decode[bitcode deserialize] Decode --> Magic[check arch magic] Magic --> Version[check version] Version --> CrcCheck[check CRC64] CrcCheck --> Restored[MicrovmState]

    因此兼容策略不是“任意旧版本都能恢复”。当前源码只接受同 major、minor 不高于当前的格式；结构字段变化仍要受 bitcode 类型匹配约束。

    12.4 guest memory 文件：Full、Diff 与 UFFD

    创建 snapshot 时，内存文件路径来自 CreateSnapshotParams.mem_file_path。SnapshotType 有 Full 和 Diff 两种：src/vmm/src/vmm_config/snapshot.rs。

    Vm::snapshot_memory_to_file 会打开或创建内存文件，按当前 guest memory 总大小设置文件长度。Full snapshot 调 guest_memory().dump() 写出完整内存，并 reset KVM dirty bitmap 与 Firecracker 的 guest memory dirty 标记；Diff snapshot 获取 dirty bitmap，只 dump dirty pages：src/vmm/src/vstate/vm.rs。

    CreateSnapshot 对 Diff snapshot 打 dev preview warning：src/vmm/src/rpc_interface.rs。这说明 diff snapshot 是可用路径，但源码把它标为开发预览能力。

    恢复时，guest memory backend 有两种：src/vmm/src/vmm_config/snapshot.rs。

    backend 机制 适用理解
    File guest_memory_from_file 打开内存文件，并用 memory::snapshot_file 映射恢复 简单直接，Firecracker 自己从文件恢复内存
    Uffd Firecracker 创建匿名 guest memory，注册 userfaultfd，把 fd 和 region mapping 通过 UDS 交给外部 page fault handler 支持按需填充内存页，恢复路径可以更懒加载

    UFFD 路径会创建 anonymous guest memory，注册每个 memory region 到 userfaultfd，并通过 UDS 发送 GuestRegionUffdMapping 和 uffd fd：src/vmm/src/persist.rs。

    12.5 恢复 snapshot 的控制流

    LoadSnapshot 只能在 pre-boot controller 中执行。如果此前已经走过普通 boot 配置路径，boot_path 为真，load 会被拒绝：src/vmm/src/rpc_interface.rs。

    restore_from_snapshot 的主路径是：src/vmm/src/persist.rs

    sequenceDiagram participant API as PrebootApiController participant Persist as restore_from_snapshot participant Mem as guest memory backend participant Builder as build_microvm_from_snapshot participant Dev as DeviceManager participant VCPU as vCPU threads API->>Persist: LoadSnapshot(params) Persist->>Persist: Snapshot::load -> MicrovmState Persist->>Persist: apply net/vsock overrides Persist->>Persist: update VmResources machine config Persist->>Persist: snapshot_state_sanity_check Persist->>Mem: guest_memory_from_file or guest_memory_from_uffd Persist->>Builder: build_microvm_from_snapshot Builder->>Builder: create KVM + VM + vCPUs Builder->>Builder: restore memory regions Builder->>VCPU: restore vCPU KVM state Builder->>Builder: restore VM arch state Builder->>Dev: DeviceManager::restore Builder->>VCPU: start_vcpus paused API->>API: optionally resume_vm

    恢复前会做几个关键动作：

    1. 读状态文件：snapshot_state_from_file 打开 snapshot 并 Snapshot::load：src/vmm/src/persist.rs。
    2. 应用 network override：按 iface_id 修改 net device 的 tap_if_name：src/vmm/src/persist.rs。
    3. 应用 vsock override：修改 vsock backend UDS path：src/vmm/src/persist.rs。
    4. 用 snapshot 中的 vCPU 数、内存大小、SMT、CPU template、huge page 等更新 VmResources.machine_config：src/vmm/src/persist.rs。
    5. 做 sanity check：必须有 memory region，必须有 DRAM，DRAM region 只能有一个 plugged slot：src/vmm/src/persist.rs。

    build_microvm_from_snapshot 会先创建 KVM、VM 和 vCPU，恢复 memory regions；x86_64 还会根据 snapshot 中的 TSC 频率决定是否 scale 当前 vCPU TSC：src/vmm/src/builder.rs。

    恢复顺序同样关键：先 restore vCPU state，再 restore VM arch state，最后 restore devices。源码说明 VMGenID restore 会向 guest 注入 interrupt，所以必须在 KVM state 恢复之后再恢复 DeviceManager，否则 interrupt 可能被覆盖：src/vmm/src/builder.rs。

    恢复完成后 vCPU 线程以 paused 状态启动；只有 LoadSnapshotParams.resume_vm 为真时，preboot controller 才会调用 resume_vm()：src/vmm/src/rpc_interface.rs。

    12.6 设备状态如何保存和恢复

    DeviceManager::save 保存四块状态：MMIO、ACPI、PCI、serial：src/vmm/src/device_manager/mod.rs。

    MMIO 侧的 DeviceStates 包含 block、net、vsock、balloon、MMDS、entropy、pmem、virtio-mem，以及 aarch64 的 legacy MMIO 设备：src/vmm/src/device_manager/persist.rs。

    flowchart TB DeviceManager[DeviceManager::save] --> Mmio[mmio_devices.save] DeviceManager --> Acpi[acpi_devices.save] DeviceManager --> Pci[pci_devices.save] DeviceManager --> Serial[serial_state] Mmio --> Transport[MmioTransportState] Mmio --> DevState[per-device state] Pci --> PciTransport[VirtioPciDeviceState] Pci --> PciDevState[per-device state] Acpi --> Vmgenid[VMGenIDState] Acpi --> Vmclock[VmClockState]

    MMIO 保存每个 virtio 设备时，会先调用设备的 prepare_save()，再保存 transport state。注释解释原因：设备 prepare 可能修改 transport state 或触发 guest interrupt，所以必须先 prepare，再保存 transport：src/vmm/src/device_manager/persist.rs。

    恢复时，MMIO 路径会 restore 具体设备对象，restore MmioTransport，重新注册 MMIO bus、ioeventfd、irqfd 和 EventManager subscriber；如果设备原先是 activated，还会重新调用 activate(mem, interrupt)：src/vmm/src/device_manager/persist.rs。

    PCI 路径类似，但先恢复 PCI segment，再按保存的 PCI transport/SBDF 恢复各类 virtio PCI device：src/vmm/src/device_manager/pci_mngr.rs。

    能力边界也在这里体现：check_unsnapshottable_devices 会拒绝包含 vhost-user-block 的 microVM，因为该设备当前没有 snapshot support：src/vmm/src/lib.rs。

    12.7 ARM64 与 x86_64 在 snapshot 上的差异

    snapshot 的共同点是 MicrovmState 顶层结构一致；差异集中在 VmState、VcpuState、snapshot magic、timer/interrupt controller 和 clock restore。

    维度 x86_64 aarch64
    snapshot magic 0x0710_1984_8664_0000 0x0710_1984_AAAA_0000
    VM state guest memory、resource allocator、PIT、KVM clock、PIC master/slave、IOAPIC guest memory、GIC state、resource allocator
    vCPU state CPUID、MSRs、debug regs、LAPIC、MP state、regs、sregs、vcpu events、xcrs、xsave、TSC kHz MP state、all registers、MPIDR、kvm_vcpu_init、pvtime IPA
    restore 特殊处理 可按 snapshot TSC 频率 scale 当前 vCPU；clock_realtime 可影响 KVM clock restore SVE vector length register 需在 finalize 前恢复；clock_realtime 不支持
    CPU 兼容提示 比较 host CPU vendor 与 snapshot CPUID vendor 比较 host manufacturer ID 与 snapshot register 中的 manufacturer ID

    x86_64 的 VM state 保存 PIT、KVM clock、PIC 和 IOAPIC：src/vmm/src/arch/x86_64/vm.rs。vCPU state 保存 CPUID、MSR、LAPIC、XSAVE、TSC 等：src/vmm/src/arch/x86_64/vcpu.rs。

    aarch64 的 VM state 保存 GIC state；保存时需要 vCPU 的 MPIDR 列表，因为 GIC redistributor/ICC 状态与 vCPU 关联：src/vmm/src/arch/aarch64/vm.rs。vCPU state 保存 all registers、MPIDR、kvm_vcpu_init 和 pvtime IPA：src/vmm/src/arch/aarch64/vcpu.rs。

    恢复时，x86_64 会先按 TSC 频率判断是否需要 scaling，再 restore vCPU 和 VM state：src/vmm/src/builder.rs。aarch64 如果传入 clock_realtime 会直接报 UnsupportedClockRealtime，然后用 MPIDR 恢复 VM/GIC state：src/vmm/src/builder.rs。

    12.8 Snapshot 能力边界小结

    Firecracker snapshot 的能力边界可以压缩成六点：

    1. 创建 snapshot 需要 microVM 已启动且 vCPU 已 paused；running 状态下保存 vCPU state 会被拒绝。
    2. load snapshot 是 pre-boot 行为；普通启动后不能再执行 LoadSnapshot。
    3. snapshot 分成状态文件和内存文件；状态文件有 arch magic、版本和 CRC64，内存文件独立保存 guest RAM。
    4. Full snapshot 写完整内存并 reset dirty tracking；Diff snapshot 写 dirty pages，并被标记为 dev preview。
    5. 设备必须实现 Persist 才能可靠保存；vhost-user-block 当前被明确拒绝。
    6. ARM64 与 x86_64 的差异主要在 VM/vCPU KVM 状态：x86 侧是 PIT/PIC/IOAPIC/KVM clock/LAPIC/MSR/CPUID，ARM64 侧是 GIC/MPIDR/all registers/KVI/pvtime。

    13. 隔离机制：jailer、seccomp 与 KVM 边界

    Firecracker 的隔离不是单一机制，而是分层组合：

    1. KVM 把 guest CPU/内存执行放进内核虚拟化边界。
    2. Firecracker VMM 只暴露很小的设备模型和 API 面。
    3. seccomp 按线程限制 Firecracker 进程可用 syscall。
    4. jailer 在 Firecracker 外层建立 chroot、uid/gid、cgroup、namespace、rlimit 和设备节点边界。

    换句话说，KVM 负责“guest 和 host 内核之间的虚拟化边界”，Firecracker 负责“用户态设备模型边界”，jailer/seccomp 负责“Firecracker 进程本身的 host 侧攻击面边界”。

    13.1 两层隔离模型

    flowchart TB Host[Host OS] --> Jailer[jailer process] Jailer -->|copy binary + chroot + uid/gid + cgroup + namespace| FC[firecracker process] FC --> API[API thread] FC --> VMM[VMM/EventManager thread] FC --> VCPU[vCPU threads] API -->|api seccomp| ApiFilter[seccomp api] VMM -->|vmm seccomp| VmmFilter[seccomp vmm] VCPU -->|vcpu seccomp| VcpuFilter[seccomp vcpu] VMM --> KVM[/dev/kvm] VCPU --> KVM VMM --> Tun[/dev/net/tun] VMM --> Uffd[/dev/userfaultfd optional]

    jailer 是独立二进制，它最终 exec Firecracker。Firecracker 自己并不在源码里调用 jailer；jailer 先整理进程环境，再把 Firecracker 放进受限目录与身份下运行。

    seccomp 则在 Firecracker 进程内部安装。它按线程类别分成 api、vmm、vcpu 三类：src/firecracker/src/seccomp.rs。

    13.2 jailer 的主流程

    jailer 启动后先 sanitize_process：关闭继承来的 fd，只保留 stdin/stdout/stderr，并清理环境变量：src/jailer/src/main.rs。

    随后 Env::run 执行真正隔离流程：src/jailer/src/env.rs。

    sequenceDiagram participant J as jailer participant FS as filesystem participant CG as cgroup participant NS as namespace participant FC as firecracker J->>J: sanitize_process J->>FS: copy firecracker binary into chroot J->>NS: join netns if configured J->>J: install rlimits J->>CG: write cgroup values and attach pid J->>FS: copy arm64 cache/MIDR info if needed J->>NS: unshare mount namespace J->>FS: pivot_root into jail J->>FS: create /dev/kvm /dev/net/tun /dev/urandom /dev/userfaultfd J->>J: optional daemonize J->>FC: exec with uid/gid and Firecracker args

    关键步骤如下：

    步骤 源码 作用
    复制 Firecracker binary copy_exec_to_chroot 不用 hard link，避免多个 Firecracker 共享可执行文件映射
    加入 netns join_netns 用 setns(..., CLONE_NEWNET) 进入指定网络 namespace
    设置 rlimit ResourceLimits::install 限制文件大小、fd 数等
    设置 cgroup CgroupConfiguration::setup 写 cgroup 参数并 attach 当前 pid
    chroot/pivot_root chroot 新 mount namespace + bind mount + pivot_root + umount old root
    创建设备节点 mknod_and_own_dev 在 jail 中暴露 /dev/kvm、/dev/net/tun、/dev/urandom、可选 /dev/userfaultfd

    copy_exec_to_chroot 的注释明确说明不用 hard link 的安全原因：copy 可以避免多个 Firecracker 进程共享可执行文件的内存映射：src/jailer/src/env.rs。

    chroot 不是简单 chroot(2)。它先 unshare(CLONE_NEWNS) 创建 mount namespace，再把 mount propagation 改为 slave，bind mount jail root，pivot_root，切到 /，最后卸载并删除 old root：src/jailer/src/chroot.rs。

    13.3 cgroup、rlimit、namespace 的边界

    cgroup 抽象是 Cgroup trait：写 property values，并把当前 pid attach 到 cgroup：src/jailer/src/cgroup.rs。setup_cgroup_conf 会先遍历写入所有 cgroup 值，再遍历 attach pid，因为 cpuset 这类 controller 可能要求先设置 cpuset.mems、cpuset.cpus 等属性：src/jailer/src/cgroup.rs。

    rlimit 由 ResourceLimits::install 设置。当前实现支持 file size 和 nofile，最终走 setrlimit：src/jailer/src/resource_limits.rs。

    network namespace 是可选的。jailer 用 OpenOptions 打开指定 netns 路径，并调用 setns(fd, CLONE_NEWNET)：src/jailer/src/env.rs。

    PID namespace 也是可选的。启用 --new-pid-ns 时，jailer 使用 clone(CLONE_NEWPID)，子进程 exec Firecracker，父进程记录 pid 后退出：src/jailer/src/env.rs。

    13.4 ARM64 下 jailer 的额外处理

    aarch64 有两个额外步骤：复制 host CPU cache topology 信息，以及复制 midr_el1 到 jail 内。

    copy_cache_info 把 /sys/devices/system/cpu/cpu0/cache 下若干 cache 属性文件复制到 chroot 中：src/jailer/src/env.rs。

    copy_midr_el1_info 把 /sys/devices/system/cpu/cpu0/regs/identification/midr_el1 复制到 chroot 中：src/jailer/src/env.rs。

    这和前面 snapshot 的 ARM64 CPU manufacturer 校验能对应起来：Firecracker 在 jail 内仍需要读取部分 CPU 身份/拓扑信息，jailer 需要提前把必要 sysfs 信息复制进去。

    13.5 seccomp filter 如何生成和分类

    Firecracker 启动时根据命令行构造 SeccompConfig：src/firecracker/src/main.rs。

    配置 来源 行为
    --no-seccomp SeccompConfig::None 返回三类空 filter，不安装 syscall 限制
    未指定自定义 filter SeccompConfig::Advanced 使用编译期生成的默认 BPF filter
    --seccomp-filter <path> SeccompConfig::Custom 从用户指定文件反序列化 BPF filter

    默认 filter 通过 include_bytes!(OUT_DIR/seccomp_filter.bpf) 编进 Firecracker binary；自定义 filter 从文件读取。两者都会经过 filter_thread_categories，只允许 vmm、api、vcpu 三类，并要求三类都存在：src/firecracker/src/seccomp.rs。

    BpfThreadMap 的类型是 HashMap<String, Arc<BpfProgram>>，也就是“线程类别 -> BPF 指令列表”：src/vmm/src/seccomp.rs。反序列化时有 100KB 输入上限，防止异常大的 filter 输入导致内存分配问题：src/vmm/src/seccomp.rs。

    13.6 seccomp 在哪些线程安装

    apply_filter 的实现很直接：空 filter 直接返回；非空 filter 先检查长度不超过 Linux BPF 4096 条指令上限，再 prctl(PR_SET_NO_NEW_PRIVS, 1)，最后 seccomp(SECCOMP_SET_MODE_FILTER, ...)：src/vmm/src/seccomp.rs。

    三类 filter 的安装点如下：

    flowchart TB Main[firecracker main] --> Filters[get_filters -> BpfThreadMap] Filters --> ApiFilter[api] Filters --> VmmFilter[vmm] Filters --> VcpuFilter[vcpu] ApiFilter --> ApiThread[ApiServer::run] VcpuFilter --> VcpuThread[Vcpu::run] VmmFilter --> Builder[build_microvm_for_boot / build_microvm_from_snapshot] ApiThread --> ApplyApi[apply_filter api] VcpuThread --> ApplyVcpu[apply_filter vcpu] Builder --> ApplyVmm[apply_filter vmm]

    API 线程在 ApiServer::run 启动 HTTP server 前安装 api filter：src/firecracker/src/api_server/mod.rs。

    vCPU 线程在 Vcpu::run 一进入线程主循环时安装 vcpu filter，随后才进入 paused/running 状态机：src/vmm/src/vstate/vcpu.rs。

    VMM 线程的 filter 在 microVM 构建末尾安装。普通 boot 路径在 build_microvm_for_boot 中，vCPU 线程已经启动并停在 paused 状态后，VMM 线程安装 vmm filter，源码注释要求它是 resume vCPU 前的最后步骤：src/vmm/src/builder.rs。

    snapshot restore 路径也类似：build_microvm_from_snapshot 在 start vCPUs 之后、返回 VMM 之前安装 vmm filter：src/vmm/src/builder.rs。

    如果 --no-api，main 会从 filter map 中移除 api，只保留 vmm 和 vcpu，因为不会创建 API thread：src/firecracker/src/main.rs。

    13.7 隔离机制的能力边界

    Firecracker 的隔离边界不是“完全没有 host 接触面”。它仍需要这些 host 能力：

    1. /dev/kvm：KVM VM/vCPU 创建与运行。
    2. /dev/net/tun：virtio-net TAP 后端。
    3. /dev/urandom：MMDS v2 等随机性需求。
    4. /dev/userfaultfd：UFFD snapshot restore 时可选。
    5. host block file、vsock UDS、metrics/log FIFO 或文件等显式配置的后端资源。

    jailer 的作用是把这些能力变成“显式放进 jail 的最小集合”。seccomp 的作用是让 Firecracker 线程在初始化完成后只能调用对应阶段需要的 syscall。

    这解释了 Firecracker 的安全设计取向：它不把隔离完全寄托在 VMM 代码正确性上，而是用小设备模型减少攻击面，用 jailer 限制进程环境，用 seccomp 限制 syscall 面，用 KVM 提供 guest 执行边界。

    14. ARM64 vs x86_64：同一 VMM 骨架下的架构分叉

    Firecracker 在两种架构上共享大量 VMM 骨架：API、VMM action、KVM fd/VM fd/vCPU fd、guest memory、EventManager、virtio device、snapshot 框架和 jailer/seccomp 都是同一套抽象。

    真正分叉发生在 src/vmm/src/arch/{aarch64,x86_64}、cpu_config/{aarch64,x86_64} 和少量设备/启动描述代码里。可以把差异压缩成一句话：x86_64 更像“精简 PC 平台”，ARM64 更像“virt machine + FDT + GIC”。

    14.1 分叉地图

    flowchart TB Shared[shared VMM core] --> Builder[builder.rs] Builder --> ArchBoot[arch::configure_system_for_boot] Builder --> ArchVm[arch VM] Builder --> ArchVcpu[arch vCPU] Builder --> CpuConfig[cpu_config] Builder --> Snapshot[snapshot state] ArchBoot --> ABoot[aarch64: FDT boot] ArchBoot --> XBoot[x86_64: cmdline + MPTable + PVH/Linux boot + ACPI] ArchVm --> AVm[aarch64: GIC device after vCPU create] ArchVm --> XVm[x86_64: irqchip/PIT before vCPU create + PIO bus] ArchVcpu --> AVcpu[aarch64: KVI + one-regs + MPIDR + pvtime] ArchVcpu --> XVcpu[x86_64: CPUID + MSRs + LAPIC + XSAVE + TSC] CpuConfig --> ACpu[aarch64: register modifiers] CpuConfig --> XCpu[x86_64: CPUID/MSR modifiers]

    14.2 guest memory layout

    ARM64 的 DRAM 从 0x8000_0000，也就是 2GiB 开始；最大 RAM 是 1022GiB：src/vmm/src/arch/aarch64/layout.rs。它的 arch_memory_regions 从 DRAM_MEM_START 开始分配，并避开 256GiB 起的 64-bit MMIO gap：src/vmm/src/arch/aarch64/mod.rs。

    x86_64 的 guest memory 从 0 开始，但需要避开 32-bit 地址末尾的 1GiB MMIO gap，以及 256GiB 位置的 256GiB 64-bit MMIO gap：src/vmm/src/arch/x86_64/mod.rs。

    flowchart LR subgraph A[aarch64] A0[0..1GiB ROM/RAM/I/O area] --> A1[1GiB..2GiB MMIO32 + PCI config] A1 --> A2[2GiB DRAM start] A2 --> A3[256GiB MMIO64 gap] A3 --> A4[DRAM may continue] end subgraph X[x86_64] X0[0..640KiB RAM] --> X1[system data / EBDA / RSDP area] X1 --> X2[1MiB kernel high memory start] X2 --> X3[32-bit MMIO gap before 4GiB] X3 --> X4[256GiB MMIO64 gap] end
    维度 aarch64 x86_64
    DRAM 起点 0x8000_0000 0
    kernel 起点 SYSTEM_MEM_START + SYSTEM_MEM_SIZE，即 DRAM 起点后预留 2MiB HIMEM_START，即 1MiB
    boot 描述区 FDT 放在 DRAM 末尾附近 zero page、PVH info、memmap、MPTable、ACPI
    MMIO32 1GiB 到 2GiB，下部还放 boot timer/RTC/serial 4GiB 前 1GiB MMIO gap
    MMIO64 256GiB 起 256GiB 256GiB 起 256GiB

    这会影响 rootfs、initrd、FDT/ACPI、virtio-mmio 地址、PCI config window 和 snapshot memory region 描述。Firecracker 的共享 VmResources.allocate_guest_memory() 最终会走架构自己的 arch_memory_regions。

    14.3 KVM wrapper 与 VM 创建顺序

    x86_64 的 Kvm 初始化会请求 dynamic XSTATE features，并缓存 host 支持的 CPUID：src/vmm/src/arch/x86_64/kvm.rs。它还暴露 msrs_to_save()，用于 snapshot 保存 MSR 列表：src/vmm/src/arch/x86_64/kvm.rs。

    ARM64 的 Kvm 初始化更薄，保存 KVM fd 和 capability modifiers；额外暴露 optional_capabilities()，当前关注 KVM_CAP_COUNTER_OFFSET：src/vmm/src/arch/aarch64/kvm.rs。

    VM irqchip 创建顺序相反：

    阶段 aarch64 x86_64
    pre-create vCPU 不做 irqchip setup create_irq_chip + create_pit2
    post-create vCPU 创建 GIC 不做额外 setup
    原因 KVM ARM 要求 vCPU 创建后再初始化 irqchip x86 需要先有 in-kernel irqchip/PIT

    ARM64 源码注释明确：KVM_CREATE_VCPU 在 IRQCHIP 已初始化时会报错，所以 GIC 要在 vCPU 创建之后 setup：src/vmm/src/arch/aarch64/vm.rs。

    x86_64 源码则在 arch_pre_create_vcpus 中创建 irqchip/PIT，并设置 dummy speaker port，避免 port 0x61 写操作触发 userspace exit：src/vmm/src/arch/x86_64/vm.rs。

    14.4 boot 配置：FDT vs PC boot structures

    两端都通过 configure_system_for_boot 完成最后的架构 boot 配置，但内容完全不同。

    sequenceDiagram participant B as builder participant A as aarch64 configure_system_for_boot participant X as x86_64 configure_system_for_boot participant M as guest memory B->>A: configure_system_for_boot(...) A->>A: build CpuConfiguration from one-regs A->>A: configure vCPU boot regs A->>A: override CLIDR_EL1 from host sysfs A->>M: write FDT with CPUs/memory/chosen/GIC/timer/devices/PCI B->>X: configure_system_for_boot(...)     ARM64 把 kernel command line 放进 FDT 的 /chosen，并把 CPU、memory、GIC、timer、clock、PSCI、devices、VMGenID、VMClock 和 PCI 节点写入 FDT：src/vmm/src/arch/aarch64/fdt.rs。

    x86_64 则先把 command line 写到 CMDLINE_START，再写 MPTable；根据 kernel entry protocol 分成 PVH boot 或 Linux boot，最后写 ACPI tables：src/vmm/src/arch/x86_64/mod.rs。

    x86_64 的 PVH 路径会构造 hvm_start_info、module list 和 memory map，并写到 PVH_INFO_START/MEMMAP_START：src/vmm/src/arch/x86_64/mod.rs。Linux boot 路径会构造 zero page boot params、E820 map、cmdline/initrd 信息：src/vmm/src/arch/x86_64/mod.rs。

    14.5 CPU template 与 vCPU state

    CPU template 是另一个核心分叉点。

    维度 aarch64 x86_64
    base CPU config 初始化 vCPU，读取 template 指定的 one-reg register list 从 KVM supported CPUID 构造 CPUID，并从第一个 vCPU 读取 template 指定 MSR
    template 修改对象 Aarch64RegisterVec CPUID leaves/subleaves + MSR map
    vCPU configure set_one_reg 写寄存器，再 setup boot regs 配置 CPUID/MSR/regs/sregs 等

    ARM64 的 CpuConfiguration::new 会先对所有 vCPU 调 init(&cpu_template.vcpu_features)，再从第一个 vCPU 读取指定寄存器；apply_template 对 register bitmap 做修改：src/vmm/src/cpu_config/aarch64/mod.rs。

    x86_64 的 CpuConfiguration::new 由 KVM supported CPUID 和第一个 vCPU 的 MSR 值构造，apply_template 修改 CPUID leaf/subleaf 和 MSR：src/vmm/src/cpu_config/x86_64/mod.rs。

    ARM64 vCPU 创建时会获取 kvm_vcpu_init，默认启用 PSCI 0.2，且 secondary vCPU 初始带 KVM_ARM_VCPU_POWER_OFF：src/vmm/src/arch/aarch64/vcpu.rs。snapshot 保存时会清掉这个 power-off bit，因为恢复时 guest 已经过了 boot 阶段：src/vmm/src/arch/aarch64/vcpu.rs。

    x86_64 vCPU state 保存顺序更敏感。源码注释说明 GET_MP_STATE、GET_VCPU_EVENTS、GET_LAPIC 等 ioctl 之间存在状态副作用和顺序要求：src/vmm/src/arch/x86_64/vcpu.rs。

    14.6 interrupt controller 与设备发现

    ARM64 通过 KVM device 创建 GIC。ArchVm 保存 GICDevice fd，snapshot 中保存 GicState：src/vmm/src/arch/aarch64/vm.rs。FDT 中的 GIC node、timer node、device node 共同告诉 guest 如何发现 interrupt controller 和设备。

    x86_64 通过 KVM in-kernel irqchip/PIT 加上 IOAPIC/PIC/LAPIC 模型。VmState 保存 PIT、KVM clock、PIC master/slave 和 IOAPIC：src/vmm/src/arch/x86_64/vm.rs。设备发现主要通过 kernel cmdline、ACPI、PCI config 和少量 legacy device 组合完成。

    这也解释了为什么前面的设备模型章节里，x86_64 的 MMIO virtio 设备还需要追加 kernel cmdline/ACPI DSDT data，而 ARM64 更自然地通过 FDT 表达设备节点。

    14.7 snapshot 差异回看

    snapshot 顶层 MicrovmState 一样，但里面的 arch state 不一样。

    flowchart TB MicrovmState[MicrovmState] --> Common[common: vm_info/kvm_state/device_states] MicrovmState --> ArchVmState[vm_state] MicrovmState --> ArchVcpuState[vcpu_states] ArchVmState --> AState[aarch64: memory + GIC + resource_allocator] ArchVmState --> XState[x86_64: memory + resource_allocator + PIT + clock + PIC + IOAPIC] ArchVcpuState --> AVState[aarch64: mp_state + regs + MPIDR + KVI + pvtime] ArchVcpuState --> XVState[x86_64: CPUID + MSRs + LAPIC + regs/sregs + events + XSAVE + TSC]

    恢复时 x86_64 会按 snapshot 中的 TSC 频率判断是否需要 TSC scaling；aarch64 会用 MPIDR 列表恢复 GIC state，并拒绝 clock_realtime：src/vmm/src/builder.rs。

    snapshot 文件本身也有架构 magic：x86_64 和 aarch64 的 magic 常量不同，所以跨架构不是兼容目标。

    14.8 jailer 与运行环境差异

    jailer 在 ARM64 下有额外处理：复制 cache topology 和 midr_el1 到 jail 内：src/jailer/src/env.rs，src/jailer/src/env.rs。

    这与 ARM64 的 FDT/CPU 模板路径相关：guest 的 cache 信息来自 host sysfs 与 CLIDR_EL1 的组合，Firecracker 还会在 boot 配置中尝试用 sysfs cache topology 修正 CLIDR_EL1：src/vmm/src/arch/aarch64/mod.rs。

    x86_64 没有对应的 jailer cache/MIDR 复制逻辑，但它在 KVM/VM/vCPU state 上携带更多 PC 兼容状态：CPUID/MSR、PIT、PIC、IOAPIC、LAPIC、KVM clock 和 TSC。

    14.9 架构差异小结

    层次 aarch64 x86_64
    平台模型 virt machine 风格 精简 PC 风格
    内存起点 2GiB 0
    boot 描述 FDT cmdline + MPTable + PVH/Linux boot params + ACPI
    interrupt GICv2/GICv3 KVM device KVM irqchip + PIT + PIC + IOAPIC + LAPIC
    CPU config one-reg register template CPUID/MSR template
    vCPU state MPIDR/KVI/one-reg/pvtime CPUID/MSR/LAPIC/XSAVE/TSC/events

    jailer 特殊处理 copy cache info 和 MIDR_EL1 无对应处理

    所以 Firecracker 的“跨架构一致性”主要体现在控制面、VMM 生命周期、KVM/VM/vCPU 抽象和 virtio 设备骨架；而“架构差异”主要集中在 guest 看到的硬件平台形状。

    15. 设备细节补充：vsock、balloon、pmem、rng、virtio-mem

    第 11 章已经建立了 Firecracker 设备模型的共性：API 配置生成 VmResources，builder 创建 virtio device，DeviceManager 选择 MMIO 或 PCI transport，event-manager 监听 eventfd，设备解析 virtqueue 并通过 interrupt 通知 guest。

    本章下钻五类容易被一句“virtio 设备”带过的设备：vsock、balloon、pmem、rng 和 virtio-mem。它们共享 virtio transport，但设备语义差别很大：有的是 socket 转发，有的是内存回收，有的是 host 文件映射，有的是随机数供给，有的直接改变 KVM memory slot 可访问性。

    flowchart TB Guest[guest virtio driver] --> Transport[MMIO/PCI transport] Transport --> Queue[virtqueue + queue eventfd] Queue --> Handler[event_manager subscriber] Handler --> Vsock[vsock: RX/TX/EVQ + Unix backend fd] Handler --> Balloon[balloon: inflate/deflate/stats/hint/report] Handler --> Pmem[pmem: flush queue + mmap host file] Handler --> Rng[rng: entropy queue + rate limiter] Handler --> Vmem[virtio-mem: plug/unplug/state requests] Vsock --> Snapshot[Persist state] Balloon --> Snapshot Pmem --> Snapshot Rng --> Snapshot Vmem --> Snapshot

    15.1 共同骨架：activate event 到 runtime event

    这五类设备都实现 VirtioDevice 和 MutEventSubscriber，共同生命周期是：

    1. 创建设备对象时先生成 queue、queue eventfd 和 activate eventfd。
    2. VirtioDevice::activate() 初始化 queue 的 guest memory 指针，写 activate eventfd，并把设备状态切到 Activated。
    3. event handler 初始只监听 activate event；激活后移除 activate event，改为监听 runtime queue/backend/rate-limiter/timer 事件。
    4. snapshot 保存 VirtioDeviceState::from_device(self)，也就是 features、queue state、activation 标记等 virtio 公共状态；设备自己的后端状态另行保存。

    这套模式在 vsock、balloon、pmem、rng、virtio-mem 的 event handler 中重复出现：未激活时只注册 activate event，激活后注册 runtime events。差别在于 runtime events 是哪些。

    设备 runtime event 关键后端 snapshot 额外状态
    vsock RXQ、TXQ、EVQ、backend fd Unix domain socket backend CID、backend UDS path、local port counter
    balloon inflate、deflate、stats、stats timer、free-page-hinting、free-page-reporting guest memory discard/page stats target/actual pages、stats、hinting state
    pmem single queue、rate limiter mmap host file + msync config space、host file config、rate limiter
    rng single entropy queue、rate limiter host RNG rate limiter
    virtio-mem single request queue hotpluggable memory region + KVM slots config、requested/usable size、plugged bitmap

    DeviceManager 保存这些状态时，会按 VirtioDeviceType downcast 到具体设备并调用各自的 save()；恢复时再用对应 restore() 创建设备，并通过通用 restore_virtio_device() 把 transport state 和 activation 状态接回去：src/vmm/src/device_manager/persist.rs。

    15.2 vsock：guest CID 到 Unix socket backend

    vsock 不是 Firecracker 内置的网络协议栈。它把 guest 里的 virtio-vsock 包转发到 host 侧 backend，默认后端是 Unix domain socket。设备对象保存 cid、三条 virtqueue、backend、activate event、RX/TX packet 缓冲：src/vmm/src/devices/virtio/vsock/device.rs。

    vsock 的队列语义：

    队列 方向 Firecracker 动作
    RXQ host/backend 到 guest 从 backend 取 pending packet，写入 guest 提供的 RX buffer
    TXQ guest 到 host/backend 从 guest TX queue 解析 VsockPacket，调用 backend send_pkt()
    EVQ device event 写入 TRANSPORT_RESET_EVENT 之类的事件给 guest

    事件处理链路如下：

    sequenceDiagram participant G as guest vsock driver participant Q as virtqueue eventfd participant V as Vsock device participant B as Vsock backend G->>Q: notify TXQ Q->>V: PROCESS_TXQ V->>V: process_tx parses guest packet V->>B: send_pkt(packet) B-->>V: may queue response V->>V: if pending RX, process_rx V-->>G: signal used TXQ/RXQ B->>V: backend fd event V->>B: notify(evset) V->>V: retry TX + drain pending RX V-->>G: signal used queues

    process_tx() 从 TXQ pop descriptor，解析 guest packet；如果 backend 暂时不能接收，就 undo_pop() 并停止处理，等待 backend fd 再通知：src/vmm/src/devices/virtio/vsock/device.rs。event handler 在 TXQ 事件后还会检查 backend 是否产生了响应，如果有就继续 process_rx()：src/vmm/src/devices/virtio/vsock/event_handler.rs。

    snapshot 边界很重要：vsock 保存 frontend 的 CID/virtio state 和 backend 的 UDS path/local port counter，但不保存连接内的 in-flight packet 或活跃连接。kick() 里的注释明确说 vsock 不支持通过 snapshot 保持连接，恢复后是“empty”，只是让 guest 处理 snapshot 前注入的 TRANSPORT_RESET_EVENT：src/vmm/src/devices/virtio/vsock/device.rs。持久化结构也能看到只保存 cid、virtio_state、uds_path、local_port_last：src/vmm/src/devices/virtio/vsock/persist.rs。

    15.3 balloon：内存压力的协商设备，不是强制回收器

    balloon 设备的本质是 VMM 与 guest 协商内存占用。Firecracker 不能在 guest 不配合的情况下可靠地“拿回任意 guest page”；它通过 virtio-balloon 请求 guest inflate/deflate，并可选收集 stats、free-page-hinting、free-page-reporting。

    Balloon::new() 会根据配置动态决定队列数量：最少 inflate/deflate 两条队列；开启 stats polling 后增加 stats queue；开启 free-page-hinting 或 reporting 后继续增加对应队列：src/vmm/src/devices/virtio/balloon/device.rs。event handler 对应注册 inflate、deflate、stats、stats timer、free-page-hinting、free-page-reporting 事件：src/vmm/src/devices/virtio/balloon/event_handler.rs。

    flowchart LR API[PATCH balloon amount/stats] --> Config[Balloon config_space] Config --> IRQ[config interrupt] Guest[guest balloon driver] --> Inflate[inflate queue] Guest --> Deflate[deflate queue] Guest --> Stats[stats queue] Guest --> Hint[free-page hint/report queues] Inflate --> VMM[Balloon handler] Deflate --> VMM Stats --> VMM Hint --> VMM VMM --> Memory[guest memory pages / stats / discard hints]

    snapshot 保存 balloon 的 stats_polling_interval_s、stats_desc_index、latest_stats、hinting_state、config_space.num_pages、config_space.actual_pages 和 virtio state：src/vmm/src/devices/virtio/balloon/persist.rs。恢复时会从 feature bits 反推出是否启用了 free-page-hinting/reporting，再根据 stats/hint/reporting 重建 queue 数量：src/vmm/src/devices/virtio/balloon/persist.rs。如果设备已激活并启用 stats，恢复还会恢复 stats descriptor 并重新 arm timer：src/vmm/src/devices/virtio/balloon/persist.rs。

    因此 balloon 的能力边界是：Firecracker 保存的是设备协商状态，不是“每个 guest page 的所有权历史”。真正哪些 page 可回收，仍取决于 guest balloon driver 的响应和 guest kernel 内存管理。

    15.4 pmem：host 文件 mmap 成 guest persistent memory

    pmem 的实现很直接：配置指定 host 文件，Firecracker 将其 mmap 后作为 guest 可见的 persistent memory 区域，并暴露 virtio-pmem 的 config space：起始地址和大小。设备对象保存 config space、host file、file length、mmap pointer、rate limiter 和原始 PmemConfig：src/vmm/src/devices/virtio/pmem/device.rs。

    pmem 队列只有一种请求：flush。process_chain() 读取 guest 提供的 4-byte request，要求请求类型为 VIRTIO_PMEM_REQ_TYPE_FLUSH，然后对 mmap 区域调用 msync(..., MS_SYNC)，再把成功/失败 status 写回 response descriptor：src/vmm/src/devices/virtio/pmem/device.rs。

    sequenceDiagram participant G as guest pmem driver participant Q as pmem queue participant P as Pmem device participant F as host backing file mmap G->>Q: FLUSH request Q->>P: queue eventfd P->>P: validate request + status descriptor P->>F: msync(mmap_ptr, file_len, MS_SYNC) P->>G: write status + queue interrupt

    pmem 的 rate limiter 只约束 queue 处理节奏；如果 queue event 到来时 limiter blocked，设备不处理队列，等 limiter event 后再 handle_queue()：src/vmm/src/devices/virtio/pmem/device.rs。event handler 只注册 queue event 和 rate-limiter event：src/vmm/src/devices/virtio/pmem/event_handler.rs。

    snapshot 保存 virtio_state、config_space、PmemConfig 和 rate_limiter_state：src/vmm/src/devices/virtio/pmem/persist.rs。恢复时用同一个配置重新打开/映射 host 文件，并调用 set_mem_region(vm) 把 pmem 区域重新注册到 VM：src/vmm/src/devices/virtio/pmem/persist.rs。这说明 pmem snapshot 并不把 backing file 内容写进 snapshot state；host 文件路径和内容必须在恢复环境中仍然可用且语义一致。

    15.5 rng：单队列随机数填充器

    RNG/Entropy 设备是最薄的一类 virtio 设备。guest 在一条 queue 上提交可写 descriptor，Firecracker 解析 descriptor chain，用 host RNG 填充随机字节，然后把实际写入长度放入 used ring 并触发 interrupt：src/vmm/src/devices/virtio/rng/device.rs。

    它有两个约束：

    1. 单次生成长度被 MAX_ENTROPY_BYTES 限制，避免 guest 构造异常 descriptor 触发 host 侧巨大分配。
    2. 每次处理前检查 rate limiter；预算不足时 undo_pop()，保留 descriptor 等待 limiter event：src/vmm/src/devices/virtio/rng/device.rs。
    flowchart LR Guest[guest rng driver] --> Queue[entropy queue] Queue --> Parse[load writable descriptor chain] Parse --> Limit{rate limiter budget?} Limit -- no --> Undo[undo_pop and wait] Limit -- yes --> Fill[rand::fill bytes] Fill --> Used[add_used + interrupt] Limiter[rate limiter event] --> Queue

    RNG 没有配置空间读写逻辑，read_config 和 write_config 都是空实现：src/vmm/src/devices/virtio/rng/device.rs。snapshot 只保存 virtio state 和 rate limiter state：src/vmm/src/devices/virtio/rng/persist.rs。这符合它的设备语义：随机数输出本身不是可恢复状态，恢复后继续从 host RNG 取新随机数即可。

    15.6 virtio-mem：会改变 KVM memory slot 的设备

    virtio-mem 与前几个设备不同，它不是单纯的 I/O 转发，而是 guest memory hotplug 的控制面。设备保存 virtio config、slot size、plugged block bitmap 和 VM 引用：src/vmm/src/devices/virtio/mem/device.rs。

    它的 config space 里有 addr、region_size、block_size、usable_region_size、plugged_size、requested_size 等字段；guest driver 读取这些字段后，通过单条 request queue 发起四类请求：

    请求 作用
    State(range) 查询指定 block range 当前是 plugged、unplugged 还是 mixed
    Plug(range) 要求把 range 标为 plugged，并更新 KVM slot
    Unplug(range) 要求把 range 标为 unplugged，discard guest memory range，并更新 KVM slot
    UnplugAll unplug 全部 block，并把 usable region size 置 0

    process_mem_queue() 从 queue pop descriptor，解析请求和 response descriptor，然后按请求类型调用 state/plug/unplug/unplug-all handler：src/vmm/src/devices/virtio/mem/device.rs。真正改变内存可访问性的逻辑在 update_range()：它更新 plugged_blocks bitmap 和 config.plugged_size，unplug 时调用 guest_memory().discard_range()，最后调用 update_kvm_slots() 按 block 状态启用或禁用相交的 hotpluggable KVM slot：src/vmm/src/devices/virtio/mem/device.rs。

    sequenceDiagram participant API as API update requested_size participant D as VirtioMem device participant G as guest virtio-mem driver participant K as KVM memory slots API->>D: update_requested_size(MiB) D->>D: validate block alignment and region size D->>G: config interrupt G->>D: Plug/Unplug/State request on MEM_QUEUE D->>D: update plugged_blocks bitmap D->>K: enable/disable intersecting hotplug slots D->>G: response + queue interrupt

    update_requested_size() 只能在设备 active 后调用，并要求 size 按 block size 对齐且不超过 region size；增加 requested size 时，它可能扩大 usable_region_size，然后触发 config interrupt 让 guest driver 继续 plug block：src/vmm/src/devices/virtio/mem/device.rs。

    激活也有一个硬边界：guest 必须 ack VIRTIO_MEM_F_UNPLUGGED_INACCESSIBLE，否则 activate 失败：src/vmm/src/devices/virtio/mem/device.rs。这意味着 Firecracker 的 virtio-mem 语义依赖 guest 支持“未插入内存不可访问”的模型。

    snapshot 保存 addr、region_size、block_size、usable_region_size、requested_size、slot_size 和完整 plugged_blocks bitmap：src/vmm/src/devices/virtio/mem/persist.rs。恢复时根据 bitmap 重算 plugged_size，再用 VirtioMem::from_state() 重建设备：src/vmm/src/devices/virtio/mem/persist.rs。

    15.7 五类设备的边界对比

    设备 Firecracker 真正保存什么 不保存/不保证什么 依赖条件
    vsock CID、virtio queue state、UDS backend path、local port counter 活跃连接、in-flight packets host UDS backend 可重建
    balloon target/actual pages、stats、hinting 状态、queue state guest 每个 page 的完整历史 guest balloon driver 协作
    pmem host file 配置、pmem config space、queue state、rate limiter backing file 内容本身 恢复端 host 文件路径和内容一致
    rng queue state、rate limiter 随机数流历史 host RNG 可用
    virtio-mem hotplug region config、requested/usable size、plugged bitmap guest 对热插内存的上层使用语义 guest ack 必需 feature，hotplug memory region 可重建

    从这里可以看出 Firecracker snapshot 的设计原则：保存“虚拟设备协议状态”和“可重建后端引用”，不保存不可合理序列化或不该由 VMM 拥有的外部世界状态。vsock 连接、pmem 文件内容、RNG 随机流都属于后者。

    16. block I/O 深挖：file engine、io_uring、fallback 与限速

    block 设备是 Firecracker 最能体现“少设备、深路径”的地方。guest 看到的是一个 virtio-blk 设备；VMM 内部真正要解决的是：如何把 virtqueue descriptor 变成 host backing file 的 read/write/flush，并在同步、异步、限速、snapshot 之间保持一致语义。

    16.1 从 virtqueue 到 block request

    block 设备只有一条 virtqueue。guest driver 把 request header、可选 data descriptor、status descriptor 串成 descriptor chain；Firecracker 在 process_queue() 中循环 pop_or_enable_notification()，解析请求并执行：src/vmm/src/devices/virtio/block/virtio/device.rs。

    sequenceDiagram participant G as guest virtio-blk driver participant Q as block virtqueue participant B as VirtioBlock participant R as Request participant E as FileEngine participant F as backing file G->>Q: header + data + status descriptors Q->>B: queue eventfd B->>Q: pop_or_enable_notification B->>R: parse descriptor chain R->>E: read/write/flush/get_id E->>F: host file operation or io_uring submit E-->>R: executed or submitted R-->>Q: write status + add_used B-->>G: queue interrupt

    Request::parse() 做三类校验：descriptor 方向必须符合 request type；read/write 数据长度必须是 512 字节扇区大小的倍数；sector + length 不能越过 backing file 暴露的 nsectors：src/vmm/src/devices/virtio/block/virtio/request.rs。

    请求类型只有四类被支持：IN、OUT、FLUSH、GET_ID。GET_ID 不进入 file engine，而是直接把 disk.image_id 写到 guest data buffer；unsupported request 会以 VIRTIO_BLK_S_UNSUPP 结束：src/vmm/src/devices/virtio/block/virtio/request.rs。

    16.2 FileEngine 是同步/异步的分界线

    DiskProperties 保存 backing file 路径、FileEngine、扇区数和 image id：src/vmm/src/devices/virtio/block/virtio/device.rs。FileEngineType 只有两种：Async 使用 io_uring，Sync 使用 blocking system calls，且默认是 Sync：src/vmm/src/devices/virtio/block/virtio/device.rs。

    flowchart TB Request[Request::process] --> Engine[FileEngine] Engine --> Sync[SyncFileEngine] Engine --> Async[AsyncFileEngine] Sync --> SRead[seek + read_exact_volatile] Sync --> SWrite[seek + write_all_volatile] Sync --> SFlush[file.flush + sync_all] Async --> ARead[io_uring read] Async --> AWrite[io_uring write] Async --> AFlush[io_uring fsync] Async --> CQ[completion eventfd + CQE]

    同步路径非常直观：read/write 先 seek() 到 sector 对应 offset，再通过 guest memory slice 做 volatile transfer；flush 先 file.flush()，再 file.sync_all()：src/vmm/src/devices/virtio/block/virtio/io/sync_io.rs。这条路径简单、默认、可预期，但会在 VMM 设备处理线程里执行阻塞 I/O。

    异步路径把 read/write/fsync 推入 io_uring。AsyncFileEngine::new_ring() 创建 128 entries 的 ring，限制只能使用预注册 fd，并只 allowlist Read、Write、Fsync 三类 opcode：src/vmm/src/devices/virtio/block/virtio/io/async_io.rs。

    异步 read 会把 guest memory slice 的 host pointer 作为 io_uring buffer，并在 user data 中携带 PendingRequest 和需要 dirty tracking 的 guest address；completion pop 时会对 read 写入的 guest memory 调 mark_dirty()：src/vmm/src/devices/virtio/block/virtio/io/async_io.rs。write/flush 不需要标记 guest memory dirty，只携带 pending request：src/vmm/src/devices/virtio/block/virtio/io/async_io.rs。

    16.3 Submitted 与 Executed：同一 request 的两种完成时机

    FileEngine 的返回值刻意分成两类：

    返回 含义 后续动作
    Executed(RequestOk) 同步完成，已经知道结果 立即写 status、add used、触发 interrupt
    Submitted 异步提交成功，结果尚未回来 暂不 add used，等待 io_uring completion event

    Request::process() 把同步返回转成 ProcessingResult::Executed，把异步提交转成 ProcessingResult::Submitted：src/vmm/src/devices/virtio/block/virtio/request.rs。

    VirtioBlock::process_queue() 对 Submitted 不做 used ring 更新；这很关键，因为 guest 不能在 host I/O 完成前复用 descriptor。只有同步完成或错误完成才会 add_used()：src/vmm/src/devices/virtio/block/virtio/device.rs。

    异步完成走另一条事件：block event handler 只在 FileEngine::Async 时注册 engine.completion_evt()；completion event 到来后，process_async_completion_queue() 循环 pop CQE，把 PendingRequest finish 成 status，再 add used 并触发 queue interrupt：src/vmm/src/devices/virtio/block/virtio/event_handler.rs，src/vmm/src/devices/virtio/block/virtio/device.rs。

    16.4 两套限速：rate limiter 与 io_uring backpressure

    block I/O 有两个不同来源的“停下”：

    1. Firecracker rate limiter 没有 ops/bytes token。
    2. io_uring submission/completion 队列暂时满了。

    request-level rate limiter 在真正执行 file engine 前发生。每个 request 先消费 1 个 Ops token；如果是 read/write，再消费 data_len 个 Bytes token。Bytes 不足时会手动补回刚消费的 Ops token：src/vmm/src/devices/virtio/block/virtio/request.rs。

    flowchart TD Pop[pop descriptor] --> Parse[parse Request] Parse --> RL{rate_limit?} RL -- yes --> Undo1[undo_pop, wait rate limiter event] RL -- no --> Engine[FileEngine read/write/flush] Engine --> SyncDone[Executed] Engine --> AsyncSubmitted[Submitted] Engine --> AsyncFull{io_uring throttling error?} AsyncFull -- yes --> Undo2[undo_pop, set is_io_engine_throttled] AsyncSubmitted --> Submit[kick_submission_queue] Submit --> CQ[completion event] CQ --> Resume[clear engine throttle and process queue]

    如果 queue event 到来时 rate limiter 已经 blocked，Firecracker 只计数并不处理队列：src/vmm/src/devices/virtio/block/virtio/device.rs。rate limiter event 到来后，先调用 rate_limiter.event_handler()，再重新 process_queue(0)：src/vmm/src/devices/virtio/block/virtio/device.rs。

    io_uring backpressure 是另一套状态。BlockIoError::is_throttling_err() 只把 async io_uring 的 throttling error 视为 engine throttling：src/vmm/src/devices/virtio/block/virtio/io/mod.rs。遇到它时，process_queue() 会 undo_pop()，设置 is_io_engine_throttled = true，停止继续取 descriptor：src/vmm/src/devices/virtio/block/virtio/device.rs。

    completion event 到来后，Firecracker 先处理完成队列；如果此前处于 is_io_engine_throttled，就清掉该标志并再次 process_queue(0)，继续处理之前 undo_pop() 留在 avail ring 里的请求：src/vmm/src/devices/virtio/block/virtio/device.rs。

    这说明 block 的“fallback”不是 async 自动退回 sync。源码里的 fallback 是控制流 fallback：限速或 ring 满时保留 descriptor，等待对应事件后继续。真正的同步/异步选择由配置中的 file_engine_type 决定，snapshot 也会保存这个选择。

    16.5 snapshot 前为什么要 drain and flush

    block snapshot 的核心风险是：virtqueue state 可保存，但 host backing file 上可能还有异步提交未完成，或者 host page cache 里还有未刷盘数据。Firecracker 在保存 device state 前会调用 prepare_save()，其中 drain_and_flush(false) 会等待异步请求完成并把数据刷到物理介质；如果是 async engine，还会继续处理 completion queue，把完成请求写回 used ring：src/vmm/src/devices/virtio/block/virtio/device.rs。

    FileEngine 层也体现这个语义：async 的 drain_and_flush() 先 submit_and_wait_all()，再 file.sync_all()；sync 的 drain_and_flush() 直接调用 flush()：src/vmm/src/devices/virtio/block/virtio/io/mod.rs。

    snapshot 保存的 block 状态包括：drive id、partuuid、cache type、root flag、disk path、virtio state、rate limiter state 和 file engine type：src/vmm/src/devices/virtio/block/virtio/persist.rs。恢复时用 disk_path 重新打开 backing file，用保存的 file_engine_type 重新创建 Sync 或 Async engine：src/vmm/src/devices/virtio/block/virtio/persist.rs。

    因此 block snapshot 也不是把磁盘内容塞进 snapshot state。它保存的是“这个 block 设备如何重新连回同一个 backing file”的协议状态；backing file 内容必须由外部存储保证一致。

    16.6 block I/O 能力边界

    问题 Firecracker 的处理
    I/O 并发 同一 block 设备一条 virtqueue；async engine 可让 host I/O 通过 io_uring 延后完成
    同步 fallback 默认 engine 是 Sync；Async 不会自动退回 Sync，配置决定 engine 类型
    ring 满或 CQ 满 undo_pop() 保留 descriptor，设置 engine throttled，等 completion event 后继续
    rate limiter request 执行前消费 Ops/Bytes token；不足时 undo_pop() 等 limiter event
    guest memory dirty async read completion 时标记被写入的 guest memory dirty
    snapshot 保存 device/queue/config/limiter/engine type；保存前 drain+flush；不保存 backing file 内容

    block 路径的设计取舍很清楚：Firecracker 不做复杂块设备栈，不模拟 SCSI/NVMe，也不做 host storage 管理。它把 virtio-blk request 精确映射到一个 host file engine，并把复杂度限制在 queue 状态、限速、异步完成和 snapshot 一致性上。

    17. UFFD 深挖：按需恢复内存的协作协议

    Firecracker 的 snapshot restore 有两种 guest memory backend：File 和 Uffd。File 表示 Firecracker 直接把 snapshot memory file 映射/加载为 guest memory；Uffd 表示 Firecracker 先创建匿名 guest memory，再把缺页处理交给外部 page fault handler。

    这不是“Firecracker 内置一个 page fault 线程”。源码里 Firecracker 只负责创建并注册 UFFD、把 UFFD fd 和内存布局发给 handler、保持 fd 生命周期。真正从 snapshot memfile 读取页面并 UFFDIO_COPY 到 guest memory 的动作，由外部 handler 完成。

    17.1 API 层：mem_backend=Uffd

    LoadSnapshotConfig 要求 mem_backend 和旧字段 mem_file_path 二选一。mem_backend 包含 backend_path 和 backend_type；backend_type 只有 File 与 Uffd 两种：src/vmm/src/vmm_config/snapshot.rs。

    {
  "snapshot_path": "vmstate",
  "mem_backend": {
    "backend_type": "Uffd",
    "backend_path": "firecracker-uffd.sock"
  },
  "resume_vm": true
}

    API parser 会拒绝同时传 mem_backend 和 mem_file_path，也会拒绝两者都不传；如果使用旧 mem_file_path，它会被转换成 MemBackendType::File：src/firecracker/src/api_server/request/snapshot.rs。测试用例也覆盖了 backend_type: Uffd 会生成 LoadSnapshotParams：src/firecracker/src/api_server/request/snapshot.rs。

    17.2 restore 主路径：先恢复结构，内存按需填充

    restore_from_snapshot() 先从 state file 读出 MicrovmState，处理 network/vsock override，更新 machine config，再根据 params.mem_backend.backend_type 选择 guest memory 创建方式：src/vmm/src/persist.rs。

    flowchart TB API[PUT /snapshot/load] --> Params[LoadSnapshotParams] Params --> State[snapshot_state_from_file] State --> MemBackend{mem_backend type} MemBackend -- File --> FileMem[guest_memory_from_file] MemBackend -- Uffd --> UffdMem[guest_memory_from_uffd] FileMem --> Build[build_microvm_from_snapshot] UffdMem --> Build Build --> VMM[VMM holds guest memory and optional UFFD fd]

    File 分支有一个硬限制：hugetlbfs guest memory snapshot 不能通过 file backend 恢复；如果 snapshot 来自 huge page guest memory，就必须使用 UFFD：src/vmm/src/persist.rs。官方 hugepages 文档也明确说 huge pages microVM snapshot 只能通过 UFFD 恢复：docs/hugepages.md。

    Uffd 分支调用 guest_memory_from_uffd(mem_backend_path, mem_state, track_dirty_pages, huge_pages)，返回 (guest_memory, Some(uffd))，再传给 build_microvm_from_snapshot()：src/vmm/src/persist.rs。builder 在 Vmm 结构里保存这个 uffd，注释说明目的只是保持它在 Firecracker 进程中 open：src/vmm/src/lib.rs。

    17.3 Firecracker 做了什么：匿名内存、注册 UFFD、发送握手

    guest_memory_from_uffd() 做四件事：

    1. 用 snapshot state 里的 memory layout 创建匿名 guest memory，而不是从 memfile 直接映射内容。
    2. 创建 UFFD 对象，要求 EVENT_REMOVE feature。
    3. 把每个 guest memory region 的 host virtual address range 注册到 UFFD。
    4. 连接 handler 的 UDS，把 mapping JSON 和 UFFD fd 发送过去。
    sequenceDiagram participant H as page fault handler participant FC as Firecracker restore participant U as UFFD object participant M as anonymous guest memory participant S as UDS socket H->>S: bind/listen backend_path FC->>M: create anonymous guest memory regions FC->>U: create UFFD with EVENT_REMOVE FC->>U: register each guest memory region FC->>S: connect backend_path FC->>H: send mapping JSON + UFFD fd FC->>FC: continue build_microvm_from_snapshot H->>U: poll pagefault/remove events

    mapping 的结构叫 GuestRegionUffdMapping，字段包括 Firecracker 进程内 guest memory 的 base_host_virt_addr、region size、memfile 中的 offset、region page size，以及兼容字段 page_size_kib：src/vmm/src/persist.rs。create_guest_memory() 会按 guest memory region 顺序累计 offset，并把这些 mapping 发给 handler：src/vmm/src/persist.rs。

    Firecracker 通过 UnixStream::connect(mem_uds_path) 连接 handler，再用 send_with_fd() 发送 mapping JSON 和 UFFD fd：src/vmm/src/persist.rs。注释里特别说明：如果 handler 崩溃而 Firecracker 关闭了自己的 fd，guest memory 可能退回 anon-mem 行为导致静默错误；所以 Firecracker 也持有 fd，handler 应该用 SO_PEERCRED 获得 Firecracker PID，并在异常时通知或杀掉 Firecracker：src/vmm/src/persist.rs。

    17.4 handler 做了什么：mmap memfile、poll UFFD、UFFDIO_COPY

    示例 handler 的 Runtime::new() 会把 snapshot memory file mmap(MAP_PRIVATE | MAP_POPULATE) 成只读 backing buffer：src/firecracker/examples/uffd/uffd_utils.rs。UffdHandler::from_unix_stream() 从 Firecracker 的 UDS 消息中接收 mapping JSON 和 UFFD fd，并反序列化 mapping：src/firecracker/examples/uffd/uffd_utils.rs。

    当 UFFD 收到 page fault，handler 找到 fault address 所在 region，计算：

    src = backing_buffer + region.offset + (fault_page_addr - region.base_host_virt_addr)
dst = fault_page_addr

    然后调用 uffd.copy(src, dst, len, true)，也就是 UFFDIO_COPY，把 memfile 中对应页复制进 Firecracker 的 guest memory：src/firecracker/examples/uffd/uffd_utils.rs。

    flowchart LR PF[UFFD Pagefault addr] --> Find[find GuestRegionUffdMapping] Find --> Calc[compute memfile offset] Calc --> Copy[UFFDIO_COPY src->dst] Copy --> Resume[blocked faulting thread resumes]

    Runtime::run() 同时 poll UDS 和所有 UFFD fd。UDS 可接收新的 UFFD 握手；UFFD fd 有事件时调用 handler 逻辑处理 page fault：src/firecracker/examples/uffd/uffd_utils.rs。这解释了为什么一个 handler 进程可以服务多个恢复中的 Firecracker 连接。

    17.5 balloon 与 EVENT_REMOVE：UFFD 不只是 page fault

    Firecracker 创建 UFFD 时无条件要求 FeatureFlags::EVENT_REMOVE。源码注释解释：只有存在 balloon 设备时才真正需要它，但提前启用不会改变普通 UFFD 行为；kernel 只在类似 madvise hook 里被动发 remove event：src/vmm/src/persist.rs。

    balloon 设备可能通过 MADV_DONTNEED 回收 guest memory range，这会让 userfaultfd 收到 UFFD_EVENT_REMOVE。官方文档要求 handler 识别 remove event，并把这些 page 视为零页，而不是再从 snapshot file 读旧内容：docs/snapshotting/handling-page-faults-on-snapshot-resume.md。

    示例 on_demand_handler 里也体现了这个复杂性：它处理 Pagefault 和 Remove 两类事件；注释说明 remove 和 pagefault 可能跨 VMM thread/vCPU thread 乱序到达，生产级 handler 需要保证同一 range 的 remove 先于后续 pagefault 生效：src/firecracker/examples/uffd/on_demand_handler.rs。

    17.6 失败语义和能力边界

    UFFD restore 的边界非常明确：Firecracker 不负责读取 memfile、不负责 handler 进程生命周期，也不负责 handler 的故障恢复。

    场景 行为/边界
    handler 没有监听 UDS guest_memory_from_uffd 连接失败，snapshot load 失败
    handler 收到 fd 后崩溃 后续 page fault 可能让 Firecracker/vCPU 永久等待
    balloon remove event 未正确处理 可能把已经被 balloon 丢弃的页错误地从 snapshot file 恢复成旧内容
    hugepage guest memory restore 只能走 UFFD，mapping 中携带 page size
    UDS 握手之后 Firecracker 与 handler 不再有业务协议通信，只有 UFFD 事件流

    官方文档也明确指出：Firecracker 发送 payload 后不会再通过 UDS 与 handler 通信；handler 崩溃时 Firecracker 可能在 page fault 上一直等待，用户需要监控 handler 或回收 Firecracker 进程：docs/snapshotting/handling-page-faults-on-snapshot-resume.md。

    所以 UFFD 的价值不是“更完整的 snapshot”，而是把恢复时的内存填充策略外置。handler 可以按需加载、预取整段、首个 fault 后 fault-in 全内存、接入远程存储或自定义缓存；Firecracker 保持自己的 VMM 逻辑简单，只暴露必要的 fd 和 address mapping。

    18. interrupt state 深挖：aarch64 GIC vs x86 irqchip

    第 14 章已经说明：aarch64 是 GIC 平台，x86_64 是精简 PC 平台。这一章继续下钻 snapshot/restore 的中断控制器状态。核心差异是：aarch64 的中断控制器是 KVM device，需要按 GIC register group 逐项保存；x86_64 的 PIT/PIC/IOAPIC 是 KVM in-kernel irqchip/PIT 模型，Firecracker 直接保存 KVM 提供的 C struct。

    18.1 VM state 里的字段差异

    ARM64 的 VmState 只有三类：guest memory 描述、GicState、resource allocator：src/vmm/src/arch/aarch64/vm.rs。x86_64 的 VmState 则保存 guest memory、resource allocator、kvm_pit_state2、kvm_clock_data、PIC master/slave 和 IOAPIC：src/vmm/src/arch/x86_64/vm.rs。

    flowchart TB Snapshot[MicrovmState.vm_state] --> A[aarch64 VmState] Snapshot --> X[x86_64 VmState] A --> AMem[GuestMemoryState] A --> AGic[GicState] A --> ARes[ResourceAllocator] X --> XMem[GuestMemoryState] X --> XRes[ResourceAllocator] X --> XPit[kvm_pit_state2] X --> XClock[kvm_clock_data] X --> XPicM[kvm_irqchip PIC master] X --> XPicS[kvm_irqchip PIC slave] X --> XIoapic[kvm_irqchip IOAPIC]

    ARM64 save 时需要 vCPU 的 MPIDR 列表，因为 GIC 的 CPU interface/redistributor state 是按 vCPU identity 访问的。ArchVm::save_state(mpidrs) 调 get_irqchip().save_device(mpidrs)；restore 时也传入同一组 MPIDR：src/vmm/src/arch/aarch64/vm.rs。

    x86_64 save 不需要类似 MPIDR 参数。它在 VM fd 上调用 get_pit2()、get_clock()，再分别以 KVM_IRQCHIP_PIC_MASTER、KVM_IRQCHIP_PIC_SLAVE、KVM_IRQCHIP_IOAPIC 填充 kvm_irqchip：src/vmm/src/arch/x86_64/vm.rs。

    18.2 aarch64 GIC state 的三层结构

    GicState 的结构很清楚：

    字段 含义
    dist distributor registers，全局 SPI 相关状态
    gic_vcpu_states 每个 vCPU 的 redistributor/ICC 状态
    its_state GICv3 ITS 状态，只有 GICv3 存在

    这些字段定义在 src/vmm/src/arch/aarch64/gic/regs.rs。GicVcpuState 又分成 rdist 和 icc；GICv2 没有 redistributor，所以 rdist 为空，只有 CPU interface ICC 状态：src/vmm/src/arch/aarch64/gic/gicv2/regs/mod.rs。

    flowchart TB GicState --> Dist[dist: distributor] GicState --> PerVcpu[gic_vcpu_states] GicState --> ITS[its_state optional] PerVcpu --> GICv2[GICv2: ICC only, rdist empty] PerVcpu --> GICv3[GICv3: redistributor + ICC] ITS --> OnlyV3[GICv3 ITS only]

    GIC device 创建也体现了这个差异。create_gic(..., None) 会优先尝试 GICv3，失败后 fallback 到 GICv2：src/vmm/src/arch/aarch64/gic/mod.rs。这不是 snapshot fallback，而是启动时选择 host KVM 支持的 GIC 版本。

    18.3 GICv2：distributor + CPU interface

    GICv2 snapshot 保存两部分：

    1. distributor registers：GICD_CTLR、enable/disable、group、config、pending/active、priority、SGI pending 等。
    2. 每 vCPU CPU interface registers：GICC_CTLR、GICC_PMR、GICC_BPR、GICC_APBR、GICC_APR1..APR4。

    GICv2 distributor 列表明确只保存 R/W 且非 implementation-specific 的寄存器，并跳过 SGI/PPI 对应的 shared IRQ register 前 32 个 interrupt 位：src/vmm/src/arch/aarch64/gic/gicv2/regs/dist_regs.rs。CPU interface 注释也明确不保存 GICC_NSAPR，因为它只存在于带 security extensions 的实现上，盲目读取可能在某些系统崩溃：src/vmm/src/arch/aarch64/gic/gicv2/regs/icc_regs.rs。

    sequenceDiagram participant VM as aarch64 VmState save participant G as GICv2 DeviceFd participant D as DIST_REGS participant C as CPU_REGS per MPIDR VM->>G: save_device(mpidrs) G->>D: get_dist_regs loop each MPIDR G->>C: get_icc_regs(mpidr) end G-->>VM: GicState { dist, gic_vcpu_states, its_state=None }

    restore 顺序是先 distributor，再校验 MPIDR 数量和 saved vCPU 数量一致，最后按 MPIDR 写回 CPU interface registers：src/vmm/src/arch/aarch64/gic/gicv2/regs/mod.rs。

    18.4 GICv3：distributor + redistributor + system ICC + ITS

    GICv3 比 GICv2 多了两类状态：redistributor 和 ITS。

    GICv3 distributor 保存列表包含 GICD_STATUSR 和 GICD_IROUTER，并明确不保存 GICD_CPENDSGIR/SPENDSGIR，因为 affinity routing 默认启用时不用这些寄存器：src/vmm/src/arch/aarch64/gic/gicv3/regs/dist_regs.rs。

    redistributor 保存 PPI/SGI 相关寄存器：GICR_STATUSR、GICR_WAKER、GICR_PROPBASER、GICR_PENDBASER、GICR_CTLR，以及 SGI 的 group、enable、pending、active、priority、config 等：src/vmm/src/arch/aarch64/gic/gicv3/regs/redist_regs.rs。

    GICv3 ICC 不是 GICv2 那种 MMIO CPU interface，而是 system register 形式：ICC_SRE_EL1、ICC_CTLR_EL1、ICC_IGRPEN0/1_EL1、ICC_PMR_EL1、ICC_BPR0/1_EL1，以及按 priority bits 条件保存的 ICC_AP0R*/ICC_AP1R*：src/vmm/src/arch/aarch64/gic/gicv3/regs/icc_regs.rs。

    GICv3 save 顺序也更复杂：先 flush redistributor pending tables 到 guest RAM，再 flush ITS tables 到 guest memory，然后保存每个 vCPU 的 redistributor 和 ICC，最后保存 ITS registers：src/vmm/src/arch/aarch64/gic/gicv3/regs/mod.rs。

    sequenceDiagram participant VM as aarch64 VmState save participant G as GICv3 DeviceFd participant I as ITS DeviceFd participant R as per-vCPU redistributor participant C as per-vCPU ICC sysregs VM->>G: save_device(mpidrs) G->>G: save_pending_tables G->>I: its_save_tables G->>G: get_dist_regs loop each MPIDR G->>R: get_redist_regs(mpidr) G->>C: get_icc_regs(mpidr) end G->>I: ItsRegisterState::save G-->>VM: GicState { dist, rdist+icc, its_state }

    ITS restore 有严格顺序。源码注释说明必须先恢复 GITS_IIDR、GITS_CBASER、GITS_CREADR、GITS_CWRITER、GITS_BASER[]，再 restore ITS tables，最后写 GITS_CTLR：src/vmm/src/arch/aarch64/gic/gicv3/regs/its_regs.rs。

    18.5 x86_64：KVM in-kernel irqchip 的整体状态

    x86_64 的中断控制器模型更像“把 PC 兼容硬件状态整体问 KVM 要出来”。Firecracker 在 pre-vCPU 阶段先 create_irq_chip()，再 create_pit2(KVM_PIT_SPEAKER_DUMMY)，避免 speaker port 0x61 写入导致 userspace exit：src/vmm/src/arch/x86_64/vm.rs。

    save 时：

    字段 KVM 调用 说明
    pitstate get_pit2() PIT state，包括 dummy speaker 配置影响
    clock get_clock() KVM clock data
    pic_master get_irqchip(KVM_IRQCHIP_PIC_MASTER) master PIC
    pic_slave get_irqchip(KVM_IRQCHIP_PIC_SLAVE) slave PIC
    ioapic get_irqchip(KVM_IRQCHIP_IOAPIC) IOAPIC

    restore 时按 PIT、clock、PIC master、PIC slave、IOAPIC 的顺序写回 KVM：src/vmm/src/arch/x86_64/vm.rs。clock_realtime 是 x86_64 特有恢复选项；如果请求该选项但 snapshot 的 clock flags 没有 KVM_CLOCK_REALTIME，restore 会报错：src/vmm/src/arch/x86_64/vm.rs。

    sequenceDiagram participant VM as x86_64 VmState participant K as KVM VM fd VM->>K: get_pit2 VM->>K: get_clock VM->>K: get_irqchip(PIC_MASTER) VM->>K: get_irqchip(PIC_SLAVE) VM->>K: get_irqchip(IOAPIC) K-->>VM: VmState structs VM->>K: set_pit2 VM->>K: set_clock VM->>K: set_irqchip(PIC_MASTER) VM->>K: set_irqchip(PIC_SLAVE) VM->>K: set_irqchip(IOAPIC)

    注意 LAPIC 不在 x86_64 VmState 里，而在每个 vCPU state 中保存。第 14 章提到的 x86 vCPU state 包含 LAPIC、vcpu events、MSRs、XSAVE/TSC 等；也就是说 x86 的 interrupt state 被拆成 VM 级 PIC/IOAPIC/PIT/clock 和 vCPU 级 LAPIC。

    18.6 为什么两端保存方式不同

    维度 aarch64 x86_64
    中断模型 GICv2/GICv3 KVM device in-kernel irqchip + PIT + per-vCPU LAPIC
    创建时机 vCPU 创建后创建 GIC vCPU 创建前创建 irqchip/PIT
    保存 API KVM device attr group + register offsets get_pit2/get_clock/get_irqchip
    每 vCPU identity MPIDR 驱动 ICC/redistributor state LAPIC 在 vCPU state，VM state 不需要 APIC ID 列表
    GICv2/v3 分叉 v2: dist+ICC；v3: dist+rdist+ICC+ITS 无 GIC 版本分叉，但有 PC 兼容 legacy state
    restore 风险点 register list、MPIDR 数量、ITS restore 顺序 clock flags、PIT/PIC/IOAPIC 写回顺序、kernel state ABI

    这就是 Firecracker 架构差异的底层实质：共享的 snapshot 框架只是序列化容器；真正的中断状态语义由 KVM 暴露的目标架构模型决定。ARM64 更像保存一个 memory-mapped/system-register interrupt controller；x86_64 更像保存一组 KVM 内核维护的 PC irqchip 结构体。

    19.2 控制面与进程模型

    flowchart TB FCAPI["Firecracker HTTP over UDS API"] --> FCVMM["VMM EventManager"] FCVMM --> FCVCPU["vCPU threads"] FCVMM --> FCDEV["in-process virtio devices"] CHCLI["cloud-hypervisor CLI / API socket / DBus"] --> CHAPI["API thread"] CHAPI --> CHVMM["VMM thread"] CHVMM --> CHDM["DeviceManager"] CHDM --> CHDEV["virtio-pci / vhost-user / VFIO / vDPA"] CVMCLI["crosvm CLI / control socket"] --> CVMMAIN["main process control loop"] CVMMAIN --> CVMDEV["forked sandboxed device processes"] CVMDEV --> CVMJAIL["Minijail + seccomp + namespaces"] CTRD["containerd"] --> KSHIM["Kata/Cube shim v2"] KSHIM --> HV["selected VMM"] KSHIM --> AGENT["guest agent over vsock/ttrpc"]

    Firecracker 的控制面最窄：API server 接收 UDS HTTP 请求，转换成 VMM action，VMM 和设备逻辑在同一 microVM 进程内运转，vCPU 独立线程进入 KVM_RUN。它的优势是路径短、状态少、审计面小；代价是它不会变成“通用虚拟机管理器”。

    Cloud Hypervisor 在启动时创建 hypervisor backend，然后启动 VMM thread 和 API thread；如果命令行给了 kernel/firmware 会发送 VmCreate 和 VmBoot，如果给了 restore 参数则发送 VmRestore：../../cloud-hypervisor/cloud-hypervisor/src/main.rs。这说明它的控制面比 Firecracker 更接近“长期可管理 VM”：API 层面包含 create/boot/restore/hotplug/snapshot 等动作。

    crosvm 的架构文档把主路径写得很清楚：main.rs 解析命令行构造 Config，然后进入平台 run_config，加载 kernel，创建控制 socket，调用架构相关 Arch::build_vm，再 create_devices 并为设备准备 Minijail 配置，最后运行 RunnableLinuxVm：../../crosvm/ARCHITECTURE.md。它还有内部 VM control socket；外部 --socket 只应通过 crosvm stop 或 crosvm_control 使用，因为协议内部且不稳定：../../crosvm/ARCHITECTURE.md。

    Kata/CubeSandbox 是更高一层。Kata 的 Go shim 在 create 路径中调用 katautils.CreateSandbox()，再取得 hypervisor pid：../../kata-containers/src/runtime/pkg/containerd-shim-v2/create.go。runtime-rs 里 SandboxRequest::CreateSandbox 会初始化 runtime instance，StartSandbox 调用 sandbox.start()：../../kata-containers/src/runtime-rs/crates/runtimes/src/manager.rs。CubeShim 则声明自己是 containerd shim 组件，向下请求 Cubelet/Cube runtime 创建 KVM MicroVM，并通过 ttrpc/vsock 转发容器生命周期到 in-VM cube-agent：../../CubeSandbox/CubeShim/README.md。

    19.3 设备模型：Firecracker 的“小”与其他项目的“大”

    维度 Firecracker Cloud Hypervisor crosvm Kata Containers CubeSandbox
    virtio 目标 少量 serverless/container 必需设备 cloud workload 设备集合 ChromeOS/Android/client 设备集合 依赖所选 hypervisor 依赖 CubeHypervisor + guest agent
    transport MMIO 为核心，也支持部分 PCI 路径 virtio-pci 是主路径，热插拔更完整 PCI/MMIO/平台相关，设备可 fork 成独立进程 QEMU/CH/FC/Dragonball 各自不同 Cloud Hypervisor 风格 virtio-pci + 平台封装
    典型设备 block、net、vsock、balloon、rng、pmem、virtio-mem、MMDS block、net、pmem、fs、vsock、memory、VFIO、vDPA、vhost-user net、block、gpu、snd、fs、9p、TPM、pmem、video、balloon、vsock 等 关注 rootfs、share-fs、vsock、hotplug，但实现委托 VMM 关注 sandbox rootfs、snapshot、network isolation、agent 通道
    隔离重点 jailer/seccomp/cgroup/namespace + 小代码面 seccomp + Landlock + Rust VMM 模块化 process-per-device + Minijail/seccomp/namespaces shim/agent/VMM 分层隔离 平台级 API/调度/网络/eBPF + VM 隔离

    Cloud Hypervisor 的 DeviceManager 明确支持在线添加 disk、fs、pmem、net、vdpa、vsock，并通过 hotplug_virtio_pci_device() 把 virtio device 加到 PCI 设备树：../../cloud-hypervisor/vmm/src/device_manager.rs。CubeSandbox 的 hypervisor/vmm/src/device_manager.rs 保留了相同风格的热插拔函数，并增加/改造 snapshot 聚合实现：../../CubeSandbox/hypervisor/vmm/src/device_manager.rs。

    crosvm 的设备面明显更大。README 列出 virtio-net、virtio-block、virtio-gpu、virtio-snd、virtio-fs、virtio-9p、console、rng、balloon、vsock、TPM、pmem、video decoder/encoder 等：../../crosvm/README.md。架构文档说明 virtio 设备实现 VirtioDevice trait，activate 后启动 worker thread 处理 virtio queues，而复杂设备可通过 ProxyDevice fork 到 sandboxed process：../../crosvm/ARCHITECTURE.md。

    Firecracker 的设计重点正相反：它把设备数量压到 workload 需要的最小集合。这样 block/net/vsock/balloon/rng/pmem/virtio-mem 都可以在一个较小 VMM 状态空间里被 snapshot、restore、seccomp 和 jailer 管住。对用户来说，这就是 Firecracker 的能力边界：它是安全可复制的 microVM building block，不是桌面/移动/通用设备虚拟化平台。

    19.4 Snapshot/restore：同名能力，语义不同

    Firecracker 的 snapshot 是 microVM 状态序列化：VM/vCPU/设备状态 + guest memory file，可选 diff snapshot；UFFD restore 把缺页填充交给外部 handler。第 12、17、18 章已经展开它的主路径和中断状态细节。

    Cloud Hypervisor 使用 vm_migration::Snapshot 聚合可迁移组件状态。DeviceManager 的 snapshot() 会先保存自身 state，然后遍历 device tree，把每个 migratable device 的 snapshot 加进去：../../cloud-hypervisor/vmm/src/device_manager.rs。MemoryManager 的 snapshot 会构造 memory range table，记录哪些 region 需要复制，供后续 transport/send 阶段使用：../../cloud-hypervisor/vmm/src/memory_manager.rs。README 也明确 snapshot/restore 和 live migration 不保证跨版本兼容：../../cloud-hypervisor/README.md。

    crosvm 的 snapshot 更贴近“多进程设备 + VM 控制循环”的系统状态保存。snapshot crate 提供 SnapshotWriter 和 SnapshotReader，以 fragment/namespace 的方式写入快照片段：../../crosvm/snapshot/src/lib.rs。vm_control 中 vCPU 有 Snapshot/Restore 控制消息，设备控制线程也有 SnapshotDevices/RestoreDevices：../../crosvm/vm_control/src/lib.rs。这与 Firecracker 的单进程状态模型不同：crosvm 必须协调 vCPU、设备进程、IRQ handler、控制 socket。

    CubeSandbox 把 snapshot 放在产品能力中心：模板生命周期先构建 rootfs，再 cold boot MicroVM，等待语言环境就绪后保存 memory/state snapshot，最后用模板实现数十毫秒级 hot start：../../CubeSandbox/docs/guide/templates.md。其 DeviceManager::snapshot() 还会并发聚合 migratable device snapshots：../../CubeSandbox/hypervisor/vmm/src/device_manager.rs。这和 Firecracker 的机制相关，但目标更偏“批量创建 sandbox 实例”。

    Kata 的 save/restore 是 runtime 能力，不是单一 VMM 内核能力。runtime-rs 的 Hypervisor trait 抽象出 pause_vm/save_vm/resume_vm 等方法：../../kata-containers/src/runtime-rs/crates/hypervisor/src/lib.rs。具体效果取决于下层 hypervisor：Firecracker、Cloud Hypervisor、QEMU、Dragonball 的状态边界并不相同。

    19.5 ARM64 与 x86_64：源码支持和产品支持不是一回事

    项目 x86_64 arm64/aarch64 关键差异
    Firecracker 一等支持 一等支持 x86 走 irqchip/PIT/CPUID/MSR/APIC；ARM64 走 FDT/MPIDR/GICv2/v3/ITS
    Cloud Hypervisor 一等支持 一等支持 arch crate 同时暴露 x86_64/aarch64/riscv64；README 的 cloud image 也列出 amd64/arm64
    crosvm 一等支持 一等支持 README 列出 x86_64/aarch64/riscv64；seccomp policy 和部分设备按架构分裂
    Kata Containers 支持 支持 README 列出 x86_64/amd64 VT-x/SVM 与 aarch64 ARM Hyp；但 hypervisor 插件和配置在各架构上能力不同
    CubeSandbox 当前用户文档要求 x86_64 Linux/KVM 未作为当前部署目标 hypervisor 代码中有 aarch64 条件路径，但产品文档和部署文档聚焦 x86_64/PVM

    Cloud Hypervisor 的 arch/src/lib.rs 明确写着 supported platforms 是 x86_64、aarch64、riscv64，并按 target_arch 导出对应模块：../../cloud-hypervisor/arch/src/lib.rs。crosvm README 也列出 x86_64、aarch64、riscv64：../../crosvm/README.md，并在架构文档中说明 seccomp policy 按架构拆分，部分设备如 ARM 的 Pl030 和 x86_64 的 I8042 是架构特定设备：../../crosvm/ARCHITECTURE.md。

    Kata README 的硬件表说明 x86_64/amd64 使用 Intel VT-x/AMD SVM，aarch64 使用 ARM Hyp：../../kata-containers/README.md。runtime-rs 中 Cloud Hypervisor 模块还用 #[cfg(all(feature = "cloud-hypervisor", any(target_arch = "x86_64", target_arch = "aarch64")))] 限定 x86_64/aarch64：../../kata-containers/src/runtime-rs/crates/hypervisor/src/lib.rs。

    CubeSandbox 这里要特别小心：不能因为它的 hypervisor 目录里存在 aarch64 条件编译代码，就认定产品支持 ARM64。README 和部署文档反复要求 x86_64 Linux + KVM：../../CubeSandbox/README.md，开发环境也要求 Linux x86_64 with KVM：../../CubeSandbox/docs/guide/dev-environment.md。所以当前比较中，CubeSandbox 应按 x86_64 优先平台理解。

    19.6 最关键的差异判断

    1. 如果要理解“最小 microVM VMM 如何实现”，Firecracker 是最好的入口。它把 API、KVM、vCPU、virtio、snapshot、jailer/seccomp 都压缩在最小闭环里。
    2. 如果要理解“现代 cloud VMM 如何支持热插拔、迁移、VFIO/vDPA/vhost-user、更多资源管理”，Cloud Hypervisor 更合适。
    3. 如果要理解“强隔离、多设备、客户端/Android/ChromeOS 场景”，crosvm 更合适，因为它的 process-per-device、Minijail 和复杂 virtio 设备面是主线设计。
    4. 如果要理解“VM 如何被接进容器生态”，Kata Containers 是关键对象；它的问题不是 KVM_RUN 如何实现，而是 shim、agent、hypervisor plugin、rootfs/share-fs/network 如何协作。
    5. 如果要理解“如何把 MicroVM 做成高并发 sandbox 服务”，CubeSandbox 是平台层样本；它把模板、快照克隆、调度、API、网络隔离和 containerd shim 打包成产品闭环。

    这也解释了 Firecracker 的能力边界：很多看似“缺失”的能力不是技术上不能做，而是与它的安全、冷启动、可审计、低开销目标冲突。Firecracker 把 VMM 做小；Kata 和 CubeSandbox 把小 VMM 纳入更大的 runtime/platform；Cloud Hypervisor 和 crosvm 则把 VMM 本身做得更通用或更宽。
