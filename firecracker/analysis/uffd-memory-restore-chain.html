    Firecracker UFFD / Memory Restore 边界链路

    本文展开 snapshot restore 时 guest memory 如何恢复，MemBackendType::File vs MemBackendType::Uffd 的边界，以及 UFFD restore 下设备 queue 如何依赖 guest memory。

    源码基线：当前仓库工作树。

    相关：snapshot/restore、memory device snapshot、横向 性能设计依据 §7。

    0. 术语与背景

    两种 memory restore backend

    backend 行为 适用
    File 直接 mmap memory 文件成 guest memory 普通 restore（hugetlbfs 拒绝，提示用 UFFD）
    UFFD 创建匿名 guest memory + 注册 userfaultfd，把 mapping+UFFD fd 发外部 handler 降低 restore 初始时延（按需填页）

    UFFD 的本质

    UFFD restore 延迟填充 guest RAM 内容，不延迟恢复 VMM/设备状态。Firecracker 负责建好 guest memory 虚拟地址范围 + 注册 UFFD + 把 fd/mapping 交出去 + 在 Vmm 中持 UFFD fd；真正按需填页由外部 handler 完成。

    关键边界

    • Firecracker 保留 UFFD fd——注释说明外部 handler 崩溃 guest 可能冻结，Firecracker 需持 fd 维持语义。
    • 设备 queue restore 依赖 guest memory region 已存在——UFFD 模式下 ring 地址/index 先恢复，访问未填充页时 handler 服务 page fault。
    • build_microvm_from_snapshot() 把 guest memory regions 注册到 KVM 后才恢复 vCPU/VM arch/DeviceManager。

    1. 核心结论

    restore 先读 snapshot state → 按 mem backend 创建 guest memory → build_microvm_from_snapshot。File = mmap 文件；UFFD = 匿名内存 + userfaultfd + fd 交外部 handler。UFFD 边界是"延迟填充 RAM 内容"，不是"延迟恢复 VMM/设备状态"。

    2. backend 选择

    // src/vmm/src/persist.rs:439
let (guest_memory, uffd) = match params.mem_backend.backend_type {
    MemBackendType::File => {
        if vm_resources.machine_config.huge_pages.is_hugetlbfs() {
            return Err(GuestMemoryFromFileError::HugetlbfsSnapshot.into());   // hugetlbfs 拒绝 file backend
        }
        (guest_memory_from_file(mem_backend_path, mem_state, track_dirty_pages)?, None)
    }
    MemBackendType::Uffd => guest_memory_from_uffd(mem_backend_path, mem_state, track_dirty_pages, huge_pages)?,
};

    3. UFFD backend（guest_memory_from_uffd + handshake）

    // src/vmm/src/persist.rs:532
fn guest_memory_from_uffd(mem_uds_path, mem_state, track_dirty_pages, huge_pages) -> Result<(Vec<GuestRegionMmap>, Option<Uffd>), _> {
    let (guest_memory, backend_mappings) = create_guest_memory(mem_state, track_dirty_pages, huge_pages)?;  // 匿名 guest memory
    let uffd = UffdBuilder::new().require_features(FeatureFlags::EVENT_REMOVE)   // balloon 场景需 EVENT_REMOVE
        .close_on_exec(true).non_blocking(true).create()?;
    for mem_region in guest_memory.iter() {
        uffd.register(mem_region.as_ptr().cast(), mem_region.size())?;          // 每 region 注册 userfaultfd
    }
    send_uffd_handshake(mem_uds_path, &backend_mappings, &uffd)?;
    Ok((guest_memory, Some(uffd)))   // Firecracker 保留 UFFD fd
}
// :589  send_uffd_handshake
fn send_uffd_handshake(mem_uds_path, backend_mappings, uffd) -> Result<(), _> {
    let socket = UnixStream::connect(mem_uds_path)?;
    socket.send_with_fd(backend_mappings_json, uffd.as_raw_fd())?;   // mapping 信息 + UFFD fd 发外部 handler
    forget(socket);   // 防 fd 关闭 race
}

    UFFD handler 在 Firecracker 之外——Firecracker 只把 guest memory faults 的处理能力交给外部进程，自己保留 fd。

    4. restore 后续：build_microvm_from_snapshot + 设备 queue 依赖

    build_microvm_from_snapshot() 把 guest memory regions 注册到 KVM → 恢复 vCPU KVM state → VM arch state → DeviceManager（builder.rs:439）。设备 queue restore 依赖 guest memory region 已存在：balloon/virtio-mem 的 queue state 先恢复 ring 地址/index，若访问未填充 page 由 UFFD handler 服务 page fault。

    resume_vm 只影响 restore 成功后是否立即 resume_vm()——不论是否 resume，restore_from_snapshot 都构建完整 VMM + 恢复设备状态。运行后首次访问未填充页才需外部 handler 响应。

    5. 能力边界 / 与 Cloud Hypervisor UFFD 差异

    维度 Firecracker Cloud Hypervisor
    UFFD handler 外部进程（Firecracker 保留 fd） VMM 内 uffd-handler 线程
    故障边界 外部 handler 崩溃 → guest 冻结 handler panic → exit event + result channel
    hugetlbfs file backend 拒绝，需 UFFD —

    两者优化目标相同：降低 restore 初始时延，把 guest RAM 内容填充延迟到首次访问。Firecracker 把 fd 交外部，CH 在 VMM 内起 handler 线程——这是两者 UFFD 的关键边界差异（见 CH migration memory transport §0/§9）。
