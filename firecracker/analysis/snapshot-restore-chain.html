Firecracker Snapshot / Restore 链路

本文展开 snapshot 保存了哪些状态，restore 如何重建 KVM VM、guest memory、vCPU、设备和架构状态。

源码基线：当前仓库工作树。

相关：API Event Loop 与线程协作、VmResources 配置边界、横向 Snapshot/Restore/Clone。

0. 术语与背景

Firecracker snapshot 是 VMM 级状态

不是 runtime 或平台级状态。state 文件 + memory 文件分离：

文件 内容
state 文件 MicrovmState（VmInfo/KVM cap/VM arch state/vCPU states/device states）
memory 文件 guest memory 内容（full dump 全量；diff 合并脏页）

state 与 memory 分离是核心：state 描述 VM 形态 + 设备/CPU 状态，memory backend 承载 guest RAM 字节。

create 是 runtime action，load 是 pre-boot action

  • CreateSnapshot 只在 runtime controller 支持（运行中 VM 才能快照）。
  • LoadSnapshot 只在 pre-boot controller 支持——restore 是启动前构建路径，不支持运行中 VM 被另一 snapshot 覆盖。

两种 memory restore backend

  • File：直接 mmap memory 文件（hugetlbfs 拒绝，提示用 UFFD）。
  • UFFD：建匿名 guest memory + userfaultfd，把 UFFD fd + mapping 经 Unix socket 发给外部 page fault handler（Firecracker 自己保留 fd 维持生命周期）。

UFFD 的本质：降低 restore 初始时延——guest RAM 内容填充延迟到首次访问（按需填页）。

1. 核心结论

  • snapshot 是 VMM 级状态：state 文件保存 MicrovmState，memory 文件单独保存 guest RAM（full dump / diff 合并脏页）。
  • create 是 runtime action，load 是 pre-boot action（load 成功后替代 boot path，VM 默认 paused，可选 resume_vm）。
  • restore 顺序：读 state → net/vsock override → 重建 guest memory → KVM VM → vCPU → VM arch state → DeviceManager（设备恢复必须在 VM arch state 之后）。
  • ARM64/x86_64 共用顶层流程，VM/vCPU arch state 差异明显。

2. 总体流程图

3. API 层分界

PUT /snapshot/create → VmmAction::CreateSnapshot；PUT /snapshot/load → VmmAction::LoadSnapshot（request/snapshot.rs:55/62）。CreateSnapshot 只 runtime controller 支持（rpc_interface.rs:680）；LoadSnapshot 只 pre-boot 支持，runtime 拒绝（:803）。

Firecracker 不支持"运行中 VM 被另一 snapshot 直接覆盖"——restore 是启动前构建路径。

4. MicrovmState 结构

// src/vmm/src/persist.rs:86
pub struct MicrovmState {
    pub vm_info: VmInfo,           // memory size/SMT/CPU template/boot source/huge page
    pub kvm_state: KvmState,       // KVM capability modifiers
    pub vm_state: VmState,         // VM 级架构状态 + memory layout
    pub vcpu_states: Vec<VcpuState>,  // 每 vCPU 的 KVM state
    pub device_states: DevicesState,  // MMIO/PCI/ACPI/serial/virtio 设备状态
}

KvmState 保存 capability modifiers，用于恢复时创建一致的 Kvm 对象（vstate/kvm.rs:75）。

5. CreateSnapshot 主路径

// src/vmm/src/persist.rs:165
pub fn create_snapshot(vmm: &mut Vmm, vm_info: &VmInfo, params: &CreateSnapshotParams) -> Result<(), CreateSnapshotError> {
    let microvm_state = vmm.save_state(vm_info)?;                       // (1) 存状态
    snapshot_state_to_file(&microvm_state, &params.snapshot_path)?;
    vmm.vm.snapshot_memory_to_file(&params.mem_file_path, params.snapshot_type)?;  // (2) 存 memory
    // (3) 运行期 queue 对象没持续标脏，这里补偿
    vmm.device_manager.mark_virtio_queue_memory_dirty(vmm.vm.guest_memory());
    Ok(())
}

mark_virtio_queue_memory_dirty 的必要性：运行期 virtio queue 对象没有持续标脏，snapshot 前需补偿标记，否则 diff snapshot 会漏掉 queue memory。

6. Vmm::save_state 顺序 + vhost-user-block 限制

save_state() 先 check_unsnapshottable_devices()——vhost-user-block 不支持 snapshot：

// src/vmm/src/lib.rs:452
pub fn check_unsnapshottable_devices(&self) -> Result<(), MicrovmStateError> {
    let mut tuples = Vec::new();
    self.device_manager.for_each_virtio_device(|device_type, device| {
        if let VirtioDeviceType::Block = device_type
            && let Some(b) = device.as_any().downcast_ref::<Block>()
            && b.is_vhost_user() {
            tuples.push(("vhost-user-block", b.id().to_owned()));   // 发现 vhost-user block → 拒绝
        }
    });
    if tuples.is_empty() { Ok(()) } else { Err(MicrovmStateError::NotAllowed(/*...*/)) }
}

保存顺序：device state → vCPU state → KVM state → VM state。注释解释 device state 先于 KVM state：某些设备 prepare save 时可能改 virtio transport 并向 guest 发中断，必须让这些变化被后续 KVM state 捕获（lib.rs:582）。vCPU state 经 VcpuEvent::SaveState 获取（:620）。

7. Memory Snapshot（full/diff）

// src/vmm/src/vstate/vm.rs:327
pub(crate) fn snapshot_memory_to_file(&self, mem_file_path: &Path, snapshot_type: SnapshotType) -> Result<(), CreateSnapshotError> {
    let mut file = OpenOptions::new().write(true).create(true).truncate(false).open(mem_file_path)?;  // truncate=false！
    file.set_len(expected_size)?;                       // 设为 guest memory 总大小
    match snapshot_type {
        SnapshotType::Diff => {
            let dirty_bitmap = self.get_dirty_bitmap()?;
            self.guest_memory().dump_dirty(&mut file, &dirty_bitmap)?;  // 只写脏页，合并进文件
        }
        SnapshotType::Full => {
            self.guest_memory().dump(&mut file)?;        // 写全量
            self.reset_dirty_bitmap(); self.guest_memory().reset_dirty();
        }
    };
}

truncate(false) 的原因：避免 snapshot 文件正是当前 VM mmap 来源时把运行中 guest memory 清零。diff snapshot 不是单独差异文件——目标文件大小匹配时把脏页直接合并进该 memory 文件。

8. LoadSnapshot 主路径

pre-boot load_snapshot() 先检查 boot_path——此前执行过 boot/drive/net 配置则返回 LoadSnapshotNotAllowed（避免普通 boot 配置与 snapshot restore 混用，rpc_interface.rs:627）。load_params.resume_vm 为 true 则恢复后立即 resume_vm()。成功后 built_vmm 设为 restored VMM，pre-boot loop 结束。

9. restore_from_snapshot 细节

// src/vmm/src/persist.rs:357
pub fn restore_from_snapshot(/*...*/) -> Result<Arc<Mutex<Vmm>>, RestoreFromSnapshotError> {
    let mut microvm_state = snapshot_state_from_file(&params.snapshot_path)?;
    // (1) net override：按 iface id 在 MMIO/PCI net state 查找并替换 tap_if_name
    for entry in &params.network_overrides {
        microvm_state.device_states.mmio_state.net_devices.iter_mut()
            .chain(microvm_state.device_states.pci_state.net_devices.iter_mut())
            .find(|x| x.device_state.id == entry.iface_id)
            .map(|d| d.device_state.tap_if_name.clone_from(&entry.host_dev_name))?;
    }
    // (2) vsock override：替换 backend UDS path
    // (3) 回填 machine config（vCPU count from vcpu_states.len() / memory size / SMT / CPU template / huge pages）
    // (4) snapshot_state_sanity_check（至少一个内存 region、至少有 DRAM、DRAM 只一个 plugged slot、架构校验 CPU vendor）
    // (5) 按 mem_backend 创建 guest memory → build_microvm_from_snapshot
}

10. File 与 UFFD Memory Backend

// src/vmm/src/persist.rs:507  (file backend)
fn guest_memory_from_file(mem_file_path, mem_state, track_dirty_pages) -> Result<Vec<GuestRegionMmap>, _> {
    let mem_file = File::open(mem_file_path)?;
    let guest_mem = memory::snapshot_file(mem_file, mem_state.regions(), track_dirty_pages)?;  // 映射
    Ok(guest_mem)   // hugetlbfs 在上层被拒绝，提示用 UFFD
}
// :532  (UFFD backend)
fn guest_memory_from_uffd(mem_uds_path, mem_state, track_dirty_pages, huge_pages) -> Result<(Vec<GuestRegionMmap>, Option<Uffd>), _> {
    let (guest_memory, backend_mappings) = create_guest_memory(mem_state, track_dirty_pages, huge_pages)?;
    let uffd = UffdBuilder::new().require_features(FeatureFlags::EVENT_REMOVE).close_on_exec(true).create()?;
    for mem_region in guest_memory.iter() {
        uffd.register(mem_region.as_ptr().cast(), mem_region.size())?;   // 每 region 注册 userfaultfd
    }
    send_uffd_handshake(mem_uds_path, &backend_mappings, &uffd)?;        // 经 Unix socket 发 mapping+UFFD fd 给外部 handler
    Ok((guest_memory, Some(uffd)))   // Firecracker 保留 fd
}

Firecracker 把 UFFD fd + mapping 发给外部 handler，自己保留 fd——注释说明外部 handler 崩溃会导致 guest 冻结，所以 Firecracker 需持 fd 维持生命周期（这与 CH 在 VMM 进程内起 handler 线程不同，见 CH migration 文档）。

11. build_microvm_from_snapshot 顺序

// src/vmm/src/builder.rs:439
pub fn build_microvm_from_snapshot(/*...*/, microvm_state, guest_memory, uffd, /*...*/) -> Result<Arc<Mutex<Vmm>>, _> {
    let kvm = Kvm::new(microvm_state.kvm_state.kvm_cap_modifiers.clone())?;   // 用 snapshot KVM cap 建 Kvm
    let mut vm = Vm::new(&kvm)?;
    let (mut vcpus, vcpus_exit_evt) = vm.create_vcpus(vcpu_count)?;
    vm.restore_memory_regions(guest_memory, &microvm_state.vm_state.memory)?;
    #[cfg(target_arch = "x86_64")] { /* TSC scaling 判断 */ }
    for (vcpu, state) in vcpus.iter_mut().zip(microvm_state.vcpu_states.iter()) { vcpu.kvm_vcpu.restore_state(state)?; }  // 恢复 vCPU
    #[cfg(target_arch = "aarch64")] { /* clock_realtime 拒绝 + 用 MPIDR 恢复 GIC */ }
    #[cfg(target_arch = "x86_64")] { vm.restore_state(&microvm_state.vm_state, clock_realtime)?; }  // 恢复 VM arch state
    // 设备恢复必须在 VM arch state 之后：VMGenID restore 会注入中断，先恢复设备会被后续 KVM state 覆盖
    let device_manager = DeviceManager::restore(device_ctor_args, &microvm_state.device_states)?;
    let mut vmm = Vmm { /* kvm, vm, uffd, device_manager, ... */ };
    vmm.start_vcpus(vcpus, /* vcpu seccomp */)?;                              // vCPU 线程 Paused 状态
    event_manager.add_subscriber(vmm.clone());
    crate::seccomp::apply_filter(/* vmm seccomp */)?;                          // 最后加载 seccomp
    Ok(vmm)
}

设备恢复必须在 VM arch state 之后：VMGenID restore 会注入中断通知 guest 新 generation ID，若先恢复设备，注入的中断会被后续 KVM state 覆盖。

12. Virtio Queue / Transport State

// src/vmm/src/devices/virtio/persist.rs:116
pub struct VirtioDeviceState {
    pub device_type: VirtioDeviceType,
    pub avail_features: u64, pub acked_features: u64,   // 协商的 features
    pub queues: Vec<QueueState>,                         // queue state
    pub activated: bool,
}
impl VirtioDeviceState {
    pub fn build_queues_checked(&self, mem, expected_device_type, expected_num_queues, expected_queue_max_size) -> Result<Vec<Queue>, PersistError> {
        if self.device_type != expected_device_type
            || (self.acked_features & !self.avail_features) != 0   // acked ⊆ avail
            || self.queues.len() != expected_num_queues { return Err(PersistError::InvalidInput); }
        // ...
    }
}

Firecracker 恢复的不只是设备配置，还包括 guest driver 已协商的 virtio 状态 + queue 游标。restore 校验 device type + acked⊆avail + queue 数量/max size。

13. 架构状态差异

层 x86_64 aarch64
VM state PIT/KVM clock/PIC master+slave/IOAPIC/memory/resource allocator memory/GIC/resource allocator
vCPU state regs/sregs/xsave/xcrs/debug regs/LAPIC/MP state/CPUID/MSRs/events/TSC MP state/all registers/MPIDR/KVI/PVTime IPA
restore 特殊 TSC frequency scaling/clock_realtime clock_realtime unsupported/GIC restore uses MPIDR

x86_64 vCPU state 保存顺序注释说明 KVM_GET_MP_STATE/KVM_GET_VCPU_EVENTS/LAPIC 等 ioctl 顺序影响可恢复性（arch/x86_64/vcpu.rs:555）；aarch64 保存 all registers/MPIDR/KVI 并清掉 KVM_ARM_VCPU_POWER_OFF（恢复时 guest kernel 已越过 boot，arch/aarch64/vcpu.rs:232）。

14. 能力边界

能力 Firecracker 表现
运行中 load snapshot 不支持，load 只能 pre-boot
snapshot 后自动恢复运行 load 可用 resume_vm
vhost-user-block snapshot 不支持（check_unsnapshottable_devices 阻止）
full memory snapshot 支持，写全量 memory file
diff memory snapshot 支持，目标文件语义是合并脏页
hugetlbfs file restore 不支持，需 UFFD
network/vsock backend override 支持替换 tap if name / UDS path
runtime/platform metadata 不保存

这与 CubeSandbox 很不同：Firecracker 只保存 microVM 可恢复运行的 VMM 状态；CubeSandbox 还要保存 rootfs lineage、catalog、network-agent、Master/Cubelet metadata、产品级 rollback binding。
