Firecracker 可观测性与诊断链路

本文回答：当 Firecracker 出故障时，证据从哪里来，能证明到哪一层。

源码基线：当前仓库工作树。

相关：API Event Loop、vCPU/KVM_RUN、snapshot/restore。

0. 术语与背景

三类可观测输出

输出 来源 内容
日志（log） LOGGER.init()（main.rs:123） API/VMM/vCPU 生命周期事件、错误
指标（metrics） METRICS 全局静态（metrics.rs:85） vCPU exit count、API latency、rate limiter throttle、block/net I/O 统计、interrupt triggers
串口（serial） setup_serial_device（mod.rs:134） guest 串口输出（文件或 stdout）

关键边界

  • 日志/指标是 host 侧 VMM 进程的输出——不依赖 guest agent（Firecracker 无固定 guest agent）。
  • metrics 文件 由 PUT /machine-config（或 config JSON）的 metrics-path 指定；FlushMetrics action 或 VM 退出时 flush。
  • vCPU exit 计数（MMIO read/write、IoIn/IoOut、failures）能证明设备模拟活动量，但不直接证明 guest 内业务状态。
  • snapshot 保存 metrics 状态（rate limiter token、balloon stats）——restore 后继续累计。

1. metrics 系统

// src/vmm/src/logger/metrics.rs:85
pub static METRICS: Metrics<FirecrackerMetrics, FcLineWriter> = Metrics::<FirecrackerFirecrackerMetrics, FcLineWriter>::new(FirecrackerMetrics::new());
// Metrics<T, M> 持 app_metrics: T（FirecrackerMetrics）+ metrics_buf: OnceLock<Mutex<M>>
// 全局静态，内部可变性（所有字段 Sync），不需 mut 即可写

FirecrackerMetrics 包含 vCPU/API/block/net/balloon/virtio-mem/seccomp/interrupt/rate_limiter 等各子系统的计数器/直方图。FlushMetrics action（或 VM 退出时）把 metrics 序列化写入 metrics-path 指定的文件。

2. serial 输出

// src/vmm/src/device_manager/mod.rs:134
fn setup_serial_device(event_manager, output: Option<&PathBuf>, state, rate_limiter) -> Result<Arc<Mutex<SerialDevice>>, std::io::Error> {
    let (serial_in, serial_out) = match output {
        Some(path) => (None, SerialOut::new(SerialOutInner::File(open_file_nonblock(path)?), rate_limiter)),  // 输出到文件
        None => { Self::set_stdout_nonblocking(); (Some(stdin()), SerialOut::new(Stdout(stdout()), rate_limiter)) }  // 输出到 stdout
    };
    let serial = Arc::new(Mutex::new(SerialDevice::new(serial_in, serial_out, state)?));
    event_manager.add_subscriber(serial.clone());   // EventManager 驱动
}

serial 输出可配置到文件（serial-out-path）或 stdout；有 rate limiter。snapshot 保存 serial state（rate limiter + 输出方式）。

3. 诊断证据分层

故障层 可观测证据 来源
API 请求失败 API error response + 日志 API thread 日志
VM 构建/启动失败 StartMicrovm error + 日志 builder 日志 + metrics
vCPU KVM exit 异常 FailEntry/InternalError + metrics vcpu.failures vCPU 线程 + METRICS
设备 I/O 异常 block/net metrics（execute_fails/event_fails/tap_read_fails） 设备 metrics
中断异常 metrics interrupts.triggers IrqTrigger/MSI-X metrics
rate limiter metrics rate_limiter_throttled RateLimiter metrics
guest panic serial 输出 + SYS_PANIC（jailer ARM64） serial + SysCtrl

Firecracker 可观测全部在 host VMM 进程——日志/指标/串口//actions（FlushMetrics）。无 guest agent、无内置 tracing/span（不同于 Kata 的 OpenTelemetry katatrace）。

4. 能力边界

问题 Firecracker 表现
日志 有（LOGGER，Unix socket API 配置 level/path）
指标 有（METRICS 全局静态，FlushMetrics 或退出时写文件）
串口 有（文件或 stdout，有 rate limiter）
tracing/span 无内置（不同于 Kata katatrace）
guest agent 无固定 agent（与 Kata/CubeSandbox 不同）
guest 内诊断 靠 serial 输出 + guest 自身工具（Firecracker 不提供）
snapshot 保存 metrics 保存设备相关 metrics state（rate limiter/balloon stats），不保存全局 METRICS
