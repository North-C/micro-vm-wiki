    Firecracker API Event Loop 与线程协作链路

    本文解释 API thread、VMM thread、EventManager、device subscriber 和 vCPU thread 如何协作（不是再次讲 microVM 如何启动）。

    源码基线：当前仓库工作树。

    相关：API 到 MicroVM 启动链路、VmResources 配置边界、vCPU KVM_RUN 链路。

    0. 术语与背景

    API 同步 ≠ 单线程执行

    Firecracker 的 API 是同步 HTTP，但 API thread 不直接修改 VMM。实际状态修改发生在 VMM thread 或 vCPU thread。API thread 只负责：解析 HTTP → 发 VmmAction → 唤醒 VMM → 阻塞等 response。

    三个并发单元

    单元 线程 职责
    API thread（fc_api） 独立线程 HTTP server、解析 request、发 action、等 response
    VMM thread 主线程 preboot loop / runtime EventManager、设备 emulation、协调 vCPU
    vCPU thread（fc_vcpu <i>） 每 vCPU 一个 KVM_RUN 循环

    三层同步边界

    1. API request/response channel：API thread ↔ VMM thread（mpsc + eventfd）。
    2. EventManager subscriber：VMM thread 的 runtime 主循环，分发到 API adapter / VMM / 各设备。
    3. vCPU event/response channel：VMM thread ↔ vCPU thread（mpsc + immediate_exit + signal）。

    关键机制

    • eventfd + mpsc 两件套：eventfd 只传"次数"（叫醒），mpsc 传结构化消息。
    • immediate_exit + signal：vCPU 正在 KVM_RUN 时，VMM 设 KVM immediate_exit 再发实时 signal，强制 vCPU 尽快退出 run loop 处理 event（pause/resume 能打断 KVM_RUN 的原理）。
    • preboot vs runtime 两阶段：preboot 是阻塞 request loop（还没 EventManager）；build 成功后 runtime 把 API/VMM/设备都注册进 EventManager。

    1. 核心结论

    • API thread 把 VmmAction 经 mpsc 发 VMM thread，写 eventfd 唤醒，阻塞等 response。
    • VMM thread 两阶段：preboot 阻塞等 API request；runtime 跑 EventManager。
    • vCPU thread 不在 EventManager 中——VMM thread 经 VcpuHandle 发 VcpuEvent + immediate_exit + signal 控制。
    • 控制面同步边界三层：API request/response channel、EventManager subscriber、vCPU event/response channel。

    2. 总体流程图

    flowchart TD Client["HTTP over Unix socket"] --> API["API thread fc_api"] API --> Parse["ParsedRequest::try_from"] Parse --> Action["VmmAction"] Action --> Tx["mpsc Sender"] Tx --> Evt["api_event_fd.write"] Evt --> Preboot["Preboot loop before boot"] Preboot --> Build["StartMicroVm builds Vmm"] Build --> Runtime["EventManager runtime loop"] Runtime --> ApiSub["ApiServerAdapter subscriber"] Runtime --> VmmSub["Vmm subscriber"] Runtime --> DevSub["virtio / legacy subscribers"] ApiSub --> Controller["RuntimeApiController"] Controller --> Vmm["Arc>"] Vmm --> VcpuHandle["VcpuHandle"] VcpuHandle --> VcpuEvt["VcpuEvent + immediate_exit + signal"] VcpuEvt --> VcpuThread["fc_vcpu threads"] Controller --> Resp["mpsc Sender"] Resp --> API

    3. HTTP Request 到 VmmAction

    ApiServer::run() 在 fc_api 线程跑 HTTP server，先加载 API thread seccomp（api_server/mod.rs:64）。handle_request() 调 ParsedRequest::try_from() 解析，URI→action 映射集中在此（/boot-source//drives//network-interfaces//actions//snapshot，parsed_request.rs:65）。当前 RequestAction 只有同步形态 Sync(Box<VmmAction>)（:36）。

    4. API Thread 到 VMM Thread

    ApiServer 三字段构成 API↔VMM 同步边界：

    // src/firecracker/src/api_server/mod.rs:28
pub struct ApiServer {
    api_request_sender: mpsc::Sender<ApiRequest>,   // 发给 VMM
    vmm_response_receiver: mpsc::Receiver<ApiResponse>,  // 收 VMM 响应
    to_vmm_fd: EventFd,                              // 通知 VMM "有 request"
}

    serve_vmm_action_request() 三步：发 mpsc → 写 eventfd → 阻塞等 response：

    // src/firecracker/src/api_server/mod.rs:147
fn serve_vmm_action_request(&mut self, vmm_action: Box<VmmAction>, /*...*/) -> Response {
    self.api_request_sender.send(vmm_action).expect("Failed to send VMM message");
    self.to_vmm_fd.write(1).expect("Cannot update send VMM fd");        // 敲门
    let vmm_outcome = *(self.vmm_response_receiver.recv().expect("VMM disconnected"));  // 阻塞等
    ParsedRequest::convert_to_response(&vmm_outcome)
}

    run_with_api() 建 API eventfd（EFD_SEMAPHORE）+ kill switch + 两个 mpsc，spawn fc_api 线程（api_server_adapter.rs:149）。API thread 结束由 kill switch 驱动，VMM runtime 结束后主线程写 kill switch join（:243）。

    5. Preboot Controller

    无 JSON 配置时 run_with_api() 调 PrebootApiController::build_microvm_from_requests()（api_server_adapter.rs:219）。preboot loop 是简单阻塞循环——还没 EventManager：

    // src/vmm/src/rpc_interface.rs:350
while preboot_controller.built_vmm.is_none() {
    let req = from_api.recv().expect("channel disconnected");          // 阻塞等 API request
    api_event_fd.read().expect("Failed to read API event_fd");         // 消费 eventfd 计数
    let res = preboot_controller.handle_preboot_request(*req);         // 处理 preboot action
    to_api.send(Box::new(res)).expect("one-shot channel closed");      // 回 API thread
    if let Some(preboot_error) = preboot_controller.fatal_error { return Err(preboot_error); }
}

    此阶段没把 API adapter 注册到 EventManager——microVM 还没 build，主要工作是收集 VmResources。handle_preboot_request() 允许 boot source/machine/block/net/pmem/balloon/vsock/MMDS/snapshot load/StartMicroVm，拒绝 pause/resume/create snapshot/runtime update/post-boot stats（rpc_interface.rs:417/487）。

    6. Runtime EventManager

    build 成功后 run_microvm() 把 API adapter 注册成 EventManager subscriber，主循环是 event_manager.run()：

    // src/firecracker/src/api_server_adapter.rs:49
fn run_microvm(api_event_fd, from_api, to_api, vmm: Arc<Mutex<Vmm>>, event_manager: &mut EventManager) -> Result<(), ApiServerError> {
    let api_adapter = Arc::new(Mutex::new(Self { api_event_fd, from_api, to_api,
        controller: RuntimeApiController::new(vmm.clone()) }));
    event_manager.add_subscriber(api_adapter);
    loop {
        event_manager.run().expect("EventManager fatal");              // runtime 主循环
        match vmm.lock().unwrap().shutdown_exit_code() {               // 每轮检查退出码
            Some(FcExitCode::Ok) => break,
            Some(exit_code) => return Err(ApiServerError::MicroVMStoppedWithError(exit_code)),
            None => continue,
        }
    }
}

    ApiServerAdapter::process() 只处理 API eventfd 的 EPOLLIN，读 eventfd 后 try_recv action 交 RuntimeApiController：

    // src/firecracker/src/api_server_adapter.rs:86
fn process(&mut self, event: Events, _: &mut EventOps) {
    if source == self.api_event_fd.as_raw_fd() && event_set == EventSet::IN {
        let _ = self.api_event_fd.read();
        match self.from_api.try_recv() {
            Ok(api_request) => {
                let request_is_pause = *api_request == VmmAction::Pause;
                self.handle_request(*api_request);
                if request_is_pause {                                  // pause 特殊处理
                    loop {                                             // 留在 process 内阻塞接收直到 resume
                        let req = self.from_api.recv().expect("...");
                        let req_is_resume = *req == VmmAction::Resume;
                        self.handle_request(*req);
                        if req_is_resume { break; }
                    }
                }
            }
            // ...
        }
    }
}

    pause 特殊处理的代价：adapter 留在 process() 内阻塞接收，不把控制权交回 EventManager，于是设备 emulation 和 metrics timerfd 一起冻结（api_server_adapter.rs:96）。这是 Firecracker 实现"整个 VM 暂停"的方式。

    7. VMM 与设备 Subscriber

    EventManager 是类型别名，subscriber 是 Arc<Mutex<dyn MutEventSubscriber>>（vmm/src/lib.rs:170）。microVM 构建时把 virtio + legacy 设备注册进去（device_manager/mod.rs:267）：block 先注册 activate event，激活后再注册 queue/rate limiter/async completion（block/.../event_handler.rs:17）；net 分 activate 与 runtime（RX/TX virtqueue/tap RX/rate limiter，net/.../event_handler.rs:83）。VMM 自身也是 subscriber，只注册 vCPU exit eventfd（lib.rs:886）；builder 启动 vCPU + 加载 VMM thread seccomp 后把 VMM 注册进 EventManager（builder.rs:338）。

    8. Runtime Controller

    RuntimeApiController::handle_request() 持 Arc<Mutex<Vmm>>（rpc_interface.rs:823），允许 create snapshot/pause/resume/MMDS/balloon/block/net/pmem/memory hotplug size update（:685），拒绝 preboot-only action（boot source/insert block/net/pmem/load snapshot/restart/machine config update，:803）。

    runtime 支持"更新已有对象"，不支持任意新增 VM 拓扑。

    9. vCPU Thread 同步

    Vcpu::new() 为每个 vCPU 建 event + response channel（vcpu.rs:120）。start_threaded() 建 fc_vcpu <index> 线程，注册 kick signal handler 后进 run()（:166/198）。VcpuHandle::send_event() 三步是 pause/resume 能打断 KVM_RUN 的原理：

    // src/vmm/src/vstate/vcpu.rs:596
pub fn send_event(&mut self, event: VcpuEvent) -> Result<(), VcpuSendEventError> {
    self.event_sender.send(event).expect("event sender channel closed");  // (1) 发 VcpuEvent
    self.vcpu_fd.set_kvm_immediate_exit(1);                               // (2) 设 KVM immediate_exit
    fence(Ordering::Release);
    self.vcpu_thread.as_ref().unwrap().kill(sigrtmin() + VCPU_RTSIG_OFFSET)?;  // (3) 发实时 signal 踢出 KVM_RUN
    Ok(())
}

    三步缺一不可：只发 event vCPU 在 KVM_RUN 里收不到；immediate_exit 让下次 KVM_RUN 立即返回；signal 把 vCPU 从 KVM_RUN 中踢出来去检查 event。

    10. Pause / Resume / Snapshot

    resume_vm() 先 kick virtio devices，再给所有 vCPU 发 Resume 并等全部 Resumed（lib.rs:524）；pause_vm() 类似发 Pause 等 Paused（:548）。save_state() 的顺序很关键：

    // src/vmm/src/lib.rs:582
pub fn save_state(&mut self, vm_info: &VmInfo) -> Result<MicrovmState, MicrovmStateError> {
    self.check_unsnapshottable_devices()?;
    // 设备 state 必须先存：有些设备（如 async engine block）可能改 virtio transport 并给 guest 发中断，
    // 若先存 KVM state，该中断恢复后永远不会送达 guest。
    let device_states = self.device_manager.save();      // (1) 先设备
    let vcpu_states = self.save_vcpu_states()?;          // (2) 再 vCPU
    let kvm_state = self.kvm.save_state();               // (3) KVM
    let vm_state = { /* x86_64 vm.save_state(); aarch64 构造 MPIDR 列表 */ };
    Ok(MicrovmState { vm_info, kvm_state, vm_state, vcpu_states, device_states })
}

    paused 状态的 vCPU 才能 SaveState（running 下返回 not allowed，vcpu.rs:296）。snapshot 只能在 Paused 状态执行——这就是 pause/resume 是 snapshot/migration 前置的原因。

    11. Shutdown 与 Guest Exit

    vCPU thread 遇 guest shutdown/reset/emulation error 进 exit()，写 vCPU exit eventfd 并不断发 VcpuResponse::Exited（vcpu.rs:362）。VMM subscriber 收 vCPU exit eventfd 后遍历 response、保留非 OK exit code、调 self.stop(exit_code)（lib.rs:886）。Vmm::stop() 只设 shutdown_exit_code，runtime loop 下一轮检查后退出（:817）。

    guest 退出不是 API thread 直接观察的，而是 vCPU thread → eventfd → VMM subscriber → runtime loop 的链路。

    12. ARM64 与 x86_64 差异

    控制面 channel/eventfd/EventManager/vCPU channel 架构中性。差异在 vCPU exit 与设备总线：x86_64 启动 vCPU 前设 PIO bus，aarch64 只设 MMIO bus（lib.rs:506）；guest shutdown/reset 在 ARM 经 KVM_SYSTEM_EVENT 进 exit()，x86 经 i8042 emulation 通知主线程（vcpu.rs:218）；SendCtrlAltDel 只 x86_64 编译（rpc_interface.rs:129/756）；snapshot VM state——x86_64 直接存，aarch64 据 vCPU state 构造 MPIDR 列表（lib.rs:582）。

    13. 能力边界

    1. API 同步，但 API thread 不直接执行 VMM 修改——只解析/发 action/唤醒/等 response。
    2. preboot（阻塞 request loop）与 runtime（EventManager subscriber loop）控制循环不同。
    3. pause 冻结 EventManager 层面的设备 emulation + metrics timerfd，直到 resume。
    4. vCPU 控制不依赖 EventManager——VMM thread 经 channel + immediate_exit + signal 控制 vCPU thread。
    5. post-boot 只允许更新已有对象/查询状态，不允许重新插入核心设备/重配 boot source/再次 start VM。
