    Firecracker ARM64 网络准样本：Restore 后网络异常

    本文承接 ARM64 网络失败原型 和 Snapshot / Restore 链路。

    前面的失败原型已经把：

    restore 前正常，restore 后异常

    归成一类。

    这一篇继续往前走一步。

    它不做真实事故回放。

    它把这一类故障整理成一份可以直接套用的准样本目标。

    源码基线：当前工作树。

    1. 样本定位

    Firecracker 当前已有两份网络准样本：

    1. TAP / vnet header 早失败
    2. MMDS / rate limiter 伪失败

    这两份分别覆盖了：

    1. 最早的 host backend 初始化
    2. 最容易误判的共享数据面现象

    但 Firecracker 还缺一个更靠后的关键样本：

    restore 后网络异常

    这也是当前覆盖矩阵里最明显的空洞之一。

    2. 为什么 restore 必须单独建样本

    这类问题和前两类不一样。

    它的危险点在于：

    host TAP 可以重新打开成功，但 guest 仍然没有网络。

    这时如果只看 net device 自己的恢复，很容易把问题看窄。

    如果只看 ARM64 arch state，又会忽略 net state 自己的恢复条件。

    因此这类样本必须单独固定。

    3. 触发条件

    Firecracker net snapshot 保存的内容是有限的。

    它只保存：

    1. tap interface name
    2. guest MAC
    3. MMDS namespace
    4. virtio state
    5. limiter state

    源码依据：virtio-net-data-path-chain.md。

    与此同时，ARM64 restore 还要恢复：

    1. MPIDR
    2. GIC
    3. KVI 等 arch state

    源码依据：arch-arm64-x86-chain.md。

    因此这类样本的真实触发条件，不应写成“restore 失败”这么粗。

    更准确的说法是：

    net state 恢复与 ARM64 arch state 恢复之间存在协同缺口。

    4. 准样本最小现象

    这类样本最小需要满足三段现象：

    1. restore 前网络正常
    2. restore 操作完成
    3. restore 后网络异常

    如果缺少第一段，就无法证明这是“回归”。

    如果缺少第二段，就无法证明问题真的发生在 restore 边界。

    如果缺少第三段，就无法构成有效失败样本。

    5. 准样本结构

    建议最小结构如下：

    [Scenario]
arch = arm64
stage = snapshot -> restore
pre_restore_network = healthy

[Pre-Restore Evidence]
evidence = host tap usable
evidence = guest network usable

[Restore Evidence]
evidence = restore call completed
evidence = tap reopened or net state restored

[Post-Restore Failure]
symptom = guest network unavailable
or
symptom = restore after net path regressed

[Classification]
layer = restore / arch-state coordination
not = pure TapOpen failure
not = pure MMDS pseudo-failure

    6. 它实际证明了什么

    如果一份样本能满足上面的三段结构，它至少证明两件事。

    第一，故障不是普通启动期的 host backend 初始化错误。

    第二，故障也不是单纯的 MMDS 分流或限速伪失败。

    它真正逼近的是：

    restore 边界上的状态协同问题

    这正是 Firecracker ARM64 比前面两类更难分析的地方。

    7. 与早失败样本的边界

    这份样本故意不覆盖：

    1. TapOpen
    2. TapSetVnetHdrSize
    3. OpenTun
    4. IfreqExecuteError

    因为这些都属于“启动前或启动中就失败”的路径。

    而本样本只处理：

    restore 之后才暴露的问题

    如果样本里连 restore 前网络成功都没有，那它就不该归到这一类。

    8. 与伪失败样本的边界

    这份样本也故意不覆盖：

    1. MMDS frame 被内部消费
    2. tx_queue.undo_pop()
    3. tx_rate_limiter_throttled

    这些现象在普通运行态就可能出现。

    它们本身不能证明 restore 回归。

    因此如果没有明确的“restore 前后对照”，也不该归到本样本。

    9. 升级为真实样本时建议保留什么

    如果后续拿到真实 ARM64 日志，建议至少保留：

    1. scenario.md
    2. pre-restore.txt
    3. restore.txt
    4. post-restore.txt
    5. classification.md

    其中 classification.md 应明确回答三件事：

    1. 为什么认定 restore 前网络是好的
    2. 为什么认定 restore 操作本身完成了
    3. 为什么判断失败点在 restore / arch-state coordination

    10. 当前最缺的证据是什么

    这类样本现在最大的问题不是原型不清楚。

    而是仓库里还没有一份现成的 ARM64 restore 网络失败日志包。

    所以这篇准样本的价值不在于替代真实样本。

    而在于：

    后续一旦拿到真实日志，可以立刻按这里的结构去落档，而不用重新定义口径。

    11. 结论

    restore 后网络异常 是 Firecracker ARM64 网络线上当前最值得补齐的第三类准样本。

    它补上的不是一个普通失败点。

    而是 Firecracker 在 ARM64 上最容易被过窄理解的一块状态协同问题。
