    1. API 控制面与启动边界

    研究目标：理解 Unix socket HTTP API 如何变成 VmmAction，以及 InstanceStart 为什么是 pre-boot 配置阶段和 runtime 阶段的分界。

    关键源码：

    • API server 先把 HTTP request 解析成 ParsedRequest，再转成 VmmAction 发送给 VMM：src/firecracker/src/api_server/mod.rs。
    • URI 到 action 的映射在 ParsedRequest::try_from() 中，例如 /boot-source、/machine-config、/drives、/network-interfaces：src/firecracker/src/api_server/parsed_request.rs。
    • /actions 中的 InstanceStart 被解析为 VmmAction::StartMicroVm：src/firecracker/src/api_server/request/actions.rs。
    • pre-boot controller 处理配置请求，StartMicroVm 成功后产出 built_vmm 并退出 pre-boot loop：src/vmm/src/rpc_interface.rs。
    flowchart LR HTTP["HTTP over Unix socket"] --> Parse["ParsedRequest"] Parse --> Action["VmmAction"] Action --> Preboot["PrebootApiController"] Preboot --> Resources["VmResources"] Preboot --> Start["StartMicroVm"] Start --> Runtime["RuntimeApiController"]

    继续深入点：

    • 已完成 API Event Loop 与线程协作链路，覆盖 API thread、eventfd、mpsc channel、preboot loop、runtime EventManager 和 vCPU event/response channel。

    2. VmResources 配置聚合

    研究目标：理解 Firecracker 为什么先收集配置对象，再一次性构建 microVM。

    关键源码：

    • VmResources 保存 machine config、boot source、block、vsock、balloon、net、entropy、pmem、memory hotplug 和 MMDS：src/vmm/src/resources.rs。
    • build_boot_source() 会创建 BootConfig，包含 kernel fd、cmdline 等启动构造信息：src/vmm/src/resources.rs。
    • block/net/pmem/balloon/vsock 等 API 在 pre-boot 阶段只更新 builder 或 config，不立即创建 guest 可见设备：src/vmm/src/rpc_interface.rs。

    继续深入点：

    • 已完成 VmResources 配置聚合与能力边界链路，覆盖 API 到 VmmAction、VmResources builder、pre-boot/runtime 分界、启动消费路径和 ARM64/x86_64 边界。

    3. build_microvm_for_boot 主路径

    研究目标：从 StartMicroVm 追到 KVM VM、vCPU、guest memory、DeviceManager、kernel/initrd 和 seccomp。

    关键源码：

    • build_microvm_for_boot() 注释明确：构建后的 microVM 和 vCPU 初始处于 paused，需要 Vmm::resume_vm() 才运行：src/vmm/src/builder.rs。
    • 函数先读取 boot source、分配 guest memory、创建 KVM、创建 VM 和 vCPU，并注册 DRAM：src/vmm/src/builder.rs。
    • 随后创建 DeviceManager，加载 kernel/initrd，按配置 attach balloon、block、net、pmem、vsock、entropy、virtio-mem 和 legacy/arch 设备：src/vmm/src/builder.rs。
    • 架构相关 boot state 由 configure_system_for_boot() 写入 guest memory 或 vCPU register：src/vmm/src/builder.rs。
    • vCPU 线程启动后先处于 paused，VMM seccomp 在最后加载：src/vmm/src/builder.rs。

    继续深入点：

    • 已完成 build_microvm_for_boot 构建链路，覆盖 KVM/VM/vCPU、guest memory、DeviceManager、kernel/initrd、设备 attach、架构 boot config、seccomp 和 resume。

    4. vCPU 线程与 KVM_RUN

    研究目标：理解 Firecracker 的虚拟化机制如何落在 KVM vCPU fd 上。

    关键源码：

    • Vmm::start_vcpus() 为每个 vCPU 设置 MMIO bus，x86_64 还设置 PIO bus，然后调用 Vcpu::start_threaded()：src/vmm/src/lib.rs。
    • start_threaded() 创建名为 fc_vcpu <index> 的线程，并在该线程中执行 self.run(filter)：src/vmm/src/vstate/vcpu.rs。
    • vCPU 主循环先加载 seccomp，再从 paused 状态运行状态机：src/vmm/src/vstate/vcpu.rs。
    • running 状态调用 run_emulation()，后者直接执行 self.kvm_vcpu.fd.run()，即 KVM_RUN：src/vmm/src/vstate/vcpu.rs。
    • MMIO read/write exit 会访问 mmio_bus，这是 guest 访问 MMIO virtio 设备进入 VMM 的关键路径：src/vmm/src/vstate/vcpu.rs。

    继续深入点：

    • 画出 vCPU state machine：Paused、Running、Exited。
    • 分析 VcpuEvent::Resume/Pause 与 response channel。
    • 对比 x86_64 PIO exit 和 aarch64 system event 路径。

    5. 设备模型与能力边界

    研究目标：解释 Firecracker 为什么把设备模型压缩到少量 virtio 设备和少量 legacy/arch 设备。

    关键源码：

    • build_microvm_for_boot() 只按配置 attach balloon、block、net、pmem、vsock、entropy、virtio-mem、boot timer、vmgenid、vmclock 和少量 legacy/arch 设备：src/vmm/src/builder.rs。
    • root block 设备会把 root=/dev/vda 或 root=PARTUUID=... 写入 kernel cmdline：src/vmm/src/builder.rs。
    • pmem root 设备会写入 root=/dev/pmem{i}：src/vmm/src/builder.rs。

    继续深入点：

    • 已完成 Virtio Block 数据面链路，覆盖 drive API、root cmdline、virtqueue 请求解析、sync/io_uring I/O、rate limiter、runtime update、snapshot state 和 ARM64/x86_64 边界。
    • 已完成 Virtio Net 数据面链路，覆盖 network API、TAP fd、TX/RX virtqueue、guest memory iovec、rate limiter、MMDS 分流、runtime PATCH、snapshot state 和 ARM64/x86_64 边界。
    • 已完成 MMDS 元数据网络链路，覆盖 API 数据更新、VmResources 绑定、virtio-net detour、token、runtime 边界和 ARM64/x86_64 差异。
    • 已完成 设备能力边界链路，覆盖 vsock、balloon、pmem、entropy/rng、virtio-mem 的运行期更新、snapshot 保存项、外部依赖和 ARM64/x86_64 边界。
    • 已完成 中断与事件通知链路，覆盖 queue notify、ioeventfd、irqfd、MMIO IrqTrigger、PCI MSI-X、GSI route 和 ARM64/x86_64 控制器差异。
    • 已完成 可观测性与诊断链路，覆盖 API 同步错误、全局 logger、全局 metrics、设备级计数和生产 serial 边界。

    6. ARM64 与 x86_64 启动差异

    研究目标：把架构差异落到代码，而不是停留在“一个用 ACPI，一个用 FDT”。

    专题进展：

    • 已完成 ARM64 与 x86_64 架构差异链路，覆盖 KVM capability、启动配置、vCPU、PIO/MMIO、FDT/ACPI、设备暴露和 snapshot state。
    • 已完成 机器描述：x86_64 ACPI 与 ARM64 FDT 链路，覆盖 x86_64 boot params/MP table/ACPI、ARM64 MPIDR/CLIDR/FDT、VMGenID/VMClock 和 DeviceManager 描述数据源。

    关键源码：

    • x86_64 configure_system_for_boot() 构造 CPUID config，配置 vCPU，写 cmdline，设置 mptable，并按 PVH/LinuxBoot 写 boot params，最后创建 ACPI tables：src/vmm/src/arch/x86_64/mod.rs。
    • aarch64 configure_system_for_boot() 构造 CPU config，配置 vCPU，override CLIDR，读取 MPIDR，创建 FDT，并把 FDT 写入 guest memory：src/vmm/src/arch/aarch64/mod.rs。
    • aarch64 有 pvtime setup 分支，x86_64 有 PIO bus 和 CtrlAltDel/i8042 路径：src/vmm/src/builder.rs、src/vmm/src/lib.rs。

    继续深入点：

    7. Snapshot / Restore 路线

    研究目标：理解 Firecracker snapshot 保存的是 VMM 级状态，不包含外部编排平台的语义。

    关键源码：

    • runtime controller 支持 CreateSnapshot，pre-boot controller 支持 LoadSnapshot：src/vmm/src/rpc_interface.rs、src/vmm/src/rpc_interface.rs。
    • snapshot 恢复走 build_microvm_from_snapshot()，它重建 KVM、VM、vCPU 和 memory regions，再恢复设备/vCPU/VMM state：src/vmm/src/builder.rs。
