    Firecracker VmResources 配置聚合与能力边界链路

    本文从源码追踪 Firecracker 如何把 HTTP API 配置收敛到 VmResources，再由 StartMicroVm 一次性构建 microVM。

    源码基线：当前仓库工作树。

    相关：API 到 MicroVM 启动链路、Runtime 设备更新链路、横向 资源管理与 QoS。

    0. 术语与背景

    Firecracker 的三阶段控制面

    Firecracker 的控制面是"先配置，后构建，运行后只窄口径 update"。理解这条线要分清三个阶段：

    阶段 做什么 允许
    pre-boot PUT/PATCH 把配置灌进 VmResources 的 builder/config 配置 boot source/machine/block/net/vsock/balloon/pmem/entropy/MMDS/...
    build（StartMicroVm） 一次性消费 VmResources，建 KVM/VM/vCPU/DeviceManager/设备 两个阶段的唯一分界线
    post-boot（runtime） 对已存在设备做有限 update block backing/rate limiter、net rate limiter、pmem rate limiter、balloon、virtio-mem size、MMDS data

    关键：API 的 PUT/PATCH 不立即创建 guest 可见设备——多数只更新 VmResources 内的 builder/config，直到 StartMicroVm 才一次性构建。

    VmResources 是什么

    VmResources 是 pre-boot 阶段的配置聚合对象——构建 VM 所需的资源集合，不是已运行 VM 的完整对象图。它持有一堆 builder（BlockBuilder/NetBuilder/...），builder 是独立类型，不是抽象概念。

    builder 模式

    BlockBuilder、NetBuilder 等只构造 host 侧设备对象，不挂到 guest bus。挂载发生在 build 阶段的 attach_*。

    1. 核心结论

    • VmResources 保存 machine/boot source/block/net/vsock/balloon/pmem/entropy/virtio-mem/MMDS/transport 开关。
    • /actions 的 InstanceStart 转成 VmmAction::StartMicroVm——pre-boot 与 runtime 的分界。
    • 启动时 build_microvm_for_boot() 一次性消费 VmResources：建 guest memory/KVM VM/vCPU/DeviceManager/kernel/initrd/virtio 设备/arch boot state。
    • 运行期不重新配置 VM，只对已存在设备做有限 update。
    • ARM64/x86_64 差异不在 VmResources 聚合层，在 build 阶段的 PCI/MMIO、FDT/ACPI、legacy device、pvtime、CtrlAltDel、snapshot restore。

    2. 总体链路

    flowchart LR HTTP["HTTP API"] --> Parsed["ParsedRequest"] Parsed --> Action["VmmAction"] Action --> Preboot["PrebootApiController"] Preboot --> Resources["VmResources"] Resources --> Start["StartMicroVm"] Start --> Build["build_microvm_for_boot"] Build --> VMM["Vmm + DeviceManager"] VMM --> Runtime["RuntimeApiController"]

    ParsedRequest::try_from() 按 HTTP method+path 选解析器，分发 /boot-source//machine-config//drives//network-interfaces//snapshot//vsock（parsed_request.rs:82）。

    3. VmResources 的内容

    // src/vmm/src/resources.rs:108
pub struct VmResources {
    pub machine_config: MachineConfig,
    pub boot_source: BootSource,
    pub block: BlockBuilder,
    pub vsock: VsockBuilder,
    pub balloon: BalloonBuilder,
    pub net_builder: NetBuilder,
    pub entropy: EntropyDeviceBuilder,
    pub pmem: PmemBuilder,
    pub memory_hotplug: Option<MemoryHotplugConfig>,
    pub mmds: Option<Arc<Mutex<Mmds>>>,
    pub mmds_size_limit: usize,
    pub boot_timer: bool,
    pub pci_enabled: bool,
    pub serial_out_path: Option<PathBuf>,
    pub serial_rate_limiter_cfg: Option<TokenBucketConfig>,
}

    默认值分散在子类型：MachineConfig::default() = 1 vCPU、默认内存、SMT false、dirty tracking false、no huge pages（machine_config.rs:149）。BootSource 同时存用户 config 和验证后的 BootConfig builder（boot_source.rs:18）。VmResources::from_json() 把 VmmConfig 逐项灌入 builder/config，并初始化 logger/metrics/metadata（resources.rs:155）。

    4. Builder 与校验

    update_machine_config() 用 MachineConfigUpdate 生成新配置，并检查 balloon target 不能超过 guest memory：

    // src/vmm/src/resources.rs:264
pub fn update_machine_config(&mut self, update: &MachineConfigUpdate) -> Result<(), MachineConfigError> {
    let updated = self.machine_config.update(update)?;
    if self.balloon.get().is_some()
        && updated.mem_size_mib < self.balloon.get_config()?.amount_mib as usize
    {
        return Err(MachineConfigError::IncompatibleBalloonSize);   // 内存不能小于 balloon target
    }
    self.machine_config = updated;
    Ok(())
}

    build_boot_source() 建 BootConfig（kernel fd、cmdline），保留原始 BootSourceConfig（:345）。set_block_device()/build_pmem_device() 互查 root device 冲突——block root 与 pmem root 不能同时占 rootfs（:361）。build_net_device() 只构造 host 侧 net 对象，未挂 guest bus（:369）。各 builder 是独立类型如 BlockBuilder（drive.rs:85）。

    5. Preboot 分发

    pre-boot loop 持续接收 API request 直到 PrebootApiController 产出 built_vmm（rpc_interface.rs:350）。handle_preboot_request() 允许的 setter（节选）：

    // src/vmm/src/rpc_interface.rs:425
match request {
    ConfigureBootSource(config) => self.set_boot_source(config),
    ConfigureLogger(logger_cfg) => /* ... */,
    ConfigureSerial(serial_cfg) => { self.vm_resources.serial_out_path = ...; }
    InsertBlockDevice(config)   => self.insert_block_device(config),
    InsertPmemDevice(config)    => self.insert_pmem_device(config),
    InsertNetworkDevice(config) => self.insert_net_device(config),
    LoadSnapshot(config)        => self.load_snapshot(&config)?,
    SetBalloonDevice(config)    => self.set_balloon_device(config),
    SetVsockDevice(config)      => self.set_vsock_device(config),
    SetEntropyDevice(config)    => self.set_entropy_device(config),
    SetMemoryHotplugDevice(config) => self.set_memory_hotplug_device(config),
    StartMicroVm                => self.start_microvm(),       // 唯一普通启动出口
    UpdateMachineConfiguration(config) => self.update_machine_config(config),
    // ...
}

    这些 setter 大多只把 boot_path 设 true 并更新 VmResources——不建 KVM VM，不起 vCPU。

    pre-boot 拒绝一切 runtime 行为（snapshot create/pause/resume/balloon update/device update/memory hotplug update 等），返回 OperationNotSupportedPreBoot：

    // src/vmm/src/rpc_interface.rs:487
CreateSnapshot(_) | FlushMetrics | Pause | Resume | GetBalloonStats | GetMemoryHotplugStatus
| UpdateBalloon(_) | UpdateBalloonStatistics(_) | UpdateBlockDevice(_) | UpdateMemoryHotplugSize(_)
| UpdateNetworkInterface(_) | UpdatePmemDevice(_) | StartFreePageHinting(_)
| GetFreePageHintingStatus | StopFreePageHinting => Err(VmmActionError::OperationNotSupportedPreBoot),

    start_microvm() 成功后保存 built_vmm，pre-boot loop 结束（:609）。

    6. LoadSnapshot 的特殊边界

    LoadSnapshot 只能在 pre-boot 执行，成功后同样设 built_vmm 进入 runtime（:625）。已走过 boot path 则拒绝 restore，避免配置路径与 snapshot restore 混用（:633）。build_microvm_from_snapshot() 用 snapshot 的 KVM/VM/vCPU/device state 重建，并把 vm_info.boot_source 写回 VmResources（builder.rs:439）。

    7. StartMicroVm 如何消费 VmResources

    build_microvm_for_boot() 先要求 boot_source.builder 存在（没 kernel config 不能启动），再分配 guest memory、读 CPU template、建 KVM/VM/vCPU、注册 DRAM：

    // src/vmm/src/builder.rs:153
let boot_config = vm_resources.boot_source.builder.as_ref()
    .ok_or(StartMicrovmError::MissingKernelConfig)?;
let guest_memory = vm_resources.allocate_guest_memory()?;
let mut boot_cmdline = boot_config.cmdline.clone();
let cpu_template = vm_resources.machine_config.cpu_template.get_cpu_template()?;
let kvm = Kvm::new(cpu_template.kvm_capabilities.clone())?;
let mut vm = Vm::new(&kvm)?;
let (mut vcpus, vcpus_exit_evt) = vm.create_vcpus(vm_resources.machine_config.vcpu_count)?;
vm.register_dram_memory_regions(guest_memory)?;

    memory hotplug 时先分配 virtio-mem 地址 + hotpluggable region 再注册（:179）。然后建 DeviceManager、加载 kernel/initrd——这里才开始把 builder 中的设备真正 attach 到 guest 可见 transport：

    // src/vmm/src/builder.rs:195
let mut device_manager = DeviceManager::new(event_manager, &vcpus_exit_evt, &vm, /* serial */)?;
let entry_point = load_kernel(&boot_config.kernel_file, vm.guest_memory())?;
let initrd = InitrdConfig::from_config(boot_config, vm.guest_memory())?;
if vm_resources.pci_enabled {
    device_manager.enable_pci(&vm)?;          // PCI 开关在此生效
} else {
    boot_cmdline.insert("pci", "off")?;
}

    8. 设备 attach 顺序

    boot timer 必须第一个 attach（保持 MMIO 地址稳定），随后 balloon → block → net → pmem → vsock → entropy → virtio-mem：

    // src/vmm/src/builder.rs:214
if vm_resources.boot_timer { device_manager.attach_boot_timer_device(&vm, request_ts)?; }
if let Some(balloon) = vm_resources.balloon.get() { attach_balloon_device(/*...*/)?; }
attach_block_devices(/*...*/, vm_resources.block.devices.iter(), /*...*/)?;
attach_net_devices(/*...*/, vm_resources.net_builder.iter(), /*...*/)?;
attach_pmem_devices(/*...*/, vm_resources.pmem.devices.iter(), /*...*/)?;
if let Some(unix_vsock) = vm_resources.vsock.get() { attach_unixsock_vsock_device(/*...*/)?; }
if let Some(entropy) = vm_resources.entropy.get() { attach_entropy_device(/*...*/)?; }
if let Some(memory_hotplug) = &vm_resources.memory_hotplug { attach_virtio_mem_device(/*...*/)?; }

    block root 写 root=/dev/vda 或 root=PARTUUID=... + ro/rw（:672）；pmem root 写 root=/dev/pmem{i}（:729）。所有 virtio 设备最后经 DeviceManager::attach_virtio_device() 进 MMIO 或 PCI transport（:695）。

    9. 架构 boot state

    aarch64 build 阶段 attach legacy devices 并按需设 pvtime；x86_64 无此分支（:285）。随后统一 configure_system_for_boot()（同名，target arch 分流，:304）：aarch64 配 vCPU、读 MPIDR、cmdline 放进 FDT、FDT 写入 guest memory（arch/aarch64/mod.rs:93）；x86_64 配 CPUID/topology、写 cmdline、设 mptable、按 PVH/LinuxBoot 写 boot params、生成 ACPI（arch/x86_64/mod.rs:175）。

    10. Runtime Controller

    启动后请求进 RuntimeApiController::handle_request()，允许 snapshot/pause/resume/MMDS/balloon/block/net/pmem/memory hotplug size update（:680）。这些 update 最终落到 Vmm 的 DeviceManager::with_virtio_device()——按 device type + id 找设备再 downcast：

    // src/vmm/src/device_manager/mod.rs:436
pub fn with_virtio_device<T, F, R>(&self, id: &str, f: F) -> Result<R, FindDeviceError>
where T: VirtioDevice + 'static + Debug, F: FnOnce(&mut T) -> R {
    if let Some(device) = self.get_virtio_device(T::const_device_type(), id) {
        let mut dev = device.lock().expect("Poisoned lock");
        Ok(f(dev.as_mut_any().downcast_mut::<T>().expect("Invalid device for type")))
    } else { Err(FindDeviceError::DeviceNotFound) }
}

    运行期 update 更新的是已有 virtio device 对象的窄字段：UpdateBlockDevice 换 backing file 或 rate limiter（:918）；UpdateNetworkInterface 只更 RX/TX rate limiter（不是热插拔网卡，:969）；UpdatePmemDevice 只更 pmem rate limiter（:950）；UpdateMemoryHotplugSize 改 virtio-mem requested size（不重建内存布局，:796）。

    11. Post-boot 禁止项

    post-boot 明确拒绝 boot source/logger/metrics/serial/block insert/pmem insert/net insert/load snapshot/CPU config/balloon set/vsock set/MMDS config/entropy/memory hotplug set/machine config update：

    // src/vmm/src/rpc_interface.rs:803
ConfigureBootSource(_) | ConfigureLogger(_) | ConfigureMetrics(_) | ConfigureSerial(_)
| InsertBlockDevice(_) | InsertPmemDevice(_) | InsertNetworkDevice(_) | LoadSnapshot(_)
| PutCpuConfiguration(_) | SetBalloonDevice(_) | SetVsockDevice(_) | SetMmdsConfiguration(_)
| SetEntropyDevice(_) | SetMemoryHotplugDevice(_) | StartMicroVm | UpdateMachineConfiguration(_)
    => Err(VmmActionError::OperationNotSupportedPostBoot),

    StartMicroVm 本身 post-boot 也被拒——一个 Firecracker 进程不会在同一生命周期里再建第二个 microVM（:818）。Firecracker 的运行期控制不是完整动态重配置——update 必须落到已存在设备的专用方法。

    12. ARM64 与 x86_64 差异

    VmResources 字段不为架构拆两套（共享聚合层）。差异：① action 层——SendCtrlAltDel 在 ARM64 API 解析时被拒（actions.rs:40）；② boot 描述——ARM64 用 FDT（cmdline/MPIDR/GIC/PCI node），x86_64 写 cmdline/mptable/PVH/Linux boot params/ACPI；③ transport——pci_enabled 通用，但 ARM64 PCI host bridge 要写 FDT node；④ snapshot restore——x86_64 有 TSC scaling/clock realtime restore，aarch64 拒绝 clock_realtime 并用 MPIDR 恢复（builder.rs:465）。

    13. 能力边界

    Firecracker 能力边界 = "一次性构建 + 有限 runtime update"：

    • 一次性构建来自 VmResources：配置先聚合，直到 StartMicroVm 才建 VM/vCPU/DeviceManager/guest 可见设备。
    • 有限 update 来自 runtime controller：只改已有对象的窄字段（rate limiter、block backing、balloon target、virtio-mem size、MMDS data）。

    它不提供 CH 那种 manager 级热插拔控制面，也不提供 Kata 那种 container/task runtime manager 语义。分析时要区分三类问题：pre-boot 可配置 / build 时固化 / post-boot 可更新——混在一起会误判 Firecracker 的设备能力与 runtime 控制能力。
