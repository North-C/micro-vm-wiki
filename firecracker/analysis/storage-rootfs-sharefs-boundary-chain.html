    Firecracker 存储 / rootfs / share-fs 边界链路

    本文承接 Virtio Block 数据面、设备能力边界 和 Snapshot/Restore，把它们收成一个问题：Firecracker 的存储、rootfs 和共享文件系统边界到底在哪。

    源码基线：当前工作树。

    相关：VmResources 配置边界、横向 存储/rootfs/share-fs。

    0. 术语与背景

    Firecracker 存储语义比 CH/Kata 更窄

    它的存储本质是 VMM 暴露块设备，而非 runtime 解释 rootfs/volume/shared mount。三句话概括：① rootfs 主要靠 virtio-blk 或 pmem 暴露；② 没有通用 share-fs 能力面（不像 CH FsConfig 或 Kata guest agent Storage）；③ 运行期只改已有设备字段，不提供通用存储热插拔框架。

    rootfs 怎么定

    Firecracker 的 rootfs 不是靠 guest agent 协议决定，而是靠：guest 可见块设备 + kernel cmdline（root=/dev/vda / root=PARTUUID=... / root=/dev/pmem{i}）。

    三个关键边界概念

    • root 只能有一个——builder 层显式约束（block root 与 pmem root 互斥）。
    • share-fs 缺位本身就是结论——不是文档遗漏，是能力边界。
    • snapshot 不含 backing file 字节——只存设备协议状态 + 可重建引用；恢复依赖 host backing file 语义一致。

    1. 核心结论

    Firecracker 存储 = 精简块设备 + 极简 rootfs 暴露，不把通用 share-fs / 运行期存储热插拔当核心能力面。

    2. 整体链路

    flowchart LR API["drive / pmem / vsock config"] --> Resources["VmResources"] Resources --> Builder["build_microvm_for_boot"] Builder --> Attach["attach block / pmem"] Attach --> Root["root=/dev/vda or /dev/pmemX"] Root --> Guest["guest sees storage device"]

    这条链里没有独立的 share-fs translator——这本身就是边界的一部分。

    3. rootfs：block 与 pmem（attach 顺序 + root 互斥）

    build_microvm_for_boot() 固定先 attach_block_devices 再 attach_pmem_devices，共同改同一个 boot cmdline：

    // src/vmm/src/builder.rs:231
attach_block_devices(&mut device_manager, &vm, &mut boot_cmdline, vm_resources.block.devices.iter(), event_manager)?;
attach_net_devices(/*...*/)?;
attach_pmem_devices(&mut device_manager, &vm, &mut boot_cmdline, vm_resources.pmem.devices.iter(), event_manager)?;

    root 只能有一个是 builder 层显式约束（block root 与 pmem root 互斥）：

    // src/vmm/src/vmm_config/drive.rs:133  (BlockBuilder::insert)
pub fn insert(&mut self, config: BlockDeviceConfig, has_pmem_root: bool) -> Result<(), DriveError> {
    if config.is_root_device && has_pmem_root {
        return Err(DriveError::AddingSecondRootDevice);     // 已有 pmem root → 拒绝再加 block root
    }
    if config.is_root_device && self.has_root_device() && position != Some(0) {
        return Err(DriveError::RootBlockDeviceAlreadyAdded); // 已有 block root → 拒绝第二个
    }
}
// src/vmm/src/vmm_config/pmem.rs:70  (PmemBuilder::build)
pub fn build(&mut self, config: PmemConfig, has_block_root: bool) -> Result<(), PmemConfigError> {
    if config.root_device && has_block_root {
        return Err(PmemConfigError::AddingSecondRootDevice); // 已有 block root → 拒绝 pmem root
    }
}

    block root 写 cmdline（root=/dev/vda 或 root=PARTUUID=... + ro/rw）：

    // src/vmm/src/builder.rs:679
if locked.root_device() {
    match locked.partuuid() {
        Some(partuuid) => cmdline.insert_str(format!("root=PARTUUID={}", partuuid))?,
        None => cmdline.insert_str("root=/dev/vda")?,
    }
    match locked.read_only() { true => cmdline.insert_str("ro")?, false => cmdline.insert_str("rw")? }
}

    pmem root 写 root=/dev/pmem{i} 并显式做 memory-backed 区域分配（不是"另一个 block 名称"）：

    // src/vmm/src/builder.rs:740
cmdline.insert_str(format!("root=/dev/pmem{i}"))?;
locked_dev.alloc_region(vm.as_ref());              // memory-backed 设备路径
locked_dev.set_mem_region(vm.as_ref())?;

    rootfs 语义 = guest 可见块设备 + cmdline，不是 guest agent Storage 协议。

    4. share-fs：不是主能力面

    当前 Firecracker 没有像 CH FsConfig 或 Kata share_rootfs/share_volume 那样的通用 share-fs 主链。

    这不是文档遗漏，是能力边界本身。Firecracker = 精简块设备 + 极简 rootfs，不是通用共享目录平台。"没有 share-fs 主线"本身就是结论。

    5. vsock：是通道，不是 share-fs

    vsock 是 host/guest 通信通道，不是 rootfs/shared mount 语义。snapshot 只存 CID/virtio state/UDS path 等可重建配置，不存活跃连接。不能把 vsock 当 share-fs 替代品——它解决通信，不解决文件系统暴露。

    6. 运行期更新边界（很窄）

    block 运行期只能换 backing file path + 更新 rate limiter：

    // src/vmm/src/devices/virtio/block/device.rs:53
pub fn update_disk_image(&mut self, disk_image_path: String) -> Result<(), BlockError> {
    match self {
        Self::Virtio(b) => b.update_disk_image(disk_image_path).map_err(BlockError::VirtioBackend),
        Self::VhostUser(_) => Err(BlockError::InvalidBlockBackend),   // vhost-user block 直接拒绝
    }
}
// src/vmm/src/devices/virtio/block/virtio/device.rs:537
pub fn update_disk_image(&mut self, disk_image_path: String) -> Result<(), VirtioBlockError> {
    self.disk.update(disk_image_path, self.read_only)?;
    self.config_space.capacity = self.disk.nsectors.to_le();          // 刷 config 容量
    if self.is_activated() {
        self.interrupt_trigger().trigger(VirtioInterruptType::Config)?; // 已激活 → 补 Config 中断让 guest 重读
    }
}

    pmem 运行期更窄——PmemDeviceUpdateConfig 只有 id + rate_limiter：

    // src/vmm/src/vmm_config/pmem.rs:26
/// Configuration for updating a pmem device at runtime. Only the rate limiter can be updated.
pub struct PmemDeviceUpdateConfig {
    pub id: String,
    pub rate_limiter: Option<RateLimiterConfig>,
}

    Firecracker 没有 CH 那种 vm_add_disk/vm_add_fs/vm_add_pmem 统一热插层。运行期存储能力不是"弱版本通用热插拔"，而是根本没把存储热插拔当核心能力面。

    7. snapshot 边界（不含 backing 字节）

    snapshot 保存设备协议状态 + 可重建引用，不含 backing file 字节。DeviceManager::save() 先 prepare_save() 再存 transport/device state：

    // src/vmm/src/device_manager/persist.rs:230
self.for_each_virtio_mmio_device(|_, devid, device| {
    locked_device.prepare_save();                    // 先 prepare，避免 prepare 改的 transport state 丢失
    let transport_state = mmio_transport_locked.save();
    // ...
});
// src/vmm/src/devices/virtio/block/virtio/device.rs:572
pub fn prepare_save(&mut self) {
    if !self.is_activated() { return; }
    self.drain_and_flush(false);                      // 把挂起 I/O 落稳
    if let FileEngine::Async(_) = self.disk.file_engine { self.process_async_completion_queue(); }
}

    prepare_save 只是把挂起 I/O 落稳，不复制 backing 字节。pmem add_device() 注释也要求 restore 时按原顺序把设备加回 builder（pmem.rs:104）——恢复依赖外部 host 上仍然可用且语义一致的 backing 对象。

    8. 与 CH / Kata 的差异

    维度 Firecracker Cloud Hypervisor Kata
    设备暴露 精简块设备 disk/fs/pmem + 运行期 add hypervisor 设备 + guest agent Storage 翻译
    share-fs 无 FsConfig + vhost-user share_rootfs/share_volume → agent
    rootfs 语义 设备暴露边界 设备暴露边界 guest 挂载/runtime 语义边界
    运行期存储 只改已有设备字段 vm_add_disk/fs/pmem（校验后） runtime + agent

    Firecracker 存储边界更接近"设备暴露"，CH/Kata 更接近"guest 挂载与运行时语义"。

    9. ARM64 与 x86_64

    attach_block_devices/attach_pmem_devices/BlockBuilder/PmemBuilder 这些决定 root 与 backing 语义的代码无 #[cfg(target_arch)] 分支——cannot confirm 架构特定的存储语义分叉。能确认的架构差异在中断控制器/机器描述/guest 设备发现层，不在 block/pmem 配置结构本身。

    风险点不在存储请求语义，而在存储设备在 guest 侧如何被发现和驱动（架构相关）。

    10. 结论

    Firecracker 擅长把精简块设备暴露给 guest 并通过 cmdline 确定 rootfs，但不把通用 share-fs 和运行期存储热插拔当核心能力面。后续补这条线应聚焦：rootfs 表达、share-fs 缺位、backing file 依赖、snapshot 恢复边界，与上层 runtime/platform 语义对齐。
