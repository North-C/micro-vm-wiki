    crosvm protected VM IOMMU / VFIO / MemoryMapper 链路

    本文继续下钻 protected VM vhost-user memory / IOTLB 链路，分析 virtio-iommu、VFIO、MemoryMapperTrait、vhost-user shared memory mapper 与 protected VM 的关系。

    关联路线：protected VM 设备边界与 virtio feature 链路、protected VM block/net/fs 数据路径链路、设备模型与隔离链路函数级分析。

    1. 总览

    flowchart TB Device["PCI virtio / VFIO device"] --> Endpoint["endpoint id"] Endpoint --> Mapper["MemoryMapperTrait"] Guest["guest virtio-iommu MAP/UNMAP"] --> IOMMU["virtio::Iommu"] IOMMU --> Mapper Mapper --> Basic["BasicMemoryMapper"] Mapper --> VFIO["VfioWrapper -> VFIO DMA map"] Vhost["vhost-user/GPU shared memory"] --> Shmem["SharedMemoryMapper"] Shmem --> VmMemory["VmMemoryRequest execute"] VmMemory --> IOMMUClient["optional IOMMU client"]

    crosvm 里有两类容易混淆的 mapper。MemoryMapperTrait 服务 virtio-iommu 的 IOVA 到 GPA/HVA 映射；SharedMemoryMapper 服务设备共享内存区域的 host mapping。

    protected VM 分析必须区分这两类路径。ACCESS_PLATFORM 让 guest driver 知道平台 DMA 受约束，但具体约束由 virtio-iommu、VFIO DMA map、shared memory mapper 和后端能力共同完成。

    2. IOMMU 设备创建入口

    create_iommu_device() 在 src/crosvm/sys/linux/device_helpers.rs:1458-1478 创建 virtio::Iommu。它也使用 virtio::base_features(protection_type)。

    run_vm 主路径在 src/crosvm/sys/linux.rs:2364-2388 调 setup_virtio_access_platform()，随后在有 IOMMU endpoint 或 hotplug isolate 需求时创建 IOMMU device。

    因此 virtio-iommu 也会继承 protected VM 的 base feature，但它真正的价值在于管理 endpoint 的 DMA 映射。

    3. setup_virtio_access_platform

    setup_virtio_access_platform() 在 device_helpers.rs:1671-1714 遍历设备列表。只要 PCI device supports_iommu()，它就为该 endpoint 分配地址并创建 mapper。

    对普通 virtio PCI 设备，这里创建 BasicMemoryMapper::new(u64::MAX)，再通过 create_ipc_mapper() 生成 IpcMemoryMapper，并调用 pci_dev.set_iommu(ipc_mapper)。

    同时，它把 endpoint id 到 MemoryMapperTrait 的映射放入 iommu_attached_endpoints。这些 endpoint 后续会交给 virtio-iommu device。

    这说明普通 virtio 设备接入 virtio-iommu 的方式是 IPC mapper，而不是设备 worker 直接操作 IOMMU。

    4. MemoryMapperTrait 语义

    MemoryMapper trait 定义在 devices/src/virtio/iommu/memory_mapper.rs:176-238。核心接口是 add_map()、remove_map()、get_mask()、supports_detach()、export() 和 release()。

    MemoryMapperTrait 在 240-241 只是把 MemoryMapper + AsRawDescriptors + Any 组合成可存进 endpoint map 的 trait object。

    BasicMemoryMapper 在 112-118 保存 IOVA 到 MappingInfo 的 BTreeMap。MappingInfo 在 37-44 记录 iova、gpa、size 和 protection。

    add_map() 在 265-285 检查 0 size、IOVA/GPA 溢出和 overlap。remove_map() 在 288-320 删除完整覆盖的映射，并在 exported region 被移除时触发 fault。

    export() 在 357-418 把 IOVA range 翻译成一个或多个 MemRegion，并记录 exported range。release() 在 420-442 释放导出记录。

    5. virtio-iommu MAP/UNMAP

    virtio-iommu 的共享状态在 devices/src/virtio/iommu.rs:172-193。它维护 endpoint_map、domain_map、endpoints 和 dmabuf_mem。

    guest ATTACH/DETACH 会维护 endpoint 到 domain 的关系。源码注释在 195-204 强调 detach 后 endpoint 不能再访问该 domain 的 mapping。

    MAP 请求在 iommu.rs:360-461 处理。它验证 range、flags 和 domain，然后把 guest 请求转成 MappingInfo 或 VFIO DMA map。

    普通 GPA path 在 441-446 调 mapper 的 add_map()。dmabuf path 在 434-440 调 mapper 的 vfio_dma_map()，把外部 mmap 区域映射给 endpoint。

    UNMAP 请求在 464-490 调 mapper 的 remove_map()。如果 unmap 会切分已有 mapping，则返回 range error。

    6. virtio-iommu worker 与 translate tube

    IOMMU worker 的 run() 在 iommu.rs:650-690 同时处理 request queue、host command tube 和 translate request tube。

    Iommu::activate() 在 815-860 保存 GuestMemory、endpoint map、hotplug ranges，并启动 v_iommu worker。

    Linux 平台的 handle_translate_request() 在 iommu/sys/linux.rs:179-235 处理 IPC mapper 的 Export、Release 和 StartExportSession 请求。

    这条链用于设备侧请求 IOVA 到 GPA region 的导出。它不是 vhost-user IOTLB 的通用替代，而是 crosvm 自己的 virtio-iommu IPC mapper 机制。

    7. VFIO 容器与 DMA map

    VfioContainer 在 devices/src/vfio.rs:328-343 表示 VFIO container。set_iommu_from() 在 608-617 根据 IommuDevType 选择 Type1、ChromeOS Type1 或 pKVM pvIOMMU。

    传统 VFIO DMA map 在 vfio.rs:400-443 通过 VFIO_IOMMU_MAP_DMA 建立 IOVA 到 user_addr 的映射。unmap 在 449-475。

    pKVM pvIOMMU 与传统 Type1 不同。vfio.rs:412-415 对 IommuType::PkvmPviommu 的 direct DMA map 返回 invalid operation。

    这说明 protected VM 下 VFIO 路径不能默认沿用传统 host userspace mapping 模型；pKVM pvIOMMU 是单独机制。

    8. VfioWrapper

    VfioWrapper 在 devices/src/virtio/iommu/sys/linux/vfio_wrapper.rs:25-31 包装 VfioContainer、group id 和 GuestMemory。

    VfioWrapper::add_map() 在 73-85 先用 GuestMemory::get_host_address_range() 把 GPA 转成 host address，再调用 do_map()。

    do_map() 在 56-70 最终调用 container 的 vfio_dma_map(iova, size, user_addr, write_en)。

    这对普通 VFIO 很直接：guest virtio-iommu MAP 请求最终变成 VFIO container DMA map。对 protected/private memory，这一步是否成立要看 memory 是否可被 host userspace 转成可 DMA 的 HVA。

    supports_detach() 在 118-131 明确返回 false，注释解释 VFIO group 语义无法安全支持单 endpoint detach。

    9. VFIO 设备创建与 endpoint 绑定

    create_vfio_device() 在 device_helpers.rs:1566-1668 创建 VFIO PCI 或 platform device，并给 VFIO device 添加 VmMemoryTube 和 VM control tube。

    PCI VFIO 会提前分配 PCI address 作为 endpoint。device_helpers.rs:1619-1627 对 IommuDevType::VirtioIommu 创建 VfioWrapper。

    NoIommu 和 PkvmPviommu 不返回 VfioWrapper，见 1624-1628。CoIOMMU 则把 endpoint 放入 coiommu endpoint 列表，见 1629-1636。

    create_devices() 主路径在 src/crosvm/sys/linux.rs:929-961 接收 viommu_mapper 后，把 endpoint id 到 wrapper 的映射加入 iommu_attached_endpoints。

    这条链说明 VFIO 接入 virtio-iommu 只发生在 IommuDevType::VirtioIommu 路径。

    10. pKVM pvIOMMU 特殊路径

    KvmVfioPviommu 在 devices/src/vfio.rs:173-309 封装 pKVM pvIOMMU 操作。attach() 在 191-220 把 device、sid index 和 vsid 关联到 pvIOMMU。

    VfioDevice::new_passthrough() 在 vfio.rs:1045-1057 对 IommuDevType::PkvmPviommu 创建 KvmVfioPviommu，查询 SID 数量，并逐个 attach。

    VfioDevice::iommu() 在 1155-1160 目前只报告 IommuDevType::PkvmPviommu。这会影响设备树或平台描述里的 IOMMU 信息。

    ARM64 protected VM 场景下，pKVM pvIOMMU 是重要边界。它不是 VfioWrapper 加 Type1 DMA map，而是通过 KVM/VFIO pvIOMMU ioctl 关联设备。

    11. SharedMemoryMapper 与 vhost-user

    SharedMemoryMapper 定义在 devices/src/virtio/virtio_device.rs:35-51，用于把 VmMemorySource 映射进设备共享内存区域。

    设备可声明 expose_shmem_descriptors_with_viommu()。默认返回 false，见 virtio_device.rs:177-185。

    VirtioPciDevice 在 virtio_pci_device.rs:1098-1116 为 shared memory region 创建设备侧 VmRequester，并调用 device.set_shared_memory_mapper(vm_requester)。

    如果设备要求通过 viommu 暴露 shared memory descriptor，代码会选择 SharedMemoryPrepareType::DynamicPerMapping，见 1103-1111。

    VmRequester::add_mapping() 在 1479-1525 最终通过 VmMemoryClient::register_memory() 注册 source 到已有 PCI BAR allocation。

    12. expose_with_viommu 影响点

    VmMemoryTube 的 expose_with_viommu 字段定义在 device_helpers.rs:131-137。注释指向 virtio device 的 shared memory region viommu 暴露语义。

    设备创建时会把 stub.dev.expose_shmem_descriptors_with_viommu() 放进 VmMemoryTube，见 src/crosvm/sys/linux.rs:1062-1064。

    运行期处理 VmMemoryRequest 时，linux.rs:4923-4939 只有在 expose_with_viommu 为 true 时，才把 iommu_client.as_mut() 传给 request.execute()。

    这说明 IOMMU client 只接入那些显式要求通过 viommu 暴露 shared memory descriptor 的设备路径。

    普通 vhost-user frontend 的 SET_MEM_TABLE 不通过这条路径。它仍然把 guest memory region/fd 直接交给 backend。

    13. GPU / vhost-user GPU

    virtio-gpu 有 shared memory region。devices/src/virtio/gpu/mod.rs:1917-1925 返回 host-visible region，并保存 SharedMemoryMapper。

    expose_shmem_descriptors_with_viommu() 在 gpu/mod.rs:1928-1931 返回 !fixed_blob_mapping，源码注释表示 fixed blob mapping 还未整合。

    vhost-user GPU backend 声明 SHMEM_MAP。vhost_user_backend/gpu.rs:128-133 的 protocol features 包含 BACKEND_REQ、SHMEM_MAP 和 DEVICE_STATE。

    backend 收到 backend request connection 后在 gpu.rs:272-280 保存 conn.shmem_mapper()。这让 backend 能通过 vhost-user backend request 发起 shared memory map/unmap。

    GPU 创建逻辑还会在有 VFIO graphics device 时关闭 fixed blob mapping，见 src/crosvm/sys/linux/gpu.rs:101-120。注释说明它尚不兼容 VFIO dma_buf mapping。

    14. protected VM 边界

    protected VM 下，要区分三种“内存暴露”。

    第一种是普通 virtio descriptor DMA。它依赖 ACCESS_PLATFORM、guest driver 和 SWIOTLB/IOMMU 约束。

    第二种是 VFIO DMA map。传统 Type1 会把 IOVA 映射到 host userspace address；pKVM pvIOMMU 则走独立 attach/config 机制。

    第三种是 vhost-user mem table 或 shared memory map。mem table 是直接把 guest memory fd/host VA 给 backend；shared memory mapper 则只对特定 shared region 走 VmMemoryRequest/IOMMU client。

    因此不能把“有 virtio-iommu”理解成所有 vhost-user backend 都安全。只有走 expose_with_viommu 和 SharedMemoryMapper 的 shared region mapping 才与 IOMMU client 建立联系。

    15. ARM64 与 x86_64 差异

    ARM64 protected VM 重点是 pKVM/pvIOMMU、restricted DMA pool 和 platform IOMMU 描述。IommuDevType::PkvmPviommu 在 VFIO、FDT 和 pKVM attach 路径上都有特殊逻辑。

    x86_64 更常见的是 virtio-iommu/ACPI/VIOT 与 VFIO Type1 组合。源码里 Iommu::new() 只在 x86_64 加 VIRTIO_IOMMU_F_PROBE，见 iommu.rs:757-759。

    vhost-user shared memory mapper 代码本身不按架构分叉，但 protected VM 安全性取决于架构后端能否让外部 backend 只访问可共享区域。

    16. 总结

    crosvm 的 IOMMU/VFIO/memory mapper 体系不是单一机制。virtio-iommu 管 endpoint IOVA；VFIO wrapper 管容器 DMA map；SharedMemoryMapper 管设备 shared memory region。

    protected VM 下，安全边界要按路径判定：普通 virtio descriptor、VFIO passthrough、vhost-user mem table、GPU shared memory map 各自有不同证明要求。

    snapshot/restore 与 protected VM 的交叉边界已继续展开到 protected VM snapshot / restore 边界链路，覆盖 IOMMU、VFIO、vhost-user device state、SharedMemoryMapper 和 ARM64/x86_64 差异。
