    crosvm protected VM 设备边界与 virtio feature 链路

    本文承接 protected VM / pVM firmware 函数级链路，继续分析 protected VM 下设备能力的边界。重点是设备如何继承 ProtectionType、何时声明 VIRTIO_F_ACCESS_PLATFORM，以及哪些路径被禁用或只能谨慎理解。

    关联路线：device-isolation-chain.md、virtio-queue-worker-chain.md、runtime-control-tube-chain.md。

    1. 总览

    flowchart TB PT["Config.protection_type"] --> CLI["CLI policy"] CLI --> Disable["disable USB / RNG"] PT --> Base["virtio::base_features"] Base --> AP["VIRTIO_F_ACCESS_PLATFORM"] PT --> Builders["device builders"] Builders --> Regular["regular virtio devices"] Builders --> KernelVhost["kernel vhost devices"] Builders --> VhostUserFE["vhost-user frontend"] Builders --> VhostUserBE["crosvm vhost-user backend"] PT --> Platform["VFIO platform early mmap"]

    protected VM 下的设备边界不是一个全局 allowlist。源码里有三类机制共同作用：CLI 直接关闭设备、virtio base feature 改变、特定后端或设备路径重解释这个 feature。

    这意味着“设备可用”必须按路径判断。普通 virtio block/net/fs/gpu 继承 cfg.protection_type；vhost-user backend 常用 ProtectionType::Unprotected；平台 VFIO 还要看 guest memory 是否 private。

    2. 全局策略：USB 和 RNG 被关闭

    CLI 解析保护模式时先保证多个 mode 互斥。src/crosvm/cmdline.rs:3016-3024 只允许 --protected-vm、自定义 firmware、无 firmware、unprotected firmware 之一存在。

    cmdline.rs:3027-3048 将这些 flag 转成 ProtectionType。只要不是 ProtectionType::Unprotected，3051-3055 就关闭 cfg.usb 和 cfg.rng。

    这里的判断不是 isolates_memory()，而是“非 Unprotected”。所以 UnprotectedWithFirmware 也会关闭 USB/RNG，即使它主要用于调试 pVM firmware 布局。

    3. 核心开关：base_features

    devices/src/virtio/mod.rs:281-289 是设备侧最核心的分流点。base_features(protection_type) 默认包含 VERSION_1、EVENT_IDX 和 SUSPEND。

    当 protection_type != ProtectionType::Unprotected 时，它额外加入 VIRTIO_F_ACCESS_PLATFORM。这会让 guest virtio driver 知道 DMA 访问受平台约束。

    因此 protected VM 的设备语义主要通过同一个 feature 传播，而不是每个设备各自判断 pVM。

    4. 普通 virtio 设备矩阵

    设备路径 源码证据 protected VM 表现
    virtio-console src/crosvm/sys/linux.rs:384-390 通过 builder 继承 cfg.protection_type
    virtio-block linux.rs:394-400，device_helpers.rs:270-274 regular block 使用 base_features(protection_type)
    virtio-scsi linux.rs:404-408，device_helpers.rs:315-320 继承 base_features(protection_type)
    virtio-pmem linux.rs:412-423，device_helpers.rs:1340-1342 继承 base_features(protection_type)，但涉及 guest memory 映射
    pmem-ext2 linux.rs:426-447，device_helpers.rs:1413-1415 继承 protected feature，同时有 ext2 worker 和 lazy init
    virtio-balloon linux.rs:728-743 继承 cfg.protection_type，还通过 VmMemoryTube 做动态映射
    virtio-net linux.rs:746-750，device_helpers.rs:802-815 tap 或 vhost-net 都从 base_features(protection_type) 开始
    virtio-snd/audio linux.rs:753-767，device_helpers.rs:1548-1552 普通 virtio sound 继承 protected feature
    media/video linux.rs:770-820，device_helpers.rs:1096-1099 adapter/decoder/encoder 按 protection_type 构造
    virtio-vsock linux.rs:823-827，device_helpers.rs:1102-1112 vhost vsock 入口继承 protected feature
    virtio-fs / 9p linux.rs:841-880，device_helpers.rs:1181-1183、1229-1230 共享目录设备继承 protected feature，但 host 文件系统仍是信任边界
    virtio-gpu src/crosvm/sys/linux/gpu.rs:145-156 GPU device 使用 base_features(cfg.protection_type)
    virtio-iommu device_helpers.rs:1458-1470 IOMMU device 自身也继承 protected feature

    这个矩阵只说明 VMM 构造路径如何传递 protected feature，不等价于每个 guest driver、backend 或 host kernel 组合都已验证可用。

    5. vhost-net：guest feature 与 vhost API feature 分离

    NetParameters::create_virtio_device() 在 device_helpers.rs:802-815 先用 base_features(protection_type) 创建 features，再决定走 tap net 还是 kernel vhost-net。

    vhost worker 还有一次重解释。devices/src/virtio/vhost/worker.rs:84-90 如果 guest ack 了 ACCESS_PLATFORM，会在传给 vhost handle 前清掉这个 bit。

    注释解释原因：vhost API 中这个 bit 表示通过 IOTLB API 做地址翻译；如果底层 virtio device 不用 viommu，就不需要让 vhost 做这层翻译。

    所以不能把 guest 看到的 ACCESS_PLATFORM 和 kernel vhost handle 的 feature 完全等同。protected VM 只保证 guest-facing virtio 协议声明了平台访问约束。

    6. vhost-user：frontend 与 backend 要分开看

    crosvm 作为 VMM 连接外部 vhost-user backend 时，create_vhost_user_frontend() 在 device_helpers.rs:400-403 使用 base_features(protection_type)。

    这说明 vhost-user frontend 设备会把 protected feature 暴露给 guest。代码也明确不创建 sandbox，因为 virtqueue handling 已经导出到另一个进程，见 410-413。

    但 crosvm 自己实现的 vhost-user backend 是另一条路径。多个 backend 使用 ProtectionType::Unprotected 生成可用 feature：

    backend 源码证据 结论
    vhost-user net backend devices/src/virtio/vhost_user_backend/net/sys/linux.rs:118-122 backend avail features 不自动带 protected feature
    vhost-user fs backend devices/src/virtio/vhost_user_backend/fs.rs:192-193 backend 使用 unprotected base feature
    vhost-user block backend devices/src/virtio/vhost_user_backend/block/sys/linux.rs:52-54 block backend 使用 unprotected base feature
    vhost-user snd backend devices/src/virtio/vhost_user_backend/snd.rs:96-97 snd backend 使用 unprotected base feature
    vhost-user wl backend devices/src/virtio/vhost_user_backend/wl.rs:112-116 wl backend 使用 unprotected base feature

    因此横向比较时要区分“crosvm 连接一个 backend”和“crosvm 自己作为 backend”。前者继承 VM protection type，后者源码上默认按 unprotected backend 能力建模。

    7. 共享文件系统与 pmem 的边界

    virtio-fs 和 9p 都会继承 base_features(protection_type)，但它们的安全边界不止 virtio feature。create_fs_device() 还会创建 sandbox minijail 或 base jail。

    device_helpers.rs:1170-1178 根据 jail config 创建不同 jail；1181-1183 再用 protected feature 创建 virtio::fs::Fs。

    9p 路径类似。device_helpers.rs:1218-1227 决定 jail/root，1229-1230 用 protected feature 创建设备。

    pmem 更敏感，因为它会把 host fd 或 lazy init memory 映射成 guest 可见区域。device_helpers.rs:1335-1342 创建 pmem memory 和 feature，1413-1415 创建 pmem-ext2。

    所以 protected VM 下的文件共享和 pmem 应分成两层判断：virtio 协议是否声明平台访问约束，以及 host 侧文件/映射路径是否满足隔离目标。

    8. VFIO platform：private memory 触发早映射

    平台 VFIO 设备有额外 protected VM 逻辑。arch/src/sys/linux.rs:149-176 的 generate_platform_bus() 接收 protection_type。

    当 protection_type.isolates_memory() 为 true 时，代码在首次访问前调用 device.regions_mmap_early(vm)。注释说明 private guest memory 不能等第一次访问时再 mmap。

    这条路径和普通 virtio 不同。它不只是加 ACCESS_PLATFORM，而是改变 platform device region 的 mmap 时机。

    9. ARM64 与 x86_64 差异

    ARM64 protected VM 同时有 SWIOTLB/FDT restricted DMA pool、pVM firmware region 和 KVM/Geniezone/Halla/Gunyah 后端检查。设备 DMA 边界更完整。

    x86_64 也会通过 base_features(protection_type) 影响 virtio 设备，但源码中 protected VM 的完整设备隔离链不如 ARM64 清晰，尤其缺少 ARM64 那套静态 SWIOTLB/FDT 表达。

    热插拔 net 设备会继承 protection type。jail_warden.rs:196-200 和 239-253 保存 config.protection_type，pci_hotplug_helpers.rs:31 创建 hotplug net device。

    这说明运行期新增设备也不是“绕过 protected VM”。至少 net hotplug 路径会把 protection type 继续传入 virtio device builder。

    10. 能力边界总结

    crosvm protected VM 设备边界可以概括为：普通 virtio 大多继承 ACCESS_PLATFORM；USB/RNG 在 CLI 层禁用；vhost-user backend 多数按 unprotected feature 建模；platform VFIO 会按 private memory 提前 mmap。

    这不是一个“设备全部安全”的声明。它是 VMM 把 protected mode 传播给设备模型的机制，真正可用性仍取决于 guest driver、host backend、IOMMU/SWIOTLB 和具体 hypervisor 支持。

    block/net/fs 数据路径已继续展开到 protected VM block/net/fs 数据路径链路，覆盖 queue、DescriptorChain、GuestMemory、worker 和后端 I/O。
