crosvm 启动与控制循环函数级分析

本文沿着 crosvm 当前工作树源码，展开 main/run_vm command -> run_config -> setup_vm_components -> run_kvm/run_gunyah/... -> run_vm -> Arch::build_vm -> RunnableLinuxVm -> run_control 这条链路。

目标是弄清楚：crosvm 如何从 CLI config 走到可运行 VM，设备、内存、irqchip 和架构机器描述在哪里组装，ARM64 与 x86_64 的分叉为什么比 Cloud Hypervisor 更早、更散。

相关横向背景：启动路径与控制面跨项目专题分析。

相关横向背景：CPU、中断控制器与机器描述跨项目专题分析。

1. 总体调用链

关键结论：crosvm 的 VM 生命周期不是由一个长期存在的 Vm manager 对象统一封装。Linux 路径中，run_vm() 负责组装资源，Arch::build_vm() 返回 RunnableLinuxVm，随后 run_control() 持有它并进入事件循环。

这和 Cloud Hypervisor 很不同。Cloud Hypervisor 的 Vm 聚合 CpuManager/MemoryManager/DeviceManager；crosvm 的聚合点更偏函数式，运行期状态集中在 RunnableLinuxVm 和 ControlLoopState。

2. run_config：通用准备后按 hypervisor 分发

Linux 主入口是 src/crosvm/sys/linux.rs::run_config(cfg)。它先调用 setup_vm_components(&cfg)，再选择 cfg.hypervisor 或 get_default_hypervisor()：src/crosvm/sys/linux.rs。

get_default_hypervisor() 会先检查 /dev/kvm。ARM64 feature 打开时，还可能检查 Geniezone、Halla、Gunyah 的设备路径：src/crosvm/sys/linux.rs。

机制结论：

  1. crosvm 的平台差异在 hypervisor kind 分发处就出现。
  2. x86_64 主路径基本围绕 KVM。
  3. ARM64 除 KVM 外，还有 Geniezone/Halla/Gunyah 等 feature-gated 后端。

3. setup_vm_components：把 CLI config 转成 VM 构建材料

setup_vm_components() 打开 initrd、pVM firmware、kernel 或 BIOS、pflash 等文件，并根据配置形成 VmComponents：src/crosvm/sys/linux.rs。

ARM64 在这里有额外 CPU 拓扑和频率处理。代码会读取 host CPU capacity、clusters、frequency domain，并构造 vCPU capacity、IPC ratio、domain path 等信息。

机制结论：setup_vm_components() 不是启动 VM，它只是把 CLI 层配置收敛成后续构建 VM 所需的材料。真正的 VM fd、memory slot、irqchip 和设备 bus 都还没创建。

4. run_kvm：创建 KVM VM、guest memory 和 irqchip

run_kvm() 打开 KVM device，创建 arch memory layout，再调用 create_guest_memory() 创建 guest memory：src/crosvm/sys/linux.rs。

随后它创建 KvmVm。x86_64 下如果启用 itmt，还会设置 MSR 平台信息读权限。非 x86_64 下，protected VM 需要额外检查 hypervisor capability。

irqchip 分支体现了架构差异。IrqChipKind::Split 只支持 x86_64，会创建 IOAPIC host/device tube 和 KvmSplitIrqChip。IrqChipKind::Kernel 创建 KvmKernelIrqChip，ARM64 还带 allow_vgic_its 参数。

机制结论：

  1. crosvm 的内存对象先在 run_kvm() 建好，再传给 hypervisor VM。
  2. irqchip 在进入 run_vm() 前已经确定。
  3. x86 split irqchip 是 x86_64 特有路径；ARM64 KVM 更偏 kernel irqchip/GIC 语义。

5. ARM64 其它 hypervisor：同样汇入 run_vm

ARM64 Gunyah 路径和 KVM 类似：打开 Gunyah device，创建 arch memory layout，创建 guest memory，再创建 GunyahVm，最后用 GunyahIrqChip 调用 run_vm()：src/crosvm/sys/linux.rs。

这说明 run_vm() 是后端无关的 Linux VM 组装层。不同 hypervisor 后端先提供 VmArch 和 IrqChipArch，再交给同一个设备和控制循环框架。

能力边界：不同后端是否支持 protected VM、VGIC ITS、pvtime 或特定 device mapping，由后端 VM/irqchip capability 决定，不由 run_vm() 本身保证。

6. run_vm：运行期对象真正组装处

run_vm() 是 crosvm Linux 路径的核心组装函数。它创建 metrics tube、hotplug manager、control socket、VM event tube、SystemAllocator、pstore region、MMIO file mappings、VFIO manager 和 worker process pid 集合：src/crosvm/sys/linux.rs。

create_devices() 在这里被调用。它返回 (BusDeviceObj, Option<Minijail>) 列表，并可通过 add_control_tube 向主循环注册控制 tube：src/crosvm/sys/linux.rs。

随后 run_vm() 分配 PCI 地址，收集 virtio PCI 设备的 bootorder fw_cfg 信息，创建 virtio-iommu 设备，并在 x86_64 下为 PCI 设备生成 ACPI。

机制结论：

  1. crosvm 的设备隔离和控制通道在 VM build 前就已经准备。
  2. SystemAllocator 是设备地址、IRQ、MMIO 分配中心。
  3. run_vm() 是设备、地址、IOMMU、控制 tube 的汇合点。

7. Arch::build_vm：架构机器描述与 vCPU 准备

LinuxArch::build_vm() 是架构相关的 VM 构造接口，返回 RunnableLinuxVm：arch/src/lib.rs。

RunnableLinuxVm 保存运行期所需对象：bus、irqchip、root PCI config、PM、suspend tube、vCPU init、可选 vCPU 对象、hypervisor VM、vm request tubes 等：arch/src/lib.rs。

这就是 crosvm 的运行期聚合对象。它不等价于 Cloud Hypervisor 的 Vm，因为它主要是 run_control() 使用的状态包，而不是创建、boot、pause、migration 的统一 manager facade。

8. x86_64 build_vm：ACPI、IO bus 和 PCI config IO

x86_64 的 build_vm() 会设置 identity map 和 TSS address，保留 PCIe config MMIO range，创建 MMIO bus、IO bus 和 hypercall bus：x86_64/src/lib.rs。

然后它把 PCI 设备从 devs 中分离出来，调用 arch::generate_pci_root() 生成 PCI root、PCI IRQ、AML 等，并插入 PciConfigIo 到 0xcf8 I/O port。

x86_64 路径明显保留传统 PC 语义：I/O port、CMOS、i8042、ACPI、PCI config IO、fw_cfg、pflash 都在这条路径中出现。

9. ARM64 build_vm：payload、FDT、GIC 和 platform devices

ARM64 的 build_vm() 先判断 BIOS/kernel payload，处理 protected VM firmware，然后决定 FDT 放在内存开头、末尾或 payload 后：aarch64/src/lib.rs。

它创建 vCPU 对象，构造 VcpuInitAArch64，初始化 vCPU features、PMU、pvtime，并 finalize irqchip。随后创建 MMIO bus、空 IO bus 和 hypercall bus。

ARM64 也会生成 PCI root，但配置访问走 MMIO PciConfigMmio，并把非 PCI 的 platform devices 分出来。IO bus 在注释中明确说明 ARM 不真正使用，只创建空 bus。

机制结论：

  1. ARM64 的启动核心是 payload 地址、FDT 地址、GIC/irqchip finalize 和 vCPU init。
  2. x86_64 的启动核心是 PC legacy、ACPI、PCI config IO/MMIO 和传统 irqchip。
  3. 两者都最终返回 RunnableLinuxVm，但内部机器描述完全不同。

10. run_control：VM 进入运行态后的串行控制点

run_vm() 最后调用 run_control()。它把 all_control_tubes 拆成 disk、fs、gpu、irq、vm-memory、vm control 等不同通道，并建立 WaitContext：src/crosvm/sys/linux.rs。

收到 VM control tube 事件时，代码构造 ControlLoopState，把 RunnableLinuxVm、config、allocator、设备 control tube、irq/vm-memory handler、vCPU handles、VFIO manager 等引用传入 process_vm_control_event()：src/crosvm/sys/linux.rs。

这说明 run_control() 是运行期管理请求的串行化点。热插拔、suspend、设备控制、外部 control socket 都通过这个循环进入主 VM 状态。

11. ARM64 与 x86_64 差异总结

维度 x86_64 ARM64
hypervisor KVM 主路径 KVM + Geniezone/Halla/Gunyah feature paths
irqchip split/kernel irqchip，split 仅 x86 kernel irqchip/GIC 后端，部分后端自带 irqchip
bus IO bus、MMIO bus、hypercall bus 都有真实用途 MMIO/hypercall 为主，IO bus 基本为空
机器描述 ACPI、PCI config IO/MMIO、CMOS/i8042/fw_cfg FDT、GIC、platform devices、MMIO PCI config
vCPU 创建 通常由 vCPU thread 创建或按 x86 init 数据配置 build_vm() 中显式创建并初始化 vCPU 对象
hotplug PCI hotplug 代码明确 x86_64 主路径 非 x86_64 下 PCI hotplug 有限制
protected VM x86 失败多在 VM 创建时暴露 ARM64 需要 pVM firmware 和 capability 检查

最重要的差异不是“有没有 PCI”，而是平台契约不同。x86_64 以 PC/ACPI/IO port/PCI 为中心；ARM64 以 FDT/GIC/MMIO/platform device 为中心。

12. 能力边界

crosvm 启动链路明确覆盖以下能力：

  1. 从 CLI Config 构造 VmComponents。
  2. 选择 KVM 或 ARM64 特定 hypervisor 后端。
  3. 创建 guest memory、hypervisor VM 和 irqchip。
  4. 创建设备、PCI 地址、IOMMU 和控制 tube。
  5. 调用架构 build_vm() 生成机器描述和 RunnableLinuxVm。
  6. 进入 run_control()，处理 VM 事件、控制请求和子进程退出。

它不直接覆盖以下语义：

  1. 设备 worker 内部的 queue 处理。
  2. ProxyDevice 子进程协议细节。
  3. snapshot 文件格式和保存顺序。
  4. guest 内部驱动、mount、容器 runtime 或平台 sandbox 状态。

这些能力需要沿后续路线继续拆：设备隔离链路、control Tube 协议、snapshot/suspend 链路和 ARM64/x86_64 机器描述细节。
