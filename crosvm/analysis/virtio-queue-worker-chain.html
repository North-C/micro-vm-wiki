    crosvm virtio Queue 与 Worker 链路函数级分析

    本文继续展开 设备模型与隔离链路函数级分析。

    焦点是 crosvm 的 virtio 设备如何从 guest driver 配置 queue，进入 PCI transport 激活，再由 block/net worker 消费 descriptor，最后写 used ring 并触发 interrupt。

    结论只来自当前仓库源码。

    1. 核心结论

    crosvm 的 virtio 设备分为 transport 层和 device worker 层。VirtioPciDevice 负责 PCI BAR、common config、MSI-X、ioeventfd 和 queue 激活。

    具体设备实现 VirtioDevice。它接收已经激活的 Queue、GuestMemory 和 Interrupt，然后自行启动 worker 或异步任务。

    guest kick queue 时，常规路径是 hypervisor ioeventfd 直接 signal queue event。若 ioevent 尚未注册，write_bar() 有一个 MMIO fallback，会手动 signal 对应 queue event。

    worker 消费 descriptor 后调用 Queue::add_used*() 写 used ring，再调用 Queue::trigger_interrupt()。是否真的注入中断由 queue 的 event index/flag 逻辑决定。

    这和 Firecracker 的 virtio worker 模型相似：transport 只负责 doorbell 和 interrupt，设备 worker 负责语义 I/O。

    2. 总体流程图

    flowchart TD Guest["guest virtio driver"] --> Config["common config writes"] Config --> QCfg["QueueConfig"] Config --> Ready["driver ready"] Ready --> Activate["VirtioPciDevice::activate"] Activate --> Ioevent["register_io_event notify BAR"] Activate --> Queue["QueueConfig::activate"] Queue --> DevAct["VirtioDevice::activate"] DevAct --> Worker["device worker"] Guest --> Kick["queue notify"] Kick --> Ioevent Ioevent --> Event["Queue event"] Event --> Worker Worker --> Used["Queue::add_used"] Used --> Intr["Queue::trigger_interrupt"] Intr --> Guest

    这个图的关键是两次 activate。transport 先把 QueueConfig 变成 active Queue，然后把 active queues 交给具体设备。

    3. VirtioDevice Trait

    VirtioDevice 是具体 virtio 设备的核心 trait：devices/src/virtio/virtio_device.rs。

    它暴露 device type、queue max sizes、features、config read/write、reset 和 activate()。

    activate(mem, interrupt, queues) 是设备开始真实处理 I/O 的边界。传入的 queues 已经是 active queue，不再是配置态 QueueConfig。

    trait 还定义 virtio_sleep()、virtio_wake()、virtio_snapshot() 和 virtio_restore()。这让 virtio queue 状态能参与 suspend/snapshot。

    4. VirtioPciDevice 构造

    VirtioPciDevice::new() 为每个 device queue 创建 QueueEvent，并按 device.queue_max_sizes() 创建 QueueConfig：devices/src/virtio/virtio_pci_device.rs。

    它还创建 MSI-X config。MSI-X vector 数量是 queue interrupt 数量加 1，额外的一个 vector 用于 config change。

    因此 PCI transport 在设备激活前已经知道 queue 数量和最大 queue size，但 queue 的 desc/avail/used 地址还要等 guest driver 写 common config。

    5. Common Config 写入 QueueConfig

    VirtioPciCommonConfig 表示现代 virtio PCI common config：devices/src/virtio/virtio_pci_common_config.rs。

    guest 写 driver feature 时，write_common_config_dword() 会调用 device.ack_features()，并让每个 QueueConfig 也 ack features。

    guest 写 queue desc、avail、used 地址时，common config 会更新当前 queue_select 指向的 QueueConfig。

    guest 写 queue enable 会把配置态 queue 标为 ready。此时 queue 还没有变成 worker 可用的 active queue。

    6. Driver Ready 触发 Transport Activate

    VirtioPciDevice::write_bar() 处理 common config、ISR、device config、notification 和 MSI-X 区域写入：devices/src/virtio/virtio_pci_device.rs。

    每次 BAR 写入后，如果设备尚未 activated 且 is_driver_ready() 为 true，就调用 self.activate()。

    这说明 crosvm 不在 queue ready 的瞬间立刻启动设备，而是在 driver status 达到 ready 条件后统一激活。

    如果 driver 后续请求 reset，write_bar() 会调用具体设备的 reset()，成功后把 device_activated 置 false。

    7. VirtioPciDevice::activate

    VirtioPciDevice::activate() 先创建 Interrupt，保存到自身，并启动 PCI interrupt resample worker：devices/src/virtio/virtio_pci_device.rs。

    然后它计算 notification BAR base。对每个 ready queue，它注册 ioevent：guest 写 notify BAR 时，hypervisor 会 signal 这个 queue event。

    随后它调用 QueueConfig::activate(&mem, queue_evt, interrupt.clone())，把配置态 queue 转成 active Queue。

    最后它调用具体设备的 device.activate(mem.clone(), interrupt, queues)。如果失败，driver status 会被标记为 NEEDS_RESET。

    8. Notification Fallback

    正常情况下，queue notify 由 hypervisor 的 ioevent 处理，不会进入 write_bar()。

    但 write_bar() 对 notification BAR 有 fallback：devices/src/virtio/virtio_pci_device.rs。

    如果 ioevent 注册尚未完成，guest 的 notify 写可能仍以 MMIO exit 进入 VMM。此时代码按 offset 计算 queue index，并 signal 对应 QueueEvent。

    这个 fallback 保证激活窗口期不会丢 queue kick。

    9. QueueConfig 到 Queue

    QueueConfig 保存 max size、size、ready、vector、features、acked features、desc table、avail ring、used ring、next_avail 和 next_used：devices/src/virtio/queue.rs。

    QueueConfig::activate() 要求 queue ready 且尚未 activated：devices/src/virtio/queue.rs。

    如果 negotiated features 包含 VIRTIO_F_RING_PACKED，它创建 PackedQueue。否则创建 SplitQueue。

    因此 split/packed 差异在 active queue 创建时确定。具体设备 worker 通过 Queue enum 使用统一接口。

    10. Queue 的统一接口

    Queue enum 包装 SplitQueue 和 PackedQueue：devices/src/virtio/queue.rs。

    worker 可以调用 pop() 获取 descriptor chain，调用 add_used() 或 add_used_with_bytes_written() 写 used ring。

    next_async() 会先尝试 pop()，没有 descriptor 时等待 queue event。异步 block worker 使用类似模式。

    trigger_interrupt() 会分派到 split 或 packed queue。它返回 bool，表示本次是否真的向 guest 注入 interrupt。

    11. SplitQueue 机制

    SplitQueue 保存 guest memory、queue event、interrupt、size、MSI-X vector、desc/avail/used ring 地址和 next indices：devices/src/virtio/queue/split_queue.rs。

    SplitQueue::new() 校验 queue size 必须是 2 的幂，并检查 desc/avail/used ring 地址和大小不会溢出。

    peek() 从 avail ring 读取 avail index。如果没有新 descriptor，返回 None。有 descriptor 时，它读取 ring entry 并构造 DescriptorChain。

    trigger_interrupt() 先调用 queue_wants_interrupt()。若需要通知 guest，它更新 last_used，并调用 interrupt.signal_used_queue(vector)。

    12. PackedQueue 机制

    PackedQueue 保存 desc table、device event suppression、driver event suppression，以及 avail/use/signalled indices：devices/src/virtio/queue/packed_queue.rs。

    peek() 读取当前 avail index 对应的 packed descriptor，并检查 descriptor 的 available bit。

    add_used_with_bytes_written_batch() 写回 len、id 和 flags。flags 最后写入，并使用 release fence，避免 guest 看到部分更新。

    Packed queue 与 split queue 的 ring 布局不同，但上层 worker 仍通过 Queue 接口处理。

    13. Interrupt 路径

    Interrupt::signal(vector, status_mask) 根据 transport 分流：devices/src/virtio/interrupt.rs。

    PCI transport 下，如果 MSI-X 启用且 vector 有效，则触发 MSI-X。否则它更新 ISR interrupt status，并触发 level irq event。

    MMIO transport 使用 edge irq event。vhost-user transport 使用 call event。

    signal_used_queue() 只是以 INTERRUPT_STATUS_USED_RING 调用 signal()。signal_config_changed() 则使用 config change vector 或 transport 特定路径。

    14. Block Async Worker

    BlockAsync::activate() 遍历 active queues，并对每个 queue 调用 start_queue()：devices/src/virtio/block/asynchronous.rs。

    start_worker() 会创建名为 virtio_blk 的 worker thread，在线程中创建 async executor、async disk 和 worker state。

    worker 主循环 run_worker() 同时处理 control tube、flush timer、kill event 和 queue start/stop 命令。

    收到 WorkerCmd::StartQueue 后，它为该 queue 创建 handle_queue() future，并用 queue event 的 async wrapper 等待 guest kick。

    15. Block Queue 处理

    handle_queue() 等待 queue event，同时推进后台 I/O task：devices/src/virtio/block/asynchronous.rs。

    收到 event 后，它循环 queue.pop()，把每个 descriptor chain 交给 process_one_chain()。

    process_one_chain() 调用 process_one_request() 执行读写、discard、write zeroes、flush、get id 等 block 请求。

    完成后，它写 virtio-blk status byte，调用 queue.add_used_with_bytes_written()，然后调用 queue.trigger_interrupt()。

    这条链路是典型的 guest kick -> descriptor -> host I/O -> used ring -> interrupt。

    16. Net Worker

    Net::activate() 根据 negotiated features 判断 multi-queue 和 control queue，校验 queue 数量和 tap 数量：devices/src/virtio/net.rs。

    queues 按 rx0, tx0, rx1, tx1, ..., ctrl 排列。每个 vq pair 会取一个 TAP，并启动一个 v_net:{i} worker thread。

    Worker::run() 用 WaitContext 同时等待 TAP read notifier、rx queue event、tx queue event、ctrl queue event 和 kill event。

    Tx queue event 触发 process_tx()，把 guest 发送的 packet 写到 TAP。RxTap/RxQueue 分支则把 TAP packet 放进 guest 提供的 rx buffers。

    control queue 处理完成后会 ctrl_queue.add_used() 并 ctrl_queue.trigger_interrupt()。

    17. Sleep、Wake 与 Snapshot

    VirtioDevice::virtio_sleep() 的设计要求设备停止处理并交还 queues。virtio_wake() 可用交还的 queues 重新启动处理。

    VirtioPciDevice::snapshot() 要求设备处于 sleep 状态。它保存 PCI config、inner device snapshot、interrupt、MSI-X、common config、queue config 和 activated queues。

    restore() 目前不支持从已经 activated 的设备状态直接恢复。源码明确在 device_activated 为 true 时失败：devices/src/virtio/virtio_pci_device.rs。

    如果 snapshot 中有 activated queues，restore 会在 sleep state 中重建 active Queue，供后续 wake 使用。

    18. ARM64 与 x86_64 差异

    virtio queue、worker、split/packed queue 和 device activate 逻辑本身基本不按架构分叉。

    差异主要在 transport 接入和中断/电源语义。x86_64 PCI 路径额外带 PmWakeupEvent，Interrupt::new() 和 resample/wakeup 处理有 x86_64 条件编译。

    ARM64 更常见 MMIO/platform bus 或 FDT 设备描述路径，但具体 virtio device worker 仍通过同一套 Queue 和 Interrupt 抽象消费 descriptor。

    因此 crosvm 的 ARM64/x86_64 差异不在 block/net worker 内部，而在 queue 如何暴露给 guest、interrupt 如何送达和设备如何被枚举。

    20. 与 Firecracker 的对照

    Firecracker 的 virtio-mmio/virtio-pci transport 也把 queue notify 转成 device event，再由设备线程处理 descriptor。

    crosvm 的差异在于设备可能通过 ProxyDevice 放进 Minijail 子进程。此时父进程看到的是 bus proxy，而真实 virtio worker 在设备进程内运行。

    对照 Firecracker，应把 crosvm 分成两层看：virtio transport/queue 机制是一层，process-per-device 隔离模型是另一层。
