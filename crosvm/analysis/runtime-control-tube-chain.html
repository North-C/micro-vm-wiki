crosvm 运行期控制与 Tube 分发链路

本文从源码解释 crosvm 运行中的 VM 如何接收外部控制请求，如何把请求分发到 VM、设备、balloon、hotplug 和内存映射路径。

相关路线：crosvm 深入路线。

相关链路：启动与控制循环函数级分析。

相关链路：Snapshot 与 Suspend 函数级分析。

相关横向专题：运行期控制面与热插拔跨项目专题分析。

1. 核心结论

crosvm 没有像 Cloud Hypervisor 那样把运行期控制抽象成独立 VMM API thread。Linux 主路径进入 run_control 后，依靠 WaitContext 监听 VM event、control socket、Tube、signal、balloon response 和 registered event。

外部命令的普通路径是 Unix seqpacket socket 到 Tube，再反序列化为 VmRequest。这条路径由 vm_control::handle_request 发起，服务端在 run_control 中把新连接包装成 TaggedControlTube::Vm。

process_vm_request 是运行期状态变更的关键分流点。它先处理 exit、hotplug、registered event、balloon、vCPU pid/tid、throttle、memory register 等特殊路径，再把普通请求交给 VmRequest::execute。

热插拔能力不是所有架构等价。VFIO PCI hotplug 的主处理函数只在 x86_64 编译，非 x86_64 对 HotPlugVfioCommand 返回 Ok。网络 hotplug 还受 pci-hotplug feature 约束。

ARM64 更显式的差异出现在 pvclock 恢复路径。send_pvclock_cmd 在 aarch64 上可能返回 SetCounterOffset，随后由 VM 执行 counter offset 设置。

2. 总体控制路径

这张图的重点是“控制入口”和“执行入口”分离。run_control 只负责事件监听和状态容器组装，真正解释 VmRequest 语义的是 process_vm_request 与 VmRequest::execute。

3. 外部 control socket 到 VmRequest

客户端侧入口在 vm_control/src/sys/linux.rs。handle_request 连接 control socket，把 socket 转成 Tube，发送 VmRequest，再等待 VmResponse。

关键证据：vm_control/src/sys/linux.rs。

服务端侧在 run_control 监听 control_server_socket。当 Token::VmControlServer 触发时，它 accept 新连接，把 socket 包装成 TaggedControlTube::Vm(Tube::try_from(socket))，并注册到 wait_ctx。

关键证据：src/crosvm/sys/linux.rs。

因此 crosvm 的控制协议不是 HTTP API，也不是长期固定的一条命令管道。它是“一次连接一个 Tube”，再由主控制循环统一监听。

4. AnyControlTube 的拆分

AnyControlTube 是运行期控制 Tube 的类型擦除入口，枚举了 Balloon、Disk、Fs、Gpu、IrqTube、PvClock、Snd、Vm、VmMemoryTube、VmMsync 等类别。

关键证据：vm_control/src/any_control_tube.rs。

run_control 启动时遍历 all_control_tubes。其中 Vm、VmMsync、Fs 会变成 TaggedControlTube 并进入主 wait loop。

Disk、Gpu、Snd、PvClock、Balloon 等保留为专门的 host tube。它们不会全部走 TaggedControlTube::Vm，因为响应模式和目标设备不同。

关键证据：src/crosvm/sys/linux.rs。

这个拆分解释了 crosvm 的控制面边界：不是所有控制都进入同一个请求枚举。某些设备有自己的 tube，只在需要 VM 全局状态时才回到主 loop。

5. run_control 监听什么

run_control 定义的 token 包括 VmEvent、Suspend、ChildSignal、VmControlServer、VmControl{id}、RegisteredEvent 和 BalloonTube。

启动时它把 VM event、suspend tube、SIGCHLD、registered event、已有 control tubes、control socket 和 balloon tube 注册到同一个 WaitContext。

关键证据：src/crosvm/sys/linux.rs。

这意味着 crosvm 把运行期管理收敛到单个事件循环。外部请求、设备上报、guest suspend、子进程退出和 balloon 异步响应都会在这里被串行处理。

6. ControlLoopState 的含义

ControlLoopState 是 process_vm_request 的运行期上下文包。它不是 VM 本体，而是 control loop 在处理一次请求时需要借用的一组状态。

它包含 RunnableLinuxVm、config、allocator、control tubes、device control tube、irq/vm-memory handler、hotplug manager、swap controller、vCPU handles、pvclock tube、VFIO manager 等。

关键证据：src/crosvm/sys/linux.rs。

这个结构解释了为什么 process_vm_request 能同时影响 VM、vCPU、设备、内存、hotplug 和 snapshot。它拿到的是运行中 VMM 的横切状态。

7. process_vm_control_event 三路分发

process_vm_control_event 按 TaggedControlTube 类型分发。

TaggedControlTube::Vm 接收 VmRequest，调用 process_vm_request，如果返回 VmResponse 就通过原 tube 发回客户端。

TaggedControlTube::VmMsync 接收 VmMemoryMappingRequest，直接在 state.linux.vm 上执行。

TaggedControlTube::Fs 接收 FsMappingRequest，使用 VM 和 allocator 执行文件系统映射请求。

关键证据：src/crosvm/sys/linux.rs。

所以 VmRequest 不是唯一运行期协议。VM 内存映射和 fs 映射被分成专门类型，避免把所有控制语义压进同一个 enum。

8. process_vm_request 的特殊路径

process_vm_request 先创建三个输出集合：要移除的 control ids、新增 TaggedControlTube、新增 irq/vm-memory handler tubes。

它内部的 add_control_tube 会把 Fs、Vm、VmMsync 放回主 control loop，把 IrqTube 和 VmMemoryTube 转交给对应 handler。

关键证据：src/crosvm/sys/linux.rs。

特殊请求包括：

请求 处理位置 语义
Exit process_vm_request 返回响应并要求 control loop 退出
HotPlugVfioCommand process_vm_request x86_64 调用 VFIO hotplug，非 x86_64 返回 Ok
HotPlugNetCommand process_vm_request pci-hotplug feature 下调用 net hotplug manager
BalloonCommand process_vm_request 通过 BalloonTube 异步或同步转发
RegisterMemory process_vm_request 调用 vm-memory control client 注册内存
UnregisterMemory process_vm_request 调用 vm-memory control client 注销内存
Throttle process_vm_request kick 指定 vCPU 后不立即回响应

普通请求最后进入 VmRequest::execute。这一层保留了对 PM、vCPU、设备控制、snapshot、swap、disk/gpu/usb/snd tube 的操作。

9. VmRequest::execute 覆盖什么

VmRequest 定义在 vm_control/src/lib.rs，包括 power、sleep、RTC、suspend/resume vCPU、swap、GPE/PME、balloon、disk、GPU、USB、VFIO/net hotplug、snapshot、listener、VM suspend/resume、throttle、memory register 等。

关键证据：vm_control/src/lib.rs。

VmRequest::execute 处理 power button、sleep button、RTC、GPE、PME、vCPU suspend/resume、swap、VM suspend/resume、disk/gpu/usb/battery/snd 转发、snapshot、VM descriptor 等。

关键证据：vm_control/src/lib.rs。

这里要注意两个边界。Balloon 在 execute 中是不可达路径，因为已经由 process_vm_request 处理。RegisterMemory/UnregisterMemory 也在进入 execute 前完成。

10. BalloonTube 的异步响应

Balloon 命令不是简单的一问一答。BalloonTube 持有 pending queue 和 pending adjust completion，用来处理需要等待 completion 的 adjust 请求。

关键证据：vm_control/src/balloon_tube.rs。

process_vm_request 调用 balloon_tube.send_cmd(cmd, Some(id))。如果没有立即响应，control loop 等待 Token::BalloonTube，收到结果后再根据保存的 control tube id 发回对应客户端。

关键证据：src/crosvm/sys/linux.rs。

这说明 crosvm 的 control loop 不只处理同步 RPC。它也承担异步响应复用，保证设备响应能回到原始控制连接。

11. 热插拔链路

VFIO hotplug 的 x86_64 主路径从 process_vm_request 进入 handle_hotplug_command，再根据 Add/Remove 调用 add_hotplug_device 或 remove_hotplug_device。

关键证据：src/crosvm/sys/linux.rs。

add_hotplug_device 会解析 host PCI 地址，寻找 hotplug bus，创建 PCIe bridge 或 VFIO endpoint，必要时通知 virtio-iommu，并调用 bus 的 hot_plug。

关键证据：src/crosvm/sys/linux.rs。

remove_hotplug_device 会定位 hotplug key，必要时通知 virtio-iommu 删除设备，执行 hot_unplug，释放 allocator 中的 PCI 资源，并递归移除 bridge。

关键证据：src/crosvm/sys/linux.rs。

网络 hotplug 在 pci-hotplug feature 下走 handle_hotplug_net_command。新增 TAP 时会创建 irq tube、vm-memory tube 和 vm tube，然后交给 PciHotPlugManager。

关键证据：src/crosvm/sys/linux.rs。

热插拔可能返回新的 control tubes。run_control 会把普通 VM/Fs/Msync tube 注册回 wait_ctx，把 irq/vm-memory tube 发送给对应 handler。

12. 设备控制 worker 边界

设备睡眠、唤醒、snapshot、restore 和状态查询通过 DeviceControlCommand 表达，包括 SleepDevices、WakeDevices、SnapshotDevices、RestoreDevices、GetDevicesState、Exit。

关键证据：vm_control/src/lib.rs。

create_devices_worker_thread 创建 device_control 线程并进入 handle_command_tube。它维护设备状态，调用 bus 的 sleep/wake/snapshot/restore 方法，并通过 VmResponse 返回结果。

关键证据：devices/src/lib.rs。

这条 worker 边界是 crosvm snapshot/suspend 的关键支撑。完整快照链路已经在 Snapshot 与 Suspend 函数级分析 展开。

13. s2idle 与 pvclock

process_vm_request 对 SuspendVcpus 有额外 s2idle 分支。开启 force s2idle 时，它会启动 trigger_vm_suspend_and_wait_for_entry，等待 guest 进入 suspend，再发送原始响应。

关键证据：src/crosvm/sys/linux.rs。

pvclock 路径由 send_pvclock_cmd 处理。aarch64 上该函数可能返回 PvClockAction::SetCounterOffset，随后 process_vm_request 调用 VM 设置 counter offset。

关键证据：src/crosvm/sys/linux.rs。

这解释了 ARM64 在运行期控制里的一个具体差异：恢复虚拟时间不只是发送 pvclock 命令，还可能需要调整架构计数器偏移。

14. ARM64 与 x86_64 差异

主题 x86_64 ARM64 / 非 x86_64
VFIO PCI hotplug 调用 handle_hotplug_command HotPlugVfioCommand 返回 Ok，主处理函数不编译
网络 hotplug 依赖 pci-hotplug feature 和 PCI hotplug manager 同样受 feature 约束，但平台 PCI 能力要看具体配置
pvclock resume 发送 pvclock command 可能返回 SetCounterOffset 并设置 counter offset
设备枚举背景 PCI/ACPI 更中心 FDT/MMIO/GIC 更常见，PCI hotplug 不应默认可用
控制面模型 Tube/control loop Tube/control loop 相同

结论是：控制面框架本身跨架构一致，差异主要出现在“请求能否真正改变硬件拓扑”和“恢复时间状态需要哪些架构动作”。

15. 能力边界

能力 crosvm 支持方式 边界
运行期关闭 VM VmRequest::Exit 退出由 control loop 驱动，随后停止 vCPU 和设备 worker
电源按钮/睡眠按钮 VmRequest::execute 调 PM 依赖平台 PM 设备是否存在
vCPU suspend/resume kick vCPU state 需要设备状态与 guest suspend 流程配合
设备 snapshot device worker + Suspendable 设备必须实现相应状态保存
VFIO hotplug x86_64 PCI hotplug 非 x86_64 不走主实现
Balloon BalloonTube 存在异步 completion 和 pending 队列
动态内存注册 vm-memory control client 需要 range 校验和 handler tube 支持

所以 crosvm 的能力边界不是“是否有 VmRequest variant”。真正边界取决于 control loop 是否有状态对象、设备 worker 是否支持、架构代码是否编译、feature 是否启用。

16. 后续调试路线

  1. 从 vm_control::handle_request 开始，确认客户端发送的 VmRequest 和期望的 VmResponse。
  2. 进入 run_control，看该请求对应的 tube 是否注册到了 WaitContext。
  3. 进入 process_vm_control_event，确认它属于 Vm、VmMsync 还是 Fs。
  4. 进入 process_vm_request，先排查是否被特殊路径截获。
  5. 如果进入 VmRequest::execute，继续追踪 PM、vCPU closure、device control tube 或具体设备 host tube。
  6. 如果涉及 hotplug，先确认目标架构、pci-hotplug feature、hotplug manager 和新 tubes 注册。

这条路线能避免直接从 VmRequest enum 猜能力。它要求每个结论都落到“谁收请求、谁持有状态、谁执行副作用、谁返回响应”四个问题上。
