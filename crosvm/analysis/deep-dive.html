crosvm 深入探索文档

本文档从当前仓库源码出发，建立对 crosvm 的系统性理解：它为什么是“强隔离、多设备、跨平台”的 VMM，process-per-device 如何影响架构，控制 socket 如何组织 VM 状态操作，以及 ARM64 与 x86_64 设备/中断/沙箱策略如何分叉。

当前版本：第 2 版
源码基线：crosvm 仓库，commit afafee6ae
阅读方式：先看顶层定位，再沿 CLI/Config -> run_config -> Arch::build_vm -> create_devices -> ProxyDevice/Minijail -> control loop 展开。

0. 问题地图

  1. crosvm 与 Firecracker、Cloud Hypervisor 的定位差异是什么？
  2. 为什么 crosvm 采用 process-per-device？
  3. 设备 fork 到 sandboxed process 后如何与主进程通信？
  4. VM control socket 解决哪些全局 VM 操作？
  5. virtio、PCI、Bus/BusDevice、ProxyDevice 如何组合？
  6. snapshot/restore 如何跨 vCPU、设备、IRQ handler 和控制 loop 协调？
  7. ARM64 与 x86_64 在设备、seccomp policy、中断模型上有什么差异？
  8. crosvm 的能力边界是什么，为什么它不是极简 microVM？

1. 一句话定位

crosvm 是一个安全、轻量、高性能的 Rust VMM，最初为 ChromeOS Linux/Android guest 设计，后来扩展到 Android、Cuttlefish 和 Windows 等场景。它的核心设计不是“最小化设备”，而是“把设备面做宽，同时用强隔离控制风险”。

源码和文档依据：

  • README 将 crosvm 定义为 secure、lightweight、performant VMM，并说明它最初用于 ChromeOS Crostini/ARCVM：README.md。
  • README 列出核心哲学：每个虚拟设备可以运行在自己的 sandboxed process 中，使用 namespace、seccomp、Minijail：README.md。
  • 架构文档把 crosvm 的首要特征列为 process per virtual device、Minijail、支持多 CPU 架构/OS/hypervisor、Rust 安全：ARCHITECTURE.md。

2. 顶层架构

架构文档给出典型 session：main.rs 解析命令行构造 Config，run_config 加载 kernel、创建控制 socket、调用架构相关 Arch::build_vm、创建 PCI/virtio 设备和 Minijail 配置，最后在 RunnableLinuxVm 中运行 vCPU 和控制 loop：ARCHITECTURE.md。

3. 能力边界

维度 crosvm
目标场景 ChromeOS、Android、Cuttlefish、client-like VM、untrusted code
设备面 virtio-net/block/gpu/snd/fs/9p、TPM、pmem、video、balloon、vsock 等
隔离策略 process-per-device + Minijail + seccomp + namespaces + capabilities
Hypervisor backend Linux/Android KVM/Gunyah/GenieZone/Halla，Windows WHPX/HAXM
架构 x86_64、aarch64、riscv64
与 Firecracker 差异 更宽设备面，更复杂 IPC/进程模型，不追求最小 microVM 边界

README 的设备列表显示 crosvm 覆盖 network、storage、graphics、display/input、audio、fs、console、rng、balloon、vsock、TPM、pmem、video decoder/encoder 等：README.md。

4. run_config 与 run_vm：真实启动主线

run_config() 是 Linux 侧的主入口。它先把 CLI 配置转换成 VmComponents，再选择 hypervisor backend，最后进入 KVM/Gunyah/GenieZone/Halla 等具体 backend 的 run_* 路径：src/crosvm/sys/linux.rs。

源码依据：

  • setup_vm_components() 打开 kernel/bios/initrd/pflash 等镜像，处理 protected VM firmware、swiotlb、fw_cfg、CPU topology/capacity/frequency 等，最后构造 VmComponents：src/crosvm/sys/linux.rs。
  • run_vm() 创建 metrics tube、hotplug manager、control socket、system allocator、VFIO container manager，然后调用 create_devices() 得到设备集合：src/crosvm/sys/linux.rs 和 src/crosvm/sys/linux.rs。
  • 设备创建后，x86_64 会创建纯虚拟 PCIe root port，随后 arch::assign_pci_addresses() 分配 PCI 地址，生成 boot order fw_cfg blob，必要时创建 virtio-iommu 设备：src/crosvm/sys/linux.rs。
  • Arch::build_vm() 是架构分叉点。它接收 components、VM handle、irqchip、devices、serial jail、battery、DT overlay 等，返回 RunnableLinuxVm：src/crosvm/sys/linux.rs。
  • RunnableLinuxVm 包含 io_bus、mmio_bus、hypercall_bus、irq_chip、root_config、vCPU init、vCPU handles、VM request tubes、设备控制线程等运行态对象：arch/src/lib.rs。

这个路径说明 crosvm 的“VM 创建”不是集中在单个 Vm::new。它是 VmComponents、设备集合、架构实现和 control loop 共同拼出来的。

5. Process-per-device 与 Minijail

设备创建时会被包装为 ProxyDevice，内部 fork 但不 exec，然后进入 Minijail；主进程丢弃设备本体，只通过 proxied BusDevice trait、guest memory shared mapping 和允许的 FD 与设备交互：ARCHITECTURE.md。

沙箱策略由 jail crate 的 create_sandbox_minijail 创建，使用 namespace 和 seccomp。seccomp policy 位于 jail/seccomp/{arch}/{device}.policy，部分设备策略按架构不同拆分：ARCHITECTURE.md。

hotplug 场景还有一个专门的 JailWarden。它本身可以运行在 sandbox 中，接收 JailCommand::ForkDevice(ResourceCarrier)，在 worker 进程内创建真实设备并返回 ProxyDevice 所需的 ChildProcIntf：src/crosvm/sys/linux/jail_warden.rs。

JailWardenImpl::new() 会保留 syslog/tracing/metrics/tube 等必要 FD，根据 jail_config 创建 sandbox minijail 或 base minijail，然后 fork 出 “jail warden” worker：src/crosvm/sys/linux/jail_warden.rs。make_proxy_device() 向 worker 发送 ForkDevice，收到 ForkDeviceOk 后把 ChildProcIntf 转为 ProxyDevice：src/crosvm/sys/linux/jail_warden.rs。

因此 crosvm 的隔离是两层：

  1. 启动期设备可以直接通过 Minijail/ProxyDevice 沙箱化。
  2. VM 运行后的 hotplug 设备通过 JailWarden 代为 fork 和创建，避免主控制线程在运行期随意打开隔离边界。

6. 控制 Tube 与主循环

crosvm 的 VM control socket 用于设备需要操作全局 VM 状态的场景，例如 guest memory mapping、MSI route、VM memory registration 等。架构文档强调不同类型的请求/响应走不同 socket，以降低设备被攻破后的权限扩大风险：ARCHITECTURE.md。

外部 --socket 也是 VM control socket 的一种，但协议内部且不稳定，推荐通过 crosvm stop 或 crosvm_control 使用：ARCHITECTURE.md。

源码中这个分流由 AnyControlTube 明确表达：Balloon、Disk、Fs、Gpu、IrqTube、PvClock、Snd、Vm、VmMemoryTube、VmMsync 都是不同控制面入口：vm_control/src/any_control_tube.rs。

process_vm_control_event() 从 TaggedControlTube::Vm 收到 VmRequest 后调用 process_vm_request()，再把 VmResponse 发回 tube；如果请求表示退出，则让 control loop 退出：src/crosvm/sys/linux.rs。process_vm_request() 直接处理 Exit、hotplug、balloon、VcpuPidTid、Throttle、RegisterMemory/UnregisterMemory 等请求；其他请求统一交给 VmRequest::execute()：src/crosvm/sys/linux.rs。

这个分层和 Cloud Hypervisor 的 VMM thread 不同：Cloud Hypervisor 把 API 请求闭包送入 VMM event loop；crosvm 则维护多类 Tube，并在 control loop 中按 Tube 类型和 request 类型分发。

7. 设备模型：Bus、BusDevice、PCI 与 virtio

Bus/BusDevice 是设备模型根。VCPU 对 MMIO/PIO 地址读写时，Bus 查找对应 BusDevice 并转发访问：ARCHITECTURE.md。

PCI 通过 PciConfigIo/PciConfigMmio 适配到 PciRoot。ARM 使用 MMIO config，x86_64 使用 I/O port config：ARCHITECTURE.md。

大多数 virtio 设备实现 VirtioDevice trait。activate 在 guest driver 完成配置后被 transport 调用，设备通常在这里启动 worker thread 处理 virtio queues 和中断：ARCHITECTURE.md。

源码依据：

  • BusDevice trait 表示能响应任意地址空间读写的设备，同时继承 Suspendable，因此 bus 级设备天然进入 snapshot/sleep/wake 体系：devices/src/bus.rs。
  • Bus 用 BTreeMap<BusRange, BusEntry> 管理地址范围，要求同一地址空间中的设备范围不能重叠：devices/src/bus.rs。
  • create_devices() 会处理 VFIO、coIOMMU、virtio 设备、vhost-user、GPU/audio/video/fs 等设备，并把需要主控能力的 tube 通过 add_control_tube() 注册回 control loop：src/crosvm/sys/linux.rs。
  • create_virtio_devices() 从 Config 中展开各种 virtio 设备，返回 VirtioDeviceStub，后续会被 transport 包成 PCI/MMIO 设备：src/crosvm/sys/linux.rs。
  • VirtioDevice trait 定义了 virtio transport 与设备的契约：features、queue size、config space、activate()、reset、shared memory mapper、sleep/wake/snapshot/restore 等：devices/src/virtio/virtio_device.rs。

8. ProxyDevice：跨进程设备访问如何落地

ProxyDevice 是 process-per-device 的落地点。父进程侧只保留代理对象，子进程持有真实设备。所有 BusDevice 操作和 Suspendable 操作都通过 Command/CommandResult 经 Tube 同步转发。

源码依据：

  • 子进程 child_proc() 启动后先等待 Command::Activate，之后循环接收 Read/Write/Config/Snapshot/Restore/Sleep/Wake 等命令：devices/src/proxy.rs。
  • Snapshot 命令由父进程创建 SnapshotFile，传给子进程；注释说明这是因为 jailed child 可能没有权限创建临时文件：devices/src/proxy.rs。
  • 子进程收到 Command::Snapshot 时调用真实设备的 device.snapshot()，写入 SnapshotFile，再把结果返回：devices/src/proxy.rs。
  • 父进程侧 ProxyDevice 实现 Suspendable，snapshot() 和 restore() 都通过 sync_send() 发送 Command::Snapshot/Restore 给子进程：devices/src/proxy.rs。

这解释了 crosvm snapshot 为什么比单进程 VMM 更复杂：设备状态可能在独立进程内，主进程必须通过 ProxyDevice 协议让设备进入 sleep/snapshot/restore 状态。

9. Snapshot/restore

crosvm snapshot 的难点在于状态分布在 vCPU、设备进程、IRQ handler、VM control loop 和 guest memory 中。

snapshot crate 提供 SnapshotWriter 和 SnapshotReader。每个 fragment 是 opaque byte blob，可以用 namespace 避免设备间命名冲突；当前实现中 fragment 是文件，namespace 是目录：snapshot/src/lib.rs。

vm_control 中 vCPU 控制消息包含 Snapshot 和 Restore，设备控制线程包含 SnapshotDevices 和 RestoreDevices：vm_control/src/lib.rs。这说明 crosvm 的 snapshot 是一个跨线程/跨设备的协调协议，不是单对象序列化。

源码展开：

  • SnapshotCommand::Take 包含 snapshot path、是否压缩内存、是否加密；DeviceControlCommand 包含 Sleep/Wake/SnapshotDevices/RestoreDevices/GetDevicesState/Exit：vm_control/src/lib.rs。
  • VmRequest::Snapshot 进入 VmRequest::execute() 后调用 do_snapshot()，传入 kick_vcpus、irq handler、device control tube、vCPU 数量、irqchip snapshot 函数等：vm_control/src/lib.rs。
  • do_snapshot() 的设备阶段向 device control thread 发送 DeviceControlCommand::SnapshotDevices，等待 VmResponse::Ok：vm_control/src/lib.rs。
  • do_restore() 创建 SnapshotReader 后依次恢复 pvclock、irqchip、vCPU、guest memory、devices，最后刷新 IRQ event tokens：vm_control/src/lib.rs。
  • vCPU thread 收到 VcpuControl::Snapshot 时将自身 snapshot 写入 vcpu/vcpu{id} fragment；收到 Restore 时读取对应 fragment 并调用 hypervisor vCPU restore：src/crosvm/sys/linux/vcpu.rs。
  • device control thread 要求设备处于 Sleep 状态才允许 snapshot/restore；否则 assert 失败：devices/src/lib.rs。
  • VirtioPciDevice::snapshot() 保存 PCI config、inner virtio device、activated state、interrupt、MSI-X config、common config、queues 和 active queue snapshot；若设备仍 awake，会报错：devices/src/virtio/virtio_pci_device.rs。
  • VirtioPciDevice::restore() 明确限制“已激活后 restore 不支持”，并按 MSI-X、interrupt、queues、ioevent、doorbell、inner device 的顺序恢复：devices/src/virtio/virtio_pci_device.rs。

能力边界要特别注意：crosvm snapshot/restore 并不是任意运行状态下的透明迁移。设备必须先 sleep，virtio-pci 对某些 activated restore 路径仍有限制，aarch64 irqchip snapshot 支持也要看具体 irqchip 实现。

10. vCPU 控制：run loop 内的状态消息

crosvm 的 vCPU 线程通过 VcpuControl 接收主线程消息，而不是让主线程直接同步修改 vCPU 状态。

VcpuControl 包含 RunState(VmRunMode)、GetStates、Snapshot、Restore、Throttle 等。VmRunMode 包含 Running、Suspending、Exiting、Breakpoint：vm_control/src/lib.rs。

vCPU loop 的关键点：

  • 当被信号中断或 run mode 不是 Running 时，vCPU thread 会从 main tube 拉取 pending messages：src/crosvm/sys/linux/vcpu.rs。
  • 收到 RunState(Suspending) 时调用 vcpu.on_suspend() 通知 hypervisor vCPU 进入 suspend 边界：src/crosvm/sys/linux/vcpu.rs。
  • 收到 Snapshot/Restore 时，vCPU 自己执行 hypervisor vCPU state 的 snapshot/restore，并通过 channel 把结果返回给主线程：src/crosvm/sys/linux/vcpu.rs。

这和 Cloud Hypervisor 的 CpuManager 很像：主控制面负责发消息和等待结果，vCPU 线程在自己的 run loop 中完成状态切换。差异在于 crosvm 把这些消息建模在 vm_control crate 中，并和外部 VM control 协议共用一套请求类型。

11. ARM64 与 x86_64 差异

维度 x86_64 aarch64
PCI config PciConfigIo 插入 I/O port bus PciConfigMmio 插入 MMIO bus
架构设备 I8042 等 PC legacy 设备 PL030 等 ARM 设备
seccomp policy jail/seccomp/x86_64/... jail/seccomp/aarch64/...
GDB regs x86 GDB arch AArch64 registers/system regs
启动描述 ACPI/PC 语义更多 FDT/ARM platform 语义更多

README 明确支持 x86_64、aarch64、riscv64：README.md。架构文档指出 seccomp policy 按架构拆分，并举例 ARM 的 Pl030 与 x86_64 的 I8042 是架构特定设备：ARCHITECTURE.md。

源码展开：

  • LinuxArch trait 把 arch_memory_layout()、guest_memory_layout()、get_system_allocator_config()、build_vm()、vCPU configure 等定义为架构实现点：arch/src/lib.rs。
  • aarch64 build_vm() 先处理 pVM firmware、FDT 位置、payload 地址，再创建所有 vCPU，读取 MPIDR，初始化 PMU/PV time，最终生成 FDT：aarch64/src/lib.rs。
  • aarch64 创建 PciConfigMmio 并插入 mmio_bus，注释明确 ARM 基本不使用 I/O bus：aarch64/src/lib.rs 和 aarch64/src/lib.rs。
  • aarch64 FDT 创建时传入 PCI IRQ、PCI config region、PCI ranges、platform device resources、vCPU MPIDR、cluster/properties、cmdline、payload range、initrd 等：aarch64/src/lib.rs。
  • x86_64 build_vm() 设置 identity map 和 TSS，保留 PCIe config MMIO，创建 MMIO/IO/hypercall bus，生成 PCI root：x86_64/src/lib.rs。
  • x86_64 使用 PciConfigIo 插入 I/O port 0xcf8..0xcff，同时也创建 PciConfigMmio 和 PciVirtualConfigMmio：x86_64/src/lib.rs。
  • x86_64 setup fw_cfg、I8042、CMOS、serial/debugcon/pflash、ACPI PM resource，并调用 acpi::create_acpi_tables() 写入 ACPI 表：x86_64/src/lib.rs 和 x86_64/src/lib.rs。

结论：crosvm 的 ARM64 路径以 FDT/GIC/MMIO/platform bus 为中心，x86_64 路径以 PC legacy、I/O port、ACPI、PCIe config MMIO、fw_cfg 为中心。两者不是“同一 VM 模型换寄存器”，而是从设备枚举和平台固件描述开始就分叉。

12. 能力边界与不适合场景

从源码看，crosvm 的强项是宽设备面和强隔离，但这也带来边界：

  1. 它不是 Firecracker 那种极简 serverless microVM。设备、Tube、Minijail、control loop、platform device 的复杂度明显更高。
  2. process-per-device 能缩小单设备被攻破后的影响面，但也要求跨进程 IPC、FD 保留、snapshot 转发、worker 生命周期都正确。
  3. snapshot/restore 是协调协议，不是简单对象序列化；设备需要 sleep，ProxyDevice 子进程需要响应，virtio-pci activated restore 仍有源码限制。
  4. x86_64 能力更完整，尤其 PCI hotplug 路径当前在 run_vm() 中明确限制非 x86_64 不支持：src/crosvm/sys/linux.rs。
  5. ARM64 支持是正式路径，但许多能力围绕 FDT/GIC/pVM/virt cpufreq/PV time 等 Android/ChromeOS 场景展开，和 x86_64 的 PC/ACPI 生态不完全等价。

13. 与 Firecracker 的关键差异

  1. Firecracker 通过减少设备面降低复杂度；crosvm 通过 process-per-device 和 Minijail 承载更宽设备面。
  2. Firecracker 的 VMM 更适合 serverless/container microVM；crosvm 更适合 ChromeOS/Android/client-like VM。
  3. Firecracker 的设备多在同一 VMM 进程内；crosvm 的设备可 fork 到独立进程，通过 Tube/shared memory/eventfd 通信。
  4. Firecracker snapshot 更紧凑；crosvm snapshot 必须协调多进程设备、control loop 和 IRQ handler。
  5. ARM64/x86_64 在 Firecracker 中主要体现为 boot/interrupt/CPU state 差异；在 crosvm 中还体现在设备策略、seccomp policy 和平台设备差异上。
