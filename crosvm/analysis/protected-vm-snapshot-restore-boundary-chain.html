crosvm protected VM snapshot / restore 边界链路

本文继续下钻 protected VM IOMMU / VFIO / MemoryMapper 链路，分析 protected VM、virtio-iommu、VFIO、vhost-user 与 snapshot/restore 的交叉边界。

关联背景：Snapshot 与 Suspend 函数级分析、protected VM vhost-user memory / IOTLB 链路。

1. 总览

crosvm snapshot 的一致性前提是 vCPU 和 devices 都停止。do_snapshot() 在 vm_control/src/lib.rs:2426-2427 创建 VcpuSuspendGuard 和 DeviceSleepGuard。

保存顺序是 pvclock、vCPU、irqchip、memory、devices，见 vm_control/src/lib.rs:2477-2549。restore 顺序是 pvclock、irqchip、vCPU、memory、devices，见 2569-2664。

protected VM 的关键问题不是“snapshot 入口是否存在”，而是每类 protected device 路径是否能满足 Suspendable、virtio transport、inner device state 和外部 backend state 的保存条件。

2. snapshot 的 stop-the-world 前提

VcpuSuspendGuard::new() 会读取所有 vCPU 状态。如果原状态是 Running，就发送 VmRunMode::Suspending 并再次确认，见 vm_control/src/lib.rs:1821-1847。

DeviceSleepGuard::new() 先读取 device state。如果设备是 Wake，就发送 SleepDevices 并等待 VmResponse::Ok，见 1866-1894。

device control thread 收到 SnapshotDevices 或 RestoreDevices 时，会断言设备必须是 Sleep，见 devices/src/lib.rs:365-389。

这说明 snapshot 的一致性模型是 stop-the-world。它不依赖 protected VM 后端提供在线迁移语义，也不自动补齐外部设备状态。

3. Suspendable 默认实现是能力边界

Suspendable 的默认 snapshot()、restore()、sleep() 和 wake() 都返回未实现错误，见 devices/src/suspendable.rs:20-50。

因此设备只要没有覆写这些方法，就不能被认为支持完整 snapshot/restore。设备能被创建、能被 jail、能处理 MMIO/PCI，并不等于能保存状态。

Bus::snapshot_devices() 会遍历唯一设备并调用 snapshot() 或 snapshot_sync()，见 devices/src/bus.rs:527-553。

Bus::restore_devices() 对称调用 restore() 或 restore_sync()，见 devices/src/bus.rs:556-575。任一设备失败都会让整次 VM snapshot/restore 失败。

4. ProxyDevice 会转发 snapshot 到子进程

ProxyDevice 的 device loop 在收到 Command::Snapshot 时调用内层 device 的 snapshot()，再写入临时 snapshot 文件，见 devices/src/proxy.rs:285-292。

收到 Command::Restore 时，它读取 snapshot 文件并调用内层 device 的 restore()，见 proxy.rs:294-298。

外层 ProxyDevice::snapshot() 只是同步发送命令并读取结果，见 proxy.rs:603-617。restore() 对称发送 Command::Restore，见 619-629。

这说明进程隔离不会自动解决状态保存。ProxyDevice 只是跨进程转发，真正能力仍取决于内层 device 是否实现 Suspendable。

5. virtio-pci 的 IOMMU 硬限制

virtio-pci 的 Suspendable 实现在 devices/src/virtio/virtio_pci_device.rs:1217-1451。

sleep() 会调用 inner device 的 virtio_sleep()，并把 active queues 保存进 sleep_state，见 1218-1245。

snapshot() 首先检查 self.iommu.is_some()。如果存在 IOMMU，就直接返回 Cannot snapshot if iommu is present.，见 1281-1284。

这是 protected VM + virtio-iommu 分析中的硬边界。只要 virtio-pci device 绑定了 IOMMU，当前源码路径就不会继续保存 config、queue、interrupt 或 inner device state。

6. virtio device 默认不保存内部状态

VirtioDevice 默认 virtio_snapshot() 和 virtio_restore() 都返回未实现错误，见 devices/src/virtio/virtio_device.rs:233-241。

virtio-pci snapshot() 会保存 PCI config、inner device、activation flag、interrupt、MSI-X、common config、queues 和 activated queues，见 virtio_pci_device.rs:1286-1311。

但 inner device 必须自己实现 virtio_snapshot()。否则 transport 层能保存 queue，也无法保存设备语义状态。

restore() 还要求当前 device 未 activated，并且不能从 active sleep state 直接恢复，见 1315-1375。这限制了 restore 的目标时机和设备生命周期。

7. virtio-iommu 本身缺少 snapshot 覆写

Iommu 结构保存 worker、config、features、endpoints、hotplug endpoint ranges、translate tubes 和 control tube，见 devices/src/virtio/iommu.rs:700-714。

Iommu 实现了 VirtioDevice，见 iommu.rs:774-835。它实现 keep fd、device type、features、config read 和 activate。

当前源码中 Iommu 没有覆写 virtio_snapshot() 或 virtio_restore()。因此它会落回 VirtioDevice 默认未实现路径。

结合上一节的 self.iommu.is_some() 拒绝逻辑，可以得出：virtio-iommu 相关状态不是当前 crosvm snapshot 的可恢复组成部分。

8. VFIO PCI 只实现 sleep/wake

VfioPciDevice 的 Suspendable 实现只覆写 sleep() 和 wake()，见 devices/src/pci/vfio_pci.rs:2115-2130。

sleep() 停止 worker thread 并保存 address、sysfs path、PM/MSI-X capability 和 vm socket 等运行期字段，见 2116-2124。

源码中没有对应的 snapshot() 或 restore() 覆写，因此它继承 Suspendable 默认未实现错误。

这意味着 VFIO PCI passthrough 当前可参与 sleep/wake，但不能直接证明支持完整 VM snapshot/restore。

9. VFIO platform 与 CoIOMMU 也不是完整快照对象

VfioPlatformDevice 只有 impl Suspendable for VfioPlatformDevice {}，见 devices/src/platform/vfio_platform.rs:91。它没有覆写 snapshot/restore/sleep/wake。

CoIommuDev 也只有空的 impl Suspendable for CoIommuDev {}，见 devices/src/pci/coiommu.rs:1576。

因此 VFIO platform 和 CoIOMMU 设备路径如果出现在 bus snapshot 中，会依赖默认未实现行为，不能被视为可恢复设备状态。

这与 protected VM 尤其相关：IOMMU/VFIO 是隔离边界的一部分，但 snapshot 能力必须另行证明。

10. pKVM pvIOMMU 状态没有进入 snapshot 树

KvmVfioPviommu 封装 pKVM pvIOMMU fd，attach() 把 device、SID index 和 VSID 关联到 pvIOMMU，见 devices/src/vfio.rs:173-220。

VfioDevice::new_passthrough() 在 IommuDevType::PkvmPviommu 下创建 pvIOMMU，查询 SID 数量，生成 VSID 并逐个 attach，见 vfio.rs:1045-1057。

VfioDevice::iommu() 目前只报告 pKVM pvIOMMU 类型、id 和 VSID 列表，见 1153-1162。

这些逻辑发生在设备创建和平台描述阶段。当前 snapshot 主流程没有单独保存 pKVM pvIOMMU fd、attach 关系或 VSID 生成来源。

11. vhost-user frontend 有 DEVICE_STATE 条件

vhost-user frontend 的 virtio_snapshot() 要求协议 feature 包含 DEVICE_STATE。否则直接失败，见 devices/src/virtio/vhost_user_frontend/mod.rs:603-609。

保存时 frontend 通过 set_device_state_fd(Save, Stopped, fd) 让 backend 写 device state，再调用 check_device_state() 确认传输完成，见 610-636。

restore 也要求 DEVICE_STATE，并校验目的端 backend 支持源端已确认的 feature bits，见 643-665。

因此 vhost-user snapshot 不是普通 mem table 的副产品。它依赖 backend 明确实现 device state 协议。

12. vhost-user backend 的状态深度取决于设备

backend handler 的 set_device_state_fd() 要求 migration phase 是 Stopped，并且所有 queues 已停止，见 vhost_user_backend/handler.rs:744-755。

保存时它把 acked features、acked protocol features 和 backend 自身 snapshot 写出，见 765-781。

加载时它在线程中读取 state，check_device_state() 再恢复 acked features、protocol features 和 backend snapshot，见 796-827。

但每个 backend 的 snapshot 深度不同。block/net/snd/console 有自己的状态结构；fs、wl、gpu 等路径有的只保存很少状态或空状态。

13. SharedMemoryMapper 的 IOMMU client 不是 snapshot 状态

VmMemoryRequestIommuClient 保存 virtio-iommu tube 和 registered_memory 集合，见 vm_control/src/lib.rs:620-632。

VmMemoryRequest::execute() 在注册动态 memory 时，如果存在 descriptor 和 IOMMU client，会发送 VfioDmabufMap，见 817-842。

注销动态 memory 时，如果 region 被记录，则发送 VfioDmabufUnmap，见 960-978。

这些状态存在于 VM memory handler 线程和 virtio-iommu worker 的运行期交互中。snapshot 文件主流程没有把 registered_memory 集合作为独立 fragment 保存。

14. restore 时机与 protected VM 的关系

Linux run_control() 在 vCPU barrier 之后检查 cfg.restore_path，再调用 vm_control::do_restore()，见 src/crosvm/sys/linux.rs:4158-4177。

restore 完成后才把 vCPU 切到 post_restore_run_mode，见 4178-4183。这保证 guest 运行前，pvclock、irqchip、vCPU、memory 和 devices 已恢复。

但这个时机也意味着被恢复的设备必须已经在新进程中按配置重建。外部 vhost-user backend、VFIO device、IOMMU endpoint 和 protected VM 后端必须能重新建立等价环境。

protected VM 的 restore 能力不能只看 guest memory 是否恢复。还要看设备隔离边界、DMA mappings、backend state 和 hypervisor-specific protected state 是否同样可重建。

15. ARM64 与 x86_64 差异

ARM64 protected VM 更容易触发 pKVM、pvIOMMU、restricted DMA pool 和 platform device/FDT 相关路径。pKVM pvIOMMU attach 关系当前没有明确 snapshot fragment。

x86_64 的 virtio-iommu 路径会增加 VIRTIO_IOMMU_F_PROBE，见 devices/src/virtio/iommu.rs:757-759。但 virtio-pci 绑定 IOMMU 后仍会拒绝 snapshot。

vhost-user DEVICE_STATE 和 SharedMemoryMapper 代码本身不按架构分叉。差异来自底层 protected VM 后端、IOMMU 表达方式和外部 backend 是否可重建。

结论是：x86_64/ARM64 都不能把 protected VM snapshot 简化成“内存加设备配置”。ARM64 还要额外审视 pKVM/pvIOMMU 的不可见状态。

16. 总结

crosvm snapshot/restore 的主框架是清晰的：vCPU suspend、device sleep、IRQ flush、memory snapshot、bus device snapshot、cold restore。

protected VM 相关路径的能力边界也很清楚：virtio-pci 绑定 IOMMU 会拒绝 snapshot；virtio-iommu 本身没有覆写 snapshot；VFIO PCI/platform 不保存完整状态。

vhost-user 只有在 frontend/backend 都支持 DEVICE_STATE 时才有 device state 迁移语义。SharedMemoryMapper 与 IOMMU client 的动态映射不等同于 snapshot state。
