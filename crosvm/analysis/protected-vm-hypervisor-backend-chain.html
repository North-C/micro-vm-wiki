crosvm protected VM hypervisor backend 分流链路

本文继续展开 protected VM / pVM firmware 函数级链路。前文已经解释 ProtectionType、pVM firmware、SWIOTLB、virtio ACCESS_PLATFORM 和设备边界；本文专门下钻 protected VM 如何进入 KVM、Geniezone、Halla、Gunyah 后端。

关联路线：deep-routes.md、boot-control-chain.md、arch-arm64-x86-chain.md、protected VM IOMMU / VFIO / MemoryMapper 链路。

1. 总览

crosvm 的 protected VM 不是单一后端实现。ProtectionType 先进入 hypervisor::Config，然后由不同 hypervisor 后端解释成 VM type、memory region flag、firmware address 或 memparcel/FDT 语义。

ARM64 是后端分流最丰富的路径。KVM、Geniezone、Halla、Gunyah 都有 protected 相关路径；x86_64 主要是 KVM 和 pVM firmware 布局，边界更窄。

2. ProtectionType 进入 hypervisor::Config

ProtectionType 在 hypervisor/src/lib.rs:653-671 定义。它区分是否隔离内存、是否由 VMM 加载 firmware、以及 VM 是否运行 pVM firmware。

isolates_memory() 在 hypervisor/src/lib.rs:673-680 只对三个 protected variant 返回 true。UnprotectedWithFirmware 会运行 firmware 布局，但不要求 host memory isolation。

setup_vm_components() 在 src/crosvm/sys/linux.rs:1586-1593 把 cfg.protection_type 写入 hypervisor::Config。

同一个函数还在 src/crosvm/sys/linux.rs:1345-1352 打开自定义 pVM firmware 文件，并在 1367-1376 为 protected 模式设置默认 64 MiB SWIOTLB。

这说明 backend 不直接读 CLI flag。它们看到的是收敛后的 VmComponents.hv_cfg、pvm_fw、swiotlb 和 guest memory region purpose。

3. run_config 后端分发

run_config() 在 src/crosvm/sys/linux.rs:2103-2133 是 Linux VM 启动的后端分发点。

它先调用 setup_vm_components(&cfg)，再读取 cfg.hypervisor。如果用户没有指定，就调用 get_default_hypervisor()。

get_default_hypervisor() 在 src/crosvm/sys/linux.rs:2058-2100 先检查 /dev/kvm。ARM64 feature 打开时，再依次尝试 Geniezone、Halla、Gunyah 设备路径。

真正分发发生在 src/crosvm/sys/linux.rs:2114-2133。KVM 通用可用，Geniezone/Halla/Gunyah 都是 ARM64 feature-gated 分支。

4. 各 run_* 的共同骨架

run_kvm()、run_gz()、run_halla() 和 run_gunyah() 都先计算 Arch::arch_memory_layout()，再调用 create_guest_memory()。

然后它们分别创建后端 VM 对象：KvmVm::new()、GeniezoneVm::new()、HallaVm::new()、GunyahVm::new()。

如果 cfg.protection_type.isolates_memory() 为 true，创建 VM 后会检查 vm.check_capability(VmCap::Protected)。

Geniezone 检查在 src/crosvm/sys/linux.rs:1818-1820。Halla 在 1877-1879。KVM 非 x86 在 1939-1944。Gunyah 在 2041-2043。

x86_64 KVM 没有这段后置检查。注释在 src/crosvm/sys/linux.rs:1939-1941 说明，x86_64 protected VM 创建不支持时会直接失败。

5. KVM：VM type 表达 protected

KVM VM 创建在 hypervisor/src/kvm/mod.rs:284-296。KvmVm::new() 调 KVM_CREATE_VM 时传入 kvm.get_vm_type(cfg.protection_type)。

ARM64 的 get_vm_type() 在 hypervisor/src/kvm/aarch64.rs:63-80。它读取 IPA size，并在 isolates_memory() 为 true 时加 KVM_VM_TYPE_ARM_PROTECTED。

x86_64 的 get_vm_type() 在 hypervisor/src/kvm/x86_64.rs:164-170。protected 模式使用 KVM_X86_PKVM_PROTECTED_VM，否则使用默认 VM type。

KVM 的 protected capability 检查在 hypervisor/src/kvm/mod.rs:614-624。VmCap::Protected 对应 KvmCap::ArmProtectedVm。

这意味着 KVM 的 protected 语义主要在 VM type 和 capability 上表达。后续 firmware load 再通过 arch-specific trait 完成。

6. KVM firmware load：ARM64 与 x86_64

ARM64 KVM 的 load_protected_vm_firmware() 在 hypervisor/src/kvm/aarch64.rs:233-242。它读取 protected VM info，检查 firmware size，再设置 firmware IPA。

x86_64 KVM 的 load_protected_vm_firmware() 在 hypervisor/src/kvm/x86_64.rs:490-499。它同样读取 protected VM info，但设置的是 firmware GPA。

相关 raw capability 是 KvmCap::X86ProtectedVm。hypervisor/src/kvm/x86_64.rs:448-463 用它读取 firmware info，466-476 用它设置 firmware GPA。

两者都依赖 arch 层先准备 firmware 地址和最大大小。区别是 ARM64 语义是 IPA，x86_64 语义是 GPA。

这也解释了为什么 protected VM firmware 不是普通 kernel image。它需要 hypervisor 后端知道 firmware 入口地址。

7. Geniezone：memory region purpose 映射为 GZ flags

Geniezone VM 创建在 hypervisor/src/geniezone/mod.rs:584-610。它创建 VM fd 后遍历 guest memory regions。

MemoryRegionPurpose::ProtectedFirmwareRegion 会映射为 GZVM_USER_MEM_REGION_PROTECT_FW，StaticSwiotlbRegion 会映射为 GZVM_USER_MEM_REGION_STATIC_SWIOTLB。

Geniezone 的 pVM firmware load 在 hypervisor/src/geniezone/mod.rs:163-172。它查询 protected VM firmware size，并设置 firmware IPA。

Geniezone capability 检查在 hypervisor/src/geniezone/mod.rs:879-888。VmCap::Protected 对应 GeniezoneCap::ArmProtectedVm。

因此 Geniezone 后端不仅通过 capability 证明 protected，还把 guest memory region purpose 直接映射成后端 memory flags。

8. Halla：VM type 与 memory flags

Halla 的 get_vm_type() 在 hypervisor/src/halla/mod.rs:96-105。它读取 IPA size，并在 isolates_memory() 为 true 时加 HVM_VM_TYPE_ARM_PROTECTED。

Halla 的 load_protected_vm_firmware() 在 hypervisor/src/halla/mod.rs:172-181。它查询 protected firmware size，然后设置 firmware IPA。

Halla VM 创建在 hypervisor/src/halla/mod.rs:616-640 附近。它遍历 guest memory regions，并把 region purpose 映射为 Halla user memory flags。

ProtectedFirmwareRegion 映射为 HVM_USER_MEM_REGION_PROTECT_FW，StaticSwiotlbRegion 映射为 HVM_USER_MEM_REGION_STATIC_SWIOTLB，见 hypervisor/src/halla/mod.rs:627-634。

Halla protected capability 在 hypervisor/src/halla/mod.rs:890-898，对应 HallaCap::ArmProtectedVm。

Halla 和 Geniezone 很像：都需要 protected VM type 或 capability，也都理解 protected firmware 和 static SWIOTLB region purpose。

9. Gunyah：lend、FDT 与 shm

Gunyah VM 创建在 hypervisor/src/gunyah/mod.rs:238-270 附近。它创建 VM fd 后遍历 guest memory regions。

如果 cfg.protection_type.isolates_memory() 为 true，Gunyah 会决定哪些 region 需要 lend 给 hypervisor，见 hypervisor/src/gunyah/mod.rs:253-262。

ProtectedFirmwareRegion 会被 lend，StaticSwiotlbRegion 不 lend。这和 Geniezone/Halla 的 flag 模型不同。

Gunyah 的 VmCap::Protected 在 hypervisor/src/gunyah/mod.rs:564-572 直接返回 true。这反映出 Gunyah 后端对 protected 能力的表达不是 KVM/GZ/Halla 式 capability ioctl。

Gunyah firmware load 在 hypervisor/src/gunyah/aarch64.rs:63-65。它调用 set_protected_vm_firmware_ipa()。

Gunyah FDT 处理更特殊。hypervisor/src/gunyah/aarch64.rs:95-104 把 protected firmware 写成 firmware-address 属性。

hypervisor/src/gunyah/aarch64.rs:147-160 对 StaticSwiotlbRegion 创建 shm device。这说明 Gunyah 的 SWIOTLB 通过 FDT/vdevice 语义暴露，不只是 memory slot flag。

10. ARM64 arch 层：region purpose 的来源

ARM64 main_memory_size() 在 aarch64/src/lib.rs:404-413 中处理 static SWIOTLB。如果后端要求静态 SWIOTLB，会从主 RAM 尾部扣除该大小。

guest_memory_layout() 在 aarch64/src/lib.rs:467-498 构造 guest memory regions。

当 protection_type.runs_firmware() 为 true，它添加 ProtectedFirmwareRegion。当存在 SWIOTLB 地址时，它添加 StaticSwiotlbRegion。

AArch64::build_vm() 在 aarch64/src/lib.rs:556-575 很早加载 pVM firmware。注释说明 pVM firmware 会影响 hypervisor capability 检查。

vCPU entry 也受保护模式影响。aarch64/src/lib.rs:1478-1502 在 VMM 加载 firmware 时设置 PC 为 firmware 起点；如果由 hypervisor 加载 firmware，则 PC 由后端设置。

11. x86_64 arch 层：存在布局，但边界更窄

x86_64 代码定义了 UnsupportedProtectionType，见 x86_64/src/lib.rs:309-310。这说明 x86 protected VM 组合不能按 ARM64 路径泛化。

pVM firmware 地址在 x86_64/src/lib.rs:456-461 定义，放在 2 GiB 以下，以便 protected VM long mode 启动时 identity-map。

x86_64/src/lib.rs:1332-1385 只在 kernel boot 分支支持 pVM firmware。BIOS boot 与 pVM firmware 不兼容，会返回错误。

entry point 在 x86_64/src/lib.rs:1387-1392 按 protection type 改变。VMM 加载 firmware 时设置 RIP 为 firmware 起点；后端加载 firmware 时 RIP 由 hypervisor 设置。

当 VM 运行 pVM firmware 时，x86_64 会准备 DTB setup_data，见 x86_64/src/lib.rs:1942-1970。DTB 会预留可扩展空间，供 pVM firmware patch。

所以 x86_64 有 pVM firmware 布局和 KVM protected VM type，但后端矩阵和 DMA/SWIOTLB/FDT protected path 不如 ARM64 丰富。

12. 后端差异矩阵

后端 架构主路径 protected VM 表达 firmware memory region purpose capability 检查
KVM ARM64 ARM64 KVM_VM_TYPE_ARM_PROTECTED 设置 firmware IPA 由 KVM memory slot 承载 KvmCap::ArmProtectedVm
KVM x86_64 x86_64 KVM_X86_PKVM_PROTECTED_VM 设置 firmware GPA pVM firmware 低地址布局 创建失败即失败，无 ARM 式后置检查
Geniezone ARM64 GZ VM + protected capability 设置 firmware IPA protected fw / static SWIOTLB flags GeniezoneCap::ArmProtectedVm
Halla ARM64 HVM_VM_TYPE_ARM_PROTECTED 设置 firmware IPA protected fw / static SWIOTLB flags HallaCap::ArmProtectedVm
Gunyah ARM64 Gunyah protected model 设置 firmware IPA lend + FDT firmware-address + shm VmCap::Protected 返回 true

这个矩阵的关键点是：ProtectionType 是统一抽象，但后端证明和内存语义完全不同。

13. UnprotectedWithFirmware 的意义

UnprotectedWithFirmware 会让 runs_firmware() 为 true，但 isolates_memory() 为 false。

因此它会触发 firmware layout 和部分设备策略，却不会触发 VmCap::Protected 后置检查。

这适合调试 pVM firmware 布局，但不能把它当作真正隔离 guest memory 的 protected VM。

文档和测试中必须区分“运行 pVM firmware”和“host 无法直接访问 guest memory”这两个条件。

14. 能力边界总结

crosvm protected VM 后端链路是：CLI/Config 生成 ProtectionType，setup_vm_components() 写入 hypervisor::Config，arch 层生成 protected firmware/SWIOTLB region，后端把 region purpose 翻译成自己的 VM type、flag、lend 或 FDT 语义。

ARM64 是多后端能力矩阵。KVM、Geniezone、Halla、Gunyah 都能接入 protected VM 抽象，但它们对 capability、firmware、memory region 和 SWIOTLB 的表达不相同。

x86_64 路径应谨慎解读。源码中存在 pVM firmware 地址、KVM protected VM type 和 DTB setup_data，但不是 ARM64 那种多后端 protected VM 平台矩阵。

这也解释了为什么 protected VM 的设备、IOMMU、VFIO、snapshot 边界必须单独分析：统一的 ProtectionType 并不意味着后端提供相同的运行期语义。
