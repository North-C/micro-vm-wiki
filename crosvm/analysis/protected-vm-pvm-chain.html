crosvm protected VM / pVM firmware 函数级链路

本文从当前源码解释 crosvm 的 protected VM 机制。重点不是泛泛讨论安全，而是 ProtectionType 如何从 CLI 进入 hypervisor、内存布局、pVM firmware、SWIOTLB、virtio DMA、设备策略和 ARM64/x86_64 差异。

关联路线：

  • deep-routes.md
  • arch-arm64-x86-chain.md
  • device-isolation-chain.md
  • boot-control-chain.md

关联横向专题：CoCo / pVM / 受保护 VM 跨项目专题分析。

1. 总览

crosvm 的 protected VM 是跨 hypervisor 后端抽象，不是某一个 KVM ioctl 的薄封装。它把 VM 类型、firmware、内存 region purpose、virtio feature、设备禁用和后端 capability 合在一起。

ARM64 路径最完整。KVM、Geniezone、Halla、Gunyah 都有 protected capability 或 protected VM type 相关逻辑；x86_64 也有 pVM firmware 布局，但完整保护路径更受限。

2. ProtectionType 语义

ProtectionType 定义在 hypervisor/src/lib.rs:653-671。它区分 Unprotected、Protected、ProtectedWithCustomFirmware、ProtectedWithoutFirmware 和 UnprotectedWithFirmware。

isolates_memory() 在 hypervisor/src/lib.rs:673-680 表示 hypervisor 是否阻止 host 直接访问 guest memory。只有三个 protected variant 返回 true。

needs_firmware_loaded() 在 682-688 表示 pVM firmware 由 VMM 从用户指定文件加载。runs_firmware() 在 690-693 表示 VM 是否运行 pVM firmware。

这个三元判断很关键：内存是否隔离、firmware 是否由 VMM 加载、VM 是否运行 firmware，是三个不同问题。crosvm 用同一个 enum 保持它们一致。

3. CLI 到 Config

src/crosvm/cmdline.rs:1670-1680 定义 --protected-vm、--protected-vm-with-firmware 和 --protected-vm-without-firmware。ARM64 还有 --swiotlb，见 2006-2010。

cmdline.rs:3016-3025 要求 protection mode flag 互斥。3027-3049 将 CLI flag 翻译成 ProtectionType，并在自定义 firmware 模式下写入 cfg.pvm_fw。

非 Unprotected 会直接禁用部分设备。cmdline.rs:3051-3055 关闭 USB，并关闭 RNG，因为 protected VM 不能信任 RNG device。

src/crosvm/config.rs:724-729 将 protection_type 和 pvm_fw 保存在 Config。默认值在 config.rs:962-967 是 Unprotected 且无 pVM firmware。

4. VmComponents 组装

setup_vm_components() 是 CLI config 到架构构造输入的收敛点。src/crosvm/sys/linux.rs:1345-1352 打开 pVM firmware 文件，生成 pvm_fw_image。

SWIOTLB 默认值也在这里决定。linux.rs:1367-1376 表示用户指定 --swiotlb 时按 MiB 转 bytes；非 protected 时为 None；其他 protected 模式默认 64 MiB。

VmComponents 在 arch/src/lib.rs:467-520 保存 hv_cfg、pvm_fw、swiotlb、memory size、VM image、initrd、PCI config 等字段。

setup_vm_components() 在 linux.rs:1588-1593 把 cfg.protection_type 写入 hypervisor::Config，在 1626 把 pvm_fw_image 写入组件。

因此 protected VM 的状态不是只挂在 CLI 上。它会跟随 VmComponents 进入所有架构的 build_vm()。

5. ARM64 内存布局

ARM64 会把 SWIOTLB 从主内存中扣出来。aarch64/src/lib.rs:404-411 在 hypervisor 要求静态 SWIOTLB 时，从 main memory size 中减去该区域。

guest_memory_layout() 在 aarch64/src/lib.rs:467-494 先放主 RAM，再按 runs_firmware() 增加 ProtectedFirmwareRegion，并按 swiotlb 增加 StaticSwiotlbRegion。

get_swiotlb_addr() 在 aarch64/src/lib.rs:231-240 根据 StaticSwiotlbAllocationRequired 能力，把 SWIOTLB 放到 guest RAM 尾部。

这些 region purpose 后续会被不同 hypervisor 后端解释。Geniezone、Halla、Gunyah 都会把 protected firmware 或 static SWIOTLB region 映射成自己的后端标志或 memparcel 语义。

6. ARM64 pVM firmware 与 vCPU 入口

AArch64::build_vm() 在 aarch64/src/lib.rs:556-574 很早处理 pVM firmware。注释说明必须先加载，因为它会告诉 hypervisor 当前 VM 是 pVM，并影响 capability 检查。

如果 needs_firmware_loaded() 为 true，VMM 用 arch::load_image() 把自定义 firmware 写到 AARCH64_PROTECTED_VM_FW_START。如果只 runs_firmware()，则调用 vm.load_protected_vm_firmware()。

vCPU 初始 PC 也受保护模式影响。aarch64/src/lib.rs:1480-1485 在 VMM 加载 firmware 时把 PC 设为 firmware 起点；在 hypervisor 加载 firmware 时让 hypervisor 设置 PC。

当 VM 运行 pVM firmware 时，aarch64/src/lib.rs:1496-1501 把 payload entry 放入 X1，把 image size 放入 X2。X0 仍是 FDT 地址。

FDT 对 pVM firmware 也有配合。aarch64/src/fdt.rs:119-124 将 frequency OPP 信息放入 CPU node，注释说明这便于部分 secure firmware 解析。

7. SWIOTLB 与 FDT restricted DMA

ARM64 FDT 的 create_fdt() 接收 swiotlb 参数，见 aarch64/src/fdt.rs:622-648。它代表为 DMA 预留的内存池。

aarch64/src/fdt.rs:678-700 在有 SWIOTLB 时创建 restricted_dma_reserved reserved memory，compatible 是 restricted-dma-pool。

aarch64/src/lib.rs:1037-1042 把 get_swiotlb_addr() 的地址和 size 传入 FDT 生成。guest 侧因此能看到受限 DMA pool。

这条链说明 protected VM 不是只保护 CPU/内存。设备 DMA 也必须被显式约束，否则 host 侧设备和 guest 侧 bounce buffer 模型会不一致。

8. virtio 与设备策略

virtio base feature 会随 protected VM 改变。devices/src/virtio/mod.rs:281-289 在非 Unprotected 时加入 VIRTIO_F_ACCESS_PLATFORM。

设备 helper 会把 ProtectionType 传给具体设备。src/crosvm/sys/linux/device_helpers.rs:197-240 定义 create_virtio_device(protection_type) 和 create_virtio_device_and_jail()。

block 设备在 device_helpers.rs:264-276 使用 virtio::base_features(protection_type)。RNG 在 418-424 也按 protection type 构造，但 CLI 层已在 protected 模式关闭 RNG。

platform device 也有 protected VM 特殊处理。arch/src/sys/linux.rs:173-176 在 guest memory private 时提前 mmap VFIO platform device region。

因此 protected VM 对设备有两层影响：一层是 config 直接禁用不可信设备，另一层是 virtio feature 和平台设备 DMA 映射语义变化。

9. 后端选择与 capability 证明

run_config() 在 src/crosvm/sys/linux.rs:2103-2133 选择 hypervisor。KVM 是通用路径，ARM64 还可能走 Geniezone、Halla、Gunyah。

默认选择逻辑在 linux.rs:2058-2098。先查 /dev/kvm，然后在 ARM64 feature-gated 场景下尝试 Geniezone、Halla、Gunyah。

每条 protected VM 路径都要检查后端能力。Geniezone 在 linux.rs:1818-1820，Halla 在 1877-1879，KVM 非 x86 在 1939-1944，Gunyah 在 2041-2043。

这些检查只在 protection_type.isolates_memory() 为 true 时触发。也就是说 UnprotectedWithFirmware 可以用于调试 pVM firmware 布局，但不要求 host memory isolation。

10. KVM 路径

KVM VM 创建在 hypervisor/src/kvm/mod.rs:286-295 调 KVM_CREATE_VM，传入 kvm.get_vm_type(cfg.protection_type)。

ARM64 的 VM type 在 hypervisor/src/kvm/aarch64.rs:63-79 生成。它读取 IPA size，并在 isolates_memory() 时加上 KVM_VM_TYPE_ARM_PROTECTED。

x86_64 的 VM type 在 hypervisor/src/kvm/x86_64.rs:164-170。protected memory 模式使用 KVM_X86_PKVM_PROTECTED_VM，否则使用默认 VM type。

KVM 的 protected capability 检查在 hypervisor/src/kvm/mod.rs:614-624。VmCap::Protected 对应 KvmCap::ArmProtectedVm。

KVM 的 firmware load 入口在 ARM64 和 x86_64 都存在。ARM64 kvm/aarch64.rs:233-242 设置 firmware IPA；x86_64 kvm/x86_64.rs:490-499 设置 firmware GPA。

11. Geniezone / Halla / Gunyah 路径

Geniezone 的 pVM firmware load 在 hypervisor/src/geniezone/mod.rs:163-168。guest memory region purpose 在 592-604 被映射为 guest memory、protected firmware 或 static SWIOTLB。

Geniezone 的 protected capability 在 geniezone/mod.rs:879-888，对应 GeniezoneCap::ArmProtectedVm。

Halla 的 VM type 在 hypervisor/src/halla/mod.rs:96-104。isolates_memory() 时加入 HVM_VM_TYPE_ARM_PROTECTED。

Halla 的 region purpose 映射在 halla/mod.rs:624-634，protected firmware 和 static SWIOTLB 都有专门 flag。protected capability 在 890-898。

Gunyah 的 firmware load 在 hypervisor/src/gunyah/aarch64.rs:63-65。它直接设置 protected VM firmware IPA。

Gunyah 的 FDT/memparcel 处理更特殊。gunyah/aarch64.rs:95-104 把 protected firmware 写成 firmware-address，147-155 为 static SWIOTLB 创建 shm device。

Gunyah 在 hypervisor/src/gunyah/mod.rs:253-262 根据 isolates_memory() 决定哪些 memory region lend 给 hypervisor。VmCap::Protected 在 564-572 恒为 true。

12. x86_64 边界

x86_64 有 pVM firmware 内存布局。x86_64/src/lib.rs:456-461 将 pVM firmware 放在 2 GiB 以下，使 protected VM long mode 启动时可 identity-map。

x86_64/src/lib.rs:1328-1385 在 kernel boot 分支加载 pVM firmware。BIOS boot 与 pVM firmware 不兼容，1332-1336 会返回错误。

entry point 也会变化。x86_64/src/lib.rs:1387-1392 在 VMM 加载 firmware 时设置 RIP 为 firmware 起点；若 hypervisor 加载 firmware，则 RIP 由 hypervisor 设置。

x86_64 会为 pVM firmware 准备 DTB。x86_64/src/lib.rs:1945-1970 在 protection_type.runs_firmware() 时把 DTB 放进 setup_data，并预留可扩展空间。

但 x86_64 代码也有边界信号。x86_64/src/lib.rs:309-310 定义 UnsupportedProtectionType，说明并非所有 protected mode 组合都可用。

因此应谨慎理解 x86：源码有 pVM firmware 布局和 KVM protected VM type，但 ARM64 的 pVM firmware、SWIOTLB、后端 capability 检查路径更完整。

13. 能力边界总结

crosvm protected VM 的主线是：CLI flag -> ProtectionType -> VmComponents -> guest memory regions -> pVM firmware -> virtio ACCESS_PLATFORM -> backend VmCap::Protected。

ARM64 重点是 pVM firmware、restricted DMA pool、GIC/FDT、KVM/Geniezone/Halla/Gunyah 后端能力。x86_64 重点是 protected firmware 地址、Linux boot params、DTB setup_data。

Protected 不等于“所有设备都可用”。USB/RNG 会被关闭，virtio 必须声明 ACCESS_PLATFORM，平台设备需要提前 mmap，后端还必须证明 VM 真的进入 protected mode。

设备边界已继续展开到 protected VM 设备边界与 virtio feature 链路，覆盖 block/net/fs/gpu/vhost-user/VFIO platform 等路径。

hypervisor 后端分流已继续展开到 protected VM hypervisor backend 分流链路，覆盖 KVM、Geniezone、Halla、Gunyah 的 VM type、capability、firmware 和 memory region 差异。
