crosvm protected VM vhost-user memory / IOTLB 链路

本文继续下钻 protected VM block/net/fs 数据路径链路 的下一步，分析 crosvm vhost-user frontend/backend、memory table、vring 地址、IOTLB 消息和 ACCESS_PLATFORM 的关系。

关联路线：protected VM 设备边界与 virtio feature 链路、virtio Queue 与 Worker 链路函数级分析、运行期控制与 Tube 分发链路函数级分析。

1. 总览

vhost-user 必须分 frontend 和 backend 两个方向看。crosvm 作为 frontend 时，会把当前 VM 的 guest memory region 通过 SET_MEM_TABLE 交给外部 backend。

crosvm 自己作为 vhost-user backend 时，会从 frontend 收到 fd 和 memory region，再在 backend 进程里重建 GuestMemory。这条路径默认并不继承某个 protected VM 的 ProtectionType。

2. frontend：feature 入口

create_vhost_user_frontend() 在 src/crosvm/sys/linux/device_helpers.rs:388-414 构造 frontend。它把 virtio::base_features(protection_type) 传给 VhostUserFrontend::new()。

VhostUserFrontend::new() 在 devices/src/virtio/vhost_user_frontend/mod.rs:105-136 接收 base features，并与 backend get_features() 做交集得到 avail_features。

这意味着 guest 最终看到的 feature 不是 crosvm 单方面决定的。ACCESS_PLATFORM 只有在 base features 和外部 backend advertised features 都包含该 bit 时才会进入 avail_features。

ack_features() 在 vhost_user_frontend/mod.rs:397-403 只记录 features & self.avail_features。activate 时如果 acked feature 变化，452-456 会调用 backend set_features()。

因此 protected VM 的 vhost-user frontend 语义是协商结果，不是强制结果。外部 backend 不支持或不声明该 bit 时，guest 侧不会得到完整的 protected DMA 声明。

3. frontend：protocol feature

frontend 默认允许 CONFIG、MQ、BACKEND_REQ、DEVICE_STATE、SHMEM_MAP 和 REPLY_ACK 等 protocol feature，见 vhost_user_frontend/mod.rs:138-148。

如果 backend 支持 VHOST_USER_F_PROTOCOL_FEATURES，frontend 会获取 protocol feature 并调用 set_protocol_features()，见 151-167。

如果协商了 BACKEND_REQ，frontend 会创建 backend request handler，并通过 set_backend_req_fd() 建立 backend 到 frontend 的请求通道，见 170-184。

这条链影响 shared memory、config change、device state 等高级能力，但它不等于 IOTLB 已经可用于 protected VM 内存翻译。

4. frontend：SET_MEM_TABLE

set_mem_table() 在 vhost_user_frontend/mod.rs:237-254 遍历 GuestMemory::regions()，把 guest physical address、size、host userspace address、mmap offset 和 shm fd 发送给 backend。

底层 BackendClient::set_mem_table() 在 third_party/vmm_vhost/src/backend_client.rs:81-101 生成 VhostUserMemoryRegion，并通过 SET_MEM_TABLE 发送 region 和 fd。

这一步非常关键：外部 backend 获得的是 guest memory 的共享内存 fd 和 host userspace address。protected VM 下能否这样做，取决于该 VM 的内存是否允许被 backend 映射。

如果 guest memory 已经是 host 不可直接访问的 private memory，那么传统 vhost-user mem table 与 protected VM 的隔离目标天然存在张力。源码这里没有自动转换成安全 bounce buffer。

5. frontend：vring 地址和事件

activate_vring() 在 vhost_user_frontend/mod.rs:256-305 设置 queue size、vring address、vring base、call fd 和 kick fd。

其中 descriptor table、used ring、available ring 地址来自 mem.get_host_address()，见 271-279。也就是说 frontend 发送给 backend 的 vring 地址是 host userspace virtual address。

activate 主路径在 446-480。它先 set_features()，再 set_mem_table(&mem)，然后逐个 activate_vring()，最后保存 sent queues 并启动 worker。

sleep 路径在 572-600 会 deactivate vring，并用 vhost_user_reclaim() 更新本地 queue 状态。snapshot 还要求 DEVICE_STATE，见 603-608。

这说明 vhost-user frontend 的数据路径建立在 backend 可访问 mem table 和 vring host address 的前提上。

6. backend：收到 memory table 后重建 GuestMemory

crosvm vhost-user backend 的通用接口是 VhostUserDevice，见 vhost_user_backend/handler.rs:126-190。start_queue(idx, queue, mem) 接收已经重建好的 GuestMemory。

VhostUserRegularOps::set_mem_table() 在 handler.rs:242-285 校验 fd 数量，基于每个 region 的 shm fd 创建 MemoryRegion，再用 GuestMemory::from_regions() 重建 memory。

它还记录 MappingInfo，保存 frontend 传来的 user_addr 到 guest physical address 的映射关系，见 277-284。

DeviceRequestHandler::set_mem_table() 在 448-464 调用上述函数，并把 guest_mem 与 vmm_maps 保存到 handler。

这说明 backend 侧不是拿原始 GPA 直接访问内存，而是用 fd 映射生成自己的 GuestMemory 视图。

7. backend：vring 地址从 VMM VA 转 GPA

backend 收到 SET_VRING_ADDR 后会处理 descriptor、used、available 三个地址。handler.rs:482-510 用 vmm_va_to_gpa() 将 frontend 传来的 VMM VA 转回 GPA。

vmm_va_to_gpa() 在 111-124 遍历 MappingInfo，把 vmm_addr 区间内的地址换算成 GuestAddress。

收到 kick fd 后，handler.rs:566-614 会 ack queue features、设置 queue ready、使用保存的 GuestMemory 激活 queue，并调用 backend start_queue(index, queue, mem)。

call fd 则在 623-646 被包装成 Interrupt::new_vhost_user()。queue enable 受 VHOST_USER_F_PROTOCOL_FEATURES 约束，见 661-672。

因此 backend 的数据路径是：mem table 重建 GuestMemory，vring addr 转 GPA，kick fd 激活 queue，最后由具体 backend worker 处理 descriptor。

8. crosvm 自带 backend 的 feature 边界

多个 crosvm vhost-user backend 默认从 ProtectionType::Unprotected 构造 feature，而不是继承某个 protected VM。

backend 源码证据 结论
block backend devices/src/virtio/vhost_user_backend/block/sys/linux.rs:52-54 BlockAsync backend 使用 unprotected base features
net backend devices/src/virtio/vhost_user_backend/net/sys/linux.rs:118-128 net backend 使用 unprotected base features，再叠加 net 和 protocol features
fs backend devices/src/virtio/vhost_user_backend/fs.rs:192-193 fs backend 使用 unprotected base features
snd backend devices/src/virtio/vhost_user_backend/snd.rs:96-97 snd backend 使用 unprotected base features
wl backend devices/src/virtio/vhost_user_backend/wl.rs:112-116 wl backend 使用 unprotected base features

block backend 的 build() 会把 self.features() 与 VHOST_USER_F_PROTOCOL_FEATURES 合并，见 vhost_user_backend/block.rs:39-48。

这不是说这些 backend 绝对不能用于 protected VM，而是说当前源码没有把某个 VM 的 ProtectionType 传播进 backend feature 构造。

9. backend：不同设备是否使用 mem

block backend 的 start_queue() 在 vhost_user_backend/block.rs:77-84 把 mem 继续传给内部 BlockAsync::start_queue()。

net backend 的 trait 实现接收 mem，见 vhost_user_backend/net.rs:175-181，但 Linux 平台 start_queue() 签名里 _mem: GuestMemory，见 net/sys/linux.rs:208-214。

fs backend 的 start_queue() 也接收 _mem: GuestMemory，见 vhost_user_backend/fs.rs:288-293。它主要依赖 queue、tube 和 FUSE worker。

这说明 mem table 对协议和 queue 激活是通用前提，但不同 backend 是否直接使用 GuestMemory 取决于设备实现。

10. IOTLB：消息类型存在，完整链路有限

third_party/vmm_vhost/src/message.rs:105-106 定义 frontend request IOTLB_MSG。181-182 也定义 backend request IOTLB_MSG。

同一文件 750-752 有注释说明 dirty log、live migration 和 IOTLB operations 仍待支持。这是当前 vmm_vhost 层能力边界的重要信号。

kernel vhost 路径也提示了 IOTLB 语义差异。devices/src/virtio/vhost/worker.rs:84-90 在把 feature 传给 vhost handle 前会清掉 ACCESS_PLATFORM。

注释说明 vhost API 中该 bit 意味着通过 IOTLB API 做地址翻译；如果底层 virtio device 不使用 viommu，就不需要 vhost translation。

因此在当前 crosvm vhost-user 源码中，不能把 ACCESS_PLATFORM 自动解读成“vhost-user IOTLB 已经提供 protected VM 安全翻译”。

11. protected VM 能力边界

protected VM 的核心目标是减少 host 对 guest private memory 的直接访问。但 vhost-user frontend 的传统 mem table 会把 guest memory fd 和 host virtual address 交给外部 backend。

这与 ProtectionType::isolates_memory() 的目标存在天然边界。除非底层 hypervisor、guest driver、bounce buffer、IOMMU/IOTLB 和 backend 都形成完整配合，否则外部 backend 不应被简单视为安全。

ARM64 protected VM 更强调 SWIOTLB/FDT restricted DMA pool。vhost-user 如果仍依赖直接 mem table，就需要额外证明 backend 只访问允许的 shared/bounce 区域。

x86_64 也会走同一 vhost-user frontend/backend 代码，但缺少 ARM64 那套显式 FDT restricted DMA pool 表达。它的保护边界更依赖具体 protected VM 后端和内存模型。

12. 总结

crosvm vhost-user frontend 把当前 VM 的 ProtectionType 带入 base features，并通过 mem table 和 vring address 把 guest memory 访问能力交给外部 backend。

crosvm vhost-user backend 则从对端收到 memory fd 和 region，重建 GuestMemory 并启动具体 device queue；多个内置 backend 默认按 unprotected feature 建模。

IOTLB 消息类型在 vmm_vhost 中存在，但当前源码没有形成一条完整的 protected VM vhost-user IOTLB 安全链路。分析 protected VM 时应把 vhost-user 视为高风险边界。

virtio-iommu、VFIO、MemoryMapper 已继续展开到 protected VM IOMMU / VFIO / MemoryMapper 链路，覆盖 endpoint、MemoryMapperTrait、VfioWrapper、pKVM pvIOMMU、SharedMemoryMapper 和 expose_with_viommu。
