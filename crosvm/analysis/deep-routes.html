1. 从 main.rs 到 run_config

研究目标：找到 crosvm 真正创建 VM 的入口，并理解平台分发。

关键入口：

  • Linux 主路径是 src/crosvm/sys/linux.rs::run_config(cfg)。它先 setup_vm_components(&cfg)，再根据 cfg.hypervisor 选择 KVM、Geniezone、Halla、Gunyah 等后端：src/crosvm/sys/linux.rs。
  • ARM64 额外可能走 Geniezone/Halla/Gunyah feature-gated 路径；x86_64 主路径主要是 KVM。

机制结论：

  1. crosvm 的平台差异很早就在 hypervisor kind 分发处出现。
  2. setup_vm_components 是 VM 构建前的通用准备层。
  3. Linux/Windows 有不同 sys 实现，分析 Linux micro-VM 场景应优先看 src/crosvm/sys/linux.rs。

继续深入点：

  • 从 CLI command 到 Config 构造。
  • setup_vm_components 如何准备 kernel、rootfs、memory、jail、devices。
  • run_kvm 如何调用 run_vm。

2. create_devices：设备构造与 Minijail

研究目标：理解 crosvm 为什么常被称为 process-per-device VMM。

关键源码：

  • create_devices() 接收 Config、VmArch、SystemAllocator、control tube 添加函数、VM event tube、IOMMU endpoint map、VFIO manager 和 worker process pid set。
  • 它返回 (BusDeviceObj, Option<Minijail>) 列表：src/crosvm/sys/linux.rs。
  • BusDevice 是设备访问抽象，要求实现 Send + Suspendable，提供 read/write/config register/power/hypercall 等接口：devices/src/bus.rs。
  • ProxyDevice 把内层 BusDevice 放到 fork 后的子进程中运行，构造时传入 device、Minijail、保留 fd；它本身也实现 BusDevice 和 Suspendable：devices/src/proxy.rs。

机制结论：

  1. crosvm 的设备隔离不是统一外置进程，而是按设备返回的 Option<Minijail> 决定是否代理/沙箱化。
  2. ProxyDevice 通过命令同步把 bus read/write/snapshot 等操作转发到子进程。
  3. 设备 snapshot 能力来自 Suspendable，因此设备模型天然参与 suspend/snapshot/restore。

继续深入点：

  • 已完成 create_devices 设备矩阵与隔离链路，覆盖 VFIO、virtio stub、VirtioPciDevice、Minijail、ProxyDevice、vhost-user frontend 和 ARM64/x86_64 落点。

3. Control loop：Tube 协议与 VM 请求

研究目标：理解运行中的 VM 如何响应外部控制请求和设备事件。

关键结构：

  • ControlLoopState 持有 RunnableLinuxVm、config、system allocator、control tubes、device control tube、irq/vm-memory handler、vCPU handles、hotplug manager、pvclock tube 等运行时状态：src/crosvm/sys/linux.rs。
  • process_vm_request() 处理 VmRequest，可追加新的 control tubes，并在 x86_64 或 pci-hotplug feature 下处理 IRQ/vm-memory tubes：src/crosvm/sys/linux.rs。
  • handle_hotplug_command() 目前显式 #[cfg(target_arch = "x86_64")]，说明 PCI hotplug 主路径是 x86_64 特化：src/crosvm/sys/linux.rs。

机制结论：

  1. Tube 是 crosvm 主进程与设备/控制端通信的核心 IPC。
  2. control loop 是 VM 管理状态的串行化点。
  3. hotplug、pvclock、suspend、device control 都通过 Tube 进入主循环或设备 worker。

继续深入点：

  • 追踪 run_control 的 epoll/wait context 注册。
  • 枚举 VmRequest variant 到 VmResponse 的映射。
  • 分析设备 worker thread 的 handle_command_tube 与 control loop 的边界。

4. virtio block/net/gpu/fs：简单设备与复杂设备

研究目标：按复杂度区分 crosvm 设备，不把所有 virtio 设备混为一类。

分类建议：

类型 典型设备 分析重点
简单块设备 virtio-block queue、disk image、rate limit、snapshot
网络设备 virtio-net/vhost-net TAP、vhost、jail、control tube
文件共享 9p/virtio-fs worker process、shared directory、sandbox policy
GPU/显示 virtio-gpu render server、Wayland/X/display backend、复杂进程模型
直通设备 VFIO IOMMU、PCI、irq、host fd 权限

继续深入点：

  • 从 create_devices() 中按 config 字段逐段建立设备矩阵。
  • 对每类设备记录是否有 Minijail、是否有 control tube、是否支持 snapshot。
  • 对 GPU/FS 额外画进程图。

专题进展：

  • 已完成 virtio Queue 与 Worker 链路函数级分析，覆盖 VirtioPciDevice::activate()、QueueConfig::activate()、block async worker、net worker、interrupt 和 ARM64/x86_64 边界。

5. Snapshot：保存顺序和设备参与

研究目标：理解 crosvm snapshot 不只是 guest memory dump，还包括 vCPU、IRQ、device、pvclock 等状态。

已确认机制：

  • BusDevice 继承 Suspendable，设备必须能参与 snapshot 或至少明确不支持。
  • ProxyDevice::snapshot() 会向子进程发送 snapshot 命令并等待结果：devices/src/proxy.rs。
  • device worker thread 明确用于处理 snapshot、sleep、suspend 等设备命令：devices/src/lib.rs。

继续深入点：

  • 找出 snapshot controller 入口和保存文件格式。
  • 对照 restore 路径确认保存顺序和恢复顺序是否严格对称。
  • 检查哪些设备在 snapshot 时返回 unsupported。

6. ARM64/x86_64 差异路线

已确认差异：

维度 x86_64 ARM64
hypervisor 后端 KVM 主路径 KVM + Geniezone/Halla/Gunyah feature paths
hotplug x86_64 handle_hotplug_command 主路径 受 feature 和平台限制
PCI config x86 传统 PCI/ACPI 更完整 MMIO/FDT/平台 IRQ 差异明显
pvclock 非 ARM 可在设备 worker 共享内存处理 offset ARM64 需要 VmAarch64::set_counter_offset action
设备描述 ACPI/PCI FDT/MMIO/平台中断

继续深入点：

  • 追踪 Arch::build_vm 对 x86_64/aarch64 的实现。
  • 对比 SystemAllocator 地址空间布局。
  • 对比 seccomp policy 和 Minijail keep-fd 列表是否按架构变化。

专题进展：

  • 已完成 protected VM / pVM firmware 函数级链路，覆盖 ProtectionType、CLI 转换、pVM firmware、SWIOTLB、virtio ACCESS_PLATFORM、后端 capability 和 ARM64/x86_64 边界。
