    crosvm 设备模型与隔离链路函数级分析

    本文沿着 crosvm 当前工作树源码，展开 run_vm -> create_devices -> create_virtio_devices/VFIO/... -> Arch::build_vm -> generate_pci_root/platform bus -> ProxyDevice -> BusDevice/Suspendable -> device worker 这条链路。

    目标是弄清楚：crosvm 的设备如何从配置变成 bus 上的 guest-visible 设备，哪些设备会进入 Minijail 子进程，ProxyDevice 如何转发 MMIO/PCI config/snapshot，为什么 crosvm 的设备隔离比 Cloud Hypervisor 更偏“按设备拆进程”。

    相关横向背景：设备模型与隔离边界跨项目专题分析。

    相关项目背景：crosvm 启动与控制循环函数级分析。

    1. 总体调用链

    flowchart TB RunVm["run_vm"] --> Create["create_devices"] Create --> VFIO["create_vfio_device"] Create --> Virtio["create_virtio_devices"] Create --> Stub["USB/stub/pvpanic"] Create --> Pairs["Vec<(BusDeviceObj, Option)>"] Pairs --> Build["Arch::build_vm"] Build --> PCI["arch::generate_pci_root"] Build --> Platform["aarch64 platform bus"] PCI --> Proxy["optional ProxyDevice"] Platform --> Proxy Proxy --> Bus["IO/MMIO/PCI bus"]

    关键结论：create_devices() 不直接决定设备一定在哪个进程运行。它返回的是设备对象和可选 Minijail。后续 generate_pci_root()、platform bus 或架构 legacy setup 才把有 jail 的设备包装成 ProxyDevice。

    因此 crosvm 的隔离边界是“设备对象 + jail policy + bus 接入点”共同决定的，而不是单一的全局设备进程模型。

    2. create_devices：生成设备对象与可选 jail

    create_devices() 接收 Config、hypervisor VM、SystemAllocator、control tube 注册函数、VM event tube、IOMMU endpoint map、VFIO manager 和 worker pid 集合，返回 Vec<(Box<dyn BusDeviceObj>, Option<Minijail>)>：src/crosvm/sys/linux.rs。

    flowchart LR Config["Config"] --> Create["create_devices"] VM["VmArch"] --> Create Alloc["SystemAllocator"] --> Create Tubes["add_control_tube"] --> Create Create --> Devs["BusDeviceObj"] Create --> Jail["Option"]

    VFIO 路径会调用 create_vfio_device()。PCI VFIO 设备会更新最大 IOVA，必要时把 IOMMU mapper 放入 iommu_attached_endpoints，再把 (vfio_pci_device, jail) 推入设备列表：src/crosvm/sys/linux.rs。

    virtio 路径先调用 create_virtio_devices() 得到 VirtioDeviceStub。每个 stub 会被包装成 VirtioPciDevice，并创建 MSI、shared-memory、ioevent、device-control tubes，最后以 (VirtioPciDevice, stub.jail) 推入设备列表：src/crosvm/sys/linux.rs。

    机制结论：

    1. 设备类型、jail policy 和控制 tube 在 create_devices() 阶段被绑定。
    2. PCI 地址分配和 bus 插入还没发生。
    3. 设备是否进入子进程，要等后续 bus/PCI root 接入时根据 Option<Minijail> 决定。

    3. BusDeviceObj：先保留类型，再转回 PCI 或 platform

    BusDeviceObj 是 crosvm 的通用设备擦除层。它允许设备在后续阶段被转回 PCI 设备或 platform 设备：devices/src/bus.rs。

    flowchart TB BusObj["BusDeviceObj"] --> AsPci["as_pci_device / into_pci_device"] BusObj --> AsPlatform["as_platform_device / into_platform_device"] AsPci --> PciRoot["generate_pci_root"] AsPlatform --> PlatformBus["generate_platform_bus"]

    x86_64 和 ARM64 的 build_vm() 都会先把 devs 按 as_pci_device() 分成 PCI 设备和其它设备：x86_64/src/lib.rs、aarch64/src/lib.rs。

    ARM64 还会把非 PCI 的 VFIO platform device 分出来，交给 generate_platform_bus()。这体现了 ARM64 的 platform device/MMIO/GIC 模型。

    4. generate_pci_root：PCI 接入时创建 ProxyDevice

    arch::generate_pci_root() 先给每个 PCI device 分配地址，再处理 BAR、IRQ、shared config mapping 和 AML/GPE 信息：arch/src/lib.rs。

    flowchart TB Gen["generate_pci_root"] --> Addr["allocate PCI address"] Addr --> Res["allocate BAR/MMIO/IO resources"] Res --> Keep["device.keep_rds + syslog/tracing/metrics fds"] Keep --> Jail{"jail?"} Jail -->|yes| Proxy["ProxyDevice::new"] Jail -->|no| Direct["device.on_sandboxed + Arc>"] Proxy --> Root["PciRoot::add_device"] Direct --> Root Root --> Bus["MMIO/IO bus insert ranges"]

    如果设备带 Minijail，generate_pci_root() 调用 ProxyDevice::new(device, jail, keep_rds, ...)，并把子进程 pid 与 debug label 写入 pid_debug_label_map。否则直接调用 device.on_sandboxed()，再包装成 Arc<Mutex<dyn BusDevice>>：arch/src/lib.rs。

    这个命名容易误解：无 jail 时也会调用 on_sandboxed()。更准确的理解是“设备已进入最终运行环境”，不是一定代表进入 Minijail。

    5. ARM64 platform bus：VFIO platform 设备的隔离路径

    ARM64 build_vm() 会把 non-PCI platform devices 分出后调用 arch::sys::linux::generate_platform_bus()：aarch64/src/lib.rs。

    platform bus 路径同样根据 Option<Minijail> 决定是否创建 ProxyDevice。有 jail 时，它保留设备需要的 fd 和 IRQ event fd，再把 proxy 插入 MMIO bus：arch/src/sys/linux.rs。

    flowchart LR A64["aarch64 build_vm"] --> Platform["platform devices"] Platform --> Gen["generate_platform_bus"] Gen --> Jail{"jail?"} Jail -->|yes| Proxy["ProxyDevice"] Jail -->|no| Direct["direct BusDevice"] Proxy --> Mmio["MMIO bus"] Direct --> Mmio

    这就是 ARM64 和 x86_64 设备接入的核心差异之一。x86_64 的复杂设备主要经 PCI root；ARM64 除 PCI 外，还保留 platform MMIO 设备路径。

    6. ProxyDevice：父进程里的 BusDevice 代理

    ProxyDevice 包装 ChildProcIntf，它本身实现 BusDevice 和 Suspendable：devices/src/proxy.rs。

    创建时，ProxyDevice::new() 调用 ChildProcIntf::new() fork 子进程，再转换为 ProxyDevice。转换过程中父进程先向子进程发送 Command::Activate，子进程返回 CommandResult::Ok 后才可使用：devices/src/proxy.rs。

    sequenceDiagram participant Parent as Parent process participant Proxy as ProxyDevice participant Child as child_proc participant Dev as real BusDevice Parent->>Proxy: ProxyDevice::new(device,jail,keep_fds) Proxy->>Child: fork_process with Minijail Child->>Dev: on_sandboxed Proxy->>Child: Activate Child-->>Proxy: Ok Parent->>Proxy: bus read/write/config Proxy->>Child: Command Child->>Dev: real operation

    机制结论：

    1. 父进程看到的是 ProxyDevice，不是原始设备。
    2. 子进程持有真实设备对象。
    3. 父子通过 Tube 传输 Command 和 CommandResult。

    7. ChildProcIntf::new：fork、保留 fd、进入 Minijail

    ChildProcIntf::new() 取设备 debug label，创建 tube pair，把 child tube fd 加入 keep_rds，然后调用 fork_process(jail, keep_rds, ...)：devices/src/proxy.rs。

    子进程闭包会先处理 swap 相关 fork 回调，然后调用 device.on_sandboxed()，再进入 child_proc(child_tube, device) 命令循环。

    flowchart TB New["ChildProcIntf::new"] --> Tube["Tube::pair"] Tube --> Keep["keep child tube + device fds"] Keep --> Fork["fork_process(jail, keep_rds)"] Fork --> Child["child process"] Child --> Hook["device.on_sandboxed"] Hook --> Loop["child_proc command loop"]

    这里有一个设计约束：ProxyDevice::new() 注释说明它应尽早使用，因为 fork 对析构、内存映射和 fd 继承都不友好；热插拔不应直接调用它，而应通过 jail warden 创建 ChildProcIntf 后再转换。

    8. 命令转发：MMIO/PCI config/snapshot 都走同一条 Tube

    child_proc() 等待 Activate 后进入循环，处理 Read、Write、ReadConfig、WriteConfig、InitPciConfigMapping、Snapshot、Restore、Sleep、Wake 等命令：devices/src/proxy.rs。

    flowchart LR ParentRead["ProxyDevice::read"] --> Cmd["Command::Read"] ParentCfg["config_register_write"] --> Cmd2["Command::WriteConfig"] ParentSnap["snapshot"] --> Cmd3["Command::Snapshot"] Cmd --> Child["child_proc"] Cmd2 --> Child Cmd3 --> Child Child --> Real["real BusDevice/Suspendable"] Real --> Result["CommandResult"]

    ProxyDevice::read() 通过 sync_send(Command::Read) 等待 ReadResult；write() 只发送命令，不等待结果。PCI config 读写会转发到子进程，并把 ConfigWriteResult 返回给父进程：devices/src/proxy.rs。

    snapshot 数据可能太大，不能直接塞进 Tube。因此 ProxyDevice 用 SnapshotFile 临时文件包装 snapshot，再把文件描述符传给子进程读写：devices/src/proxy.rs。

    9. BusDevice 与 Suspendable：设备生命周期合约

    BusDevice 继承 Send + Suspendable，并定义 read/write、PCI config、virtual config、power management、hypercall 和 range 查询等方法：devices/src/bus.rs。

    Suspendable 定义 snapshot()、restore()、sleep()、wake() 四个方法。默认实现返回“未实现”错误：devices/src/suspendable.rs。

    classDiagram class Suspendable { snapshot() restore(data) sleep() wake() } class BusDevice { read(info,data) write(info,data) config_register_read() config_register_write() on_sandboxed() } Suspendable <|-- BusDevice BusDevice <|-- ProxyDevice

    这意味着 crosvm 的设备模型天然要求设备参与 sleep/snapshot/restore 语义。设备可以不支持，但必须通过 trait 边界明确表达。

    10. device worker：对 bus 上设备统一 sleep/snapshot/restore

    crosvm 会创建 device_control 线程，监听 DeviceControlCommand。线程内部调用 handle_command_tube()，持有 IO bus 和 MMIO bus：devices/src/lib.rs。

    sequenceDiagram participant Control as run_control participant Worker as device_control thread participant Bus as IO/MMIO Bus participant Dev as BusDevice Control->>Worker: SleepDevices Worker->>Bus: sleep_devices Bus->>Dev: sleep Control->>Worker: SnapshotDevices Worker->>Bus: snapshot_devices Bus->>Dev: snapshot

    SnapshotDevices 和 RestoreDevices 都断言设备必须处于 Sleep 状态。snapshot 时，它按 bus 建 namespace，调用 bus.snapshot_devices()；restore 时调用 bus.restore_devices()：devices/src/lib.rs。

    机制结论：crosvm snapshot 的设备参与不是事后补丁，而是由 BusDevice: Suspendable、device worker 和 control tube 三者共同形成的协议。

    11. x86_64 与 ARM64 差异总结

    维度 x86_64 ARM64
    主设备总线 PCI root + IO/MMIO bus PCI root + platform MMIO bus
    legacy 设备 pflash、fw_cfg、debugcon 等有独立 jail 包装点 IO bus 基本为空，platform device 更重要
    hotplug x86_64 PCI hotplug 主路径 register_pci_device 当前返回 unsupported
    PCI config IO port 0xcf8 + MMIO config MMIO PciConfigMmio
    platform device 不是主路径 VFIO platform 走 generate_platform_bus
    ProxyDevice PCI/legacy 设备都可能使用 PCI/platform 设备都可能使用

    不要把 crosvm 的隔离理解成“所有设备都外置进程”。更准确的说法是：设备按 Option<Minijail> 决定是否通过 ProxyDevice 隔离；未隔离设备仍是同一个 BusDevice/Suspendable 合约的一部分。

    12. 能力边界

    crosvm 设备隔离链路明确覆盖以下能力：

    1. 从 config 创建 VFIO、virtio、USB、stub、pvpanic 等设备对象。
    2. 为 virtio-pci 设备创建 MSI、ioevent、shared memory、device-control tubes。
    3. 为带 jail 的设备 fork 子进程并通过 ProxyDevice 代理。
    4. 把 PCI 设备插入 PCI root，把 platform 设备插入 MMIO bus。
    5. 通过 BusDevice/Suspendable 统一处理 read/write/config/sleep/snapshot/restore。
    6. 通过 device worker 对 IO/MMIO bus 上设备执行 sleep、wake、snapshot、restore。

    它不覆盖以下语义：

    1. 每个 virtio queue 的具体处理逻辑。
    2. vhost-user backend 自己的进程协议。
    3. guest 内部驱动是否成功绑定设备。
    4. Kata/CubeSandbox 这类 runtime/platform 对设备的业务抽象。

    这条边界正好解释 crosvm 与 Cloud Hypervisor 的差异：Cloud Hypervisor 更多是进程内 manager 聚合；crosvm 更强调 BusDevice trait、Tube IPC、Minijail 和按设备进程隔离。
