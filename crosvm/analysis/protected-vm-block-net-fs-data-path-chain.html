crosvm protected VM block/net/fs 数据路径链路

本文继续下钻 protected VM 设备边界与 virtio feature 链路，聚焦 block、net、fs 三条高频数据路径。目标是解释 ACCESS_PLATFORM 如何进入设备 feature，以及实际 I/O 如何经由 queue、DescriptorChain、GuestMemory 和 worker 执行。

关联路线：virtio Queue 与 Worker 链路函数级分析、设备模型与隔离链路函数级分析、protected VM / pVM firmware 函数级链路。

1. 总览

这三条路径的共同点是：protected VM 影响的是设备向 guest 暴露的 virtio feature。真正搬运数据时，worker 仍通过 DescriptorChain.reader/writer 访问 guest buffer。

源码里没有在 block/net/fs worker 内部大量出现 ProtectionType 分支。保护语义在更早的 feature 协商和平台 DMA/IOMMU/SWIOTLB 层建立。

2. 共同入口：feature 到 queue

devices/src/virtio/mod.rs:281-289 定义 base_features(protection_type)。非 Unprotected 时会加入 VIRTIO_F_ACCESS_PLATFORM。

设备构造时把这个 base_features 合入各自的 avail_features。block 在 device_helpers.rs:270-274，net 在 807-815，fs 在 1181-1183。

QueueConfig 保存 device feature、acked feature 和三段 ring 地址，见 devices/src/virtio/queue.rs:42-86。snapshot/restore 也会保存 features 与 acked_features，见 307-342。

Queue 是 split/packed virtqueue 的统一接口。queue.rs:422-425 的 pop() 取出 descriptor chain，456-460 触发中断，546-558 把已用 descriptor 放回 used ring。

3. DescriptorChain 是数据搬运核心

DescriptorChain 定义在 devices/src/virtio/descriptor_chain.rs:45-63。它包含 GuestMemory、descriptor index、Reader、Writer、packed queue id 和 descriptor count。

DescriptorChain::new() 在 81-144 从 split/packed iterator 读 descriptor，并拆分为 device-readable 和 device-writable regions。

validate_mem_regions() 在 147-178 检查每个 region 是否落在 GuestMemory 内，并检查总长度是否溢出。这是 worker 处理 guest buffer 前的基础边界检查。

这也说明 protected VM 并没有替换 crosvm 的 descriptor 解析模型。它让 guest 知道 DMA 受平台约束，但 worker 仍基于 GuestMemory 和 Reader/Writer 处理 buffer。

4. block：feature 进入 BlockAsync

block regular 路径在 src/crosvm/sys/linux/device_helpers.rs:264-282。DiskConfig::create_virtio_device() 先计算 base_features(protection_type)，再传给 BlockAsync::new()。

vhost-user block builder 是不同路径。device_helpers.rs:285-307 使用 ProtectionType::Unprotected 生成 base feature，这与 protected VM frontend 路径不同。

BlockAsync::new() 在 devices/src/virtio/block/asynchronous.rs:641-724 保存 disk image、queue size、worker 配置，并调用 build_avail_features()。

build_avail_features() 在 727-740 从 base features 开始叠加 block 自身 feature，例如 read-only、discard、write-zeroes、多队列和 packed queue。

因此 block 的 protected VM 语义进入点是 base_features，不是 block request 执行函数里的单独判断。

5. block：queue 到 DiskFile

BlockAsync::activate() 在 asynchronous.rs:1112-1121 接收 GuestMemory、interrupt 和 queue map，然后逐个调用 start_queue()。

start_queue() 在 1033-1043 启动或复用 worker thread，并把 WorkerCmd::StartQueue 发送给 worker。

主 worker run_worker() 在 469-590 管理 control tube、flush timer、kill event 和 queue handler。收到 StartQueue 后，它为该 queue 创建 handle_queue() future。

handle_queue() 在 300-344 等待 queue event，然后循环 queue.pop()。每个 descriptor chain 会交给 process_one_chain()。

process_one_chain() 在 274-295 调 process_one_request()，完成后调用 queue.add_used_with_bytes_written() 并触发中断。

6. block：请求执行

process_one_request() 在 231-272 从 descriptor chain 拿 reader/writer，并把 writer 最后一个字节拆成 status writer。

execute_request() 在 760-937 读取 virtio_blk_req_header，检查 read-only、sector、disk size 和请求类型。

读请求 VIRTIO_BLK_T_IN 使用 writer.write_all_from_at_fut() 从 disk image 写入 guest writable buffer，见 801-818。

写请求 VIRTIO_BLK_T_OUT 使用 reader.read_exact_to_at_fut() 从 guest readable buffer 写到 disk image，见 820-837。

discard/write-zeroes 在 849-913 处理，flush 在 915-928 调 fdatasync()，GET_ID 在 930-933 写入 guest buffer。

protected VM 下，这些代码仍然按 Reader/Writer 操作 guest buffer。隔离要求要靠 ACCESS_PLATFORM、SWIOTLB/IOMMU 和 hypervisor memory isolation 与 guest driver 配合满足。

7. net：feature 进入 TAP 或 vhost-net

net regular 路径在 device_helpers.rs:802-815。它先生成 features = virtio::base_features(protection_type)，再根据配置选择 tap net 或 kernel vhost-net。

devices/src/virtio/net.rs:510-541 从 base features 开始叠加 virtio-net feature，包括 checksum、control vq、TSO/UFO、MTU、多队列、MAC 和 mergeable rx buffer。

Net::features() 在 621-623 返回 avail_features。ack_features() 在 625-647 过滤 guest 未请求 feature，并把 acked feature 转成 TAP offload。

这意味着 ACCESS_PLATFORM 与网络 offload 是同一轮 feature 协商的一部分，但 TAP offload 只关心网络相关 feature。

8. net：queue 到 TAP

Net::activate() 在 net.rs:655-733 根据 acked feature 判断 control queue 和多队列数量，然后按 rx/tx 成对取出 queues。

每个 queue pair 会启动一个 v_net:{i} worker thread。worker 持有 rx queue、tx queue、control queue、tap、acked features 和 kill event，见 707-724。

RX 单 buffer 路径在 net/sys/linux.rs:162-213。它从 TAP 读数据，通过 descriptor writer 写入 guest buffer，随后 add_used() 并触发中断。

mergeable RX 路径在 88-160。它先从 TAP 读入 pending buffer，再用 try_pop_length() 收集足够 writable descriptors，最后批量 add_used。

TX 路径在 215-235。worker 从 tx queue pop() descriptor chain，通过 reader 把 guest buffer 写到 TAP，然后 add_used。

因此 net 数据路径的核心方向是：TAP -> Writer -> guest，或 guest -> Reader -> TAP。protected VM 不改变这个 worker 算法，但改变 guest-facing DMA 约束声明。

9. vhost-net 的特殊点

kernel vhost-net 构造也从 device_helpers.rs:807-815 的 features 开始。因此 guest 侧仍可能看到 ACCESS_PLATFORM。

但 vhost worker 会在传给 vhost handle 前重解释该 bit。devices/src/virtio/vhost/worker.rs:84-90 在 acked features 包含 ACCESS_PLATFORM 时清掉它。

注释说明 vhost API 里的这个 bit 表示通过 IOTLB API 做地址翻译。如果底层 virtio device 不使用 viommu，就不需要让 vhost 做这层翻译。

结论是：net protected VM 需要区分 guest virtio feature、TAP/vhost offload、vhost API feature 三层，不能把一个 bit 的意义跨层直接等同。

10. fs：feature 进入 virtio-fs

virtio-fs regular 路径在 device_helpers.rs:1170-1183。它先建立 jail，然后用 base_features(protection_type) 创建 virtio::fs::Fs。

Fs::new() 在 devices/src/virtio/fs/mod.rs:134-173 保存 avail_features = base_features，构造 PassthroughFs，并创建 high priority queue 加 request queues。

use_dax 在 158-160 明确受架构限制：当前只有 target_arch = "x86_64" 且配置打开 DAX 才会使用。ARM64 这里不会启用 DAX。

因此 fs 在 protected VM 下同样继承 ACCESS_PLATFORM，但 DAX、共享内存和 host filesystem 隔离是额外问题。

11. fs：queue 到 FUSE server

Fs::activate() 在 fs/mod.rs:218-269 检查 queue 数量，创建 fuse::Server，处理可选 DAX shared memory，然后为每个 queue 启动 worker。

worker 的 queue loop 在 fs/worker.rs:180-250。它等待 queue event，读 eventfd 后调用 process_fs_queue()。

process_fs_queue() 在 147-163 循环 queue.pop()，把 descriptor reader/writer 交给 server.handle_message()，然后 add_used 并触发中断。

fs/worker.rs:33-60 将 virtio Reader/Writer 适配成 FUSE Reader/Writer 和 ZeroCopyReader/ZeroCopyWriter。

这条路径说明 virtio-fs 的 guest buffer 访问仍通过 descriptor reader/writer。host 文件系统操作由 FUSE server 和 PassthroughFs 决定。

12. fs：PassthroughFs 读写

PassthroughFs::read() 在 fs/passthrough.rs:2812-2849 找到 inode/handle 对应文件后，用 writer 从 host file 写入 guest buffer。

PassthroughFs::write() 从 2852 开始处理 guest 到 host 的写入。它通过 ZeroCopyReader 从 guest buffer 读数据并写入 host file。

所以 virtio-fs 是 guest memory 和 host filesystem 的桥。protected VM 只解决 DMA/内存访问语义的一部分，不自动消除共享目录本身的信任边界。

13. ARM64 与 x86_64 差异

ARM64 protected VM 更依赖 SWIOTLB/FDT restricted DMA pool。block/net/fs 的 ACCESS_PLATFORM 会与该 DMA 约束共同构成 guest 侧设备访问模型。

x86_64 也会继承 ACCESS_PLATFORM，但 fs DAX 在源码上只允许 x86_64。fs/mod.rs:158-160 的 cfg!(target_arch = "x86_64") 是明确差异。

net 和 block 的 worker 算法在这份代码里不是按 ARM64/x86_64 分叉。架构差异主要出现在内存隔离、DMA 池、DAX 和后端 capability 层。

14. 能力边界总结

block、net、fs 三条路径可以统一理解为：ProtectionType 影响 feature；feature 影响 guest driver 协商；worker 通过 queue 和 DescriptorChain 处理 guest buffer。

ACCESS_PLATFORM 不是“worker 内部额外安全检查”。它是 virtio 协议层告诉 guest DMA 需要遵守平台访问约束的声明。

vhost-user memory/IOTLB 已继续展开到 protected VM vhost-user memory / IOTLB 链路，覆盖 frontend/backend、mem table、vring 地址和 IOTLB 边界。
