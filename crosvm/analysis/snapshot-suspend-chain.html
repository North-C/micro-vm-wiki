crosvm Snapshot 与 Suspend 函数级分析

本文沿着 crosvm 当前工作树源码，展开 VmRequest -> process_vm_request -> VmRequest::execute -> VcpuSuspendGuard/DeviceSleepGuard -> do_snapshot/do_restore -> device_control thread -> BusDevice/Suspendable 这条链路。

目标是弄清楚：crosvm 如何区分 vCPU suspend、完整 VM suspend 和 snapshot，保存顺序为什么是 pvclock、vCPU、irqchip、memory、devices，restore 为什么在 run_control 初始化后、vCPU 真正运行前完成。

相关横向背景：Snapshot / Restore / Clone 跨项目专题分析。

相关项目背景：crosvm 设备模型与隔离链路函数级分析。

1. 总体调用链

关键结论：crosvm 的 snapshot 不是单个 dump 操作。它先用 guard 把 vCPU 和设备停住，再按固定顺序保存 pvclock、vCPU、irqchip、guest memory 和 bus devices。

这个机制和 Cloud Hypervisor 的 manager trait 模型不同。crosvm 的一致性边界由 VmRequest、vCPU control channel、device control tube、IRQ handler thread 和 snapshot crate 共同形成。

2. VmRequest：区分 vCPU suspend、VM suspend 和 snapshot

VmRequest 定义了 SuspendVcpus、ResumeVcpus、SuspendVm、ResumeVm 和 Snapshot(SnapshotCommand) 等请求：vm_control/src/lib.rs。

SuspendVcpus 只要求 vCPU 进入 VmRunMode::Suspending。ResumeVcpus 会先检查设备状态，如果设备仍处于 Sleep，会拒绝唤醒 vCPU，并提示应使用完整 resume。

SuspendVm 更强。它先停 vCPU，保存 hypervisor pvclock，再向 device control tube 发送 SleepDevices。这才是 VM 级 suspend 的语义。

3. process_vm_request：运行期控制请求的汇合点

run_control() 收到 control tube 事件后构造 ControlLoopState，再调用 process_vm_control_event()，后者读取 VmRequest 并进入 process_vm_request()：src/crosvm/sys/linux.rs。

process_vm_request() 对 hotplug、memory register 等请求有平台侧处理。其余请求交给 VmRequest::execute()，并传入 VM、disk/gpu/usb tubes、device control tube、IRQ handler control、vCPU kick 闭包和 irqchip snapshot 闭包：src/crosvm/sys/linux.rs。

这里的设计边界很清楚：control loop 持有运行期对象，VmRequest::execute() 只通过传入的闭包和 tube 操作这些对象。

4. vCPU suspend：VcpuSuspendGuard

VcpuSuspendGuard::new() 先用 get_vcpu_state() 获取所有 vCPU 当前状态。如果原状态是 Running，它向所有 vCPU 发送 VcpuControl::RunState(VmRunMode::Suspending)，再阻塞确认状态已切换：vm_control/src/lib.rs。

Guard 被 drop 时，如果原状态不是 Suspending，会把 vCPU 恢复到原始 run mode。这样 snapshot/restore 期间即使中间失败，也能按 RAII 语义回滚 vCPU 状态。

机制结论：crosvm snapshot 的第一层一致性来自 vCPU stop-the-world，不是来自 dirty-log 增量同步。

5. device sleep：DeviceSleepGuard 和 device_control thread

DeviceSleepGuard::new() 先向 device control tube 发送 GetDevicesState。如果设备当前是 Wake，就发送 SleepDevices 并等待 VmResponse::Ok：vm_control/src/lib.rs。

DeviceSleepGuard 被 drop 时，如果原状态是 Wake，会发送 WakeDevices 并等待成功响应。失败会 panic，因为设备无法恢复会导致 VM 行为不可预期。

device control thread 由 create_devices_worker_thread() 创建。它持有 IO bus 和 MMIO bus，并在 handle_command_tube() 中处理 SleepDevices、WakeDevices、SnapshotDevices、RestoreDevices：devices/src/lib.rs。

6. do_snapshot：保存顺序和原因

Snapshot(Take) 请求最终调用 do_snapshot()：vm_control/src/lib.rs。

do_snapshot() 先创建 VcpuSuspendGuard 和 DeviceSleepGuard。然后通知 IRQ handler thread 反复 WakeAndNotifyIteration，直到本轮没有 token 被处理，以 flush pending IRQ。

保存顺序是：

  1. pvclock：写入 suspended_pvclock_state。
  2. vcpu namespace：向 vCPU 线程发送 VcpuControl::Snapshot。
  3. irqchip fragment：调用 snapshot_irqchip()。
  4. mem 与 mem_metadata：调用 vm.get_memory().snapshot()。
  5. devices：发送 DeviceControlCommand::SnapshotDevices。

内存 snapshot 的调用被标记为 unsafe，源码注释说明前提是 VM 和 devices 已停止。这正是前面两个 guard 的作用。

7. device snapshot：按 bus namespace 保存

device control thread 收到 SnapshotDevices 时，断言 devices state 必须是 Sleep，然后调用 snapshot_handler()：devices/src/lib.rs。

snapshot_handler() 遍历 IO bus 和 MMIO bus，分别创建 bus0、bus1 namespace，并调用 Bus::snapshot_devices()。

Bus::snapshot_devices() 会计算每个唯一设备的 snapshot key，然后调用 snapshot() 或 snapshot_sync()，并把结果写成 fragment：devices/src/bus.rs。

如果设备是 ProxyDevice，snapshot() 会通过 Tube 向子进程发送 Command::Snapshot，并用临时文件传递可能较大的 snapshot 数据。

8. do_restore：恢复顺序和 IRQ token 刷新

run_control() 在创建 device worker、vCPU threads、IRQ handler 和 VM memory handler 后，如果 cfg.restore_path 存在，会调用 vm_control::do_restore()：src/crosvm/sys/linux.rs。

这个时机很重要：restore 发生在 vCPU barrier 之后，但在 vCPU 被踢到真实运行状态之前。

do_restore() 也创建 VcpuSuspendGuard 和 DeviceSleepGuard，然后读取 SnapshotReader。恢复顺序是：pvclock、irqchip、vCPU、memory、devices，最后发送 RefreshIrqEventTokens 给 IRQ handler thread：vm_control/src/lib.rs。

刷新 IRQ tokens 的原因是，restore 后设备和 irqchip 状态可能重新建立了事件关系，IRQ handler 必须更新自己监听的事件 token 集合。

9. snapshot 文件结构：fragment 和 namespace

SnapshotWriter::new(root, encrypt) 要求目标目录不存在，并在目录下创建 snapshot fragments。write_fragment() 使用 CBOR 序列化写入单个 fragment：snapshot/src/lib.rs。

add_namespace(name) 创建子目录，用于 vCPU、bus 等分组。SnapshotReader 对称地提供 read_fragment()、list_fragments() 和 namespace()：snapshot/src/lib.rs。

这解释了为什么 crosvm snapshot 更像目录树，而不是单一二进制镜像。不同组件通过 fragment 和 namespace 独立保存，再由 restore 按名字读取。

10. suspend/resume 与 snapshot 的边界

SuspendVcpus 只改变 vCPU run mode。它不会 sleep devices，因此 ResumeVcpus 会主动检查设备状态，防止设备仍处于 Sleep 时只唤醒 vCPU：vm_control/src/lib.rs。

SuspendVm 会停 vCPU、保存 pvclock、sleep devices。ResumeVm 会先 wake devices，再尽可能晚地恢复 pvclock，最后把 vCPU 切回 Running：vm_control/src/lib.rs。

机制结论：snapshot 内部会临时 suspend vCPU 和 devices，但 snapshot 不等同于 SuspendVm。SuspendVm 是运行期状态转换；snapshot 是带文件输出的一致性保存流程。

11. ARM64 与 x86_64 差异总结

维度 x86_64 ARM64
vCPU restore 保存 host TSC reference moment 无 x86 TSC reference path
pvclock resume 可通过 hypervisor pvclock ARM64 pvclock action 可要求 set_counter_offset
irqchip snapshot x86 split/kernel irqchip 语义 GIC/kernel irqchip 语义
device bus IO bus + MMIO bus 都重要 MMIO/platform 设备更重要，IO bus 基本为空
hotplug 后 restore 风险 PCI hotplug 设备更多 platform device/FDT/GIC 关系更突出
force s2idle 通过 sleep/power button 协作 guest 同样控制面，但平台 PM 行为取决于实现

不要把差异理解成 snapshot 框架完全不同。crosvm 的 snapshot 控制面和文件结构是共享的；架构差异集中在 vCPU state、irqchip、pvclock 和设备机器描述。

12. 能力边界

crosvm snapshot/suspend 链路明确覆盖以下能力：

  1. 通过 control tube 接收 suspend、resume 和 snapshot 请求。
  2. 用 vCPU guard 和 device guard 建立一致性窗口。
  3. 保存 pvclock、vCPU、irqchip、guest memory 和 bus devices。
  4. 通过 SnapshotWriter/Reader 组织 fragment 和 namespace。
  5. 通过 device worker 调用 BusDevice/Suspendable 的 snapshot/restore。
  6. restore 后刷新 IRQ handler tokens，并按目标 run mode 启动 vCPU。

它不覆盖以下语义：

  1. guest 内部文件系统一致性。
  2. vhost-user 后端进程自己的外部状态。
  3. Kata runtime sandbox/container metadata。
  4. CubeSandbox 平台级 clone/rollback metadata 与网络状态。

这条边界对横向比较很关键：crosvm 给出的是 VMM 级 suspend/snapshot；Kata 和 CubeSandbox 必须在此之上额外处理 guest agent、container runtime 和平台状态。
