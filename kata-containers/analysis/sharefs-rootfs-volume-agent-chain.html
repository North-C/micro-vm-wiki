Share-fs / Rootfs / Volume 到 Agent 链路

本文分析 Kata 非机密计算路径中，容器 rootfs、共享目录和 volume 如何从 host runtime 转成 hypervisor device 与 guest agent storage/mount。

源码基线：当前仓库工作树。Kata CoCo/TDX/SEV/SNP/CCA 暂不展开。

相关：runtime-rs ResourceManager 资源设备、storage/device 到 agent RPC、横向 存储/rootfs/share-fs。

0. 术语与背景

Kata 存储是三层，不是单一 VMM 设备模型

层 谁做 产出
① host runtime resource runtime-rs ResourceManager / Go FilesystemShare hypervisor device（virtio-fs/block/pmem）
② hypervisor device hypervisor plugin VM 内 guest 可见设备
③ guest agent storage/mount kata-agent add_storages + rustjail guest 内真实挂载点 + OCI mount

关键边界：host runtime 负责"把资源暴露进 VM"，guest agent 负责"把 VM 内资源挂到 container bundle/OCI mount 语义"。agent 不直接信任 host mount 路径——先 add_storages() 转成 guest 内挂载点，再让 rustjail 按更新后的 OCI spec 创建容器。

rootfs 不是单一路径

分析 Kata rootfs 不能只看 hypervisor plugin——某些是 virtio-fs，某些是 block device，某些是 guest pull 或多层 EROFS。runtime-rs 把它们分类成不同 Rootfs 实现。

share-fs rootfs vs block rootfs（是否需要 agent storage）

  • share-fs rootfs：已通过共享目录进 guest，get_storage() 返回 None——不需要 agent 再挂 block storage。
  • block rootfs：agent 要在 guest 内挂 block device——get_storage() 返回 agent Storage。

1. 结论先行

  • runtime-rs VirtSandbox::prepare_for_start_sandbox() 生成 ResourceConfig，share-fs 和 VM rootfs 在 VM start 前交给 ResourceManager。
  • container 创建时先 handler_rootfs() 再 handler_volumes()，转成 agent Storage 与 OCI mount 变更。
  • guest agent 收到 CreateContainerRequest 后 add_storages() 把 storage driver 转成 guest 内挂载点。
  • Go virtcontainers 语义相同，实现位置不同（FilesystemShare + kataAgent.createContainer）。

2. 总体分层

3. runtime-rs sandbox 资源准备

ResourceConfig 是 sandbox 启动资源清单：

// src/runtime-rs/crates/resource/src/lib.rs:35
pub enum ResourceConfig {
    Network(NetworkConfig), ShareFs(SharedTsInfo), VmRootfs(BlockConfig),
    HybridVsock(HybridVsockConfig), Vsock(VsockConfig),
    Protection(ProtectionDeviceConfig), PortDevice(PortDeviceConfig), InitData(BlockConfig),
}

prepare_for_start_sandbox() 按顺序准备 VM socket → network → share-fs → VM rootfs → initdata/PCIe port：

// src/runtime-rs/crates/runtimes/virt_container/src/sandbox.rs:161
async fn prepare_for_start_sandbox(&self, id: &str, network_env) -> Result<Vec<ResourceConfig>> {
    let mut resource_configs = vec![];
    resource_configs.push(self.prepare_vm_socket_config().await?);       // VM socket
    if let Some(net) = self.prepare_network_resource(&network_env).await { resource_configs.push(net); }
    resource_configs.push(ResourceConfig::ShareFs(self.hypervisor.hypervisor_config().await.shared_fs));  // share-fs
    if let Some(block_config) = self.prepare_rootfs_config().await? {
        resource_configs.push(ResourceConfig::VmRootfs(block_config));   // VM rootfs（与容器 rootfs 不同）
    }
    Ok(resource_configs)
}

VirtSandbox::start() 顺序：prepare_vm → prepare_for_start_sandbox → prepare_before_start_vm → start_vm（:580）。

share-fs 设备和 VM rootfs block 属于 VM 启动前资源——不是 container create 阶段才临时注入的普通 volume。

4. ResourceManager before/after VM start

prepare_before_start_vm() 收到 ShareFs 时检查 hypervisor capability，支持则建 ShareFs 实例 + setup_device_before_start_vm + sandbox bind mounts；VmRootfs 包成 BlockCfg 经 do_handle_device() 交 device manager：

// src/runtime-rs/crates/resource/src/manager_inner.rs:144
pub async fn prepare_before_start_vm(&mut self, device_configs: Vec<ResourceConfig>) -> Result<()> {
    for dc in device_configs {
        match dc {
            ResourceConfig::ShareFs(c) => {
                self.share_fs = if self.hypervisor.capabilities().await?.is_fs_sharing_supported() {
                    let share_fs = share_fs::new(&self.sid, &c)?;
                    share_fs.setup_device_before_start_vm(self.hypervisor.as_ref(), &self.device_manager).await?;
                    self.handle_sandbox_bindmounts(true).await?;     // sandbox bind mounts
                    Some(share_fs)
                } else { None };
            }
            ResourceConfig::VmRootfs(r) => {
                do_handle_device(&self.device_manager, &DeviceConfig::BlockCfg(r)).await?;  // 交 device manager
            }
            ResourceConfig::Network(c) => { self.handle_network(c).await?; }
            // ...
        }
    }
}

VM start 后 setup_after_start_vm() 对 share-fs 调 setup_device_after_start_vm()（:300）——给 inline virtio-fs 或需 VM 运行后更新的共享挂载留出阶段。

5. share-fs 设备模型

ShareFsConfig 承载 virtio-fs 设备配置；ShareFsDevice::attach() 是 share-fs 进 hypervisor plugin 的统一入口：

// src/runtime-rs/crates/hypervisor/src/device/driver/virtio_fs.rs:52
pub struct ShareFsConfig {
    pub host_shared_path: String,   // passthrough fs 导出目录的 upperdir
    pub fs_type: String,            // virtiofs 或 inline-virtiofs
    pub sock_path: String,          // virtiofs socket
    pub mount_tag: String,          // guest 侧挂载标签
    pub queue_size: u64, pub queue_num: u64,
    pub options: Vec<String>,
    pub mount_config: Option<ShareFsMountConfig>,
}
// :101
impl Device for ShareFsDevice {
    async fn attach(&mut self, _pcie_topo, h: &dyn hypervisor) -> Result<()> {
        h.add_device(DeviceType::ShareFs(self.clone())).await?;     // 统一入口
        Ok(())
    }
}

当前 share_fs::new() 只创建 virtio-fs 或 inline-virtio-fs，其它 shared-fs 类型不在 runtime-rs 这条实现里。prepare_virtiofs() 创建 host ro/rw shared path + bind mount（share_virtio_fs.rs:31）。

6. runtime-rs rootfs 分类

RootFsResource::handler_rootfs() 按 rootfs mounts 分类：

// src/runtime-rs/crates/resource/src/rootfs/mod.rs:66
match rootfs_mounts {
    [] => { /* 无 rootfs mount → share-fs rootfs (ShareFsRootfs) */ }
    _ if is_single_layer_rootfs(rootfs_mounts) => {
        let layer = &rootfs_mounts[0];
        if let Some((dev_id, layer)) = is_block_rootfs(layer) { /* BlockRootfs */ }
        else if let Some(share_fs) = share_fs {
            if layer.fs_type == NYDUS_ROOTFS_TYPE { /* NydusRootfs */ } else { /* ShareFsRootfs */ }
        }
    }
    _ => { /* 多层 EROFS / virtual volume */ }
}
类型 判定 实现
无 rootfs mount [] ShareFsRootfs
单层 block is_block_rootfs() BlockRootfs
单层 nydus fs type nydus NydusRootfs
单层普通 fs 有 share-fs ShareFsRootfs
guest pull virtual volume 无 share-fs + virtual volume VirtualVolume
多层 EROFS is_erofs_multi_layer() ErofsMultiLayerRootfs

ShareFsRootfs::get_storage() 返回 None（已通过共享目录进 guest，不需 agent 再挂 block storage）。BlockRootfs::new() 构造 BlockConfig + do_handle_device() + 生成 agent Storage：

// src/runtime-rs/crates/resource/src/rootfs/block_rootfs.rs:25
pub async fn new(d, sid, cid, dev_id, rootfs: &Mount) -> Result<Self> {
    let block_device_config = &mut BlockConfig { major, minor, driver_option, path_on_host: rootfs.source, /*...*/ };
    let device_info = do_handle_device(d, &DeviceConfig::BlockCfg(block_device_config.clone())).await?;
    let mut storage = Storage { fs_type: rootfs.fs_type.clone(), mount_point: container_path, options: rootfs.options, /*...*/ };
    if let DeviceType::Block(device) = device_info {
        match block_driver.as_str() {
            VIRTIO_BLK_PCI => { storage.source = device.config.pci_path?.to_string(); }
            VIRTIO_SCSI | VIRTIO_PMEM => { return Err(anyhow!("Complete support for block driver {} has not been implemented yet")); }  // 容器 rootfs 未完整实现
            _ => {}
        }
    }
}

注意：容器 rootfs 的 virtio-pmem 和 virtio-scsi 在 BlockRootfs 中明确未完整实现。VM rootfs（hypervisor kernel 参数 PMEM/blk root device）≠ 容器 rootfs 支持 PMEM/SCSI storage。

7. runtime-rs volume 分类

VolumeResource::handler_volumes() 遍历 OCI mounts，按类型选 volume 实现：shm/local/ephemeral/block/direct volume/hugepage/share-fs volume/default（volume/mod.rs:52）。block volume 构造 BlockConfig + do_handle_device + handle_block_volume 生成 agent storage（block_volume.rs:25）。share-fs volume 经 ShareFsVolume 维护 mounted info + 引用计数（支持多 container 共享同 host path），只读/读写变化时触发 remount（share_fs_volume.rs:40）。

8. runtime-rs CreateContainerRequest（语义收敛点）

container create() 先 handler_rootfs()（写回 OCI root path + rootfs Storage），再 handler_volumes()（OCI mount + storage），最后构造 CreateContainerRequest：

// src/runtime-rs/crates/runtimes/virt_container/src/container_manager/container.rs:100
pub async fn create(&self, mut spec: oci::Spec) -> Result<()> {
    let rootfs = self.resource_manager.handler_rootfs(/*...*/).await?;
    root.set_path(rootfs.get_guest_rootfs_path().await?);     // 写回 OCI root path
    let mut storages = vec![];
    if let Some(s) = rootfs.get_storage().await { storages.append(&mut s); }
    let volumes = self.resource_manager.handler_volumes(/*...*/).await?;
    for v in volumes { oci_mounts.append(&mut v.get_volume_mount()?); storages.append(&mut v.get_storage()?); }
    spec.set_mounts(Some(oci_mounts));
    let r = agent::CreateContainerRequest { process_id, storages, oci: Some(spec), /*...*/ };  // 收敛点
    self.agent.create_container(r).await?;
}

这是 host runtime 到 guest agent 的语义收敛点：hypervisor 看到 device，agent 看到 storage + OCI spec + guest device id。

9. guest agent storage 落地

guest agent do_create_container() 收到请求后调 add_storages()——注释明确：rootfs 和 volume 用同一套 storage 流程，先挂到指定 MountPoint，rustjail 再按 OCI mounts 绑定：

// src/agent/src/rpc.rs:199
async fn do_create_container(&self, req: CreateContainerRequest) -> Result<()> {
    // rootfs 和 volume 同样处理：先 mount 到 MountPoint，匹配 oci.Mounts，rustjail 再 bind mount
    let m = add_storages(sl(), req.storages.clone(), &self.sandbox, Some(req.container_id)).await?;
    // ...
}
// src/agent/src/storage/mod.rs:253
pub async fn add_storages(logger, storages, sandbox, cid) -> Result<Vec<String>> {
    for storage in &storages {
        let handler = STORAGE_HANDLERS.get_handler(&storage.driver).ok_or_else(|| anyhow!("no handler for driver {}", storage.driver))?;
        handler.handle_storage(logger, storage, &sandbox, &cid).await?;
    }
}

STORAGE_HANDLERS 注册了 virtio-blk-mmio/pci、ephemeral、local、pmem、overlayfs、scsi、virtio-fs、bind-watcher、image-pull、multi-layer-erofs（s390x 才有 ccw，:136）。通用 handler 执行 mount_storage() 按 source/mount_point/fs_type/options mount（:384）。最后 agent 调 setup_bundle() 写 bundle spec，guest 内 runtime 才按更新后的 OCI spec 创建进程。

10. Go virtcontainers 对照 / 能力边界

Go 路径在 sandbox 初始化时建 FilesystemShare，Prepare() 后 agent.createSandbox()（sandbox.go:641）；FilesystemSharer 接口定义 Prepare/ShareFile/ShareRootFilesystem/Unshare（fs_share.go:27）；bindMountContainerRootfs() 把容器 rootfs bind mount 到 <cid>/rootfs（mount_linux.go:96）。Go kataAgent.createContainer() 先 fsShare.ShareRootFilesystem() 转 shared rootfs/storage，处理 shared-dir/ephemeral/hugepages/local/block OCI mounts，替换 OCI mount source，设 grpcSpec.Root.Path = sharedRootfs.guestPath，构造 grpc.CreateContainerRequest（kata_agent.go:1371/1470）。

问题 结论
Kata 是否直接把 host path 放进 guest OCI 不是，改写为 guest path 或 agent storage
share-fs rootfs 是否需要 agent storage 通常不需要（已在 guest shared dir）
block rootfs 是否需要 agent storage 需要（agent 在 guest 内挂 block）
volume 是否总是 share-fs 不是（block/direct/ephemeral/local/hugepage/share-fs）
runtime-rs share-fs 类型 当前聚焦 virtio-fs 和 inline-virtio-fs
容器 rootfs PMEM/SCSI BlockRootfs 未完整实现，不能和 VM rootfs kernel 参数混写
hypervisor 看到什么 virtio-fs/block/vsock/port 设备
agent 看到什么 Storage/OCI spec/devices/shared_mounts
guest 最终由谁创建进程 kata-agent/rustjail

这解释了 Kata 与 Firecracker 的差异：Firecracker 自身只提供 block/net/vsock VMM 设备；Kata 还要把 Kubernetes/OCI 的 mount/rootfs/volume 语义落到 guest。

11. ARM64 与 x86_64

runtime-rs rootfs/volume 分类逻辑不按架构分叉。分叉点在 block driver/virtio transport/hypervisor capability：BlockRootfs::new() 按 VIRTIO_BLK_PCI/VIRTIO_BLK_MMIO/VIRTIO_BLK_CCW 选 PCI path/virt path/CCW address；x86_64 偏 PCI/ACPI，ARM64 偏 MMIO/FDT/GIC（取决于 QEMU/Dragonball/CH/FC plugin）。guest agent storage handler 也体现 transport 差异（virtio-blk-mmio/pci 共享，s390x 才有 ccw）。

Kata ARM64 风险不是"runtime 不会构造 rootfs"，而在 guest kernel 是否支持对应 virtio-fs/block/pmem/erofs/nydus、VMM 是否支持该 transport、设备路径能否被 agent handler 识别。多层 EROFS 是独立 rootfs 路径，会生成多个 block storage + overlay，有设备数量上限，可能消耗 PCI slot。
