    Kata Containers ARM64 网络观测指南

    本文承接 ARM64 网络能力边界矩阵。

    前一篇回答“能力边界在哪里”。

    本文继续回答“ARM64 网络出问题时，最先会在哪一层暴露，以及该看哪些源码锚点”。

    源码基线：当前工作树。

    1. 核心结论

    Kata ARM64 网络问题通常不是在一个地方爆出来。

    它更像四层递进：

    1. host runtime 是否接受当前 machine/IOMMU 组合。
    2. endpoint/hotplug 是否真的把网卡接进 VM。
    3. guest agent 是否能按 ARM64 的 PCI/sysfs 路径找到设备。
    4. backend 差异是否改变了网络设备的接入方式。

    所以排查顺序不能反过来。

    如果一上来就盯 guest 内 eth0，很容易错过更早的 machine 或 hotplug 失败。

    2. 总体观测图

    flowchart TB Host["host runtime / qemu config"] --> Attach["endpoint attach / hotplug"] Attach --> Guest["guest agent device discovery"] Guest --> Backend["backend-specific behavior"]

    这四层的关系是单向依赖。

    前一层没过，后一层看到的多数只是连带症状。

    3. 第一层：host runtime 最早暴露的 ARM64 错误

    ARM64 QEMU 路径最早的边界，在 newQemuArch()。

    如果 machine 不是 virt，它会直接返回：

    unrecognised machinetype: ...

    源码依据：qemu_arm64.go。

    这是最早也最干净的一类错误。

    它说明根本还没进入网络设备阶段。

    第二类更明确的边界是 appendIOMMU()。

    ARM64 这里直接返回：

    Arm64 architecture does not support vIOMMU

    源码依据：qemu_arm64.go。

    这类错误的意义也要说清楚。

    它并不等于“ARM64 不支持网络”。

    它只说明：当前网络或设备组合依赖了 x86 风格的 vIOMMU 假设，而 ARM64 QEMU 路径明确不接受。

    4. 第二层：endpoint 与 hotplug 会先暴露什么

    启动后、但在 guest 配网之前，最关键的信号在 RescanNetwork() 和 configureGuestNetwork()。

    RescanNetwork() 会先打印：

    waiting for network interfaces in namespace

    源码依据：sandbox.go。

    如果 5 秒内仍没发现 endpoint，它会打印：

    no network interfaces found after timeout — networking may be configured by prestart hooks

    源码依据：sandbox.go。

    一旦发现 endpoint，configureGuestNetwork() 会打印：

    configuring hotplugged network in guest

    源码依据：sandbox.go。

    这三条信号可以把问题切成两类：

    1. host netns 里根本没发现接口。
    2. 接口发现了，但后续 agent 配置可能失败。

    如果连 configuring hotplugged network in guest 都没有，就不该先怀疑 guest 路由逻辑。

    5. 第三层：agent RPC 会怎样暴露失败

    Go runtime 的 kataAgent.updateInterface() 对 “Link not found” 会自动重试 20 次。

    如果仍失败，它会打：

    update interface request failed

    并把 requested/resulting interface 一起写进日志。

    源码依据：kata_agent.go。

    updateRoutes() 失败时也会打：

    update routes request failed

    源码依据：kata_agent.go。

    这两条日志的意义不同。

    update interface request failed 更偏设备可见性或接口定位问题。

    update routes request failed 更偏 guest 内路由状态问题。

    因此看到 routes 失败时，不应该立刻怀疑 hotplug 本身。

    而看到 interface 失败时，则必须先回溯 endpoint 和 guest 设备发现。

    6. 第四层：guest agent 的 ARM64 特有风险点

    guest agent 在处理 update_interface 时，如果 devicePath 不为空，会先等网络接口出现。

    非 s390x 路径统一走：

    wait_for_pci_net_interface(...)

    源码依据：rpc.rs。

    真正的 ARM64 差异不在这里的函数名。

    差异在它依赖的 PCI root bus path。

    linux_abi.rs 对 aarch64 的实现，会先查 ACPI 路径。

    查不到时，再扫描 /devices/platform/*.pcie/...

    源码依据：linux_abi.rs。

    所以 ARM64 下最常见的设备发现问题，不该被概括成“guest 没网卡”。

    更准确的说法是：

    guest agent 可能在 sysfs 根路径选择上失败，导致明明设备已经存在，却仍返回 interface not available。

    这也是 ARM64 与 x86_64 真正分叉的观测点。

    7. 第五层：guest netlink 更新不代表和 x86_64 一样稳定

    update_interface() 在 guest 内按 MAC 查 link。

    它会处理重命名、IPv6 开关、地址重建和 name 冲突。

    源码依据：netlink.rs。

    这说明 ARM64 下哪怕设备已经被找到，仍然可能在更晚一层失败。

    例如：

    1. 新接口名与已有接口冲突。
    2. IPv6 开关状态与地址族不一致。
    3. MAC 虽匹配，但接口状态未准备好。

    因此 ARM64 的“设备可见”仍不等于“guest 网络 ready”。

    8. runtime-rs：后端差异如何改变观测点

    runtime-rs QEMU backend 的网络 hotplug 会在 hotplug_device() 里检查 QMP。

    如果 QMP 没初始化，会直接返回：

    QMP not initialized

    源码依据：qemu/inner.rs。

    Cloud Hypervisor backend 则走 open_named_tuntap() 和带 fd 的 netdev add。

    源码依据：ch/inner_device.rs。

    Dragonball backend 直接构造 Dragonball net config 并 insert_network_device()。

    源码依据：dragonball/inner_device.rs。

    这意味着 Kata ARM64 网络问题不能只按“架构”切分。

    同样是 ARM64：

    1. QEMU 路径更容易在 QMP/hotplug 阶段暴露错误。
    2. Cloud Hypervisor 路径更容易在 tap/fd/open_named_tuntap 阶段暴露错误。
    3. Dragonball 路径更像直接插设备配置，问题边界又不同。

    9. 推荐的排查顺序

    建议把 ARM64 Kata 网络问题固定按这四步排查。

    第一步：先看 host runtime 配置。

    重点看 machine type 和 IOMMU 组合，确认没有 unrecognised machinetype 或 does not support vIOMMU。

    第二步：再看 endpoint 与 hotplug。

    重点看是否出现 waiting for network interfaces in namespace、超时告警或 configuring hotplugged network in guest。

    第三步：再看 guest agent。

    重点看 update interface request failed、update routes request failed，以及 guest agent interface not available。

    第四步：最后再分 backend。

    重点区分当前是 QEMU、Cloud Hypervisor 还是 Dragonball 路径。

    10. 最小观测表

    层级 优先信号 常见失败锚点
    host runtime QEMU arm64 初始化成功 unrecognised machinetype
    IOMMU/device model 网络不依赖 vIOMMU Arm64 architecture does not support vIOMMU
    endpoint discovery waiting for network interfaces... 后出现 endpoint no network interfaces found after timeout
    guest config start configuring hotplugged network in guest updating interface ... in guest 错误
    Go agent RPC 接口和路由 RPC 成功 update interface request failed / update routes request failed
    guest agent PCI 路径找到接口 interface not available
    backend-specific QMP/tap/insert_network_device 成功 QMP not initialized / open named tuntap / insert network device

    11. 结论

    Kata ARM64 网络的关键，不是再重复说一次“控制面基本共享”。

    真正重要的是知道：

    哪类错误会在 host runtime 先失败，哪类错误会在 guest agent 才暴露，以及 backend 差异会把失败点推到哪里。

    这就是这篇文档的用途。
