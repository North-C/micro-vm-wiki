Kata runtime-rs ResourceManager 资源设备链路

本文展开 runtime-rs 非机密计算资源链路：sandbox 启动资源 → ResourceManager → DeviceManager → Hypervisor.add_device，以及 container 创建资源 → rootfs/volume/device → agent CreateContainerRequest。

源码基线：当前仓库工作树。Kata CoCo 暂不展开。

相关：runtime-rs Hypervisor Plugin 生命周期、Share-fs/Rootfs/Volume 到 Agent、runtime-rs Manager 请求分发。

0. 术语与背景

资源处理的两个"ready"阶段

阶段 谁做 产出
VM ready（sandbox 启动） ResourceManager.prepare_before_start_vm → DeviceManager → Hypervisor.add_device share-fs/network/block/vsock 进 VM
container ready（container 创建） Container::create → rootfs/volume/device → agent guest path/storages/devices/OCI spec

关键：VM 启动成功 ≠ sandbox ready（还要 agent 连接 + 启动后资源同步 + CreateSandboxRequest）；设备 attach 成功 ≠ container 可用（rootfs/volume/device 还要转成 guest path/agent storage/agent device/OCI mount）。

DeviceManager 是 host 侧设备抽象中枢

把 DeviceConfig 变成具体 Device，经 Device::attach() 调 Hypervisor.add_device()。但 agent 不是设备热插拔唯一入口——host 侧设备先经 hypervisor 进 VM，guest 内网络/storage/mount/container 语义再经 agent RPC 收敛。

能力边界随 VMM plugin 不同

runtime-rs 对上层暴露统一 Hypervisor.add_device()，但各 VMM（QEMU/CH/Firecracker/Dragonball）接收的设备类型不同。Kata 能力边界 ≠ DeviceConfig 枚举本身——必须看当前 hypervisor plugin 是否真正实现该 DeviceType。

1. 核心结论

  • 两条链路：① sandbox 启动（VirtSandbox::start 生成 ResourceConfig → ResourceManager 转 share-fs/network/block/vsock/port 设备）；② container 创建（Container::create 处理 rootfs/volume/device → CreateContainerRequest）。
  • DeviceManager 是 host 侧设备中枢：DeviceConfig → 具体 Device → Device::attach() → Hypervisor.add_device()。
  • agent 不是唯一入口；host 设备先经 hypervisor 进 VM，guest 语义经 agent RPC 收敛。

2. 总体流程图

VM ready、sandbox ready、container ready 是三个阶段。

3. Sandbox 启动资源生成

VirtSandbox::start() 顺序固定：prepare_vm → prepare_for_start_sandbox → prepare_before_start_vm → start_vm → 连 agent → setup_after_start_vm → create_sandbox（sandbox.rs:593）。prepare_for_start_sandbox() 生成启动前资源（VM socket → network → share-fs → VM rootfs block → PCIe port，:160）。ResourceConfig 枚举覆盖 network/share-fs/VM rootfs/hybrid-vsock/vsock/port/protection。

资源还没全部变成 agent 请求——启动前能插 VM 的部分先落 hypervisor 设备模型。

4. 启动前资源如何变成设备

prepare_before_start_vm() 遍历 ResourceConfig 按类型处理（manager_inner.rs:150）：share-fs 检查 capability + setup_device_before_start_vm + sandbox bind mount；VM rootfs/vsock/port 转成 DeviceConfig 经 do_handle_device() 进 DeviceManager。network 单独走 handle_network()——专门建 OS thread + 单线程 tokio runtime，避免 async 线程切换丢 netns 上下文：

// src/runtime-rs/crates/resource/src/manager_inner.rs:220
pub async fn handle_network(&mut self, network_config: NetworkConfig) -> Result<()> {
    let network = thread::spawn(move || -> Result<Arc<dyn Network>> {     // 专门 OS thread
        let rt = runtime::Builder::new_current_thread().enable_io().build()?;  // 单线程 tokio runtime
        let d = rt.block_on(network::new(&network_config, device_manager))?;
        rt.block_on(d.setup())?;
        Ok(d)
    }).join()??;   // block_on 保证 netns 上下文不丢
    self.network = Some(network);
}

5. DeviceManager 的真实边界

// src/runtime-rs/crates/hypervisor/src/device/device_manager.rs:93
pub struct DeviceManager {
    devices: HashMap<String, ArcMutexDevice>, hypervisor: Arc<dyn Hypervisor>,
    shared_info: SharedInfo, pcie_topology: Option<PCIeTopology>,
}
// :578  do_handle_device 三步
pub async fn do_handle_device(d: &RwLock<DeviceManager>, dev_info: &DeviceConfig) -> Result<DeviceType> {
    let device_id = d.write().await.new_device(dev_info).await?;          // (1) 建具体设备
    d.write().await.try_add_device(&device_id).await?;                     // (2) attach
    let device_info = d.read().await.get_device_info(&device_id).await?;   // (3) 返回 DeviceType
    Ok(device_info)
}

new_device() 按 DeviceConfig 创建 BlockDevice/NetworkDevice/ShareFsDevice/VfioDevice/VsockDevice（:288），且对 block/network/share-fs/vfio 先 find_device 复用同 host path 的已注册设备。具体设备经 Device::attach() 调 Hypervisor.add_device()：

// src/runtime-rs/crates/hypervisor/src/device/driver/virtio_blk.rs:163
impl Device for BlockDevice {
    async fn attach(&mut self, _pcie_topo, h: &dyn hypervisor) -> Result<()> {
        if self.increase_attach_count().await? { return Ok(()); }          // 引用计数，已 attach 则复用
        match h.add_device(DeviceType::Block(self.clone())).await {
            Ok(dev) => { if let DeviceType::Block(blk) = dev { self.config = blk.config; } Ok(()) }
            Err(e) => { self.decrease_attach_count().await?; Err(e) }
        }
    }
}
// virtio_net.rs:73 / virtio_fs.rs:101 同模式，只是 DeviceType::Network / ShareFs

6. VM 启动后的 agent 同步

start_vm() 后先执行 OCI hook（hook 可能改 netns → 重新扫描处理网络，sandbox.rs:615），再获 agent socket + agent.start() + setup_after_start_vm()：

// src/runtime-rs/crates/resource/src/manager_inner.rs:299
pub async fn setup_after_start_vm(&mut self) -> Result<()> {
    self.cgroups_resource.setup_after_start_vm(self.hypervisor.as_ref()).await?;
    if let Some(share_fs) = &self.share_fs { share_fs.setup_device_after_start_vm(self.hypervisor.as_ref(), &self.device_manager).await?; }
    if let Some(network) = self.network.as_ref() {
        self.handle_interfaces(network).await?;     // network interfaces/ARP/routes 同步给 agent
        self.handle_neighbours(network).await?;
        self.handle_routes(network).await?;
    }
}

最后 CreateSandboxRequest 带 sandbox storages（来自 share-fs backend + sandbox shm tmpfs，sandbox.rs:685/manager_inner.rs:330）。

7. Container 创建资源链路

container 阶段从 Container::create() 开始：handler_rootfs（改写 OCI root path + rootfs storage）→ handler_volumes（OCI mount + storage）→ handler_devices。device 阶段读 OCI Linux devices，block device 转 BlockConfig attach + 按 PCI/SCSI/CCW/virt 构造 agent device：

// src/runtime-rs/crates/resource/src/manager_inner.rs:410
pub async fn handler_devices(&self, _cid, linux: &Linux) -> Result<Vec<ContainerDevice>> {
    for d in linux.devices().iter() {
        match d.typ() {
            LinuxDeviceType::B => {
                let dev_info = DeviceConfig::BlockCfg(BlockConfig { major: d.major(), minor: d.minor(), /*...*/ });
                let device_info = do_handle_device(&self.device_manager, &dev_info).await?;
                if let DeviceType::Block(device) = device_info {
                    let id = if let Some(pci_path) = device.config.pci_path { pci_path.to_string() }   // agent device id 优先级
                        else if let Some(scsi) = device.config.scsi_addr { scsi }
                        else if let Some(ccw) = device.config.ccw_addr { ccw } else { device.config.virt_path.clone() };
                    devices.push(ContainerDevice { device: Device { id, container_path, /*...*/ }, /*...*/ });
                }
            }
            // ... other device types ...
        }
    }
}

最后 CreateContainerRequest 携带 process_id/storages/oci/devices/shared_mounts/passfd IO ports（container.rs:260）。

8. Rootfs / Volume 分支（详见 sharefs 文档）

RootFsResource::handler_rootfs()（rootfs/mod.rs:78）分类：空 rootfs mounts 依赖 share-fs；多层 erofs 走 ErofsMultiLayerRootfs；单层 block rootfs → BlockRootfs；nydus/普通共享 → ShareFsRootfs；guest pull → VirtualVolume。VolumeResource::handler_volumes()（volume/mod.rs:65）按 OCI mount 类型选 shm/local/ephemeral/block/direct/hugepage/share-fs/default。block volume 构造 BlockConfig + DeviceManager attach + 生成 agent storage + OCI mount（block_volume.rs:31）。

详见 Share-fs/Rootfs/Volume 到 Agent 链路。

9. VMM plugin 设备边界（能力随 plugin 不同）

// QEMU（hypervisor/src/qemu/inner.rs:816）
pub(crate) async fn add_device(&mut self, mut device: DeviceType) -> Result<DeviceType> {
    if self.qmp.is_some() { device = self.hotplug_device(device)? }   // VM ready → hotplug network/block/VFIO
    else { self.devices.push(device.clone()); }                       // 未 ready → 存 self.devices
}
// Cloud Hypervisor（ch/inner_device.rs:52）
pub(crate) async fn add_device(&mut self, device: DeviceType) -> Result<DeviceType> {
    if self.state != VmState::VmRunning {
        match device { DeviceType::ShareFs|Network|Vfio|Protection(_) => self.pending_devices.insert(0, device),  // 未运行 → pending
            _ => { /* ignoring early add */ } }
        return Ok(device);
    }
    // ... 运行中 handle_add_device 分发 ...
}
// Firecracker（firecracker/inner_device.rs:18）
match device {
    DeviceType::Block(block) => self.hotplug_block_device(/*...*/),   // 只 block/net/hybrid-vsock/vsock
    DeviceType::Network(network) => self.add_net_device(/*...*/),
    DeviceType::HybridVsock|Vsock(_) => /* add vsock */,
    _ => Err(anyhow!("unhandled device")),                            // 不支持 share-fs
}

Kata 能力边界 ≠ DeviceConfig 枚举：QEMU 未 ready 时存 self.devices + ready 后 hotplug；CH 未运行存 pending（share-fs/network/VFIO/protection）；Firecracker 只 block/net/vsock，明确不支持 share-fs；Dragonball 支持 network/VFIO/block/vhost-user block/share-fs/vhost-user net（dragonball/inner_device.rs:41）。

10. ARM64 与 x86_64 / 能力边界

ResourceManager/DeviceManager/agent request 组织方式架构中性。差异在三层：① hypervisor plugin 是否在目标架构编译；② VMM 是否支持对应设备；③ guest kernel 是否识别该 transport。block device agent id 选择按 PCI path/SCSI/CCW/virt 优先级（已体现总线差异，manager_inner.rs:434）。QEMU runtime-rs rootfs kernel params：aarch64 关闭 DAX，非 aarch64 默认开（cmdline_generator.rs:181）。VFIO host 检查：x86/x86_64 要求 cmdline iommu=，ARM 由 BIOS 设置不走该检查（vfio.rs:683）。

五个能力边界：① VM 启动成功 ≠ sandbox ready；② 设备 attach 成功 ≠ container 可用（rootfs/volume/device 还要转 guest path/agent storage/device/OCI mount）；③ share-fs 是 capability 驱动（Firecracker 无 share-fs）；④ network ready 含 host endpoint/VM NIC/guest interface-route 三层（handle_network + agent RPC 两阶段）；⑤ ARM64/x86_64 差异不能只从 runtime-rs 抽象判断，需沿 hypervisor plugin/guest kernel/transport 追踪。
