    Kata Containers ARM64 网络准样本：Guest Agent 设备发现失败

    本文承接 ARM64 网络观测指南 和 ARM64 网络失败原型。

    这不是一份真实故障回放。

    它是一份围绕 interface not available 和 update interface request failed 整理出的准样本。

    它对应的是 Kata ARM64 网络线上最典型的中层失败：

    host 已经在做网络接入，但 guest agent 仍无法稳定定位接口。

    源码基线：当前工作树。

    1. 样本定位

    这份准样本不处理最早的 machine/IOMMU 失败。

    它假设系统已经往前走到了：

    1. endpoint 扫描
    2. guest 网络结构生成
    3. agent UpdateInterface

    但在 guest 设备发现这一步卡住了。

    这正是 ARM64 与 x86 最容易真正分叉的地方。

    2. 场景入口

    如果 RescanNetwork() 发现 endpoint，它会调用 configureGuestNetwork()。

    这里会先打印：

    configuring hotplugged network in guest

    然后把 endpoint 转成 interfaces 和 routes。

    随后逐个调用 agent updateInterface()。

    源码依据：sandbox.go。

    这意味着一旦看到这条日志，问题已经晚于：

    1. machine 选择
    2. vIOMMU 组合
    3. host netns 完全无接口

    3. guest agent 的真实失败点

    guest agent 处理 update_interface 时，如果 devicePath 不为空，会先等待 PCI net interface。

    非 s390x 路径统一走：

    wait_for_pci_net_interface(...)

    如果等待失败，agent 返回：

    interface not available: ...

    源码依据：rpc.rs。

    这条错误不是“guest 完全没网卡”的简单说法。

    更准确地说，它表示：

    agent 没能按当前 devicePath 和 guest PCI/sysfs 结构稳定定位到目标接口。

    4. Go runtime 会怎样暴露这个失败

    Go 侧 kataAgent.updateInterface() 对包含 Link not found 的错误会做 20 次重试。

    如果仍失败，会带上 requested/resulting interface 打出：

    update interface request failed

    源码依据：kata_agent.go。

    因此这一类准样本通常会同时有两条信号：

    1. guest agent 侧：interface not available
    2. host runtime 侧：update interface request failed

    5. ARM64 的关键差异在哪里

    ARM64 的关键差异不在 update_interface 这个 RPC 名字。

    而在它依赖的 PCI root bus path。

    agent 的 linux_abi.rs 在 aarch64 下，会先尝试 ACPI 路径。

    如果找不到，再 fallback 到 platform PCIe controller 路径。

    这就是 ARM64 最容易出现“设备其实出来了，但 agent 仍定位不到”的根本原因。

    这一点在 ARM64 网络能力边界矩阵 里已经单独压过。

    6. 准样本结构

    这类样本的最小结构建议如下：

    [Scenario]
arch = arm64
hypervisor = qemu / cloud-hypervisor / dragonball
stage = configureGuestNetwork -> updateInterface

[Host Signals]
info = configuring hotplugged network in guest
error = update interface request failed

[Guest Agent Signals]
error = interface not available: <...>

[Classification]
layer = guest device discovery
after = endpoint attach / hotplug
before = route convergence

    7. 它实际证明了什么

    如果出现 configuring hotplugged network in guest，说明 endpoint 已经被发现。

    如果随后出现 interface not available 或 update interface request failed，说明失败点已经推进到：

    guest agent 设备发现 / 接口定位

    这时不该优先回头怀疑：

    1. machine 不是 virt
    2. vIOMMU 不支持
    3. host netns 完全没有 endpoint

    因为这些更早层级通常会先爆出更明确的错误。

    8. 与 update routes request failed 的区别

    这份准样本故意不把 update routes request failed 混进来。

    原因很简单。

    route 失败比 interface 失败更晚一层。

    如果已经看到 route 失败，往往说明接口层至少部分成功了。

    而本样本要固定的是更关键的中层边界：

    接口还没真正被 guest agent 接住。

    9. 后端差异怎么读

    这份准样本还应保留当前 hypervisor backend。

    因为同样的 update interface request failed，前面的触发链可能不同。

    例如：

    1. QEMU runtime-rs 可能更早暴露 QMP not initialized
    2. Cloud Hypervisor runtime-rs 可能更早暴露 open named tuntap
    3. Dragonball runtime-rs 可能更早暴露 insert network device

    源码依据：

    1. qemu/inner.rs
    2. ch/inner_device.rs
    3. dragonball/inner_device.rs

    因此正式样本里，backend 字段不该省略。

    10. 升级为真实样本时建议保留什么

    如果后续拿到真实 ARM64 故障日志，建议至少保留：

    1. scenario.md
    2. host.txt
    3. agent.txt
    4. classification.md

    其中 classification.md 应明确写出：

    1. 为什么判断失败点在 guest device discovery
    2. 为什么不是更早的 machine/IOMMU 问题
    3. 为什么还没推进到 route convergence

    11. 结论

    guest agent 设备发现失败 是 Kata ARM64 网络线上最值得优先补成真实样本的一类准样本。

    因为它最能检验前面那套四层分法是否真的有用：

    machine / endpoint / guest discovery / backend
