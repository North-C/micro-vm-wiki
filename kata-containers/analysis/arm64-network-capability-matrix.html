    Kata Containers ARM64 网络能力边界矩阵

    本文承接 网络 Endpoint 到 Agent 链路 和 ARM64 与 x86_64 架构支持链路。

    目标不是重复描述 Kata 网络链路。

    目标是把普通非机密计算路径下，ARM64 与 x86_64 在网络能力上的真实边界压成一张源码驱动的矩阵。

    源码基线：当前工作树。

    1. 核心结论

    Kata 的 ARM64 网络控制面并没有单独重写一套实现。

    LinuxNetwork.AddEndpoints()、agent UpdateInterface/UpdateRoutes、runtime-rs handle_interfaces/handle_routes 基本都共享同一套逻辑。

    真正的 ARM64 差异，主要集中在四个地方：

    1. QEMU machine 被收敛为 virt，而不是 x86_64 的 q35/microvm 双路径。
    2. ARM64 QEMU 路径显式拒绝 vIOMMU。
    3. 网络 hotplug 能力是否成立，要看具体 hypervisor capability，而不是只看架构名。
    4. guest 侧 PCI/sysfs 发现路径与 x86_64 不同，设备可见不等于 agent 一定能稳定定位接口。

    因此 ARM64 网络的判断口径不应该是“支持/不支持网络”。

    更准确的说法是：控制面共享，但设备总线、IOMMU、hotplug 和 guest 设备发现的边界不同。

    2. 总体矩阵

    维度 x86_64 ARM64 关键源码依据
    host netns 扫描 LinuxNetwork.AddEndpoints() 共享实现 同一路径 network_linux.go
    agent 配网 UpdateInterface/UpdateRoutes 共享实现 同一路径 kata_agent.go
    默认 QEMU machine q35 virt qemu_amd64.go，qemu_arm64.go
    额外 machine microvm 可选 无 qemu_amd64.go，qemu_arm64.go
    network hotplug capability Q35 显式设置 arm64 继承 qemuArchBase qemu_amd64.go，qemu_arch_base.go
    vIOMMU x86 路径存在 appendIOMMU() 显式报错 qemu_arm64.go
    guest PCI 根路径 标准 PCI root bus ACPI 优先，platform PCIe fallback linux_abi.rs
    runtime-rs 网络设备 NetworkConfig 无架构字段 同一路径 virtio_net.rs
    runtime-rs QEMU net hotplug 依赖 QMP hotplug 同一接口，但受 virt/IOMMU/总线约束 qemu/inner.rs

    3. 控制面：ARM64 与 x86_64 共享的部分

    Kata 的 host 网络准备阶段对 ARM64 和 x86_64 基本不分叉。

    LinuxNetwork.AddEndpoints() 负责扫描 netns、创建 endpoint，并根据 hotplug 选择 Attach 或 HotAttach。

    源码依据：network_linux.go。

    Sandbox.configureGuestNetwork() 会把 endpoint 转成 interface 和 route，再逐个调用 agent updateInterface()，最后调用 updateRoutes()。

    源码依据：sandbox.go。

    运行期新增网卡也同样共享流程。

    Sandbox.AddInterface() 先把请求转成 NetworkInfo，调用 AddEndpoints(..., true)，再把 DevicePath 写回并调用 agent updateInterface()。

    源码依据：sandbox.go。

    所以如果只看控制面，ARM64 并没有“另一套网络栈”。

    这也是最容易误解的地方。

    共享控制面，不等于共享能力边界。

    4. QEMU machine：ARM64 被收敛到 virt

    Go virtcontainers 的 ARM64 QEMU 默认 binary 是 /usr/bin/qemu-system-aarch64。

    默认 machine 是 virt，默认 options 是 usb=off,accel=kvm,gic-version=host。

    源码依据：qemu_arm64.go。

    更关键的是，ARM64 newQemuArch() 会拒绝任何非 virt machine。

    源码依据：qemu_arm64.go。

    相比之下，x86_64 同时支持 q35 和 microvm。

    源码依据：qemu_amd64.go。

    这会直接影响网络设备能力的讨论。

    因为 ARM64 网络不是在“多 machine 选择”上调优，而是在 virt 这一个 machine 上受限。

    5. vIOMMU：ARM64 明确拒绝

    ARM64 的 appendIOMMU() 不是“暂未使用”。

    它直接返回：

    Arm64 architecture does not support vIOMMU

    源码依据：qemu_arm64.go。

    这意味着凡是依赖 Intel-style vIOMMU 的网络推导，在 ARM64 Kata QEMU 路径里都不能直接照搬。

    例如：

    1. 某些 VFIO/network 组合能力不能按 x86_64 经验类推。
    2. 某些 IOMMU 相关 network hotplug 路径要单独看 hypervisor plugin 能力。

    这也是 ARM64 网络能力边界里最明确的一条源码结论。

    6. network hotplug：不是简单的“有/没有”

    QEMU 公共基类 qemuArchBase.capabilities() 默认会设置 network hotplug。

    源码依据：qemu_arch_base.go。

    x86_64 的 qemuAmd64.capabilities() 则在 q35 场景显式设置 block 和 network hotplug。

    源码依据：qemu_amd64.go。

    ARM64 qemuArm64 没有覆写这段能力逻辑，因此它继承的是公共基类。

    源码依据：qemu_arm64.go。

    这说明：

    1. 从 runtime 抽象层看，ARM64 不是“完全无 network hotplug”。
    2. 但它的真实可用性仍受 virt machine、总线、QMP 实现和 guest 设备发现影响。

    所以对 ARM64 网络 hotplug 的正确判断不是“代码里有没有 capability bit”。

    而是 capability bit 加上 machine 约束，加上 guest agent 实际能否看见设备。

    7. guest 侧设备发现：ARM64 风险在 sysfs 根路径

    Kata 的 guest agent 处理网络设备时，在非 s390x 场景下走 PCI net device 发现。

    源码依据：network_device_handler.rs。

    而 ARM64 与 x86_64 的关键差异，在于 PCI root bus path 的构造不同。

    x86_64 使用标准 PCI root bus 路径。

    ARM64 先尝试 ACPI 路径；如果不存在，再 fallback 到 /sys/devices/platform/*.pcie 这类 platform PCIe controller 路径。

    源码依据：linux_abi.rs。

    这意味着 ARM64 下最值得验证的不是“guest 内有没有网卡”这么粗的判断。

    而是：

    1. runtime 传入的 DevicePath 是否和 guest 真实 sysfs 路径兼容。
    2. agent 等待 PCI net interface 时，是否会落到 fallback 路径。
    3. guest 内设备可见后，agent 是否还能稳定按 MAC 和路径定位到同一接口。

    8. runtime-rs：网络设备结构共享，但后端行为不同

    runtime-rs 的 NetworkConfig 并没有架构字段。

    它只描述 host device name、guest iface name、guest MAC、queue size 等通用属性。

    源码依据：virtio_net.rs。

    NetworkDevice.attach() 只调用 hypervisor trait 的 add_device(DeviceType::Network(...))。

    源码依据：virtio_net.rs。

    所以 runtime-rs 层面对 ARM64/x86_64 的差异并不显式表达。

    差异被下沉到了具体后端：

    1. QEMU 路径通过 QMP 做 network hotplug。
    2. Cloud Hypervisor 路径把 NetworkConfig 转成 NetConfig。
    3. Dragonball 路径构造 Dragonball network config。

    源码依据：qemu/inner.rs，ch/inner_device.rs。

    另见：dragonball/inner_device.rs。

    因此 ARM64 网络在 runtime-rs 里的正确分析方式，不是找架构专属配置结构。

    而是比较不同 hypervisor backend 在 ARM64 上到底暴露了什么能力。

    9. Dragonball、Cloud Hypervisor、Firecracker 的网络边界

    Dragonball 在 runtime-rs 中有显式的 network device 插入路径。

    源码依据：dragonball/inner_device.rs。

    Cloud Hypervisor 路径会把网络设备转成 CH 的 NetConfig，并关注 queue pair 和 tap 打开位置。

    源码依据：ch/inner_device.rs。

    Firecracker 则根本不支持通用设备 hotplug。

    这在其代码注释里写得很清楚。

    源码依据：firecracker/fc_api.rs。

    这意味着 Kata 的 ARM64 网络能力，还要继续分成“后端相关”。

    同样是 ARM64：

    1. QEMU/Cloud Hypervisor/Dragonball 的能力边界并不相同。
    2. Firecracker 路径不能按通用 hotplug 网络模型理解。

    10. ARM64 与 x86_64 的最小判断表

    flowchart TB Shared["shared control plane"] --> Machine["machine constraints"] Machine --> IOMMU["IOMMU / bus constraints"] IOMMU --> Agent["guest path discovery"] Agent --> Runtime["actual network ready"]

    可以把 Kata 普通网络的 ARM64 判断压缩成下面这张表：

    问题 x86_64 ARM64
    netns 扫描与 endpoint 创建 共享实现 共享实现
    agent UpdateInterface/Routes 共享实现 共享实现
    QEMU machine 选择 q35/microvm virt only
    vIOMMU 可能存在 明确不支持
    guest 设备发现 标准 PCI root 更常见 ACPI 优先，platform PCIe fallback
    network hotplug Q35 路径更成熟 依赖 base capability + virt machine + guest 发现
    backend 差异 QEMU/CH/DB/FC 各异 同样各异，不能只看架构名

    11. 结论

    Kata 的 ARM64 网络不是“单独一套控制面”，而是“共享控制面 + 更强的 machine/device/path 约束”。

    如果只看 LinuxNetwork.AddEndpoints() 或 agent UpdateInterface()，会误以为 ARM64 与 x86_64 基本等价。

    真正决定边界的，是 virt machine、appendIOMMU() 的明确拒绝、后端 capability，以及 guest 侧 PCI/sysfs 路径发现。
