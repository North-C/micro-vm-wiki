    1. containerd shim v2：生命周期入口

    研究目标：理解 containerd 请求如何进入 Kata runtime，并变成 sandbox/container 操作。

    关键源码：

    • containerd shim 接口要求实现 TaskService、Cleanup、StartShim。
    • 源码依据：src/runtime/vendor/github.com/containerd/containerd/runtime/v2/shim/shim.go。
    • Kata shim v2 的 New() 初始化 service，读取 namespace，创建 container map、event channel、exit channel，启动 processExits() 和 events forwarder。
    • 源码依据：src/runtime/pkg/containerd-shim-v2/service.go。
    flowchart LR Containerd["containerd TaskService"] --> Shim["kata shim v2 service"] Shim --> Events["events forwarder"] Shim --> Exits["processExits"] Shim --> VC["virtcontainers"]

    机制结论：

    1. shim v2 是 Kata 的 containerd 接入层，负责事件、退出状态、namespace 和 service 生命周期。
    2. 真正的 VM/sandbox 逻辑下沉到 virtcontainers 或 runtime-rs。
    3. 事件转发和 exit 处理是理解 Kata 行为的关键，不应只看 create/start。

    继续深入点：

    • 逐个追踪 Create、Start、Exec、Delete、Shutdown。
    • 建立 containerd TaskService request 到 virtcontainers method 的映射表。
    • 分析 shim 崩溃恢复和 state persist。

    专题展开：shim v2 Exit / Event / Recovery 链路。

    结论是 Wait 读取 container/exec 的 exitCh，TaskExit 由后台 wait() 通过 s.ec -> processExits -> event forwarder 发布。

    persist/recover 的权威在 virtcontainers 层，不在 shim service 的内存 channel 与 container map。

    2. runtime-rs manager：请求到 VirtContainer

    研究目标：理解 Rust runtime 线如何组织 sandbox/container 请求。

    建议路线：

    flowchart LR Request["SandboxRequest / TaskRequest"] --> Manager["runtime-rs manager"] Manager --> Sandbox["sandbox object"] Sandbox --> Hypervisor["Hypervisor trait"] Sandbox --> Agent["agent client"] Sandbox --> Resource["resource/device/network"]

    研究重点：

    1. Manager 如何区分 sandbox 级请求与 container/task 级请求。
    2. Sandbox 对象如何持有 hypervisor、agent、resource manager。
    3. Rust 线与 Go virtcontainers 线的状态模型是否一致。

    验证建议：

    • 用 CodeGraph 分别查 SandboxRequest、TaskRequest、VirtContainer。
    • 对比 runtime-rs 和 Go runtime 在 create/start/delete 的调用顺序。
    • 检查 persist/restore 数据结构是否兼容。

    3. Hypervisor plugin：Dragonball、Cloud Hypervisor、Firecracker

    研究目标：理解 Kata 的 hypervisor 抽象如何屏蔽不同 VMM。

    已确认源码：

    • runtime-rs Dragonball 实现 Hypervisor trait，提供 prepare_vm、start_vm、stop_vm、wait_vm、pause_vm、resume_vm 和 save_vm 等 VM 生命周期能力。
    • 它还提供 resize_vcpu、add_device、remove_device、get_agent_socket、cleanup 等能力：src/runtime-rs/crates/hypervisor/src/dragonball/mod.rs。
    • Firecracker 也实现同一 Hypervisor trait，但 get_passfd_listener_addr() 返回 not supported。
    • 这说明不同 VMM 的 capability 并不完全一致：src/runtime-rs/crates/hypervisor/src/firecracker/mod.rs。
    flowchart TB Kata["Kata sandbox"] --> HV["Hypervisor trait"] HV --> DB["Dragonball"] HV --> FC["Firecracker"] HV --> CH["Cloud Hypervisor"] HV --> QEMU["QEMU"]

    机制结论：

    1. Kata 的 hypervisor abstraction 是能力并集，不是每个实现都完整支持所有方法。
    2. Dragonball 在 runtime-rs 路径中是深度集成实现，支持 VM start/stop/pause/resume/save/device/memory/capabilities。
    3. Firecracker 支持核心生命周期，但部分 fd/listener/device 能力可能缺失。

    继续深入点：

    • 对比 add_device/remove_device/update_device 的实现边界。
    • 分析 save_vm 与 Kata persist state 的关系。

    4. agent RPC：guest 内 container 生命周期

    研究目标：理解 Kata 如何把 container 操作转发到 guest agent。

    关键源码：

    • agent ttrpc client 提供 container 生命周期 RPC，例如 CreateContainer、StartContainer、RemoveContainer、ExecProcess、SignalProcess 和 WaitProcess。
    • 它还提供 update、stats、pause/resume、interface 和 route 相关 RPC：src/runtime/virtcontainers/pkg/agent/protocols/grpc/agent_ttrpc.pb.go。
    sequenceDiagram participant Runtime as Kata runtime participant AgentClient as agent ttrpc client participant Guest as kata-agent participant Jail as guest runtime/runc-like Runtime->>AgentClient: CreateContainer AgentClient->>Guest: ttrpc grpc.AgentService/CreateContainer Runtime->>AgentClient: StartContainer AgentClient->>Guest: StartContainer Guest->>Jail: create/start process

    机制结论：

    1. VM 内 agent 是 Kata container 生命周期的实际执行者。
    2. host runtime 不直接在 host 创建 workload 进程。
    3. 网络、路由、接口、ephemeral mounts 也通过 agent RPC 管 guest 内状态。

    继续深入点：
