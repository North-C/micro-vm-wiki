Kata runtime-rs Manager 请求分发链路

本文从源码追踪 Kata runtime-rs 非机密计算路径下的请求分发：ttrpc service、SandboxRequest/TaskRequest、RuntimeHandlerManager、RuntimeInstance、VirtSandbox 和 VirtContainerManager。

源码基线：当前仓库工作树。本文不展开 Kata CoCo/TDX/SEV/SNP/CCA 机密计算路径。

相关：runtime-rs Hypervisor Plugin 生命周期、runtime-rs ResourceManager 资源设备、Agent Container 生命周期。

0. 术语与背景

两条 API 线 + 一个 RuntimeInstance

runtime-rs 入口分 Sandbox API 和 Task API 两条线，都先转内部 enum 再由 RuntimeHandlerManager 分发。RuntimeInstance 是控制面的汇聚点，只有两个核心对象：

// src/runtime-rs/crates/runtimes/common/src/runtime_handler.rs:16
#[derive(Clone)]
pub struct RuntimeInstance {
    pub sandbox: Arc<dyn Sandbox>,              // 控 VM + agent ready
    pub container_manager: Arc<dyn ContainerManager>,  // 控 container/process + Task 语义
}

sandbox 生命周期与 container/process 生命周期被刻意拆开——sandbox 控 VM 和 agent ready，container manager 控 container/process 和 containerd Task 语义。

关键概念

  • lazy start：仅用 Task API 时，sandbox 在第一个 container create 时才启动（CreateTask 特殊路径），与显式 Sandbox API create/start 不完全同形。
  • ContainerProcess：用 (container_id, exec_id) 归一分类——空 exec id 或 container_id==exec_id 是 container init，非空是 exec。runtime-rs 不用 guest Linux pid 做 host 侧 process key。
  • host pid vs guest pid：对 containerd 暴露的 pid 是 shim/runtime-rs 进程 pid；guest workload pid 留在 guest agent/rustjail 内，host 用 container id + exec id 定位。

1. 核心结论

  • Sandbox API 的 CreateSandbox 只初始化 runtime instance；真正启动 VM/guest sandbox 在 StartSandbox 或 Task API CreateTask 的 lazy start 路径。
  • Task API 的 CreateTask 是 containerd 常用路径：加载 OCI spec → 初始化 runtime instance → sandbox.start() → 创建 container。
  • RuntimeInstance 只有两个对象（sandbox + container manager）。
  • runtime-rs 对 containerd 暴露的 pid 是 shim 进程 pid，guest workload pid 在 agent/rustjail 内。
  • ARM64/x86_64 差异不在 service/manager/container manager 主链，下沉到 hypervisor plugin/设备 transport/guest kernel/agent device handler。

2. 总体链路

3. 内部请求类型

TaskRequest 覆盖 containerd Task API（create/start/exec/kill/wait/delete/pause/resume/stats/update/pids/connect/close io），SandboxRequest 覆盖 Sandbox API（create/start/platform/stop/wait/status/ping/shutdown）：

// src/runtime-rs/crates/runtimes/common/src/types/mod.rs:30
pub enum TaskRequest {
    CreateContainer(ContainerConfig), StartProcess(ContainerProcess),
    ExecProcess(ExecProcessRequest), KillProcess(KillRequest), WaitProcess(ContainerProcess),
    DeleteProcess(ContainerProcess), StateProcess(ContainerProcess),
    PauseContainer(ContainerID), ResumeContainer(ContainerID),
    StatsContainer(ContainerID), UpdateContainer(UpdateRequest),
    Pid, ConnectContainer(ContainerID), CloseProcessIO(ContainerProcess),
    /* ShutdownContainer, ResizeProcessPTY */
}
// :148
pub enum SandboxRequest {
    CreateSandbox(Box<SandboxConfig>), StartSandbox(SandboxID), Platform(SandboxID),
    StopSandbox(StopRequest), WaitSandbox(SandboxID), SandboxStatus(/*...*/), Ping(SandboxID), ShutdownSandbox(SandboxID),
}

ContainerProcess::new() 的 init/exec 分类贯穿 start/wait/delete/signal：

// src/runtime-rs/crates/runtimes/common/src/types/mod.rs:113
impl ContainerProcess {
    pub fn new(container_id: &str, exec_id: &str) -> Result<Self> {
        let (exec_id, process_type) = if exec_id.is_empty() || container_id == exec_id {
            ("".to_string(), ProcessType::Container)   // init process
        } else {
            validate::verify_id(exec_id)?; (exec_id.to_string(), ProcessType::Exec)  // exec
        };
        Ok(Self { container_id: ContainerID::new(container_id)?, exec_id, process_type })
    }
}

4. Service 层转换 / RuntimeHandlerManager 初始化

service manager 把同一个 RuntimeHandlerManager 注册给 SandboxService 和 TaskService（service/src/manager.rs:143）。SandboxService::handler_message()/TaskService::handler_message() 把 ttrpc request 转内部 request（sandbox_service.rs:27、task_service.rs:28）。trans_from_shim.rs 把 CreateTaskRequest 转成 TaskRequest::CreateContainer(ContainerConfig)，StartRequest/WaitRequest/... 都先构造 ContainerProcess（exec id 语义在进 manager 前归一，:158/188）。

RuntimeHandlerManagerInner::try_init() 初始化 linux/wasm/virt runtime、读配置、处理 rootless/netns、静态资源 sizing（runtimes/src/manager.rs:160）。init_runtime_handler() 按 config.runtime.name 选 LinuxContainer/WasmContainer/VirtContainer，普通 Kata VM 走 VirtContainer::new_handler()（:111）。VirtContainer::new_instance() 建 hypervisor/agent/ResourceManager/VirtSandbox/VirtContainerManager 返回 RuntimeInstance（virt_container/src/lib.rs:101）——这是控制面汇聚点，hypervisor/agent/resource manager 从这里同时注入 sandbox 与 container manager。

5. Sandbox API 分发

handler_sandbox_message() 特殊处理 CreateSandbox——只初始化 runtime instance 后返回（manager.rs:435）。其余进 handler_sandbox_request()：StartSandbox 调 sandbox.start()、StopSandbox 调 sandbox.stop()、ShutdownSandbox 调 sandbox.shutdown()（:528）。Platform 直接返回 std::env::consts::OS/ARCH（来自 host runtime 不是 guest agent，:547）。Sandbox API start 返回的 pid 是 runtime-rs 进程 pid，不是 guest init pid（:542）。

6. Task API CreateTask 特殊路径（lazy start）

handler_task_message() 对 CreateContainer 做特殊处理——这是 lazy start 的核心：

// src/runtime-rs/crates/runtimes/src/manager.rs:453
pub async fn handler_task_message(&self, req: TaskRequest) -> Result<TaskResponse> {
    if let TaskRequest::CreateContainer(container_config) = req {
        let mut spec = oci::Spec::load(&bundler_path)?;                       // 加载 OCI spec
        self.task_init_runtime_instance(&mut spec, &state, &options).await?;  // 初始化 runtime instance
        let instance = self.get_runtime_instance().await?;
        instance.sandbox.start().await.context("start sandbox in task handler")?;  // lazy start sandbox
        let shim_pid = instance.container_manager.create_container(container_config, spec).await?;
        let pid = shim_pid.pid;
        tokio::spawn(async move {                                             // 后台 wait
            let _ = instance.sandbox.wait_process(container_manager, process_id, pid).await;
        });
        let event = TaskCreate { container_id, bundle, pid, ..Default::default() };  // TaskCreate 事件(pid=shim pid)
        msg_sender.send(Message::new(Action::Event(Arc::new(event)))).await?;
    }
}

仅用 Task API 时，sandbox 在第一个 container create 时 lazy start——与显式 Sandbox API create/start 不同形。

7. 普通 Task 分发

handler_task_request() 取 RuntimeInstance，拆 sandbox/container_manager/msg_sender，按 TaskRequest match（manager.rs:582，节选）：

// src/runtime-rs/crates/runtimes/src/manager.rs:582
match req {
    TaskRequest::CreateContainer(_) => Err(anyhow!("Unreachable")),   // CreateContainer 走 §6 特殊路径
    TaskRequest::StartProcess(process_id) => {
        let shim_pid = cm.start_process(&process_id).await?;
        tokio::spawn(async move { sandbox.wait_process(cm, process_id, pid).await });  // 后台 wait
        if process_type == ProcessType::Container { /* 发 TaskStart 事件 */ }
        Ok(TaskResponse::StartProcess(shim_pid))
    }
    TaskRequest::WaitProcess(process_id) => {
        let exit_status = cm.wait_process(&process_id).await?;
        if cm.is_sandbox_container(&process_id).await { sandbox.stop().await?; }   // 等 sandbox container 还 stop sandbox
        Ok(TaskResponse::WaitProcess(exit_status))
    }
    TaskRequest::DeleteProcess(process_id) => {
        let resp = cm.delete_process(&process_id).await?;
        if process_id.process_type == ProcessType::Container { /* 发 TaskDelete */ }
        Ok(TaskResponse::DeleteProcess(resp))
    }
    TaskRequest::ExecProcess(req) => { cm.exec_process(req).await?; /*...*/ }
    TaskRequest::KillProcess(req) => { cm.kill_process(&req).await?; /*...*/ }
    TaskRequest::PauseContainer(id) => { cm.pause_container(&id).await?; /*...*/ }
    TaskRequest::ResumeContainer(id) => { cm.resume_container(&id).await?; /*...*/ }
    TaskRequest::StatsContainer(id) => { let s = cm.stats_container(&id).await?; /*...*/ }
    TaskRequest::UpdateContainer(req) => { cm.update_container(req).await?; /*...*/ }
    // CloseProcessIO / StateProcess / ResizeProcessPTY / Pid / ConnectContainer / ShutdownContainer ...
}

8. VirtSandbox start

VirtSandbox 持 agent/hypervisor/ResourceManager/health monitor/sandbox config/状态（sandbox.rs:92）。start() 要求状态 Init，顺序是 VM 启动 → agent → CreateSandbox：

// src/runtime-rs/crates/runtimes/virt_container/src/sandbox.rs:568
async fn start(&self) -> Result<()> {
    let mut inner = self.inner.write().await;
    if inner.state != SandboxState::Init { return Ok(()); }            // 必须 Init
    self.hypervisor.prepare_vm(id, netns, &annotations, selinux_label).await?;
    let resources = self.prepare_for_start_sandbox(id, network_env).await?;
    self.resource_manager.prepare_before_start_vm(resources).await?;   // 设备先于 VM
    self.hypervisor.start_vm(10_000).await?;                           // 启动 VM
    self.execute_oci_hook_functions(&prestart, &create_runtime, &state).await?;  // OCI hook
    // hook 后可能重新处理网络资源
    let address = self.hypervisor.get_agent_socket().await?;
    self.agent.start(&address).await?;                                 // 连 agent
    self.set_agent_policy().await?;
    self.resource_manager.setup_after_start_vm().await?;
    self.agent.create_sandbox(CreateSandboxRequest { hostname, dns, storages, /*...*/ }).await?;
    inner.state = SandboxState::Running;                               // 进 Running
    // 启动 OOM watcher
}

顺序硬约束：prepare_before_start_vm（设备先于 VM）→ start_vm → OCI hook → agent.start + policy → setup_after_start_vm → create_sandbox → Running + OOM watcher（:568/615/664/704）。

9. VirtContainerManager / Container create

create_container() 建 Container、执行 create-container hooks、container.create(spec)、插入 map、返回 shim pid：

// src/runtime-rs/crates/runtimes/virt_container/src/container_manager/manager.rs:82
async fn create_container(&self, config: ContainerConfig, spec: oci::Spec) -> Result<PID> {
    let mut container = Container::new(self.pid, config.clone(), spec.clone(), self.agent.clone(),
        self.resource_manager.clone(), passfd_addr).await?;
    let vmm_master_tid = self.hypervisor.get_vmm_master_tid().await?;
    { /* NetnsGuard 内执行 create_container hooks，hook pid = vmm_master_tid */ }
    let mut containers = self.containers.write().await;
    container.create(spec).await?;                                     // → agent CreateContainerRequest
    containers.insert(container.container_id.to_string(), container);
    Ok(PID { pid: self.pid })                                          // 返回 shim pid
}

Container::create() 构造 agent::CreateContainerRequest（process id、storages、OCI spec、sandbox pidns、devices、shared mounts、passfd ports）发 agent（container.rs:259）。Container::new() 的 init process pid 字段是 shim pid 不是 guest pid（container.rs:57）。

这与 Go virtcontainers 一致：host runtime 准备资源和 spec，guest agent/rustjail 才真正创建 guest 内进程。

10. Start / Exec / IO / Wait

Container::start() 按 process type 分流：init 调 start_container()、exec 调 start_exec_process()（container.rs:293）。legacy IO 下 Process::start_io_and_wait() 起 stdin/stdout/stderr copy，IO 结束后才发 WaitProcessRequest（process.rs:242）；passfd IO 下 passfd_io_wait() 后台发 WaitProcessRequest（:177）。

VirtSandbox::wait_process() 是后台事件路径——等 container manager exit status 后发 TaskExit：

// src/runtime-rs/crates/runtimes/virt_container/src/sandbox.rs:880
async fn wait_process(&self, cm: Arc<dyn ContainerManager>, process_id: ContainerProcess, shim_pid: u32) -> Result<()> {
    let exit_status = cm.wait_process(&process_id).await?;
    if cm.is_sandbox_container(&process_id).await { self.stop().await?; }
    let cid = process_id.container_id();
    let eid = process_id.exec_id();
    let id = if eid.is_empty() { cid.to_string() } else { eid.to_string() };  // init 用 cid，exec 用 eid
    let event = TaskExit { container_id: cid.to_string(), id, pid: shim_pid,   // TaskExit.pid = shim pid
        exit_status: exit_status.exit_code as u32, /*...*/ };
    msg_sender.send(Message::new(Action::Event(Arc::new(event)))).await?;
}

与 Go shim 一致：containerd 看到的 pid 不是 guest workload pid，退出码来自 guest agent wait。

11. Stop / Delete / 资源释放

stop_process() 先向 agent 发 SIGKILL，init 进 cleanup_container()（等 exit status 读锁、发 RemoveContainerRequest、关 exit watcher、清 volumes/rootfs）。delete_process() 删 init 时移 map + poststop hooks + 返回 state；删 exec 只删 exec map 记录（manager.rs:146）。kill_process() 对 SIGKILL/SIGTERM 幂等容错（container 不存在/agent 断连/进程已终止按场景视为成功，:220）。

12. Pause / Resume / Stats / Update / Persist

pause/resume_container() 调 agent 后改 host 侧 process 状态（container.rs:590）；stats_container() 调 agent 包装成 StatsInfo（:666）；update_container() 反序列化 OCI LinuxResources、更新 ResourceManager 资源、发 agent UpdateContainerRequest（:675）——运行期控制是双边界（host 资源 + guest agent 状态都要更新）。VirtSandbox::save() 保存 hypervisor + resource state 写 SandboxState（只含 sandbox type/resource/hypervisor state，不含 container process map，sandbox.rs:996、sandbox_persist.rs:11）；restore() 当前只支持 Dragonball/QEMU 分支，其他报 unsupported（sandbox.rs:1037）。

13. 与 Go virtcontainers 路径对比 / ARM64

  • Go service 方法直接在 service.go 分发到 virtcontainers.Sandbox；runtime-rs 多一层内部 enum + RuntimeHandlerManager。
  • runtime-rs 的 CreateTask lazy start 更集中（load spec/init/start sandbox/create container/TaskCreate 全在 handler_task_message 特殊分支）。
  • 事件覆盖不同：Go shim 发 TaskExecAdded/TaskExecStarted/TaskPaused/TaskResumed（service.go:603）；runtime-rs 当前只发 TaskCreate/TaskDelete/TaskStart（manager.rs:18）。
  • ARM64/x86_64：主链无分叉；差异在 VirtContainer::init()/new_hypervisor() 的 feature + target arch gate（virt_container/src/lib.rs:37），更深差异下沉到 hypervisor plugin/VMM 机器类型/设备 bus/guest kernel/agent device handler。

14. 能力边界

  • runtime-rs manager 不是 VMM 也不是 guest agent——是 containerd API 到 sandbox/container trait 的分发器。
  • CreateSandbox（只初始化 instance）与 CreateTask（lazy start sandbox + create container）初始化语义不同。
  • containerd 的 Pid/Connect/CreateTaskResponse/StartResponse 都返回 host shim pid（Kata VM 隔离模型的接口适配，非 guest workload pid）。
  • Delete container 的真正 guest remove 发生在 IO/wait 后的 stop/cleanup 路径；DeleteProcess 更多是返回 state + 移 map 记录 + poststop hooks。
  • runtime-rs persist 当前保存 sandbox/resource/hypervisor 层状态，不能视为完整 task/process checkpoint。
