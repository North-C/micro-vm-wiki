Kata Agent Container 生命周期链路

本文从源码追踪 Kata 非机密计算路径下的 container 生命周期：containerd shim v2 → virtcontainers → kataAgent → guest agent → rustjail。

源码基线：当前仓库工作树。不展开 Kata CoCo/TDX/SEV/SNP/CCA。

相关：shim v2 到 sandbox/container 生命周期、guest agent CreateContainer 落地、shim v2 Exit/Event/Recovery。

0. 术语与背景

Kata 容器生命周期 = host 代表 pid + guest 真实进程

不是 host 上直接 fork workload。containerd 请求先到 shim，再到 virtcontainers，经 kataAgent ttrpc 进 VM 内 kata-agent，guest agent 用 rustjail 创建/控制 workload 进程。

维度 host shim 侧 guest agent/rustjail 侧
containerd 可见 pid s.hpid（hypervisor host pid） 不直接暴露
init process id container id / process token guest Linux pid（rustjail Process.pid）
signal 定位 container id + token find_container_process
wait 返回 guest exit status Process.exit_code

containerd 看到的 pid 不是 workload pid，是 Kata 用于维持 task v2 语义的 host 侧代表 pid（hypervisor pid）。

Create 与 Start 严格分离（关键设计）

  • Create：guest 内准备 bundle/rootfs/device/storage + 建 init process 等待点（不运行）。
  • Start：释放 init process 等待点，用户命令才开始运行。

Exec 两阶段

containerd Exec 只在 shim 侧建 exec 记录；后续 Start 携带 ExecID 才经 ExecProcessRequest 进 guest。

1. 核心结论

  • 容器生命周期不是 host 直接 fork：containerd → shim → virtcontainers → kataAgent ttrpc → guest agent → rustjail。
  • host runtime 只保存 container 状态/token/退出状态/事件，不拥有 guest 内真实 Linux pid。
  • Create 与 Start 严格分离（Create 准备等待点，Start 释放）。
  • Exec 两阶段（Exec 建记录，Start(ExecID) 才进 guest）。
  • shim 返回 containerd 的 pid 是 s.hpid（hypervisor pid）。

2. 总体链路

两个核心边界：① containerd → Kata shim；② host runtime → VM 内 guest agent。VMM 提供 VM/设备/通信通道；guest agent 才负责 guest 内 OCI bundle/cgroup/mount/process/信号。

3. shim v2 生命周期入口

Create 调 helper create()，成功后存 s.containers + 发 TaskCreate + 返回 Pid: s.hpid：

// src/runtime/pkg/containerd-shim-v2/service.go:406
func (s *service) Create(ctx context.Context, r *taskAPI.CreateTaskRequest) (*taskAPI.CreateTaskResponse, error) {
    container, err := create(ctx, s, r)
    container.status = task.Status_CREATED
    s.containers[r.ID] = container            // 存 shim 内 container
    // ... 发 TaskCreate ...
}
// :465
func (s *service) Start(ctx context.Context, r *taskAPI.StartRequest) (*taskAPI.StartResponse, error) {
    c, err := s.getContainer(r.ID)
    if r.ExecID == "" {
        startContainer(spanCtx, s, c); s.send(&eventstypes.TaskStart{ ContainerID: c.id, Pid: s.hpid })
    } else {
        startExec(spanCtx, s, r.ID, r.ExecID); s.send(&eventstypes.TaskExecStarted{ /* Pid: s.hpid */ })
    }
    return &taskAPI.StartResponse{ Pid: s.hpid }, nil   // 返回 pid 仍是 s.hpid
}

Wait 不直接发 guest RPC——等 shim 内 exitCh，真正等 guest process 的动作由后台 wait() goroutine 发起（详见 shim exit/recovery）。

4. Create 与 Start 分离（释放等待点）

startContainer() 区分 sandbox container（启动整个 sandbox + monitor）与普通 pod container（sandbox.StartContainer）：

// src/runtime/pkg/containerd-shim-v2/start.go:18
func startContainer(ctx context.Context, s *service, c *container) error {
    if c.cType.IsSandbox() {
        s.sandbox.Start(ctx); s.monitor, _ = s.sandbox.Monitor(ctx); go watchSandbox(ctx, s)   // sandbox 路径
    } else {
        s.sandbox.StartContainer(ctx, c.id)                                                    // 普通 pod container
    }
}

guest do_start_container() 只找 container 调 ctr.exec().await——这一步释放 create 阶段的等待点，用户命令才开始运行：

// src/agent/src/rpc.rs:356
async fn do_start_container(&self, req: StartContainerRequest) -> Result<()> {
    let ctr = s.get_container(&cid).ok_or_else(|| anyhow!("Invalid container id"))?;
    if sid != cid { /* 非 sandbox container → start OOM event loop */ }
    ctr.exec().await           // 释放等待点
}

5. virtcontainers 到 kataAgent

Container.create() 设备 attach + mount 准备后调 agent.createContainer，保存返回 process 为 c.process：

// src/runtime/virtcontainers/container.go:1398
func (c *Container) create(ctx context.Context) error {
    c.attachDevices(ctx); c.getSystemMountInfo()
    process, err := c.sandbox.agent.createContainer(ctx, c.sandbox, c)   // 进 guest agent
    c.process = *process
}
// :1513  stop
func (c *Container) stop(ctx context.Context, force bool) error {
    c.kill(ctx, syscall.SIGKILL, true)                                   // 先 SIGKILL
    c.sandbox.agent.waitProcess(ctx, c, c.id)                            // 等 process 退出（避免 RemoveContainerRequest 失败）
    c.sandbox.agent.stopContainer(ctx, c.sandbox, *c)                    // kataAgent 实际发 RemoveContainerRequest
}

6. kataAgent 请求封装

kataAgent.createContainer() 转 rootfs/mount/device/storage/OCI 为 CreateContainerRequest，init ExecId 用 container id：

// src/runtime/virtcontainers/kata_agent.go:1371
func (k *kataAgent) createContainer(ctx context.Context, sandbox *Sandbox, c *Container) (*Process, error) {
    grpcSpec, _ := ociSpecToGrpc(&ociSpec)
    req := &grpc.CreateContainerRequest{
        ContainerId: c.id, ExecId: c.id,                                // init ExecId = container id
        Storages: ctrStorages, Devices: ctrDevices, OCI: grpcSpec, SandboxPidns: sharedPidNs,
    }
    k.sendReq(ctx, req)
    return buildProcessFromExecID(req.ExecId)
}

kataAgent.exec() 为每次 exec 生成 UUID + 转 protobuf Process + 发 ExecProcessRequest（:582）；signalProcess() 在 all==true 时清空 ExecId（guest agent 用空 exec id 表示 init + 整个 cgroup，:2017）。

7. guest agent 执行语义

guest AgentService RPC 都先 policy 检查再进 do_* handler。do_create_container() 解析 OCI + devices/storages/namespaces/hooks/bundle + 建 LinuxContainer + init Process：

// src/agent/src/rpc.rs:199
async fn do_create_container(&self, req: CreateContainerRequest) -> Result<()> {
    add_devices(&cid, &sl(), &req.devices, &mut oci, &self.sandbox).await?;
    let m = add_storages(sl(), req.storages.clone(), &self.sandbox, Some(req.container_id)).await?;
    update_container_namespaces(&s, &mut oci, use_sandbox_pidns)?;
    let mut ctr: LinuxContainer = LinuxContainer::new(cid, CONTAINER_BASE, Some(s.devcg_info.clone()), opts, &sl())?;
    s.add_container(ctr);
}

do_signal_process() 对 init 未处理 SIGTERM 转 SIGKILL；exec id 空时冻结 cgroup + 枚举 cgroup pids 逐个发信号 + 解冻：

// src/agent/src/rpc.rs:459
async fn do_signal_process(&self, req: SignalProcessRequest) -> Result<()> {
    let p = sandbox.find_container_process(cid, eid)?;
    if p.init && sig == libc::SIGTERM && !is_signal_handled(&proc_status_file, sig) { sig = libc::SIGKILL; }  // init SIGTERM→SIGKILL
    p.signal(sig)?;
    if eid.is_empty() {                                  // signal all remaining in cgroup
        self.freeze_cgroup(&cid, FreezerState::Frozen).await?;
        for pid in self.get_pids(&cid).await? { unsafe { libc::kill(*pid, sig) }; }
        self.freeze_cgroup(&cid, FreezerState::Thawed).await?;
    }
}

do_remove_container() 移 bind watcher + ctr.destroy() + 清 storage/mount/container/PCI map（:381）。

8. rustjail Process 模型

LinuxContainer::start() 准备 stdio/pty/pipe/namespace/cgroup/child command，读子进程写回的 pid，插 process map：

// src/agent/rustjail/src/container.rs:965
async fn start(&mut self, mut p: Process) -> Result<()> {
    if p.init { unistd::mkfifo(fifo_file, Mode::from_bits(0o644).unwrap())?; /* exec fifo 等待点 */ }
    let (prfd, cwfd) = unistd::pipe()?; let (crfd, pwfd) = unistd::pipe()?;
    let mut child = std::process::Command::new(exec_path).arg("init").env(INIT, p.init).env(CRFD_FD, crfd).env(CWFD_FD, cwfd);
    child.spawn()?;
    let pid = read_async(&mut pipe_r).await?.parse::<i32>()?;   // 读子进程写回的 pid
    p.pid = pid; if p.init { self.init_process_pid = p.pid; }
    self.processes.insert(p.exec_id.clone(), p);
}
// src/agent/rustjail/src/process.rs:79
pub struct Process {
    pub exec_id: String, pub init: bool, pub pid: pid_t, pub exit_code: i32,
    pub exit_watchers: Vec<Sender<i32>>, pub oci: OCIProcess,
    pub stdin/stdout/stderr: Option<RawFd>, /* term_master/tty/proc_io ... */
}

exec fifo 是 Create/Start 分离的同步机制：init process 启动后阻塞在 exec fifo 上，直到 do_start_container 的 ctr.exec() 释放才运行。Process.signal() 本质是对 guest pid 调 libc::kill。

9. Wait 与 TaskExit 边界

handle_sigchild() 经 waitpid 捕获子进程退出 → 找 rustjail Process → 写 exit code + 关 exit channel：

// src/agent/src/signal.rs:21
async fn handle_sigchild(logger, sandbox) -> Result<()> {
    loop {
        let wait_status = wait::waitpid(Some(Pid::from_raw(-1)), Some(WNOHANG|__WALL))?;
        if let Some(pid) = wait_status.pid() {
            let p = sandbox.find_process(pid.as_raw())?;
            p.exit_code = match wait_status { Exited(_, c) => c, Signaled(_, sig, _) => sig as i32, _ => continue };
            let _ = p.exit_tx.take();                        // 关 exit watcher
        }
    }
}

find_container_process()：空 exec id = init process，非空按 process map 查 exec（sandbox.rs:315）。

10. pid/token 边界 / Update/Stats/Pause/Resume

维度 host shim 侧 guest agent/rustjail 侧
containerd 可见 pid s.hpid 不直接暴露
init process id container id / process token guest Linux pid
exec process id shim exec id → guest token guest Linux pid
signal 定位 container id + token find_container_process
wait 返回 guest exit status Process.exit_code

Pids() 明确说明 Kata 无法从 VM 取 container pid，只返回 hypervisor pid（service.go:851）。Update（解析 LinuxResources → Sandbox.UpdateContainer → kataAgent.updateContainer，清空 guest cpuset/mems 因 guest 不跟踪，container.go:1702）、Stats（→ agent StatsContainerRequest → rustjail ctr.stats()）、Pause/Resume（shim 改本地状态 + virtcontainers 持久化 + guest rustjail 操作 cgroup freezer Frozen/Thawed）。

11. ARM64 与 x86_64

生命周期 RPC 主链无明显架构分叉（service.go/container.go/kata_agent.go/rpc.rs 通用）。差异从 VM/hypervisor 层开始：x86_64 默认 QEMU qemu-system-x86_64 + Q35 + tsc/no_timer_check/PCI lastbus（qemu_amd64.go:45）；ARM64 默认 qemu-system-aarch64 + virt + gic-version=host + iommu.passthrough=0（qemu_arm64.go:27）。对 container 生命周期，ARM64 影响设备如何进 guest、guest sysfs 路径、agent handler 等待哪类 bus 设备——不是 Create/Start/Exec/Wait 语义。

12. 能力边界

  • Kata 能把 containerd task 语义映射到 VM 内容器语义，但不向 containerd 暴露 workload 的 guest pid——host pid 是代表 pid。
  • Delete 与 guest RemoveContainer 不只是删 shim 记录：非 sandbox container 删除路径会先 stop 再删 virtcontainers container + 触发 guest 资源清理。
  • guest agent 能 update/stats/pause/resume，但受 guest cgroup/kernel/agent policy/hypervisor/device 支持。

与 CubeSandbox 相比，Kata 的 shim 已把 RemoveContainerRequest 接入 stop/delete 路径；CubeSandbox 当前对应路径仍有 guest remove 未接入的实现缺口（见 CubeSandbox CubeShim container lifecycle §9）。
