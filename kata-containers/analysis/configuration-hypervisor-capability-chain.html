Kata configuration 到 Hypervisor capability 链路

本文分析 Kata 如何从 configuration-*.toml 模板收敛到 hypervisor 配置，并在 runtime-rs 中形成能力矩阵。

源码基线：当前仓库工作树。不展开 CoCo。

相关：hypervisor plugin lifecycle、QEMU launch params。

0. 术语与背景

配置收敛链

configuration-*.toml → Go/runtime-rs 配置栈 → plugin 注册 → capability matrix → shared-fs/热插拔/设备决策。

关键配置字段

字段 影响
hypervisor 选择 QEMU/CH/Dragonball/FC
shared_fs share-fs 类型（virtio-fs/virtio-9p）
machine_type Q35/virt/microvm
kernel_irqchip split/full（IOMMU 场景）
default_vcpus/default_memory VM 默认规格 
// src/runtime-rs/crates/runtimes/src/manager.rs:111
fn init_runtime_handler(config: &RuntimeConfig) -> Result<Box<dyn RuntimeHandler>> {
    match config.runtime.name.as_str() {
        "virt" => Ok(Box::new(VirtContainer::new_handler(config)?)),
        _ => Err(anyhow!("unsupported runtime")),
    }
}

1. 能力边界

Kata 配置层不区分 ARM64/x86_64——同一 toml 模板可跨架构使用。真正的架构差异在 hypervisor plugin 是否在目标架构编译 + guest kernel 是否支持对应 driver。init_runtime_handler() 按 config.runtime.name 选 plugin（LinuxContainer/WasmContainer/VirtContainer），普通 Kata VM 走 VirtContainer::new_handler()。shared-fs 决策链取决于 hypervisor capability is_fs_sharing_supported。
