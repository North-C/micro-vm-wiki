Kata Containers 可观测性与诊断机制函数级链路

本文回答：Kata 出故障时证据从哪里来，能证明到哪一层。

源码基线：当前仓库工作树。不展开 CoCo。

相关：shim exit event recovery、横向 observability。

0. 术语与背景

Kata 诊断双层（与 CubeSandbox 同构）

层 信号来源 依赖 agent？
host 侧 shim 进程 + hypervisor 进程 + shim events + tracing + metrics 否
guest 侧 agent stats/check/GetOOMEvent/GetGuestDetails 是（agent 断 → 丢失）

关键：agent 不可达时诊断退化

agent 是 guest 内诊断的唯一通道——watchAgent 失败 → markDead → 丢失 guest 可见性（container stats/OOM/guest details），但 watchHypervisor 与 shim 事件流仍工作。

// src/runtime/pkg/containerd-shim-v2/service.go:941
span, spanCtx := katatrace.Trace(s.rootCtx, shimLog, "Connect", shimTracingTags)
defer span.End()

1. host 侧诊断信号

  • shim events：TaskExit/OOM 等 → processExits → checkProcesses → forwarder → containerd。
  • tracing：katatrace.Trace() 创建 OpenTelemetry span（Create/Start/Stop/Stats 等关键路径，service.go:941/963/1009）。
  • monitor：newWatcher → watchHypervisor + watchAgent（5s 轮询）。

2. guest 侧诊断信号

  • StatsContainer：agent → rustjail ctr.stats()（cgroup stats）。
  • Check：agent health check（HealthClient.Check）。
  • GetOOMEvent：agent OOM event（watchOOMEvents goroutine）。
  • GetGuestDetails：guest 内 memory block size + hotplug probe 支持。

3. 能力边界

Kata 诊断是host/guest 双层：host 不依赖 agent（shim/hypervisor/monitor）；guest 依赖 agent（stats/OOM/guest details）。ARM64/x86_64 在诊断路径上几乎不分叉——WaitProcess 能否稳定返回取决于 guest agent 与 VM 状态，不是 shim channel 机制。
