Kata agent RPC 边界链路

本文补齐 Kata 非机密计算路径下的 agent RPC 分层：host 侧 kataAgent wrapper、generated ttrpc client、guest agent server trait 和 do_* handler。

源码基线：当前仓库工作树。不展开 CoCo。

相关：shim sandbox lifecycle、agent container lifecycle。

0. 术语与背景

agent RPC = host protobuf request → ttrpc → guest policy check → do_* handler

host runtime 先构造 protobuf request，sendReq() 按消息类型分发到 generated ttrpc client。guest 侧 ttrpc server 接收 grpc.AgentService 方法，先做 policy 检查，再进 do_* handler。

CreateContainerRequest 是 host/guest 语义边界

host 编码 rootfs/storage/device/OCI spec/IO 端口；guest 解码这些字段并落地为 bundle/mount/device/rustjail process。

1. host 侧 sendReq（按 msgName 分发）

// src/runtime/virtcontainers/kata_agent.go:2439
func (k *kataAgent) sendReq(spanCtx context.Context, request interface{}) (interface{}, error) {
    k.connect(spanCtx)
    msgName := string(proto.MessageName(request.(proto.Message)))
    handler := k.reqHandlers[msgName]    // 按 msgName 查 handler
    return handler(k.client, request)    // 调 generated ttrpc client
}

reqHandlers 是 msgName → handler func 映射——每种 protobuf 消息类型对应一个 generated ttrpc 方法调用。

2. guest 侧 is_allowed（policy check）

// src/agent/src/policy.rs:31
pub async fn is_allowed(req: &(impl MessageDyn + serde::Serialize)) -> ttrpc::Result<()> {
    let request = serde_json::to_string(req).unwrap();       // 序列化 JSON
    let mut policy = AGENT_POLICY.lock().await;               // 全局 AGENT_POLICY 锁
    allow_request(&mut policy, req.descriptor_dyn().name(), &request).await
}

所有 agent RPC 在进 do_* handler 前都先 is_allowed!()——序列化请求、拿全局 AGENT_POLICY 锁、按 endpoint 名称 + 请求内容执行 policy 检查。policy 不通过 → 拒绝操作。

3. 能力边界

ARM64/x86_64 在 RPC 方法和 protobuf 字段上没有分叉。架构差异下沉到 hypervisor 设备、guest sysfs 路径和 agent handler 等待设备的方式。sendReq 的错误处理有 DeadlineExceeded 特判（超时 → gRPC status error）。
