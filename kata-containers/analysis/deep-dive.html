Kata Containers 深入探索文档

本文档从当前仓库源码出发，建立对 Kata Containers 的系统性理解：它不是一个单体 VMM，而是把 containerd shim、runtime、hypervisor plugin、guest agent、rootfs/share-fs/network/storage 组合成 VM-based container runtime。

当前版本：第 2 版 源码基线：kata-containers 仓库，commit 2629df278 阅读方式：先理解“runtime 平台层”定位，再沿 containerd shim -> runtime manager -> sandbox -> hypervisor trait -> agent ttrpc/vsock 展开。

0. 问题地图

  1. Kata Containers 与 Firecracker/Cloud Hypervisor/crosvm 的层级差异是什么？
  2. containerd shim v2 在 Kata 中承担什么角色？
  3. runtime-rs 的 crate 划分如何映射到 sandbox lifecycle？
  4. Hypervisor trait 如何屏蔽 Dragonball/QEMU/Cloud Hypervisor/Firecracker 差异？
  5. guest agent 如何接管 VM 内 container 生命周期？
  6. vsock/ttrpc 在控制面和数据面中扮演什么角色？
  7. snapshot/save/restore 在 Kata 中为什么取决于底层 hypervisor？
  8. ARM64 与 x86_64 的差异体现在哪里？

1. 一句话定位

Kata Containers 是 VM-based container runtime。它的核心价值不是实现 KVM_RUN，而是把“每个 pod/sandbox 一个轻量 VM”的隔离模型接入 containerd/Kubernetes 生态，并通过 guest agent 在 VM 内创建和管理容器。

源码和文档依据：

  • README 说明 Kata 在 64-bit 系统上运行，并列出 x86_64/amd64、aarch64、ppc64le、s390x 的虚拟化技术：README.md。
  • README 说明配置文件包含 runtime、agent、hypervisor 等系统部分：README.md。
  • runtime-rs README 将其定义为 Kata Containers 4.0 的 Rust containerd shim v2 runtime：src/runtime-rs/README.md。
  • agent README 说明 Kata agent 是运行在 VM 内的长生命周期进程，runtime 启动 hypervisor 创建 VM 后，agent 负责 VM 内 container 生命周期：src/agent/README.md。

2. 顶层架构

runtime-rs README 列出核心 crate：shim 是 containerd shim v2 入口，service 实现 TaskService，runtimes 管理 sandbox/container，resource 管理 network/share_fs/rootfs/volume/cgroups/cpu_mem，hypervisor 提供 hypervisor 实现，agent 负责 KataAgent 通信，persist 保存状态：src/runtime-rs/README.md。

3. 两条 runtime 线：Go virtcontainers 与 runtime-rs

当前仓库同时保留了 Go 版 virtcontainers/containerd-shim-v2 路径和 Rust runtime-rs 路径。深入 Kata 时不能只看其中一条，否则会误判架构边界。

Go 路径的核心接口是 VC 和 VCSandbox。VC 只暴露 CreateSandbox() 和 CleanupContainer()；VCSandbox 暴露 sandbox/container 生命周期、网络、设备、metrics、agent URL、policy 等操作：src/runtime/virtcontainers/interfaces.go。VCImpl.CreateSandbox() 只是转调 virtcontainers.CreateSandbox()：src/runtime/virtcontainers/implementation.go。

Rust 路径则把 containerd shim v2、service、runtimes、resource、hypervisor、agent、persist 拆成多个 crate。runtime-rs/README.md 明确列出 shim、service、runtimes、resource、hypervisor、agent、persist 的职责：src/runtime-rs/README.md。

结论：Kata 不是一个 VMM 项目，而是 VM-based container runtime。它真正关心的是“如何把容器生命周期映射到一个 VM sandbox 和 guest agent”，VMM 只是其中一个可替换后端。

4. Go shim v2 到 virtcontainers 的控制面

runtime-rs 的 handler_sandbox_message() 对 CreateSandbox 先初始化 runtime instance，再处理其他 sandbox 请求；handler_task_message() 在 CreateContainer 时加载 OCI spec，初始化 runtime instance，启动 sandbox，再创建 container：src/runtime-rs/crates/runtimes/src/manager.rs。

Go 版 shim 的 create 路径也体现相同结构：调用 katautils.CreateSandbox() 创建 sandbox，然后读取 hypervisor pid 保存到 service：src/runtime/pkg/containerd-shim-v2/create.go。

源码展开：

  • Go shim New() 创建 service，保存 sandbox id、pid、context、container map、event channel、exit channel，并启动 processExits() 和 event forwarder：src/runtime/pkg/containerd-shim-v2/service.go。
  • containerd-shim-v2/create.go 在 PodSandbox 分支中处理 factory、rootless、CDI annotations，然后用 service 的长期 context 调用 katautils.CreateSandbox()，创建成功后保存 s.sandbox 和 hypervisor pid：src/runtime/pkg/containerd-shim-v2/create.go。
  • katautils.CreateSandbox() 从 OCI spec 和 runtime config 生成 SandboxConfig，设置 hypervisor shared path，处理 rootfs、Docker netns、network namespace、policy/initdata annotations，然后调用 vci.CreateSandbox()：src/runtime/pkg/katautils/create.go。
  • virtcontainers.CreateSandbox() 创建 sandbox 后，依次创建网络、设置 cgroup/resource controller、启动 VM、执行 post-created network、读取 guest details、创建容器：src/runtime/virtcontainers/api.go。
  • Go Sandbox 对象持有 devManager、factory、hypervisor、agent、persist store、fsShare、network、containers、resource controller、state 等：src/runtime/virtcontainers/sandbox.go。

这条路径的关键点是：PodSandbox 创建阶段已经启动 VM 并创建初始容器，但 Sandbox.Start() 才把容器逐个 start 并持久化 sandbox 状态：src/runtime/virtcontainers/sandbox.go。

5. runtime-rs 控制面：manager、sandbox、container manager

runtime-rs 的 manager 把 containerd 请求转成 runtime 内部请求。

源码依据：

  • handler_sandbox_message() 只在 CreateSandbox 时初始化 runtime instance，其他 sandbox 请求转到 handler_sandbox_request()：src/runtime-rs/crates/runtimes/src/manager.rs。
  • handler_task_message() 在 CreateContainer 时加载 OCI spec，初始化 runtime instance，调用 instance.sandbox.start()，然后调用 container_manager.create_container()，最后发送 TaskCreate event：src/runtime-rs/crates/runtimes/src/manager.rs。
  • VirtSandbox::prepare_for_start_sandbox() 准备 VM socket、network、sharefs、VM rootfs、initdata/protection device、PCIe port devices 等资源配置：src/runtime-rs/crates/runtimes/virt_container/src/sandbox.rs。
  • sandbox start 主路径是：hypervisor.prepare_vm() -> resource_manager.prepare_before_start_vm() -> hypervisor.start_vm() -> 执行 OCI hooks -> 处理可能变化的 netns -> agent.start() -> resource_manager.setup_after_start_vm() -> agent.create_sandbox() -> 进入 Running：src/runtime-rs/crates/runtimes/virt_container/src/sandbox.rs。
  • VirtContainerManager::create_container() 创建 Container 对象，进入 VMM netns 执行 CreateContainer hooks，然后调用 container 的 create()，失败时清理资源：src/runtime-rs/crates/runtimes/virt_container/src/container_manager/manager.rs。
  • container create 最终构造 agent::CreateContainerRequest，包含 process id、storages、OCI spec、sandbox pidns、devices、shared mounts、passfd IO ports，然后调用 agent.create_container()：src/runtime-rs/crates/runtimes/virt_container/src/container_manager/container.rs。

这条 Rust 路径把 host resource 准备和 guest container 创建分得更清楚：resource manager 管 host/VM 侧资源，agent 管 guest 内进程语义。

6. Hypervisor 抽象

runtime-rs 的 Hypervisor trait 是理解 Kata 的核心边界。它包含 VM 管理、设备管理和辅助查询：

方法组 代表方法 说明
VM manager prepare_vm、start_vm、stop_vm、pause_vm、save_vm、resume_vm sandbox VM 生命周期
resize resize_vcpu、resize_memory 资源调整
device manager add_device、remove_device、update_device hotplug/rootfs/sharefs/network 等设备
utility get_agent_socket、get_thread_ids、get_pids、cleanup agent 连接、监控、清理

源码依据：Hypervisor trait 定义在 src/runtime-rs/crates/hypervisor/src/lib.rs。该文件同时定义了 HYPERVISOR_DRAGONBALL、HYPERVISOR_QEMU、HYPERVISOR_FIRECRACKER、HYPERVISOR_REMOTE 等常量：src/runtime-rs/crates/hypervisor/src/lib.rs。

runtime-rs README 列出的支持 hypervisor 包括 Dragonball、QEMU、Cloud Hypervisor、Firecracker、Remote，并说明 Dragonball 是 built-in VMM，Cloud Hypervisor/Firecracker 是 external：src/runtime-rs/README.md。

这个 trait 的能力边界有三点：

  1. Kata 的 save_vm()/resume_vm() 是抽象能力，是否可用、语义是什么，取决于具体 hypervisor plugin。
  2. add_device()/remove_device()/update_device() 把 rootfs、sharefs、network、vfio、vsock 等资源映射到 VMM 后端的设备模型。
  3. get_agent_socket() 是 host runtime 与 guest agent 连接的关键桥，Dragonball/Firecracker/Cloud Hypervisor/QEMU 的 socket 形态可能不同，但上层只看这个抽象。

7. Agent 与 vsock/ttrpc

Kata agent 运行在 guest VM 内。runtime 启动 hypervisor 创建 VM 后，agent 开始负责 VM 内 container 生命周期：src/agent/README.md。

agent 配置中默认 agent.server_addr 是 vsock://-1:1024，并且还有 debug console/log vport/passfd listener 等 vsock 相关配置：src/agent/README.md。

这说明 Kata 的控制面跨越 host 和 guest：host 侧 shim/runtime 只负责启动 VM、准备资源和发 RPC；guest 内真正的 container 创建、exec、kill、mount、namespace 操作由 agent 完成。

源码展开：

  • agent main() 创建 Tokio runtime。如果 agent 作为 PID 1 运行，退出前会 sync() 并 poweroff guest：src/agent/src/main.rs。
  • start_sandbox() 创建 guest 内 Sandbox，启动 signal handler、uevent watcher，初始化 initdata/attestation/mem-agent，然后通过 rpc::start() 在 agent.server_addr 上启动 ttrpc server：src/agent/src/main.rs。
  • AgentService 持有 guest 内 Sandbox、init mode 和可选 mem-agent：src/agent/src/rpc.rs。
  • create_sandbox() RPC 会设置 hostname/sandbox id/running 状态，加载 kernel modules，建立共享 namespace，挂载 sandbox storages，加载 guest hooks，设置 DNS：src/agent/src/rpc.rs。
  • create_container() RPC 校验 container id，解析 OCI spec，处理 passfd IO、devices、storages、shared mounts，并在 guest 内创建容器资源：src/agent/src/rpc.rs。
  • AgentService 实现了 create/start/remove/exec/signal/wait/update 等 ttrpc 方法，每个方法先做 policy 检查，再调用对应 do_* 实现：src/agent/src/rpc.rs。

因此 Kata 的“容器运行时”本质是双端协作：host 端做 VM 和资源编排，guest agent 端把 OCI/container 操作真正落到 namespace、cgroup、mount、process 上。

8. 资源、设备与网络：Kata 的数据面边界

Kata 的设备语义不是某个 VMM 的设备枚举，而是来自 runtime resource 层：

  • VM socket：为 agent 通信准备 vsock/hvsock/remote socket。
  • network：从 netns/DAN/endpoint 中构造 tap、veth、macvlan、ipvlan、vhost-user-net 等后端资源。
  • share-fs：virtio-fs standalone/inline 等共享文件系统方式。
  • rootfs：share-fs rootfs、block rootfs、nydus、erofs、virtual volume 等。
  • volume：local/default/sharefs/block/ephemeral/hugepage/direct volume。
  • cgroups/cpu/memory/swap：host 侧 sandbox 和 hypervisor 进程资源控制。

这些模块集中在 runtime-rs resource crate 下：src/runtime-rs/crates/resource/src。prepare_for_start_sandbox() 把它们汇总成 ResourceConfig，再交给 ResourceManager 在 VM 启动前后分别处理：src/runtime-rs/crates/runtimes/virt_container/src/sandbox.rs。

这也是 Kata 与单体 VMM 的重要区别：VMM 只看到“加一块 block 设备/virtio-fs/vsock/tap”，Kata 看到的是 Kubernetes/OCI 的 volume、rootfs、netns、emptyDir、CDI device、policy/initdata，并把它们翻译成 hypervisor 和 agent 可理解的对象。

9. Snapshot/save/restore 的语义

Kata 的 save_vm/resume_vm 是 runtime 抽象，不等于某一个 VMM 的 snapshot 格式。底层实现取决于 hypervisor plugin：Firecracker、Cloud Hypervisor、QEMU、Dragonball 的 VM state、memory、device、agent 状态边界不同。

runtime-rs README 说明 persist crate 负责把 sandbox recovery 状态以 JSON 存到 /run/kata/<sandbox-id>/state.json：src/runtime-rs/README.md。这类持久化是 runtime 层恢复，不是完整 VM memory snapshot 的同义词。

源码边界：

  • Hypervisor trait 暴露 pause_vm()、save_vm()、resume_vm()、save_state()，但没有规定具体 snapshot 文件格式：src/runtime-rs/crates/hypervisor/src/lib.rs。
  • persist crate 保存的是 sandbox recovery 状态；这类状态用于 shim/runtime 恢复，不等价于 guest memory/device/vCPU 完整快照。
  • agent 侧没有“保存整个 VM”的能力，它保存和恢复的是 guest 内 container/sandbox 语义状态，VM memory/device snapshot 仍属于 hypervisor 后端。

因此分析 Kata snapshot/save/restore 必须分三层：runtime persist、hypervisor VM snapshot、agent/container 状态。只看 save_vm() 会把这三层混在一起。

10. ARM64 与 x86_64 差异

维度 x86_64 aarch64
README 硬件要求 Intel VT-x / AMD SVM ARM Hyp
Cloud Hypervisor plugin runtime-rs 中限定 x86_64/aarch64 同左
Firecracker/Dragonball/QEMU 是否支持取决于插件构建和配置 同左
guest image/kernel 架构相关 rootfs、kernel、agent build 架构相关 rootfs、kernel、agent build
设备 transport PCI/MMIO/CCW 取决于 hypervisor/arch ARM 常见 MMIO/FDT/GIC 语义

README 的硬件表明确 x86_64/amd64 与 aarch64 虚拟化技术：README.md。runtime-rs 的 Cloud Hypervisor 模块用 #[cfg(all(feature = "cloud-hypervisor", any(target_arch = "x86_64", target_arch = "aarch64")))] 限定：src/runtime-rs/crates/hypervisor/src/lib.rs。

补充源码视角：

  • runtime-rs 有按架构拆分的 make options：arch/x86_64-options.mk、arch/aarch64-options.mk、arch/s390x-options.mk、arch/riscv64gc-options.mk 等：src/runtime-rs/arch。
  • Dragonball 自带 boot crate 同时有 dbs_boot/src/x86_64 和 dbs_boot/src/aarch64；x86_64 有 bootparam/mptable/mpspec，aarch64 有 FDT/layout：src/dragonball/dbs_boot/src/x86_64 和 src/dragonball/dbs_boot/src/aarch64。
  • agent 自身大部分是架构无关的 guest 进程，但 device handling 存在 block/scsi/nvdimm/vfio/network 等差异模块，实际路径由 guest kernel、hypervisor 设备模型和 runtime 配置共同决定：src/agent/src/device。

结论：Kata 的 ARM64/x86_64 差异不是集中在一个 VMM boot 文件里，而是跨越 hypervisor plugin、Dragonball boot、guest kernel/rootfs/agent build、设备 transport 和配置模板。

11. 与 Firecracker 的关键差异

  1. Firecracker 是 VMM；Kata 是 runtime/orchestration 层，可以选择 Firecracker 作为下层 hypervisor。
  2. Firecracker API 管一个 microVM；Kata shim 管一个 sandbox/pod 生命周期，并通过 agent 管 VM 内 containers。
  3. Firecracker snapshot 是 VMM 状态；Kata 的 save/restore 要同时考虑 runtime state、hypervisor state、guest agent state。
  4. Firecracker 的设备边界由 VMM 决定；Kata 的设备语义来自 rootfs/share-fs/network/storage/hypervisor plugin 的组合。
  5. ARM64/x86_64 在 Firecracker 中是 VMM 架构分叉；在 Kata 中还叠加 guest image、agent build、hypervisor plugin、kernel 配置差异。
