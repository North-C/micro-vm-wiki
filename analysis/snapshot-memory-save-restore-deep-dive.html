    Snapshot 内存保存与恢复专题

    本文聚焦 snapshot/restore 中最复杂、最核心的部分——guest memory 的保存与恢复。从 VMM 用户态实现到内核 KVM/userfaultfd 底层机制，逐层展开。

    源码基线：Linux 6.6.0 内核 + Firecracker/Cloud Hypervisor/CubeSandbox VMM 源码。

    相关：Snapshot/Restore 底层内核技术深度解读、Snapshot/Restore/Clone 跨项目专题。

    0. 问题定义

    guest memory 保存/恢复是 snapshot 中数据量最大、耗时最长的部分。一台 256 MiB 的 microVM，state 文件只有几 KB（CPU 寄存器 + 设备协议状态），但 memory 文件是 256 MB。核心矛盾是：

    • 保存：如何高效地把 guest RAM 字节写出来？如何只写变化过的页（增量）？
    • 恢复：如何快速地把 256 MB 数据变成 guest 可访问的内存？预拷贝 vs 按需填页？
    • 正确性：guest CPU 写 + VMM 设备模拟 DMA 写，如何不丢页？

    1. 内存保存：full dump vs dirty diff

    1.1 Firecracker：dump / dump_dirty

    Firecracker 的内存保存分两条路径，核心在 snapshot_memory_to_file()（vstate/vm.rs:333）：

    // firecracker/src/vmm/src/vstate/vm.rs:333
pub(crate) fn snapshot_memory_to_file(&self, mem_file_path: &Path, snapshot_type: SnapshotType)
    -> Result<(), CreateSnapshotError>
{
    let mut file = OpenOptions::new().write(true).create(true).truncate(false).open(mem_file_path)?;
    // truncate(false)！——避免文件正是当前 VM mmap 来源时 truncate 把运行中 guest memory 清零
    file.set_len(expected_size)?;   // 设为 guest memory 总大小

    match snapshot_type {
        SnapshotType::Full => {
            self.guest_memory().dump(&mut file)?;      // 全量写
            self.reset_dirty_bitmap();                   // 清 KVM dirty log
            self.guest_memory().reset_dirty();           // 清 VMM atomic bitmap
        }
        SnapshotType::Diff => {
            let dirty_bitmap = self.get_dirty_bitmap()?;            // 读 KVM dirty log
            self.guest_memory().dump_dirty(&mut file, &dirty_bitmap)?; // 只写脏页
        }
    };
    file.flush()?; file.sync_all()?;
}

    full dump 实现

    // firecracker/src/vmm/src/vstate/memory.rs:687
fn dump<T: WriteVolatile + std::io::Seek>(&self, writer: &mut T) -> Result<(), MemoryError> {
    self.iter().flat_map(|region| region.slots()).try_for_each(|(mem_slot, plugged)| {
        if !plugged {
            // 未 plugged 的 slot（hotplug 预留）→ seek 跳过（保持文件偏移对齐）
            writer.seek(SeekFrom::Current(ilen))?;
        } else {
            // plugged slot → 写全部字节到文件
            writer.write_all_volatile(&mem_slot.slice)?;
        }
        Ok(())
    })
}

    plugged 概念：Firecracker 的 memory 分为"已 plugged"（guest 可用）和"未 plugged"（hotplug 预留空间）。dump 时未 plugged 的 slot 只 seek 跳过——文件保持 guest physical 地址对齐，restore 时按偏移直接 mmap。

    dirty diff 实现

    // firecracker/src/vmm/src/vstate/memory.rs:703
fn dump_dirty<T: WriteVolatile + std::io::Seek>(&self, writer: &mut T, dirty_bitmap: &DirtyBitmap)
    -> Result<(), MemoryError>
{
    let page_size = host_page_size();
    self.iter().flat_map(|region| region.slots()).try_for_each(|(mem_slot, plugged)| {
        if !plugged {
            writer.seek(SeekFrom::Current(ilen))?;   // 未 plugged → 跳过
        } else {
            let kvm_bitmap = dirty_bitmap.get(&mem_slot.slot)?;   // 取该 slot 的 dirty bitmap
            mem_slot.dump_dirty(writer, kvm_bitmap, page_size)?;   // 只写 dirty bit=1 的页
        }
        Ok(())
    })
}

    diff 不是单独 delta 文件——dirty 页直接合并进目标 memory 文件（dump_dirty 用 seek 保持偏移对齐，只覆盖 dirty 页位置）。如果目标文件大小匹配，restore 时直接 mmap 整个文件即可，不需合并 delta。

    dirty bitmap 的来源

    // firecracker/src/vmm/src/vstate/vm.rs:307
pub fn get_dirty_bitmap(&self) -> Result<DirtyBitmap, VmError> {
    // 返回 HashMap<u32, Vec<u64>>：slot → dirty bitmap
    // 1. 有 bitmap 的 slot → KVM_GET_DIRTY_LOG ioctl
    // 2. 无 bitmap 的 slot → mincore() 系统调用 fallback
}

    KVM_GET_DIRTY_LOG 在内核里 copy dirty_bitmap 到用户态（virt/kvm/kvm_main.c:2158）。mincore() 是 fallback——当 slot 未启用 KVM_MEM_LOG_DIRTY_PAGES 时，用 mincore() 检查页是否在内存中（resident）作为近似 dirty。

    1.2 Cloud Hypervisor：MemoryRangeTable + send

    Cloud Hypervisor 的内存保存分两步：snapshot() 生成计划（哪些 range 要发送），send() 传输字节。

    // cloud-hypervisor/vmm/src/memory_manager.rs:2988
fn snapshot(&mut self) -> Result<Snapshot, MigratableError> {
    let memory_ranges = self.memory_range_table(true)?;   // 生成 range table
    // 存到 snapshot_memory_ranges，供 send() 复用（避免 send 重复计算哪些 range 要复制）
    self.snapshot_memory_ranges = memory_ranges;
    Ok(Snapshot::from_data(SnapshotData::new_from_state(&self.snapshot_data())?))
}

    // cloud-hypervisor/vmm/src/memory_manager.rs:3007  send（传输字节）
fn send(&self, _snapshot: &Snapshot, destination_url: &str) -> Result<(), MigratableError> {
    if self.snapshot_memory_ranges.is_empty() { return Ok(()); }
    let mut memory_file = OpenOptions::new().read(true).write(true).create_new(true).open(path)?;
    let guest_memory = self.guest_memory.memory();
    for range in self.snapshot_memory_ranges.regions() {
        let mut offset: u64 = 0;
        loop {
            // 从 guest memory GPA 读字节，写入 memory-ranges 文件
            let bytes_written = guest_memory.write_volatile_to(
                GuestAddress(range.gpa + offset), &mut memory_file, (range.length - offset) as usize)?;
            offset += bytes_written as u64;
            if offset == range.length { break; }
        }
    }
}

    CH 与 FC 的关键差异：CH 用 MemoryRangeTable（range 列表）而非逐 slot bitmap——因为 CH 支持 memory zone + virtio-mem，内存拓扑比 FC 复杂。memory_range_table(snapshot=true) 在 MAP_SHARED + host hardlink 时跳过复制（共享 backing file 由用户经原文件保存）。

    1.3 CubeSandbox：FICLONE clone + 增量写入

    CubeSandbox 不直接 dump guest memory——它用 CubeCoW FICLONE clone 创建 memory volume 的 O(1) 副本，然后 VMM 只写入变化页：

    // Cubelet/services/cubebox/snapshot_base_memory.go:188  prepareCommitMemoryArtifact
// Tier 1 soft-dirty: FICLONE clone 上次 snapshot 的 memory volume → VMM 只写 soft-dirty 页
memoryObject, _ := storage.CommitTemplateMemoryFromBase(ctx, baseMemoryObject, templateID, memorySizeBytes)
//   → CubeCoW CommitTemplateMemory = FICLONE ioctl（O(1) 共享 extent）
return memoryObject, snapshotTypeSoftDirty, nil

    FICLONE clone 后，目标文件是源的完整副本（共享 XFS extent）。VMM 写入时 XFS CoW fork 分配新 block——只有实际写入的页才复制。这与 FC/CH 的"逐页 dump"完全不同：CubeSandbox 不读 guest memory 字节写文件，而是先 reflink 共享，再让 VMM 覆盖变化页。

    2. 内存恢复：eager copy vs lazy UFFD

    2.1 Firecracker：File mmap vs UFFD

    模式 实现 时延特征
    File backend guest_memory_from_file() → mmap memory 文件成 guest memory regions 初始时延 = mmap（O(1)），但首次访问触发 page fault 从文件读页
    UFFD backend guest_memory_from_uffd() → 匿名内存 + userfaultfd 注册 + fd 发外部 handler 初始时延 = 创建匿名内存 + UFFD 注册（O(1)），首次访问由外部 handler 填页 
    // firecracker/src/vmm/src/persist.rs:507  File backend
fn guest_memory_from_file(mem_file_path, mem_state, track_dirty_pages) -> Result<Vec<GuestRegionMmap>, _> {
    let mem_file = File::open(mem_file_path)?;
    let guest_mem = memory::snapshot_file(mem_file, mem_state.regions(), track_dirty_pages)?;  // mmap
    Ok(guest_mem)
}
// hugetlbfs 拒绝 file backend → 提示用 UFFD

// firecracker/src/vmm/src/persist.rs:532  UFFD backend
fn guest_memory_from_uffd(mem_uds_path, mem_state, track_dirty_pages, huge_pages) -> Result<(Vec<GuestRegionMmap>, Option<Uffd>), _> {
    let (guest_memory, backend_mappings) = create_guest_memory(mem_state, track_dirty_pages, huge_pages)?;  // 匿名内存
    let uffd = UffdBuilder::new().require_features(FeatureFlags::EVENT_REMOVE)
        .close_on_exec(true).non_blocking(true).create()?;
    for mem_region in guest_memory.iter() {
        uffd.register(mem_region.as_ptr().cast(), mem_region.size())?;   // 每 region 注册 UFFD
    }
    send_uffd_handshake(mem_uds_path, &backend_mappings, &uffd)?;  // mapping + UFFD fd 发外部 handler
    Ok((guest_memory, Some(uffd)))   // Firecracker 保留 fd
}

    Firecracker UFFD 的关键设计：UFFD fd 发给外部进程（经 Unix socket + SCM_RIGHTS），Firecracker 自己保留一份 fd。注释说明外部 handler 崩溃会导致 guest 冻结——Firecracker 需持 fd 维持语义。

    2.2 Cloud Hypervisor：Copy vs OnDemand

    // cloud-hypervisor/vmm/src/memory_manager.rs:1663  new_from_snapshot
pub fn new_from_snapshot(snapshot, vm, config, source_url, prefault, memory_restore_mode, ...) -> Result<Arc<Mutex<MemoryManager>>, Error> {
    let mem_snapshot: MemoryManagerSnapshotData = snapshot.to_state()?;
    let mm = MemoryManager::new(vm, config, Some(prefault), phys_bits, /*...*/, Some(&mem_snapshot), /*...*/)?;  // 重建拓扑
    if memory_restore_mode == MemoryRestoreMode::OnDemand {
        mm.lock().unwrap().restore_by_uffd(&memory_file_path, &mem_snapshot.memory_ranges, exit_evt)?;  // UFFD
    } else {
        mm.lock().unwrap().fill_saved_regions(memory_file_path, &mem_snapshot.memory_ranges)?;  // Copy
    }
}

    Copy（eager）——fill_saved_regions

    // cloud-hypervisor/vmm/src/memory_manager.rs:785
fn fill_saved_regions(&mut self, file_path: PathBuf, saved_regions: &MemoryRangeTable) -> Result<(), Error> {
    let mut memory_file = OpenOptions::new().read(true).open(file_path)?;
    let guest_memory = self.guest_memory.memory();
    for range in saved_regions.regions() {
        let mut offset: u64 = 0;
        loop {
            // 从 snapshot 文件读字节 → 写入 guest memory 对应 GPA
            let bytes_read = guest_memory.read_volatile_from(
                GuestAddress(range.gpa + offset), &mut memory_file, (range.length - offset) as usize)?;
            offset += bytes_read as u64;
            if offset == range.length { break; }
        }
    }
}

    函数名易误导：fill_saved_regions 是从 snapshot 文件读字节写入 guest memory（不是写文件）。手动 retry 循环因为 vm-memory read_exact_from() 行为不正确（rust-vmm/vm-memory#174）。

    OnDemand（lazy）——restore_by_uffd + uffd_handler_loop

    // cloud-hypervisor/vmm/src/memory_manager.rs:844
fn restore_by_uffd(&mut self, file_path, saved_regions, exit_evt) -> Result<(), Error> {
    // 1. 验证 GPA/长度按基础页对齐
    // 2. 创建 UFFD fd
    let uffd_fd = uffd::create(required_uffd_features)?;
    // 3. 每 region 注册 UFFD
    for range in saved_regions.regions() {
        let host_addr = guest_memory.get_host_address(GuestAddress(range.gpa))?;
        uffd::register(uffd_fd.as_fd(), host_addr, range.length)?;
    }
    // 4. 启动 uffd-handler 线程（VMM 内部）
    //    → uffd_handler_loop: epoll 等 UFFD 事件 → 从文件 seek+read 一页 → UFFDIO_COPY
}

    // cloud-hypervisor/vmm/src/memory_manager.rs:1016  uffd_handler_loop（VMM 内部线程）
fn uffd_handler_loop(uffd_fd, stop_event, mut snapshot_file, ranges, page_size, ready_tx) -> Result<(), io::Error> {
    // epoll 同时监听 stop event + UFFD fd
    loop {
        let num_events = epoll::wait(epoll_fd, -1, &mut events)?;
        // 收到 UFFD page fault 事件
        if token == EVENT_UFFD {
            let mut msg: uffd::UffdMsg = unsafe { std::mem::zeroed() };
            libc::read(uffd_raw_fd, &mut msg, size_of::<UffdMsg>());
            if msg.event == UFFD_EVENT_PAGEFAULT {
                let fault_addr = msg.pf_address;
                // 对齐到 page → 算 file_pos → seek+read 一页 → UFFDIO_COPY
            }
        }
    }
}

    CH 与 FC UFFD 的关键差异：CH 在 VMM 进程内起 uffd-handler 线程（epoll + read + UFFDIO_COPY）；FC 把 fd 发外部进程。CH handler panic → exit event + result channel；FC handler 崩溃 → guest 冻结。

    2.3 内核 UFFD 机制：handle_userfault + UFFDIO_COPY

    UFFD 的内核实现是理解 lazy restore 的关键。

    handle_userfault：page fault 的阻塞路径

    // kernel/fs/userfaultfd.c:419
vm_fault_t handle_userfault(struct vm_fault *vmf, unsigned long reason)
{
    // 1. 创建 fault 消息（含 fault 地址、原因 MISSING/WP/MINOR）
    userfault_msg(vmf->address, &vmf->flags, reason, &ctx->flags);

    // 2. 加入 fault_pending_wqh 等待队列
    init_waitqueue_func_entry(&uwq.wq, userfaultfd_wake_function);
    __add_wait_queue(&ctx->fault_pending_wqh, &uwq.wq);

    // 3. 释放 mmap lock（允许其他线程继续 mmap 操作）
    release_fault_lock(vmf);

    // 4. 阻塞当前线程——直到 UFFDIO_COPY 填充页面
    set_current_state(TASK_INTERRUPTIBLE);
    if (userfaultfd_must_wait(ctx, vmf->address, vmf->flags, reason))
        schedule();   // ← 线程在此阻塞

    // 5. 唤醒后返回 VM_FAULT_RETRY——VMM 重新执行 faulting 指令
    return VM_FAULT_RETRY;
}

    对于 KVM：guest EPT violation → host page fault → handle_userfault → vCPU 线程阻塞。直到 VMM/handler 经 UFFDIO_COPY 填充对应页面后唤醒——vCPU 重新执行 guest 指令，此时页面已存在。

    UFFDIO_COPY：填充页面

    // kernel/mm/userfaultfd.c:141  mfill_atomic_pte_copy
static int mfill_atomic_pte_copy(pmd_t *dst_pmd, struct vm_area_struct *dst_vma,
                                  unsigned long dst_addr, unsigned long src_addr, ...)
{
    // 1. 分配新 folio（物理页）
    folio = vma_alloc_folio(GFP_HIGHUSER_MOVABLE, 0, dst_vma, dst_addr, false);

    // 2. 从用户态源地址 copy 数据到 folio（禁用 page fault 防死锁）
    pagefault_disable();
    kaddr = kmap_local_folio(folio, 0);
    copy_from_user(kaddr, src_addr, PAGE_SIZE);   // 从 snapshot 文件读一页
    pagefault_enable();

    // 3. 安装 PTE（映射到 guest memory 虚拟地址）
    //   → set_pte_at()：建立页表项
    //   → 唤醒等待该页的 faulting 线程
}

    O(1) per page：每个 page fault 只处理一页（4KB）。guest 只访问的页才会被填充——对于大部分页只访问一小部分的 workload，restore 几乎瞬时。

    race condition 防护

    // kernel/fs/userfaultfd.c:328  userfaultfd_must_wait
// 在 schedule() 前再次检查页表状态，避免 lost wake-up：
// 如果 UFFDIO_COPY 已经在 must_wait 检查前填充了页面，
// faulting 线程不应再等待。
static inline bool userfaultfd_must_wait(struct userfaultfd_ctx *ctx, unsigned long address, ...)
{
    if (pte_none(*pte) || pte_uffd_wp(*pte))
        return true;   // 仍需等待
    return false;      // 页面已存在，不需等待
}

    3. dirty log：如何精确跟踪 guest 写过的页

    3.1 内核 dirty bitmap 维护

    当 memory slot 带 KVM_MEM_LOG_DIRTY_PAGES 标志时，KVM 在 guest 写某页时设置 kvm_memory_slot.dirty_bitmap 对应位：

    // kernel/include/linux/kvm_host.h:600
struct kvm_memory_slot {
    unsigned long *dirty_bitmap;   // 脏页位图（每 bit = 一页）
    u32 flags;                      // KVM_MEM_LOG_DIRTY_PAGES
    // ...
};

    写保护机制（架构分叉）：

    架构 机制 实现
    x86 EPT entry 设为只读 → guest 写触发 EPT violation → KVM 处理 → 设 dirty bit → 恢复可写 arch/x86/kvm/mmu/mmu.c
    ARM64 Stage-2 entry 设为只读 → guest 写触发 Stage-2 fault → KVM 处理 → 设 dirty bit + HDBSS 硬件加速 arch/arm64/kvm/mmu.c + arch/arm64/kvm/arm.c:1982 
    // kernel/arch/arm64/kvm/arm.c:1982  ARM64 dirty log 同步
void kvm_arch_sync_dirty_log(struct kvm *kvm, struct kvm_memory_slot *memslot)
{
#ifdef CONFIG_ARM64_HDBSS
    // HDBSS：dirty 状态缓冲在硬件 buffer 中
    // kick 所有 vCPU 强制 VM-Exit，刷新硬件 dirty buffer 到 dirty_bitmap
    kvm_for_each_vcpu(i, vcpu, kvm)
        kvm_vcpu_kick(vcpu);
#endif
}

    ARM64 HDBSS 是硬件加速 dirty log——dirty 状态先缓冲在 CPU 的硬件 buffer 中，kvm_arch_sync_dirty_log 时 kick vCPU 刷出。x86 不需要这步（EPT violation 直接同步设 dirty bit）。

    3.2 KVM_GET_DIRTY_LOG：读取脏页快照

    // kernel/virt/kvm/kvm_main.c:2158
// 1. 先同步架构特定 dirty buffer（ARM64 kick vCPU 刷 HDBSS）
kvm_arch_sync_dirty_log(kvm, *memslot);

// 2. 检查是否有脏页
for (i = 0; !any && i < n/sizeof(long); ++i)
    any = (*memslot)->dirty_bitmap[i];

// 3. copy_to_user 到 VMM 提供的 buffer
if (copy_to_user(log->dirty_bitmap, (*memslot)->dirty_bitmap, n))
    return -EFAULT;

    3.3 VMM 侧 dirty log 的双重来源

    // cloud-hypervisor/vmm/src/memory_manager.rs:3056
fn dirty_log(&mut self) -> Result<MemoryRangeTable, MigratableError> {
    for r in &self.guest_ram_mappings {
        let vm_dirty_bitmap = self.vm.get_dirty_log(r.slot, r.gpa, r.size)?;  // KVM dirty log
        let vmm_dirty_bitmap = region.bitmap().get_and_reset();                  // VMM atomic bitmap
        let dirty_bitmap = vm_dirty_bitmap.iter().zip(vmm_dirty_bitmap.iter())
            .map(|(x, y)| x | y);   // 逐位 OR——必须合并！
    }
}

    为什么必须 OR？ - KVM dirty log 只跟踪 guest CPU 经 EPT/Stage-2 的写入（guest 指令直接写内存）。 - VMM 自身经 host userspace mapping 修改 guest memory（如 virtio 设备模拟 DMA 写、balloon discard）不经 EPT——KVM dirty log 看不到。 - 只看 KVM dirty log 会漏掉 VMM 写的页 → migration/增量 snapshot 丢失数据。

    3.4 Firecracker 的 virtio queue dirty 补偿

    // firecracker/src/vmm/src/persist.rs:165  create_snapshot
vmm.device_manager.mark_virtio_queue_memory_dirty(vmm.vm.guest_memory());

    Firecracker 运行期不持续标脏 virtio queue 对应的 guest memory 页（性能考虑）。snapshot 前需 mark_virtio_queue_memory_dirty() 补偿——把所有已激活 virtio 设备的 queue memory 标脏，确保 diff snapshot 不漏 queue 数据。

    4. 内存恢复的难点与陷阱

    4.1 restore 顺序约束

    必须先创建 guest memory → 注册 KVM memory slot → 再恢复 vCPU/设备/interrupt state

    // firecracker/src/vmm/src/builder.rs:439  build_microvm_from_snapshot

vm.register_dram_memory_regions(guest_memory)?;   // ← 先注册 memory slot
// 然后才能恢复 vCPU state（KVM_SET_REGS 等需要 memory 已映射）
for (vcpu, state) in vcpus.iter_mut().zip(microvm_state.vcpu_states.iter()) {
    vcpu.kvm_vcpu.restore_state(state)?;
}
// 设备 restore 必须在 VM arch state 后（VMGenID 注入中断会被覆盖）
let device_manager = DeviceManager::restore(device_ctor_args, &microvm_state.device_states)?;

    hugetlbfs 大页不能直接 mmap 成 guest memory（内核限制）——Firecracker 拒绝 file backend，提示用 UFFD。

    4.4 truncate(false) 陷阱

    // firecracker/src/vmm/src/vstate/vm.rs:340
let mut file = OpenOptions::new().write(true).create(true).truncate(false).open(mem_file_path)?;
// truncate(false)！——如果文件正是当前 VM mmap 来源，truncate 会把运行中 guest memory 清零

    Firecracker diff snapshot 会把脏页合并进当前 VM 的 memory 文件（如果 restore 时从该文件 mmap）。truncate(false) 避免打开文件时清零——只 set_len 调整大小，然后 dump_dirty 只覆盖 dirty 页位置。

    4.5 并发 restore 瓶颈

    CubeSandbox ARM64 实测（snapshot_base_memory.go）：

    并发数 restore p99 瓶颈
    c50 ~536ms 单 VM restore 本身
    c100 ~2190ms 并发争用：内存带宽 + KVM memory slot 锁 + fd 池

    单点 restore 可以很快（UFFD lazy），并发 restore 的长尾来自资源争用——不是单 VM 的算法问题。优化方向是分批启动 + ready 检测。
