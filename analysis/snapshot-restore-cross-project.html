    Snapshot / Restore / Clone 跨项目专题分析

    本文从源码出发，系统比较 Firecracker、Cloud Hypervisor、crosvm、Kata Containers 和 CubeSandbox 五个项目的 snapshot、restore、clone、migration 能力。

    核心问题：五个项目都用"snapshot"这个词，但保存的状态层级完全不同——VMM 级 snapshot 保存 CPU/内存/设备寄存器；runtime 级 save 额外保存 sandbox/container metadata；平台级 clone 还要恢复 rootfs/网络/metadata。混用会导致严重误判。

    源码基线：当前工作树。

    内核底层机制详见 Snapshot/Restore 底层内核技术深度解读。

    0. 一张图看清五个项目的状态边界

    flowchart TB subgraph L1["VMM 级（CPU/内存/设备寄存器/中断控制器）"] FC["Firecracker\nMicrovmState + memory file"] CH["Cloud Hypervisor\nMigratable trait 体系"] Crosvm["crosvm\nSuspendable + 多进程设备"] end subgraph L2["Runtime 级（sandbox/container/agent metadata）"] Kata["Kata Containers\nhypervisor.SaveVM + persist + agent"] end subgraph L3["Platform 级（rootfs/网络/metadata/clone/rollback）"] Cube["CubeSandbox\nVMM snapshot + CubeCoW + catalog + network-agent"] end L1 --> L2 --> L3

    判断原则：先问"保存的是哪一层状态"，再讨论 API。VMM 级 snapshot 只保证"VM 可恢复运行"；runtime 级还要保证"container 语义可恢复"；平台级还要保证"rootfs/网络/metadata 一致"。

    1. Firecracker：一次性构建 + 有限 runtime update

    1.1 snapshot 保存什么

    Firecracker 的 snapshot 是纯 VMM 级状态，分两个文件：

    文件 内容 内核接口
    state 文件 MicrovmState：vm_info + kvm_state + vm_state + vcpu_states + device_states KVM_GET_* ioctl 序列
    memory 文件 guest RAM 字节（full dump 或 dirty diff） KVM_GET_DIRTY_LOG + dump()/dump_dirty() 
    // firecracker/src/vmm/src/persist.rs:86
pub struct MicrovmState {
    pub vm_info: VmInfo,           // mem_size/SMT/cpu_template/boot_source/huge_pages
    pub kvm_state: KvmState,       // KVM capability modifiers
    pub vm_state: VmState,         // x86: PIT/clock/PIC/IOAPIC；aarch64: GIC
    pub vcpu_states: Vec<VcpuState>,  // x86: 11 种状态；aarch64: regs+MPIDR+PVtime
    pub device_states: DevicesState,  // MMIO/PCI/ACPI/serial 设备协议状态
}

    state 与 memory 分离是 Firecracker 的核心设计——state 文件只保存 VMM 协议状态，memory 文件单独保存 guest RAM。restore 时先读 state → 创建 guest memory → build_microvm_from_snapshot。

    1.2 snapshot 创建流程

    1. pause_vm()          → vCPU 发 Pause + immediate_exit + signal → 等 Paused ACK
2. save_state()        → device → vCPU(11 步 ioctl) → KVM → VM arch state
3. snapshot_memory_to_file()
   → full: guest_memory.dump()          // 全量写
   → diff: get_dirty_bitmap() + dump_dirty()  // 只写脏页（KVM_GET_DIRTY_LOG）
4. mark_virtio_queue_memory_dirty()  // 补偿：virtio queue 运行期不持续标脏

    1.3 restore 流程

    读 MicrovmState → net/vsock override → sanity check
→ 创建 guest memory（File mmap 或 UFFD）
→ Kvm::new() → Vm::new() → create_vcpus()
→ register_dram_memory_regions()             [KVM_SET_USER_MEMORY_REGION]
→ [x86] TSC scaling
→ 每 vCPU: SET_MP_STATE → SET_REGS → ... → SET_VCPU_EVENTS  (11 步逆序)
→ [aarch64] 构造 MPIDR 列表 → vm.restore_state(&mpidrs)    [GIC restore]
→ [x86] vm.restore_state(clock_realtime)
→ DeviceManager::restore()                   [必须在 VM arch state 后]
→ start_vcpus(paused) → apply seccomp
→ [可选] resume_vm()

    设备 restore 必须在 VM arch state 后——VMGenID restore 会注入中断通知 guest generation ID 变了，如果先恢复设备，注入的中断会被后续 KVM state 覆盖（builder.rs:507 注释）。

    1.4 能力边界

    能力 支持？ 说明
    full snapshot ✓ 全量 memory dump
    diff snapshot ✓ KVM dirty log，合并进目标文件（不是单独 delta）
    UFFD restore ✓ fd 发外部 handler（Firecracker 保留 fd）
    live migration ✗ 无 transport 机制
    vhost-user-block snapshot ✗ check_unsnapshottable_devices 阻止
    runtime/platform metadata ✗ 纯 VMM 级
    clone/rollback ✗ 不是 Firecracker 产品语义

    2. Cloud Hypervisor：Migratable trait 体系

    2.1 trait 继承链

    Cloud Hypervisor 把 snapshot/restore/migration 组织成 4 层 trait：

    // cloud-hypervisor/vm-migration/src/lib.rs
pub trait Pausable: Send { fn pause(&mut self); fn resume(&mut self); }
pub trait Snapshottable: Pausable { fn id(&self) -> String; fn snapshot(&mut self) -> Result<Snapshot>; }
pub trait Transportable: Snapshottable { fn send(&self, snapshot: &Snapshot, url: &str) -> Result<()>; fn recv(&mut self, snapshot: &Snapshot) -> Result<()>; }
pub trait Migratable: Transportable {
    fn start_dirty_log(&mut self) -> Result<()>;
    fn dirty_log(&mut self) -> Result<MemoryRangeTable>;
    fn complete_migration(&mut self) -> Result<()>;
}

    关键设计：snapshot() 只生成状态计划（哪些 range 要发送），send() 才传输真实字节。MemoryManager::snapshot() 先生成 MemoryRangeTable 存到 snapshot_memory_ranges，send() 阶段遍历 range 从 guest memory 读字节写入 memory-ranges 文件。

    2.2 VM 作为复合迁移对象

    Vm 实现了 Migratable，它的 snapshot 聚合三个 manager：

    Manager 保存什么 源码
    CpuManager 每 vCPU CpuState（regs/sregs/xsave/msr/events/mp_state/CPUID） cpu.rs:2693
    MemoryManager MemoryManagerSnapshotData（memory_ranges + guest_ram_mappings + hotplug_slots + arch_mem_regions） memory_manager.rs:2970
    DeviceManager DeviceManagerState（device_tree + device_id_cnt + 每设备 Migratable state） device_manager.rs:887

    2.3 dirty log 双重来源

    // cloud-hypervisor/vmm/src/memory_manager.rs:3056
fn dirty_log(&mut self) -> Result<MemoryRangeTable, MigratableError> {
    for r in &self.guest_ram_mappings {
        let vm_dirty_bitmap = self.vm.get_dirty_log(r.slot, r.gpa, r.size)?;  // KVM dirty log
        let vmm_dirty_bitmap = region.bitmap().get_and_reset();                  // VMM atomic bitmap
        let dirty_bitmap = vm_dirty_bitmap.iter().zip(vmm_dirty_bitmap.iter())
            .map(|(x, y)| x | y);   // 逐位 OR
        table.extend(MemoryRangeTable::from_dirty_bitmap(dirty_bitmap, r.gpa, 4096));
    }
}

    为什么必须 OR？ KVM dirty log 只跟踪 guest CPU 经 EPT/Stage-2 的写入。VMM 自身经 host userspace mapping 修改 guest memory（如 virtio 设备模拟 DMA）不经 EPT——需要 VMM 侧 atomic bitmap 补充。只看 KVM dirty log 会漏掉 VMM 写的页。

    2.4 migration 迭代协议

    flowchart LR A["start_dirty_log\nKVM_MEM_LOG_DIRTY_PAGES"] --> B["Round 1: 全量发送\nguest 继续运行"] B --> C["Round 2: 发送 round 1 脏页"] C --> D["Round N: 脏页收敛"] D --> E["pause VM\nstop-and-copy"] E --> F["最后一轮脏页"] F --> G["complete_migration"]

    收敛条件：某轮 dirty 页量低于阈值（或达到最大轮数）→ stop-and-copy。与 QEMU/KVM 传统 migration 一致，但用 Migratable trait 而非 QMP。

    2.5 两种 restore 模式

    模式 行为 优势
    Copy（默认） fill_saved_regions() 从文件读全部 range 写入 guest memory 简单，恢复后不依赖 handler
    OnDemand（UFFD） restore_by_uffd() 注册 UFFD → uffd_handler_loop 后台按需填页 restore 初始时延低

    2.6 能力边界

    能力 支持？ 说明
    snapshot/restore ✓ Migratable trait
    live migration ✓ dirty log 多轮迭代
    UFFD restore ✓ VMM 内部 uffd_handler_loop 线程（非外部）
    VFIO dirty log ✗ 默认空实现——VFIO DMA 不经 KVM EPT
    runtime/platform metadata ✗ 纯 VMM 级
    clone/rollback ✗ 不是 CH 产品语义

    3. crosvm：Suspendable + 多进程设备协调

    3.1 Suspendable trait

    // crosvm/devices/src/suspendable.rs:18
pub trait Suspendable: Send {
    fn snapshot(&mut self) -> Result<serde_json::Value>;
    fn restore(&mut self, data: serde_json::Value) -> Result<()>;
    fn sleep(&mut self) -> Result<()>;
    fn wake(&mut self) -> Result<()>;
}

    crosvm 的 snapshot 难点不在 trait，而在多进程设备——很多设备运行在 fork 出来的子进程里，snapshot 要通过 Tube IPC 协调。

    3.2 ProxyDevice 的跨进程 snapshot

    flowchart LR Main["主进程 ProxyDevice"] -->|"Tube IPC: snapshot 命令"| Child["子进程 device"] Child -->|"序列化 → SnapshotFile 临时文件"| Temp["tempfile"] Temp -->|"FD 传递"| Main

    ProxyDevice 把 BusDevice 放到子进程，经 Tube 通信。snapshot 数据可能太大不能经 Tube 一次发送——SnapshotFile 用临时文件承载序列化后的 AnySnapshot（proxy.rs:62）。

    3.3 区分 guest-visible vs host-ephemeral

    GPU 设备示例（virtio_gpu.rs:99/200）：surface ID 不是 guest visible，restore 时重新分配——只保存"是否有 surface"和 parent scanout id。不是所有 host 对象都原样持久化。

    3.4 能力边界

    能力 支持？ 说明
    snapshot/restore ✓ Suspendable + 多进程 Tube
    live migration 部分 取决于设备实现
    子进程设备 snapshot ✓ 但需 IPC + 临时文件 + FD 传递
    host ephemeral state ✗ restore 时重建
    clone/rollback ✗ 不是 crosvm 产品语义

    4. Kata Containers：三层独立保存

    Kata 不是 VMM，是 VM-based container runtime。它的 save/restore 比 VMM 多一层 runtime metadata。

    4.1 三层保存（不在一个事务内）

    层 保存什么 保存方式 源码
    virtcontainers persist sandbox/container/hypervisor/agent/network/mounts/config metadata Sandbox.Save() → store.ToDisk() persist.go:278
    hypervisor SaveVM VM CPU/memory/device QEMU QMP migrate / FC / CH / Dragonball 各自实现 hypervisor.go:1297
    agent state container/process 运行态 不自动保存——需 reconnect/reuse — 
    // kata-containers/src/runtime/virtcontainers/persist.go:278
func (s *Sandbox) Save() error {
    s.dumpState(&ss, cs); s.dumpHypervisor(&ss); s.dumpDevices(&ss, cs)
    s.dumpProcess(cs); s.dumpMounts(cs); s.dumpAgent(&ss); s.dumpNetwork(&ss); s.dumpConfig(&ss)
    return s.store.ToDisk(ss, cs)
}

    关键区别：Sandbox.Save() 不等于 hypervisor.SaveVM()——前者落盘的是 virtcontainers 层 runtime metadata（让 shim 重启后恢复 virtcontainers 对象），后者是 VM 级 snapshot（CPU/memory/device）。两层是独立操作，不在一个事务内。

    4.2 SaveVM 能力因 plugin 而异

    • QEMU SaveVM()：QMP migrate → DevicesStatePath
    • remoteHypervisor.SaveVM()：返回 not implemented
    • stratovirt.SaveVM()：空实现

    Kata 的 SaveVM() 是抽象能力，不等于每个 plugin 都有同等级实现。

    5.2 两条 snapshot 路径

    路径 入口 rootfs 来源 memory snapshot type

    5.3 增量 snapshot 三层退化（CubeSandbox 独有）

    // Cubelet/services/cubebox/snapshot_base_memory.go:188
func prepareCommitMemoryArtifact(ctx, stepLog, cb, templateID, memorySizeBytes) (*CowSnapshotObject, string, error) {
    // Tier 1: soft-dirty — FICLONE clone 上次 snapshot 的 memory volume → VMM 只写 soft-dirty 页
    if baseMemoryObject, err := resolveBaseMemoryObject(ctx, cb); err == nil {
        memoryObject, _ := storage.CommitTemplateMemoryFromBase(ctx, baseMemoryObject, templateID, memorySizeBytes)
        return memoryObject, snapshotTypeSoftDirty, nil
    }
    // Tier 2: pagemap_anon — FICLONE clone 上次 restore 的 base memory → VMM 只写 anon CoW 页
    if restoreBase, err := resolveRestoreBaseMemoryObject(ctx, cb); err == nil {
        memoryObject, _ := storage.CommitTemplateMemoryFromBase(ctx, restoreBase, templateID, memorySizeBytes)
        return memoryObject, snapshotTypeIncremental, nil
    }
    // Tier 3: full — 新建空 memory volume → VMM 写全部 memory
    memoryObject, _ := storage.CreateTemplateMemoryVolume(ctx, templateID, memorySizeBytes)
    return memoryObject, snapshotTypeFull, nil
}

    关键设计：增量不是 delta——目标 memory 文件始终是可直接 restore 的完整 image。增量只是"FICLONE clone 后只覆盖变化页"，restore 不需合并 delta。

    5.5 restore 两条路径

    创建期 app snapshot restore：

    CubeShim start_vm → restore_vm(RestoreConfig)
  RestoreConfig: source_url + fs/net/disks/pmem/vsock + memory_vol_url
→ CubeHypervisor vm_restore() → Vm::new_from_snapshot() → Vm::restore() → Vm::resume()

    运行期 rollback restore：

    CubeShim rollback_vm(target_config)
→ 断开 agent + VmDelete + drain stale VmShutdown   [防误判]
→ restore_vm(target_config)
  → [同上，但 target_config 只含 source_url + memory_vol_url + disks]

    差异：创建期 restore 有 RestoreConfig.net/fs/vsock/pmem（覆盖当前节点 host 后端）；rollback restore 的 Cubelet JSON 当前不填 net/fs/vsock——VMM 用 snapshot 中保存的 tap_if_name 重开。

    5.6 并发 restore 瓶颈（实测）

    CubeSandbox ARM64 c100（100 并发）restore：

    阶段 c50 p99 c100 p99 瓶颈
    network-agent/CubeVS ~0.1ms ~0.1ms 已优化（非瓶颈）
    CubeShim RestoreVm ~536ms ~2190ms 并发争用：内存带宽 + KVM memory slot 锁
    端到端 ~543ms ~2668ms VMM snapshot restore 是主瓶颈

    单点 restore 可以很快（UFFD lazy），并发 restore 的长尾来自资源争用——不是单 VM 算法问题。

    10. 本专题结论

    五个项目的"snapshot"含义完全不同：

    1. Firecracker = VMM 级一次性 snapshot（state + memory 分离，diff 基于 KVM dirty log）。
    2. Cloud Hypervisor = VMM 级 Migratable trait 体系（snapshot + transport + dirty log 多轮 migration）。
    3. crosvm = VMM 级 Suspendable 协议（多进程设备经 Tube/临时文件协调 snapshot）。
    4. Kata = Runtime 级三层独立保存（virtcontainers persist + hypervisor SaveVM + agent state——不在一个事务内）。
    5. CubeSandbox = Platform 级产品能力（VMM snapshot + CubeCoW O(1) clone + catalog metadata + network-agent + 增量 soft-dirty/pagemap_anon/full）。

    后续所有分析都应先标明"状态边界"，再讨论具体 API。 把 VMM snapshot 误解成产品级 clone/rollback，是最常见的分析错误。
