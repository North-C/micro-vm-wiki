    Snapshot 设备状态保存与恢复专题

    本文聚焦 snapshot/restore 中设备状态的部分——保存什么、按什么顺序、restore 时如何重建设备对象 + transport + 中断路由 + 事件订阅。

    源码基线：Linux 6.6.0 内核 + Firecracker/Cloud Hypervisor/CubeSandbox VMM 源码。

    相关：Snapshot/Restore 底层内核技术深度解读、Snapshot 内存保存与恢复专题、Snapshot/Restore/Clone 跨项目专题。

    0. 设备状态保存的核心问题

    设备 snapshot 比 CPU/内存更复杂——因为设备有三层状态：

    状态层 保存什么 为什么不能只存一层
    设备协议状态 virtio features/queue/config space/device-specific（block disk path/balloon target/net TAP name） guest driver 协商结果 + 设备后端配置
    transport 状态 MMIO: irq_status/feature_select/queue_select/device_status；PCI: SBDF/PCI config/common config/MSI-X table+PBA/BAR guest 可见的总线协议寄存器
    运行时事件订阅 ioeventfd/irqfd/event subscriber 注册关系 不直接保存——restore 时重新注册

    运行时事件订阅不持久化——ioeventfd/irqfd 是内核 fd，无法序列化。restore 时必须重新创建 fd + 重新注册到 KVM + 重新订阅 EventManager。

    1. Firecracker：三层分离保存

    1.1 DevicesState 结构

    // firecracker/src/vmm/src/device_manager/mod.rs:558
fn save(&self) -> Self::State {
    DevicesState {
        mmio_state: self.mmio_devices.save(),    // MMIO transport + virtio 设备
        acpi_state: self.acpi_devices.save(),      // ACPI 设备（VMGenID/VMClock/GED）
        pci_state: self.pci_devices.save(),         // PCI transport + virtio 设备
        serial_state: self.serial_state(),          // 串口
    }
}

    Firecracker 按 transport 类型（MMIO vs PCI）分开保存。如果 pci_enabled=false，所有设备走 MMIO；如果 pci_enabled=true，走 PCI。restore 时按 snapshot 中保存的 transport 类型重建。

    1.2 VirtioDeviceState + QueueState（设备协议状态）

    // firecracker/src/vmm/src/devices/virtio/persist.rs:116
pub struct VirtioDeviceState {
    pub device_type: VirtioDeviceType,    // Net/Block/Balloon/Vsock/Mem/Pmem/Rng
    pub avail_features: u64,              // 设备提供的 features
    pub acked_features: u64,              // guest 协商确认的 features
    pub queues: Vec<QueueState>,          // 每 virtqueue 的状态
    pub activated: bool,                  // 设备是否已激活
}
// :34
pub struct QueueState {
    max_size: u16,        // 队列最大元素数
    size: u16,            // guest 选择的队列大小
    ready: bool,          // 队列配置完成标志
    desc_table: u64,      // descriptor table 的 GPA
    avail_ring: u64,      // available ring 的 GPA
    used_ring: u64,       // used ring 的 GPA
    // next_avail/used: queue 游标
    // num_added: 已添加到 used ring 的计数
}

    QueueState 保存的是 guest driver 已配置的 ring 地址 + 游标。restore 后不需 guest 重新配置 queue——直接恢复到 snapshot 时的队列状态。build_queues_checked() restore 时校验 acked ⊆ avail + queue 数量 + max size。

    1.3 prepare_save：为什么设备保存前要先"准备"

    // firecracker/src/vmm/src/device_manager/persist.rs:233
// We need to call `prepare_save()` on the device before saving the transport
// so that, if we modify the transport state while preparing the device, e.g. sending
// an interrupt to the guest, this is correctly captured in the saved transport state.
locked_device.prepare_save();
let transport_state = mmio_transport_locked.save();   // ← 在 prepare_save 之后

    // firecracker/src/vmm/src/devices/virtio/block/virtio/device.rs:572
pub fn prepare_save(&mut self) {
    if !self.is_activated() { return; }
    self.drain_and_flush(false);                          // 排空挂起的 I/O + flush
    if let FileEngine::Async(ref _engine) = self.disk.file_engine {
        self.process_async_completion_queue();            // 处理异步完成队列
    }
}

    prepare_save 的意义：设备可能有挂起的异步 I/O（block async engine 的 io_uring completion）。如果直接保存而不排空，restore 后这些 I/O 结果会丢失——guest 等不到 completion。排空后，prepare_save 可能向 guest 发中断（通知 I/O 完成）——这个中断状态必须被后续的 transport save 捕获。因此 prepare_save 必须在 transport save 之前。

    1.4 save 顺序：prepare_save → transport → device state

    for each virtio device:
  1. prepare_save()          → 排空 I/O + flush（可能发中断）
  2. transport.save()         → 保存 MMIO/PCI 寄存器（含 prepare_save 产生的中断状态）
  3. device.save()            → 保存设备协议状态（VirtioDeviceState + QueueState）
  4. 按 device_type 分到 balloon_device/block_devices/net_devices/... 字段

    1.5 restore 顺序：重建设备 → transport → 注册 → activate

    // firecracker/src/vmm/src/device_manager/persist.rs:354  MMIO restore
fn restore(constructor_args, state) -> Result<Self, Self::Error> {
    // 1. 按 device_type 重建设备对象（从 device_state 反序列化）
    let device = Arc::new(Mutex::new(Block::restore(BlockConstructorArgs { mem }, &block_state.device_state)?));
    // 2. 重建 transport（从 transport_state 反序列化）
    let mmio_transport = MmioTransport::restore(restore_args, state)?;
    // 3. 注册到 MMIO bus + EventManager（重新创建 ioeventfd/irqfd + 订阅）
    dev_manager.register_mmio_virtio(vm, id, MMIODevice { resources, inner: mmio_transport }, event_manager)?;
    // 4. 如果原设备已激活 → 重新 activate（注册 queue/rate limiter/async completion event）
    if activated { device.lock().unwrap().activate(mem, interrupt)?; }
}

    // firecracker/src/vmm/src/device_manager/pci_mngr.rs:428  PCI restore
fn restore(constructor_args, state) -> Result<Self, Self::Error> {
    // 1. 建 PCI segment
    pci_devices.attach_pci_segment(constructor_args.vm)?;
    // 2. 按 device_type 重建设备 + 从 device_state 反序列化
    let device = Arc::new(Mutex::new(Balloon::restore(BalloonConstructorArgs { mem }, &balloon_state.device_state)?));
    // 3. 重建 VirtioPciDevice（从 transport_state）
    // 4. 注册到 PCI bus + MMIO bus + ioeventfd + EventManager
    pci_devices.restore_pci_device(vm, device, &device_id, &transport_state, event_manager)?;
}

    restore 重建的不只是数据——还有 fd（ioeventfd/irqfd/eventfd）、bus 注册（MMIO/PCI bus 地址分发）、EventManager 订阅。这些运行时对象无法序列化，必须从 snapshot 中的 transport/device state 重新创建。

    1.6 设备特有状态

    设备 特有保存项 restore 重建
    Block disk_path/partuuid/cache_type/root_device/file_engine_type 重新打开 backing file + 检测 image type
    Net tap_if_name/MAC/MMDS namespace/rate limiter state 重新打开 TAP（按 tap_if_name）+ 配置 offload
    Balloon stats_polling_interval/stats_desc_index/latest_stats/hinting_state/config_space(num_pages/actual_pages) 恢复 balloon target + 统计 + hinting
    Vsock CID/UDS path/last local port 重新打开 UDS backend + transport reset
    Pmem file path/size/discard_writes 重新打开 file + mmap + 注册 memory region
    Virtio-mem addr/region_size/block_size/usable_region_size/plugged_blocks/requested_size/slot_size 恢复 plugged bitmap + KVM slot

    vhost-user-block 不支持 snapshot——check_unsnapshottable_devices() 在 save 前检查，发现 vhost-user block 直接返回 NotAllowed。

    2. Cloud Hypervisor：Migratable trait + DeviceTree

    2.1 DeviceManager 保存：device_tree 是拓扑权威

    // cloud-hypervisor/vmm/src/device_manager.rs  DeviceManagerState
// 保存：device_tree（parent/children/BDF/BAR/MMIO resources）+ device_id_cnt
// 每个设备自己的 Migratable::snapshot() 保存协议状态

    CH 的设备保存与 FC 不同——它用 DeviceTree 记录拓扑（谁是谁的 parent/child、BDF/BAR/MMIO 资源），每个设备经 Migratable trait 自己保存协议状态。

    2.2 两阶段 restore

    // cloud-hypervisor/vmm/src/device_manager.rs:4930  第一阶段：DeviceManager::restore
fn restore(&mut self, snapshot: Snapshot) -> Result<(), MigratableError> {
    self.set_state(&snapshot.to_state(DEVICE_MANAGER_SNAPSHOT_ID)?);  // 恢复 device_tree + device_id_cnt
    self.create_devices(None, None, None)?;   // 按 device_tree 重建设备对象（复用 BDF/BAR/MMIO）
    Ok(())
}

    // cloud-hypervisor/vmm/src/device_manager.rs:4478  第二阶段：restore_devices
pub fn restore_devices(&mut self, snapshot: Snapshot) -> Result<(), MigratableError> {
    // children traversal 反序 + parent traversal 反序 → 两组
    let devices_children = self.device_tree.lock().unwrap().breadth_first_traversal_children().rev().cloned().collect();
    let devices_parent = self.device_tree.lock().unwrap().breadth_first_traversal_parent().rev().cloned().collect();
    // 每组内并发（tokio），组间等待
    self.restore_device_node((devices_children, devices_parent), snapshot)?;
}

    // cloud-hypervisor/vmm/src/device_manager.rs:4426  restore_device_node
// 每个 migratable 设备：
//   1. 要求 snapshot 中存在同 id 子快照（缺则 "Missing device <id>"）
//   2. pause() → restore(snapshot)
//   3. 组内并发，组间等待

    CH 与 FC 的关键差异：CH restore 分两阶段——① DeviceManager::restore 先恢复 device_tree + create_devices（按快照拓扑重建设备对象，复用 BDF/BAR/MMIO）；② restore_devices 再逐个恢复设备内部状态（pause + restore）。FC 是一次性重建设备 + transport + activate。

    2.3 DeviceTree 复用：restore 不重新分配资源

    // cloud-hypervisor/vmm/src/device_manager.rs  pci_resources
// restore 时查 device_tree 同 id node → 复用 MmioAddressRange{base, size}
let (pci_device_bdf, resources) = if let Some(node) = self.device_tree.lock().unwrap().get(id) {
    let pci_device_bdf = node.pci_bdf.ok_or(DeviceManagerError::MissingDeviceNodePciBdf)?;
    (Some(pci_device_bdf), Some(node.resources.clone()))   // 复用 BDF + BAR/MMIO
} else {
    (None, None)   // 新建设备才分配
};

    pmem 的 guest address range 不能改——restore 时必须复用 snapshot 中的 MmioAddressRange。新分配会导致 guest physical 地址不一致。

    2.4 VirtioPciDevice restore 顺序

    1. MsixConfig::restore()（set_state）     → 重建 MSI-X table/PBA/mask + 重建 route + enable irqfd
2. common_config.restore()                → 恢复 queue select/msix vector 等
3. configuration.restore()                → 恢复 PCI config space
4. queue state restore                    → 恢复 desc/avail/used ring 地址 + 游标
5. if device_activated && driver ready → activate()  → 重新注册 queue/rate limiter/async completion event

    MSI-X 最先恢复——确保设备配置恢复前中断路由已重建。这与 Firecracker 的 restore 顺序一致（pci_device.rs:1184）。

    3. CubeSandbox：继承 CH + 平台层设备恢复

    3.1 CubeSandbox 的设备 snapshot 继承 CH

    CubeSandbox 的 CubeHypervisor 是 Cloud Hypervisor 派生——设备 save/restore 的核心逻辑（DeviceTree + Migratable + 两阶段 restore）与 CH 一致。

    3.2 平台层设备恢复差异

    CubeSandbox 在 CH 之上增加了平台层设备恢复：

    设备类型 CH 层恢复 CubeSandbox 平台层
    virtio-net transport + MSI-X + queue + RestoreConfig.net 替换 TAP 后端（按 id）
    virtio-fs transport + queue + backend state（back_state） + RestoreConfig.fs 替换 shared_dir/allowed_dirs
    virtio-block transport + queue + disk_path + RestoreConfig.disks 替换 disk path
    virtio-pmem transport + MMIO range + RestoreConfig.pmem 替换 file
    vsock transport + CID + UDS path + RestoreConfig.vsock 替换 socket

    "换后端，不换拓扑"：CubeSandbox restore 时设备拓扑（BDF/BAR/MMIO/queue ring 地址）来自 snapshot 不可变；但 host 后端（TAP/disk path/fs shared_dir）可替换为当前节点资源。这是 RestoreConfig 的核心语义。

    3.3 native virtio-fs 的 back_state 恢复

    // CubeSandbox-sandbox-clone/hypervisor/virtio-devices/src/fs.rs:916  Fs::activate
if self.restore {
    if !self.back_state.is_empty() {
        server.deserialize_and_apply_data(self.back_state.as_ref())?;  // 应用旧 server 状态
    }
}

    native virtio-fs 不只重开目录——它还恢复 backend server 的序列化状态。vhost-user fs 不存 backend 内部对象，只存协商 features + 重新连 socket + 重建 vring。

    4. 设备 save/restore 的顺序约束

    4.1 save 顺序

    1. pause vCPU（确保设备不再产生新 I/O）
2. for each device:
   a. prepare_save()     → 排空挂起 I/O + flush（可能发中断）
   b. transport.save()   → 保存总线寄存器（含 prepare_save 产生的中断状态）
   c. device.save()      → 保存设备协议状态 + queue state
3. save vCPU state
4. save KVM/VM arch state
5. save memory

    prepare_save 必须在 transport save 前——否则 prepare_save 产生的中断状态不会被 transport save 捕获。

    4.2 restore 顺序

    1. 创建 guest memory + 注册 KVM memory slot
2. 恢复 vCPU state（KVM_SET_*）
3. 恢复 VM arch state（interrupt controller / clock）
   [aarch64] GIC/ITS restore（必须在设备前——GICR_TYPER ← MPIDR）
4. 恢复 DeviceManager（set_state + create_devices）→ 重建设备对象 + transport
5. 恢复设备内部状态（restore_devices → pause + restore per device）
   MSI-X 最先 → common config → PCI config → queue state
6. if activated → activate()（重新注册 ioeventfd/irqfd/queue event/rate limiter）
7. start vCPU（paused）
8. [可选] resume

    设备 restore 必须在 VM arch state 后——VMGenID restore 会注入中断，如果先恢复设备，注入的中断会被后续 KVM state（含中断控制器）覆盖。ARM64 GIC restore 必须在设备前——GICR_TYPER 从 vCPU MPIDR 推导，ITS table 必须完整重建。

    4.3 顺序约束对比

    约束 FC CH CubeSandbox 原因
    prepare_save 在 transport save 前 ✓ —（CH 用 Migratable） ✓ prepare_save 产生的中断状态需被 transport 捕获
    设备 restore 在 VM arch state 后 ✓ ✓ ✓ VMGenID 注入中断会被 KVM state 覆盖
    ARM64 GIC restore 在设备前 — ✓ ✓ GICR_TYPER ← MPIDR；缺 GicV3Its snapshot 报错
    MSI-X restore 在 common config 前 ✓ ✓ ✓ 中断路由必须先于设备配置恢复
    activate 在 queue restore 后 ✓ ✓ ✓ activate 需 queue ring 地址已恢复
    vhost-user-block 不可 snapshot ✓ — — check_unsnapshottable_devices 阻止

    6. 关键设计决策与陷阱

    6.1 "设备 restore 成功 ≠ guest 可用"

    设备 restore 重建了 transport + device state + ioeventfd/irqfd——但 guest driver 是否感知到设备恢复取决于 guest memory 中的 virtqueue ring 内容是否与 restore 的 QueueState 一致。如果 memory restore 与 device restore 不一致（如 memory UFFD 还没填到 queue ring 那一页），guest 看到的 queue 是空的或错位的。

    6.2 vsock 连接不跨 snapshot

    vsock 的 prepare_save 会发 transport reset event——vsock 不支持连接跨 snapshot 保持。restore 后 vsock 是 empty 状态，需重新建立连接。

    6.3 VFIO dirty log 遗漏

    VFIO 设备经 IOMMU 直接 DMA 写 guest memory，不经 KVM EPT/Stage-2——KVM dirty log 完全看不到。CH 的 DeviceManager::dirty_log() 遍历 migratable 设备，但 VFIO dirty log 默认空实现。这意味着 VFIO 设备的 migration/snapshot 可能丢失 guest memory 中被设备 DMA 写入的页。

    6.4 并发 restore 的设备争用

    CubeSandbox c100 并发 restore 时，除了 memory 带宽/KVM slot 锁，设备 restore 也会争用——特别是 ioeventfd/irqfd 创建（内核 fd 分配）和 MMIO bus 注册（全局锁）。这是 c100 p99 ~2.7s 的部分来源。

    6.5 CubeSandbox 增量 snapshot 的设备一致性

    CubeSandbox 的 soft-dirty/incremental snapshot 只写变化内存页——但设备状态始终全量保存（不像内存可以增量）。CommitSandbox 每次都调 vm.snapshot() 保存完整 VMM state（含 device state），只是 memory 走增量。这保证了设备状态的一致性——不会出现"内存是增量的但设备状态是旧的"。
