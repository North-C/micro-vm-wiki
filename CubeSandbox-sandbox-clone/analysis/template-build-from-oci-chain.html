CubeSandbox Template 构建链路：从 OCI 镜像到 Template

本文追踪 CubeSandbox 如何从 OCI 容器镜像构建出可 clone/rollback 的 Template——分析完整构建过程、各产物组成以及配置空间。

源码基线：当前仓库工作树。

相关：snapshot create/commit、CubeCoW 存储引擎、cubelet workflow create、snapshot catalog restore binding。

0. 术语与背景

Template 是什么

Template 是 CubeSandbox 的可复制基线：从 OCI 镜像 + 资源配置构建一次 VM，对运行中 VM 执行 full snapshot（CPU/memory/device 状态 + rootfs），然后销毁临时 VM。后续创建 sandbox 时从 Template clone（O(1) FICLONE），不需重新启动 VM。

Template vs Runtime Snapshot

类型 kind rootfs kind memory kind 构建方式 增量基础
Template template snapshot volume AppSnapshot：建临时 cubebox → full snapshot → rootfs from build 是后续所有 clone 的基线
Runtime Snapshot runtime_snapshot snapshot snapshot CommitSandbox：对运行中 sandbox snapshot 从 Template 或上次 snapshot 增量

构建链路全景

1. 构建输入：OCI 镜像 + 资源配置

1.1 OCI 镜像

Template 构建的镜像经 containerd image service 拉取/解压。containerd 的 snapshotter 负责把镜像 layer 解压成 rootfs 文件系统。Cubelet workflow 的 images action 调 EnsureImage 确保镜像可用。

1.2 资源配置

// Cubelet/services/cubebox/appsnapshot.go:42
type CubeboxSnapshotSpec struct {
    Resource    json.RawMessage `json:"resource,omitempty"`   // CPU/memory
    Disk        json.RawMessage `json:"disk,omitempty"`        // disk 配置
    Pmem        json.RawMessage `json:"pmem,omitempty"`        // pmem 配置
    Kernel      string          `json:"kernel,omitempty"`       // guest kernel 路径
    ContainerID string          `json:"container_id,omitempty"` // 临时 container id
}
// :50
type ResourceSpec struct {
    CPU    int `json:"cpu"`       // vCPU 数
    Memory int `json:"memory"`    // 内存 MB
}

specDir 按 "{CPU}C{Memory}M" 格式生成（如 "2C4G"），成为 snapshot 目录的一部分。同一 template id 不同资源规格可共存（不同 specDir）。

2. AppSnapshot 七步构建过程

Step 1: 创建临时 cubebox

// Cubelet/services/cubebox/appsnapshot.go:114
stepLog.Info("Step 1: Creating cubebox...")
// templateID + "_0" 作为 sandbox id（固定格式）
createReq.Annotations[createIDKey] = templateID + "_0"
createRsp, err := s.Create(ctx, createReq)   // 经完整 workflow create（images/volume/storage/network/cgroup/cubebox）

临时 cubebox 经 完整 workflow create 路径——和普通 sandbox 创建走同一流程（cubelet workflow create 编排），包括镜像拉取、网络配置、cgroup、containerd NewContainer/NewTask、CubeShim 启动 VM。唯一差异是 sandbox id 固定为 <templateID>_0。

Step 2: 从 containerd spec 提取 CubeboxSnapshotSpec

// :206
stepLog.Info("Step 2: Getting cubebox spec...")
spec, err := s.getCubeboxSnapshotSpec(ctx, sandboxID)
// 从 containerd 容器 spec 中提取：resource/disk/pmem/kernel/containerID
// 验证 resourceSpec.CPU > 0 && Memory > 0
specDir := fmt.Sprintf("%dC%dM", resourceSpec.CPU, resourceSpec.Memory)
snapshotPath := filepath.Join(snapshotDir, "cubebox", templateID, specDir)
tmpSnapshotPath := snapshotPath + ".tmp"   // 先写临时目录，成功后 rename

Step 3: 创建空 memory volume

// :253
stepLog.Info("Step 3: Creating snapshot at temporary path...")
memoryObject, err = storage.CreateTemplateMemoryVolume(ctx, templateID, memorySizeBytes)
// Cubelet/storage/cubecow_snapshot_artifacts.go:110
func CreateTemplateMemoryVolume(ctx, templateID, sizeBytes) (*CowSnapshotObject, error) {
    volume, err := manager.CreateMemoryVolume(ctx, templateID, sizeBytes)   // CubeCoW 建空 volume
    return cubecowVolumeToSnapshotObject(ctx, manager, volume)
}

创建的是空 volume（不是从已有 memory clone）。因为 Template 的 memory snapshot 是 full——VMM 会把 guest RAM 全量写入这个 volume。

Step 4: cube-runtime snapshot（pause → full snapshot → resume）

// :279
stepLog.Info("Step 4: Executing cube-runtime snapshot...")
// AppSnapshot builds a brand-new template from a fresh sandbox: there is
// no prior snapshot to diff against → always full
s.executeCubeRuntimeSnapshot(ctx, sandboxID, spec, tmpSnapshotPath, memoryObject.DevPath, snapshotTypeFull)

snapshotTypeFull = 固定 full（新建 template 没有增量基础）。Shim 侧经 HTTP API 对运行中 VMM 执行 pause → snapshot → resume（详见 snapshot create/commit §6）。VMM 把 guest memory 全量写入 memoryObject.DevPath（CubeCoW volume），VM state 写入 tmpSnapshotPath/ 目录。

Step 5: 从 build rootfs 创建 template rootfs

// :304
rootfsObject, err = storage.CreateTemplateRootfsFromBuild(ctx, templateID)
// Cubelet/storage/cubecow_snapshot_artifacts.go:98
func CreateTemplateRootfsFromBuild(ctx, templateID) (*CowSnapshotObject, error) {
    volume, err := manager.CommitTemplateRootfs(ctx, cowTemplateBuildRootfsName(templateID), templateID)
    // CommitTemplateRootfs = FICLONE clone build rootfs → template rootfs snapshot
    return cubecowVolumeToSnapshotObjectWithoutActivation(ctx, manager, volume)
}

rootfs kind = snapshot（不是 volume）。CubeCoW CommitTemplateRootfs 经 FICLONE 把临时 cubebox 的 build rootfs（容器镜像解压后的可写层）clone 成 template rootfs snapshot。后续 create-from-template 再从这个 snapshot FICLONE clone 出每个 sandbox 的 rootfs。

Step 6: 销毁临时 cubebox

// :319
stepLog.Info("Step 5: Destroying temporary cubebox...")
destroyRsp, err := s.Destroy(destroyCtx, destroyReq)   // 销毁临时 VM + 清理
// 失败 fallback：force destroy

销毁临时 cubebox = 停 VM + 清理 containerd container/task + 清理网络/cgroup/storage。snapshot 已在 Step 4-5 保存到独立路径，不依赖 cubebox 是否存活。

Step 7: 移到最终路径 + 写 catalog

// :360
stepLog.Info("Step 6: Moving snapshot to final path...")
os.Rename(tmpSnapshotPath, snapshotPath)   // 原子 rename
// :376
stepLog.Info("Step 7: Writing snapshot status flag file...")
writeSnapshot(stepLog)   // 写 flag 标记 template 可用
storage.WriteSnapshotCatalog(&SnapshotCatalogEntry{
    SnapshotID: templateID, Kind: storage.CatalogKindTemplate,
    RootfsVol: rootfsObject.Name, RootfsKind: "snapshot",
    MemoryVol: memoryObject.Name, MemoryKind: "volume",
    /*...*/
})

Rename 保证原子性——要么完整 template 可用，要么不存在（不会看到半完成的 template）。catalog.json 是 Cubelet 本地权威。

3. Template 产物组成

3.1 物理目录结构

<snapshotDir>/cubebox/<templateID>/<specDir>/
├── config.json         # VMM VM 配置（CPU/memory/kernel/disk/pmem/vsock）
├── state.json          # VMM 运行状态（vCPU/device/transport/interrupt controller）
├── catalog.json        # SnapshotCatalogEntry（rootfs/memory vol name + kind）
└── [可选 metadata.json] # SnapshotInfo（CPU/memory/kernel version/disk fs+size/pmem/container id）

3.2 CubeCoW 对象

对象 kind CubeCoW 名 内容
rootfs snapshot snapshot <templateID> FICLONE clone 自 build rootfs（OCI 镜像可写层）
memory volume volume <templateID>_memory（或类似） VMM full snapshot 写入的完整 guest RAM

rootfs 是 snapshot，不是 volume——因为它是从 build rootfs FICLONE clone 来的。后续 sandbox clone 从这个 snapshot 再 FICLONE。memory 是 volume（空 volume，VMM 写入 full content）。

3.3 SnapshotCatalogEntry

// Cubelet/storage/snapshot_catalog.go:30
type SnapshotCatalogEntry struct {
    SnapshotID      string `json:"snapshot_id"`        // template id
    InstanceType    string `json:"instance_type"`       // "cubebox"
    SpecDir         string `json:"spec_dir"`            // "2C4G"
    SnapshotPath    string `json:"snapshot_path"`       // VMM snapshot 目录
    MetaDir         string `json:"meta_dir"`            // metadata 目录
    RootfsVol       string `json:"rootfs_vol"`          // CubeCoW rootfs 对象名
    RootfsKind      string `json:"rootfs_kind"`         // "snapshot"（template）
    MemoryVol       string `json:"memory_vol"`          // CubeCoW memory 对象名
    MemoryKind      string `json:"memory_kind"`         // "volume"（template）
    BuildRootfsVol  string `json:"build_rootfs_vol"`   // 构建 rootfs 名（commit 后保留）
    RootfsSizeBytes uint64 `json:"rootfs_size_bytes"`  // rootfs 大小
    Kind            string `json:"kind"`                // "template" vs "runtime_snapshot"
    CreatedAt       string `json:"created_at"`          // 创建时间
}

4. 从 Template 创建 Sandbox（create-from-template）

4.1 Catalog 查找 + CubeCoW clone

// Cubelet/storage/local.go
// 1. 从 annotation 取 template id + spec dir → 查 catalog → 拿 rootfs_vol/memory_vol
entry, err := storage.GetLocalSnapshot(ctx, templateID)
// 2. CubeCoW rootfs clone（FICLONE from template rootfs snapshot）
CreateSandboxRootfsFromTemplate(ctx, sandboxID, templateID, gen, desiredSizeBytes)
//   → manager.CreateSnapshot(templateRootfsVol, sandboxRootfsVol)
//   → FICLONE O(1) clone（共享 extent，写入时 CoW）
// 3. Memory volume 从 template memory volume restore
//   → memory_vol_url = "file://<devpath>"（指向 CubeCoW memory 对象的 dev path）

4.2 restore 流程

CubeShim start_vm → 检测 snapshot mode → restore_vm(RestoreConfig)
  source_url = snapshot_path（config.json + state.json）
  memory_vol_url = file://<CubeCoW memory dev path>
  disks = 当前节点 disk 替换
  → CubeHypervisor vm_restore()
  → MemoryManager fast/slow restore（从 memory volume 读 guest RAM）
  → Vm::restore()（vCPU/device/interrupt controller state 从 state.json 恢复）
  → Vm::resume()

create-from-template 不重新 boot VM——它直接 restore 从 template snapshot 恢复的 guest memory + device state。VM 启动到可用状态的时间 = restore 时间（CubeSandbox 实测 c50 p99 ~536ms），不是冷启动时间。

5. 配置空间

5.1 Template 构建时的可配项

配置 来源 说明
OCI 镜像 RunCubeSandboxRequest.Containers[].Image 决定 rootfs 内容
资源规格 cube.vmmres annotation（CPU/memory） 决定 specDir + memory volume 大小
Guest kernel cube.vm.kernel.path annotation 决定 VMM 启动用的 kernel
Disk 配置 cube.disk annotation（mount list） 决定 virtio-block 设备
pmem 配置 cube.pmem annotation 决定 virtio-pmem 设备
存储介质 storage medium annotation 决定 rootfs 存储后端（CubeCoW/default）
DNS container spec 写入 guest /etc/resolv.conf
网络类型 RunCubeSandboxRequest.NetworkType tap/ptp
Snapshot 目录 AppSnapshotRequest.SnapshotDir template snapshot 存储位置

5.2 Template clone 时的可配项

配置 来源 能否覆盖 template？
rootfs CubeCoW clone from template 否（FICLONE 共享 extent，写入时 CoW 分配新 block）
memory CubeCoW restore from template memory volume 否（full restore template 时的 guest RAM）
VM 配置 config.json 否（vCPU 数/memory 大小固定）
disk 后端 RestoreConfig.disks 是（按 id 替换 disk path）
net 后端 RestoreConfig.net 是（按 id 替换 TAP name）
fs allowed_dirs RestoreConfig.fs 是（按 id 替换 shared_dir/allowed_dirs）
网络/CubeVS network-agent 当前状态 是（重新 EnsureNetwork）

Template 的"不可变"边界：rootfs（经 FICLONE CoW）、memory（full restore）、VM 配置（vCPU/memory 固定）从 template 继承不可改；disk/net/fs 后端可替换为当前节点的资源。后续运行期可通过 VmSetFs（allowed_dirs）或 UpdateContainer（资源）做窄口径更新。

5.3 配置空间总结

6. 能力边界与陷阱

问题 结论
Template 是否包含 host 网络资源 否（只存 tap_if_name，restore 时 network-agent 重建 TAP + CubeVS）
同一 template id 不同资源规格是否可共存 是（specDir = {CPU}C{Memory}M 隔离）
Template rootfs 能否修改 不能（snapshot kind = immutable）；clone 后的 sandbox rootfs 可写（CoW 分配新 block）
Template memory 是否是增量 否（AppSnapshot 固定 full）
Template 构建是否需要网络 需要临时 cubebox 的完整 workflow create（含 network/cgroup/storage）
构建失败是否自动清理 是（cleanupSnapshotObjects + os.RemoveAll(tmp) + Destroy）
Template 是否区分 ARM64/x86_64 Template snapshot 不区分（控制面无 arch 分支）；但 VMM snapshot state 含架构特定状态（GIC vs IOAPIC）——template 不能跨架构 restore
