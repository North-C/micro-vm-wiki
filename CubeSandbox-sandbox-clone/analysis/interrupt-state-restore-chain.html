CubeSandbox 中断状态恢复链路（snapshot → restore → route re-enable）

本文承接 CubeSandbox 深入路线，沿一条具体链路做函数级分析：

MsixConfig snapshot → VirtioPciDevice restore → GIC/IOAPIC route re-enable

研究目标：说清 CubeSandbox（Cloud Hypervisor 派生 VMM）在 snapshot/restore 时，PCI 设备的 MSI-X 中断状态怎么存、怎么恢复，以及 ARM64 GIC/ITS 与 x86 IOAPIC 的路由在 restore 哪一步重新使能、为什么这个顺序是硬约束。

源码基线：当前仓库工作树，VMM 在 hypervisor/ 子目录。

相关横向专题：中断与事件通知跨项目专题分析。

相关项目级链路：Virtio 中断注入函数级链路、VMM snapshot restore state chain、VMM device restore chain。

1. 整体顺序：Vm::restore 的分层

CubeSandbox 的中断恢复不是单点，而是嵌在 Vm::restore() 的分层恢复里。先看全局顺序（hypervisor/vmm/src/vm.rs:2772-2907）：

阶段 动作 锚点
① 基础设施 状态检查；x86_64 恢复 KVM 时钟 vm.rs:2776-2799
② metadata device_manager.restore() 仅恢复 metadata，不建设备 vm.rs:2801-2815
③ vCPU cpu_manager.restore() 恢复 vCPU 状态（含 saved_vcpu_states） vm.rs:2817-2831
④ controller（aarch64） restore_vgic_and_enable_interrupt() vm.rs:2833-2841
⑤ devices device_manager.restore_devices() 建设备 + 逐个 restore（含 MSI-X） vm.rs:2843-2857
⑥ 启动 cpu_manager.start_restored_vcpus() vm.rs:2859-2871
⑦ 外设 setup_signal_handler() + setup_tty() vm.rs:2873-2887

关键时序约束：

  • ARM64：GIC 必须在设备 restore 之前完成（阶段 ④ → ⑤）。设备 MSI-X restore（阶段 ⑤ 内）依赖 controller 路由已就绪。
  • MSI-X：设备 restore 内部，MSI-X 最先恢复，确保设备配置恢复前中断路由已重建。

2. MsixConfig snapshot：存什么、不存什么

MsixConfig 是 PCI 设备的 MSI-X 运行态，定义在 hypervisor/pci/src/msix.rs:63-77：

运行态字段 含义 是否序列化
table_entries: Vec<MsixTableEntry> MSI-X 表项（地址、数据、掩码） ✓
pba_entries: Vec<u64> Pending Bit Array ✓
masked: bool 函数级掩码 ✓
enabled: bool MSI-X 使能状态 ✓
devid: u32 设备 ID ✗（restore 时从设备重建）
interrupt_source_group 中断源组（含 irqfd/route） ✗（restore 时从设备重建）

序列化结构 MsixConfigState 只含前四项（msix.rs:63-68）。

机制结论：snapshot 只存"纯数据状态"（表项、PBA、mask、enabled），不存路由资源（devid、interrupt_source_group）。后者在 restore 时由设备重新构造——这是为什么 restore 必须经过"重建路由"而非"照搬 fd"。

  • snapshot 入口：MsixConfig::snapshot() → state()（msix.rs:103）。
  • snapshot 调用方：VirtioPciDevice::snapshot() 内 msix_config.lock().unwrap().snapshot()。

3. VirtioPciDevice restore：MSI-X 最先恢复

VirtioPciDevice 在 hypervisor/virtio-devices/src/transport/pci_device.rs:315 持有 PCI 配置、common config、msix_config: Option<Arc<Mutex<MsixConfig>>>、queues、interrupt_source_group 等。

3.1 snapshot 保存的子状态

VirtioPciDevice::snapshot()（pci_device.rs:1167）依次保存：

  1. PCI 配置空间 configuration.snapshot()；
  2. virtio 公共配置 common_config.snapshot()；
  3. MSI-X 配置（若存在）msix_config.lock().unwrap().snapshot()。

3.2 restore 顺序（MSI-X 优先）

VirtioPciDevice::restore()（pci_device.rs:1184）按固定顺序恢复：

顺序 恢复对象 作用
1 msix_config.restore() 先重建中断路由（见 §4）
2 common_config.restore() virtio 公共配置
3 configuration.restore() PCI 配置空间

机制结论：MSI-X 最先恢复，确保设备状态恢复前中断路由已重建。这个顺序是刻意的——若先恢复设备配置再建路由，设备一旦开始产生完成中断会找不到路由。

4. MsixConfig restore → route re-enable

MsixConfig::restore() → set_state()（msix.rs:112-146）分两步：

步骤一：恢复纯数据状态

table_entries/pba_entries/masked/enabled 直接从 MsixConfigState 克隆回来。

步骤二：若已使能且未掩码，重建硬件路由

// MsixConfig::set_state 伪代码
if self.enabled && !self.masked {
    for (idx, table_entry) in self.table_entries.iter().enumerate() {
        if !table_entry.masked() {
            let config = MsiIrqSourceConfig { /* high_addr, low_addr, data, devid */ };
            self.interrupt_source_group.update(idx, MsiIrq(config), self.masked)?;  // 重建 route
            self.interrupt_source_group.enable()?;                                    // 重注册 irqfd
        }
    }
}
动作 作用 落点
update(idx, MsiIrq(config), masked) 把 MSI 地址/数据/devid 写成 KVM route InterruptSourceGroup（vm-device/src/interrupt/mod.rs:118-156）
enable() 重新注册 irqfd（eventfd ↔ GSI） 同上
KVM route MsiIrq → kvm_irq_routing_entry（ARM64 走 MSI_DEVID 扩展） hypervisor/src/kvm/mod.rs:507-542（make_routing_entry）
irqfd eventfd 注册到 GSI hypervisor/src/kvm/mod.rs:423-427（register_irqfd）

机制结论：

  1. route 重建只在 enabled && !masked 时发生——避免对仍掩码的 vector 重复注册。
  2. 每个 unmasked vector 各做一次 update + enable，恢复 snapshot 前的完整路由拓扑。
  3. 这里没有"照搬 fd"，而是用 snapshot 里的地址/数据/devid 重新构造 KVM route 与 irqfd。

5. ARM64 GIC/ITS restore：VM 级硬约束

CubeSandbox 在 ARM64 下不靠 DeviceManager 顺带 restore GIC，而是在 Vm::restore 里走专门的 restore_vgic_and_enable_interrupt()（vm.rs:2288-2396）。这是它与 Cloud Hypervisor 的关键差异。

完整步骤：

步骤 动作 锚点
1 cpu_manager.get_saved_states() 取恢复后的 vCPU 状态 vm.rs:2288-2396
2 create_vgic(&vm, Gic::create_default_config(vcpu_count))（GIC 在 device_manager restore 时不会创建，必须显式建） —
3 cpu_manager.init_pmu(AARCH64_PMU_IRQ + 16) —
4 set_gicr_typers(&saved_vcpu_states)（从 vCPU 状态恢复 GICR_TYPER） —
5 要求存在 GIC_V3_ITS_SNAPSHOT_ID → restore(gicv3_its_snapshot)；缺则 Err("Missing GicV3Its snapshot") —
6 interrupt_controller.enable()（激活 GIC 路由） —

硬前提：缺少 GicV3Its snapshot 直接报错返回——GIC/ITS snapshot 不是"最好有"，而是 restore 成立的硬前提。

snapshot 对侧

add_vgic_snapshot_section()（vm.rs:2256-2284）在 snapshot 时：先用 saved_vcpu_states 调 set_gicr_typers()，再把 interrupt controller 的 snapshot 加入 VM snapshot。

机制结论：ARM64 下 controller restore（阶段 ④）必须在 device restore（阶段 ⑤）之前完成。设备 MSI-X enable() 注册的 irqfd，最终要靠 GIC/ITS 路由才能注入 guest——若 GIC 未恢复，设备路由即使重建也无法送达。

6. x86_64 IOAPIC restore：随设备 restore

x86_64 下没有 VM 级 GIC 编排，IOAPIC 作为设备在 device_manager.restore_devices() 阶段恢复。

Ioapic 定义在 hypervisor/devices/src/ioapic.rs:128-145：

字段 含义
id_reg / reg_sel 寄存器选择
reg_entries: [RedirectionTableEntry; NUM_IOAPIC_PINS] 重定向表（vector/delivery/trigger/mask）
used_entries: [bool; NUM_IOAPIC_PINS] pin 使用情况
apic_address APIC 基地址
interrupt_source_group 中断源组（不序列化）

IoapicState（ioapic.rs:139-145）序列化前五类纯数据。Ioapic::restore() → set_state()（ioapic.rs:299-314）：

  1. 恢复 id_reg/reg_sel/reg_entries/used_entries/apic_address；
  2. 对每个 used_entries[irq] == true 的 pin 调 update_entry(irq)，按 reg_entries[irq] 配置更新 interrupt_source_group（重建 delivery_mode/vector/trigger/mask 路由）。

机制结论：x86_64 IOAPIC 的 route 重建嵌在设备自身 restore 里（update_entry），不像 ARM64 那样需要 VM 级 controller 编排——因为 IOAPIC 本身就是 MMIO bus 上的设备。

7. ARM64 与 x86_64 差异

维度 ARM64 (aarch64) x86_64
中断控制器 GICv3 + ITS（显式创建） IOAPIC + PIC（设备树中）
创建时机 restore_vgic_and_enable_interrupt() 显式 DeviceManager::create_devices() 时
restore 时机 阶段 ④（设备 restore 之前） 阶段 ⑤（设备 restore 期间）
snapshot 要求 必须存在（缺报错） 可选（设备存在时恢复）
PMU 显式 init_pmu() 无
GICR_TYPER 从 saved_vcpu_states 设置 无对应
路由使能 interrupt_controller.enable() 每设备 interrupt_source_group.enable()
时钟 无 KVM 时钟恢复 load_clock_from_snapshot()
关键常量 GIC_V3_ITS_SNAPSHOT_ID、AARCH64_PMU_IRQ 无

8. 完整调用链

Vm::restore()                                    [vm.rs:2772]
├─ device_manager.restore()                      (metadata)  [vm.rs:2801]
├─ cpu_manager.restore()                         [vm.rs:2817]
├─ [aarch64] restore_vgic_and_enable_interrupt() [vm.rs:2833]
│  ├─ get_saved_states()
│  ├─ create_vgic()
│  ├─ init_pmu()
│  ├─ set_gicr_typers(&saved_vcpu_states)
│  ├─ gic.restore(gicv3_its_snapshot)   ← 必须 snapshot 存在
│  └─ gic.enable()
├─ device_manager.restore_devices()              [vm.rs:2843]
│  └─ [每个设备] VirtioPciDevice::restore()      [pci_device.rs:1184]
│     ├─ msix_config.restore() → MsixConfig::set_state()  [msix.rs:112]
│     │  ├─ 恢复 table_entries/pba/masked/enabled
│     │  └─ if enabled && !masked:
│     │     ├─ interrupt_source_group.update(idx, MsiIrq)  ← 重建 route
│     │     └─ interrupt_source_group.enable()             ← 重注册 irqfd
│     ├─ common_config.restore()
│     └─ configuration.restore()
├─ cpu_manager.start_restored_vcpus()            [vm.rs:2859]
└─ setup_signal_handler() / setup_tty()          [vm.rs:2873]

路由重建的三个分支点：

  1. ARM64 GIC：restore_vgic_and_enable_interrupt() → gic.restore() → gic.enable()（阶段 ④）。
  2. x86_64 IOAPIC：device_manager.restore_devices() → ioapic.restore() → set_state() → update_entry()（阶段 ⑤ 内）。
  3. PCI MSI-X：VirtioPciDevice::restore() → msix_config.restore() → set_state() → update() + enable()（阶段 ⑤ 内）。

9. 能力边界与判错顺序

能力边界：

  • snapshot 只存纯数据（表项/PBA/mask/enabled），路由资源（devid、interrupt_source_group）在 restore 重建——这是"数据可移植、资源需重建"的设计。
  • ARM64 GIC/ITS restore 是 VM 级硬约束，必须在设备 restore 前完成，且 snapshot 必须存在。
  • x86_64 IOAPIC restore 嵌在设备自身，不需 VM 级编排。

判错顺序（restore 后"设备完成但 guest 无中断"）：

层 先看什么 锚点
MSI-X 数据 snapshot 里 table_entries/enabled/masked 是否正确 msix.rs:63-68
route 重建 set_state 是否进了 enabled && !masked 分支、每个 unmasked vector 是否 update+enable msix.rs:112-146
VirtioPciDevice 顺序 restore 是否 MSI-X 先于 common/configuration pci_device.rs:1184
ARM64 controller restore_vgic_and_enable_interrupt 五步是否全走完；GicV3Its snapshot 是否存在 vm.rs:2288-2396
x86 IOAPIC set_state 后 used_entries 对应 pin 是否 update_entry ioapic.rs:299-314
KVM route/irqfd make_routing_entry/register_irqfd 是否成功 kvm/mod.rs:507-542、:423-427

实用判读：

  • 设备 restore() 成功 ≠ 中断可用。MSI-X set_state 只在 enabled && !masked 时重建路由；若 snapshot 里 enabled=false，restore 后设备不会主动重建路由（需 guest 重新配置 MSI-X）。
  • ARM64 下若 GicV3Its snapshot 缺失，restore 直接报错——这是比"设备 restore 失败"更早的失败点，排查应从 Vm::restore 阶段 ④ 开始，而非设备层。
  • 同样"guest 无中断"，ARM64 优先查 GIC/ITS restore 编排，x86_64 优先查 IOAPIC/MSI-X route。

10. 继续深入点

  • interrupt_source_group.update()/enable() 的具体实现在 hypervisor/devices/src/interrupt/（MsiInterruptSourceGroup）与 aarch64 特定中断管理，当前未完全展开。
  • make_routing_entry() 之后的 KVM_SET_GSI_ROUTING 与 KVM_IRQFD ioctl 调用链，以及 MSI-X vector 到 GSI 的分配逻辑，可单独追踪。
  • 对照 Cloud Hypervisor 的 restore_vgic()（在 DeviceManager 内）与 CubeSandbox 的 VM 级 restore_vgic_and_enable_interrupt()，确认两者在"controller restore 时机"上的差异如何影响迁移兼容性。
