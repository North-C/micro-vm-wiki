    CubeSandbox 性能机制与社区基准测试项分析

    结论摘要

    本文回答的问题是：CubeSandbox 当前源码已经用哪些设计降低 Template 创建、单机密度、Snapshot、Restore、Rollback、Clone、Pause / Resume 的成本，这些成本被消除、共享、延迟或转移到哪里，社区基准报告又实际观察到了什么。

    结论是，CubeSandbox 的共同优化主线不是“把完整 VM 操作做得更快”，而是改变请求路径上的工作量：用预制状态 restore 代替 guest 冷启动，用 MAP_PRIVATE | MAP_NORESERVE 和 XFS reflink 共享基线，把内存与 rootfs 的复制成本延迟到 page fault / CoW 写入；Snapshot 先过滤匿名页，再在 steady state 只覆盖 soft-dirty 页；Rollback 复用 shim/VMM 进程且省掉临时 safety checkpoint；Clone 把一次 capture 共享给 N 次有界并发 restore；Resume 直接恢复持久状态而非重新启动 guest。普通 Pause 是例外：在固定源码基线中仍保存 full snapshot，并未采用报告预测的 soft-dirty Pause。

    社区报告的数据与这些机制的预期方向一致，但没有固定被测二进制版本，且测试是 x86_64、warm-up 后、空载或低 dirty、单批次并发。因而：

    • Community report observation 可说明报告环境中出现了共享、增量写和并行 fan-out 的效果信号。
    • Inference 只能把这些信号映射为当前源码机制的待验证假设，不能证明某个机制的贡献比例。
    • 绝对数值对固定源码基线 5135a40d86c94a85fe2521fd9ed913ac5fd6cfd9 属于 non-comparable；操作定义与 x86_64 机制方向最多 partially comparable；对 ARM64 数值结论为 non-comparable。

    本文没有运行新 benchmark，也不产生新的独立性能报告。

    1.3 指标语义校正

    Local fact：当前 cube-bench 在单个 create 调用周围记录逐请求 latency，并用 successful / elapsed 算 throughput；Python concurrency 脚本主要记录一批操作从发出到全部完成的 wall time。当前脚本只能解释指标实现，不能证明 2026-06 历史执行使用了完全相同版本。证据：runner.go、report.go、stats.go 及 Snapshot/Rollback/Clone 脚本目录。

    • wall / N 是完成该批 N 项的批吞吐间隔，等价于 1 / batch throughput，不是任一请求的 latency，也不表示用户在该时间内收到一个结果。
    • 一批操作的 wall 近似其中最慢任务的完成时间，并包含批内排队与资源竞争；它不提供每请求 p50/p95。
    • Python 表只有 2--5 rounds，按 nearest-rank 统计时 p95 等于 max；这些 p95 不能当作稳定尾延迟估计。
    • Rollback 的 timer 只包围 rollback()；每个 sandbox 的 checkpoint 在 timer 之前创建。因此 81.6 ms 等数字不包含 checkpoint creation，报告正文把它称为“打快照 + 回滚全流程”与脚本边界不一致。
    • Dirty-page restore 丢弃首次 restore，Clone 明确声明文件已在 Page Cache；两者都是 warm-cache 观察。

    2. 统一关键路径与成本模型

    2.1 端到端边界

    外部 create/restore 类请求的成本路径为：CubeAPI/CubeMaster 调度与状态管理 -> Cubelet workflow 的 storage/network/containerd 动作 -> CubeShim 启动 VMM 或恢复 VM -> VMM 映射 guest memory、恢复 device/vCPU/KVM state -> guest vsock ready -> CubeShim 连接 agent 并完成 guest CreateSandbox -> 平台返回。

    Snapshot/Rollback/Pause 则额外跨越 VMM pause、pagemap/soft-dirty 扫描、memory 文件写入、CubeCoW rootfs generation、catalog binding、VM delete/restore 和 agent/monitor 重连。深入链路已有独立文档，本文只在成本边界上引用：

    • Sandbox Ready 生命周期：create 返回前的 VMM、vsock、agent 与 guest ready 边界。
    • Snapshot Create / Commit：full、anonymous-page 与 soft-dirty 的创建和退化顺序。
    • Snapshot Catalog / Restore Binding：logical snapshot 到本地 rootfs/memory/meta 的绑定。
    • VMM Snapshot Restore 状态恢复：memory、device、vCPU 和架构状态恢复。
    • CubeCoW 存储引擎：XFS reflink、对象所有权和恢复边界。
    • Rollback / Runtime Update：Rollback 删除旧 VM 再 restore 新 VM 的真实语义。
    • Network-Agent EnsureNetwork：TAP、CubeVS、port mapping 与资源池边界。

    2.2 可证伪成本模型

    为避免把优化效果误写成单一“瓶颈”，本文使用以下模型解释成本如何变化：

    L_create = Q_control + C_storage_meta + C_network + C_vmm
         + C_state_restore + F_memory + C_device_vcpu + C_agent_ready

L_snapshot = C_pause + C_scan(P_total) + C_range(P_candidate)
           + W(B_written) + C_state_fs + C_resume

M_host(N) = M_shared_baseline + N * (M_fixed + M_pagetable + M_device)
          + sum(R_private_dirty_i) + M_page_cache + M_kernel

T_batch(N, C) = queue/service time across control, CPU, storage metadata,
                memory write/fault, network pool and agent-ready stages
wall/N = 1 / observed batch throughput

    其中 F_memory 是 restore 后按需 fault/cache miss 成本，W(B_written) 是实际写入 memory snapshot 的字节成本。优化的核心因果链是：

    • 预制 snapshot 让 guest boot + application initialization 从 L_create 移到模板构建阶段。
    • reflink 与 private file mapping 把完整复制从 create/restore 移到后续写时 CoW 和缺页。
    • anonymous-page / soft-dirty 过滤把 W(total guest RAM) 降为 W(candidate or dirty bytes)，但保留 scan、state 与同步固定成本。
    • 并发只会降低 T_batch/N；当 CPU、NUMA、存储 metadata、Page Cache、TAP pool 或 agent-ready stage 饱和时，排队会抬高逐请求 latency。

    当前没有分阶段 trace 或本地 profile，故本文不把任何一个剩余项断言为主导瓶颈；相关判断均保留为待验证假设。

    2.3 Linux/KVM 机制基座：优化的是何种对象

    下面四组对象决定了“共享、延迟、增量”分别发生在哪里。它们是 Linux/KVM 通用机制在 CubeSandbox 调用点上的映射，不是 CubeSandbox 自创的内核能力。

    file-backed guest RAM、Page Cache 与 CoW

    Local fact：fast restore 打开 snapshot memory 文件后，以 MAP_PRIVATE | MAP_NORESERVE 建立可读写 VMA；只有 prefault=true 才附加 MAP_POPULATE。new_from_snapshot、create_ram_region

    mmap(snapshot fd, MAP_PRIVATE | MAP_NORESERVE)
  -> 建立 VMA，通常尚未为每个 guest page 建 host PTE
  -> KVM memslot 记录 GPA range -> HVA range
  -> vCPU 首次读 GPA
       -> warm Page Cache: minor fault，建立 host PTE/KVM secondary mapping
       -> cold Page Cache: major fault，先从 storage 读入 cache folio
  -> vCPU 首次写仍共享的 file page
       -> write-protection fault
       -> 分配 anonymous page + 复制旧内容 + 替换 PTE

    MAP_PRIVATE 允许多个 VM 读取同一 page-cache folio，但写入不会回写基线文件；MAP_NORESERVE 只减少 mmap 时的 swap/commit 预留，在 strict overcommit 下可能被忽略，也不保证未来 CoW 分配一定成功。MAP_POPULATE 把一部分 fault、PTE 和 readahead 成本拉回 restore 阶段，因此是 ready latency、首次 workload latency 与密度之间的交换，不是无条件加速。

    Local fact（Linux/KVM 通用机制）：minor fault 只表示无需阻塞读取文件，不代表零成本；仍可能包含 fault handler、页表分配/锁、rmap/mapcount 和 KVM secondary-MMU 建映射。major fault 还引入 filesystem/block I/O。配置的 2 GiB guest RAM 是 GPA 地址空间，不能等同于 2 GiB 独占物理内存；RSS 会计入 resident shared file pages，PSS 才按映射者分摊，anonymous CoW pages 则随每个 workload 写集独立增长。

    KVM memslot：注册地址关系，不是复制内存

    Local fact：create_userspace_mapping() 为每段 guest RAM 分配 slot，把 (slot, guest_phys_addr, memory_size, userspace_addr, readonly, log_dirty) 交给 hypervisor；KVM backend 最终执行 KVM_SET_USER_MEMORY_REGION。create_userspace_mapping、KVM backend

    guest virtual address
  -> guest page table -> GPA/GFN
  -> KVM memslot lookup -> HVA
  -> Linux host page table / GUP -> PFN
  -> KVM secondary MMU (EPT on x86_64) -> host physical page

    memslot 建立本身不会把整个 memory file 读入 RAM。VMA 变化、reclaim、NUMA migration 或 userspace unmap 需要 MMU notifier 使 KVM 缓存的 secondary mappings 失效；因此“大文件只做一个 mmap”仍存在每 VM 的 memslot、页表、KVM MMU 与 vCPU/device 固定成本。

    XFS reflink：共享 extent，不是共享文件语义

    Local fact：CubeCoW 先 create_new 目标文件，再执行 ioctl(dst_fd, FICLONE, src_fd)；成功后把 snapshot 投影到对象索引，并 best-effort 同步父目录。create_snapshot、ficlone

    XFS 让源与目标的逻辑 extent 指向相同物理 blocks，并用 refcount metadata 记录共享。目标首次写共享 extent 时，filesystem 才分配 CoW staging blocks、写入新数据、完成 extent swap/refcount 更新。因而 create/snapshot 的数据复制被改成 metadata 操作，但随机小写可能带来 extent unshare、metadata 更新、fragmentation 和 write amplification；删除对象也只有引用归零后才回收物理 blocks。

    soft-dirty：PTE tracking window，不是字节级 dirty log

    Local fact（Linux 通用机制）：向 /proc/self/clear_refs 写 4 会清 soft-dirty 状态并写保护相关 PTE；后续 CPU 写通过 write fault 重新设置 pagemap bit 55。clear 操作需要进程范围的 page-table walk、MMU notifier 与 TLB flush，后续第一次写还会承担重新置位的 fault 成本。

    Unconfirmed：当前源码注释把 device DMA 也概括为会设置 soft-dirty，但 Linux clear_refs 对可能 DMA-pinned 的 PTE 有跳过路径；本文没有证明所有设备 DMA 写都被当前 soft-dirty 窗口捕获。Snapshot 正确性验证必须包含 DMA/virtio 写入，不能只测 vCPU store。

    Local fact（带边界）：KPF_ANON 只说明 PFN 当前属于 anonymous 类页面，不足以证明它一定由 guest 写入产生；host/VMM 对 private mapping 的写也可能使页面匿名化。当前过滤将其作为“可能偏离 file base”的保守候选，再与 soft-dirty 取交集，而不是把它解释为 guest-write provenance。

    4. 单机密度与内存成本

    4.1 已实现优化设计与实现路径

    未经优化时，N 个 2 GiB VM 可能为每实例预提交规格上限并复制相同基线。CubeSandbox 的目标是让 host 物理成本随实际 working set 与 private writes 增长，而不是随 guest address-space 上限线性预占。

    Local fact：snapshot memory 使用 MAP_PRIVATE | MAP_NORESERVE，默认不 MAP_POPULATE；rootfs 与派生 memory 对象使用 reflink/CoW。create_userspace_mapping() 只有配置 mergeable 时才执行 MADV_MERGEABLE，所以不能把默认密度归功于 KSM。create_userspace_mapping

    密度优化发生在物理页和 extent 的拥有关系上，而不是缩小 guest 可见地址空间：

    flowchart LR MF[同一 snapshot memory file] --> PC[Host Page Cache clean folios] PC --> V1[VM 1 private VMA] PC --> V2[VM 2 private VMA] PC --> VN[VM N private VMA] V1 -->|首次写| A1[VM 1 anonymous CoW pages] V2 -->|首次写| A2[VM 2 anonymous CoW pages] RF[同一 rootfs extents] --> R1[VM 1 reflink view] RF --> R2[VM 2 reflink view] R1 -->|首次写| U1[unshared XFS extents] R2 -->|首次写| U2[unshared XFS extents]

    图中证据（Local fact）：snapshot RAM 的 private mapping 由 create_ram_region 建立，rootfs extent sharing 由 CubeCoW create_snapshot 与 ficlone 建立；图中的 anonymous page 与 unshared extent 是两条机制首次写入后的分叉。

    因此每增加一个 idle VM，不必立即增加一个 guest-size 的独占内存副本，但必然增加 VMM/shim heap、host/guest page tables、KVM MMU metadata、vCPU/device/virtio queue、TAP、fd 和控制面对象。随着各 VM 触碰和写入不同页面，匿名页与 unshared extents 向 N * working-set 方向增长；内存压力回收共享 file pages 后，下一次读取还会从 minor fault 退化为 major fault。

    NUMA 也决定“共享”是否便宜。create_ram_region() 在配置 host NUMA node 时执行 mbind(MPOL_BIND, MPOL_MF_STRICT | MPOL_MF_MOVE)；private CoW 页通常按 faulting task 与 VMA policy 分配，而 file page-cache page 的位置受最初填充者和 filesystem read 路径影响。NUMA binding 因而同一基线被跨 socket vCPU 访问时可能共享物理页却支付 remote-NUMA latency；把所有 VM 固定到单节点又会先耗尽该节点容量。

    4.2 被消除、共享和转移的成本

    • 消除：按 2 GiB 规格为每个空载 VM 预提交等量 host RAM；为每实例复制相同 rootfs/memory 数据块。
    • 共享：干净 snapshot pages、Page Cache 和 reflink extents。
    • 延迟/转移：首次访问产生 page fault；写入产生 anonymous/private page 与 extent unshare；高密度还支付 VMM/shim heap、页表、KVM/kernel metadata、virtio queue、TAP 和 fd 等固定成本。
    • 前置条件：小 working set、较低 dirty/unshare、Page Cache 可容纳共享页、host 没有强内存压力；XFS 支持 reflink。

    6. Snapshot 与 Dirty Page 规模

    6.1 已实现优化设计与实现路径

    未经优化时写入量是 guest RAM 上限；当前设计把写入量降为 anonymous candidate，并在 tracker 已 armed 的 steady state 进一步降为本窗口 dirty subset。send_soft_dirty_memory() 要求 delta 覆盖到已经存在的 base 文件；base 缺失会报错，clear_refs re-arm 失败则 disarm，下一次退回完整 anonymous-page 路径。这些回退保护“生成的文件可恢复”不变量，而不是为追求小写入量生成不完整 artifact。

    状态机必须按 snapshot 周期理解：

    Unarmed
  -> 写入全部 anon candidate 到既有完整 base
  -> clear_refs(4) 成功: Armed
  -> clear_refs(4) 失败: 保持 Unarmed

Armed
  -> 读取 anon bitmap 与 pagemap bit 55
  -> must_save = anon AND soft_dirty
  -> 连续 page 合并为 MemoryRange
  -> 按 GPA->file offset 覆盖既有完整 image
  -> clear_refs(4) 成功: 继续 Armed
  -> clear_refs(4) 失败: 转为 Unarmed，下轮保守写全 anon

    anonymous 候选来自 /proc/self/pagemap 的 PFN 与 /proc/kpageflags 的 KPF_ANON；读取 PFN 需要相应权限，present page 的 PFN 为 0 时当前实现报 capability error；swapped page 被保守纳入。get_anon_pages soft-dirty scan 读取 pagemap bit 55，也把 swapped page 保守视为 dirty。get_soft_dirty_pages

    Local fact（带边界）：bitmap 交集之后，连续页被合并为范围，再通过 GPA 到 snapshot file offset 的表做原位覆盖；它减少写入 bytes 和碎片化调用，但 scan 仍触达整个声明范围。filter_memory_ranges_by_anon_and_soft_dirty 当前 swapped page 会被保存，但统计结构未同步增加相应 swapped 计数，因而日志统计不能作为 swap 覆盖完整性的唯一证据。

    Unconfirmed durability boundary：已检查的 memory snapshot overlay 路径可见 write_at/文件覆盖与 metadata/state 写入，但未看到明确的 fsync、fdatasync、临时文件原子 rename 或两阶段 publication。CubeCoW reflink 路径虽调用目录 fsync，错误也被忽略。本文因此只能断言“调用返回前完成用户态写入”，不能断言掉电后的 crash durability 或 memory/state/rootfs 三者原子一致；故障注入必须覆盖写一半、state 已发布但 memory 未持久化等窗口。

    6.2 被消除、共享和转移的成本

    • W(total RAM) 变为 W(anonymous candidate) 或 W(anonymous intersect soft-dirty)。
    • scan cost 仍与页表/候选范围有关；device/vCPU state 和 pause/resume 是近似固定项。
    • dirty 写越多，snapshot write、CoW extent 与缓存压力越大；“增量”节省当次写 I/O，但 base 生命周期、绑定与 crash consistency 成为额外控制成本。
    • 生效条件是正确建立首次基线和 tracking window；环境表写有 soft-dirty 不等于每种操作都走 soft-dirty。

    Local fact（仅当前脚本）：固定基线的 bench_snapshot_dirty.py 没有在 3 个 snapshot 正式样本前额外丢弃一次 snapshot；它只在每个正式 round 内丢弃该 snapshot 的第一次 restore，再计时暖缓存 restore。因此报告的“每个数据点先预热”不能用于断言 snapshot 表也排除了首个 snapshot 样本，历史脚本又未绑定到具体 commit。

    Inference：观察支持 L_snapshot = fixed scan/state cost + W(B_written) 中写入字节是随 dirty 增长的重要项；它不证明唯一成本是磁盘带宽，也不证明 clear_refs、base binding 或故障回退在历史运行中正确执行。3 rounds 下 p95 就是 max。

    6.4 局限与进一步优化

    报告没有 raw log、write bandwidth、pagemap scan time、fsync、dirty-page spatial distribution 或 base chain 深度，不能从斜率外推其他存储和 workload。

    Engineering judgment：优化前先把 total_pages / anonymous_pages / soft_dirty_pages / written_bytes / scan_us / write_us / sync_us 关联到 snapshot id 和 base id。可评估 range coalescing 或异步 I/O，但必须保持可直接 restore artifact、base ownership 和 crash consistency；任一 restore checksum/state validation 失败或固定成本增加抵消低-dirty 收益时回滚。

    7. 基于 Snapshot 创建沙箱

    7.1 已实现优化设计与实现路径

    未经优化时恢复需要把整个 memory image 读入匿名内存再构建 VM。fast restore 直接把 memory file 私有映射为 guest RAM，然后恢复 device/vCPU/KVM state，并在实际访问时 fault；rootfs 由 reflink 派生。平台仍需重建实例特有网络、vsock 和 guest agent 会话。

    相关 Local facts 与 Template create 相同：new_from_snapshot() 选择 memory-file fast path，create_ram_region() 使用 private/noreserve mapping，restore_vm() 注入当前实例设备 backend。详细状态边界见 VMM Snapshot Restore 和 Snapshot Catalog / Restore Binding。

    restore 的 VM 内部顺序如下；“API ready”发生在 agent 重连之后，但 lazy memory fault 可以发生在 ready 之前或之后，取决于 restore/device/agent 和 workload 实际触碰的页：

    flowchart TD A[读取 snapshot config/state] --> B[创建空 hypervisor VM] B --> C[恢复 MemoryManagerSnapshotData] C --> D{fast restore supported?} D -->|yes| E[open memory file read-only] E --> F[mmap MAP_PRIVATE/NORESERVE] D -->|no| G[allocate normal regions] G --> H[fill_saved_regions eager copy] F --> I[register GPA-HVA KVM memslots] H --> I I --> J[重建实例 fs/net/disk/pmem/vsock backend] J --> K[按 device tree 顺序 restore] K --> L[restore vCPU/arch state and resume] L --> M[connect agent, reset guest, rebind clients/monitors] M --> N[platform ready] N --> O[后续 workload 继续产生 file faults/CoW]

    图中证据（Local fact）：fast path 的显式适用条件是没有 shared-memory zone 且没有 virtio-mem hotplug；不满足时使用 fill_saved_regions()，不能把 private mapping 的成本模型套到 fallback。new_from_snapshot、support_fast_restore_check snapshot 中的 MemoryManagerSnapshotData 还原 memory ranges、guest RAM mapping、slot 序号和 hotplug state；这些 metadata 必须与 config 和 device topology 匹配，否则“文件可读”仍不足以恢复 VM。

    Page Cache 热度决定的是 fault 成本而非 restore 正确性。warm cache 可能让报告中的 API ready 只承担 minor faults；cold cache、reclaim 或跨 NUMA 访问会让相同代码路径出现 storage read 和 remote memory。prefault/readahead 能减少 ready 后首个 workload 的 fault，却会提高 restore I/O、RSS 和并发时的 cache/bandwidth 压力，所以必须用“API ready + 首次真实请求”的联合 SLO 选择策略。

    7.2 被消除、共享和转移的成本

    • 消除：restore 请求中的全 memory memcpy、guest cold boot 与应用初始化。
    • 共享：snapshot clean pages、warm Page Cache、rootfs reflink extents。
    • 延迟/转移：snapshot 越大并不必然增加 API 返回前的 copied bytes，但之后访问会产生 page fault/cache miss；首次写产生 memory/rootfs CoW。
    • 前置条件：fast-restore 支持、snapshot metadata/device topology 兼容、本地 artifact 完整、实例网络/backend 可重建。warm Page Cache 是低 fault 成本条件，不是语义正确性的条件。

    7.3 社区报告如何观察它

    Community report observation：Dirty Page 分档中的 create avg 为 60.7--68.4 ms，max 为 66.1--84.6 ms；脚本丢弃第一次 restore，所以这是 warm restore。独立 create-from-snapshot 批测试中 c1/c10/c20/c50 的 wall avg 为 63.9/89.9/118.9/180.3 ms，wall/N 为 63.9/9.0/5.9/3.6 ms。

    Inference：API 返回前耗时对 artifact captured bytes 不敏感，与 file mapping + lazy fault 方向一致；它不能证明“恢复成本与 snapshot 大小无关”。总工作集变大时，成本只是转移到返回后的 fault、cache miss、NUMA remote access 和首次写 CoW。独立测试的 3-round p95 等于 max，3.6 ms 仍只是 batch throughput interval。

    7.4 局限与进一步优化

    报告未测 cold cache、memory pressure、首次 guest workload latency、major/minor faults、NUMA placement 或 restore 后 state/data correctness。

    Engineering judgment：对比 lazy、targeted readahead 和 prefault 必须同时测 API ready latency、ready 后首个真实 workload latency、fault count、RSS/PSS 与密度。prefault 可能降低首访问 latency，却把 I/O 和 resident memory 拉回请求路径。若 ready latency、内存密度或无访问 workload 明显回退，则恢复 lazy 默认；只对有可预测 working set 的模板选择性启用预取。

    8. Rollback

    8.1 已实现优化设计与实现路径

    未经优化时 Rollback 可以重建整个 shim/VMM 进程，或先为当前状态制作 safety checkpoint 再尝试 restore。当前设计选择保留控制进程、替换内部 VM，并明确省掉临时 checkpoint。

    Local fact：Cubelet rollback 在生命周期锁内要求 CubeCoW backend，经本地 catalog 解析目标，并用 RollbackDeriveNewGen() 从目标 rootfs 派生新 generation。Rollback

    Local fact：rollback_vm() 断开 agent/monitor，发送 VmDelete 删除当前 VM 对象但保留 VMM 进程，清空 stale shutdown event，再用调用方的 RestoreConfig 恢复。rollback_vm 源码明确不先做 temporary checkpoint；目标 restore 失败时 VM 保持 deleted。恢复后 resume_vm_with_config() 重连 agent、reset guest、重绑 container client 并重启 monitor。resume_vm_with_config

    sequenceDiagram participant Master as CubeMaster participant Let as Cubelet participant Cow as CubeCoW participant Ctrd as containerd/shim update participant Shim as CubeShim participant VMM as existing VMM process participant Agent as Guest Agent Master->>Let: Rollback(snapshot_id, new_gen) Let->>Let: acquire per-sandbox lifecycle lock Let->>Let: resolve catalog/ownership/current rootfs Let->>Cow: derive new rootfs generation from target Cow-->>Let: new dev path Let->>Let: build RestoreConfig(memory + substituted disks) Let->>Ctrd: update action=rollback + restore_config Ctrd->>Shim: rollback_vm Shim->>Agent: disconnect and abort old monitors Shim->>VMM: VmDelete Shim->>VMM: drain stale VmShutdown events Shim->>VMM: VmResumeFromSnapshot(target) Shim->>Agent: reconnect/reset/rebind/restart monitors Shim-->>Let: success Let->>Let: persist new generation/base binding Let->>Cow: delete old rootfs best-effort Let-->>Master: rollback result

    图中证据（Local fact）：Cubelet 在派生新 generation 后设置 deferred cleanup；只有 shim restore 成功才取消该 cleanup。它还在 shim 操作期间设置 RollingBack，避免 DeadGC 或 task status 的短暂 Unknown 把 sandbox 标成 terminated；成功后清理旧终止标记并持久化新 rootfs/base binding。RollbackSandbox

    这条顺序维持两个不变量：进入 shim 前目标 rootfs/memory/state 已经解析为具体对象；对外宣告成功前 agent/container clients 与 monitors 已绑定新 VM。它没有维持“失败后仍可继续使用旧 VM”不变量：VmDelete 之后若 target restore 或 agent reconnect 失败，旧 VM object 已丢失。VMM 进程复用节省 process/bootstrap 成本，但不是事务回滚。

    8.2 被消除、共享和转移的成本

    • 消除：shim/VMM process recreate、guest cold boot、完整 rootfs copy、临时 safety checkpoint 的 memory I/O。
    • 共享/复用：现有控制进程、本地 catalog、CubeCoW target rootfs 与 snapshot restore path。
    • 保留：VM delete、event drain、memory/device restore、agent/container reconnect 和 monitor rebuild。
    • 转移的风险：省掉 safety checkpoint 缩短成功路径，但 restore 失败没有自动恢复到调用前状态。
    • 前置条件：sandbox 处于允许 rollback 的状态、无阻塞 exec、snapshot 属于该 sandbox 且本节点 catalog/artifact 完整、CubeCoW backend 可派生 generation。

    8.3 社区报告如何观察它

    Community report observation：c1/c5/c10 的 rollback-only batch wall avg 为 81.6/189.6/266.1 ms，wall/N 为 81.6/37.9/26.6 ms；每个 sandbox 使用自己的预建 checkpoint。

    Local fact（仅当前脚本）：checkpoint creation 在 timer 之前。因此报告正文把约 82 ms 称为“create_snapshot + rollback”不符合脚本计时边界。上述数值只能解释 rollback 调用，不包含创建 checkpoint、sandbox setup 和 cleanup。由于报告未固定脚本 commit，该事实用于校正当前可见方法边界，不能证明历史脚本完全相同。5 rounds 的 p95 等于 max。

    Inference：并发 batch throughput 改善与独立 sandbox restore 可并行一致，但不能说明完整 checkpoint-to-rollback workflow，也没有证明回滚后内存、文件系统、agent 和 device state 正确。

    8.4 局限与进一步优化

    Engineering judgment：Rollback 的第一优先级不是继续省步骤，而是为 rootfs derive / VmDelete / state restore / agent reconnect / ready 建阶段 trace，并注入 restore failure 验证 deleted-state、catalog/generation cleanup 和可恢复性。若要重新引入可选 safety checkpoint，应明确性能与恢复保证的产品选择；若优化路径的 restore failure rate、orphan generation 或不可恢复状态超过零容忍阈值，回滚到更保守的 checkpoint/recreate 路径。

    9. Clone

    9.1 已实现优化设计与实现路径

    未经优化时 N 个 clone 可能重复 capture 源状态 N 次并逐个完整复制。CubeSandbox Node SDK 的 Clone 不是“fork 运行进程”的底层原语，而是一次 createSnapshot()，再从同一 snapshot 有界并发执行 N 次 Sandbox.create()。

    Local fact：clone() 创建一次临时 snapshot，以 min(n, concurrency) 个 worker drain 全部 create；失败时清理已创建 siblings，最终删除临时 snapshot。clone

    展开后的 clone() 运行流不是单个 API 原语，而是两阶段编排：

    sequenceDiagram participant Caller as Caller participant SDK as Node SDK clone participant Snap as Snapshot API/path participant Create as Create-from-snapshot path participant Child as Child sandboxes Caller->>SDK: clone(N, concurrency=C) SDK->>Snap: createSnapshot(parent) once Snap-->>SDK: temporary snapshot_id loop min(N,C) bounded workers SDK->>Create: Sandbox.create(template=snapshot_id) Create->>Create: schedule + rootfs reflink + VM restore Create-->>SDK: child or error end alt all create calls succeed SDK-->>Caller: N children sharing CloneCleanup Child->>SDK: release/kill each child SDK->>Snap: delete temporary snapshot after last release else any create fails SDK->>Child: kill every successful sibling, allSettled SDK->>Snap: force idempotent cleanup SDK-->>Caller: throw first error end

    图中证据（Local fact）：CloneCleanup 用 released-id set 保证同一 child 只扣减一次，用 remaining 在最后一个 child release 时删临时 snapshot，并用 cleanupStarted 防止并发重复删除。CloneCleanup snapshot delete 是 best-effort，因此 SDK 清理逻辑防止正常路径泄漏，但不能提供进程崩溃后的 GC 保证。

    每个 worker 发起的都是第 7 节完整 create-from-snapshot：各自经历 CubeAPI/Master 调度、节点 rootfs 派生、network/containerd/shim、VMM mmap/memslot/device/vCPU restore 和 agent ready。只被摊薄的是 parent snapshot capture 与 immutable base；每个 child 的控制对象、KVM/device 状态、页表和 ready handshake 均不能共享。

    内核层共享也有清晰生命周期：所有 child 的 MAP_PRIVATE memory VMA 可以引用同一 snapshot file 的 clean Page Cache，rootfs 文件可以引用相同 XFS extents；child 读冷页仍各自触发 fault 路径，child 写入则各自生成 anonymous page 或 unshared extent。删除临时 snapshot 名称不会立刻回收仍被打开/引用的 file pages 或 extents，但 catalog、文件 fd 与 CubeCoW ownership 必须保持到所有 child 建立自己的有效引用之后。

    9.2 被消除、共享和转移的成本

    • 消除：N 次重复 snapshot capture、N 次完整 memory/rootfs copy、严格串行的 N 次 restore。
    • 共享：同一 immutable snapshot、memory clean pages、rootfs reflink extents 和 Page Cache。
    • 并行：有界 worker fan-out；n=100 时提高 C 减少批次数。
    • 转移：每个 child 后续的 page faults、private writes 和 CoW unshare；共享 artifact 的 fan-out、缓存与生命周期压力。
    • 前置条件：首次 snapshot 成功；所有 child 都能访问 artifact；并发额度不压垮控制面、network/storage/VMM；partial failure cleanup 正确。

    9.3 社区报告如何观察它

    Community report observation：n1/c1 的 wall avg 219.6 ms；固定 n=100 时 c10/c20/c50 为 870.4/638.6/540.9 ms，wall/N 为 8.7/6.4/5.4 ms。报告明确涉及的文件已在 Page Cache；n=100 只有 2 rounds，所以 p95 等于 max。

    Inference：固定 N 时更多 worker 减少批次数，与有界 fan-out 设计一致；warm shared Page Cache 也可能降低 fault/read 成本。但 5.4 ms 不是一个 clone request 的 latency，且 n1/c1 与 n100 档位的固定 snapshot/调度摊销不同，不能直接作单请求加速倍数。报告没有隔离“批次数减少”和“Page Cache 复用更充分”的贡献。

    9.4 局限与进一步优化

    冷 cache、memory pressure、大 dirty source、child 首次 workload、partial failure、artifact cleanup 和 fan-out 上限均未覆盖。

    Engineering judgment：按 source working set、snapshot bytes、fan-out、cache state 和多资源容量设置 clone admission；记录 snapshot-once 固定成本、child request latency、faults、cleanup 成功率及 shared/unshared bytes。若 adaptive concurrency 增加失败/泄漏、child p95 或 Page Cache thrashing，回滚到固定 worker 上限；不要以更低 wall/N 单独作为放宽并发的依据。

    10. Pause / Resume

    10.1 已实现优化设计与实现路径

    Pause 的功能目标是持久化 VM 状态并删除运行 VM，从而在 paused 期间释放运行资源；Resume 直接恢复持久状态，避免 guest cold boot。当前性能设计只优化了 Resume 路径和 paused 生命周期，没有把普通 Pause 的 memory capture 增量化。

    Local fact：SandBox::pause_vm() 断开 agent、创建 per-sandbox snapshot 目录、调用 pause_vm_cube() 并等待 shutdown event。pause_vm pause_vm_cube() 创建没有指定 type 的 SnapshotConfig 并发送 VmPauseToSnapshot。pause_vm_cube SnapshotType::default() 是 Full。SnapshotType VMM vm_pause_to_snapshot() 顺序执行 pause、snapshot、delete。vm_pause_to_snapshot

    Local fact：Resume 发送 VmResumeFromSnapshot，随后重连 agent/container client 与 monitor。它复用 snapshot restore 的 private mapping/lazy fault 设计，而不是重新引导 guest。

    sequenceDiagram participant API as Pause/Resume API participant Shim as CubeShim participant Agent as Guest Agent participant VMM as VMM participant Disk as pause snapshot directory API->>Shim: pause Shim->>Shim: Normal -> Paused; reject active exec Shim->>Agent: disconnect Shim->>Disk: recreate per-sandbox directory Shim->>VMM: VmPauseToSnapshot(default SnapshotConfig) VMM->>VMM: pause vCPUs/devices VMM->>Disk: full memory + VM/device/vCPU state VMM->>VMM: VmDelete VMM-->>Shim: VmShutdown event Shim-->>API: paused API->>Shim: resume Shim->>VMM: VmResumeFromSnapshot(directory) VMM->>Disk: restore state + private memory mapping Shim->>Agent: reconnect + reset guest Shim->>Shim: rebind clients, OOM/VM monitors; Paused -> Normal Shim-->>API: resumed

    图中证据（Local fact）：默认 SnapshotConfig 的 SnapshotType 在此基线为 Full，所以 Pause 会遍历并写出 full memory ranges；runtime Snapshot 的 unarmed/armed soft-dirty state machine 不在这条入口上。pause_vm_cube、vm_pause_to_snapshot Resume 可以使用相同 fast memory mapping，因此“Pause 写得多、Resume 返回快”在机制上并不矛盾：前者承担持久化，后者把一部分读取延迟到 fault。

    Pause 返回还依赖 shutdown event；Resume 返回依赖 agent 重新连接、guest reset、container client 重绑和 monitor 重建，而不只是 VmResumeFromSnapshot ioctl 完成。测试如果只检查 API success 而不执行 guest memory、filesystem、network/device 和 agent operation 校验，只覆盖生命周期控制面，不足以证明恢复正确。

    10.2 被消除、共享和转移的成本

    • Pause 已消除的成本：paused 期间不继续保留 active VM 执行资源；持久化后可删除 VM。
    • Resume 已消除的成本：guest cold boot 与应用初始化；恢复读取可转为 mapping/page fault。
    • Pause 当前未消除的成本：普通路径仍保存 full snapshot，不是 soft-dirty delta。
    • 转移：Resume 后的 page faults/CoW；Pause 的完整 memory write 落到持久存储。
    • 前置条件：per-sandbox snapshot 路径可用，full snapshot 完整，restore metadata 兼容，agent/monitor 可重连。

    10.3 社区报告如何观察它

    Community report observation：Pause c1/c5/c10 batch wall avg 为 558.4/656.9/682.1 ms，wall/N 为 558.4/131.4/68.2 ms；Resume 为 41.8/28.2/35.7 ms，wall/N 为 41.8/5.6/3.6 ms。每档 5 rounds，p95 等于 max。

    Inference：Pause 的较大固定 wall 与 full snapshot 写路径方向一致；并发 wall 增长较小只说明该 warm、空载批次有并行余量，不证明高 dirty/full 2 GiB 写入可同样扩展。Resume 的短 warm batch 与直接 restore/lazy mapping 一致，但不包含 cold cache 和恢复后首个 workload。

    Community report observation：报告预测 future soft-dirty Pause 约 60 ms、降低 80--90%，但没有提供实测。该数字不是当前实现事实，也不是当前 baseline 的性能结果。

    10.4 局限与进一步优化

    Engineering judgment，P1：要把 soft-dirty 接入 Pause，不能只修改 SnapshotType。设计必须拥有持久 full base + delta overlay，定义 first pause、连续 pause、resume 后 tracking re-arm、base 失效、crash consistency、artifact GC 和失败回退。选择该方案是因为 runtime Snapshot 已有 soft-dirty primitive；“每次 full copy”保留为首次/失效 fallback，“只保存裸 delta”因不能独立恢复而拒绝。

    验证必须同时覆盖 pause wall/bytes、resume ready、恢复后 memory/filesystem/device/agent correctness、base/delta ownership、crash injection 和并发 I/O。若 base 缺失、tracking/re-arm 失败或 restore validation 失败，立即回退 full snapshot；若低-dirty 收益不足以抵消生命周期复杂度，也保留 full 为默认。

    12. 架构、正确性与适用边界

    • Local fact：CubeCoW reflink、Cubelet workflow 和多数 control-plane 编排没有 ARM64/x86_64 分支；VMM 的 CPU、interrupt controller、memory layout 和 device state restore 存在架构差异。详见 ARM64 与 x86_64 架构差异 与 中断状态恢复。
    • Engineering judgment：共享控制路径不能替代架构专项验证。报告只测 x86_64，故 ARM64 create/restore/Pause 的正确性与性能都保持 unconfirmed/non-comparable。
    • Snapshot/restore 的首要不变量是 memory、vCPU、device、interrupt、filesystem、network 与 agent-visible state 一致；API success 或 Hello World 前置验证不能覆盖这些不变量。
    • fast restore、reflink 和 soft-dirty 分别依赖 memory layout、filesystem 与 kernel capability。任一前置条件不成立时，应显式 fallback 或失败，不能把不完整 artifact 当成功。
    • warm-cache 数字不能覆盖 cold start；空载数字不能覆盖 dirty/CPU/I/O workload；单波 batch 不能覆盖稳态排队与 backpressure。

    最终回答是：社区报告覆盖的所有操作都能在当前源码中找到明确的优化设计，但优化的价值来自“减少或迁移工作”，而不是报告中的某个绝对毫秒数。当前证据足以建立机制、前置条件、代价和验证假设；不足以把报告数值升级为 5135a40d... 的 SLA、把 warm path 外推到 cold/loaded path，或把 x86_64 观察外推到 ARM64。
