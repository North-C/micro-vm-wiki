    CubeCoW 存储引擎链路

    本文补齐 CubeSandbox snapshot 路线的存储引擎层——聚焦 CubeCoW 对象、Go FFI、Rust ReflinkEngine、启动恢复（snapshot 生成/catalog 绑定/VMM restore 见各自文档）。

    源码基线：当前仓库工作树。

    相关：Snapshot Create/Commit 生成链路、snapshot catalog restore binding、VMM snapshot restore state。

    0. 术语与背景

    CubeCoW = reflink-capable 文件系统上的 O(1) clone

    CubeCoW 不是独立块设备池。Rust cubecow crate 只有一个 shipping backend：ReflinkEngine，把 volume 和 snapshot 都映射为 reflink-capable 文件系统上的文件。快照语义来自 Linux FICLONE（文件级 reflink，O(1)）。

    三层结构

    flowchart TB Cubelet["Cubelet storage/cubebox"] --> Manager["CowVolumeManager"] Manager --> GoSDK["Cubelet/pkg/cubecow (Go, cgo)"] GoSDK --> FFI["cubecow/src/ffi.rs (C ABI)"] FFI --> Trait["Box"] Trait --> Reflink["ReflinkEngine"] Reflink --> FS["FICLONE filesystem (xfs reflink=1)"]
    层 持有什么 职责
    Go SDK（*cubecow.Engine） opaque pointer + 读写锁 cgo 调用、C string 转换、错误码映射
    Rust FFI（C ABI） Box<EngineHandle>（包 Box<dyn Engine>） 生命周期、panic::catch_unwind、负数错误码
    ReflinkEngine name_index + <root_dir>/volumes/ 布局 volume/snapshot/activation/metrics

    关键边界

    • filesystem as source of truth——没有 on-disk ledger，启动扫描 layout 重建 index。
    • activate 不创建设备节点——reflink backend 只返回文件路径；CubeCoW 交给 VMM 的 memory_vol_url 是 file://<path>，不是 dm-thin 设备节点。
    • 需要 cgo——非 cgo 构建只有报错 stub。
    • snapshot 扁平化——snapshot-of-snapshot 放 ultimate origin volume 目录，origin_volume 记最初的 volume。

    1. 结论先行

    • CubeCoW = reflink backend（FICLONE O(1) clone），不是块设备池。
    • Cubelet 经 Go cgo SDK 调 Rust FFI；引擎对象在 Rust 侧 Box<dyn Engine>，C ABI 暴露为 opaque pointer。
    • 启动恢复不依赖 ledger——ReflinkEngine 扫描 <root_dir>/volumes/ 重建全局 name index，清理 crash 产物。
    • ARM64/x86_64 在 CubeCoW 层无分支；差异在上层 VMM memory snapshot/设备状态/中断控制器恢复。

    2. 分层位置

    Cubelet 不直接操作 reflink layout——只经 CowVolumeManager 创建/删除/解析对象路径，把 dev path 写入 StorageInfo/snapshot catalog/VM restore annotation。Go SDK 不保存对象元数据（只负责线程绑定/C string/错误码/调 FFI），Rust 侧才持 name_index + layout 规则。

    3. Cubelet 初始化

    Cubelet storage config 固定 cubecow backend 为 reflink，按 data_path 推导 root_dir（默认 <data_path-base>/cubecow-reflink，storage/plugin.go:149）。PrepareCowInlineConfig() + BuildCowInitJSON() 生成内联 JSON，initCowEngineWithConfig() 调 cubecow.InitWithoutLoggingFromJSON() → FFI cubecow_init_without_logging_from_json → Rust initialize_without_logging（:206）。

    节点重新初始化（local.Init() → resetCowNodeStorage() 清 root/data + cubecow volumes）是破坏性 host re-init 路径，不是普通重启恢复。普通引擎初始化扫描现有 layout；reset/cleanup 用于 host re-init。

    4. Go SDK 与 FFI

    // Cubelet/pkg/cubecow/engine.go:12
type Engine struct { ptr unsafe.Pointer; mu sync.RWMutex }   // 只存 opaque pointer + 读写锁

// 核心方法：CreateVolume/CreateSnapshot/ActivateVolume/DeactivateVolume/ResizeVolume/GetVolumeInfo/ListSnapshots/GetMetrics

    非 cgo 构建有完整 stub，所有方法返回 "cubecow native support requires cgo"（cubecow_stub.go:11）——cubecow backend 依赖 cgo/native artifact，不是纯 Go fallback。

    Rust FFI 生命周期：config path/JSON 转 AppConfig → crate::initialize() → Box<dyn Engine> 包 Box<EngineHandle> 返 opaque pointer：

    // cubecow/src/ffi.rs:239
#[no_mangle]
pub extern "C" fn cubecow_init_from_json(config_json: *const c_char) -> *mut c_void {
    let result = panic::catch_unwind(|| {                                  // 所有导出包 catch_unwind
        let config = AppConfig::from_json_str(config_json)?;
        match crate::initialize(config) {
            Ok(engine) => { let boxed: Box<EngineHandle> = Box::new(engine); Some(Box::into_raw(boxed) as *mut c_void) }
            Err(e) => { set_last_init_error(/*...*/); None }
        }
    });
    match result { Ok(Some(ptr)) => ptr, Ok(None) => ptr::null_mut(), Err(_) => { set_last_init_error("panic"); ptr::null_mut() } }
}

    失败时负数错误码 + cubecow_last_error() 返 Go，Go 映射为 CowError。

    6. ReflinkEngine layout + Create volume

    // cubecow/src/engine/reflink.rs:17
pub struct ReflinkEngine {
    volumes_dir: PathBuf,                              // <root_dir>/volumes/（engine 只碰这个子树）
    name_index: RwLock<HashMap<String, NameKind>>,     // 全局 volume+snapshot name index

    <root_dir>/volumes/
  <vol-A>/
    <vol-A>      # volume main file
    <snap-1>     # FICLONE(<vol-A>)
    <snap-2>     # FICLONE(<snap-1>), 放 ultimate origin <vol-A> 目录

    create_volume() 先校验名称，再在 name_index 预留 name（防并发 create/delete 竞态），建目录+主文件+set_len+sync file+dirs：

    // cubecow/src/engine/reflink.rs:356
fn create_volume(&self, name: &str, size_bytes: u64) -> CubecowResult<Volume> {
    Self::validate_name(name, "volume")?;
    { let mut idx = self.name_index.write()?;                          // 预留 name（原子 vs 并发）
      if idx.contains_key(name) { return Err(AlreadyExists); }
      idx.insert(name.to_string(), NameKind::Volume); }
    let result = (|| {                                                 // 失败必须回滚 index 项
        std::fs::create_dir_all(self.vol_dir(name))?;
        let file = OpenOptions::new().write(true).create_new(true).open(self.vol_main_file(name))?;
        file.set_len(size_bytes)?; file.sync_all()?;
        fsync_dir(&dir)?; fsync_dir(&self.volumes_dir)?;               // 持久化目录项
        self.project_volume(name)
    })();
    if result.is_err() { idx.remove(name); /* 删主文件+目录，启动扫描兜底 */ }
    result
}

    7. Create snapshot（FICLONE）

    create_snapshot() 源可为 volume 或 snapshot；源 snapshot 时 clone snapshot 文件但目标放 ultimate origin 目录。ficlone() 调 Linux FICLONE ioctl：

    // cubecow/src/engine/reflink.rs:638
fn create_snapshot(&self, source_name: &str, snapshot_name: &str, _activate: bool) -> CubecowResult<Snapshot> {
    // activate 对 reflink 无作用：device path = file path，FICLONE 返回即可寻址（与可能需激活的 backend 接口一致）
    let (source_path, ultimate_origin) = match idx.get(source_name) {   // 源 volume/snapshot
        Some(NameKind::Volume) => (self.vol_main_file(source_name), source_name),
        Some(NameKind::Snapshot { origin_volume }) => (self.snap_file(origin_volume, source_name), origin_volume.clone()),  // 扁平化
    };
    // 预留 snapshot name → ficlone → fsync_dir
}
// :972  ficlone
fn ficlone(src: &File, dst_path: &Path) -> Result<(), i32> {
    let dst = OpenOptions::new().write(true).create_new(true).open(dst_path).map_err(|e| e.raw_os_error().unwrap_or(EIO))?;
    let rc = unsafe { libc::ioctl(dst.as_raw_fd(), FICLONE, src.as_raw_fd()) };   // Linux FICLONE
    if rc != 0 { let errno = /*...*/; let _ = std::fs::remove_file(dst_path); return Err(errno); }  // 失败删部分目标
    Ok(())
}

    FICLONE 完成后可删除源主文件，snapshot 文件保留（reflink 独立于源文件）。activate 参数对 reflink 无作用（保留为接口一致）。

    9. Crash recovery（filesystem as source of truth）

    initialize_with_config() 建 volumes dir → probe FICLONE 支持 → scan_and_rebuild_index() 重建 index：

    // cubecow/src/engine/reflink.rs:134
fn initialize_with_config(config: AppConfig) -> anyhow::Result<Self> {
    let volumes_dir = root_dir.join("volumes");
    std::fs::create_dir_all(&volumes_dir)?;
    probe_reflink_support(&volumes_dir).map_err(|e| /* 提示 mount xfs -m reflink=1 */)?;
    let name_index = scan_and_rebuild_index(&volumes_dir)?;            // 扫描 layout 重建
    /* 统计 volume_count/snapshot_count 设 metrics */
    Ok(Self { volumes_dir, name_index: RwLock::new(name_index), metrics })
}

    scan_and_rebuild_index 恢复规则来自 layout 本身（:1127）：

    现象 恢复行为
    <vol>/<vol> 存在 注册 volume
    volume dir 为空且主文件缺失 删空目录
    主文件存在且有其他文件 注册其他为 snapshot
    snapshot 文件 size 0 删（crash during FICLONE）
    顶层 stray file 忽略告警
    重名 snapshot 跳过告警

    "filesystem as source of truth"——CubeCoW 不需额外事务日志，但filesystem layout 完整性就是恢复边界。

    10. Rootfs / memory 对象 + Restore path 解析

    Cubelet 在 cubecow_snapshot_artifacts.go 把底层 cow volume 包装成 CowSnapshotObject（name/kind/dev path/size/rootfs generation，:31）。AppSnapshot：memory 经 CreateTemplateMemoryVolume() 建空 volume（VMM 写 full），rootfs 经 CreateTemplateRootfsFromBuild() 从 build rootfs 生成 snapshot——rootfs kind=snapshot，memory kind=volume。CommitSandbox：CommitTemplateRootfs() 从当前 sandbox writable rootfs 生成 rootfs snapshot；memory 经 prepareCommitMemoryArtifact() 优先 reflink-clone base（kind=snapshot，VMM 写 soft-dirty/incremental），找不到 base 才 CreateTemplateMemoryVolume()（full）。

    create-from-snapshot 时 prefetchRestoreMemoryVolURL() 从本地 catalog 查 logical id 的 MemoryVol/MemoryKind（storage/local.go:865），ResolveDevPath() 把 cubecow name/kind 转真实文件路径返 file://...，CBRI 写入 cube.vm.snapshot.memory_vol_url。rollback 也走本地解析（ResolveSnapshotForRollback 分解 rootfs snapshot + memory object，:165）。

    Master 只保存 logical snapshot id 不够——能 restore 的前提是请求落到持有 catalog + cubecow 文件对象的 Cubelet 节点。

    11. 能力边界 / ARM64

    问题 结论
    是否需 LVM/dm-thin 当前 reflink backend 不需要
    是否需 cgo 需要；非 cgo build 只有报错 stub
    snapshot 是否 O(1) 是（reflink-capable FS 的 FICLONE）
    snapshot 是否独立于源文件 FICLONE 完成后可删源主文件，snapshot 保留
    是否有 on-disk ledger 没有，启动扫描 filesystem layout
    activate 是否建设备节点 reflink backend 不建，只返文件路径
    是否支持跨 filesystem clone 不支持（FICLONE 因 EXDEV 失败）
    Master 是否知道物理路径 不权威，Cubelet local catalog + CubeCoW 解析

    稳定性边界集中在宿主文件系统：无 reflink 支持/路径不在同一 filesystem/对象目录被外部破坏都会破坏 snapshot/clone 语义。实现边界：RollbackDeriveNewGen() 派生 snapshot 小于期望大小时尝试 resize，但 ReflinkEngine resize 只支持 volume 不支持 snapshot——这类场景失败。catalog 兼容：增量 commit 的 memory 对象 kind=snapshot，旧请求/旧 catalog 缺省回退 legacy kind=volume。

    ARM64/x86_64：CubeCoW 的 Go/FFI/Rust engine/reflink layout 无架构分支——FICLONE 是宿主 Linux 文件系统能力，不关心 guest 架构。共同验证：宿主 kernel/filesystem 是否支持 reflink、pagemap/soft-dirty 是否可用于 VMM memory snapshot、路径权限。ARM64 额外风险不在 CubeCoW 而在 VMM restore（GIC/ITS/FDT/MPIDR/设备拓扑可恢复）。
