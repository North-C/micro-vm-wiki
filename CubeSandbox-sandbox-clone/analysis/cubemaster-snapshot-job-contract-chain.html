CubeMaster Snapshot Job Contract 链路

本文展开 CubeMaster templatecenter 如何把同步 API 转成 snapshot job、Cubelet gRPC 和 READY/FAILED 终态。

源码基线：当前仓库工作树。

相关：CubeAPI Long Operation Contract、snapshot create/commit、snapshot catalog restore binding。

0. 术语与背景

snapshot job 不是普通异步后台任务

TemplateImageJob 把请求落盘，但 API 调用线程随后同步 claim + 执行 + finalize。request_id 是幂等键——同一 request id 只能绑定同一种 operation + 匹配 payload；不匹配当并发冲突。

"Master thin、Cubelet authoritative"

Master 只保存 logical definition/replica/job 进度。rootfs/memory/meta dir/snapshot path 的物理权威在 Cubelet local catalog。

1. snapshot job 创建 + Cubelet gRPC

// CubeMaster/pkg/templatecenter/snapshot_ops.go:246
func runSnapshotCreateJob(ctx, jobID, sandboxID, nodeID, nodeIP, createReq, storedReq) error {
    _ = updateTemplateImageJob(ctx, jobID, map[string]any{ "status": JobStatusRunning, "phase": JobPhaseSnapshotting, "progress": 10 })
    commitRsp, err := cubelet.CommitSandbox(ctx, cubelet.GetCubeletAddr(nodeIP), &cubeboxv1.CommitSandboxRequest{
        RequestID: uuid.NewString(), SandboxID: sandboxID, TemplateID: snapshotID, SnapshotDir: createReq.SnapshotDir,
    })
    if err != nil { return failSnapshotCreateJob(ctx, jobID, snapshotID, /*...*/) }
    // Create replica record + Update definition to READY
    replica := ReplicaStatus{ NodeID: nodeID, NodeIP: nodeIP, InstanceType: createReq.InstanceType, Status: ReplicaStatusReady }
    _ = UpsertReplica(ctx, snapshotID, createReq.InstanceType, replica)
}

snapshot create/rollback/delete 都直接调 Cubelet gRPC（不经 scheduler task/retry）。job 的 READY/FAILED 终态是同步返回给 API 调用方的。

2. 能力边界

Master snapshot job 层不区分 arm64/x86_64。架构差异发生在 Cubelet/CubeShim/CubeHypervisor 处理 rootfs/memory/设备/中断时。调度 task/retry 主要服务 sandbox create/template image 路径——不是 snapshot job 的主执行机制（snapshot job 经 templatecenter 直接调 Cubelet）。
