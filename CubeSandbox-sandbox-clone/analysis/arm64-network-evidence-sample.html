    CubeSandbox ARM64 网络实测样本记录

    本文承接 ARM64 网络实测取证模板。

    前面的模板定义了“应该怎么记”。

    本文用仓库里现成的一组 ARM64 one-click 产物，示范一份真实样本记录应该怎么写。

    样本来源：

    tmp/oneclick-artifacts/e552b1ba46b7-arm64-20260611103537/e2e-offline-20260611

    源码基线：当前仓库工作树。

    1. 样本边界

    这份样本不是原始节点全量日志。

    它是一组安装、健康检查、E2E 摘要和请求结果文件。

    因此它能证明的平台层结果，比底层 network-agent/VMM 细节更强。

    反过来，它也不能替代底层 TAP、TC 和 GIC 级别日志。

    2. 样本清单

    本轮实际读取了四份核心证据：

    1. E2E_SUMMARY.txt
    2. install-xfs.log
    3. final-health.log
    4. requests_snapshot_e2e_result.json

    其中 E2E_SUMMARY.txt 给出最终结论。

    install-xfs.log 给出安装和 quickcheck 过程。

    final-health.log 给出最终服务健康态。

    requests_snapshot_e2e_result.json 给出运行中命令、snapshot、clone 和 rollback 的结果。

    3. 记录头

    可以从样本中直接提取出这些基础字段：

    字段 样本值
    日期 2026-06-11T19:12:23+08:00
    节点架构 aarch64
    样本主机 k8s-master / aarch64
    样本类型 ARM64 one-click offline E2E
    总体结论 PASS

    源码依据：E2E_SUMMARY.txt。

    4. 第一段：host 前置条件

    样本里没有直接保存 /dev/kvm 命令输出。

    但它给出了更强一点的平台信号：

    1. one-click 安装成功。
    2. quickcheck 成功。
    3. network-agent /readyz 被实际检查过。

    install-xfs.log 明确记录了：

    [quickcheck] 1/5 check network-agent healthz

    [quickcheck] 2/5 check network-agent readyz

    [quickcheck] OK

    源码依据：install-xfs.log。

    这说明该 ARM64 样本至少通过了 one-click 控制面和 network-agent 的进程级 ready 检查。

    但它仍不能证明：

    1. network-agent 是否真的创建了 TAP。
    2. CubeVS 是否成功 attach 了 TC filter。
    3. host 节点是否记录过 eBPF verifier 细节。

    5. 第二段：network-agent 与 CubeVS

    这组样本没有保留 network-agent 的原始运行日志。

    因此看不到：

    1. network-agent newTap begin
    2. network-agent newTap attach filter done
    3. network-agent newTap ready
    4. register cubevs tap

    这意味着样本在这一层的证据是间接的。

    它只能通过后续功能结果反推：

    如果后面的 sandbox 运行、对外访问、snapshot clone 和 rollback 都成功，那么 host 网络路径大概率至少闭环到了“可工作”。

    但这仍不足以证明 CubeVS 的 attach 行为在日志层完全健康。

    因此这份样本在 network-agent/CubeVS 层的结论只能写成：

    功能结果支持其大致可用，但缺少 host 侧结构化日志，不能单独证明 TAP/TC attach 细节。

    6. 第三段：CubeShim/VMM/virtio-net ready

    样本没有直接保存 CubeShim 的 vm ready, vsock is listening 日志。

    也没有直接保存 virtio-device activated 事件。

    但它给出了两个更高层的强信号。

    第一，template 创建成功并达到 READY。

    第二，sandbox create 成功，并且后续命令可以在 guest 中执行。

    E2E_SUMMARY.txt 里明确写了：

    Template success: ... READY

    Sandbox create: PASS

    源码依据：E2E_SUMMARY.txt。

    这说明：

    1. VM 至少已经成功启动到业务可用。
    2. guest agent 通道至少已经可用。
    3. runtime 层已经能把命令送进 guest。

    但它仍不能单独区分：

    是 VsockServerReady 通知路径成功，还是 fallback probe 成功。

    也不能直接证明 virtio-net 的激活日志是否完整出现。

    7. 第四段：guest cube-agent 配网

    这组样本对 guest 网络的最强证据，不是原始 agent 日志。

    而是业务命令确实在 guest 内跑通了，并返回了架构信息。

    requests_snapshot_e2e_result.json 里的 cmd1.stdout 是：

    v1

    aarch64

    源码依据：requests_snapshot_e2e_result.json。

    这至少证明了三件事：

    1. sandbox 已进入运行态。
    2. guest 用户态命令可执行。
    3. 该样本确实落在 ARM64 guest，而不是 host 假阳性。

    同时 E2E_SUMMARY.txt 还写明：

    Command/data-plane: PASS, envd via cube-proxy returned v1 and aarch64

    源码依据：E2E_SUMMARY.txt。

    这比单纯的 guest 内命令更强。

    因为它证明了请求已经经过了 cube-proxy 路径，而不是只在 guest 本地做一次 exec。

    但这份样本仍没有保留：

    1. wait a pci
    2. Failed to update interface
    3. create sandbox!, config net

    因此 guest 配网层的结论应写成：

    业务结果证明 guest 网络最终可用，但缺少 agent 原始日志，无法细分 PCI 等待、接口更新和路由更新各自耗时与阶段性状态。

    8. 第五段：snapshot、clone 与 rollback

    这组样本在 snapshot 相关路径上的证据是比较完整的。

    E2E_SUMMARY.txt 明确写了：

    1. Snapshot create/list: PASS
    2. Create from snapshot: PASS
    3. Rollback: PASS

    源码依据：E2E_SUMMARY.txt。

    requests_snapshot_e2e_result.json 进一步给出了：

    1. snapshot id 和 READY 状态
    2. clone 后读到 v1
    3. 改写到 v2
    4. rollback 后重新读到 v1

    源码依据：requests_snapshot_e2e_result.json。

    这说明 ARM64 样本不只是“能建 sandbox”。

    它还证明了平台级 snapshot/clone/rollback 至少在这个工作负载上能闭环。

    但这份样本仍然不能直接证明：

    1. restore 时是否真的走到了 gic-v3-its section。
    2. 是否出现过 restore 后首包中断异常但被应用层掩盖。
    3. 底层 set_gicr_typers() 是否按预期执行。

    因此这层结论应当精确写成：

    平台级 snapshot/clone/rollback 功能在 ARM64 样本上成功，但尚未从底层 VMM/GIC 日志直接验证 restore 首包唤醒链。

    9. 第六段：最终健康态

    final-health.log 保存了一组很有价值的结尾证据。

    它显示：

    1. cube-sandbox-network-agent.service 是 active running
    2. ready
    3. {"status":"ok","sandboxes":0}

    源码依据：final-health.log。

    这说明测试结束后，控制面和 network-agent 没有明显残留异常，清理后 sandbox 数量归零。

    这对“流程是否干净收尾”是强证据。

    但它依旧不是数据面日志。

    所以它只能增强“平台最终状态健康”的判断，不能替代中间链路观测。

    10. 这份样本实际证明了什么

    基于当前仓库内的这组 ARM64 产物，可以比较稳妥地得出以下结论：

    1. ARM64 one-click 安装与 quickcheck 在该节点成功。
    2. network-agent 的服务级就绪检查成功。
    3. ARM64 template create 成功并进入 READY。
    4. ARM64 sandbox create 成功，且 guest 内命令确实返回 aarch64。
    5. 通过 cube-proxy 的业务访问成功。
    6. ARM64 路径上的 snapshot、clone 和 rollback 在该工作负载上成功。
    7. 最终平台健康态正常，且无残留 sandbox。

    11. 这份样本还不能证明什么

    同样需要明确写出它的缺口。

    这份样本还不能直接证明：

    1. network-agent newTap 的每个阶段日志都成功出现。
    2. CubeVS from_cube/from_world/from_envoy 的 attach 细节在 ARM64 上完全正常。
    3. CubeShim 的 VsockServerReady 一定走的是 notify path 而不是 fallback。
    4. guest cube-agent 的 wait a pci、update_interface、update_routes 明细都成功打印。
    5. restore 后底层 gic-v3-its 和首包唤醒链有直接日志支撑。

    这不是样本无效。

    而是它的证据层级更偏平台集成结果，不够覆盖底层网络与中断细节。

    12. 结论

    这份 ARM64 样本已经足以作为“平台级成功案例”的第一份记录。

    它最有价值的地方，是证明 ARM64 路径并非只能停留在源码分析，而是已经在 one-click E2E 产物里留下了可复核的成功证据。

    下一步最值得做的，不是继续扩写抽象文档。

    而是补一份更底层的节点日志样本，把 network-agent、CubeShim/VMM 和 guest agent 的原始日志拼进来，补足这份样本目前缺失的中间层证据。
