    CubeSandbox API 到 Cubelet 创建链路

    本文沿 POST /sandboxes 追踪 CubeSandbox 从 CubeAPI、CubeMaster 到 Cubelet 的创建路径，解释平台控制面如何把外部请求变成节点上的 containerd/CubeShim 启动。

    源码基线：当前仓库工作树。

    相关：Cubebox Action 到 Containerd/CubeShim、CubeMaster Scheduler 与 Task Retry、CubeMaster 缓存一致性。

    0. 术语与背景

    create 是平台级流程，不是单个 VMM 调用

    CubeSandbox 的 create 跨 API → Master → Scheduler → Cubelet workflow → containerd → CubeShim 六段。核心边界：CubeAPI 做产品 API 适配；CubeMaster 做调度/重试/元数据；Cubelet 做节点资源 + containerd；CubeShim/CubeHypervisor 才进 VM 生命周期。

    每段的"输入→输出"契约

    段 输入 输出 关键动作
    CubeAPI E2B 风格 NewSandbox（template/network/timeout） CreateSandboxRequest（带 annotations） 补齐 Master 所需内部 annotations + 网络策略
    CubeMaster CreateCubeSandboxReq RunCubeSandboxRequest + 选定节点 调度、retry/failover、写 proxy map/spec
    Cubelet service RunCubeSandboxRequest RunCubeSandboxResponse gRPC contract、默认值、workflow context
    Cubelet workflow CreateContext containerd container/task step/action 流水线编排
    cubebox plugin CubeBox metadata OCI spec + containerd 调用 NewContainer/NewTask（触发 CubeShim）

    关键概念

    • annotation 是跨段携带状态的主要载体：template id、hostdir mount、appsnapshot 标志等都靠 annotation 从 API 传到 Cubelet。
    • RunCubeSandboxRequest 是 Master↔Cubelet 的 gRPC contract——Cubelet 收到的不是原始 API 请求，而是带完整容器/卷/网络/annotation 的节点执行描述。
    • workflow 不是写死的函数串：Cubelet create 由 workflow 配置编排的插件流水线，cubebox create 只是其中一个 action。
    • Cubelet 不直接调 VMM——它通过 containerd NewTask 触发 CubeShim。

    5. Master 构造 Cubelet 请求

    ConstructCubeletReq() 是 API 层资源描述 → 节点执行描述的转换点：

    // CubeMaster/pkg/service/sandbox/util.go:121
func ConstructCubeletReq(ctx context.Context, req *types.CreateCubeSandboxReq) (*cubebox.RunCubeSandboxRequest, error) {

    if req.Timeout <= 0 { req.Timeout = config.GetConfig().CubeletConf.CommonTimeoutInsec }

    6. 调度与重试

    Handle() → handleCubelet() 在循环里先调度再调 Cubelet（sandbox_run.go:179/197）：

    // 失败走 BackoffSelect

func (c *createSandboxContext) callCubelet() bool {           // 返回 true 表示需 retry

    if err != nil { return c.errRetry(err) }                  // 错误码决定 retry/reschedule
    // ...
}
    sequenceDiagram participant Master as createSandboxContext participant Scheduler participant Node as selected node participant Cubelet loop until success or terminal failure Master->>Scheduler: Select(selctx) Scheduler-->>Master: node Master->>Node: IncrNodeConcurrent Master->>Cubelet: cubelet.Create(node, RunCubeSandboxRequest) Cubelet-->>Master: RunCubeSandboxResponse / error Master->>Node: DecrNodeConcurrent end

    Master 能力边界是控制面决策——不建 VM，只选节点/构造请求/处理 retry-failover，成功后写 proxy map + sandbox spec。

    9. workflow engine + cubebox create

    Engine.Create() 只是 e.run(flow_create, ctx, opts)（engine.go:544）；run() 找 create workflow、申请并发 limiter、按 step 顺序执行（step 内 action 并行，失败触发 failover cleanup，:251）。workflow 来自 plugin 配置（plugin.go:84）——create 不是写死函数串，是配置编排的插件流水线。

    cubebox local.Create() → createContainers() → runContainer()：

    这是 Cubelet 到 CubeShim 的真实边界：Cubelet 不直接调 VMM——通过 containerd NewTask 创建触发 CubeShim（shim v2）。

    10. 能力边界

    层级 负责什么 不负责什么
    CubeAPI 外部 API、template annotation、network policy 输入 节点选择和 VM 创建
    CubeMaster request normalization、scheduler、retry、proxy/spec metadata containerd task 和 VM 启动细节
    Scheduler 节点 prefilter/filter/score/backoff 节点本地资源实际创建
    Cubelet service gRPC contract、default、workflow context、runtime dispatch 外部 API 兼容层
    workflow engine create flow 编排、并发限制、失败 cleanup 单个插件内部实现
    cubebox plugin CubeBox metadata、OCI spec、containerd container/task VMM 内部启动实现
    CubeShim shim v2、VM/agent lifecycle API/Master 调度

    CubeSandbox 比 Kata 更平台化：Kata 入口是 container runtime；CubeSandbox 入口是产品 API，到达 shim 前多了 Master 调度、Cubelet workflow、storage/network 平台状态。

    11. ARM64 与 x86_64 观察点

    API/Master/Scheduler/Cubelet workflow 的 create 顺序与架构无关。差异在 CubeShim/CubeHypervisor、guest image、kernel config、network-agent/CubeVS eBPF、device model。但控制面会间接暴露架构差异：ARM64 节点资源/template replica/kernel/eBPF 能力不足时，表现为 scheduler filter、Cubelet create error 或 CubeShim task error。

    ARM64 验证不能只看 VMM 能否 boot——还要覆盖 template locality、CubeVS、Cubelet workflow、CubeShim agent ready、snapshot/rollback。
