    CubeSandbox Virtio Net / Fs Restore 内部状态链路

    本文展开 VMM Device Restore 设备恢复链路 的下一步，聚焦 virtio-net 与 virtio-fs 在 restore 中到底恢复了哪些状态、哪些只是重新绑定当前节点后端。

    结论只来自当前仓库源码。

    transport 层 MSI-X/queue 恢复详见 中断状态恢复链路；网络 RX/TX 热路径见 网络数据面与中断唤醒链路。

    0. 术语与背景

    两层状态

    virtio 设备 restore 分两层，恢复的内容完全不同：

    层 由谁负责 恢复什么
    transport 层 VirtioPciDevice PCI config、MSI-X、virtio common config、virtqueue 地址（desc/avail/used ring）+ ready 状态
    device 层 具体设备（Net/Fs/vhost-user） 协商 features、设备 config、queue size；复杂设备还有 backend 内部状态

    restore 时 transport 层先把 virtqueue 地址/ready/中断配置恢复到位，device 层的内部 restore 才有意义——device restore 依赖 transport restore。

    关键概念

    • NetState / 设备 state：普通 virtio 设备只存"轻量"状态（features、config、queue size）。不存运行时对象（tap fd、epoll worker、rate limiter）——这些在 activate 时按当前配置重建。
    • back_state（virtio-fs 专属）：native virtio-fs 把 backend server 的内部状态序列化进 back_state，restore activate 时反序列化应用到新 server。这是 net 没有的重状态。
    • donated tap：CubeSandbox 的 tap fd 由 network-agent 经 SCM_RIGHTS 捐赠（见 TAP fd 链路）。donated tap 的 offload 不被 VMM 改。
    • vhost-user re-negotiation：vhost-user net/fs 不存 backend 内部对象，只存协商后的 features/protocol features/queue 数；restore 时重新连 socket、再协商、重建 vring。
    • guest-visible 来自快照，host 后端来自当前请求：这是贯穿 net/fs/vhost-user 的恢复原则。

    1. 核心结论

    • transport 层：VirtioPciDevice 恢复 PCI config、MSI-X、virtio common config、virtqueue 地址和 ready 状态，再重新 activate。
    • device 层：普通 virtio-net 只保存 features/config/queue size；tap fd、epoll worker、rate limiter 在 activate 时重建。
    • native virtio-fs 比 net 重：序列化 backend server 状态到 back_state，restore activate 时反序列化应用。
    • vhost-user net/fs：不存 backend 内部对象，存协商状态；restore 重新建协议和 vring。
    • ARM64 与 x86_64 在这两个设备内部状态上基本共享同一实现，差异在上一层 transport/中断/PCI 暴露方式。

    2. 状态分层图

    flowchart TD A["DeviceManager restore_devices"] --> B["VirtioPciDevice::restore"] B --> C["restore MSI-X"] B --> D["restore common config"] B --> E["restore PCI config"] B --> F["restore QueueState"] F --> G{"device_activated and driver ready?"} G -->|yes| H["VirtioPciDevice::activate"] H --> I["Net::activate or Fs::activate"] I --> J["spawn worker threads"] G -->|no| K["wait for driver activation"]

    3. VirtioPciDevice 保存与恢复的状态（transport 层）

    VirtioPciDeviceState 保存 device_activated、每个 queue 的 size/ready/desc/avail/used ring 地址、interrupt_status（pci_device.rs:279）。state() 从当前 Queue 读三段 ring 地址（:508），set_state() 恢复并用 guest memory 中的 used idx 重设 next avail/used（:527）。

    restore() 的顺序刻意 MSI-X 最先，确保设备配置恢复前中断路由已重建：

    // hypervisor/virtio-devices/src/transport/pci_device.rs:1184  (顺序骨架)
fn restore(&mut self, snapshot: Snapshot) -> Result<()> {
    // 1. 先恢复 MSI-X（重建中断路由）—— MsixConfig::set_state 见 interrupt-state-restore-chain
    if let Some(msix_config) = &self.msix_config { /* msix_config.restore(...)? */ }
    // 2. virtio common config
    //    common_config.restore(...)?;
    // 3. PCI config
    //    configuration.restore(...)?;
    // 4. 若 device_activated 且 driver ready，重新 activate()
}
    状态层 保存位置 作用
    PCI config PciConfiguration snapshot 恢复 PCI 配置空间
    virtio common config VirtioPciCommonConfig snapshot 恢复 queue select、MSI-X vector 等
    queue rings VirtioPciDeviceState 恢复 desc/avail/used 地址
    MSI-X MsixConfig snapshot 恢复 table/PBA/mask + 重建 route（见 中断状态恢复 §3-4）
    device features 具体设备 state 恢复 negotiated features
    backend state 设备自定义 net 基本无；fs 有 server state

    4. 普通 virtio-net 状态（device 层）

    NetState 只含"轻量"字段——没有 tap、没有 worker、没有 rate limiter 运行时状态：

    // hypervisor/virtio-devices/src/net.rs:423
#[derive(Serialize, Deserialize)]
pub struct NetState {
    pub avail_features: u64,
    pub acked_features: u64,
    pub config: VirtioNetConfig,
    pub queue_size: Vec<u16>,
}

    tap 不在 NetState 里。Net::new() 按当前 NetConfig 重新 open_tap()；from_tap_fds() dup 传入的 donated fd 构造 Tap（net.rs:514）。

    guest-visible 配置来自快照，host tap 后端来自当前恢复请求。CubeSandbox restore 网络走的是当前节点的新 tap：VMM 先在 RestoreConfig.net 替换 tap，再创建 Net。所以 virtio-net 的 features/config 来自快照，但 tap 是新的。

    5. virtio-net activate

    Net::activate() 先 common.activate()，再按 queue 数创建 control queue worker 和 RX/TX queue pair worker（net.rs:646）。每个 RX/TX pair 都新建 RxVirtio/TxVirtio/rate limiter/tap clone/queue eventfd/epoll worker。tap offload 按 restored acked_features 重配；donated tap 不被 VMM 改 offload（net.rs:723）。Net::snapshot() 只存 NetState，Pausable 只转发到 VirtioCommon，无额外 backend 序列化（:832）。

    flowchart LR A["Restored NetState"] --> B["Net::new_with_tap"] C["Current tap/tap fd"] --> B B --> D["VirtioPciDevice restore queue state"] D --> E["Net::activate"] E --> F["spawn ctrl queue worker"] E --> G["spawn RX/TX workers"]

    6. native virtio-fs 状态（back_state）

    native Fs 比 net 重——它序列化 backend server 内部状态到 back_state。Fs 结构含 backendfs_config、pending_dev_message、server、back_state、restore 标志（fs.rs:657）。

    snapshot 时，若 server 已存在，Fs::snapshot() 调 server.serialize_data() 把返回数据写进 state.back_state：

    // hypervisor/virtio-devices/src/fs.rs:1094
fn snapshot(&mut self) -> std::result::Result<Snapshot, MigratableError> {
    let mut state = self.state();
    if let Some(server) = &self.server {
        self.prepare_backend_serialization_if_needed(server)?;
        let result = server.serialize_data()        // 序列化 server 内部状态
            .map(|data| { state.back_state = data; });
        result?;
    }
    // ...
}

    restore activate 时，Fs::activate() 先建新 backend server；若 restore 为 true 且 back_state 非空，反序列化应用：

    // hypervisor/virtio-devices/src/fs.rs:916
fn activate(&mut self, mem, interrupt_cb, mut queues) -> ActivateResult {
    self.common.activate(&queues, &interrupt_cb)?;
    let server = self.init_backend_fs_server(&self.backendfs_config)?;
    if self.restore {
        if !self.back_state.is_empty() {
            server.deserialize_and_apply_data(self.back_state.as_ref())?;  // 应用旧 server 状态
        }
    }
    // ...
}

    native virtio-fs 不只是重新打开目录——它还尝试恢复 backend server 的内部序列化状态。前提是新 shared_dir/allowed_dirs/backend 配置能被 server 接受。

    7. allowed_dirs 与 fs 更新

    BackendFsConfig 含 shared_dir/cache/xattr/writeback/read_only/allowed_dirs（fs.rs:520）。restore 前 RestoreConfig.fs 经 update_fses() 覆盖 shared_dir/allowed_dirs/cache/rate limiter（config.rs:2322）。activate 时 init_backend_fs_server() canonicalize shared_dir、构造 passthrough fs、把 allowed_dirs 传给 Server::new()（fs.rs:775）。

    运行中更新走另一条路（非 restore）：vm_set_fs() 更新 VM config 后调 vm.fs_device_update()（lib.rs:1070）→ DeviceManager 把 FsEvent 推入 node 的 pending_dev_message 再写 dev_evt 唤醒 worker（device_manager.rs:1173）→ worker 收 DEVICE_EVENT 后调 server.update_filter(&allowed_dirs)（fs.rs:466）。

    sequenceDiagram participant API as VmSetFs participant VMM as VMM participant DM as DeviceManager participant FS as Fs worker participant Server as virtiofs server API->>VMM: fs config VMM->>VMM: update_fses VMM->>DM: fs_device_update DM->>DM: push FsEvent DM->>FS: write dev_evt FS->>Server: update_filter(allowed_dirs) Server-->>FS: success/fail

    8. vhost-user net/fs 差异

    vhost-user net/fs 的设备 state 存协商状态而非 backend 内部对象：

    设备 State 字段 锚点
    vhost-user net features、config、acked protocol features、vhost-user queue 数 vhost_user/net.rs:39
    vhost-user fs 同上 + backend_req_support vhost_user/fs.rs:33

    restore 构造时两者都重新连 socket，再用保存的 features/protocol features 调 set_protocol_features_vhost_user()（net :83、fs :102）。snapshot 都调 vu_common.snapshot(id, state) 合并通用 vhost-user 状态（net :403、fs :368）。

    9. vhost-user vring 重建

    setup_vhost_user() 先把 guest memory table 重发 backend，再为每个 queue 发 vring num/addr/base/call eventfd/kick eventfd（vu_common_ctrl.rs:153）。它按 queue 的 desc/used/avail 地址从 guest memory 转出 host address 调 set_vring_addr()（:204）；vring base 用当前 queue 的 avail idx；call eventfd 来自 virtio interrupt notifier，kick eventfd 来自 transport 传入的 queue eventfd。最后 set_vring_enable(..., true)、保存 vrings_info、标记 ready。若 backend 协商到 LOG_SHMFD + VHOST_F_LOG_ALL 还建 inflight tracking shared memory（:440）。

    10. ARM64 与 x86_64 落点

    virtio-net、native virtio-fs、vhost-user net/fs 的 device 层代码不按 target_arch 分裂：

    • net：tap 后端、queue worker、offload 配置共用代码；
    • fs：backend server 序列化、allowed_dirs filter、queue worker 共用代码。

    差异在上一层：virtio-pci 资源如何暴露、中断控制器如何投递、legacy MMIO/PIO 如何描述。

    因此同架构内 restore 的主要风险来自 host 后端可用性（tap 能否拿到、virtiofsd 能否重连）。跨架构 restore 的失败点仍在 VM/DeviceManager/CPU/GIC/IOAPIC 层，不是这两个设备内部。

    11. 能力边界

    • 普通 virtio-net 不恢复 tap 历史状态——tap 必须由当前节点重新提供，且 id/队列拓扑要与快照匹配。rate limiter 在 activate 时按当前配置重建，不持久化令牌桶。
    • native virtio-fs 能恢复 server 序列化状态，但前提是新 shared_dir/allowed_dirs/backend 配置能被 server 接受。
    • vhost-user net/fs 依赖外部 backend 可重连，并接受保存的 protocol features/queue 数/vring 配置。
    • virtqueue 地址来自 guest memory 快照——若 memory restore 或 queue ring 内容不一致，设备 activate 后无法靠 device 层修复。
