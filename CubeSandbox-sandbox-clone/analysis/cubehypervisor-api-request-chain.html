    CubeHypervisor API Request 内部调度链路

    本文解释 CubeShim 如何把 sandbox 操作变成 ApiRequest，以及这些请求如何在内嵌 VMM 线程中串行落到 VM 方法。

    源码基线：当前仓库工作树。

    控制面事件（ApiRequest 唤醒 / NotifyEvent 状态通道）的分层辨析见 中断与事件通知链路；VmRestore 内部状态恢复见 VMM Snapshot Restore 状态恢复链路。

    0. 术语与背景

    内嵌库模式 vs 外部 HTTP

    CubeShim 用的是内嵌库模式——不是默认经外部 HTTP socket 控制 VMM，而是 CubeHypervisor 直接持有 cube_hypervisor::VmmInstance，调 send_request(ApiRequest::...)。HTTP API 是可选控制面（VmmConfig::http_path 默认 None，vmm_config.rs:22/38），但 SandBox::new() 会把 ch_http_api 设成 Utils::chapi_path(id)，所以真实 sandbox 通常额外起一个 Unix socket HTTP API（sb.rs:87）。

    三条通道

    通道 类型 方向 用途
    ApiRequest / ApiResponse 同步 RPC（mpsc + eventfd） CubeShim → VMM → CubeShim "执行这个 VM 操作" + 拿执行结果
    NotifyEvent 异步推送（独立 channel） VMM/guest → CubeShim "VM 生命周期变了"（started/ready/shutdown）
    HTTP /api/v1/vm.* 可选外部控制 外部 → VMM app snapshot 工具等外部调用

    关键区分：ApiResponse 只表示请求执行完，不代表 guest ready。guest ready 要看独立的 NotifyEvent::VsockServerReady。

    VM 生命周期模型

    CubeSandbox 的 VM 操作分两类，VmCreate 只存配置不建 VM：

    操作 做什么 前置条件
    VmCreate 只存 VmConfig 无 vm_config
    VmBoot 建 Vm::new() + vm.boot() 有 vm_config
    VmRestore 从快照复活（new_from_snapshot + restore + resume） 无 vm 且 无 vm_config
    VmPauseToSnapshot pause + snapshot + delete 当前 VM 有 vm
    VmResumeFromSnapshot 实际就是 vm_restore() 无 vm/vm_config

    因此普通 boot 必须 create_vm() 再 boot_vm()；snapshot restore 只能 restore_vm()，不能先 create。而 VmResumeFromSnapshot 本质是重建 VM，所以 rollback 前必须先 VmDelete。

    1. 核心结论

    • CubeShim 用内嵌库模式：CubeHypervisor 创建 VmmInstance，直接 send_request（cube_hypervisor.rs:75、hypervisor/src/lib.rs:278）。
    • VmmInstance 内部沿用 Cloud Hypervisor 风格：一个 VMM thread + ApiRequest mpsc + API eventfd + response channel（hypervisor/src/lib.rs:214、service.rs:60）。
    • CubeShim 对 VMM 的调用是同步 RPC——拿到 response 时 VMM 分支已执行完或返回错误。

    2. 两条 API 面

    flowchart TB Shim["CubeShim CubeHypervisor wrapper"] --> Lib["VmmInstance::send_request"] Lib --> Service["VMM_SERVICE"] Service --> EventFd["api EventFd"] Service --> ReqCh["ApiRequest channel"] EventFd --> Loop["VMM epoll control_loop"] ReqCh --> Loop HTTP["optional HTTP /api/v1"] --> Endpoint["EndpointHandler"] Endpoint --> Service
    • 嵌入式路径：CubeShim 常规 hypervisor 方法。不经 JSON route 解析、不经 EndpointHandler，直接构造 Rust enum。
    • HTTP 路径：HTTP_ROUTES 把 /api/v1/vm.* 映到 handler，handler 调同一组 API helper 也进 VMM_SERVICE（api/http/mod.rs:112、http_endpoint.rs:52）。

    app snapshot 是例外：Snapshot::do_app_snapshot() 不持有 CubeHypervisor wrapper，而是连 sandbox 的 Unix socket HTTP API，PUT /api/v1/vm.pause、/vm.snapshot、/vm.resume（snapshot/mod.rs:140/181）。

    3. CubeShim wrapper：产品动作 → ApiRequest

    CubeShim 的每个 wrapper 方法就是把产品动作翻成一个 ApiRequest 发出去。看几个就懂模式：

    // CubeShim/shim/src/hypervisor/cube_hypervisor.rs:113
pub async fn create_vm(&self, config: &VmConfig) -> CResult<()> {
    let ch = self.ch.as_ref().unwrap().lock().await;
    let vm_config = config.to_vm_config();
    ch.send_request(ApiRequest::VmCreate(Box::new(vm_config)))??   // VmCreate
}
// :126
pub async fn boot_vm(&mut self) -> CResult<()> {
    ch.send_request(ApiRequest::VmBoot)??                          // VmBoot
}
// :173
pub async fn restore_vm(&self, config: config::RestoreConfig) -> CResult<()> {
    ch.send_request(ApiRequest::VmRestore(Arc::new(config)))??     // VmRestore
}

    CubeSandbox 暂停路径常用 pause_vm_cube() 发 VmPauseToSnapshot（pause+snapshot+delete，cube_hypervisor.rs:289、lib.rs:616）；resume_vm_cube() 发 VmResumeFromSnapshot（实际走 restore，cube_hypervisor.rs:303）。

    CubeShim wrapper ApiRequest VMM 端方法
    create_vm VmCreate vm_create（只存配置）
    boot_vm VmBoot vm_boot
    restore_vm VmRestore vm_restore
    snapshot_vm VmSnapshot vm_snapshot
    pause_vm / resume_vm VmPause / VmResume vm_pause / vm_resume
    pause_vm_cube VmPauseToSnapshot vm_pause_to_snapshot
    resume_vm_cube VmResumeFromSnapshot vm_resume_from_snapshot（=restore）

    4. VmmInstance 启动线程

    VmmInstance::new() 先初始化日志/事件监控/notifier，再建 request/response channel + API eventfd（hypervisor/src/lib.rs:93/214），把它们注册进全局 VMM_SERVICE（:218）——这样后续 send_request() 不用持有 sender/eventfd。最后建 hypervisor backend 并调 vmm::start_vmm_thread()，barrier 保证 control loop ready 后 new() 才返回（:225/232）。

    sequenceDiagram participant Shim as CubeShim participant VI as VmmInstance::new participant Svc as VMM_SERVICE participant VMM as VMM thread Shim->>VI: new(VmmConfig) VI->>Svc: init(req_sender, api_evt, res_receiver) VI->>VMM: start_vmm_thread(...) VMM-->>VI: barrier ready VI-->>Shim: VmmInstance

    全局单例边界：VMM_SERVICE 是 lazy_static 全局 Mutex<VmmService>（service.rs:11/60）。同一进程内它不是多 VMM instance 的服务表——后初始化的 instance 会覆盖内部连接。

    5. VmmService 同步请求协议

    send_request() 顺序严格：先写 mpsc，再敲 eventfd，最后阻塞等 response：

    // hypervisor/vmm/src/api/service.rs:85
pub fn send_request(&self, request: ApiRequest) -> Result<ApiResponse, Error> {
    self.api_sender.send(request).map_err(Error::RequestSend)?;  // (1) 数据走 mpsc
    self.api_evt.write(1).map_err(Error::EventFdWrite)?;          // (2) 敲门
    self.res_receiver.recv().map_err(Error::ResponseRecv)         // (3) 阻塞等响应
}

    control loop 在 EpollDispatch::Api 分支按 eventfd 计数从 receiver 取同等数量 request，串行 match 分发（lib.rs:1927，详见 中断与事件通知链路 §3）：

    // hypervisor/vmm/src/lib.rs:1927
EpollDispatch::Api => {
    for _ in 0..self.api_evt.read().map_err(...)? {              // 按 eventfd 计数
        let api_request = api_receiver.recv().map_err(...)?;     // 从 mpsc 取
        match api_request { /* VmCreate/VmBoot/VmSnapshot/VmRestore/VmSetFs/VmAddDevice → self.vm_*() */ }
    }
}

    这是同步 RPC：调用者拿 response 时 VMM 分支已执行完。VmmShutdown 在发 response 后 break 退出 control loop（lib.rs:2013/855）；普通 shutdown/delete 不退出 VMM thread。

    6. VM create / boot / restore 边界

    源码最能说明三个操作的边界差异：

    // hypervisor/vmm/src/lib.rs:542
fn vm_create(&mut self, config: Box<VmConfig>) -> result::Result<(), VmError> {
    // We only store the passed VM config. The VM will be created when being asked to boot it.
    if self.vm_config.is_none() {
        self.vm_config = Some(Arc::new(Mutex::new(*config)));     // 只存配置！不建 VM
        Ok(())
    } else { Err(VmError::VmAlreadyCreated) }
}

// :553
fn vm_boot(&mut self) -> result::Result<(), VmError> {
    if self.vm_config.is_none() { return Err(VmError::VmMissingConfig); }
    if self.vm.is_none() {
        let vm = Vm::new(/* vm_config, exit_evt, ... */)?;        // 此时才建 VM
        self.vm = Some(vm);
    }
    self.vm.as_mut().unwrap().boot()                              // 再 boot
}

    vm_restore() 要求无 vm 且无 vm_config，从 snapshot 目录读 config/state，按 RestoreConfig 替换后端，Vm::new_from_snapshot() + vm.restore() + vm.resume()（lib.rs:653/725，完整见 VMM Snapshot Restore 状态恢复链路）。

    flowchart LR Create["VmCreate"] --> Store["store vm_config only"] Boot["VmBoot"] --> New["Vm::new"] New --> BootRun["vm.boot"] Restore["VmRestore"] --> Recv["recv_vm_config + recv_vm_state"] Recv --> Patch["apply RestoreConfig overrides"] Patch --> NewSnap["Vm::new_from_snapshot"] NewSnap --> RestoreRun["vm.restore + vm.resume"]

    7. Snapshot 与 pause-to-snapshot

    // hypervisor/vmm/src/lib.rs:616
fn vm_pause_to_snapshot(&mut self, snapshot_config: &SnapshotConfig) -> result::Result<(), VmError> {
    self.vm_pause()?;                // (1) pause
    self.vm_snapshot(snapshot_config)?; // (2) snapshot
    self.vm_delete()                 // (3) delete 当前 VM
}
// :633
fn vm_resume_from_snapshot(&mut self, restore_cfg: RestoreConfig) -> result::Result<(), VmError> {
    self.vm_restore(restore_cfg)     // 本质就是 restore
}

    VmPauseToSnapshot 会删除当前 VM——CubeSandbox 的 pause/resume 更像 snapshot-backed suspend/resume，不是简单冻结旧 VM 对象。VmResumeFromSnapshot 实际走 vm_restore()，所以要求当前无 VM/config，rollback 前必须先 VmDelete。

    8. Device 与 FS 更新

    操作 VM 未运行 VM 运行中
    vm_add_device 只更新 vm_config.devices，返回空 payload（lib.rs:968） vm.add_device()，返回 PciDeviceInfo（:947）
    vm_remove_device 无 pre-boot 删除分支 vm.remove_device(id)（:1005）
    vm_set_fs 更新 vm_config fs 配置 再调 vm.fs_device_update(fs_cfg)（:1070）

    运行期 allowed_dirs 更新：CubeShim 发 VmSetFs，VMM 同时更新配置镜像和运行中设备（设备侧 server.update_filter 见 Virtio Net/Fs Restore §7）。

    9. 异步 NotifyEvent 通道

    NotifyEvent 与 ApiResponse 是两条不同通道。launch_vmm() 建 channel::<NotifyEvent>()，sender 放进 VmmConfig.event_notifier（cube_hypervisor.rs:89、hypervisor/src/lib.rs:170）。guest 写 sys_ctrl 触发 SysStart/VsockServerReady，VM shutdown 触发 VmShutdown（sys_ctrl.rs:86、vm.rs:1335）。CubeShim wait_notify() 阻塞读——start 路径等 VsockServerReady，pause 路径等一次 shutdown（cube_hypervisor.rs:253、sb.rs:810/1324）。

    完整的 NotifyEvent 机制（event_notify! 宏、stale event drain）见 中断与事件通知链路 §4-5。

    10. CubeShim 生命周期串联

    start_vm() 先 launch_vmm()；若允许 snapshot 试 restore_vm()，失败（且非强制 app snapshot restore）回退普通 boot（sb.rs:781）。普通 boot：prepare_resource() → create_vm() → boot_vm() → 等 VsockServerReady（失败 fallback vsock probe，sb.rs:938/810）。restore：校验 snapshot metadata → 生成 RestoreConfig（fs/net/disk/pmem/vsock/memory volume URL，sb.rs:946/984）。rollback：先删当前 VM → 用调用方 RestoreConfig resume → drain 旧 VmShutdown（sb.rs:1346/1375）。

    11. ARM64 与 x86_64 差异

    CubeShim→ApiRequest 的同步机制不按架构分叉（mpsc/eventfd/epoll 共享）。差异在：

    维度 x86_64 aarch64
    wrapper seccomp 放行 SYS_mkdir 放行 SYS_mkdirat
    kernel cmdline console=hvc0 + no_timer_check 等 console=ttyAMA0,115200
    ACPI 创建时机 创建 boot vCPU 前创建（vm.rs:2145） 等 vCPU 配置后拿 MPIDR 再创建（:2189）
    restore 兼容性 CPUID compatibility check（lib.rs:688） 走 GIC/FDT/MPIDR 恢复链路
    snapshot 架构状态 clock + common CPUID（vm.rs:2650） 额外保存/恢复 vGIC（:2726/2773）

    ARM64 验证重点不是 ApiRequest 能否分发，而是 Vm::new/new_from_snapshot、设备恢复、VsockServerReady 在 ARM64 guest 上是否稳定闭环。

    12. 容易误读的点

    1. VmCreate 不创建 VM，只存配置——看到 create_vm() 不能理解成 vCPU/设备已启动。
    2. VmPauseToSnapshot 会删除当前 VM——pause/resume 是 snapshot-backed，不是冻结旧对象。
    3. VmResumeFromSnapshot 实际走 vm_restore()——要求无 VM/config，rollback 前必须先 VmDelete。
    4. ApiResponse 只说明请求执行完，不代表 guest ready——guest ready 看 NotifyEvent::VsockServerReady。
    5. HTTP route 存在不代表 CubeShim 常规方法用 HTTP——它们走 VMM_SERVICE，只有 app snapshot 工具走 Unix socket HTTP API。
