    CubeMaster 缓存一致性边界链路

    本文聚焦 CubeMaster 内部缓存如何影响创建调度、运行时控制和实例状态。结论只覆盖当前源码，不把缓存能力外推成强一致控制面。

    调度插件与重试整体路径见 CubeMaster Scheduler 与 Task Retry 链路；物理副本收敛见 Snapshot Replica Reconciler 链路。

    0. 术语与背景

    CubeMaster 的缓存不止一层

    CubeMaster 内部有多种缓存，分别服务不同决策、生命周期不同。混为一谈是最大误读：

    缓存/存储 位置 何时写 何时读 性质
    node metadata/metric cache 进程内 localcache 启动从 DB/Redis 拉 + 后台刷新 scheduler 选址 调度输入，非实时健康证明
    image/template cache 进程内 localcache templatecenter + 节点模板同步 template locality filter 依赖上报与 reconciler
    snapshot storage state 进程内 localcache 探测/reconciler template locality filter（条件） unknown/missing 即不可写
    sandbox list cache 进程内 sync.Map ListSandbox 聚合填充 exec/update/remove 快速定位 周期清空，非持久
    Redis sandbox proxy map Redis create 成功后写 exec/update/remove fallback 持久路由
    MySQL instance / Redis instance info DB + Redis instancecache API/业务查询 状态镜像，非事务

    三类用途的边界

    • 调度选址只用 localcache（节点元数据/指标/template locality）。
    • 运行时路由（exec/update/remove 找"这个 sandbox 在哪台机器"）用 list cache + Redis proxy map，与调度无关——创建后 sandbox 跑在哪只能查路由缓存，不能靠 scheduler 重选。
    • 实例状态镜像（instancecache）写 MySQL + 同步 Redis，是状态记录，不参与选址。

    核心判断：缓存命中 ≠ VM 健康，也不等于 guest ready。CubeMaster 仍需 Cubelet 返回、任务终态、snapshot catalog 来证明实际状态。

    1. 核心结论

    调度阶段依赖 localcache 的节点元数据/指标/template locality；snapshot storage state 只在启用强制约束时参与。运行时 exec/update/remove 依赖 sandbox list cache 或 Redis proxy map。instancecache 是实例状态镜像，不参与常规选址。缓存命中不等价于 VM 健康。

    2. 组件图

    flowchart TB API["CubeAPI / service request"] --> Master["CubeMaster service"] Master --> Scheduler["scheduler.Select"] Scheduler --> NodeCache["localcache node + metric"] Scheduler --> TemplateCache["image/template locality cache"] Scheduler --> SnapshotState["snapshot storage state\nconditional"] Master --> Cubelet["Cubelet gRPC"] Cubelet --> Runtime["CubeShim / VM / guest"] Master --> ProxyMap["Redis sandbox proxy map"] Master --> ListCache["in-process sandbox list cache"] Master --> InstanceDB["instancecache -> MySQL"] InstanceDB --> InstanceRedis["Redis instance info"]

    3. 节点缓存与调度输入

    localcache.Init() 启动时重建本地视图（建 cache/imageCache/templateNodeCache、从 DB/Redis 拉节点与指标），再用后台循环维持：

    // CubeMaster/pkg/localcache/export.go:50
func Init(ctx context.Context) error {
    l.cache = cache.New(0, 0)
    l.imageCache = cache.New(0, 0)
    l.templateNodeCache = cache.New(0, 0)
    l.db = db.Init(config.GetDbConfig())
    // ...
    if err := l.loadAllFromDB(); err != nil { return ... }       // 从 DB 拉节点
    if err := l.loadMetricFromRedis(); err != nil { ... }        // 从 Redis 拉指标
    l.loopSelfNodes(ctx)
    go l.loop(ctx); go l.dealEvent(ctx); go l.loopUpdateMetric(ctx)
    go l.cleanSandboxCache(ctx)                                   // 周期清空 list cache
    return nil
}

    GetHealthyNodesByInstanceType() 的 fallback 很重要——product 缓存缺失时不直接失败，而放宽到全部健康节点：

    // CubeMaster/pkg/localcache/export.go:130
func GetHealthyNodesByInstanceType(n int, product string) node.NodeList {
    l.lockSortedNodes.RLock()
    clusterNodes, exists := l.sortedNodesByClusters[product]
    l.lockSortedNodes.RUnlock()
    if !exists { return GetHealthyNodes(n) }   // fallback：放宽到健康节点集合
    // ...
}

    节点元数据（updateNodeFromMetaData：IP/CPU/内存/磁盘/zone/quota/CPUType/InstanceType，node_cache.go:276）与指标（updateNodeMetric：quota usage/load/使用率/MVM 数，:318）是两条更新线。prefilter 从 GetHealthyNodesByInstanceType() 取候选，过滤健康/熔断/affinity/MVM 上限/metric 超时（prefilter.go:33）。

    节点 cache 是调度入口数据，不是创建成功后的事实确认。

    4. 创建链路中的缓存写入

    创建请求进 CreateSandbox() → newContext() 构造 selector context + Cubelet request + 资源 → scheduler buffer（sandbox_run.go:100/543）。选址在 createSandboxContext.schedule() 调 scheduler.Select（debug direct host 时按 node id/host ip 从 localcache 直查，sandbox_run.go:419/570）。

    Cubelet 创建成功后 dealSuccResult() 写返回，并并行做 Redis proxy map 写入 + sandbox spec 持久化（sandbox_run.go:254）。setProxyToRedis() 只对 cubebox instance type 写 bypass_host_proxy:<sandboxID>：

    // CubeMaster/pkg/service/sandbox/sandbox_run.go:518
func (c *createSandboxContext) setProxyToRedis() error {
    switch c.cubeletReq.GetInstanceType() {
    case cubebox.InstanceType_cubebox.String():
        proxy := &proxytypes.SandboxProxyMap{
            HostIP:      c.selectHost.HostIP(),
            SandboxID:   c.masterRsp.SandboxID,
            SandboxIP:   c.masterRsp.SandboxIP,
            SandboxPort: "8080",
            CreatedAt:   strconv.FormatInt(time.Now().UnixNano(), 10),
        }
        if config.GetConfig().CubeletConf.EnableExposedPort {
            proxy.ContainerToHostPorts = c.cubeletRspPorts
        }
        return localcache.SetSandboxProxyMap(c.ctx, proxy)
    }
    return nil
}

    Redis proxy map 写失败会把 create 返回改成 DBError——持久路由是 create 成功的一部分。

    5. Template locality 与快照存储状态

    templateLocalityFilter.Select() 只在请求含 TemplateID 时生效，依次检查 template node scope、image cache 是否含节点、snapshot storage 是否允许写（template_locality.go:31，一组硬过滤不是评分）。GetImageStateByNode() 取 image cache 再确认含目标 node id（export.go:404）。SyncNodeTemplates() 对比节点上报，删消失副本/注新增副本（template_locality.go:13）。

    snapshot storage state 以 node id/ip 索引，IsSnapshotStorageWriteAllowed() 只允许 healthy/warn：

    // CubeMaster/pkg/localcache/snapshot_storage_state.go:88
func IsSnapshotStorageWriteAllowed(mode string) bool {
    switch strings.ToLower(strings.TrimSpace(mode)) {
    case "healthy", "warn": return true
    default:                return false   // unknown/missing 即不可写
    }
}

    EnforceSnapshotStorage 来自 app snapshot template 注解 + DistributionScope；没有这个标志时 template locality 不检查 snapshot storage state（util.go:53、template_locality.go:48）。物理副本证明在 reconciler + Cubelet local catalog（见 Snapshot Replica Reconciler 链路）。

    6. Runtime 路由缓存（调度与路由是两件事）

    GetSandboxCache() 读进程内 sync.Map，值只有 SandboxID 和 HostIP；后台 cleanSandboxCache() 周期整体清空：

    // CubeMaster/pkg/localcache/list_cache.go:17
var listCache = &sync.Map{}
type SandboxCache struct { SandboxID string; HostIP string }
func cleanSandboxCache() { listCache = &sync.Map{} }       // 周期清空
func GetSandboxCache(sandboxID string) *SandboxCache { /* Load */ }

    create 成功不写 list cache——它由 ListSandbox 聚合 Cubelet 返回时填充（sandbox_list.go:106），是 list 结果的短期镜像。Exec 定位 HostIP 的 fallback 顺序：

    // CubeMaster/pkg/service/sandbox/sandbox_exec.go:49
var hostIP string
if v := localcache.GetSandboxCache(req.SandboxID); v != nil {        // (1) 先查 list cache
    hostIP = v.HostIP
} else if proxyMap, ok := localcache.GetSandboxProxyMap(ctx, req.SandboxID); ok {  // (2) 再查 Redis
    hostIP = proxyMap.HostIP
} else {
    rsp.Ret.RetMsg = "sandbox not found"; return                      // (3) 都没有 → 失败，不重新调度
}
calleeEndpoint := cubelet.GetCubeletAddr(hostIP)                      // 拿到后直连 Cubelet

    运行时控制面路由和调度是两件事：创建后 sandbox 在哪台机器，后续请求只能查路由缓存或持久路由，不能靠 scheduler 重选。Remove 同样先按 list cache/proxy map 找，销毁后删两者（sandbox_remove.go:114/166）。Update 的 pause/resume 同序（sandbox_update.go:50）。

    7. Instancecache 的状态镜像

    UpdateInstanceCreateInfo() 写 instance state/uuid/host_ip/private ip，host ip 能从 localcache 反查节点时回填 CPUType/host_id/zone（instancecache/export.go:160）。UpdateInstanceStatus() 先更 MySQL 再 SetInstanceInfoField() 写 Redis hash（:199、localcache/export.go:244）。

    DB 和 Redis 之间可能出现短暂分歧——源码通过合并错误返回暴露失败，但没有把这一步变成跨存储事务，也不自动回滚 MySQL。

    8. 一致性边界表

    缓存/存储 主要写入者 主要读取者 用途 边界
    node metadata cache localcache 初始化和节点事件 scheduler、debug direct host、instancecache 节点资源、规格、架构标签 不是实时健康证明
    node metric cache Redis 指标刷新 scheduler score/filter 负载、quota、并发 存在采样延迟
    image/template cache templatecenter、节点模板同步 template locality filter、template score 模板本地性 依赖上报和 reconciler
    snapshot storage state snapshot storage 探测/reconciler template locality filter 强制快照存储场景的写入可用性 unknown/missing 即不可写
    sandbox list cache ListSandbox exec/update/remove/info 快速定位 HostIP 周期清空，非持久
    Redis proxy map create 成功后写入 exec/update/remove/info 持久路由 fallback 写失败会影响 create 成功
    MySQL instance info instancecache API/业务查询 实例状态事实源之一 与 Redis hash 非事务
    Redis instance info instancecache/localcache 快速实例信息查询 状态镜像 可能滞后于 MySQL

    9. 典型失配场景

    • node metric 延迟 → scheduler 在旧负载视图上打分（用并发计数 + Cubelet 错误码重试缓解，但缓存不保证实时）。
    • template cache 未及时注册真实副本 → template locality 过滤掉可用节点；cache 残留已删副本 → 由 Cubelet local catalog/restore 兜底。
    • snapshot storage state 缺失 + 启用 EnforceSnapshotStorage → 节点被直接过滤（缺失不当成乐观可写）。
    • list cache 被清空 → Exec/Update 仍可经 Redis proxy map 找到；Redis 也缺 → sandbox not found。
    • list cache 残留旧 HostIP → 优先于 Redis 被读，Cubelet 调用失败后调用方才看到运行时错误。
    • MySQL 已更新但 Redis hash 失败 → 查不同存储看到不同状态（UpdateInstanceStatus() 返回合并错误，不回滚）。

    10. ARM64 与 x86_64 边界

    CubeMaster 缓存层无独立 ARM64/x86_64 调度算法。架构差异通过节点字段/instance type/CPUType/labels/template locality/镜像可用性间接表达：updateNodeFromMetaData() 存 CPUType/InstanceType（node_cache.go:276），UpdateInstanceCreateInfo() 回填 CPUType（instancecache/export.go:168）。

    CubeMaster 可经缓存/标签把请求导向 arm64 或 x86_64 节点，但 VM 能否在该架构启动仍由 Cubelet/CubeShim/CubeHypervisor/guest image/内核决定。
