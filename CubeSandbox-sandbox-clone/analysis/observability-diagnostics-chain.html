CubeSandbox 可观测性与诊断机制链路

本文回答：CubeSandbox 出故障时证据从哪里来，能证明到哪一层。

源码基线：当前仓库工作树。

相关：arm64-log-source-map、arm64-log-collection-gap、中断与事件通知。

0. 术语与背景

多组件平台 = 多组件日志

CubeSandbox 有 6+ 个组件进程，诊断信号分散在各组件。没有一个单一 metrics 文件能覆盖全部。

组件 日志目录 诊断焦点
CubeAPI /data/log/CubeAPI/ 请求路由/限流/长操作
CubeMaster /data/log/CubeMaster/ 调度/快照任务/缓存一致性
Cubelet /data/log/Cubelet/ workflow/quota/resource/cgroup
CubeShim /data/log/CubeShim/ VMM 控制/sandbox ready/notify
CubeVmm /data/log/CubeVmm/ virtio 设备/GIC/ITS/restore
network-agent /data/log/network-agent/ TAP/CubeVS/port mapping

两类诊断入口

入口 用途
quickcheck.sh 基础健康检查（network-agent /healthz /readyz + cubelet.sock + network-agent-grpc.sock）
collect-logs.sh 按模块采集日志 + 系统快照（ps/ports/dmesg/env/mounts/cgroup/cpuinfo）

1. collect-logs.sh 模块采集

# deploy/one-click/scripts/cube-diag/collect-logs.sh:102
DATA_LOG_DIR="${CUBE_DATA_LOG_DIR:-/data/log}"
# :212  按模块采集 _collect_data_log_dir
_collect_data_log_dir "${DATA_LOG_DIR}/CubeMaster" "${dest}"
_collect_data_log_dir "${DATA_LOG_DIR}/Cubelet" "${dest}"
_collect_data_log_dir "${DATA_LOG_DIR}/CubeAPI" "${dest}"
collect_cubeshim()  { /* /data/log/CubeShim/ */ }
collect_cubevmm()   { /* /data/log/CubeVmm/ */ }
collect_network_agent() { /* /data/log/network-agent/ + runtime network-agent.log */ }

collect-logs 不抓 journald——抓 /data/log/<组件>/ + /var/log/cube-sandbox-one-click/ + 系统快照。支持 --module 选择性采集。

2. 平台级 vs 组件级诊断边界

  • 平台级（quickcheck /readyz + E2E_SUMMARY + final-health）：证明平台流程走完，但不证明每个组件内部正常。
  • 组件级（/data/log/<组件>/ 原始日志）：才是组件内部证据。

最常见的误判：看到平台级成功但 guest 行为异常 → 必须下沉到组件级日志（CubeShim/CubeVmm/network-agent），不能止步于平台级端点。详见 arm64-log-collection-gap。

3. 能力边界

问题 CubeSandbox 表现
日志结构 两层：/var/log/cube-sandbox-one-click（runtime 启动）+ /data/log/<组件>/（结构化模块日志）
健康端点 network-agent /healthz//readyz + cubelet.sock + network-agent-grpc.sock
日志采集 collect-logs.sh 按模块 + 系统快照
guest agent 诊断 需经 CubeShim vsock 通道（通道断则 guest 可见性丢失）
平台级成功 ≠ 组件内部正常 ≠ guest ready（需分层排查）
