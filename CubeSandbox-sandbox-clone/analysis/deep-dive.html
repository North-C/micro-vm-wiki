    CubeSandbox-sandbox-clone 深入探索文档

    本文档基于 CubeSandbox-sandbox-clone 仓库分析 CubeSandbox 0.3.0 方向的架构。结论从源码和仓库文档出发：CubeSandbox 不是单个 Micro-VM VMM，而是一套面向 AI Agent sandbox 的平台系统；虚拟化只是其中的执行边界，真正的产品能力来自 CubeAPI、CubeMaster、Cubelet、network-agent、CubeCoW、CubeShim、CubeHypervisor 和 guest cube-agent 的组合。

    当前版本：第 2 版
    源码基线：CubeSandbox-sandbox-clone 仓库，commit b871e4c
    阅读方式：先建立平台分层，再沿 CubeAPI -> CubeMaster -> Cubelet -> containerd/CubeShim -> CubeHypervisor -> cube-agent -> CubeCoW/network-agent 展开。

    0. 问题地图

    1. CubeSandbox 与 Firecracker/Cloud Hypervisor/crosvm/Kata 的层级差异是什么？
    2. CubeAPI、CubeMaster、Cubelet、CubeShim、CubeHypervisor、cube-agent、CubeCoW、network-agent 分别负责什么？
    3. POST /sandboxes 如何变成节点上的 MicroVM sandbox？
    4. Snapshot、clone、rollback 为什么不是单纯的 VMM snapshot？
    5. CubeCoW 的存储快照和 CubeHypervisor 的 VM/memory snapshot 如何配合？
    6. network-agent/CubeVS 的网络隔离边界在哪里？
    7. ARM64 与 x86_64 的实际差异从源码能看到什么？
    8. CubeSandbox 与 Kata Containers 的边界在哪里？

    1. 一句话定位

    CubeSandbox 是基于 RustVMM/KVM 的高并发 AI Agent sandbox 服务平台。它对外兼容 E2B SDK，对内通过平台控制面、节点代理、containerd shim、KVM VMM、guest agent、CoW 存储和 eBPF 网络隔离来组织 MicroVM 生命周期。

    源码和文档依据：

    • README 定义 Cube Sandbox 是基于 RustVMM/KVM 的 secure sandbox service，可在 60ms 内创建硬件隔离 sandbox，内存开销低于 5MB：README.md。
    • README 0.3.0 新闻说明 CubeCoW Copy-on-Write snapshot engine 支持 event-level snapshots、instant cloning、rollback：README.md。
    • README 架构表列出 CubeAPI、CubeMaster、CubeProxy、Cubelet、CubeVS、CubeHypervisor & CubeShim 的职责：README.md。
    • CubeShim README 明确 CubeShim 是 containerd shim 组件，通过 ttrpc/vsock 转发 container lifecycle 到 in-VM cube-agent：CubeShim/README.md。
    • agent/README.md 明确 cube-agent 运行在 MicroVM 内作为 PID 1，负责 guest 内 container lifecycle：agent/README.md。

    2. 顶层架构

    flowchart TB SDK["E2B-compatible SDK / cubesandbox SDK"] --> API["CubeAPI\nRust REST Gateway"] API --> MASTER["CubeMaster\nscheduler + metadata + task"] MASTER --> CUBELET["Cubelet\nnode lifecycle manager"] CUBELET --> NETAGENT["network-agent\nTAP/CubeVS/port proxy"] CUBELET --> COW["CubeCoW\nxfs-reflink snapshot engine"] CUBELET --> CTD["containerd"] CTD --> SHIM["CubeShim\ncontainerd-shim-cube-rs"] SHIM --> HYP["CubeHypervisor\nKVM VMM wrapper"] HYP --> VM["MicroVM"] SHIM --> AGENT["cube-agent\nPID 1 in guest"] NETAGENT --> CUBEVS["CubeVS/eBPF"] CUBEVS --> VM COW --> SHIM

    这个架构要按“平台层 + 节点层 + 虚拟化层 + guest 层”理解：

    层级 组件 作用
    产品/API 层 CubeAPI、SDK、CubeProxy 对外暴露 E2B-compatible sandbox、snapshot、rollback、clone、connect
    集群控制面 CubeMaster 选择节点、维护 metadata、把请求转成 Cubelet gRPC 操作、管理异步/重试任务
    节点控制面 Cubelet 节点注册、状态上报、controller 运行、调用 containerd、网络 agent、存储 engine
    节点数据面 network-agent、CubeVS、CubeCoW 管 TAP/eBPF/端口映射、CoW volume/snapshot、状态恢复
    Runtime 层 containerd、CubeShim 承接 containerd shim v2 生命周期，把 container/sandbox 操作转成 VM 和 guest agent 操作
    虚拟化层 CubeHypervisor、cube_hypervisor 创建 VMM、VM、boot、pause/resume、snapshot/restore
    Guest 层 cube-agent、rustjail VM 内 PID 1，配置网络/存储/namespace，执行 OCI workload

    因此 CubeSandbox 的“能力边界”不能只看 VMM。它更像一个把 MicroVM 变成 Agent sandbox 产品的控制系统。

    3. 能力边界

    维度 CubeSandbox-sandbox-clone
    目标场景 AI Agent 代码执行、浏览器自动化、RL/SWE-Bench、E2B 替代
    对外接口 E2B-compatible REST + Python/Go SDK
    隔离边界 每个 Agent 拥有 Guest OS kernel，结合 eBPF 网络隔离
    快启动 resource pool + snapshot cloning + CoW
    新增能力 event-level snapshot、instant clone、rollback
    VMM 层 CubeHypervisor 管理 KVM MicroVM，宿主层借鉴 Cloud Hypervisor/Kata 模型
    存储层 CubeCoW 基于 xfs-reflink/FICLONE 的 O(1) snapshot/clone
    网络层 network-agent 管 TAP、端口代理、CubeVS/eBPF 映射
    架构 x86_64 完整支持，aarch64 初步支持；PVM 仅 x86_64

    README 明确 x86_64 是 primary fully-supported architecture，aarch64 在 /dev/kvm 可用时为 preliminary support，PVM 目前 x86_64-only：README.md。

    4. 控制面端到端流程

    sequenceDiagram participant User as SDK / HTTP client participant API as CubeAPI participant Master as CubeMaster participant Scheduler as scheduler participant Cubelet as Cubelet participant Net as network-agent participant Cow as CubeCoW participant Ctd as containerd participant Shim as CubeShim participant Hyp as CubeHypervisor participant Agent as cube-agent User->>API: create sandbox / clone / rollback API->>Master: CubeMasterClient request Master->>Scheduler: prefilter/filter/score/select Master->>Cubelet: CubeboxMgr gRPC Cubelet->>Net: EnsureNetwork Cubelet->>Cow: create/activate volume or snapshot Cubelet->>Ctd: create task / sandbox Ctd->>Shim: shim v2 request Shim->>Hyp: launch_vmm/create_vm/boot_vm/restore_vm Shim->>Agent: CreateSandbox over ttrpc/vsock Agent-->>Shim: guest sandbox ready Shim-->>Ctd: task ready Cubelet-->>Master: result/status Master-->>API: operation terminal/ready

    这条链路里有三个重要边界：

    1. CubeAPI 是 HTTP 产品入口，不直接操作 VMM。
    2. CubeMaster/Cubelet 用 gRPC 和任务系统连接集群调度与节点执行。
    3. CubeShim/CubeHypervisor/cube-agent 才是 VM 和 guest 生命周期的实际执行路径。

    5. CubeAPI：REST 入口和长操作契约

    flowchart LR Route["Axum route"] --> Handler["handler"] Handler --> Service["SandboxService / SnapshotService"] Service --> MasterClient["CubeMasterClient"] MasterClient --> Master["CubeMaster"]

    CubeAPI/src/routes.rs 把普通 sandbox 路由与 snapshot/rollback/template 删除等长操作路由分开。普通路由包括 create/list/get/delete/pause/resume/connect；snapshot create 和 rollback 放入 240 秒 long route，因为 CubeMaster/Cubelet 需要等待同步终态：CubeAPI/src/routes.rs。

    代码注释给出很关键的语义：snapshot 创建通过 cubelet.CommitSandbox，大 rootfs 可能运行几十秒；rollback 需要等待 Cubelet 恢复 memory + rootfs；template/snapshot 删除也可能等待 Cubelet 物理清理 LVM/metadata，因此必须走 long router：CubeAPI/src/routes.rs、CubeAPI/src/routes.rs。

    AgentHub 相关接口也复用了这个长操作路由，包括创建/删除 agent snapshot、rollback、recover、clone、publish-template：CubeAPI/src/routes.rs。这说明 clone/rollback 已经是产品 API 的一等能力，不是内部调试命令。

    SandboxService::create_sandbox() 构造 CreateSandboxRequest，写入 template id/version annotation，设置 timeout、labels、network_type、CubeVS context，然后调用 cubemaster.create_sandbox()：CubeAPI/src/services/sandboxes.rs。

    connect_sandbox() 如果发现 sandbox 是 Paused，会通过 update_sandbox(..., "resume") 自动恢复，再返回可连接信息：CubeAPI/src/services/sandboxes.rs。

    6. CubeMaster：调度、任务和 Cubelet 调用

    CubeMaster 是 CubeAPI 和节点 Cubelet 之间的集群控制面。它的核心职责不是“跑 VM”，而是选择节点、调用 Cubelet、追踪结果、处理失败重试。

    调度主线在 scheduler.Select()：

    flowchart LR Request["SelectorCtx"] --> Pre["runPreFilter"] Pre --> Filter["parallelRunFilters"] Filter --> Score["runScoreFilter"] Score --> Pick["LeastRandomSelect"] Pre -.failed.-> Backoff["BackoffSelect"] Filter -.failed.-> Backoff

    源码显示 Select() 先跑 prefilter，再跑 filter，再跑 score，最后 LeastRandomSelect() 选节点；如果 prefilter/filter 失败，在非 template locality 强约束场景会走 backoff select：CubeMaster/pkg/scheduler/schedule.go。

    普通 filter 是并行执行的：parallelRunFilters() 用 errgroup 运行所有 filter，再保留命中所有 filter 的节点：CubeMaster/pkg/scheduler/schedule.go。score 阶段按插件权重聚合、排序，并把结果写回 selector context：CubeMaster/pkg/scheduler/schedule.go。

    CubeMaster 调 Cubelet 的接口集中在 CubeMaster/pkg/cubelet/actions.go。可以看到 Create、Destroy、AppSnapshot、CommitSandbox、RollbackSandbox、ListLocalSnapshots、GetStorageMetrics、Exec、Update 等都是对 Cubelet CubeboxMgr gRPC client 的封装：CubeMaster/pkg/cubelet/actions.go。

    任务系统负责异步化和重试。handleTask() 根据错误码决定普通重试或 loop retry，并在成功/失败后上报 metrics；DestroySandboxTaskHandler 成功后会删除 sandbox proxy/cache，并运行 destroy-success hook：CubeMaster/pkg/task/handlers.go、CubeMaster/pkg/task/handlers.go。

    7. Cubelet：节点上的生命周期编排器

    Cubelet 是节点侧的核心 daemon。它持有 master client、controller map、CRI image service、run template manager、network-agent client，并负责节点注册和状态上报。

    Cubelet 结构体字段直接说明它的边界：masterClient 连接 CubeMaster，controllerMap 跑本地 controller，criImage 管镜像，rtManager 管 run template，networkAgentClient 连接 network-agent：Cubelet/pkg/cubelet/cubelet.go。

    NewCubelet() 从宿主机 identity 生成 node name/labels/IP，构造 Cubelet，并把 node status 函数和 instance type 注入 run template manager：Cubelet/pkg/cubelet/cubelet.go。

    Run() 启动节点状态同步 goroutine，然后遍历 controllerMap 并运行每个 CubeMetaController；controller 接口本身只有 Run(stopCh)，说明 Cubelet 通过 controller 插件化地组织节点本地循环：Cubelet/pkg/cubelet/cubelet.go、Cubelet/pkg/controller/interface.go。

    Cubelet 对外 API 的 proto 文档列出 RunCubeSandboxRequest、RollbackSandboxRequest、CommitSandboxRequest、AppSnapshotRequest、ListLocalSnapshotsRequest、GetLocalSnapshotRequest、GetStorageMetricsRequest 等对象：Cubelet/doc/cubelet-api.md。其中 AppSnapshotRequest 明确语义是创建一个 cubebox、用 cube-runtime 创建 app snapshot、再销毁 cubebox，并要求 app snapshot 相关 annotations：Cubelet/doc/cubelet-api.md。

    8. CubeShim 与 CubeHypervisor：VM 生命周期执行路径

    sequenceDiagram participant CTD as containerd participant Shim as CubeShim participant CH as CubeHypervisor participant VMM as cube_hypervisor VMM participant Agent as cube-agent CTD->>Shim: shim v2 request Shim->>CH: launch_vmm() CH->>VMM: VmmInstance::new() Shim->>CH: create_vm() CH->>VMM: ApiRequest::VmCreate Shim->>CH: boot_vm() CH->>VMM: ApiRequest::VmBoot Shim->>Agent: CreateSandbox over ttrpc/vsock

    CubeShim README 说明 containerd 创建 sandbox 时会启动 containerd-shim-cube-rs，CubeShim 向 Cubelet/Cube runtime 请求 KVM MicroVM，向上隐藏 VM 复杂度，向下通过 ttrpc/vsock 管理 in-VM cube-agent：CubeShim/README.md。

    SandBox::new() 创建 CubeHypervisor，并保存 ttrpc client、OCI spec、配置、containers、状态和监控句柄：CubeShim/shim/src/sandbox/sb.rs。

    SandBox::init() 从 OCI annotations 构造 Cube 配置；如果是 app snapshot restore，要求必须提供 fresh cube.vm.snapshot.memory_vol_url，否则报错。这说明 restore 不是只靠 template ID，必须由上游解析并传入本次启动实际使用的 memory volume：CubeShim/shim/src/sandbox/sb.rs。

    CubeHypervisor::launch_vmm() 设置 runtime seccomp rules，构造 VmmConfig 和 event notifier，然后创建 cube_hypervisor::VmmInstance：CubeShim/shim/src/hypervisor/cube_hypervisor.rs。

    create_vm() 把 VmConfig 转成 cube_hypervisor VM config，并发送 ApiRequest::VmCreate；boot_vm() 发送 ApiRequest::VmBoot；snapshot_vm() 发送 ApiRequest::VmSnapshot；restore_vm() 发送 ApiRequest::VmRestore：CubeShim/shim/src/hypervisor/cube_hypervisor.rs。

    9. Guest agent：VM 启动后的真正可用性边界

    cube-agent 是 guest 内 PID 1。文档说明它在 MicroVM 内初始化 guest 环境，监听 ttrpc/vsock，处理 CreateContainer/StartContainer/ExecProcess/SignalProcess/RemoveContainer，并通过 rustjail 执行 OCI workload：agent/README.md。

    SandBox::create_sandbox() 的顺序也证明了这一点：先 start_vm()，如果需要则通知 snapshot 结果，然后 connect_agent()；连接 agent 后才认为 "agent is ready"，再做 snapshot restore 的 guest reset、hotplug device、构造 storage/DNS/network，最后向 agent 发 CreateSandboxRequest：CubeShim/shim/src/sandbox/sb.rs。

    这意味着“VM boot 成功”不等于“sandbox 可用”。CubeSandbox 的可用性条件至少包括：

    1. VMM 已启动并 boot VM。
    2. vsock/ttrpc 能连接到 guest cube-agent。
    3. agent 完成 storage、network、route、ARP、DNS、namespace/container 初始化。
    4. shim 开始监控 VM exit/OOM/agent health。

    10. CubeCoW：snapshot/clone 的存储基础

    CubeCoW 是 Rust library crate，基于 xfs-reflink/FICLONE 提供 thin-provisioned volume 和 O(1) snapshot/clone：cubecow/README.md。

    flowchart TB API["Cubelet / Go cgo wrapper"] --> FFI["cubecow C FFI"] FFI --> Trait["dyn Engine"] Trait --> Reflink["ReflinkEngine"] Reflink --> FS["FICLONE-capable filesystem"] FS --> Vol["volume file"] FS --> Snap["snapshot file"]

    README 对实现边界说得很清楚：当前唯一 backend 是 ReflinkEngine，在支持 FICLONE 的文件系统上用 regular files 表示 volumes 和 snapshots；snapshot 通过 kernel FICLONE ioctl 共享 extents，因此是元数据级 O(1) 操作：cubecow/README.md。

    磁盘布局是 <root_dir>/volumes/<vol>/ 下的一个 volume 文件和多个 snapshot 文件；snapshot 是 flat model，删除某个 snapshot 不影响其他 snapshot：cubecow/README.md。

    Engine trait 把能力分成 volume、snapshot、activation、node、observability 几类：create/delete/resize/list volume，create/delete/list snapshot，activate/deactivate，reset node storage，metrics：cubecow/src/engine/mod.rs。

    因此 CubeCoW 解决的是 rootfs/volume 的 CoW snapshot/clone，不等同于 VM memory snapshot。一个完整的 app snapshot/rollback 往往要同时处理：

    1. rootfs/volume 状态：CubeCoW/FICLONE。
    2. VM/memory/device 状态：CubeHypervisor snapshot/restore。
    3. 平台 metadata：CubeMaster/Cubelet/SnapshotService 的 snapshot/template/replica 信息。
    4. 网络状态：network-agent/CubeVS/TAP/port mapping。

    11. network-agent 与 CubeVS：网络数据面边界

    network-agent 是节点级网络编排组件，从 Cubelet 中迁出为独立服务，负责 MicroVM sandbox 本地网络配置：network-agent/docs/ARCHITECTURE.md。

    它的核心职责包括 TAP 创建和 CubeVS 映射、主机端口代理到 guest 服务、本地状态持久化和启动恢复、向 Cubelet 提供独立网络管理接口：network-agent/docs/ARCHITECTURE.md。

    flowchart TB Cubelet --> GRPC["gRPC/HTTP API"] Cubelet --> FD["FD Server\nUnix socket TAP FD"] GRPC --> LS["LocalService"] FD --> LS LS --> IPAM["IP allocator"] LS --> TAP["TAP pool"] LS --> Port["Port allocator"] LS --> Proxy["Host proxy"] LS --> Store["JSON state store"] LS --> CubeVS["CubeVS/eBPF"] CubeVS --> Guest["MicroVM guest"]

    Service 接口提供 EnsureNetwork、ReleaseNetwork、ReconcileNetwork、GetNetwork、ListNetworks、Health：network-agent/internal/service/service.go。

    localService 持有 state store、IP allocator、port allocator、host device、cube gateway device、active states、tap pool、quarantined taps、destroy-failed taps：network-agent/internal/service/local_service.go。

    NewLocalService() 要求显式 eth_name，创建 state store、IP allocator、port allocator、machine device、cubegw0，然后初始化 CubeVS 参数和默认 SNAT IP：network-agent/internal/service/local_service.go。

    网络创建路径会从 TAP 池取 TAP 或新建 TAP，配置端口映射，注册 CubeVS TAP，持久化 sandbox network state：network-agent/internal/service/local_service.go。恢复路径会 restore TAP、重新分配 IP/端口、refresh CubeVS TAP、恢复 ARP 和 port map：network-agent/internal/service/local_service.go。

    默认 interface 会把 guest 内部 IP/MAC/MTU/gateway 写入返回结构，同时持久化 sandbox_ip、host_tap_name、mvm_inner_ip、gateway_ip 等 metadata：network-agent/internal/service/local_service.go。

    cubeVSTapRegistration() 默认允许 Internet access，或者使用请求里的 allow/deny 配置构造 cubevs.MVMOptions：network-agent/internal/service/local_service.go。

    12. Snapshot、clone、rollback 的真实组成

    README 和 guide 明确三类高级 API：

    API 语义 sandbox ID
    create_snapshot() 持久化当前 sandbox memory + filesystem state 不变
    clone(n=N) 从运行中 sandbox 派生 N 个独立副本 新 ID
    rollback(snapshot_id) 原地恢复到指定 snapshot state 不变

    SDK 示例文档说明 create_snapshot() 返回可作为 Sandbox.create(template=snapshot_id) 使用的 snapshot，clone() 创建独立副本，rollback() 原地恢复且 sandbox ID 不变：docs/guide/snapshot-rollback-clone.md。

    CubeAPI 的 SnapshotService::create() 会先构建 create request payload，然后调用 cubemaster.create_snapshot()，检查 response、snapshot_id 和 ready 状态：CubeAPI/src/services/snapshots.rs。

    SnapshotService::delete() 依赖 CubeMaster 同步删除契约：返回成功时，replica、metadata、cubelet-side LVM/meta 都已删除；路由使用 240 秒 timeout 避免慢清理被 30 秒默认预算切断：CubeAPI/src/services/snapshots.rs。

    SnapshotService::rollback() 调用 cubemaster.rollback_sandbox()，并要求 operation 进入 ready/terminal 状态后才返回：CubeAPI/src/services/snapshots.rs。

    CubeShim 的 snapshot 子命令支持普通 snapshot 和 app snapshot 两种路径。普通 snapshot 会 launch VMM、boot VM、等待 VM ready、create snapshot、store metadata；app snapshot 则通过已有 VM 的 HTTP API 调用 pause、snapshot、resume：CubeShim/shim/src/snapshot/mod.rs。

    SnapshotArgs 支持 --snapshot-type full|incremental|soft-dirty，其中 incremental 保存 CoW anonymous pages，soft-dirty 尝试保存上次 soft-dirty snapshot 以来被 dirty 的 page；还支持 --memory-vol 把 memory range data 写到独立 volume：CubeShim/shim/src/snapshot/cmd.rs。

    flowchart TB Running["running sandbox"] --> Pause["vm.pause"] Pause --> VMSnap["vm.snapshot\nfull / incremental / soft-dirty"] Running --> CowSnap["CubeCoW rootfs/volume snapshot"] VMSnap --> Metadata["snapshot metadata"] CowSnap --> Metadata Metadata --> Clone["clone -> new sandbox ID"] Metadata --> Rollback["rollback -> same sandbox ID"] Rollback --> Restore["vm.restore + volume restore + network reconcile"]

    这里最容易误解的一点是：CubeSandbox 的 snapshot/clone/rollback 是平台级语义，不是单个 VMM API。VM snapshot 只保存 CPU/memory/device 层；CubeCoW 保存文件系统/volume；CubeMaster/Cubelet 保存元数据和本地 snapshot catalog；network-agent 负责网络状态恢复。

    13. ARM64 与 x86_64 差异

    维度 x86_64 aarch64
    README 支持状态 primary, fully-supported preliminary support with /dev/kvm
    PVM supported not supported currently
    deploy one-click/PVM/bare-metal 主路径 deploy/aarch64 提供 kernel build/config 辅助
    CubeShim seccomp 允许 SYS_mkdir 允许 SYS_mkdirat
    agent build <arch>-unknown-linux-musl 同样按当前 uname -m musl target 生成
    VMM 语义 x86 KVM/PCI/ACPI/CPUID 路径 ARM64 KVM/GIC/FDT/MPIDR 路径，成熟度低于 x86
    平台组件 Go/Rust 控制面基本跨架构 网络/eBPF/kernel config 仍依赖 arm64 内核能力

    README 明确 x86_64 与 aarch64 支持状态：README.md。CubeShim snapshot 和 CubeHypervisor 代码中对 x86_64/aarch64 有 syscall 级差异，例如 x86_64 添加 SYS_mkdir，aarch64 添加 SYS_mkdirat：CubeShim/shim/src/snapshot/mod.rs、CubeShim/shim/src/hypervisor/cube_hypervisor.rs。

    cube-agent 的构建脚本按 uname -m 安装 musl target，输出路径也是 target/<arch>-unknown-linux-musl/release/cube-agent，这表明 guest agent 本身按架构构建，而不是 x86-only 二进制：agent/README.md。

    从源码证据看，ARM64 的差异主要不在 CubeAPI/CubeMaster/Cubelet 这些控制面，而在三类更底层路径：

    1. Hypervisor/VM 架构路径：KVM vCPU、GIC、FDT、guest boot 协议。
    2. guest kernel/rootfs/agent artifact：必须使用 aarch64 kernel/image/agent。
    3. network/CubeVS：eBPF、TAP、SNAT、内核参数在 ARM64 kernel 上要验证。

    因此，ARM64 下 CubeSandbox 更应该按“平台控制面可复用，VMM/guest/network artifact 需要逐项验收”来理解。

    14. 与 Firecracker、Cloud Hypervisor、Kata 的关键差异

    对比对象 CubeSandbox 的不同点
    Firecracker Firecracker 是专注极简 VMM/API server 的 MicroVM 引擎；CubeSandbox 是上层 sandbox 平台，VMM 只是执行层之一
    Cloud Hypervisor Cloud Hypervisor 是通用 Rust VMM，强调 virtio、hotplug、migration/snapshot；CubeSandbox 把类似能力包装到 Agent sandbox 生命周期
    crosvm crosvm 是 ChromeOS/Android 体系的多进程设备模型 VMM；CubeSandbox 的重点是 E2B-compatible API、模板、clone/rollback 和平台调度
    Kata Containers Kata 是 VM-based container runtime；CubeSandbox 继承 containerd shim/guest agent 思路，但产品入口变成 Agent sandbox API，并把 snapshot/clone/rollback 做成核心能力

    与 Kata 的关系最接近。Cube agent 文档说明 cube-agent derived from Kata agent，但替换为 Cube ttrpc API，增加 Cube-specific sandbox extensions，并适配 Cube hypervisor/shim 的 vsock 端口和 boot flow：agent/README.md。

    关键边界是：Kata 更像通用 container runtime；CubeSandbox 更像面向 AI Agent 的 sandbox 产品平台。它借用了 Kata/containerd shim 模型，但额外引入 CubeAPI、CubeMaster、Cubelet、CubeVS、CubeCoW、template/snapshot/clone 语义。

    15. 当前源码揭示的风险和待验证点

    1. CodeGraph 对跨语言/protobuf/RPC 的端到端调用边支持有限，CubeAPI -> CubeMaster -> Cubelet -> containerd 的部分边要结合 proto、client wrapper 和文档确认。
    2. README 宣称 60ms 创建和 <5MB 内存开销，但需要 benchmark 脚本或运行环境验证，不能只凭源码静态分析确认。
    3. CubeCoW 依赖 FICLONE-capable filesystem，生产环境必须验证 XFS/Btrfs/OCFS2 mount 参数和故障恢复。
    4. network-agent 默认写 /proc/sys/net/ipv4/ip_local_port_range，并依赖 CubeVS/eBPF 初始化；这对宿主内核权限和运维隔离有直接要求。
    5. ARM64 目前应按 preliminary support 看待；控制面跨架构不代表 VMM/guest/network artifact 已达到 x86_64 同等成熟度。
