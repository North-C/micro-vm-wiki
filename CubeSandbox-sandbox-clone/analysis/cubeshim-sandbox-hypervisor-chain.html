CubeShim、VMM 与 guest：控制 socket、网络和 I/O 分层

本文回答：CubeShim 与 CubeHypervisor/VMM 到底通过什么通信，普通创建、 snapshot restore、pause/resume、容器 stdio 和网络收发如何组合这些通道？

先行结论：CubeSandbox 没有在 CubeShim 与 VMM 之间再放一台“管理 VM”。v0.7.1 中 CubeShim 与 CubeHypervisor 处于同一 shim 进程，常规 VM 控制走 mpsc + eventfd + response channel；chapi 才是可选的 HTTP/Unix socket 旁路。cube.sock 是 host 侧 virtio-vsock backend，用来把 host 连接映射到 guest agent；cubetap.sock 用来向 VMM 交付 TAP fd；真正 网络和块设备热路径都走 virtqueue/设备 worker，不经过控制 socket。把这四条 路径分开，是理解 create、restore 和 I/O 故障的第一步。

范围与边界：源码基线 v0.7.1@31d911e430fdf8a8879bd062b8e78066c1a8e89d；覆盖 x86_64 与 ARM64 共享的控制/vsock/TAP/virtio 机制，并单列架构分歧。本文没有运行 build、VM、网络或性能实验；“源码存在”不等于部署默认启用或运行已验证。

版本变化单独见 v0.5.1 → v0.7.1 演进， 避免把当前机制与历史变化混成一条时间线。

A. 身份与基线

  • 版本：v0.7.1；完整提交： 31d911e430fdf8a8879bd062b8e78066c1a8e89d。
  • 证据来自固定 Git object 的源码；提交标题只说明作者意图，不替代行为证据。
  • 主要对象：SandBox、CubeHypervisor、VmmInstance、VmmServiceInner、 VsockMuxer、Tap、NetEpollHandler、BlockEpollHandler。
  • 不把独立 cube-hypervisor binary、README 或 ch-remote 的存在，当成 CubeShim 常规路径使用进程间 VMM 的证明。

B. 背景与术语

B.1 这里没有独立的“管理 VM”

SandBox::new() 在 shim 内创建 CubeHypervisor wrapper；launch_vmm() 直接 调用库函数 VmmInstance::new()。后者创建 request/response channel、API eventfd 和名为 vmm 的线程，并在 barrier 返回后才向上层报告 launch 完成 （CubeShim/shim/src/sandbox/sb.rs:82-120、 CubeShim/shim/src/hypervisor/cube_hypervisor.rs:75-102、 hypervisor/src/lib.rs:179-187,228-256）。record_pid() 还把同一个 process::id() 同时写进 shim.pid 与 vmm.pid（ CubeShim/shim/src/common/utils.rs:184-195）。

B.2 五类容易混淆的通道

通道 边界 传什么 是否是常规 VM 控制
VMM_SERVICE CubeShim thread ↔ VMM thread ApiRequest / ApiResponse 是
chapi Unix socket 上的 HTTP/1.1 /api/v1/vm.* 否；app snapshot 等旁路
cube.sock host AF_UNIX ↔ virtio-vsock ↔ guest AF_VSOCK ttrpc、CONNECT、可选 passfd stdio 否；这是 guest 通信
cubetap.sock VMM ↔ Cubelet TAP pool JSON 请求 + SCM_RIGHTS TAP fd 否；这是 host backend 获取
virtqueue worker guest memory ↔ TAP/file/fs backend 网络帧、块请求、文件系统请求 否；这是 steady-state 数据面

C. 对象、所有权与生命周期

对象 所有者 生命周期与关键边界
CubeHypervisor SandBox.ch 保存状态、VmmInstance 与异步通知 receiver；每次 wrapper 调用加锁
VmmInstance CubeHypervisor.ch 持有 VMM thread handle；new() 初始化全局 VMM_SERVICE
VMM_SERVICE 进程级静态单例 保存一个 request sender、eventfd、response receiver；不是多实例路由表
NotifyEvent receiver CubeHypervisor 与同步 ApiResponse 分离；用于 ready/shutdown 等生命周期事件
VsockMuxer virtio-vsock device bind 每 sandbox 的 cube.sock，管理 host 发起的 vsock 连接与 passfd stream
TAP fd Cubelet pool 或 VMM slow path donated fd 进入 Tap 后由 virtio-net worker 持有；CubeShim 只传 TAP name
container stdio fd CubeShim/containerd 一侧 passfd 模式经 SCM_RIGHTS 交给 VsockMuxer；legacy 模式由 ttrpc 流转发

VMM_SERVICE 是全局 Mutex<VmmService>，init() 会替换其中的单个 inner（hypervisor/vmm/src/api/service.rs:14-16,31-49）。CubeSandbox 的 shim-per-sandbox 模型使这个选择可用，但不能据此推断一个 shim 进程可安全托管 多个独立 VmmInstance。

D. 控制、数据与状态链

D.1 主控制链：不是 socket，而是 channel + eventfd

CubeHypervisor::{create_vm,boot_vm,restore_vm,...} 把产品动作转换为 ApiRequest（cube_hypervisor.rs:113-193,197-250,289-342）。同步请求顺序是：

  1. api_sender.send(request)：把 enum 放进 mpsc；
  2. api_evt.write(1)：唤醒 VMM epoll；
  3. res_receiver.recv()：调用线程阻塞等待执行结果。

决定行为的最小代码位于 hypervisor/vmm/src/api/service.rs:85-88。VMM control loop 读 eventfd 计数，按相同次数从 channel 取请求，再串行分派到 vm_create、vm_boot、vm_restore 等方法并返回 response（ hypervisor/vmm/src/lib.rs:1971-2089）。

边界：ApiResponse 只表示该 VMM 方法返回，不证明 guest agent 已 ready。 而且 VmmServiceInner::send_request() 自身没有 timeout；若 VMM control loop 不返回，wrapper 会一直等待。

D.2 chapi：同一 VMM 的 HTTP/Unix socket 旁路

每个 SandBox 把 HypConfig.ch_http_api 设为 /run/vc/vm/<sandbox-id>/chapi，随后 start_vmm_thread() 另起 HTTP 线程 （sb.rs:89-99、common/utils.rs:42,472-474、 hypervisor/vmm/src/lib.rs:417-422）。HTTP handler 最终仍把请求送进同一套 VMM API。

常规 CubeHypervisor wrapper 不走这条 socket。一个明确消费者是 app snapshot： Snapshot::request_ch() 连接 chapi，发送 HTTP/1.1 PUT 到 /api/v1/vm.pause、vm.snapshot、vm.resume（ CubeShim/shim/src/snapshot/mod.rs:140-181,181-220）。

同一 snapshot 模块还包含一个 standalone helper，可直接 VmmInstance::new() 启动自己的 VMM（snapshot/mod.rs:230-254）；它也没有把 SandBox 的常规 create/start wrapper 改成 HTTP 调用。

D.3 guest agent：cube.sock 只是 host 入口

Utils::vsock_path() 生成 /run/vc/vm/<id>/cube.sock；同一配置把 guest CID 固定为 3（common/utils.rs:468-484）。VMM 的 VsockMuxer::new() bind 该 Unix socket；epoll_nested=true 时立即把 listener 加进 nested epoll，否则在 device activate 阶段由 add_host_sock_to_listener() 补注册（ hypervisor/virtio-devices/src/vsock/unix/muxer.rs:674-725）。

CubeShim 连接 agent 时发送 CONNECT 1024\n，等待 OK，dup Unix stream fd 后交给 ttrpc client（common/utils.rs:529-559）。VMM 接受 host stream，解析 目标 port，再建立 host-CID 到 guest-CID 的 vsock connection（ muxer.rs:763-827,851-940）。所以 guest agent 监听的是 guest 内 AF_VSOCK， 不是 host 文件系统里的 Unix socket。

ready 又是另一条状态链：guest 写 SysCtrl 的 SYS_VSOCK_SERVER 位，VMM 发出 NotifyEvent::VsockServerReady，CubeShim 从独立 mpsc receiver 读取 （hypervisor/devices/src/legacy/sys_ctrl.rs:86-97、 hypervisor/event_notifier/src/lib.rs:15-23,37-54、 cube_hypervisor.rs:253-281）。

D.4 普通 cold boot

SandBox::start_vm() 的实际顺序是：

  1. launch_vmm()；
  2. 没有可用 snapshot 时 prepare_resource → VmCreate → VmBoot；
  3. 最多等待 10 秒取得恰好 VsockServerReady；
  4. connect_agent() 建 ttrpc；
  5. CreateSandboxRequest 下发 interfaces/routes/ARP/DNS/storage；
  6. 启动 OOM 与 VM monitor。

证据：sb.rs:866-921、sb.rs:472-550。

这里 VmCreate 只提交配置，实际 VM/设备创建发生在 VmBoot；控制完成、 vsock ready、agent CreateSandbox 完成是三个不同的门槛。

D.5 创建期 snapshot restore 与 app snapshot restore

普通 snapshot restore 仍先 launch_vmm()，但直接构造 RestoreConfig{source_url, fs, net, disks, pmem, vsock, ...} 发 VmRestore。其中 net/fs/disk/vsock 是当前 sandbox 的 backend 绑定，用来 替换 snapshot 中的 host 侧资源；随后继续等待 VsockServerReady（ sb.rs:923-1008）。

app snapshot restore 有一个需要单独观察的分支：restore_vm() 成功后， start_vm() 在 app_snapshot_restore 为 true 时立即返回，不执行后面的 10 秒 VsockServerReady 等待；create_sandbox() 随即尝试 connect_agent()（sb.rs:874-911,472-484）。因此 app restore 的可见失败 可能首先表现为 Unix socket connect/CONNECT handshake，而不是 ready event timeout。

D.6 snapshot、pause-to-snapshot、resume 与 rollback

场景 控制路径 状态/数据边界
在线 create snapshot VmPause → VmSnapshot → VmResume 原 VM 对象保留（sb.rs:1325-1335）
v0.7.1 pause-to-snapshot VmPauseToSnapshot disconnect agent，写 snapshot 后删除 MicroVM，等 VmShutdown，再写 metadata（sb.rs:1365-1435）
v0.7.1 resume Master 重新 create from snapshot legacy Task::Resume 明确返回错误（sb.rs:1346-1349,1459-1462）
rollback VmDelete → drain stale events → VmResumeFromSnapshot 原 VMM thread 保留，VM 对象重建；随后重连 agent 与 container I/O（sb.rs:1475-1580）

rollback 显式 drain VmDelete 留下的 VmShutdown，否则新 monitor 可能把旧事件 误判为新 VM 退出（sb.rs:1504-1519）。这说明同步 API response 与异步 NotifyEvent 必须按各自生命周期消费，不能合并理解。

D.7 TAP fd 如何进入 VMM

NetConfig 类型还支持 fds、MTU 与多队列；但当前 CubeShim add_nets()/restore 实际填写的是 id、TAP name、MAC 与限速，其余保持默认。VMM DeviceManager 创建 virtio-net 时把 sandbox_id 交给 Net::new()（ hypervisor/vmm/src/device_manager.rs:2437-2463）。Net::new() 调 open_tap()；单 RX queue 且有 TAP name/sandbox id 时，先走 pool fast path （hypervisor/virtio-devices/src/net.rs:516-556、 hypervisor/net_util/src/open_tap.rs:63-105）。

fast path 连接 /data/cubelet/cubetap.sock（或 CUBE_TAP_SERV_PATH），发送 TAP name + sandbox id，请求通过 SCM_RIGHTS 取得 fd；Tap 把它标为 donated（hypervisor/net_util/src/tap.rs:198-228）。失败才回退到 Tap::open_named()。因此：

  • CubeShim 不直接持有 TAP fd；
  • cube.sock 不传 TAP fd；
  • cubetap.sock 只交付 host TAP backend，不承载 guest 网络帧。

D.8 virtio-net RX/TX 热路径

每个 RX/TX queue pair 有独立 epoll worker。四个最重要的事件是：

  • RX_QUEUE_EVENT：guest 提供了可写 RX descriptor；
  • TX_QUEUE_EVENT：guest 把待发送 frame 放进 TX queue；
  • RX_TAP_EVENT：host TAP 上有 frame 可读；
  • TX_TAP_EVENT：之前 EAGAIN 的 TAP 重新可写。

NetEpollHandler 的事件与 signal 路径见 hypervisor/virtio-devices/src/net.rs:141-299；真正搬运由 TxVirtio::process_desc_chain() 对 TAP writev()、 RxVirtio::process_desc_chain() 对 TAP readv() 完成（ hypervisor/net_util/src/queue_pair.rs:44-176,194-306）。完成后更新 used ring， 必要时经 VirtioInterrupt 通知 guest。

D.9 container stdio：legacy ttrpc 与可选 passfd

v0.7.1 新增了一条可选 stdio fast path，但它仍不是 VMM control API：

  1. 只有 annotation cube.use_passfd_io=true、不是 app snapshot create、且 stdout/stderr 非空才启用；默认值为 false（ CubeShim/shim/src/sandbox/config.rs:79-105,185-190、 CubeShim/shim/src/container/mod.rs:559-571）。
  2. CubeShim 打开 containerd 提供的 stdin/stdout/stderr 路径，连接 cube.sock，一次 sendmsg() 发送 passfd 1027 <labels>\n 和最多三个 SCM_RIGHTS fd（common/utils.rs:562-681）。
  3. VsockMuxer 校验 Unix peer 与 VMM 同 UID，只接受 FIFO/socket，设置 O_NONBLOCK；批次中任一 fd 无效则整批拒绝（muxer.rs:495-572,600-667）。
  4. 每个 fd 被包装成 PassFdStream，成为一条到 guest 端口 1027 的 vsock backend；数据直接读写 fd，不再经过 host UnixStream payload（ hypervisor/virtio-devices/src/vsock/unix/stream.rs:1-65,108-142）。
  5. guest agent 的 AF_VSOCK listener 只接受 CID_HOST，按 VMM 回传的动态 local port 配对；等待 5 秒后过期（agent/src/passfd_io.rs:13-18,84-195）。
  6. create/exec 的 ttrpc 请求只携带三个 port；create-from-snapshot 在 agent 的 do_create_container() restore 分支重绑已有 process，原地 rollback/resume 则由 ReconnectContainerIO 重建 stdio stream（container/mod.rs:573-657、 agent/src/rpc.rs:150-215,471-496）。

当前部署边界：在该 tag 的 Cubelet 源码中未找到 cube.use_passfd_io 的设置方。因此这里能证明“代码支持 opt-in”，不能证明 标准 Cubelet 路径默认启用。未启用时仍使用独立 ttrpc/vsock log-forward 连接。

D.10 block、rootfs 与 virtio-fs 不走这些 socket 的数据面

rootfs/agent image、disk、fs 的配置随 VmCreate/VmRestore 进入 VMM； 设备激活后，steady-state 数据不再经过 VMM_SERVICE 或 chapi：

  • virtio-block worker 从 descriptor 解析请求，向 async disk backend 提交并在 completion 后更新 used ring（hypervisor/virtio-devices/src/block.rs:180-343）；
  • Block::activate() 为每个 queue 创建 BlockEpollHandler 线程 （block.rs:761-833）；
  • native virtio-fs 由设备 backend/worker 服务；只有明确配置 vhost-user socket 时才存在另一条外部 backend socket，这不等于 CubeShim↔VMM control socket （hypervisor/vmm/src/device_manager.rs:2588-2677、 hypervisor/virtio-devices/src/fs.rs:614-660）。

E. 失败与兼容边界

观察 首先检查 能排除什么
ApiRequest 调用一直不返回 VMM control loop、eventfd、response sender 不能先归因于 chapi socket；常规路径没走它
chapi connect/HTTP 失败 /run/vc/vm/<id>/chapi listener 与 HTTP thread 不等于进程内 VMM_SERVICE 已失败
Recv len invalid:0 / CONNECT 无 OK cube.sock listener、VsockMuxer、guest agent port 1024 不等于 TAP/virtio-net 数据面失败
VsockServerReady timeout guest SysCtrl write、通知 channel、事件顺序 VmBoot response 成功不能证明 ready
TAP pool 请求失败但 VM 仍继续 cubetap.sock 与随后 slow path fast path 失败不等于最终没有 TAP
guest 有网卡但网络不通 TAP RX/TX、CubeVS/CNI、guest interface/route/ARP 不能只凭 PCI 枚举认定网络闭环
stdio 仍走 ttrpc annotation、stdout/stderr、app snapshot create passfd 源码存在不代表已启用
restore 后 stdio 断开 create-from-snapshot 的 do_create_container 分支；原地 rollback 的 set_client() / ReconnectContainerIO 旧 passfd fd 不会自动跨 VM 重建
block I/O 慢或失败 virtqueue、async backend、rate limiter、后端文件 不应先检查 cube.sock payload

关键超时并不统一：cold boot ready 等待 10 秒，CreateSandboxRequest 使用 25 秒 ttrpc context，passfd host 连接有 10 秒上限、guest stream 等待 5 秒； 而 VMM_SERVICE::send_request() 与 connect_agent() 的 connect/read 本层没有 统一 timeout。诊断时必须记录卡在哪一层，不能笼统写“socket timeout”。

F. 优点与代价

  • 工程判断——进程内控制的收益：少一次序列化与进程切换，直接复用 Rust 类型；代价是 VMM 卡死会同步阻塞 shim，且全局单实例服务不适合无改造扩展为 同进程多 VMM。
  • 工程判断——HTTP 旁路的收益：外部 snapshot 工具无需持有 wrapper；代价 是出现第二个控制入口，权限、错误和观测必须与主通道分别检查。
  • 工程判断——TAP pool 的收益：把 netlink/TUN 初始化移出启动热路径；代价 是增加 cubetap.sock、fd 所有权与 fast/slow fallback 两套故障分支。
  • 工程判断——passfd 的收益：container stdio payload 少经过一层 UnixStream 转发；代价是新增 fd 校验、动态 port 配对、timeout、restore reconnect 与 backpressure 语义。本报告没有运行数据，不能宣称性能提升幅度。

G. 失败、反例与错误矩阵

  1. 反例：仓库有独立 hypervisor binary 和 HTTP API。 这不能推出 CubeShim 常规 create/start 走外部进程；固定版本源码显示 wrapper 直接调用库与 VMM_SERVICE。
  2. 反例：NetConfig.fds 与 Net::from_tap_fds() 存在。 当前 CubeShim add_nets/restore 路径传 TAP name，不填该 fd 数组；产品主链的 TAP fd 来自 VMM 内的 pool lookup。
  3. 反例：cube.sock 是 Unix socket。 guest agent 并不 bind 这个文件； 它监听 AF_VSOCK，Unix socket 是 host muxer 的入口。
  4. 反例：passfd 代码位于 vsock muxer。 它传的是 container stdio FIFO/socket，不是 TAP fd，也不改变 VM control transport。
  5. 反例：VmRestore 返回成功。 app snapshot restore 分支可能尚未消费 VsockServerReady；后续 agent handshake 仍可能失败。

I. 架构边界与未确认项

控制 channel、chapi、vsock muxer、TAP 与 virtio-net worker 本身使用共享实现。 已确认的架构分歧主要在外围：

  • wrapper seccomp 在 x86_64 放行 SYS_mkdir，ARM64 放行 SYS_mkdirat （cube_hypervisor.rs:79-87）；
  • guest cmdline 在 ARM64 使用 console=ttyAMA0,115200，x86_64 追加 no_timer_check/noreplace-smp 并使用 hvc0（ CubeShim/shim/src/hypervisor/config.rs:95-117）；
  • virtio used-ring 通知下游分别落到 x86 APIC/IOAPIC/MSI 或 ARM GIC/MSI； 本文没有把这层差异误写成 CubeShim transport 差异。

尚未确认：生产环境是否开启 passfd；chapi socket 的部署权限/SELinux 策略； 不同架构上 pause/restore 后第一包与 stdio reconnect 的运行稳定性；各 timeout 在真实负载下是否合理。它们需要单独、明确授权的运行验证，不能从源码存在性 推断。
