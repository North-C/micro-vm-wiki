    CubeSandbox Virtio 中断注入函数级链路

    本文承接 中断与事件通知链路，沿 VirtioPciDevice → InterruptManager → GIC/IOAPIC → KVM irqfd 做函数级 trace，并嵌入关键源码片段。

    目标：回答两个问题——guest 写 queue notify 后如何唤醒 VMM 设备线程；设备完成工作后如何通过 MSI-X、GSI routing 和 irqfd 把中断送回 guest。

    源码基线：当前仓库工作树，VMM 在 hypervisor/ 子目录（Cloud Hypervisor 派生）。

    配套专题：snapshot/restore 链路见 中断状态恢复链路。

    0. 术语与背景

    读后面源码前，先把这些反复出现的术语一次性讲清。它们是理解中断注入的两条方向链的钥匙。

    两条方向链

    virtio 中断机制本质是两个方向相反的事件流，都建立在 Linux eventfd（一个可被读写的轻量事件 fd，写一次 = signal 一次）之上：

    flowchart LR subgraph GH["guest → host（通知有新工作）"] G1["guest 写 notification BAR"] --> K1["KVM ioeventfd"] --> E1["host queue eventfd 被唤醒"] end subgraph HG["host → guest（工作完成，注入中断）"] E2["host 写 irqfd"] --> K2["KVM 按 GSI routing"] --> G2["guest 收到 MSI / legacy 中断"] end
    机制 方向 触发方式 用途
    ioeventfd guest → host guest 写一个特定 MMIO/PIO 地址，KVM 不退出到 VMM 的 MMIO handler，直接 signal 一个 eventfd virtio queue notify（kick）
    irqfd host → guest host（或设备 worker）写一个 eventfd，KVM 按 GSI routing 把它转成一次 guest 中断注入 virtio 完成通知（中断回送）

    关键点：两者都让数据面绕开 VMM 线程的 syscall 往返——这是 virtio 高吞吐的基础（详见 性能设计依据 §5）。

    GSI 与 routing table

    • GSI（Global System Interrupt）：KVM 的全局中断号空间。每个 irqfd 绑定到一个 GSI。
    • GSI routing table：KVM 维护的"GSI → 真实中断源"映射表，由 VMM 用 KVM_SET_GSI_ROUTING 一次性下发。一个 GSI 可以映射成 MSI（带地址+数据的 memory-write 中断）或 legacy IRQ（接到 IOAPIC pin / GIC IRQ）。
    • 所以 irqfd 只是"写 eventfd"，真正变成什么中断由 routing table 决定。

    MSI / MSI-X（PCI 中断通知机制）

    传统 PCI 用物理引脚中断（INTx）：共享、电平触发、需要 IOAPIC/GIC 的 pin。现代 PCI 设备改用 MSI / MSI-X——设备"向一个特定地址写一段特定数据"就等于发一次中断（memory write，不走引脚）：

    项 MSI MSI-X
    向量数 1 个（或多向量但共享） 每个向量一个独立 entry
    表结构 寄存器配置 MSI-X Table：每 entry = msg_addr_lo + msg_addr_hi + msg_data + vector_ctl（mask 位）
    掩码粒度 全局 每 entry 独立 mask
    pending 记录 无 PBA（Pending Bit Array）：vector 被 mask 时不丢事件，记 pending；unmask 后补注

    virtio-pci 设备用 MSI-X：每个 virtqueue 分配一个 vector，设备完成该 queue 的工作后写对应 vector 的 irqfd。

    Legacy irqfd vs MSI

    • MSI 路径（virtio-pci 走这条）：每 vector 一个 GSI，routing entry 是 KVM_IRQ_ROUTING_MSI，KVM 直接按 address/data 注入 MSI。
    • Legacy 路径（serial、IOAPIC/GIC 自身、老设备走这条）：用 LegacyUserspaceInterruptManager，绑到 IOAPIC pin 或 GIC legacy IRQ，routing entry 是 KVM_IRQ_ROUTING_IRQCHIP。本文称"legacy irqfd"即指这条引脚式中断路径，与按向量的 MSI 相对。

    InterruptSourceGroup / InterruptRoute

    Cloud Hypervisor 抽象（CubeSandbox 继承），把设备和 KVM 细节隔开：

    • InterruptSourceGroup：一组中断源（如某 PCI 设备的全部 MSI-X vector）。提供 update()（配置路由）、enable()（注册 irqfd）、trigger(index)（触发某 vector）、notifier(index)（拿 eventfd 给后端）。
    • InterruptRoute：group 里的一条 = 一个 GSI + 一个 eventfd（+ registered 标志）。trigger() 就是 irq_fd.write(1)。
    • 设备不直接碰 KVM，只通过 group 抽象。

    GIC / ITS 与 IOAPIC

    • x86_64：IOAPIC（I/O 中断，pin + redirection table，处理 level/EOI）+ local APIC（每 CPU）。
    • aarch64：GIC（通用中断控制器）+ ITS（Interrupt Translation Service，把 device ID + event ID 翻译成 LPI，是 ARM 上 MSI 的载体）。

    1. 核心结论

    CubeSandbox 的 virtio PCI 中断链分两个方向：

    • guest → host：写 notification BAR → VirtioPciDevice::ioeventfds() 暴露每 queue 的 eventfd → DeviceManager 注册成 KVM ioeventfd。
    • host → guest：设备 worker 调 VirtioInterruptMsix::trigger() → InterruptRoute::trigger() 写 irqfd。

    关键时序：route 和 irqfd 不是触发时临时创建的。在 guest 配置 MSI-X table / message control 阶段，MsixConfig 就调 InterruptSourceGroup::update() 建好 KVM GSI routing 并 enable irqfd。运行期触发只写已经注册好的 fd。

    2. 总体函数链

    flowchart TB subgraph 创建期["创建期（VM 启动 / guest 配置前）"] Create["DeviceManager::add_virtio_pci_device"] VpdNew["VirtioPciDevice::new"] Group["MsiInterruptManager::create_group"] Msix["MsixConfig::new"] Ioevt["VirtioPciDevice::ioeventfds"] RegIo["KvmVm::register_ioevent"] end subgraph 配置期["配置期（guest 写 MSI-X table）"] GuestCfg["guest writes MSI-X config/table"] Update["MsiInterruptGroup::update"] Route["KvmVm::make_routing_entry"] SetRoute["KvmVm::set_gsi_routing"] Enable["InterruptRoute::enable"] end subgraph 运行期["运行期（每次 I/O 完成）"] Worker["virtio worker"] Trigger["VirtioInterruptMsix::trigger"] Irqfd["InterruptRoute::trigger"] KVM["KVM irqfd -> guest interrupt"] end Create --> VpdNew --> Group --> Msix Create --> Ioevt --> RegIo GuestCfg --> Update --> Route --> SetRoute Update --> Enable Worker --> Trigger --> Irqfd --> KVM

    三个阶段清晰分层：创建期分配资源 → 配置期建路由 → 运行期只写 fd。后面逐段展开。

    3. DeviceManager 创建中断基础设施

    DeviceManager 在 new() 阶段就要把中断"地基"搭好。这里有个容易被忽略的依赖顺序，源码注释直接点明：

    // hypervisor/vmm/src/device_manager.rs:1048
// First we create the MSI interrupt manager, the legacy one is created
// later, after the IOAPIC device creation.
// The reason we create the MSI one first is because the IOAPIC needs it,
// and then the legacy interrupt manager needs an IOAPIC. So we're
// handling a linear dependency chain:
// msi_interrupt_manager <- IOAPIC <- legacy_interrupt_manager.
let msi_interrupt_manager: Arc<dyn InterruptManager<GroupConfig = MsiIrqGroupConfig>> =
    Arc::new(MsiInterruptManager::new(
        Arc::clone(&address_manager.allocator),
        vm,
    ));

    为什么是这个顺序？ 因为 MSI manager 是更底层的资源分配器（分配 GSI、建 routing），而 IOAPIC/GIC 控制器自身发中断时也要走 MSI（它对外暴露的也是 MSI group），所以 IOAPIC 反而依赖 MSI manager；而 legacy manager 又依赖 IOAPIC。链是 MSI ← IOAPIC ← legacy，所以 MSI 必须最先建。

    随后 create_devices() 里，先建中断控制器，再用它构造 legacy manager：

    // hypervisor/vmm/src/device_manager.rs:1226
let interrupt_controller = self.add_interrupt_controller()?;

// Now we can create the legacy interrupt manager, which needs the freshly
// formed IOAPIC device.
let legacy_interrupt_manager = Arc::new(LegacyUserspaceInterruptManager::new(
    Arc::clone(&interrupt_controller),
));

    add_interrupt_controller() 按架构分流，但两者都把刚建好的 msi_interrupt_manager 传给控制器：

    // hypervisor/vmm/src/device_manager.rs:1435  (aarch64)
let interrupt_controller = Arc::new(Mutex::new(
    gic::Gic::new(self.config.lock().unwrap().cpus.boot_vcpus,
                  Arc::clone(&self.msi_interrupt_manager))?,
));
// 注释：aarch64 的 "interrupt_controller" 只是提供中断投递服务的 Gic 对象，
//       不是真正的 GIC device，因此不插入 device tree。

    // hypervisor/vmm/src/device_manager.rs:1462  (x86_64)
let interrupt_controller = Arc::new(Mutex::new(
    ioapic::Ioapic::new(id, APIC_START, Arc::clone(&self.msi_interrupt_manager))?,
));

    Gic::new() 自己也会从同一个 MSI manager 创建一个 legacy IRQ group（base 为 IRQ_LEGACY_BASE），见 hypervisor/devices/src/gic.rs:40——这就是上节说的"legacy irqfd"来源。

    本节要点：中断基础设施是一个三层依赖链（MSI manager → IOAPIC/GIC → legacy manager），MSI manager 先建、由它统一分配 GSI。virtio-pci 的 MSI-X 走 msi_interrupt_manager；serial 等老设备走 legacy_interrupt_manager。

    4. virtio-pci 包装与 MSI-X group

    DeviceManager 收集完 MetaVirtioDevice，对每个 virtio 设备调 add_virtio_pci_device()（device_manager.rs:1373）。它分配 PCI BDF、计算 msix_num = queue_count + 1（device_manager.rs:3591/3615）——多出来的 1 个 vector 给 config change（配置变更通知）。

    核心在 VirtioPciDevice::new()，它一次完成三件事：

    // hypervisor/virtio-devices/src/transport/pci_device.rs:399
// (1) 为每个 queue 建一个 eventfd（用于 ioeventfd 通知）
let mut queue_evts = Vec::new();
for _ in locked_device.queue_max_sizes().iter() {
    queue_evts.push(EventFd::new(EFD_NONBLOCK)?)
}

// (2) 用 MSI manager 创建中断源组：count = msix_num（queue 数 + 1）
let interrupt_source_group = interrupt_manager.create_group(MsiIrqGroupConfig {
    base: 0,
    count: msix_num as InterruptIndex,
})?;

// (3) 建 MsixConfig（MSI-X table / PBA / mask 状态），把 group 传进去
let msix_config = Arc::new(Mutex::new(MsixConfig::new(
    msix_num,
    interrupt_source_group.clone(),
    pci_device_bdf,        // devid，用于 routing
)));

    最后把 MsixConfig、config vector、queue vectors、interrupt group 绑成运行期触发器 VirtioInterruptMsix（pci_device.rs:496）：

    // hypervisor/virtio-devices/src/transport/pci_device.rs:496
virtio_pci_device.virtio_interrupt = Some(Arc::new(VirtioInterruptMsix::new(
    msix_config.clone(),
    virtio_pci_device.common_config.msix_config.clone(),  // config vector
    virtio_pci_device.common_config.msix_queues.clone(),  // 每 queue 的 vector
    virtio_pci_device.interrupt_source_group.clone(),
)));

    此刻还没有 KVM route。 create_group() 只分配了 GSI 和 eventfd（见 §5），MSI 的 address/data 要等 guest 写 MSI-X table（§8）才确定。

    5. MsiInterruptManager 分配 GSI 与 irqfd

    MsiInterruptManager::new() 建一个跨 PCI 设备共享的 gsi_msi_routes（interrupt.rs:251）——注释说明这是为了维护完整的 GSI 列表，避免一个设备覆盖另一个设备的 routing 设置。

    create_group() 为 group 里每个 index 建一条 InterruptRoute，每条独立分配一个 GSI 和一个 eventfd（interrupt.rs:282）。InterruptRoute 的定义是本链路最小的积木：

    // hypervisor/vmm/src/interrupt.rs:23
struct InterruptRoute {
    gsi: u32,
    irq_fd: EventFd,
    registered: AtomicBool,
}

impl InterruptRoute {
    pub fn new(allocator: &mut SystemAllocator) -> Result<Self> {
        let irq_fd = EventFd::new(libc::EFD_NONBLOCK)?;
        let gsi = allocator.allocate_gsi()     // 从 SystemAllocator 分配全局 GSI
            .ok_or_else(|| ... "Failed allocating new GSI")?;
        Ok(InterruptRoute { gsi, irq_fd, registered: AtomicBool::new(false) })
    }

    pub fn enable(&self, vm: &Arc<dyn hypervisor::Vm>) -> Result<()> {
        if !self.registered.load(Ordering::Acquire) {
            vm.register_irqfd(&self.irq_fd, self.gsi)?;   // 绑定 eventfd ↔ GSI
            self.registered.store(true, Ordering::Release);
        }
        Ok(())
    }

    pub fn trigger(&self) -> Result<()> { self.irq_fd.write(1) }  // 运行期注入 = 写 fd
}

    本节要点：创建期只做"分配"——分 GSI、建 eventfd。enable()（注册 irqfd）和 update()（写 routing）要等 guest 配置 MSI-X 才调。运行期 trigger() 就是 write(1)，不碰 KVM。

    6. guest → host：ioeventfd 注册

    VirtioPciDevice::ioeventfds(base_addr) 按 notification BAR base 为每个 queue eventfd 算出地址：

    // hypervisor/virtio-devices/src/transport/pci_device.rs:756
fn ioeventfds(&self, base_addr: u64) -> Vec<(&EventFd, u64)> {
    let notify_base = base_addr + NOTIFICATION_BAR_OFFSET;
    self.queue_evts().iter().enumerate().map(|(i, event)| {
        (event, notify_base + i as u64 * u64::from(NOTIFY_OFF_MULTIPLIER))
    }).collect()
}

    add_virtio_pci_device() 完成设备添加后，遍历 ioeventfds() 调 vm.register_ioevent(event, &io_addr, None)（device_manager.rs:3707）。KVM wrapper 把地址转成 IoEventAddress 再下沉（hypervisor/src/kvm/mod.rs:470）。

    效果：guest driver 写 notification BAR 时，KVM 不退出到普通 MMIO handler，直接 signal 对应 queue eventfd，VMM 设备线程被唤醒——这就是 §0 的 ioeventfd 方向。

    7. virtio common config 选择 vector

    guest 在 virtio common config 里告诉设备"每个 queue 用哪个 MSI-X vector"：

    • offset 0x10：config MSI-X vector（配置变更用哪个 vector）；
    • offset 0x1a：当前 selected queue 的 MSI-X vector（pci_common_config.rs:158/175）。

    写 0x10 只更新 config vector；写 0x1a 只更新 msix_queues[queue_select]。这些字段决定 §11 trigger() 时选哪个 vector——它们本身不建 KVM route，真正的 address/data 来自 MSI-X table。

    8. MSI-X table 与 message control 建立 routing

    这一段是"配置期"的核心：guest 配置 MSI-X 时，VMM 据此建好 KVM routing。两个入口：

    (a) 写 message control（enable / function mask）：PciConfiguration::write_config_register() 触发 MsixConfig::set_msg_ctl()（configuration.rs:887），它更新 masked/enabled，并在使能变化时重建路由：

    // hypervisor/pci/src/msix.rs:156
pub fn set_msg_ctl(&mut self, reg: u16) {
    self.masked  = ((reg >> FUNCTION_MASK_BIT) & 1) == 1;
    self.enabled = ((reg >> MSIX_ENABLE_BIT)  & 1) == 1;

    if old_masked != self.masked || old_enabled != self.enabled {
        if self.enabled && !self.masked {
            for (idx, table_entry) in self.table_entries.iter().enumerate() {
                let config = MsiIrqSourceConfig {                  // 用 table 里的 address/data
                    high_addr: table_entry.msg_addr_hi,
                    low_addr:  table_entry.msg_addr_lo,
                    data:      table_entry.msg_data,
                    devid:     self.devid,
                };
                self.interrupt_source_group.update(                // 建/更新 route
                    idx as InterruptIndex,
                    InterruptSourceConfig::MsiIrq(config),
                    table_entry.masked())?;
            }
        } else if old_enabled || !old_masked {
            self.interrupt_source_group.disable()?;                 // 禁用 irqfd
        }
    }
}

    (b) 写 MSI-X table entry：MsixConfig::write_table() 更新 address/data/vector_ctl，并在"已使能、未全局 mask、该 entry 未 mask"时重建该 entry 的 route（msix.rs:251/301）：

    // hypervisor/pci/src/msix.rs:305
if self.enabled && !self.masked && !table_entry.masked() {
    let config = MsiIrqSourceConfig { /* 用新 address/data/devid */ };
    self.interrupt_source_group.update(
        index as InterruptIndex,
        InterruptSourceConfig::MsiIrq(config),
        table_entry.masked())?;
}

    机制结论：MSI-X routing 完全由 guest 配置驱动。设备运行期触发中断时，不再重新计算 address/data——只写 fd。

    9. MsiInterruptGroup 更新 KVM route

    §8 调用的 update() 落到 MsiInterruptGroup::update()（interrupt.rs:168）：按 index 找 InterruptRoute，调 vm.make_routing_entry(gsi, &config) 生成 routing entry；masked 则 disable irqfd，否则先 route.enable() 注册 irqfd，再把 route 写进共享 gsi_msi_routes 并 set_gsi_routes()：

    // hypervisor/vmm/src/interrupt.rs:100
fn set_gsi_routes(&self, routes: &HashMap<u32, RoutingEntry>) -> Result<()> {
    let mut entry_vec: Vec<IrqRoutingEntry> = Vec::new();
    for (_, entry) in routes.iter() {
        if entry.masked { continue; }            // masked 的 route 不下发
        entry_vec.push(entry.route);
    }
    self.vm.set_gsi_routing(&entry_vec)          // 一次性 KVM_SET_GSI_ROUTING
}

    注意 set_gsi_routes 会过滤掉 masked route，只把未 mask 的下发给 KVM。

    10. KVM routing entry 与 irqfd

    KvmVm::make_routing_entry() 把 MsiIrq config 转成 KVM_IRQ_ROUTING_MSI（kvm/mod.rs:507），写入 address/data；ARM64 还要处理 devid：

    // hypervisor/hypervisor/src/kvm/mod.rs:507
InterruptSourceConfig::MsiIrq(cfg) => {
    let mut kvm_route = kvm_irq_routing_entry {
        gsi, type_: KVM_IRQ_ROUTING_MSI, ..Default::default()
    };
    kvm_route.u.msi.address_lo = cfg.low_addr;
    kvm_route.u.msi.address_hi = cfg.high_addr;
    kvm_route.u.msi.data       = cfg.data;

    if self.check_extension(Cap::MsiDevid) {
        // aarch64 对 devid 有 ≤65536 限制，BDF 的 segment 在高 16 位会超范围，
        // 所以用 (devid & 0x00ff_0000) >> 8 | devid & 0xff 重编码成合法 devid
        let modified_devid = (cfg.devid & 0x00ff_0000) >> 8 | cfg.devid & 0xff;
        kvm_route.flags = KVM_MSI_VALID_DEVID;
        kvm_route.u.msi.__bindgen_anon_1.devid = modified_devid;
    }
    kvm_route.into()
}

    为什么 ARM64 要改写 devid？ ARM ITS 靠 (device ID, event ID) 定位中断，而 PCI BDF 的高 16 位是 segment，会超过 ITS 的 u16 devid 上限。CubeSandbox 只支持单 segment 多 bus，于是把 bus 位用 segment 低 8 位替换，凑出合法且唯一的 devid。

    set_gsi_routing()（kvm/mod.rs:561）构造 kvm_irq_routing 复制每个 entry，调 VM fd 的 set_gsi_routing()；InterruptRoute::enable() 调 vm.register_irqfd(&irq_fd, gsi)（interrupt.rs:42 / kvm/mod.rs:423）。

    到这里 KVM 就明白了：某 irqfd 被写时，对应 GSI 按当前 routing 变成 MSI（或 legacy IRQ）注入 guest。

    11. 运行时触发：VirtioInterruptMsix 到 irqfd

    运行期是整条链最短的一段。设备完成队列工作后调 VirtioInterrupt::trigger(Queue(index))（virtio-net 的 signal_used_queue() 即如此，net.rs:183）。VirtioInterruptMsix::trigger()：

    // hypervisor/virtio-devices/src/transport/pci_device.rs:795
fn trigger(&self, int_type: VirtioInterruptType) -> std::result::Result<(), std::io::Error> {
    // (1) 按 Queue(index) 或 Config 选 vector
    let vector = match int_type {
        VirtioInterruptType::Config => self.config_vector.load(Ordering::Acquire),
        VirtioInterruptType::Queue(i) => self.queues_vectors.lock().unwrap()[i as usize],
    };
    if vector == VIRTQ_MSI_NO_VECTOR { return Ok(()); }   // guest 还没配 vector

    let config = &mut self.msix_config.lock().unwrap();
    let entry = &config.table_entries[vector as usize];
    // (2) 若被 mask（全局或单 vector），不注入，只记 PBA pending
    if config.masked() || entry.masked() {
        config.set_pba_bit(vector, false);
        return Ok(());
    }
    // (3) 未 mask：触发对应 vector
    self.interrupt_source_group.trigger(vector as InterruptIndex)
}

    MsiInterruptGroup::trigger() 找 InterruptRoute 调 route.trigger()，而后者就是（interrupt.rs:74）：

    pub fn trigger(&self) -> Result<()> { self.irq_fd.write(1) }

    整条运行期注入路径的最短核心：设备不直接操作 IOAPIC/GIC，也不直接调 KVM ioctl——只写一个已经在配置期注册好的 irqfd。这就是"数据面离开 VMM 线程"在中断侧的体现。

    12. PBA 与 masked vector

    上节看到 vector 被 mask 时不注入而记 PBA。这是 MSI-X 规范要求"不丢事件"的实现：

    • mask 时：MsixConfig::set_pba_bit(vector, false) 置 pending（pci_device.rs:808 / msix.rs:383）。
    • guest 把 entry 从 masked 改 unmasked 时，write_table() 检测到 PBA bit 置位，调 inject_msix_and_clear_pba()（msix.rs:330）补注并清 PBA：
    // hypervisor/pci/src/msix.rs:407
fn inject_msix_and_clear_pba(&mut self, vector: usize) {
    match self.interrupt_source_group.trigger(vector as InterruptIndex) {
        Ok(_) => debug!("MSI-X injected on vector control flip"),
        Err(e) => error!("failed to inject MSI-X: {}", e),
    }
    self.set_pba_bit(vector as u16, true);   // 清 pending
}

    这解释了为什么"设备触发"有时不立即变成 guest 中断——MSI-X mask/PBA 是中间状态，unmask 时才补。

    13. legacy IRQ 与 IOAPIC/GIC

    走 LegacyUserspaceInterruptManager 的设备（serial 等）用引脚式中断，绑到 IOAPIC/GIC 的固定 IRQ（interrupt.rs:196/267）。LegacyUserspaceInterruptGroup::trigger() 调 controller 的 service_irq()（interrupt.rs:207）。

    • x86_64：Ioapic::service_irq() 调自身 MSI group trigger()，level interrupt 时设 Remote IRR 等 EOI 清除（ioapic.rs:378）；vCPU run loop 收到 VmExit::IoapicEoi(vector) 时调 interrupt_controller.end_of_interrupt(vector)（cpu.rs:1045）。guest 写 IOAPIC redirection table 时 update_entry() 把 entry 转成 MsiIrqSourceConfig 调 update()（ioapic.rs:314）。
    • aarch64：Gic::enable() 先 enable interrupt group，再为 legacy IRQ 写 LegacyIrqSourceConfig route（gic.rs:90）；Gic::service_irq() 直接 interrupt_source_group.trigger(irq)（gic.rs:116）。VM 配置阶段先 Gic::create_default_config(vcpu_count) 建 VGIC，再经 arch::configure_system() 生成 FDT，最后 Gic::enable()（vm.rs:1214/1260）。

    注意：即便 legacy 路径，最终也落到同一个 interrupt_source_group 抽象——这就是为什么 §11 说"设备只通过 group 抽象触发"。

    14. ARM64 与 x86_64 差异

    virtio PCI MSI-X 高层模型两架构共享（vector 选择、MSI-X table、interrupt source group、irqfd 都一样）。差异在底层控制器：

    维度 x86_64 aarch64
    控制器 IOAPIC（MMIO bus 设备，redirection table + Remote IRR + EOI）+ local APIC GICv3 + ITS
    KVM 设备 — KvmGicV3Its（distributor + redistributor + MSI region），FDT 兼容 arm,gic-v3-its（kvm/aarch64/gic/mod.rs:77/154/272）
    MSI devid 直接用 BDF 受 ≤65536 限制，需重编码（kvm/mod.rs:520）
    flowchart LR Common["virtio-pci MSI-X common path"] --> X86["x86_64"] Common --> ARM["aarch64"] X86 --> IOAPIC["IOAPIC redirection + EOI"] X86 --> APIC["APIC MSI address/data"] ARM --> GIC["GICv3 + ITS"] ARM --> Devid["MSI devid rewrite"]

    15. restore 与热插拔边界

    • restore：VirtioPciDevice::restore() 恢复 MSI-X / common config / PCI config / queue（见 virtio-net-fs-restore-chain）。MSI-X restore 用 MsixConfig::set_state()：若 restored state 里 enabled 且未 masked，遍历未 mask entry 调 update() + enable()。完整恢复链路见 中断状态恢复链路。
    • 热插拔：也走 add_virtio_pci_device()（device_manager.rs:4275），运行中添加后照样注册 ioeventfd、挂入 PCI/device tree。

    restore 与 hotplug 的关键不是另造中断路径，而是重新执行 route / ioeventfd / irqfd / queue eventfd 的绑定。

    16. 容易误读的点

    1. InterruptSourceGroup::trigger() ≠ 重新配置中断。配置发生在 update()，触发只写已注册的 eventfd。
    2. virtio common config 的 queue vector 只决定选哪个 vector；真正的 MSI address/data 来自 MSI-X table。
    3. ioeventfd 与 irqfd 方向相反：ioeventfd 是 guest 写地址唤醒 host；irqfd 是 host 写 fd 注入 guest。
    4. IOAPIC/GIC 不是每次 virtio MSI-X 触发都被设备代码直接调用，设备只通过 interrupt group 抽象触发。
    5. ARM64 与 x86_64 的差异不在 trigger()，而在 KVM routing、GIC/ITS、IOAPIC/APIC 与 restore controller state。
