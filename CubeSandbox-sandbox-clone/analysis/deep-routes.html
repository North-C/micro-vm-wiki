1. CubeAPI：route、handler、service、长操作契约

研究目标：理解外部 API 如何被映射成 CubeMaster 操作，以及为什么 snapshot/rollback/delete 要使用长 timeout。

关键源码：

  • CubeAPI/src/routes.rs 中普通 sandbox route 包括 create/list/get/delete/pause/resume/connect，snapshot create/rollback 放入 long sandbox routes：CubeAPI/src/routes.rs。
  • 注释明确 snapshot 创建通过 cubelet.CommitSandbox，rollback 需要等待 Cubelet 恢复 memory + rootfs，因此放入 240 秒预算：CubeAPI/src/routes.rs。
  • AgentHub 也暴露 snapshot、rollback、recover、clone、publish-template 等长操作：CubeAPI/src/routes.rs。

继续深入点：

  • 建立 route -> handler -> service -> CubeMasterClient 映射表。
  • 对所有 long route 标注同步终态条件。
  • 分析错误码、operation ready/terminal 判定和 API timeout 之间的关系。

专题展开：CubeAPI Long Operation Contract 链路。

结论是 long route 只是 HTTP 预算通道；snapshot create/delete/rollback 的真正契约是 CubeMaster 同步返回 READY 终态，AgentHub 另有产品层 operation 流水。

2. CubeMaster：metadata、scheduler、task retry

研究目标：理解 CubeMaster 如何把产品请求变成节点选择和 Cubelet gRPC 调用。

关键源码：

  • scheduler.Select() 先 prefilter，再 filter，再 score，最后 LeastRandomSelect()：CubeMaster/pkg/scheduler/schedule.go。
  • 失败时，在非 template-locality 场景可走 backoff select。
  • parallelRunFilters() 并行运行所有 filter，并只保留命中所有 filter 的节点：CubeMaster/pkg/scheduler/schedule.go。
  • CubeMaster 调 Cubelet 的动作集中在 CubeMaster/pkg/cubelet/actions.go：CubeMaster/pkg/cubelet/actions.go。
  • 这些动作包括 Create、Destroy、AppSnapshot、CommitSandbox、RollbackSandbox、Exec、Update 等。
  • handleTask() 根据错误码决定重试或 loop retry：CubeMaster/pkg/task/handlers.go。

专题展开：CubeMaster Scheduler 与 Task Retry 链路。

继续深入点：

  • 展开 scheduler plugin：template locality、resource、node health、snapshot locality。
  • 追踪 snapshot/template reconciler 如何处理物理副本。

专题展开：CubeMaster Snapshot Job Contract 链路。

结论是 snapshot create/rollback/delete 走 templatecenter job 表和同步 READY/FAILED 闸门，物理 rootfs/memory/meta 以 Cubelet local catalog 为权威。

专题展开：CubeMaster 缓存一致性边界链路。

结论是 node/metric/template/snapshot cache 属于调度输入，sandbox proxy/list cache 属于运行时路由输入，instancecache 属于 DB/Redis 状态镜像。

3. Cubelet：CubeboxMgr、workflow、containerd integration

研究目标：理解节点上的创建请求如何被 workflow engine 执行。

关键源码：

  • Cubelet service.Create() 校验参数，设置默认值，创建 workflow.CreateContext，判断 runtime 类型：Cubelet/services/cubebox/service.go。
  • 随后它调用 s.engine.Create(ctx, createInfo) 或 other runtime。
  • SetRunCubeSandboxRequestDefaultValue() 会设置 instance type、image storage media 默认值、network type 默认值为 tap：Cubelet/services/cubebox/service.go。
  • workflow.Engine 持有 workflow map 和 cleanup flow，可限制 flow 并发：Cubelet/plugins/workflow/engine.go。
  • Cubelet 本体持有 master client、controller map、CRI image service、run template manager、network-agent client：Cubelet/pkg/cubelet/cubelet.go。

继续深入点：

  • 画出 engine.Create 的 flow/step/action 列表。
  • 追踪 containerd namespace、task、shim 创建。
  • 分析创建失败时 cleanup flow 如何补偿。

4. CubeShim：shim v2、sandbox lifecycle、agent ttrpc

研究目标：理解 CubeShim 如何把 containerd shim 请求转成 VM 和 guest agent 请求。

关键源码：

  • SandBox::new() 创建 CubeHypervisor 并保存 ttrpc client、OCI spec、config、containers、state、monitor/OOM handles：CubeShim/shim/src/sandbox/sb.rs。
  • SandBox::init() 从 annotations 构造 Cube config；app snapshot restore 必须有 fresh cube.vm.snapshot.memory_vol_url：CubeShim/shim/src/sandbox/sb.rs。
  • create_sandbox() 先启动 VM、连接 agent，必要时 reset guest，再 hotplug device，最后向 agent 发送 CreateSandboxRequest：CubeShim/shim/src/sandbox/sb.rs。

继续深入点：

  • 找出 shim v2 service entry，与 SandBox 方法建立映射。
  • 追踪 container lifecycle：create/start/exec/kill/remove。
  • 分析 monitor VM、OOM、agent health 的退出语义。

5. CubeHypervisor：API request、device、snapshot/restore

研究目标：理解 CubeHypervisor 与内嵌 cube_hypervisor VMM 的边界。

关键源码：

  • launch_vmm() 设置 runtime seccomp rules，构造 VmmConfig、event notifier，并创建 cube_hypervisor::VmmInstance：CubeShim/shim/src/hypervisor/cube_hypervisor.rs。
  • create_vm()、boot_vm()、snapshot_vm()、restore_vm() 分别发送 VM create、boot、snapshot、restore API request：CubeShim/shim/src/hypervisor/cube_hypervisor.rs。

继续深入点：

  • 对比 hypervisor/ 目录与 Cloud Hypervisor 的模块差异。
  • 分析 device hotplug、fs allow dir、snapshot memory volume 的配置转换。

专题展开：CubeHypervisor API Request 内部调度链路。

结论是常规 CubeHypervisor wrapper 通过 VmmInstance -> VMM_SERVICE -> mpsc + eventfd -> VMM epoll loop 同步分发 ApiRequest。

HTTP Unix socket 是并存控制面，app snapshot 工具路径会用它调用 pause、snapshot、resume；NotifyEvent 是独立异步状态通道。

6. CubeCoW：FFI、ReflinkEngine、crash recovery

研究目标：理解 CubeSandbox 0.3.0 snapshot/clone 的存储基础。

关键源码：

  • CubeCoW 是 Rust library crate，基于 xfs-reflink/FICLONE 提供 thin-provisioned volume 和 O(1) snapshot/clone：cubecow/README.md。
  • Engine trait 提供 create/delete/resize/list volume，create/delete/list snapshot，activate/deactivate，reset node storage，metrics：cubecow/src/engine/mod.rs。
  • Cubelet 通过 RefreshStorageInfoPathsWithEngine() 用 cubecow engine 解析 volume/snapshot device path：Cubelet/storage/cubecow_volume_manager.go。

继续深入点：

  • 追踪 Go wrapper 到 C FFI 到 Rust Engine。
  • 分析 ReflinkEngine 启动扫描如何恢复 in-memory index。
  • 对比 rootfs volume snapshot 与 VM memory volume 的关系。

7. network-agent/CubeVS：TAP、FD passing、eBPF policy

研究目标：理解 CubeSandbox 的网络隔离和端口映射不是 CubeShim 单独完成的。

关键源码：

  • network-agent 负责 TAP 创建、CubeVS 映射、主机端口代理、本地状态持久化和启动恢复：network-agent/docs/ARCHITECTURE.md。
  • Service 接口包括 EnsureNetwork、ReleaseNetwork、ReconcileNetwork、GetNetwork、ListNetworks、Health：network-agent/internal/service/service.go。
  • localService 持有 state store、IP allocator、port allocator、machine device、cube gateway、tap pool、quarantined taps 等组件。
  • 源码依据：network-agent/internal/service/local_service.go。
  • 创建网络时会分配/复用 TAP，配置 port mapping，注册 CubeVS TAP 并保存状态：network-agent/internal/service/local_service.go。

继续深入点：

  • 已完成 中断与事件通知链路，把 API eventfd、NotifyEvent、virtio interrupt 和 TAP fd passing 分层。
  • 已完成 Virtio 中断注入函数级链路，追踪 VirtioPciDevice、MSI-X、InterruptManager、GSI routing、irqfd 和 GIC/IOAPIC。
  • 已完成 网络数据面与中断唤醒链路，把 CubeVS eBPF -> TAP -> virtio-net worker -> guest eth0 串成一条热路径。
  • 分析 CubeVS eBPF map、allow/deny policy、SNAT。
  • 验证 reconcile 如何处理 agent 重启和残留 TAP。

  • 已完成 ARM64 网络观测与取证指南，把 network-agent、CubeShim/VMM、guest agent 和 restore 的成功信号与失败锚点对齐。
  • 已完成 ARM64 网络实测取证模板，把验证矩阵和取证指南落成可填写的实测记录格式。
