    CubeSandbox ARM64 网络实测取证模板

    本文承接 ARM64 网络验证矩阵 和 ARM64 网络观测与取证指南。

    前两篇回答“该验什么”和“应当先看哪里”。

    本文继续把它们落成一份可填写的实测模板。

    源码基线：当前仓库工作树。

    1. 用途

    这份模板不替代源码分析。

    它的用途是让一次 ARM64 网络实测，最终能落成一份结构稳定、证据可回溯的记录。

    建议按五段填写：

    1. host 前置条件
    2. network-agent 与 CubeVS
    3. CubeShim/VMM/virtio-net ready
    4. guest cube-agent 配网
    5. restore 后首包唤醒

    每段都只记录三类信息：

    1. 看到了什么
    2. 这说明了什么
    3. 还不能说明什么

    2. 记录头

    建议每次实测先写清这几个基础字段：

    字段 记录内容
    日期 YYYY-MM-DD HH:MM
    节点架构 arm64/aarch64
    host 内核 版本与关键 config 来源
    guest kernel deploy/aarch64/mvm.config 对应版本
    sandbox 配置 网络类型、端口映射、是否 snapshot/restore
    对照组 是否同时跑了 x86_64
    结论 通过 / 部分通过 / 失败

    3. 第一段：host 前置条件

    应记录的证据

    先记录 network-agent 的基础就绪状态。

    源码里 /readyz 会直接返回 200 ready。

    源码依据：server.go。

    仓库里的 quickcheck.sh 和 cube-diag/check-procs.sh 也都把 /readyz 当成必要条件。

    源码依据：quickcheck.sh，check-procs.sh。

    Agent.md 里已有最小 curl 样例。

    源码依据：Agent.md。

    建议填写模板

    [Host Preconditions]
- /dev/kvm:
- network-agent /healthz:
- network-agent /readyz:
- cubelet/master 相关基础探针:
- 备注:

    解释口径

    /readyz = 200 只能证明 network-agent 进程级 ready。

    它不能证明 TAP、CubeVS、virtio-net 和 guest 配网已经成功。

    4. 第二段：network-agent 与 CubeVS

    应记录的证据

    newTap() 会给出一串阶段日志。

    最关键的是：

    1. network-agent newTap begin
    2. network-agent newTap attach filter done
    3. network-agent newTap ready

    源码依据：netdevice.go。

    registerCubeVSTap() 还会记录：

    network-agent register cubevs tap: sandbox_id=... ifindex=... sandbox_ip=...

    源码依据：local_service.go。

    如果 ARM64 上 CubeVS 或 TC attach 失败，优先关注：

    1. can't load localgw/mvmtap/nodenic
    2. ebpf.NewCollectionWithOptions
    3. tc.Open failed
    4. tcnl.Qdisc.Add failed
    5. tcnl.Filter.Replace failed

    源码依据：bpf_arm64.go，tc.go。

    建议填写模板

    [Network-Agent And CubeVS]
- newTap begin:
- newTap attach filter done:
- newTap ready:
- register cubevs tap:
- CubeVS / tc error text:
- 备注:

    解释口径

    newTap ready 说明 host TAP 资源和 filter attach 基本已经完成。

    它仍不能证明 guest 一定能收到数据包。

    register cubevs tap 说明 control plane 已把 TAP 注册进 CubeVS。

    它仍不能证明实际包路径与策略路径已经走通。

    5. 第三段：CubeShim/VMM/virtio-net ready

    应记录的证据

    CubeShim start_vm() 成功等待到 VsockServerReady 时，会打印：

    vm ready, vsock is listening (notify path)

    源码依据：sb.rs。

    guest agent 启动成功通知 vsock ready 时，也会打印：

    vsock server ready notified at:...

    源码依据：main.rs。

    virtio-net 激活后，设备层会发出：

    virtio-device activated

    源码依据：net.rs。

    建议填写模板

    [VMM Ready]
- vm ready, vsock is listening:
- guest vsock server ready notified:
- virtio-device activated:
- wait_notify fallback / VmShutdown:
- 备注:

    解释口径

    VsockServerReady 说明 guest agent 通路 ready。

    它不能证明 guest 网络已经配好。

    virtio-device activated 说明 virtio-net 已经激活。

    它不能证明 host eBPF 或 guest 路由已正确。

    6. 第四段：guest cube-agent 配网

    应记录的证据

    create_sandbox() 会先打印：

    receive create sandbox

    带 pciPath 的接口在真正配网前会打印：

    wait a pci:...

    源码依据：rpc.rs。

    接口或路由失败时会直接返回：

    1. Failed to update interface: ...
    2. Failed to update routes: ...
    3. Failed to add ARP neighbours: ...

    源码依据：rpc.rs。

    三段都走完后，会打印：

    create sandbox!, config net:...

    源码依据：rpc.rs。

    建议填写模板

    [Guest Agent Networking]
- receive create sandbox:
- wait a pci:
- update interface result:
- update routes result:
- add arp neighbours result:
- create sandbox!, config net:
- 备注:

    解释口径

    wait a pci 成功，说明 guest 侧设备枚举至少到了 agent 可见阶段。

    它不能证明 MAC 匹配和 eth0 重命名已经成功。

    create sandbox!, config net 出现，才更接近“guest 配网已完成”的结论。

    7. 第五段：restore 后首包唤醒

    应记录的证据

    ARM64 restore 时，VMM 会重新创建 VGIC，重建 GICR_TYPER，恢复 gic-v3-its，再 enable 中断路由。
