CubeSandbox CPU / vCPU 资源边界链路

本文承接 运行期控制与 VMM 更新链路、CubeHypervisor API Request 内部调度链路 和 ARM64 与 x86_64 架构差异链路，回答：CubeSandbox 的 CPU/vCPU 资源语义跨了哪几层，哪些是 VMM 级、哪些是平台或容器级。

源码基线：当前工作树。

容器资源 update 的 guest agent 侧（cgroup set）见 CubeShim Container 到 Guest Agent 生命周期链路 §10。

0. 术语与背景

两种 CPU 语义（不要混）

CubeSandbox 里"CPU 资源"其实是两种不同的东西，落在不同层：

语义 含义 落点
VM 级 vCPU 数 guest 看到几个虚拟 CPU CubeShim VmConfig → VMM CpuManager
container 级 CPU quota 容器能用多少 CPU（cgroup quota/period） Cubelet updateCgroup → guest cgroup

把它们混成"给 VM 配几个 CPU"就会误判问题落点。

四层模型

CPU/vCPU 资源跨四层，职责不同：

  • ①② 决定 VM 有几个 vCPU（启动配置）。
  • ③ 决定 vCPU 是否真的被创建/调整（VMM resize）。
  • ④ 决定 guest 是否把 CPU 用起来 + container quota 是否生效（guest online + cgroup）。

VM 里的 vCPU 数、guest 里 CPU 是否在线、container 是否真用到这些 CPU，不是同一件事——这和 Kata 的 CPU 线一样：host resize 和 guest online 是两个阶段。

1. 核心结论

CubeSandbox 的 CPU/vCPU 资源跨四层：Cubelet 资源规格 → CubeShim VmConfig vCPU 注入 → VMM CpuManager 拓扑/resize → guest/container cgroup 收敛。四层相互依赖但职责不同。

2. 第一层：Cubelet 资源规格（container CPU quota）

Cubelet 在 container create 时读容器资源配置。updateCgroup() 从 CpuLimit 或 Cpu 解析出 quota，构造 specs.LinuxResources 的 CPU 字段：

// Cubelet/services/cubebox/cube_container_create.go:1099
func updateCgroup(ctx context.Context, ci *cubeboxstore.Container) error {
    cpuStr := ci.Config.GetResources().GetCpuLimit()
    if cpuStr == "" { cpuStr = ci.Config.GetResources().GetCpu() }   // CpuLimit 优先，回退 Cpu
    if cpuStr != "" {
        cpuQ, _ := resource.ParseQuantity(cpuStr)
        var (
            period = uint64(100000)
            quota  = cpuQ.MilliValue() * 100                        // millicores → quota
        )
        res := &specs.LinuxResources{ CPU: &specs.LinuxCPU{ Quota: &quota, Period: &period } }
        // ... 应用到容器 task 的 Update 路径 ...
    }
}

这是 container 级 CPU quota（cgroup），不是 VM 级 vCPU 数。两者是不同字段、不同落点。

3. 第二层：CubeShim VmConfig vCPU 注入

CubeShim 把 CPU 数直接写进 VmConfig——一个明确的 VM 配置对象，而非运行时动态猜的值：

// CubeShim/shim/src/hypervisor/config.rs:138
impl VmConfig {
    pub fn to_vm_config(&self) -> VC {
        let mut vc = VC::default();
        vc.cpus.max_vcpus  = self.vcpus as u8;       // max = boot（当前不开 hotplug 上限差异）
        vc.cpus.boot_vcpus = self.vcpus as u8;
        let topology = CpuTopology {
            threads_per_core: 1,                      // 每 core 1 线程（不开 SMT）
            cores_per_die: self.vcpus as u8,
            dies_per_package: 1,
            packages: 1,
        };
        vc.cpus.topology = Some(topology);
        // ... memory / payload / ...
    }
}

注意 threads_per_core: 1——CubeSandbox 默认不开 SMT，vCPU 全部铺成独立 core。这与 Firecracker ARM64 拒绝 SMT 的取向一致（见 资源管理与 QoS）。

4. 第三层：VMM vCPU resize

底层 hypervisor 支持 vCPU resize。测试里直接 resize_command(... desired_vcpus ...) 触发 VMM resize，随后 guest 侧手工把新增 CPU online（hypervisor/tests/integration.rs:5045）。

即使 VMM 侧已把目标 vCPU 数调上去，guest 内也不保证立即可用——还要 guest online。这与 Kata 的 CPU 线一致：host resize 和 guest online 是两个阶段。

5. 第四层：guest online 与 cgroup 收敛

CubeSandbox 当前开源代码里更容易直接看到的是 container cgroup/quota 更新（§2 的 updateCgroup），而不是独立的 CPU online agent API。平台层 CPU 资源最终收敛到 container task 的资源控制——即 vCPU 数与 container CPU 限制是两条相交但不同的线。

6. 与 pause/resume、网络线的区别

线 关注
pause/resume vCPU stop / device quiesce / VM 状态切换（见 runtime-control-vmm-update）
网络 endpoint/virtio-net/guest interface/route/interrupt
CPU/vCPU 资源 VM 配置中的 vCPU 表达 / guest online / container 资源控制

它们的共性只是都跨多层，但故障定位口径完全不同，不该混进同一文档。

7. ARM64 与 x86_64

控制路径两架构基本一致（Cubelet → CubeShim → CubeHypervisor → VMM）。分叉在底层 CPU 拓扑表达：ARM64 用 MPIDR/FDT/GIC，x86_64 用 CPUID/ACPI/APIC（见 arch-arm64-x86-chain）。

这条线的 ARM64 风险点不在平台 API 入口，而在底层 VMM 如何把 vCPU 数与拓扑正确暴露给 guest。

8. 边界表

层级 主要入口 负责什么
平台资源规格 Cubelet resource / cubebox config 定义 CPU limit / quota / VM 级需求
VM 配置层 VmConfig::to_vm_config（config.rs:141） 把 vCPU 数 + topology 写入 VMM 启动配置
VMM 层 resize command / CpuManager 真正创建或调整 vCPU
guest / container 收敛 guest online + cgroup update（cube_container_create.go:1099） 让新增 CPU 与 quota 真正生效

9. 结论与已知证据边界

CubeSandbox 的 CPU/vCPU 资源边界本质是：平台规格 + VM 配置 + VMM vCPU 数 + guest/container 收敛。

诚实声明：当前开源代码里，VMM resize 的证据主要来自测试文件（integration.rs），独立的 guest CPU online agent API 未见明确暴露。后续补这条线，更值的不是再加抽象图，而是围绕 ARM64 guest online 证据 / container quota/cpuset 最终状态 / VMM resize 后真实观测 去补更实的样本或诊断路径。
