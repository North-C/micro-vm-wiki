Snapshot Restore 网络恢复链路

本文聚焦 CubeSandbox 恢复 VM 时网络如何恢复——核心问题不是"snapshot 是否包含网卡"，而是恢复时 host 侧 TAP、VMM virtio-net 后端、guest 内接口状态分别由谁负责。

源码基线固定为 CubeSandbox canonical 工作树提交 5135a40d86c94a85fe2521fd9ed913ac5fd6cfd9（分支记录为 0731-after-v0.6.0）。

相关：snapshot create/commit、rollback runtime update、network-agent ensure network。

0. 术语与背景

两条容易混淆的恢复路径

路径 触发 RestoreConfig.net
创建期 app snapshot restore CubeShim start_vm 检测 snapshot mode → restore_vm 重新生成（当前 sandbox TAP name/MAC/限速）
运行期 rollback restore Cubelet RollbackSandbox → CubeShim rollback_vm 当前 Cubelet rollback JSON 不填 net（只有 source_url/memory_vol_url/disks）

关键边界

  • snapshot 不保存 host TAP 资源——只存 VMM 设备状态（virtio-net config/MSI-X/queue）+ tap_if_name。
  • restore 时 host TAP 经 RestoreConfig.net 按 id 替换 snapshot 中已有 virtio-net 的 host tap 后端（不是新增网卡）。
  • guest 内接口状态（IP/route/ARP）在 restore 后保持 snapshot 时的状态（guest memory + device state 恢复）。

1. restore_vm（RestoreConfig 含 net）

// CubeShim/shim/src/sandbox/sb.rs:889  restore_vm 构造 RestoreConfig
let config = RestoreConfig {
    source_url: PathBuf::from(snapshot),
    fs: Some(fss), net: Some(nets), disks: Some(disks), pmem: Some(pmems), vsock: Some(vsock),
    memory_vol_url: restore_memory_vol_url,
    ..Default::default()
};
ch.restore_vm(config).await?;   // ApiRequest::VmRestore

创建期 restore：CubeShim 重新生成 RestoreConfig.net——把当前 sandbox 的 TAP name/MAC/限速传给 VMM，VMM 按 id 替换 snapshot 中已有 virtio-net 的 host tap 后端。运行期 rollback：Cubelet 生成的 rollback JSON 不含 net → VMM restore 用 snapshot 中保存的 tap_if_name 重新打开同名 TAP。

2. 能力边界

问题 结论
snapshot 是否保存 host TAP 否（只存 tap_if_name + VMM 设备状态）
创建期 restore 如何获得 TAP RestoreConfig.net 替换 snapshot 中同 id 网卡后端
rollback restore 如何获得 TAP 当前 Cubelet JSON 不填 net → VMM 用 snapshot 中 tap_if_name 重开
guest 内接口状态 restore 后保持 snapshot 时状态（guest memory + device state 恢复）
RESTORE 分支 cube-agent create_sandbox 在 RESTORE 模式下只追加 virtiofs storage，不重新配置网络（见 cubeshim container agent）
