    Snapshot Create / Commit 生成链路

    本文分析 CubeSandbox 的 snapshot 如何被创建——重点不是 API 名称，而是 VM state、guest memory、rootfs、CubeCoW 对象和本地 catalog 如何组合成可 restore/rollback 的平台级快照。

    源码基线：当前仓库工作树。

    相关：CubeCoW storage engine、snapshot catalog restore binding、VMM snapshot restore state。

    0. 术语与背景

    平台级快照不是单个文件

    它至少由三层组成：① VMM 目录里的 config/state；② 外部 memory volume；③ CubeCoW rootfs/memory 对象；④ Cubelet 本地 catalog.json。

    flowchart TB SnapshotID["logical snapshot/template id"] --> Catalog["catalog.json"] Catalog --> Meta["snapshot path / meta_dir"] Catalog --> Rootfs["CubeCoW rootfs object"] Catalog --> Memory["CubeCoW memory object"] Meta --> VMMDir["snapshot/ 目录"] VMMDir --> Config["VM config JSON"] VMMDir --> State["VM state JSON"] Memory --> MemFile["external memory_vol_url dev path"]

    restore/rollback 不能只看 VMM 目录——没有 catalog 和 CubeCoW 对象，平台无法解析 rootfs 和 memory 的实际设备路径。

    两条创建路径

    路径 目标 sandbox 生命周期 rootfs 来源 memory snapshot type
    AppSnapshot 生成 template 建临时 sandbox → snapshot → 销毁 template build rootfs full（永远）
    CommitSandbox 运行中 sandbox 的 runtime snapshot 原 sandbox 继续运行 当前 sandbox writable rootfs soft-dirty → incremental → full（三层退化）

    memory 增量的关键设计

    CubeSandbox 的增量 snapshot 不是保存一个 delta 文件——目标文件始终被构造成可直接 restore 的完整 memory image，只是写入时只覆盖变化页（soft-dirty / pagemap_anon 增量写入）。

    runtime binding 两类 label（增量链路）

    • MasterAnnotationRuntimeSnapshotID：sandbox 当前绑定的最新 runtime snapshot（Commit 后更新，rollback 后也更新）。
    • MasterAnnotationRuntimeRestoreSnapshotID：VM 上次从哪个 snapshot 恢复（Commit 不更新——因 pagemap_anon 脏页语义是"自上次 restore 以来被写过的 anon 页"）。

    1. 结论先行

    • AppSnapshot = "建临时 sandbox → full VM snapshot → rootfs from build → 销毁临时 sandbox"，用于生成 template。
    • CommitSandbox = "对运行中 sandbox 生成 runtime snapshot"，先 commit rootfs，再准备 memory artifact（soft-dirty 优先，退化 pagemap_anon，再退化 full）。
    • 两条路径最后都调 cube-runtime snapshot --app-snapshot --vm-id ...，Shim 侧走 HTTP API 对运行中 VMM 执行 pause → snapshot → resume。

    2. AppSnapshot 路径

    AppSnapshot() 接收 AppSnapshotRequest（必须含 create request + template id），创建临时 cubebox，从 containerd spec 提取 CubeboxSnapshotSpec，建 memory volume，执行 cube-runtime snapshot（固定 full），从 template build rootfs 生成 rootfs snapshot，销毁临时 cubebox，写 catalog：

spec, err := s.getCubeboxSnapshotSpec(ctx, sandboxID)                        // 从 containerd spec 提取
memoryObject, err = storage.CreateTemplateMemoryVolume(ctx, templateID, memorySizeBytes)
s.executeCubeRuntimeSnapshot(ctx, sandboxID, spec, tmpSnapshotPath, memoryObject.DevPath, snapshotTypeFull)  // 固定 full
rootfsObject, err = storage.CreateTemplateRootfsFromBuild(ctx, templateID)   // rootfs from build
destroyRsp, destroyErr := s.Destroy(destroyCtx, destroyReq)                  // 销毁临时 cubebox
storage.WriteSnapshotCatalog(&storage.SnapshotCatalogEntry{ SnapshotID: templateID, Kind: storage.CatalogKindTemplate, /*...*/ })

    3. CommitSandbox 路径

    CommitSandbox() 针对运行中 sandbox——要求 cubecow backend、sandbox 运行、无不支持的 hostPath/host_dir/sandbox_path volume。rootfs 来自当前 sandbox writable rootfs（非 template build），memory 走三层退化：

    // Cubelet/services/cubebox/template_ops.go:73
if !storage.IsCowBackend() { return /* PreConditionFailed: requires storage_backend=cubecow */ }
cb, err := s.cubeboxMgr.cubeboxManger.Get(ctx, rsp.SandboxID)
sourceRootfs, err := storage.GetSandboxRootfsForSnapshot(ctx, rsp.SandboxID, rootVolumeName)
rootfsObject, err := storage.CommitTemplateRootfs(ctx, sourceRootfs, rsp.TemplateID)        // commit 当前 rootfs
memoryObject, snapshotTypeForCmd, err := prepareCommitMemoryArtifact(ctx, stepLog, cb, rsp.TemplateID, memorySizeBytes)  // 三层退化

    4. memory artifact 三层退化（核心）

    prepareCommitMemoryArtifact() 定义三层退化，返回 CubeCoW memory object + 传给 cube-runtime 的 snapshot type：

    // Cubelet/services/cubebox/snapshot_base_memory.go:188
func prepareCommitMemoryArtifact(ctx, stepLog, cb, templateID, memorySizeBytes) (*storage.CowSnapshotObject, string, error) {
    // Tier 1: soft-dirty over previous-snapshot base
    if baseMemoryObject, err := resolveBaseMemoryObject(ctx, cb); err == nil {
        memoryObject, _ := storage.CommitTemplateMemoryFromBase(ctx, baseMemoryObject, templateID, memorySizeBytes)  // reflink-clone
        return memoryObject, snapshotTypeSoftDirty, nil
    }
    // Tier 2: pagemap_anon over last-restore base
    if restoreBase, err := resolveRestoreBaseMemoryObject(ctx, cb); err == nil {
        memoryObject, _ := storage.CommitTemplateMemoryFromBase(ctx, restoreBase, templateID, memorySizeBytes)
        return memoryObject, snapshotTypeIncremental, nil
    }
    // Tier 3: full + fresh empty volume
    memoryObject, _ := storage.CreateTemplateMemoryVolume(ctx, templateID, memorySizeBytes)
    return memoryObject, snapshotTypeFull, nil
}

    三层语义：Tier1 用当前绑定的 snapshot memory 作 base，reflink-clone 后 VMM 写 soft-dirty 页；Tier2 当前绑定不存在时，用上次 restore 的 base memory，写 pagemap_anon 增量；Tier3 两者都无法解析时，建空 memory volume 写 full。增量不是存 delta 文件，而是只覆盖变化页的完整 image。

    5. runtime binding 与 opaque restore

    两个 label 维护增量链路：

    // Cubelet/services/cubebox/snapshot_runtime_binding.go:21
func runtimeSnapshotBindingLabels(snapshotID string, attachedAt time.Time) map[string]string {
    return map[string]string{ constants.MasterAnnotationRuntimeSnapshotID: snapshotID, /* attachedAt */ }
}
func runtimeRestoreBaseLabels(snapshotID string, attachedAt time.Time) map[string]string {
    return map[string]string{ constants.MasterAnnotationRuntimeRestoreSnapshotID: snapshotID, /* attachedAt */ }
}
// :79  opaque restore 时把两类标 invalid，迫使下次 Commit 走 full
func invalidateRuntimeSnapshotBindingsAfterOpaqueRestore(cb, attachedAt) {
    cb.Metadata.AddLabels(map[string]string{
        constants.MasterAnnotationRuntimeSnapshotID:        runtimeSnapshotBindingInvalidID,
        constants.MasterAnnotationRuntimeRestoreSnapshotID: runtimeSnapshotBindingInvalidID,
    })
}

    Commit 不更新 restore base label——pagemap_anon 脏页语义是"自上次 restore 以来被写过的 anon 页"，所以 restore base 必须保持上次 restore 的值。若 VM 从 Cubelet 无法 reflink 的不透明来源恢复（如内部 pause/resume），invalidateRuntimeSnapshotBindingsAfterOpaqueRestore 把两类标 invalid，下次 Commit 走 full。

    6. cube-runtime snapshot 命令

    buildCubeRuntimeSnapshotArgs() 生成命令形态：

    // Cubelet/services/cubebox/appsnapshot.go:586
func buildCubeRuntimeSnapshotArgs(sandboxID, spec, snapshotPath, memoryVol, snapshotType string) []string {
    return []string{
        "snapshot", "--app-snapshot", "--vm-id", sandboxID, "--path", snapshotPath, "--force",
        "--snapshot-type", normalizeSnapshotType(snapshotType),  // full|incremental|soft-dirty
        // ... --resource --kernel --memory-vol file://<devpath> ...
    }
}

    参数名叫 --app-snapshot，但 CommitSandbox 也复用这条命令，差异来自上层传入的 snapshot type 和 memory volume。Shim 侧 do_app_snapshot() 顺序是 pause → snapshot → resume（snapshot 失败也尝试 resume）：

    // CubeShim/shim/src/snapshot/mod.rs:119
async fn do_app_snapshot(&mut self) -> CResult<()> {
    self.api_pause_vm().await?;
    let snapshot_result = async { self.api_snapshot_vm().await?; self.store_metadata() }.await;
    let resume_result = self.api_resume_vm().await;       // 无论 snapshot 成败都尝试 resume
    match (snapshot_result, resume_result) { /* 合并错误 */ }
}

    这条路径暂停 VM 但不销毁，与 CubeShim 内部 pause_vm_cube()（pause-to-snapshot 后删除 VM）不同。

    VMM 收到 VmSnapshot 后 vm_snapshot() 调 vm.snapshot() 捕获状态再 vm.send() 写文件：

    // hypervisor/vmm/src/lib.rs:640
fn vm_snapshot(&mut self, snapshot_config: &SnapshotConfig) -> result::Result<(), VmError> {
    if let Some(ref mut vm) = self.vm {
        vm.snapshot().map_err(VmError::Snapshot)
            .and_then(|snapshot| vm.send(&snapshot, snapshot_config).map_err(VmError::SnapshotSend))
    } else { Err(VmError::VmNotRunning) }
}
// hypervisor/vmm/src/vm.rs:2911
fn send(&self, snapshot: &Snapshot, config: &SnapshotConfig) -> Result<(), MigratableError> {
    // 写 VM config 到 destination/SNAPSHOT_CONFIG_FILE
    // 写 VM state（附 SnapshotMetadata.snapshot_type）到 destination/SNAPSHOT_STATE_FILE
    if let Some(mm_snapshot) = snapshot.snapshots.get(MEMORY_MANAGER_SNAPSHOT_ID) {
        let mm_config = SnapshotConfig { destination_url, snapshot_type: config.snapshot_type, memory_vol_url };
        self.memory_manager.lock().unwrap().send(&mm_snapshot, &mm_config)?;  // 把 type + memory_vol_url 传 MM
    }
}

    MemoryManager 按 snapshot type 写 memory：Full 遍历所有 range 完整写；Incremental 用 pagemap/kpageflags 过滤 anon CoW 页只覆盖；SoftDirty 首次未 armed 写 anon 页 + clear_refs(4)，后续写 anon∩soft-dirty 页再重新 arm。memory_vol_url 非空时写外部 dev path，config/state 仍在 destination 目录。

    8. SnapshotInfo metadata（平台层兼容门禁）

    Shim snapshot 命令在 VMM snapshot 完成后调 store_metadata() 生成 metadata.json（来自 SnapshotInfo：CPU/memory/image version/kernel version/disk fs+size/pmem id+fs+size/app snapshot container id）。restore 时 CubeShim 重构期望 SnapshotInfo 与文件对比，不匹配拒绝 restore。

    这不是 VMM restore 所需的 VM state——是 CubeShim 在平台层增加的兼容性门禁。

    9. 能力边界

    问题 AppSnapshot CommitSandbox
    目标 生成 template 生成运行中 sandbox 的 runtime snapshot
    sandbox 生命周期 建临时 sandbox，snapshot 后销毁 原 sandbox 继续运行
    rootfs 来源 template build rootfs 当前 sandbox writable rootfs
    memory 来源 新建 memory volume clone base 或新建 memory volume
    snapshot type full soft-dirty / incremental / full
    catalog kind template runtime_snapshot
    是否更新 runtime binding 不更新运行中 sandbox 成功后更新
    网络状态是否进入 catalog 不进入 不进入

    网络状态不写入 snapshot catalog——host 侧网络仍依赖 network-agent 当前状态；VMM restore 时 net 后端替换依赖 RestoreConfig.net。

    10. ARM64 与 x86_64 观察点

    Cubelet 层 AppSnapshot/CommitSandbox/CubeCoW catalog/memory artifact 选择无显式架构分支。Shim snapshot 命令的 VMM seccomp 有架构差异（x86 放行 mkdir，aarch64 放行 mkdirat）。VMM snapshot 本身的架构差异在 VM state（x86 含 CPUID/IRQ/ACPI；ARM64 关注 GIC/FDT/MPIDR/设备枚举稳定性）；MemoryManager 的 full/incremental/soft-dirty 逻辑依赖 Linux pagemap/kpageflags/soft-dirty，不是 vCPU 架构。

    soft-dirty 的 ARM64 关键点：宿主 kernel 是否支持 CONFIG_MEM_SOFT_DIRTY、/proc/self/clear_refs 和 pagemap bit 55 是否可用——不支持时退化到 pagemap_anon。
