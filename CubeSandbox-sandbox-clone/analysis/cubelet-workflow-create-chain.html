Cubelet Workflow Create 编排链路

本文承接 API 到 Cubelet 创建链路 和 CubeShim sandbox 与 CubeHypervisor 创建链路，展开 Cubelet 进入 CubeShim 之前的 create workflow。

源码基线：当前仓库工作树。

相关：Cubebox Action 到 Containerd/CubeShim、network-agent EnsureNetwork、CubeCoW storage engine。

0. 术语与背景

create 不是硬编码函数，是配置驱动的串并行 workflow

默认配置把 create 拆成 4 个 step：

# Cubelet/config/config.toml:143
actions = [["createid", "appsnapshot"],
           ["images","volume","storage","network","netfile", "cube-sandbox-store"],
           ["cgroup"],
           ["cubebox"]]
step 内容 并行
1 createid + appsnapshot（确定 sandbox 身份 + 模板上下文） step 内并行
2 images/volume/storage/network/netfile/cube-sandbox-store（外部资源准备） step 内并行
3 cgroup（资源计算 + 池分配） 单 action
4 cubebox（物化 containerd + CubeShim） 单 action

两个事实：① storage/network/netfile 不依赖 cgroup——它们把结果写入 CreateContext，等 cubebox 消费；② cgroup 必须早于 cubebox——cubebox 读 opts.CgroupInfo 生成 VM spec annotation + 创建容器后设 host cgroup 限制。

关键概念

  • CreateContext：各 action 的共享数据总线（ReqInfo/NetworkInfo/StorageInfo/CgroupInfo/VolumeInfo/NetFile/...）。
  • Flow 接口：每个 action 实现 ID/Init/Create/Destroy/CleanUp，从 containerd plugin registry 取出。
  • 串并行模型：一个 step 内 Actions 并行（errgroup），step 间顺序。
  • Failover：默认 true，create 失败时异步调 destroy 补偿（可被 cube.debug.disable_failover 关闭）。

1. 结论先行

Cubelet create 是配置驱动的串并行 workflow：step 内并行、step 间顺序，结果经 CreateContext 聚合，最后由 cubebox action 物化成 containerd container/task 进入 CubeShim。

2. 总体流程图

3. Workflow Engine 执行模型

// Cubelet/plugins/workflow/engine.go:251
type Flow interface {
    ID() string
    Init(context.Context, *InitInfo) error
    Create(context.Context, *CreateContext) error
    Destroy(context.Context, *DestroyContext) error
    CleanUp(context.Context, *CleanContext) error
}
type Workflow struct { Name string; MaxConcurrent int64; Limiter *semaphore.Limiter; Steps []*Step }
type Step struct { Name string; Actions []Flow }   // Actions 并行，Step 间顺序

Engine.run() 抢 flow 级 limiter → 逐 step 调 parallelRunSteps() → 任一 action 出错按 Failover 决定补偿：

// Cubelet/plugins/workflow/engine.go:334
func (e *Engine) run(do string, ctx context.Context, opts ReqContext) error {
    flow := e.workflows[do]
    if !flow.Limiter.TryAcquire() { return ret.Errorf(ErrorCode_ConcurrentFailed, "flow exceed limited") }  // 并发限流
    defer flow.Limiter.Release()
    for _, step := range flow.Steps {
        if err := e.parallelRunSteps(do, ctx, opts, step); err != nil {
            if flow_create == do {
                rOpts := opts.(*CreateContext)
                if rOpts.Failover { go e.failover(ctx, opts) }   // 异步 destroy 补偿
            }
            if flow_destroy == do { e.cleanUp(ctx, opts) }
            return err
        }
    }
}

parallelRunSteps() 用 errgroup 并发运行一个 step 内所有 action（每个带 trace/metric，:412）。

失败补偿链：create 失败 → failover（构 DestroyContext + rollback 标记 + 调同 engine Destroy()）→ destroy 自身失败 defer 调 cleanup flow（:475）。各 action 还有局部回滚（storage cleanupCreateResult、tap ReleaseNetwork、cgroup 归还 pool id）。

4. Step 1：确定 Sandbox 身份和模板上下文

createid.Create() 默认 GenerateID() 写 opts.SandboxID；app snapshot 时固定 <templateID>_0：

// Cubelet/plugins/cube/internals/createid/plugin.go:44
func (l *local) Create(ctx context.Context, opts *workflow.CreateContext) error {
    opts.SandboxID = utils.GenerateID()
    if opts.IsCreateSnapshot() {
        templateID, _ := opts.GetSnapshotTemplateID()
        opts.SandboxID = templateID + "_" + "0"     // app snapshot 固定 ID
    }
}

appsnapshot.Create() 只在"从模板恢复 + cubebox v2"时工作，确保本地 run template 写 opts.LocalRunTemplate。后面 storage/network/cgroup/cubebox 都以 opts.SandboxID 为核心索引。

5. Step 2：并行准备外部资源

各 action 把结果写入 CreateContext：images（CRI EnsureImage，images/local.go:171）、volume（opts.VolumeInfo，volume.go:113）、storage（后端文件/CubeCoW volume/snapshot 派生 + 本地 metadata，opts.StorageInfo，storage/local.go:742）、network（tap plugin，opts.NetworkInfo）、netfile（hostname/hosts/resolv.conf，opts.NetFile，netfile_plugin.go:88）、cube-sandbox-store（containerd SandboxStore，Sandboxer=cube，cube_sandbox_store.go:90）。

Network Action 真实边界（tap 由 Cubelet 经 network-agent 建，非 CubeShim 临时建）

// Cubelet/network/plugin_tap.go:429
func (l *local) Create(ctx context.Context, opts *workflow.CreateContext) error {
    // 解析网络 annotation + 合并 DNS allow-out CIDR → 构造 EnsureNetworkRequest
    ensureResp, naErr := l.networkAgentClient.EnsureNetwork(ctx, ensureReq)     // 调 network-agent
    defer func() {                                                                // 局部回滚
        if err == nil { return }
        l.networkAgentClient.ReleaseNetwork(rollbackCtx, releaseReq)            // 失败 → ReleaseNetwork
        l.unregisterNetworkAgentTapForPool(rollbackCtx, opts.SandboxID)         // + 注销 fd pool
    }()
    shimReq, err := l.buildShimNetReqFromEnsureResponse(ensureResp, req)        // 转成 shim 网络请求
    l.registerNetworkAgentTapForPool(ctx, opts.SandboxID, shimReq)              // 注册 TAP fd pool
    if req.Qos != nil { shimReq.Interfaces[0].Qos = &QosConfig{ /* bandwidth/ops */ } }  // QoS
    opts.NetworkInfo = shimReq
}

tap 不是 CubeShim 临时建的——Cubelet 调 network-agent EnsureNetwork，再转成 shim ShimNetReq，注册 TAP fd pool。失败时 defer ReleaseNetwork + 注销 fd pool，避免只创建一半的网络资源。

6. Step 3：Cgroup 资源计算与池分配

CgPlugin.Create() 读 opts.VolumeInfo 计算开销 + 匹配 VM snapshot spec + 从 cgroup pool 取 id：

// Cubelet/plugins/cube/internals/cgroup/local.go:299
func (l *CgPlugin) Create(ctx context.Context, opts *workflow.CreateContext) error {
    defer func() { if err != nil && fullCgID != nil { l.pool.Put(ctx, *fullCgID) } }()  // 失败归还 pool
    resourceQuantity, err := l.overhead.GetResourceWithOverhead(ctx, realReq, opts.VolumeInfo)  // 读 VolumeInfo
    vmSnapshotSpec, resourceQuantity := l.overhead.MatchVMSnapshotSpec(ctx, *resourceQuantity, vmSnapshotSpecs, /*...*/)
    fullCgID, err = l.pool.Get(ctx, opts.GetSandboxID(), usePoolV2, numa)    // cgroup pool
    opts.CgroupInfo = &Info{ CgroupID: MakeCgroupPathByID(*fullCgID), ResourceQuantity: *resourceQuantity, VmSnapshotSpec: vmSnapshotSpec, /*...*/ }
}

cgroup 单独成 step：它需读 step2 的 opts.VolumeInfo，cubebox 又需读它的 opts.CgroupInfo——处于依赖链中间。

7. Step 4：Cubebox 物化 containerd + CubeShim

local.Create() 把 CubeBoxCreated 置 true → createContainers() → genSandboxOptions/genContainerTmpOpt/genNetworkAnnotationOpt/genCgroupAnnotationOpt 把上下文转 OCI annotation → runContainer（containerd NewContainer/NewTask）：

// Cubelet/services/cubebox/cube_container_create.go:86
func (l *local) Create(ctx context.Context, opts *workflow.CreateContext) error {
    opts.CubeBoxCreated = true
    if err := l.createContainers(ctx, opts); err != nil { return err }
    if cgInfo, ok := opts.CgroupInfo.(*cgroupp.Info); ok {
        cgroupp.SetCubeboxCgroupLimit(ctx, cgInfo.CgroupID, cgInfo.ResourceQuantity.HostCpuQ, /*...*/)  // host cgroup 限制
    }
}
// :1149
func (l *local) runContainer(ctx, cubebox, ci, cOpts, ociRuntime) error {
    c, err := l.client.NewContainer(ctx, ci.ID, cOpts...)            // containerd NewContainer
    task, err := c.NewTask(ctx, ioCreater, taskOpts...)              // NewTask → 触发 CubeShim
    exitCh, _ := task.Wait(ctx); ci.ExitCh = exitCh
    task.Start(ctx)
}

genContainerTmpOpt 从 opts.StorageInfo/opts.NetworkInfo/opts.CgroupInfo 生成 cube.mount.list/网络/cgroup 类 annotation，告诉 shim/guest 有哪些 host disk/image device/网络/cgroup。runContainer 是 Cubelet→CubeShim 的真实边界（runtime 是 cube shim）。

8. 失败补偿 / ARM64 / 能力边界

失败补偿：create flow 默认 Failover=true（service.Create，可被 cube.debug.disable_failover 关闭，service.go:238）。Engine.run create 出错时 go e.failover() 异步 destroy 补偿；destroy 自身失败 defer 调 cleanup flow。各 action 还有局部回滚（storage/tap/cgroup）。

ARM64：workflow 绝大多数架构无关（TOML flow + Go action + CreateContext 字段流转无 arch 分支）。差异在下游：storage（reflink 文件系统/block 设备路径/guest kernel）、network（ARM64 kernel 的 eBPF/TAP/FD passing/virtio-net）、cgroup（NUMA/quota 实际表现）、cubebox/shim（CubeHypervisor 的 ARM64 KVM/GIC/FDT/guest image）。

ARM64 关键问题不是 workflow 能否跑到 cubebox，而是 cubebox 之后的 VMM/guest/network/storage 组合能否按这些 annotations 正确启动。

分层"create 成功"含义：

层级 成功含义
workflow step2 镜像/存储/网络/netfile/sandbox store 准备完成
cgroup step host 资源池 + VM spec 已计算
cubebox step containerd container/task 已创建 → 进入 CubeShim
CubeShim VM 创建/启动或恢复 + agent 建连 + sandbox/container RPC 完成
产品层 CubeAPI/CubeMaster 收到终态 + metadata 与节点状态一致

workflow 保证"资源准备顺序/并行执行/失败补偿/上下文聚合"，不直接保证 VM 已启动或 guest agent 已完成配置——这些靠 cubebox/containerd shim/CubeShim/CubeHypervisor/cube-agent 完成。
