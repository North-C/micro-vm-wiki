    CubeSandbox Sandbox / VM / Container 层次与 OCI Template 运行链路

    结论摘要

    本文回答两个问题：CubeSandbox 中 Sandbox、VM、Container 到底如何对应，以及 OCI image 变成 Template 后又如何恢复成一个新 Sandbox。读者是需要定位控制面、节点状态、VMM 和 guest workload 边界的工程师。

    源码基线固定为 CubeSandbox canonical 工作树提交 5135a40d86c94a85fe2521fd9ed913ac5fd6cfd9（分支记录为 0731-after-v0.6.0）。本文只讨论 io.containerd.cube.rs microVM 主路径和由 OCI image 构建的 AppSnapshot Template；不把独立的 host io.containerd.runc.v2 路径、runtime snapshot、ARM64 2-vCPU restore 调查或公开 Wiki 发布纳入范围。

    • [本地事实] Sandbox、VM、Container 不等价。 逻辑 Sandbox 是包含网络、卷、资源、模板来源和 1..N 个 Container 的聚合；在当前 cube runtime 中，它在任一活动时刻通常对应一个 Cubelet CubeBox、一个 CubeShim SandBox、一个活动 VM。多个 Container 共享该 VM 和 guest kernel。
    • [本地事实] 第一个 Container 是实现锚点而非 Sandbox 的同义词。 它的 container ID 等于 sandboxID，首次 NewTask 负责触发 CubeShim 的 VM/agent sandbox 初始化，但 guest agent 仍把它创建为真实 OCI 容器。
    • [本地事实] VMM 不是 CubeShim 的子进程。 CubeShim 进程内的 VmmInstance 通过 channel 和 EventFd 驱动同进程的命名 vmm 线程；containerd 观察到的 PID 是 shim PID，不是 guest workload PID。
    • [本地事实，纠错] guest 主路径不启动 containerd 或外部 runc。 cube-agent 直接构造内嵌 rustjail::LinuxContainer，执行 namespace、cgroup、mount、fork 和最终 execvp。仓内另有 runc-like 语义或注释，不等于存在 guest runc 进程。
    • [本地事实] OCI -> Template 与 Template -> new Sandbox 是两个生命周期。 前者先生成独立 RootfsArtifact，再在每个目标 Cubelet 上创建临时 Sandbox/VM、运行 workload 并保存 full AppSnapshot；后者读取逻辑 templateID，在拥有 READY replica 的节点派生新 rootfs、解析 memory device，启动新的 CubeShim 并 restore 新 Sandbox。
    • [本地事实，纠错] cold boot 与 AppSnapshot restore 的 ready 栅栏不同。 cold boot 明确等待 VsockServerReady；AppSnapshot restore 成功后从 start_vm 提前返回，不等该事件，但两者随后都必须连接 agent、完成 guest CreateSandbox、container task、可选 probe 和 create-time envd init，才可能对外成功。
    • [推断] Template 是可实例化的状态基线，不是长驻共享 VM。 rootfs/memory backing 可以共享底层数据，但每次运行仍有独立 Sandbox 身份、CubeShim/VMM 执行上下文和 VM 隔离域。

    证据标签与术语

    本文使用以下标签：[本地事实] 表示固定提交源码可直接证明；[推断] 表示由多个本地事实推出且保留不确定性；[工程判断] 表示风险或设计评价；[未确认] 表示当前证据不足。本文没有使用外部社区材料或运行实验。

    术语 本文中的源码语义
    Sandbox 跨层资源身份。CubeAPI 是对外 DTO；CubeMaster 持有创建意图、节点绑定和 best-effort SandboxSpec；Cubelet 的 CubeBox 是节点聚合根；CubeShim 的 SandBox 是单 VM、agent 连接和 guest containers 的运行聚合根。
    VM SandBox 内 hypervisor/VMM 所管理的 KVM guest；没有独立 CubeMaster CRUD/DB 实体。pause/restore 可让同一逻辑 Sandbox 跨越不同活动 VM execution instance。
    Container Sandbox 内的 OCI workload 单元。Cubelet、containerd/CubeShim 与 guest agent 各持有相应投影；第一个 Container 同时是 sandbox anchor。
    Template TemplateDefinition(kind=template)、节点 TemplateReplica 和本地 AppSnapshot assets 共同表达的可复制基线；不是 OCI image、RootfsArtifact 或运行中的 VM。
    Snapshot TemplateDefinition 同表也可表示 kind=snapshot；本文只讨论 AppSnapshot Template。它也不同于 containerd image snapshot metadata。
    OCI image registry image ref、manifest/config/layers 语义的输入。Template Center 将其导出为 rootfs，再制成 ext4 artifact。
    RootfsArtifact CubeMaster Template Center 独立管理的 ext4 rootfs 产物和 DB 身份，可按 fingerprint 复用；它是 Template 构建输入，不是最终 Template。
    AppSnapshot assets 节点上的 VMM config.json/state.json、metadata.json、memory CubeCoW volume、rootfs CubeCoW snapshot 和 catalog.json。
    ready 分层同步结果，不是单一 bit：VMM、transport、agent、guest sandbox、container task、probe、envd、Cubelet 和 Master 各有不同成功边界。

    Sandbox 各层类型可从源码直接消歧：CubeAPI 的响应模型只投影外部字段（该 Sandbox DTO 定义外部 templateID/sandboxID/clientID 等字段）；Cubelet 的 CubeBox 持有 containers、runtime、endpoint、volumes 和 template 等节点状态（该结构定义节点聚合字段）；CubeShim 的 SandBox 只有一个 hypervisor handle，却有 container map（该结构展示单 ch 与多 containers）。

    对象、基数、状态 owner 与隔离映射

    对象/运行实体 身份与基数 主要状态 owner 生命周期/持久性 隔离边界
    对外 Sandbox sandboxID；一次 API 资源对应一个节点实例 CubeMaster 持有意图与 host binding；CubeAPI 只适配协议 创建到 destroy；SandboxSpec 写入是 best-effort 控制面资源，不自身提供 workload 隔离
    Cubelet CubeBox Metadata.ID == sandboxID；1:1 对应节点 Sandbox Cubelet local store 跨 Cubelet RPC 使用，destroy workflow 成功后清理 节点协调/故障边界
    活动 VM 当前主路径 1 CubeBox : 1 CubeShim SandBox : 1 active VM CubeShim + VMM boot/restore 到 poweroff；pause/restore 可替换 execution instance Sandbox 间 KVM 强隔离边界
    Container 1 Sandbox : 1..N；首个 ID=sandboxID Cubelet metadata、CubeShim proxy、guest agent/rustjail 分层持有 container task/create/start/kill/delete；guest poweroff 最终回收 guest 内 namespace/cgroup 次级边界
    TemplateDefinition templateID；1 : 0..N TemplateReplica CubeMaster DB PENDING/CREATING/READY/PARTIALLY_READY/FAILED/DELETING 逻辑基线，不是隔离域
    TemplateReplica 逻辑键意图为 (templateID,nodeID) CubeMaster DB distribution/snapshot/ready/cleaning 等控制状态 locality 投影，不拥有物理路径
    RootfsArtifact artifactID 由 spec fingerprint 派生；可被复用 CubeMaster DB + artifact filesystem build/READY/GC 独立于 Template 构建数据，不是 VM/container 边界
    AppSnapshot assets 节点以 templateID + specDir 和 catalog 映射到物理对象 Cubelet filesystem + CubeCoW 跨 Sandbox 实例存在；多资源分步提交 restore 数据基线，不是共享运行域

    [本地事实] CubeBox 的总体状态投影自 first container（这些方法读取 first container status 作为 Sandbox 主状态）。[推断] 这是用 anchor task 代表 Sandbox/VM 状态的实现策略，不改变 CubeBox 仍聚合多容器、网络、卷和模板状态的事实。

    [本地事实] CubeMaster 成功后会写 host/proxy/spec，但 SandboxSpec 写失败只告警（该成功后处理把持久化错误降级为 warning）。因此表中的 0..1 SandboxSpec 比“每个 Sandbox 必有一行”更准确。

    从四个问题判断“是不是同一个对象”

    1. 身份是否相同

    • Sandbox 的稳定运行身份是 sandboxID。
    • 第一个 Container 的 host/containerd ID 被刻意设成 sandboxID。
    • 其他 Container 有各自生成的 ID。
    • CubeShim SandBox.id 继承 sandboxID。
    • VMM 配置、socket 和 vsock backend 也以该 ID 组织。

    [本地事实] 身份字符串被复用不代表类型等价。第一个 Container 复用 sandboxID 是为了让 containerd task 成为 Sandbox runtime anchor；同一个 CubeBox 仍然保存多个 Container 和 Sandbox 级资源。

    2. 生命周期是否相同

    • Sandbox 从 Master create 意图开始，经过调度、节点创建、pause/resume，直到 destroy 与控制面清理。
    • 活动 VM 从 CubeShim boot/restore 开始，到 guest poweroff/VMM thread join； pause/restore 允许逻辑 Sandbox 存续而活动 VM execution instance 被替换。
    • Container 有 created、started、exited、deleted 等 task 生命周期；它可以先于 Sandbox 终止。
    • Template 在运行 Sandbox 之前存在，并可在多个 Sandbox 销毁后继续存在。

    [推断] 生命周期不重合是四者不等价的第二个直接理由。

    3. 状态由谁拥有

    • Master 不持有 KVM/VMM 的实时状态。
    • Cubelet 不持有 guest LinuxContainer 的进程对象。
    • CubeShim 不拥有 Template definition/replica 的逻辑 READY 状态。
    • guest agent 不拥有 host artifact、catalog 或 scheduler binding。

    [本地事实] 状态按控制面、节点协调、VM runtime、guest runtime 分层，任何 把所有状态都归到“Sandbox object”的单层图都会丢失故障和一致性边界。

    4. 隔离边界是否相同

    • Sandbox 间的主要 workload 隔离由不同 KVM VM 提供。
    • 同一 Sandbox 内的 Containers 共享 guest kernel、VM 资源和 agent service。
    • Containers 仍通过 rustjail 配置的 OCI namespaces/cgroups/mounts形成次级边界。
    • Template 与 RootfsArtifact 是存储/控制面对象，不是活动安全域。

    [未确认] 本文不把上述结构关系提升为形式化安全保证；seccomp、capability、 host/guest cgroup 和具体 namespace sharing仍需独立审计。

    先区分四个入口

    “请求模型支持多个 Container”不代表每个 northbound API 都允许调用者直接传入多个 Container。固定基线存在四个不同入口：

    入口 多 Container 的来源 当前边界
    CubeMaster POST /cube/sandbox 请求体的 containers[]，或与 Template 保存的 containers[] 合并 这是最直接的底层入口；无 Template 的 legacy local-config 路径要求请求 container 数不能超过 CubeBoxReqTemplate 的 container 数

    Container 之间共享什么、隔离什么

    维度 同一 Sandbox 内的关系 源码机制
    VM / guest kernel 共享 单 CubeShim SandBox 只有一个 hypervisor handle
    Sandbox IP / network namespace 共享 CubeShim 发送 OCI spec 前移除 network namespace，Container 留在 guest Sandbox network namespace
    UTS / IPC namespace 共享 agent 将每个 spec 的 UTS/IPC path 改为 Sandbox 创建的 shared namespace
    PID namespace 默认分离 CubeShim 同时移除原 PID namespace；agent 默认追加一个新 PID namespace。只有 sandbox_pidns=true 才共享，而当前 CubeShim 请求使用默认 false
    mount namespace / rootfs 分离 每个 Container 保留独立 mount namespace、bundle、rootfs 和 mount list
    cgroup / resource controls 分离 每个 LinuxContainer 持有自己的 cgroup manager 和 OCI resources
    guest agent / vsock 共享 同一个 CubeShim SandBox.client 服务所有 Container proxy
    named Sandbox volume 可共享数据 Sandbox 声明一次 volume，各 Container 通过自己的 volume_mounts 引用
    lifecycle result 创建阶段整体收敛 Cubelet 顺序 create/start/probe；任一 Container 失败会让 workflow 返回失败并进入 Sandbox failover/cleanup

    [本地事实] CubeShim 在把 OCI spec 发往 guest 前删除 network、PID、cgroup namespace，并把其余 namespace path 清空（实际过滤逻辑）。 agent 随后把 IPC/UTS 指向 Sandbox shared namespace，并按 sandbox_pidns 决定 PID 是 共享还是新建（update_container_namespaces）。 当前 CubeShim 的 CreateSandboxRequest.sandbox_pidns 显式为 false，而 CreateContainerRequest 没有覆盖默认值（Sandbox 请求构造， Container 请求构造），所以本文把 “PID 默认分离”作为当前主路径事实。

    多 Container Template 的 restore 映射

    Template build 时，Cubelet 使用确定性 ID：首 Container 是 <templateID>_0，第 N 个是 <templateID>_<N>（ID 生成规则）。 restore 时：

    1. first Container 优先从 metadata.json.app_snapshot_container_id 恢复原 ID；
    2. 后续 Container 的 CBRI CreateContainer hook 根据 container index 注入 <templateID>_<index>；first Container 走上一步的 Sandbox hook，不走该分支；
    3. CubeShim 把新的 host/containerd real_id 映射为 snapshot 内 guest id；
    4. agent 按该 guest ID 查找 snapshot 中已有 Process，而不是新建并二次 exec。

    这些边分别由 first Container metadata/fallback 解析、 per-container restore annotation、 CubeShim 的 id/real_id 映射和 agent restore lookup支撑。

    [工程判断] 多 Container Template 必须在 build 时就包含完整 Container 集合，并在 restore 时保持 index/语义对应。/cube/template/from-image 只生成一个 Container；不能 把它当成多 Container Template，然后在恢复请求中任意追加第二个 Container。虽然固定 源码具备 <templateID>_<index> 的多 Container restore 映射，但本次没有发现覆盖 “多 OCI Container Template build -> snapshot -> restore -> 全部 probe”整条链路的 端到端测试，因此生产采用前仍应补一项 KVM 集成验证。

    Cubelet 到 guest workload 的实际运行链

    组件深度

    1. Cubelet：节点 workflow owner。 service.Create 校验请求、补默认值、选择 cube runtime 并运行 workflow；创建 CubeBox 和 container records，准备 OCI spec、rootfs/volumes，再通过 containerd NewContainer/NewTask/Start 触发 shim。Cubelet 不实现 VMM。
    2. CubeShim：containerd Shim v2 和 Sandbox runtime group。 containerd-shim-cube-rs 为 task API 提供服务，TaskService 持有一个 SandBox。第一个 NewTask 同步完成 VM boot/restore、agent connect、guest sandbox create 和 guest container create后才返回。
    3. VMM：CubeShim 同进程线程。 VmmInstance 建立 request/response channels 与 EventFd；VMM thread 持有 KVM VM、vCPU、memory/device model。CubeShim 以 ApiRequest::VmCreate/VmBoot/VmRestore 控制它。
    4. guest agent：vsock/ttrpc server。 CubeShim 连接 /run/vc/vm/<sandboxID>/cube.sock 后发送 CONNECT 1024，再复用 fd 建 ttrpc client；agent 在 guest port 1024 注册 agent/health services。
    5. rustjail：内嵌 OCI executor。 CreateContainer 处理 storage/device/OCI bundle，构造 LinuxContainer 和 init Process；StartContainer 写 FIFO 放行子进程，最终 execvp 替换成 workload。

    明确纠正 guest containerd/runc 说法

    [本地事实] 节点配置同时存在 io.containerd.cube.rs 与可选 host io.containerd.runc.v2（runtime 配置把两条 host 路径列为独立 handler），但本文 microVM 链选的是前者。guest cube-agent manifest 直接依赖 workspace rustjail（agent 的 Cargo manifest 声明 rustjail dependency），RPC 又直接构造 LinuxContainer。因此：

    • [未确认] guest image 是否额外包含未参与主链的 containerd/runc 二进制未检查，不影响主调用链结论。

    生命周期二：Template -> 新 Sandbox restore

    1. Master 解析逻辑 Template。 API 请求只需 alias/templateID；Master 读取 TemplateDefinition.RequestJSON，合并 containers、volumes、network/runtime 等模板配置，只选择健康、非 stale 的 READY replica 所在节点。
    2. Cubelet 生成新身份并解析本地物理引用。 运行 sandboxID 随机生成，不复用 templateID 或 <templateID>_0。Cubelet 从 tpl-<templateID>-rootfs 派生 sb-<sandboxID>-rootfs-gen0，从 catalog 读取 memory object 并重新 ResolveDevPath。
    3. annotations 绑定 restore。 Cubelet/CBRI 写入 cube.vm.snapshot.path 与 fresh cube.vm.snapshot.memory_vol_url；CubeShim 对 restore 缺少 memory URL 会直接报错。
    4. CubeShim/VMM restore。 首 task 读取 metadata，校验 CPU/memory/kernel/disk/pmem compatibility，以 <snapshotPath>/snapshot 为 source，并动态替换 fs/net/disk/pmem/vsock 与 memory URL，再调用 VMM restore。
    5. 重新关联 guest process。 snapshot 保存原 app_snapshot_container_id。新的 host/containerd ID 通过 annotation 映射到原 guest container ID；agent 查找已恢复 process并重连 IO/mount propagation，不新建 LinuxContainer。
    6. 不二次 exec。 restore 时 guest id != real_id，CubeShim Start 不再调用 agent StartContainer，只恢复 wait/log/IO 管理。

    关键证据：Master 把 Template request 合并进 Sandbox create request 并校验可用 replica；Cubelet 从 template rootfs 创建 sandbox rootfs 派生对象并从 catalog 解析 fresh memory device，miss 时失败；CBRI 注入 snapshot path 和 memory URL annotations；CubeShim restore_vm 校验 metadata并构造 restore config；guest agent 识别 snapshot container annotation 后查找并重连现有 process。

    Control、data、state 三条路径

    Control flow

    CubeAPI -> CubeMaster -> Cubelet workflow -> containerd Shim v2 Task API -> CubeShim -> {VMM API, guest agent ttrpc} -> rustjail。Master 决定调度和逻辑 Template；Cubelet决定节点执行顺序、probe 与回滚；CubeShim把 VM 控制和 guest container 控制分开；agent把 OCI lifecycle 转成 guest 内系统操作。

    Data flow

    • OCI/config： OCI image 在 Template build 阶段变成 ext4 RootfsArtifact；运行时 OCI spec 由 Cubelet 写入 containerd bundle，CubeShim读取并 protobuf 化传给 agent。
    • rootfs/volume： ext4/pmem、CubeCoW writable rootfs 和 external volumes 由 Cubelet编码进 annotations/storage；VMM/virtiofs/pmem/disk跨 host/guest，agent mount后由 rustjail纳入 container root。
    • memory/state： Template RAM 写入 tpl-<id>-memory，VMM config/state 写入 snapshot 子目录；restore 时 local catalog解析 fresh device URL，不能依赖构建时 memory.dev 字符串。
    • stdio/log： containerd task IO进入 CubeShim，可经专用 vsock/ttrpc connection 或 passfd port 1027连接 guest process pipes。
    • exit/OOM： guest agent wait/OOM事件经 CubeShim转换为 containerd task events；Cubelet保存 task wait channel并用于 probe/destroy 判断。

    Stop、delete 与已知缺口

    • [本地事实] Cubelet destroy 先标记 removing，按“first container 最后”的次序 stop containers；对运行 task发送 SIGKILL(all=true)、等待 exit、DeleteTask，再删除 containerd metadata（destroy workflow 展开 stop/delete 顺序）。
    • [本地事实] CubeShim Container::destroy_container 当前只保证 SIGKILL并返回 exit info，源码留有 todo: remove container in guest（当前 delete 实现明确暴露未调用 guest remove 的缺口）。
    • [本地事实] guest agent 已实现 do_remove_container，包括 kill、umount、bundle/cgroup/map 清理（该 RPC 实现完整 guest remove 操作），但当前 CubeShim delete path没有调用它。
    • [推断] 整体 Sandbox destroy 随后 poweroff VM，通常会回收整个 guest；但“单独删除某个 container且 VM继续运行”不能声称已完成精细 guest cleanup。
    • [本地事实] 当 shim container map为空时，shutdown调用 guest DestroySandbox；agent唤醒主流程执行 Linux poweroff，CubeShim等待 VmShutdown并 join VMM thread（CubeShim 的 sandbox shutdown 等待事件并回收 VMM thread，agent 的 destroy RPC触发 guest关机信号）。
    • [推断] 普通 destroy 主链是 container kill/wait/delete -> shim shutdown -> guest poweroff，而不是一个完整实现的 CubeHypervisor::stop_vm 对称 API。

    最终回答

    [本地事实] 在固定提交的 cube runtime 中，最准确的逻辑表达是 Sandbox 1 -> 1..N Container，最准确的活动运行映射是 Sandbox/CubeBox 1 -> CubeShim SandBox 1 -> active VM 1；Container共享一个 guest，guest agent使用内嵌 rustjail执行 workload。[推断] “Sandbox就是VM”可作为运行实体速记，但不能替代逻辑模型；“Container就是VM”以及“guest containerd/runc执行容器”均不符合主链源码。

    [本地事实] OCI Template 不是 OCI image的改名：它先经过独立 RootfsArtifact，再由临时 <templateID>_0 Sandbox运行并物化为节点 rootfs/memory/VMM state/catalog资产，最后由 Master发布逻辑 definition/replica。之后从 Template创建 Sandbox是另一次生命周期：新的 sandboxID、新的 CubeShim/VMM执行上下文、派生 rootfs和 restored guest process；其 ready边界必须按 restore特有的“跳过 VsockServerReady notify、但仍 connect agent并完成上层 gates”解释。
