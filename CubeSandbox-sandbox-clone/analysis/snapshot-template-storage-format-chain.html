    CubeSandbox Snapshot 与 Template 存储、格式、恢复链路专题

    本文系统分析 CubeSandbox 中 Snapshot 和 Template 的保存位置、保存格式、恢复链路、使用场景——从物理目录结构到 CubeCoW 对象再到 catalog 绑定，逐层拆解。

    源码基线：当前仓库工作树。

    相关：snapshot create/commit、template build from OCI、CubeCoW 存储引擎、snapshot catalog restore binding、snapshot-restore-kernel-deep-dive。

    0. 两类快照，四种场景

    CubeSandbox 有两类快照，对应四种使用场景：

    类型 kind 生产者 场景
    Template template AppSnapshot() 从 OCI 镜像构建可复制基线
    Runtime Snapshot runtime_snapshot CommitSandbox() 对运行中 sandbox 快照（支持增量）
    场景 触发 消费者 产出
    Template 构建 CubeAPI template create AppSnapshot 新 Template（full snapshot）
    Runtime Commit CubeAPI commit CommitSandbox 运行中 sandbox 的 snapshot（soft-dirty/incremental/full 三层退化）
    Clone/Restore CubeAPI sandbox create（带 template id） CubeShim restore_vm 从 Template clone 新 sandbox
    Rollback CubeAPI rollback CubeShim rollback_vm 删旧 VM + 从 runtime snapshot restore

    1. 保存位置：物理目录结构

    1.1 默认路径

    // Cubelet/services/cubebox/appsnapshot.go:35
DefaultSnapshotDir = "/usr/local/services/cubetoolbox/cube-snapshot"

    1.2 VMM snapshot 目录

    <snapshotDir>/cubebox/<snapshotID>/<specDir>/
├── config.json         # VMM VM 配置（serde_json 序列化的 VmConfig）
├── state.json          # VMM 运行状态（serde_json 序列化的 Snapshot + metadata）
└── catalog.json        # SnapshotCatalogEntry（物理对象绑定）

    specDir = "{CPU}C{Memory}M"（如 "2C4096M"）。同一 snapshot id 不同资源规格可共存——specDir 隔离不同 VM 形状的 snapshot。

    1.3 CubeCoW 对象布局

    CubeCoW 不在 snapshot 目录内——它在独立的 CubeCoW volumes 树中：

    <root_dir>/volumes/           ← CubeCoW ReflinkEngine 的唯一根
├── <templateID>/              ← 每个 volume 一个目录
│   └── <templateID>           ← volume 主文件（同名）
├── <templateID>_memory/       ← memory volume 目录
│   └── <templateID>_memory    ← memory volume 主文件
├── <sandboxID>_rootfs/        ← 从 template clone 的 sandbox rootfs
│   ├── <sandboxID>_rootfs     ← rootfs 主文件（FICLONE from template rootfs snapshot）
│   └── <gen_snapshot_name>    ← 可能有多个 generation snapshot
└── ...

    CubeCoW 对象不在 VMM snapshot 目录内——它们由 CubeCoW Rust engine（ReflinkEngine）独立管理。catalog.json 负责绑定 logical snapshot id 到 CubeCoW 对象名 + kind。

    1.4 catalog.json：logical→物理绑定

    // Cubelet/storage/snapshot_catalog.go:30
type SnapshotCatalogEntry struct {
    SnapshotID      string `json:"snapshot_id"`        // logical id（template id / runtime snapshot id）
    InstanceType    string `json:"instance_type"`       // "cubebox"
    SpecDir         string `json:"spec_dir"`            // "2C4096M"
    SnapshotPath    string `json:"snapshot_path"`       // VMM snapshot 目录绝对路径
    MetaDir         string `json:"meta_dir"`            // metadata 目录（通常 = SnapshotPath）
    RootfsVol       string `json:"rootfs_vol"`          // CubeCoW rootfs 对象名
    RootfsKind      string `json:"rootfs_kind"`         // "snapshot" 或 "volume"
    MemoryVol       string `json:"memory_vol"`          // CubeCoW memory 对象名
    MemoryKind      string `json:"memory_kind"`         // "snapshot" 或 "volume"
    BuildRootfsVol  string `json:"build_rootfs_vol"`    // 构建临时 rootfs（仅 Template，commit 后保留）
    BuildRootfsKind string `json:"build_rootfs_kind"`
    RootfsSizeBytes uint64 `json:"rootfs_size_bytes"`
    Kind            string `json:"kind"`                // "template" 或 "runtime_snapshot"
    CreatedAt       string `json:"created_at"`          // RFC3339 时间戳
}

    catalog.json 是 Cubelet 本地物理状态的权威。Master 只存 logical id + replica 状态——不存物理路径。create-from-template / rollback / replica reconcile 都先查 catalog。

    1.5 物理布局完整示例

    /usr/local/services/cubetoolbox/cube-snapshot/     ← DefaultSnapshotDir
└── cubebox/
    └── tpl-abc123/                                 ← snapshotID = templateID
        └── 2C4096M/                                ← specDir
            ├── config.json                          ← VmConfig JSON
            ├── state.json                          ← Snapshot + metadata JSON
            └── catalog.json                        ← SnapshotCatalogEntry

/data/cubecow-reflink/volumes/                     ← CubeCoW root_dir
├── tpl-abc123/
│   └── tpl-abc123                                  ← rootfs snapshot 主文件（FICLONE from build）
├── tpl-abc123_memory/
│   └── tpl-abc123_memory                           ← memory volume 主文件（full image）
├── sb-xyz001_rootfs/
│   └── sb-xyz001_rootfs                            ← sandbox rootfs（FICLONE from tpl-abc123）
└── sb-xyz001_memory/
    └── sb-xyz001_memory                             ← sandbox memory（restore from template）

    2. 保存格式：每类文件的内容

    2.1 config.json — VmConfig

    // CubeSandbox-sandbox-clone/hypervisor/vmm/src/vm.rs:2911  Vm::send
let vm_config = serde_json::to_string(self.config.lock().unwrap().deref())?;
snapshot_config_file.write(vm_config.as_bytes())?;
snapshot_config_file.sync_all()?;   // 确保落盘（跨机器 pause-snapshot 一致性）

    config.json 是 VMM 启动配置的 JSON 序列化——含 CPUs/memory/kernel/payload/disks/net/fs/pmem/vsock/balloon 等全部 VM 配置字段。restore 时 recv_vm_config() 反序列化恢复 VmConfig。

    2.2 state.json — Snapshot + metadata

    // CubeSandbox-sandbox-clone/hypervisor/vmm/src/vm.rs:2950
let mut snapshot_with_meta = snapshot.clone();
snapshot_with_meta.metadata = Some(vm_migration::SnapshotMetadata {
    snapshot_type: config.snapshot_type,   // full / incremental / soft-dirty
});
let vm_state = serde_json::to_vec(&snapshot_with_meta)?;
snapshot_state_file.write(&vm_state)?;

    state.json 是 VMM 运行状态的 JSON 序列化——含 CPU state（每 vCPU 寄存器）、DeviceManager state（device_tree + 每设备 Migratable state）、MemoryManager snapshot data（memory_ranges + guest_ram_mappings + hotplug slots）。memory 字节不在 state.json 内——在 CubeCoW memory volume 中。

    2.3 CubeCoW volume 文件 — guest RAM / rootfs

    CubeCoW volume 是 XFS reflink 文件——内容是原始字节（guest RAM 或 rootfs 文件系统镜像）。没有自定义序列化格式——就是 mmap 出来的字节。

    对象 kind 内容 大小
    Template rootfs snapshot FICLONE clone 自 build rootfs（OCI 镜像可写层） rootfs 大小
    Template memory volume VMM full snapshot 写入的完整 guest RAM VM 内存大小（如 4096 MB）
    Runtime rootfs snapshot 当前 sandbox writable rootfs（CommitTemplateRootfs） rootfs 大小
    Runtime memory snapshot（Tier 1/2）或 volume（Tier 3） FICLONE clone base + VMM 只写变化页 VM 内存大小
    Sandbox rootfs snapshot FICLONE clone 自 template rootfs rootfs 大小
    Sandbox memory volume（AppSnapshot restore）或 snapshot（Commit restore） 从 template/runtime memory restore VM 内存大小

    2.4 catalog.json — 原子写

    // Cubelet/storage/snapshot_catalog.go:140  WriteSnapshotCatalog
func WriteSnapshotCatalog(entry *SnapshotCatalogEntry) error {
    os.MkdirAll(entry.SnapshotPath, 0o755)
    path := filepath.Join(entry.SnapshotPath, "catalog.json")
    tmp := path + ".tmp"                           // 先写临时文件
    body, _ := json.MarshalIndent(entry, "", "  ")
    os.WriteFile(tmp, body, 0o644)
    os.Rename(tmp, path)                           // 原子 rename——要么完整可用，要么不存在
    // 同时更新内存缓存
    snapshotCatalogIndex[entry.SnapshotID] = cloneCatalogEntry(entry)
}

    原子写保证：tmp + rename 确保 catalog 要么完整写入，要么不存在——不会看到半完成的 catalog。内存缓存避免每次查 catalog 都读文件。

    3. 保存链路：从 API 到物理文件

    3.1 AppSnapshot（Template 构建）

    flowchart TB A["CubeAPI template create\n(annotation: template id)"] --> B["CubeMaster templatecenter\nrunSnapshotCreateJob"] B --> C["Cubelet AppSnapshot()"] C --> D["Step 1: 建临时 cubebox\n(workflow create + containerd)"] D --> E["Step 2: 从 spec 提取\nCubeboxSnapshotSpec"] E --> F["Step 3: CreateTemplateMemoryVolume\nCubeCoW 建空 volume"] F --> G["Step 4: cube-runtime snapshot\n--snapshot-type full\npause → snapshot → resume"] G --> H["VMM 写 config.json + state.json\n到 tmpSnapshotPath"] G --> I["VMM 写 memory 全量\n到 CubeCoW memory volume"] H --> J["Step 5: CreateTemplateRootfsFromBuild\nCubeCoW FICLONE clone build rootfs"] I --> j["Step 5: memory volume 已写满"] j --> K["Step 6: Destroy 临时 cubebox"] K --> L["Step 7: Rename tmp → 最终路径\nWriteSnapshotCatalog\nwriteSnapshotFlag"]

    cube-runtime 命令行参数：

    // Cubelet/services/cubebox/appsnapshot.go:586
args := []string{
    "snapshot", "--app-snapshot",
    "--vm-id", sandboxID,
    "--path", snapshotPath,          // VMM snapshot 目录
    "--force",
    "--snapshot-type", "full",       // AppSnapshot 固定 full
    "--resource", resourceJSON,      // CPU/memory 配置
    "--disk", diskJSON,              // disk 配置
    "--pmem", pmemJSON,              // pmem 配置
    "--kernel", kernelPath,          // guest kernel
    "--container-id", containerID,
    "--memory-vol", "file://<devPath>",  // CubeCoW memory volume 设备路径
}

    3.2 CommitSandbox（Runtime Snapshot）

    flowchart TB A["CubeAPI commit\n(template id + sandbox id)"] --> B["CubeMaster templatecenter"] B --> C["Cubelet CommitSandbox()"] C --> D["校验 cubecow backend + sandbox 运行"] D --> E["CommitTemplateRootfs\nCubeCoW FICLONE clone 当前 rootfs"] D --> F["prepareCommitMemoryArtifact\n三层退化"] F --> F1{"Tier 1\nresolveBaseMemoryObject\n(上次 snapshot binding)"} F1 -->|"可用"| G1["FICLONE clone base + soft-dirty"] F1 -->|"不可用"| F2{"Tier 2\nresolveRestoreBaseMemoryObject\n(上次 restore base)"} F2 -->|"可用"| G2["FICLONE clone base + incremental"] F2 -->|"不可用"| G3["新建空 volume + full"] G1 --> H["cube-runtime snapshot\n--snapshot-type soft-dirty/incremental/full\npause → snapshot → resume"] G2 --> H G3 --> H H --> I["VMM 写 config.json + state.json"] H --> J["VMM 只写变化页到 CubeCoW memory volume"] I --> K["setRuntimeSnapshotBindingLabels\n更新 binding"] J --> K K --> L["WriteSnapshotCatalog\nkind=runtime_snapshot"]

    Template 和 Runtime Snapshot 的保存路径结构完全一样（<snapshotDir>/cubebox/<id>/<specDir>/），区别只在 catalog.json 的 Kind 字段和 memory 的增量方式。

    4. 恢复链路

    4.1 Create-from-Template

    flowchart TB A["CubeAPI sandbox create\n(template id + spec dir)"] --> B["Cubelet storage action"] B --> C["GetLocalSnapshot templateID\n查 catalog.json"] C --> D["CreateSandboxRootfsFromTemplate\nCubeCoW FICLONE clone rootfs"] C --> E["prefetchRestoreMemoryVolURL\n查 catalog 拿 memory volume dev path"] E --> F["memory_vol_url = file://devPath"] D --> G["CubeShim start_vm + restore_vm"] F --> G G --> H["CubeHypervisor vm_restore\nrecv_vm_config\nnew_from_snapshot\nMemoryManager restore\nVm::restore + resume"]

    4.2 Rollback

    5. CubeCoW 对象的生命周期

    5.1 对象 kind 与角色

    kind 含义 创建方式 可 FICLONE？
    volume 可写主文件 create_volume()（set_len + fsync） ✓（作为 FICLONE source）
    snapshot FICLONE clone（CoW 共享 extent） create_snapshot(source, name) ✓（snapshot-of-snapshot 放 ultimate origin）

    snapshot 不复制数据——FICLONE 后两个文件共享 XFS extent。写入时 XFS CoW fork 分配新 block。删除源文件不影响 snapshot（reflink 引用计数保护）。

    6. 使用场景总结

    6.1 Template（AppSnapshot 产出）

    场景 触发 链路
    首次构建 CubeAPI template create AppSnapshot：建临时 cubebox → full snapshot → rootfs from build
    Clone 新 sandbox CubeAPI sandbox create（带 template id） catalog 查 template → FICLONE clone rootfs → restore memory → VMM restore
    Template 删除 CubeAPI template delete CubeCoW 删 rootfs/memory volume + 删 snapshot 目录 + 删 catalog
    Template 跨节点复制 replica reconciler CubeMaster 查 catalog → 经 Cubelet gRPC 校验 → 需要外部机制复制 CubeCoW 文件

    6.2 Runtime Snapshot（CommitSandbox 产出）

    场景 触发 链路
    运行中 sandbox 快照 CubeAPI commit CommitSandbox：CommitTemplateRootfs + prepareCommitMemoryArtifact → cube-runtime snapshot
    Rollback CubeAPI rollback catalog 查 runtime snapshot → CubeShim rollback_vm → VmDelete + drain + restore
    增量 commit 连续多次 CubeAPI commit 每次 Tier 1 soft-dirty（FICLONE clone 上次 snapshot memory → VMM 只写 soft-dirty 页）
    Binding 失效后首次 commit opaque restore / binding invalid 自动退化到 Tier 3 full（新建空 volume → VMM 写全部）

    6.3 增量 snapshot 的 binding 状态机

    stateDiagram-v2 [*] --> Full: AppSnapshot（full） Full --> SoftDirty: Commit（binding 可用） SoftDirty --> SoftDirty: Commit（连续增量） SoftDirty --> Incremental: binding 失效 → restore base 可用 Incremental --> SoftDirty: Commit（新 binding 建立） Full --> Full: binding 失效 + restore base 不可用 SoftDirty --> Full: opaque restore（binding invalidate）

    8. 能力边界与已知限制

    问题 结论
    snapshot 是否跨架构 restore 不能——VMM state 含架构特定状态（GIC vs IOAPIC），CubeCoW 文件不能跨架构 reflink
    catalog 是否跨节点 不跨——catalog.json 是本地文件，跨节点由 replica reconciler 校验
    Template rootfs 是否可修改 不能（snapshot kind = immutable）；clone 后 sandbox rootfs 可写
    增量 snapshot 是否保存 delta 不保存——目标始终是完整 image，增量只覆盖变化页
    Commit 后 runtime binding 是否更新 RuntimeSnapshotID 更新；RuntimeRestoreSnapshotID 不更新（pagemap_anon 语义需要 restore base 不变）
    opaque restore 后 binding invalidateRuntimeSnapshotBindingsAfterOpaqueRestore 标 invalid → 下次 Commit 走 full
    并发 restore 瓶颈 c100 p99 ~2.7s（内存带宽 + KVM slot 锁 + fd 池争用）
    snapshot 目录是否含网络状态 不含——网络由 network-agent 当前状态重建
