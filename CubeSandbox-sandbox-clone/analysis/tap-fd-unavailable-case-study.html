CubeSandbox ARM64 tap fd unavailable 故障案例分析

本文承接 ARM64 网络失败原型 和 ARM64 网络实测样本记录。

目标不是再做一层抽象归纳。

目标是把已经在 ARM64 样本里真实出现过的：

tap fd unavailable

沿源码和现有报告串成一条具体故障链。

源码基线：当前工作树。

1. 核心结论

tap fd unavailable 不是 virtio-net 队列问题。

它发生在更早的一层：

network-agent 把原始 TAP fd 交给 Cubelet fd 池这一步。

更具体地说，这条故障链跨了四段：

  1. network-agent 的 GetTapFile()
  2. restoreTap() 对现存 TAP 状态的判断
  3. Cubelet 通过 requestNetworkAgentTapFile() 请求 fd
  4. hypervisor open_tap() 的快速路径是否还能拿到同一个 fd

现有 ARM64 基准报告已经证明：

优化前，这条链在并发创建场景里会打出 tap fd unavailable ... Link not found。

优化后，这一类错误在 5 轮全量测试中降到了 0 次。

2. 真实错误签名

仓库里的 ARM64 网络优化报告给出了完整错误文本。

基线复现示例是：

CubeMaster returned error code 130547:
register network-agent tap for pool failed:
request original tap fd for <sandbox-id>:
tap fd unavailable for sandbox "...": Link not found

源码依据：arm64-network-opt-benchmark-report-20260613.md。

同一份报告还给出统计结果：

  1. baseline-fixed 阶段累计 14 次命中
  2. 优化后二进制 5 轮全量测试命中次数为 0

源码依据：arm64-network-opt-benchmark-report-20260613.md。

这让它和其他“只有源码原型”的失败类型不同。

它已经是一条有真实样本支撑的 ARM64 网络故障线。

3. 第一段：network-agent 为什么会返回 tap fd unavailable

network-agent 的 GetTapFile() 是这条故障的第一现场。

如果 state.tap 为空，或者 state.tap.File 为空，它会调用 restoreTapFunc(...) 重新构造 TAP 句柄。

源码依据：tap_fd_provider.go。

如果 restoreTapFunc(...) 返回错误，GetTapFile() 会直接包装成：

tap fd unavailable for sandbox %q: %w

源码依据：tap_fd_provider.go。

如果 restoreTap() 成功了，但 File 仍是空的，它还会直接返回：

tap fd unavailable for sandbox %q: tap %s is currently held by another process

源码依据：tap_fd_provider.go。

因此 tap fd unavailable 本质上是：

TAP fd 没能在当前时刻从 network-agent 一侧稳定交还给请求者。

它不是 guest 内的网卡配置失败。

4. 第二段：restoreTap() 为什么会走到 Link not found

restoreTap() 的职责是：

基于现存 TAP 名、IP、ifindex 和状态，重新构造 tapDevice。

它首先会按 name 做 netlinkLinkByName(name)。

如果 link 本身就找不到，restoreTap() 直接返回错误。

源码依据：netdevice.go。

这就能解释样本里的：

tap fd unavailable ...: Link not found

因为 GetTapFile() 只是把 restoreTap() 的错误向上包了一层。

也就是说，这个签名通常意味着：

network-agent 记录里的 TAP 名还在，但宿主机上对应的 link 在请求瞬间已经不存在了。

5. 第三段：为什么这个问题会在并发创建里放大

restoreTap() 还有一个很重要的分支。

如果 TAP 当前被认为 InUse，并且还没有拿到 File，它会跳过 fd 获取。

注释说明原因很直接：

对 IFF_ONE_QUEUE TAP 来说，如果另一个进程还持有原始 fd，TUNSETIFF 会因为 EBUSY 失败。

源码依据：netdevice.go。

这解释了为什么该问题在并发 Template create 里更容易出现。

并发创建时，TAP 的：

  1. link 是否存在
  2. 原始 fd 是否还被别的进程持有
  3. network-agent 何时尝试重新拿 fd

都更容易出现时序窗口。

因此这不是一个简单的单点 bug。

它更像：

TAP 链路状态和 fd 所有权在高并发下短暂失配。

6. 第四段：Cubelet 这边是怎样把错误放大的

Cubelet 会在 registerNetworkAgentTapForPool() 中主动向 network-agent 请求原始 TAP fd。

源码依据：plugin_tap.go。

真正发请求的是：

requestNetworkAgentTapFile(...)

如果返回错误，registerNetworkAgentTapForPool() 会把它包成：

request original tap fd for %s: %w

源码依据：plugin_tap.go。

这也是为什么样本里最终会出现三段连起来的错误：

  1. register network-agent tap for pool failed
  2. request original tap fd for ...
  3. tap fd unavailable ...

因此从 Cubelet 侧看，这个故障并不是 cubetap socket 本身写失败。

它在请求 fd 的业务阶段就已经失败了。

7. 第五段：cubetap fd server 和 hypervisor 为什么不是第一责任点

Cubelet 自己的 cubetap fd server 是后续一段链。

它从 Name2MvmNet 查找 tap file，再通过 WriteMsgUnix 把 fd 发出去。

源码依据：tap_provider.go。

只有在 registerNetworkAgentTapForPool() 成功之后，这个池子里才会真的存下 Tap.File。

而当前样本里的失败，正是发生在“把原始 TAP fd 放进池子”之前。

因此这类故障的第一责任点不是 cubetap server。

更不是 hypervisor open_tap() 里的快速路径。

相反，open_tap() 的快速路径只是后面一个受害者。

它优先调用 Tap::lookup_from_pool() 请求捐赠 fd，失败后才 fallback 到慢路径。

源码依据：open_tap.rs，tap.rs。

所以 tap fd unavailable 真正发生时，hypervisor 甚至还没拿到可用的池内 fd。

8. 第六段：为什么优化后这类错误消失了

仓库里的优化报告已经给出两项关键优化：

  1. CubeVS 侧缓存 pinned map/program fd
  2. network-agent 复用 TAP 池时，跳过已完成的 TC filter attach 和 ARP 安装

源码依据：arm64-network-opt-benchmark-report-20260613.md。

第二项和这条故障的关系最直接。

因为 restoreTap() 在恢复 pooled TAP 时，本来就可能再次做：

  1. filter attach
  2. ARP 安装

源码依据：netdevice.go。

如果这些恢复动作在高并发场景下重复发生，就更容易放大 TAP 状态切换窗口。

而优化后“已完成则跳过”，会让 pooled TAP 更少进入重复初始化路径。

从样本结果看，这一类错误的命中次数确实降到了 0。

这至少说明：

优化方向和故障链路是对齐的。

9. 这个案例真正证明了什么

这份案例分析现在已经能稳妥证明三件事。

第一，tap fd unavailable 不是 guest 内网络配置问题。

第二，它首先属于：

network-agent -> restoreTap -> Cubelet fd pool

这一段 host fd handoff 问题。

第三，现有 ARM64 优化样本已经证明：

围绕 pooled TAP 恢复路径做减法，确实能显著降低这一类并发故障。

10. 还没证明什么

这份案例分析还没有直接证明：

  1. 优化后 collect-logs.sh 中间层日志里每一次 pooled TAP 恢复都完全没有竞争
  2. 所有 tap fd unavailable 都来自同一个时序窗口
  3. 其它 snapshot/rollback/clone 异常与这条链绝对无关

因此下一步最值的仍然是：

在优化后二进制上再采一轮带 collect-logs.sh 产物的 ARM64 并发样本，把中间层日志补齐。

11. 结论

tap fd unavailable 是当前四个项目里，少数已经有“真实 ARM64 故障签名 + 源码链路 + 优化前后对照结果”的案例。

这让它很适合作为后续样本归档的模板。

后面再补其他项目的 ARM64 样本时，最理想的效果就是也达到这个粒度：

不是只知道“哪一层会坏”，而是能把真实签名和具体源码链条直接对上。
