    CubeSandbox VMM Device Restore 设备恢复链路

    本文展开 VMM Snapshot Restore 状态恢复链路 的下一步，聚焦 DeviceManager::create_devices() 与 DeviceManager::restore_devices() 如何协同恢复设备拓扑、后端和内部状态。

    结论只来自当前仓库源码。

    中断状态恢复（GIC/ITS/MSI-X route re-enable）见 中断状态恢复链路；virtio-net/fs 设备内部状态见 Virtio Net/Fs Restore 链路。

    0. 术语与背景

    两阶段恢复

    DeviceManager 的 restore 不是单一动作，而是两阶段：

    阶段 动作 入口
    ① 重建设备对象 先恢复 DeviceManagerState，再 create_devices() 按快照拓扑重建所有设备 DeviceManager::restore()
    ② 恢复内部状态 按 device tree 顺序对每个 migratable 设备 pause() + restore() DeviceManager::restore_devices()

    关键概念

    • device tree：restore 的物理拓扑记录。不只是逻辑设备列表，还保存 parent/children 关系、PCI BDF、BAR/MMIO 资源（Resource::MmioAddressRange）。DeviceManagerState 只有 device_tree 和 device_id_cnt 两个字段（device_manager.rs:1305）。
    • restoring 标志：Vm::new_from_memory_manager() 创建 DeviceManager 时传入（vm.rs:557）。restore 路径下 restoring=true，设备构造函数据此决定"复用快照资源"还是"新分配"。
    • state_from_id(snapshot, id)：多数 virtio 构造函数会调它，把快照里对应 id 的子状态传给设备对象——所以设备在构造阶段就已经读到了自己的快照状态。
    • Migratable trait：设备实现 snapshot()/restore()/pause()。阶段 ② 只对 node.migratable 非空的节点操作。

    核心约束：restore 要求设备拓扑与快照一致——device tree、BDF、BAR、MMIO range 都来自快照状态，不能随意改。

    1. 核心结论

    • 阶段 ①"按快照拓扑重建设备对象"：DeviceManager::restore() 先 set_state(DeviceManagerState)，再 create_devices(None,None,None)。
    • 阶段 ②"恢复每个 migratable 设备内部状态"：Vm::restore() 在 CPU/GIC 状态处理后调 restore_devices()。
    • 设备构造阶段已读子快照（state_from_id）；restore_devices() 不重新分配拓扑，只按 device tree 顺序恢复队列/寄存器/backend 内部状态。
    • ARM64 与 x86_64 差异不在 virtio 设备类型，而在 legacy device、中断控制器、PIO/MMIO、ACPI/FDT 描述方式。

    2. 两阶段恢复模型

    flowchart TD A["Vm::new_from_snapshot"] --> B["Vm::new_from_memory_manager(restoring=true)"] B --> C["DeviceManager::new(snapshot)"] C --> D["Vm::restore(snapshot)"] D --> E["DeviceManager::restore"] E --> F["set_state(DeviceManagerState)"] F --> G["create_devices(None,None,None)"] G --> H["construct devices with state_from_id"] D --> I["restore_devices"] I --> J["pause + restore each migratable device"]

    3. create_devices 的主顺序

    flowchart LR Start["create_devices"] --> IRQ["add_interrupt_controller"] IRQ --> Legacy["add_legacy_devices"] Legacy --> ACPI["add_acpi_devices"] ACPI --> Console["add_console_device"] Console --> Virtio["make_virtio_devices"] Virtio --> PCI["add_pci_devices"] PCI --> Other["pvpanic / ivshmem"]

    先建中断控制器再建 legacy interrupt manager（依赖顺序，详见 中断注入 trace §3）→ 挂 MemoryManager ACPI 区 → legacy/ACPI/console/TPM → virtio 设备收集成 MetaVirtioDevice 列表 → add_pci_devices() 统一变 PCI 设备（device_manager.rs:1216/1288）。

    阶段 ① 先 set_state()，所以后续构造函数能从旧 device tree 找回资源（BDF、BAR、MMIO range）。

    4. virtio 设备构造顺序

    make_virtio_devices() 顺序：block → net → rng → fs → pmem → vsock → mem → balloon → watchdog → vDPA（device_manager.rs:2172）。每个设备先构造自身 virtio backend，再把 migratable 句柄写入 device tree。

    设备 构造入口 restore 关键点
    block make_virtio_block_device() 重新打开 disk path，按 id 读设备快照（device_manager.rs:2214）
    net make_virtio_net_device() tap/fds/ip 后端，按 id 读快照（:2384）
    fs make_virtio_fs_device() native backendfs 或 vhost-user-fs
    pmem make_virtio_pmem_device() 复用快照中的 MMIO range
    vsock make_virtio_vsock_device() 同时恢复 device 和 backend 子状态（:2898）

    5. pmem 的资源复用（"换 file，不换地址"）

    pmem 是理解 restore 拓扑边界的关键。make_virtio_pmem_device() 先查 device tree——找到同 id node 就认为在 restore，从 node.resources 里复用 MmioAddressRange：

    // hypervisor/vmm/src/device_manager.rs:2712
let region_range = if let Some(node) = self.device_tree.lock().unwrap().get(&id) {
    debug!("Restoring virtio-pmem {} resources", id);
    let mut region_range: Option<(u64, u64)> = None;
    for resource in node.resources.iter() {
        match resource {
            Resource::MmioAddressRange { base, size } => {     // 复用快照里的 base/size
                region_range = Some((*base, *size));
            }
            _ => { /* ... */ }
        }
    }
    region_range
} else {
    None       // 新建设备才新分配 range
};
// 随后打开【当前】pmem_cfg.file, mmap 到原 guest physical address
    flowchart TD P["pmem config id"] --> T{"device tree has id?"} T -->|yes| R["reuse saved MmioAddressRange"] T -->|no| N["allocate new range"] R --> F["open current pmem file"] N --> F F --> M["mmap file"] M --> U["MemoryManager create_userspace_mapping"] U --> V["virtio_devices::Pmem::new"]

    这就是"换后端，不换拓扑"的具体实现：pmem 的 guest 地址布局来自快照（base/size 复用），但 file 来自当前节点。所以 CubeShim 要在 restore 前对齐 pmem metadata——VMM 能换 file，但不能改 pmem 的 guest 地址。

    6. PCI 包装与 device tree

    virtio 设备最终包装成 VirtioPciDevice。add_virtio_pci_device() 创建 virtio-pci-<id> 父节点，原 virtio device node 的 parent 指向它（device_manager.rs:3591）；PCI BDF/BAR 经 pci_resources() 分配或复用后写回 node；包装完注册 ioeventfd 并保存 BDF/handle/migratable 句柄（:3699）。AddressManager 在 BAR 更新时同步更新 allocator/bus range/device tree resource（:625）。

    7. restore_devices 的顺序语义

    阶段 ② 的核心是两组反序遍历 + 组间等待。源码最能说明：

    // hypervisor/vmm/src/device_manager.rs:4478
pub fn restore_devices(&mut self, snapshot: Snapshot) -> Result<(), MigratableError> {
    // 注释：必须按正确顺序恢复——children 先于 parent。所以用 device tree 反序遍历。
    let devices_children: Vec<_> = self.device_tree.lock().unwrap()
        .breadth_first_traversal_children().rev().cloned().collect();   // 第 1 组：children 反序
    let devices_parent: Vec<_> = self.device_tree.lock().unwrap()
        .breadth_first_traversal_parent().rev().cloned().collect();     // 第 2 组：parent 反序
    self.restore_device_node((devices_children, devices_parent), snapshot)?;
    self.restoring = false;
    Ok(())
}

    restore_device_node 用 tokio 多线程运行时，组内并发、组间严格等待；每个 migratable 节点要求快照里有同 id 子快照（否则 Missing device <id>），且先 pause() 再 restore()：

    // hypervisor/vmm/src/device_manager.rs:4426
rt.block_on(async move {
    let groups = [device_groups.0, device_groups.1];
    for (group_index, nodes) in groups.into_iter().enumerate() {        // 逐组处理
        let mut thread_pool = vec![];
        for (_i, node) in nodes.into_iter().enumerate() {
            if let Some(migratable) = node.migratable {
                let node_id = node.id.clone();
                if let Some(snapshot) = snapshot.snapshots.get(&node_id).cloned() {
                    thread_pool.push(tokio::spawn(async move {           // 组内并发
                        let mut guard = migratable.lock().unwrap();
                        guard.pause()?;                                   // 先 pause
                        guard.restore(*snapshot)?;                        // 再 restore
                        Ok(())
                    }));
                } else {
                    return Err(MigratableError::Restore(anyhow!("Missing device {}", node_id)));
                }
            }
        }
        for t in thread_pool { t.await.unwrap()?; }                      // 组间：等本组全完成
    }
    Ok(())
})?;
    flowchart TD A["device_tree"] --> B["children traversal reversed"] A --> C["parent traversal reversed"] B --> D["restore group 1 (concurrent)"] D --> E["wait all"] E --> F["restore group 2 (concurrent)"] F --> G["restoring=false"]

    三个要点：① children 必须先于 parent 恢复（拓扑依赖）；② 组内并发是为了缩短 restore 时间，但组间必须等待（await）；③ 缺任意设备子快照直接报错——这保证设备对象已创建并挂入 bus 后才恢复运行时状态。

    8. x86_64 与 ARM64 差异

    维度 x86_64 ARM64
    interrupt controller IOAPIC，进 MMIO bus 和 device tree（:1462） GIC 对象，不作为普通 device tree node（:1435）
    legacy I/O PIO + io_bus（:1603） MMIO + id_to_dev_info（:1694）
    serial 16550，固定 IRQ 4 和 0x3f8 PL011，动态 IRQ + 固定 MMIO
    power button ACPI GED GPIO + ACPI GED
    virtio 主路径 virtio-pci virtio-pci，PCI config 经 MMIO 描述
    restore 额外状态 依赖 PCI/IOAPIC/ACPI 依赖 GIC/ITS + MMIO legacy
    ACPI serial 描述 PNP0501 + I/O port（:4710） ARMH0011 + MMIO 地址

    9. 与 CubeSandbox restore 配置的关系

    CubeShim restore 传入 disk/net/fs/pmem/vsock 覆盖配置。VMM 在 vm_restore() 先把这些覆盖写入快照 VmConfig，随后 create_devices() 按修改后配置重建设备后端。

    所以 TAP/rootfs/pmem file/vsock socket 的替换发生在设备构造前；设备的 guest-visible 拓扑仍来自快照。这就是"换后端，不换拓扑"。

    10. 能力边界

    DeviceManager restore 的强约束：

    • device tree 中设备 id 必须与 snapshot 子快照匹配（否则 Missing device <id>）。
    • virtio-pci 父子关系、BDF、BAR/MMIO 资源必须能按快照重建。
    • pmem 的 guest address range 不能随意改变。
    • net 可换 tap 后端，但不能在此路径改变 virtio-net 数量。
    • vsock 可换 socket，但 device/backend 子状态必须可恢复。
    • ARM64 的 GIC/ITS 不走普通 device tree restore，需 VM 层专门恢复。

    这也解释了为什么跨架构 restore 不成立——x86_64 和 ARM64 的 legacy device、中断控制器、ACPI/FDT 暴露方式都不同。
