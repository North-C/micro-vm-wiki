    CubeSandbox ARM64 网络观测与取证指南

    本文承接 ARM64 网络验证矩阵。

    验证矩阵回答“该验什么”。

    本文继续回答“每个成功信号应该从哪里看见，失败时最先出现在哪一层”。

    源码基线：当前仓库工作树。

    1. 核心结论

    ARM64 网络问题要按链路观测，不能只盯一个日志面。

    最少要同时看四类证据：

    1. network-agent 是否把 TAP、TC filter 和 CubeVS 注册好。
    2. CubeShim 和 VMM 是否把 VM 启到 VsockServerReady，并激活 virtio-net。
    3. guest cube-agent 是否等到 PCI 网卡并完成 update_interface/update_routes。
    4. restore 后，GIC/ITS 与队列中断是否仍能把首包送进 guest。

    因此观测顺序必须和真实依赖顺序一致。

    应该先看 host 资源，再看 VMM ready，再看 guest 配网，最后看数据面和 restore。

    2. 总体观测图

    flowchart TB Host["host logs / netlink / tc / bpffs"] --> Shim["CubeShim / VMM ready"] Shim --> Guest["guest cube-agent logs"] Guest --> Data["packet path / queue wakeup"] Data --> Restore["restore after first packet"]

    这不是为了多看日志。

    而是因为每一层的失败都只会给出局部症状。

    如果跳层观测，很容易把 guest 配网失败误判成 VMM 中断失败，或者把 eBPF attach 失败误判成 virtio-net 故障。

    3. 第一组证据：network-agent 是否把 host 侧资源准备好

    newTap() 里已经埋了比较完整的阶段日志。

    它会依次打印：

    1. network-agent newTap begin
    2. network-agent newTap link add done
    3. network-agent newTap set vnet hdr done
    4. network-agent newTap link set up done
    5. network-agent newTap attach filter done
    6. network-agent newTap set mtu done
    7. network-agent newTap ready

    源码依据：netdevice.go。

    这组日志的价值很高。

    它能把“创建 TAP”“拿到 fd”“挂上 TC filter”和“host 侧接口 ready”分成独立阶段。

    如果 ARM64 节点的问题出在 TC 或 ioctl，这组日志会比 guest 侧更早暴露。

    registerCubeVSTap() 还会打印一条高价值日志：

    network-agent register cubevs tap: sandbox_id=... ifindex=... sandbox_ip=...

    同时带出 allow_internet_access、allow_out 和 deny_out。

    源码依据：local_service.go。

    因此 host 侧最小成功信号应当是：

    1. TAP 已创建并拿到 fd。
    2. attach filter done 出现。
    3. register cubevs tap 出现。

    如果缺少其中任一项，就不应继续把问题归因到 guest 内。

    4. 第二组证据：CubeVS/TC attach 失败通常会在哪里暴露

    CubeVS 的失败大多不会写成“ARM64 不支持”这种直白错误。

    更常见的是底层调用失败后返回具体错误文本。

    例如：

    1. can't load localgw/mvmtap/nodenic
    2. ebpf.NewCollectionWithOptions
    3. tc.Open failed
    4. tcnl.Qdisc.Add failed
    5. tcnl.Filter.Replace failed

    源码依据：bpf_arm64.go，miscs.go，tc.go。

    这些错误的定位方式也不同。

    can't load ... 和 NewCollectionWithOptions 更像对象加载或 verifier 问题。

    Qdisc.Add 和 Filter.Replace 更像 host tc/接口状态问题。

    因此一旦 guest 表现为“能看到网卡但没有数据流”，优先应回到这组错误文本。

    5. 第三组证据：VMM 是否真的把网络设备和 ready 状态送进 guest

    CubeShim start_vm() 在等待 VM ready 时，会优先等 NotifyEvent::VsockServerReady。

    成功时会打印：

    vm ready, vsock is listening (notify path)

    源码依据：sb.rs。

    这条日志证明的是 guest agent 通道 ready。

    它不能证明 guest 网络已经 ready。

    但如果连这条都没有，就不应该先查 guest eth0。

    virtio-net 激活后，设备层会打出：

    virtio-device activated

    源码依据：net.rs。

    再往下，PCI queue notify 与中断注入的结构性证据来自：

    1. VirtioPciDevice::ioeventfds() 暴露 queue eventfd
    2. VirtioInterruptMsix::trigger() 负责队列完成后的中断注入

    源码依据：pci_device.rs。

    因此这一层最小成功信号是：

    1. VM 到达 VsockServerReady
    2. virtio-net 设备完成 activated

    如果这两项已经有了，而 guest 仍无网络，问题更可能落在 guest 配网或 host eBPF 数据面。

    6. 第四组证据：guest cube-agent 是否真的完成了配网

    guest create_sandbox() 一开始会打：

    receive create sandbox

    源码依据：rpc.rs。

    如果接口带 pciPath，agent 会在真正配接口前打印：

    wait a pci:...

    源码依据：rpc.rs。

    这条日志很关键。

    它能区分“设备还没在 guest 内枚举出来”和“设备已出现但 netlink 配置失败”。

    guest 侧接口配置真正失败时，返回文案会直接带：

    Failed to update interface: ...

    路由失败会带：

    Failed to update routes: ...

    ARP 失败会带：

    Failed to add ARP neighbours: ...

    源码依据：rpc.rs。

    配网流程结束后，agent 会打印：

    create sandbox!, config net:...

    源码依据：rpc.rs。

    这条日志比单独的 receive create sandbox 更有意义。

    它至少说明 interface、routes 和 ARP 三段都已经走完。

    7. 第五组证据：guest 内接口定位为什么值得单独观察

    update_interface() 不按名字找网卡。

    它按 MAC 地址找 link，然后删旧地址、加新地址、设 MTU、改名并拉起。

    源码依据：netlink.rs。

    这意味着 ARM64 上如果 guest 枚举顺序变化，但 MAC 仍正确，流程理论上仍能成功。

    反过来，如果 MAC 不匹配，即使 virtio-net 设备已经在 guest 内出现，eth0 也可能永远配不上。

    因此对 ARM64 节点来说，最重要的 guest 侧观察点不是“有没有 virtio-net driver”。

    而是：

    1. wait a pci 是否成功。
    2. update_interface 是否成功。
    3. create sandbox!, config net 是否最终出现。

    8. 第六组证据：restore 之后该观察什么

    ARM64 restore 不是只恢复 CPU 和内存。

    VMM 会重新创建 VGIC，初始化 PMU IRQ，重建 GICR_TYPER，恢复 gic-v3-its section，再重新 enable interrupt routing。

    源码依据：vm.rs。

    同时 snapshot 路径会额外加入 VGIC snapshot section。

    源码依据：vm.rs。

    Gic::pause() 还会把 pending tables 和 ITS tables flush 到 guest RAM。

    源码依据：gic.rs。

    所以 restore 后的观测重点不是“restore 调用成功返回了没有”。

    真正该看的是：

    1. restore 前网络是否正常。
    2. restore 后 guest 是否仍到达 ready。
    3. restore 后首个入站包能否再次触发 guest 可见的 RX 进展。

    如果 restore 前后只有首包失效，优先怀疑中断恢复链，而不是 CubeVS attach。

    9. 推荐观测顺序

    建议把 ARM64 网络问题的取证顺序固定成下面五步。

    第一步：看 network-agent。

    确认 newTap ready 和 register cubevs tap 是否都出现。

    第二步：看 CubeShim/VMM。

    确认 vm ready, vsock is listening 和 virtio-device activated 是否都出现。

    第三步：看 guest agent。

    确认 wait a pci、Failed to update interface/routes 或 create sandbox!, config net 的最终结果。

    第四步：看数据面。

    结合 网络数据面与中断唤醒链路，区分是 from_cube、from_world/from_envoy 还是 RX/TX queue 唤醒问题。

    第五步：看 restore。

    只在前四步已经闭环的前提下，再判断 gic-v3-its 和首包唤醒是否异常。

    10. 取证模板

    可以把 ARM64 网络问题的证据整理成下面这张表。

    观测面 成功信号 失败锚点 典型归因
    network-agent newTap ready attach filter failed TAP/TC/eBPF host 侧失败
    CubeVS register cubevs tap can't load ... / Filter.Replace failed loader、verifier、tc attach 失败

    11. 结论

    ARM64 网络问题最难的地方，不是缺少代码入口。

    而是证据分散在 network-agent、CubeVS、VMM、CubeShim 和 guest agent 五个面。

    这份指南的作用，就是把它们重新按依赖顺序排好。

    以后继续补 ARM64 实测记录时，应该先把这五类证据填完整，再下结论说问题落在哪一层。
