CubeAPI Long Operation Contract 链路

本文聚焦 CubeAPI 的长操作契约：哪些路由走 240s 预算、哪些操作要求 CubeMaster 返回同步终态、AgentHub 如何包装。

源码基线：当前仓库工作树。

相关：CubeMaster snapshot job contract、API 到 Cubelet 创建链路。

0. 术语与背景

long route 不是异步任务系统

只是给慢操作更长 HTTP timeout——避免 CubeMaster/Cubelet 仍在工作时 API 层先 30s 超时。

同步终态约束

snapshot create/delete/rollback 的强约束：CubeAPI 收到成功响应时，继续检查 snapshot/operation status 必须为 READY。AgentHub 是例外——部分 API 返回自己的 operation 流水，甚至 tokio::spawn 后立即 202 Accepted。

1. 两条 HTTP 预算通道

// CubeAPI/src/routes.rs:26
const DEFAULT_ROUTE_TIMEOUT: Duration = Duration::from_secs(30);
// :38  240s 覆盖 ~99% 的 LVM/cubelet 操作
const SNAPSHOT_LONG_ROUTE_TIMEOUT: Duration = Duration::from_secs(240);
// :50  build_router 先构造 standard(30s) router，再 merge snapshot-long(240s) router

snapshot create/delete/rollback 走 240s router；普通 sandbox create/exec/update 走 30s router。

2. 能力边界

CubeAPI 路由层不区分 arm64/x86_64。架构差异下沉到 Cubelet/CubeShim/CubeHypervisor/网络/存储恢复路径。long route 只是 HTTP timeout 差异，不改变 CubeMaster/Cubelet 的执行语义。
