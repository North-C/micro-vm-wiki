    CubeShim Container 到 Guest Agent 生命周期链路

    本文下钻 CubeShim sandbox 与 CubeHypervisor 创建链路，分析 containerd task lifecycle 如何变成 guest cube-agent 的 container/process RPC。

    源码基线：当前仓库工作树。

    上游 Cubelet→containerd→CubeShim 的触发见 Cubebox Action 到 Containerd/CubeShim 链路；资源 update 的平台侧见 runtime control vmm update 链路。

    0. 术语与背景

    containerd shim v2 与 Task API

    CubeShim 是一个 containerd shim v2 进程——containerd 通过 ttrpc（containerd 的二进制 RPC）调用它的 TaskService（create/start/exec/kill/wait/delete/update）。CubeShim 不在 host 上 fork workload，而是把这些操作翻译成 ttrpc 请求发进 VM 给 cube-agent。

    host pid vs guest pid（关键区分）

    视角 pid 含义
    containerd 看到的（create/start/exit） shim 进程 pid（sb.pid() / std::process::id()）
    真实 workload pid 在 guest 内，由 cube-agent + rustjail 维护

    这与 Kata 同构：host runtime 管的是 shim/task 抽象，workload 真实进程在 VM 内。TaskExit.pid 也是 shim pid。

    两阶段语义

    containerd 的容器操作很多是两阶段——"创建记录"与"运行"分开：

    操作 阶段 1（创建记录） 阶段 2（运行）
    容器 create → agent CreateContainer（准备态） start → agent StartContainer（exec init）
    exec exec → 只存 Exec 记录 start(exec_id) → agent ExecProcess

    rustjail

    guest 内的容器运行时（类似精简 runc），由 cube-agent 调用，负责 namespace/cgroup/setup bundle/创建 LinuxContainer 和 Process。

    1. 结论先行

    CubeShim 的容器生命周期不是 host 侧直接 fork workload。containerd 请求进 CubeShim 后，被转成 ttrpc 请求交给 VM 内 cube-agent；退出事件由 CubeShim 后台 WaitProcess 任务转发（agent 等到 guest 进程退出 → 返回 exit code → CubeShim 发 containerd TaskExit）。

    flowchart LR Ctd["containerd Task API"] --> TS["CubeShim TaskService"] TS --> SB["SandBox"] SB --> C["Container"] C --> RPC["agent ttrpc"] RPC --> Agent["cube-agent"] Agent --> RJ["rustjail LinuxContainer"] RJ --> Proc["guest process"]

    2. TaskService 分发

    TaskService 持 Arc<Mutex<SandBox>>——一个 shim 服务内部对应一个 sandbox，后续 create/start/exec/kill/delete/update 都从此进入。create() 加载 OCI spec，首次 create 时初始化 sandbox（init + create_sandbox），然后调 sb.create_container()，返回 pid = sb.pid()：

    // CubeShim/shim/src/service/task_srv.rs:85
async fn create(&self, _ctx: &TtrpcContext, req: api::CreateTaskRequest) -> TtrpcResult<api::CreateTaskResponse> {
    let bundle = req.bundle.as_str();
    let spec = Utils::load_spec(bundle)?;                  // 加载 OCI spec
    let mut sb = self.sandbox.lock().await;
    if !sb.inited() {
        sb.init(spec.clone())?;                            // 首次：初始化 sandbox
        sb.create_sandbox().await?;
    }
    sb.create_container(req.id.clone(), spec, info).await?;
    Ok(api::CreateTaskResponse { pid: sb.pid(), ..Default::default() })  // pid = shim pid
}

    start() 按 exec_id 分流：空 exec_id = 启动容器 init；非空 = 启动 exec process（task_srv.rs:186/208/221）。

    3. Create Container

    Container::create_container() 构造 CreateContainerRequest（container id、exec id、storages、OCI protobuf spec、custom files）发 agent：

    // CubeShim/shim/src/container/mod.rs:373
pub async fn create_container(&mut self) -> CResult<()> {
    let req = agent::CreateContainerRequest {
        container_id: self.id.clone(),
        exec_id: self.id.clone(),
        storages: self.get_storages()?.into(),             // rootfs/volume
        OCI: Some(self.get_pb_spec()?).into(),             // 清理重写后的 OCI spec
        custom_files: self.get_custom_files()?.into(),     // 来自 annotation
        ..Default::default()
    };
    let client = self.client.as_ref().unwrap().lock().await;
    client.create_container(self.ctx.clone(), &req).await?;   // agent RPC
    self.state = Some(ContainerState::new(self.log.clone()));
    Ok(())
}

    guest agent 收到后先处理 device/storage，再更新 namespace/device cgroup/guest hooks，写 bundle，建 rustjail LinuxContainer 和 init Process（agent/rpc.rs:156 的 do_create_container → add_devices/add_storages/setup_bundle/LinuxContainer::new/Process::new）。

    这一步创建的是 guest 内 container init process 的准备状态，真正运行由后续 StartContainer 驱动。

    4. Start Container

    Container::start_container() 冷启动路径发 StartContainerRequest，随后创建后台 wait task：

    // CubeShim/shim/src/container/mod.rs:396
pub async fn start_container(&mut self) -> CResult<()> {
    let client = self.client.as_ref().unwrap().lock().await;
    if self.is_cold_start() {
        let req = agent::StartContainerRequest { container_id: self.id.clone(), ..Default::default() };
        client.start_container(self.ctx.clone(), &req).await?;   // agent StartContainer
    }
    if !self.sb_conf.app_snapshot_create {
        let state = self.state.as_mut().unwrap();
        state.wait_process(client.clone(), cid, real_id, String::new(), tx_containerd).await;  // 后台 wait
    }
    Ok(())
}
    sequenceDiagram participant TS as TaskService participant SB as SandBox participant C as Container participant Agent as cube-agent participant Ctd as containerd TS->>SB: start_container(id) SB->>C: start_container() C->>Agent: StartContainerRequest C->>Agent: WaitProcessRequest Agent-->>C: exit status C-->>Ctd: TaskExit

    agent do_start_container() 找 LinuxContainer 调 ctr.exec()；若启动的是 sandbox 容器自身直接返回，否则启动 OOM monitor（agent/rpc.rs:277/288）。

    5. Exec Process（两阶段）

    exec() 只创建 exec 记录（解析 OCI process spec、构造 Tty、sb.exec_container() → Container::create_exec() 把 Exec 放入 exec map，task_srv.rs:501/539、container/mod.rs:608）。真正运行在 start(exec_id)：Container::start_exec() 把 OCI process 转 ExecProcessRequest 发 agent exec_process()，再起 wait task 和 stdio 转发（container/mod.rs:629/688/692/703）。agent do_exec_process() 找 LinuxContainer、grpc process 转 OCI process、建 rustjail Process、open_io、ctr.run(p)（agent/rpc.rs:387/405/411/418）。

    6. Stdio 转发

    CubeShim exec 的 stdio 不直接共享 guest fd。Exec::forward_std() 起三个异步任务：stdin 从 host 文件读再调 agent write_stdin()；stdout/stderr 反向调 agent read_stdout()/read_stderr() 写回 host 文件（exec.rs:33/66/151/216、agent do_write_stream rpc.rs:603）。

    CubeShim 负责 containerd IO 文件与 guest process stream 的桥接；guest 内 process fd 的所有权仍在 agent/rustjail。

    7. Kill 与 Signal

    TaskService::kill() 把 container id/exec id/signal 交 sb.kill_container()；req.all=true 时 exec_id 置空（signal init 或全部进程，task_srv.rs:353、sb.rs:1060、container/mod.rs:425/463）。agent do_signal_process() 找 guest Process：init 的 SIGTERM 若无 handler 改发 SIGKILL；exec id 空则冻结 cgroup、枚举 cgroup pids、向剩余进程发信号（agent/rpc.rs:425/441/459）。

    8. Wait 与 TaskExit

    wait() 不等 host pid，调 sb.wait_container() 选 init/exec 的 ContainerState（task_srv.rs:237、sb.rs:1103）。后台 wait 在 wait_process_task() 发 WaitProcessRequest，把返回 status写 exit info 再发 containerd TaskExit：

    // CubeShim/shim/src/container/container_mgr.rs:86
async fn wait_process_task(&mut self, client, cid, real_cid, exec_id, tx_containerd) {
    let req = agent::WaitProcessRequest { container_id: cid.clone(), exec_id: exec_id.clone(), ..Default::default() };
    let rsp = tokio::select! { r = client.wait_process(ctx, &req) => r, /* signal 分支 */ };
    // ... exit code 处理 ...
    let event = TaskExit {
        container_id: real_cid.clone(),
        id: exec_id,
        pid: std::process::id(),              // TaskExit.pid 也是 shim pid
        exit_status: exit_info.0,
        exited_at: Some(e_tm).into(),
        ..Default::default()
    };
}

    agent do_wait_process() 找 guest process、把 watcher 放进 exit_watchers、等 exit signal（SIGCHLD 驱动，signal.rs:21）、清 stream 返回 WaitProcessResponse.status（agent/rpc.rs:533/553/587）。

    这条链是 containerd 事件与 guest workload 生命周期的桥。host pid ≠ workload pid，TaskExit.pid 也是 shim pid。

    9. Delete 与 Remove 边界（已知 gap）

    TaskService::delete() 空 exec_id 调 sb.delete_container()，非空调 sb.delete_exec()（task_srv.rs:278/301/325）。

    当前 CubeShim 的 destroy 边界有个重要 gap——destroy_container() 只发 SIGKILL 然后返回本地 exit info，源码留着 todo:remove container in guest：

    // CubeShim/shim/src/container/mod.rs:524
pub async fn destroy_container(&mut self) -> Result<(u32, DateTime<Utc>)> {
    self.signal_container(&"".to_string(), libc::SIGKILL as u32).await?;  // 只发 SIGKILL
    //remove
    //todo:remove container in guest
    //be lazy here
    Ok(self.state.as_ref().unwrap().get_exit_info().await)
}

    agent 侧确实实现了 RemoveContainerRequest（do_remove_container → rustjail destroy() + 删 sandbox container map，agent/rpc.rs:309/331/342），但当前 CubeShim destroy 路径没调 remove_container()。所以本文只把 agent remove 视为"已实现但未被该路径调用"的能力，不写成 containerd delete 的默认落点。

    10. Update Container

    update() 处理 resources（转 OCI LinuxResources）、sandbox annotations、扩展 update route（task_srv.rs:380/394/405）。Container::update() 只抽 CPU shares/quota/period/cpus + memory limit，构造 UpdateContainerRequest：

    // CubeShim/shim/src/container/mod.rs:745
pub async fn update(&mut self, res: &LinuxResources) -> CResult<()> {
    let mut pb_res = oci::LinuxResources::default();
    if let Some(c) = res.cpu() {
        let cpu = pb_res.mut_cpu();
        if let Some(v) = c.shares() { cpu.set_shares(v); }
        if let Some(v) = c.quota()  { cpu.set_quota(v); }
        if let Some(v) = c.period() { cpu.set_period(v); }
        if let Some(v) = c.cpus()   { cpu.set_cpus(v.clone()); }
    }
    if let Some(mem) = res.memory() {
        if let Some(limit) = mem.limit() { pb_res.mut_memory().set_limit(limit); }
    }
    let req = agent::UpdateContainerRequest { container_id: self.id.clone(), resources: Some(pb_res).into(), ..Default::default() };
    client.update_container(self.ctx.clone(), &req).await?;     // agent update_container
}

    agent update_container() 转 OCI resources 调 rustjail ctr.set()（更新 cgroup manager，rpc.rs:763、rustjail/container.rs:836）。

    11. Host PID 与 Guest PID

    视角 pid 含义 源码
    containerd create/start shim pid TaskService::create/start
    containerd exit event shim pid ContainerState::wait_process_task
    guest agent guest process pid rustjail::process::Process
    signal/wait agent 查 guest process Sandbox::find_container_process

    12. ARM64 与 x86_64

    CubeShim container lifecycle 主链路无显式架构分叉（TaskService/SandBox/Container/agent RPC/rustjail 同一套）。差异从这些层出现：guest process（rustjail/namespace/cgroup 共享）、storage/device path（取决于 guest 设备枚举）、ready notify（x86 I/O port vs ARM /dev/mem MMIO，agent/rpc.rs:1831）、PCI root path（agent/linux_abi.rs:12）、shim kernel cmdline/seccomp（config.rs:71、cube_hypervisor.rs:75）、VMM restore（CPU/GIC/CPUID/拓扑分叉）。

    ARM64 验证不能只看 TaskService 是否可调用——必须验证 guest image 中 rustjail/cgroup/namespace/storage handler/virtio-net/agent stream RPC 都能工作。

    13. 能力边界

    问题 结论
    containerd create 是否启动 workload 不直接启动；创建 guest container 准备态
    containerd start 的真实动作 agent StartContainer 触发 guest init exec
    exec 是否两阶段 是，exec 创建记录，start 才发 ExecProcess
    kill 是否 host kill 不是，转 agent SignalProcess
    wait 是否等 host pid 不是，等 agent WaitProcess
    delete 是否完整 agent remove 当前 destroy 路径未调 agent remove（todo）
    pid 是否是 guest pid containerd 侧不是，agent/rustjail 内才是
