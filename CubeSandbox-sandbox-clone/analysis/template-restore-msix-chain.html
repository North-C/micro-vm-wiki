基于 Template 启动到 RestoreVm 与 MSI-X Restore 的链路分析

本文解释两个问题：

  1. 基于 CubeSandbox Template 创建沙箱进行并发启动时延测试时，为什么运行链路会进入 RestoreVm。
  2. MSI-X restore 和观测到的 interrupt_group_update_many 分别对应哪一段执行链路。

本文聚焦 Template 启动时延路径，也就是基准测试中“基于 Template 创建沙箱”的 create-only 路径。

结论概览

基于 Template 创建沙箱不是一次冷启动 VM。CubeSandbox 的 Template 背后绑定的是 AppSnapshot/runtime snapshot。创建请求进入 CubeMaster 后，会先根据 template id 展开历史保存的创建请求；Cubelet 再把 snapshot 元数据转换成 OCI annotations；CubeShim 读取到 cube.appsnapshot.restore=true 后，会调用 hypervisor 的 VM restore 接口，而不是走完整冷启动路径。

核心调用链如下：

CubeAPI create sandbox
  -> CubeMaster dealCubeboxCreateReqWithTemplateCenter
  -> CubeMaster ConstructCubeletReq
  -> Cubelet cbri 生成 snapshot restore annotations
  -> Cubelet containerd NewTask / task.Start
  -> containerd-shim-cube-rs SandBox::start_vm
  -> SandBox::restore_vm
  -> CubeHypervisor::restore_vm
  -> VMM ApiRequest::VmRestore
  -> Vmm::vm_restore
  -> Vm::new_from_snapshot
  -> Vm::restore
  -> DeviceManager::restore_devices
  -> VirtioPciDevice::restore
  -> MsixConfig::restore / set_state
  -> MsiInterruptGroup::update
  -> KVM irqfd / GSI routing update

因此，在并发 Template 启动压测中，如果 Cubelet 侧的 storage/network 阶段耗时很小，而 CubeShim 的 RestoreVm 统计值接近整体 sandbox-start 耗时，说明瓶颈已经进入 shim/VMM 的 VM restore 阶段。后续定位应重点关注 VM 内存恢复、CPU/device manager 恢复、arm64 vGIC 恢复、virtio PCI 设备恢复、MSI-X 路由恢复和 KVM GSI routing 更新。

1. CubeMaster 展开 Template 请求

Template 路径从创建请求携带 template id annotation 开始。dealCubeboxCreateReqWithTemplate 会规范化 AppSnapshot annotations，然后在默认 Template 版本下进入 template-center 路径。

// CubeMaster/pkg/service/httpservice/cube/cubeboxutil.go:325
func dealCubeboxCreateReqWithTemplate(ctx context.Context, reqInOut *types.CreateCubeSandboxReq) error {
    if reqInOut.InstanceType != cubebox.InstanceType_cubebox.String() {
        return nil
    }
    constants.NormalizeAppSnapshotAnnotations(reqInOut.Annotations)

    templateID, hasTemplateID := reqInOut.Annotations[constants.CubeAnnotationAppSnapshotTemplateID]

    if !hasTemplateID && config.GetConfig().Common.EnableAGSColdStartSwitch {
        return handleColdStartCompatibility(reqInOut)
    }

    if constants.GetAppSnapshotVersion(reqInOut.Annotations) == templatecenter.DefaultTemplateVersion {
        return dealCubeboxCreateReqWithTemplateCenter(ctx, templateID, reqInOut)
    }

    return dealCubeboxReqTemplateByLocalConfig(ctx, reqInOut)
}

dealCubeboxCreateReqWithTemplateCenter 会读取 Template 保存的创建参数，确认本地 Template 可用，判断 Template 类型，然后把 Template 中的 annotations、volumes、containers、network type、runtime handler、namespace 等信息合并到当前创建请求中。

// CubeMaster/pkg/service/httpservice/cube/cubeboxutil.go:368
func dealCubeboxCreateReqWithTemplateCenter(ctx context.Context, templateID string, reqInOut *types.CreateCubeSandboxReq) error {
    templateReq, err := templatecenter.GetTemplateRequest(ctx, templateID)
    if err != nil {
        return fmt.Errorf("failed to get template param from store: %w", err)
    }
    constants.NormalizeAppSnapshotAnnotations(templateReq.Annotations)

    err = templatecenter.EnsureTemplateLocalityReady(ctx, templateID, reqInOut.InstanceType)
    if err != nil {
        return fmt.Errorf("template %s is not ready on any healthy node: %w", templateID, err)
    }

    templateKind, err := templatecenter.GetTemplateKind(ctx, templateID)
    if err != nil {
        return fmt.Errorf("failed to resolve template kind: %w", err)
    }

    if strings.EqualFold(templateKind, templatecenter.TemplateKindSnapshot) {
        if err := bindSnapshotCreateReplica(ctx, templateID, reqInOut); err != nil {
            return err
        }
    }

    applyTemplateAnnotationsAndLabels(templateReq, reqInOut)
    if !strings.EqualFold(templateKind, templatecenter.TemplateKindSnapshot) {
        if err := bindAppSnapshotTemplateReplica(ctx, templateID, reqInOut); err != nil {
            return err
        }
    }
    reqInOut.CubeVSContext = mergeCubeVSContexts(templateReq.CubeVSContext, reqInOut.CubeVSContext)

    reqInOut.Volumes = append(reqInOut.Volumes, templateReq.Volumes...)
    for i, templateCtr := range templateReq.Containers {
        if len(reqInOut.Containers) <= i {
            reqInOut.Containers = append(reqInOut.Containers, templateCtr)
            continue
        }
        if err := applyTemplateToContainer(reqInOut.Containers[i], templateCtr, i); err != nil {
            return err
        }
    }
    // network/runtime/namespace are also inherited from templateReq.
    return nil
}

这一阶段完成后，请求形式上仍然是普通 sandbox create request，但它已经携带了 Template/AppSnapshot 所需的元数据。

2. CubeMaster 构造 Cubelet 请求

ConstructCubeletReq 会保留 labels 和 annotations，并把 API 层的创建请求转换成 Cubelet 使用的 cubebox.RunCubeSandboxRequest。

// CubeMaster/pkg/service/sandbox/util.go:121
func ConstructCubeletReq(ctx context.Context, req *types.CreateCubeSandboxReq) (*cubebox.RunCubeSandboxRequest, error) {
    out := &cubebox.RunCubeSandboxRequest{
        RequestID:      req.RequestID,
        Labels:         req.Labels,
        InstanceType:   req.InstanceType,
        NetworkType:    req.NetworkType,
        Annotations:    make(map[string]string),
        RuntimeHandler: req.RuntimeHandler,
        Namespace:      req.Namespace,
        CubevsContext:  mapCubeVSContext(req.CubeVSContext),
    }

    err := checkAndGetAnnotation(req, out)
    if err != nil {
        return nil, ret.Err(errorcode.ErrorCode_MasterParamsError, err.Error())
    }
    if err = checkAndGetVolumes(req, out); err != nil {
        return nil, ret.Err(errorcode.ErrorCode_MasterParamsError, err.Error())

    if err = checkAndGetContainers(req, out); err != nil {
        return nil, ret.Err(errorcode.ErrorCode_MasterParamsError, err.Error())

    if err = getExposedPorts(req, out); err != nil {

    }
    return out, nil
}

关键点是：Template 展开后的 annotations 会继续传递到 Cubelet，后续 Cubelet 才能生成 shim 需要的 snapshot restore annotations。

3. Cubelet 将 Template 元数据转换成 Restore Annotations

Cubelet 的 cbri plugin 会根据 flowOpts 中的 template/snapshot 信息生成 OCI annotations。决定性 annotation 是：

cube.appsnapshot.restore=true

该 annotation 被 CubeShim 读取后，会让启动路径进入 snapshot restore。

// Cubelet/plugins/cbri/cubeboxcbri/cubebox.go:180

    }
    snapBasePath = paths.Base

    if err != nil {
        return nil, ret.Err(errorcode.ErrorCode_AppSnapshotNotExist, err.Error())

}

annotations[constants.AnnotationVMSnapshotPath] = snapBasePath

这里会设置 snapshot base path、snapshot memory volume URL、kernel/image 路径，以及 AnnotationAppSnapshotRestore=true。这些信息最终进入 OCI spec，供 containerd shim 读取。

这就是基于 Template 启动会进入 restore 路径，而不是从空 VM 冷启动的直接原因。

4. Cubelet 创建并启动 containerd Task / CubeShim

Cubelet 随后创建并启动 containerd task。基准测试中看到的 sandbox-start 统计，覆盖的是 NewTask 之前到 task.Start 之后的时间区间。

// Cubelet/services/cubebox/cube_container_create.go:1185
taskStart := time.Now()
task, err := c.NewTask(ctx, ioCreater, taskOpts...)
if err != nil {
    return transformError(err)
}
workflow.RecordCreateMetric(ctx, err, constants.CubeShimCreatetId, time.Since(taskStart))

exitCh, err := task.Wait(ctx)
if err != nil {
    return ret.Err(errorcode.ErrorCode_WaitTaskFailed, err.Error())
}

if err := task.Start(ctx); err != nil {
    return ret.Err(errorcode.ErrorCode_StartTaskFailed, err.Error())
}

workflow.RecordCreateMetric(ctx, err, constants.CubeShimStartId, time.Since(taskStart))

因此，如果压测数据中 sandbox-start 的大部分耗时与 CubeShim 的 RestoreVm stat 对齐，说明主要耗时已经在 shim/VMM restore，而不是 Cubelet 的存储准备或网络准备阶段。

5. CubeShim 判断并进入 RestoreVm

CubeShim 在 sandbox 初始化时解析 OCI annotations。如果 app_snapshot_restore 为 true，它会校验 fresh memory volume URL 是否存在。

// CubeShim/shim/src/sandbox/sb.rs:137
pub fn init(&mut self, spec: Spec) -> CResult<()> {
    self.spec = spec;
    let annotations = self.spec.annotations();
    self.conf = config::Config::new(annotations)?;
    if self.conf.app_snapshot_restore {
        let snapshot_base = annotations
            .as_ref()
            .and_then(|anno| anno.get(config::ANNO_SNAPSHOT_BASE))
            .map(|value| value.trim())
            .unwrap_or("");
        let snapshot_memory_vol_url = annotations
            .as_ref()
            .and_then(|anno| anno.get(config::ANNO_SNAPSHOT_MEMORY_VOL_URL))
            .map(|value| value.trim())
            .unwrap_or("");
        if snapshot_memory_vol_url.is_empty() {
            return Err(format!(
                "app snapshot restore requires fresh memory_vol_url annotation (cube.vm.snapshot.memory_vol_url); upstream must resolve the template memory volume for this start, snapshot_base:{}",
                snapshot_base
            ));
        }
    }
    Ok(())
}

start_vm 会先启动 VMM，然后在 sandbox 基于 snapshot 时调用 restore_vm。对于 AppSnapshot restore，restore 失败是致命错误，不会继续走冷启动兜底。

// CubeShim/shim/src/sandbox/sb.rs:781
async fn start_vm(&mut self) -> CResult<bool> {
    infof!(self.log, "start vm start");
    {
        let mut ch = self.ch.as_mut().unwrap().lock().await;
        ch.launch_vmm().await?;
    }
    let mut snapshot = false;

    if self.by_snapshot() {
        match self.restore_vm().await {
            Ok(_) => {
                snapshot = true;
                if self.conf.app_snapshot_restore {
                    return Ok(snapshot);
                }
            }
            Err(e) => {
                if self.conf.app_snapshot_restore {
                    return Err(format!("app snapshot restore vm failed:{}", e));
                }
            }
        }
    }
    // Cold boot fallback is only possible for non-AppSnapshot restore.
}

CubeShim 的 restore_vm 会构造 RestoreConfig，其中包含 snapshot path、运行时设备配置、网络配置、磁盘/pmem/vsock 配置，以及 fresh memory volume URL。

// CubeShim/shim/src/sandbox/sb.rs:946

shim 到 VMM 的调用是 ApiRequest::VmRestore。

// CubeShim/shim/src/hypervisor/cube_hypervisor.rs:173
pub async fn restore_vm(&self, config: config::RestoreConfig) -> CResult<()> {
    let ch = self.ch.as_ref().unwrap().lock().await;

    let restore_config = Arc::new(config);

        .map_err(|e| self.status_err(format!("Restore vm failed:{}", e)))?;
    stat.set_ok();
    Ok(())
}

6. VMM 处理 VmRestore

VMM 收到 VmRestore 后，会从 snapshot 读取 VM config 和 VM state，并用 RestoreConfig 中的运行时设备信息覆盖 snapshot 中的静态配置，然后基于 snapshot 构建 VM、恢复 VM 状态并 resume。

// hypervisor/vmm/src/lib.rs:653
fn vm_restore(&mut self, restore_cfg: RestoreConfig) -> result::Result<(), VmError> {
    let source_url = restore_cfg.source_url.as_path().to_str().ok_or(VmError::InvalidRestoreSourceUrl)?;
    let vm_config = Arc::new(Mutex::new({
        let mut vm_config = recv_vm_config(source_url).map_err(VmError::Restore)?;
        if let Some(disks) = &restore_cfg.disks {
            vm_config.update_disks(disks);
        }
        if let Some(nets) = &restore_cfg.net {
            vm_config.update_nets(nets);
        }
        if let Some(vsock) = &restore_cfg.vsock {
            vm_config.update_vsock(vsock);
        }
        if let Some(fses) = &restore_cfg.fs {
            vm_config.update_fses(fses);
        }
        if let Some(pmems) = &restore_cfg.pmem {
            vm_config.update_pmem(pmems);
        }
        vm_config.memory.dirty_log = restore_cfg.dirty_log;
        vm_config
    }));

    let snapshot = recv_vm_state(source_url).map_err(VmError::Restore)?;

    let mut vm = Vm::new_from_snapshot(
        &snapshot,
        vm_config.clone(),
        // events / seccomp / hypervisor omitted
        Some(source_url),
        restore_cfg.prefault,
        restore_cfg.memory_vol_url.as_deref(),
    )?;

    vm.restore(snapshot).map_err(VmError::Restore)?;
    vm.resume().map_err(VmError::Resume)?;
    self.vm_config = Some(vm_config.clone());
    self.vm = Some(vm);
    Ok(())
}

在 arm64 上，Vm::restore 中还包含 arm64 专有的 vGIC restore，然后才恢复所有设备并启动恢复后的 vCPU。

// hypervisor/vmm/src/vm.rs:2736
fn restore(&mut self, snapshot: Snapshot) -> std::result::Result<(), MigratableError> {
    if let Some(device_manager_snapshot) = snapshot.snapshots.get(DEVICE_MANAGER_SNAPSHOT_ID) {
        self.device_manager.lock().unwrap().restore(*device_manager_snapshot.clone())?;
    }

    if let Some(cpu_manager_snapshot) = snapshot.snapshots.get(CPU_MANAGER_SNAPSHOT_ID) {
        self.cpu_manager.lock().unwrap().restore(*cpu_manager_snapshot.clone())?;
    }

    #[cfg(target_arch = "aarch64")]
    self.restore_vgic_and_enable_interrupt(&snapshot)?;

    if let Some(device_manager_snapshot) = snapshot.snapshots.get(DEVICE_MANAGER_SNAPSHOT_ID) {
        self.device_manager.lock().unwrap().restore_devices(*device_manager_snapshot.clone())?;
    }

    self.cpu_manager.lock().unwrap().start_restored_vcpus()?;
    self.setup_signal_handler()?;
    self.setup_tty()?;
    Ok(())
}

这说明 arm64 的 restore 路径比普通设备恢复多了一段 vGIC/中断控制器恢复逻辑。并发启动时，如果该路径存在锁竞争、ioctl 开销或串行化热点，就可能放大整体启动时延。

7. MSI-X Restore 发生在哪里

DeviceManager::restore_devices 会遍历 device tree，并对每个可迁移设备调用 restore()。virtio PCI 设备的恢复就在这个阶段发生。

// hypervisor/vmm/src/device_manager.rs:4478
pub fn restore_devices(&mut self, snapshot: Snapshot) -> std::result::Result<(), MigratableError> {
    let devices_children: Vec<_> = self.device_tree.lock().unwrap()
        .breadth_first_traversal_children()
        .rev()
        .cloned()
        .collect();

    let devices_parent: Vec<_> = self.device_tree.lock().unwrap()
        .breadth_first_traversal_parent()
        .rev()
        .cloned()
        .collect();

    let device_groups = (devices_children, devices_parent);
    self.restore_device_node(device_groups, snapshot)?;
    self.restoring = false;
    Ok(())
}

遍历过程中，每个 migratable device 都会执行自己的 restore 方法。

// hypervisor/vmm/src/device_manager.rs:4450
for node in nodes {
    if let Some(migratable) = node.migratable {
        if let Some(snapshot) = snapshot.snapshots.get(&node.id).cloned() {
            thread_pool.push(tokio::spawn(async move {
                let mut guard = migratable.lock().unwrap();
                guard.pause()?;
                guard.restore(*snapshot)?;
                Ok(())
            }));
        }
    }
}

对 virtio PCI 设备而言，MSI-X 的恢复发生在 virtio common config、PCI config、virtqueue state 和设备 activate 之前。

// hypervisor/virtio-devices/src/transport/pci_device.rs:1201
fn restore(&mut self, snapshot: Snapshot) -> std::result::Result<(), MigratableError> {
    if let Some(virtio_pci_dev_section) =
        snapshot.snapshot_data.get(&format!("{}-section", self.id))
    {
        // Restore MSI-X
        if let Some(msix_config) = &self.msix_config {
            let id = msix_config.lock().unwrap().id();
            if let Some(msix_snapshot) = snapshot.snapshots.get(&id) {
                msix_config.lock().unwrap().restore(*msix_snapshot.clone())?;
            }
        }

        // Restore VirtioPciCommonConfig
        if let Some(virtio_config_snapshot) = snapshot.snapshots.get(&self.common_config.id()) {
            self.common_config.restore(*virtio_config_snapshot.clone())?;
        }

        // Restore PciConfiguration
        if let Some(pci_config_snapshot) = snapshot.snapshots.get(&self.configuration.id()) {
            self.configuration.restore(*pci_config_snapshot.clone())?;
        }

        self.set_state(&virtio_pci_dev_section.to_state()?)?;
        // Then activate the device.
    }
    Ok(())
}

因此，日志或 profile 中看到的 virtio_pci_restore_detail、msix_restore_profile，对应的就是 DeviceManager::restore_devices -> VirtioPciDevice::restore -> MsixConfig::restore/set_state 这一段。

8. interrupt_group_update_many 对应什么

interrupt_group_update_many 是部署版本日志/profile 中观测到的阶段名。当前源码中没有完全同名函数时，可以把它理解为 MSI-X restore 过程中对多个 MSI-X vector 重复或批量执行的 interrupt route update 工作。

更具体地说，它对应的是：

  1. 从恢复出的 MSI-X table entry 生成 MSI interrupt 配置。
  2. 对每个未 mask 的 MSI-X vector 调用 InterruptSourceGroup::update。
  3. 启用或重新注册对应 irqfd。
  4. 更新共享的 gsi_msi_routes。
  5. 调用 KVM set_gsi_routing 更新 GSI 路由表。

MsixConfig::set_state 会恢复 MSI-X table、PBA、masked/enabled 状态。如果 MSI-X enabled 且未整体 masked，就会遍历所有未 mask 的 table entry，并调用 interrupt source group 的 update/enable。

// hypervisor/pci/src/msix.rs:112
fn set_state(&mut self, state: &MsixConfigState) -> result::Result<(), Error> {
    self.table_entries = state.table_entries.clone();
    self.pba_entries = state.pba_entries.clone();
    self.masked = state.masked;
    self.enabled = state.enabled;

    if self.enabled && !self.masked {
        for (idx, table_entry) in self.table_entries.iter().enumerate() {
            if table_entry.masked() {
                continue;
            }

            let config = MsiIrqSourceConfig {
                high_addr: table_entry.msg_addr_hi,
                low_addr: table_entry.msg_addr_lo,
                data: table_entry.msg_data,
                devid: self.devid,
            };

            self.interrupt_source_group
                .update(idx as InterruptIndex, InterruptSourceConfig::MsiIrq(config), self.masked)
                .map_err(Error::UpdateInterruptRoute)?;

            self.interrupt_source_group
                .enable()
                .map_err(Error::EnableInterruptRoute)?;
        }
    }
    Ok(())
}

VMM 中的 interrupt group update 主要做三件事：

  1. 根据 MSI config 构造 KVM routing entry。
  2. 对 route 对应的 irqfd 执行 enable/disable。
  3. 锁住共享的 gsi_msi_routes，然后调用 KVM set_gsi_routing。
// hypervisor/vmm/src/interrupt.rs:168
fn update(
    &self,
    index: InterruptIndex,
    config: InterruptSourceConfig,
    masked: bool,
) -> Result<()> {
    if let Some(route) = self.irq_routes.get(&index) {
        let entry = RoutingEntry {
            route: self.vm.make_routing_entry(route.gsi, &config),
            masked,
        };
        if masked {
            route.disable(&self.vm)?;
        } else {
            route.enable(&self.vm)?;
        }
        let mut routes = self.gsi_msi_routes.lock().unwrap();
        routes.insert(route.gsi, entry);
        return self.set_gsi_routes(&routes);
    }

    Err(io::Error::new(io::ErrorKind::Other, format!("update: Invalid interrupt index {}", index)))
}

set_gsi_routes 会重建 active routes，并调用 hypervisor VM 的 set_gsi_routing。

// hypervisor/vmm/src/interrupt.rs:99
fn set_gsi_routes(&self, routes: &HashMap<u32, RoutingEntry>) -> Result<()> {
    let mut entry_vec: Vec<IrqRoutingEntry> = Vec::new();
    for (_, entry) in routes.iter() {
        if entry.masked {
            continue;
        }
        entry_vec.push(entry.route);
    }

    self.vm.set_gsi_routing(&entry_vec).map_err(|e| {
        io::Error::new(io::ErrorKind::Other, format!("Failed setting GSI routing: {}", e))
    })
}

KVM 层会实现 irqfd 注册和 routing entry 构造。arm64 上 MSI routing 还涉及 device id 限制；当 KVM 支持 Cap::MsiDevid 时，代码会对 devid 做改写。

// hypervisor/hypervisor/src/kvm/mod.rs:423
fn register_irqfd(&self, fd: &EventFd, gsi: u32) -> vm::Result<()> {
    self.fd
        .register_irqfd(fd, gsi)
        .map_err(|e| vm::HypervisorVmError::RegisterIrqFd(e.into()))
}

// hypervisor/hypervisor/src/kvm/mod.rs:507
fn make_routing_entry(&self, gsi: u32, config: &InterruptSourceConfig) -> IrqRoutingEntry {
    match &config {
        InterruptSourceConfig::MsiIrq(cfg) => {
            let mut kvm_route = kvm_irq_routing_entry {
                gsi,
                type_: KVM_IRQ_ROUTING_MSI,
                ..Default::default()
            };

            kvm_route.u.msi.address_lo = cfg.low_addr;
            kvm_route.u.msi.address_hi = cfg.high_addr;
            kvm_route.u.msi.data = cfg.data;

            if self.check_extension(crate::kvm::Cap::MsiDevid) {
                // On AArch64, devid cannot be greater than u16 max.
                let modified_devid = (cfg.devid & 0x00ff_0000) >> 8 | cfg.devid & 0xff;
                kvm_route.flags = KVM_MSI_VALID_DEVID;
                kvm_route.u.msi.__bindgen_anon_1.devid = modified_devid;
            }
            kvm_route.into()
        }
        // Legacy IRQ omitted.
    }
}

所以两个术语可以这样对应：

  • MSI-X restore：恢复每个 virtio PCI 设备的 MSI-X table、PBA、mask/enabled 状态，并重新设置所有未 mask vector 的中断路由。
  • interrupt_group_update_many：由 MSI-X vector 恢复触发的一组或多组 interrupt route update，包括 irqfd enable/register、共享 route cache 更新、KVM GSI routing ioctl。

9. 为什么这对高并发 Template 启动很关键

在 c50/c200、c50/c500 这类并发 Template 启动测试中，如果 Cubelet 的 network 和 storage 阶段耗时较小，而 CubeShim 的 RestoreVm 几乎覆盖了整个 sandbox-start 时延，就说明主要瓶颈位于 VMM restore 链路。

按照上面的代码路径，每个并发启动的沙箱都需要完成：

  1. VM memory restore。
  2. CPU manager restore。
  3. Device manager restore。
  4. arm64 vGIC restore。
  5. virtio PCI devices restore。
  6. MSI-X routes restore。
  7. KVM irqfd/GSI routing 更新。
  8. restored vCPUs start。

当前观测到的 VMM 日志：

restore non-shared map, speed up restore by share map memory file

说明内存恢复已经命中共享内存文件的快速 restore 路径，而不是退化成慢速内存复制。这样一来，高并发场景下剩余的主要怀疑点应优先放在设备和中断恢复路径上，尤其是：

  1. restore_vgic_and_enable_interrupt 的 arm64 vGIC 恢复成本。
  2. DeviceManager::restore_devices 的设备恢复并发度和锁竞争。
  3. VirtioPciDevice::restore 中 MSI-X restore 的耗时。
  4. MsiInterruptGroup::update 对 gsi_msi_routes 的锁竞争。
  5. 每个 vector 反复触发 set_gsi_routing 导致的 KVM ioctl 开销。

这也是为什么在分析 arm64 并发 Template 启动时延与 x86 官方基准差距时，不能只看 Cubelet 侧的网络/存储耗时，还需要把 VMM 内部的 MSI-X、GSI routing、vGIC restore 路径单独拆出来观察。

10. KVM irqbypass XArray 补丁实验记录

本节记录 2026-06-23 至 2026-06-24 在远端 ARM64 机器上进行的 irq_bypass_register_consumer() 锁竞争修复实验。实验目标是验证 KVM irqbypass producer/consumer 管理结构从全局链表改为 XArray 后，是否能缓解 高并发 Template 启动中 RestoreVm -> irqfd/GSI route 路径的锁竞争。

10.1 实验动机

前序 c50 高并发启动分析中，perf lock contention -S kvm 曾观察到 irq_bypass_register_consumer+0x54 附近 mutex 竞争明显：

观测项 数值
contended 6823
total wait 1.13 min
avg wait 9.92 ms
max wait 57.01 ms

该热点与本文前面分析的 MsixConfig::restore -> InterruptSourceGroup::update -> irqfd/GSI routing 链路一致：每个并发启动的 VM 都会恢复多组 virtio PCI MSI-X vector，并触发 irqfd 注册和 KVM routing 更新。当并发数提升时，KVM irqbypass 的全局 producer/consumer 结构会被频繁访问，链表扫描加全局 mutex 可能成为放大器。

  • 参考 v2 序列：KVM: irqbypass: Convert producers/consumers single linked list to XArray

社区补丁不能直接应用到当前 openEuler 6.6 树，需要手工适配。适配后的核心变化：

  1. 将全局 producers / consumers 从链表替换为 DEFINE_XARRAY。
  2. 从 struct irq_bypass_producer 和 struct irq_bypass_consumer 中移除 list_head node。
  3. 注册路径使用 xa_load 检查 token 是否重复，使用 xa_insert 插入。
  4. unregister 路径使用 xa_load 校验 token 对应对象，再执行 disconnect 和 xa_erase。
  5. 对 __connect() 失败路径增加 xa_erase() 回滚，避免已插入 XArray 的对象 在连接失败时残留。
  6. 增加 irqbypass_exit()，在模块退出时 xa_destroy(&producers) 和 xa_destroy(&consumers)。

注意：当前 openEuler kernel 中 xa_insert() 返回 int，不是 error pointer。 因此适配版本直接使用 ret = xa_insert(...)，没有使用 xa_err(xa_insert(...))。

10.7 结论

实验结果支持以下判断：

  1. irq_bypass_register_consumer() 的 mutex 竞争确实是高并发 Template 启动的关键瓶颈之一。
  2. 将 KVM irqbypass producer/consumer 结构改为 XArray 后，高并发场景改善非常明显： c50n500 平均时延从约 2592 ms 降到约 182 ms，P99 从约 5313 ms 降到约 350 ms。
  3. 单并发 c1n20 没有改善，反而略慢；这符合补丁目标。该补丁主要降低并发注册/匹配 irqbypass consumer/producer 时的锁竞争和扫描成本，不是优化单个 VM restore 的固定开销。
  4. 该补丁不能替代 VMM 层后续优化。restore_vgic_and_enable_interrupt()、 DeviceManager::restore_devices()、VirtioPciDevice::restore() 和 MsixConfig::restore() 仍需要保留分段统计，用于继续定位非 irqbypass 锁竞争的耗时。

后续建议：

  1. 在相同内核上重新跑 perf lock contention -S kvm，确认 irq_bypass_register_consumer 是否从热点中消失或显著下降。
  2. 继续对 restore_vgic_and_enable_interrupt() 和 device_restore_group_1 做分段 profile，区分内核锁竞争改善后剩余瓶颈。
  3. 如果要进入发布流程，需要将 kernel patch 以独立补丁形式保存，并记录 openEuler 版本、RPM 路径、uname -a 标签和回退内核启动项。
