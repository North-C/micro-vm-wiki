CubeSandbox 网络数据面与中断唤醒链路

本文承接 CubeVS eBPF 数据面链路、TAP FD 与 NetworkInfo 闭环、Guest Agent 网络配置链路 和 中断与事件通知链路。

目标：把 CubeVS → TAP → virtio-net worker → guest eth0 串成一条完整链，并讲清 RX/TX 队列事件与 TAP 可读事件的区别——这是读 virtio-net 数据面最容易搞反的地方。

源码基线：当前仓库工作树。

控制面事件（ApiRequest/NotifyEvent/TAP fd passing）见 中断与事件通知链路；MSI-X/irqfd 注入细节见 Virtio 中断注入函数级链路。

0. 术语与背景

TAP 与 virtio-net virtqueue

  • TAP：Linux 的虚拟以太网设备（/dev/net/tun），是 host 用户态与 guest 之间的"网线"。VMM 往 TAP 写 = 包进 host 网络栈；从 TAP 读 = 取出要给 guest 的包。CubeSandbox 的 TAP fd 由 network-agent 经 SCM_RIGHTS 交给 VMM（见 TAP fd 链路）。
  • virtqueue（virtio 队列）：guest 与设备共享的环形缓冲。网络设备用成对的 RX/TX 队列：
  • TX 队列：guest 把要发出的包描述符放这里（guest → host 方向）。
  • RX 队列：guest 把可填充的空描述符放这里，host 收到包后填进去（host → guest 方向）。

NetEpollHandler 的四类事件（本文最关键的区分）

virtio-net worker 用一个 epoll 同时监听四类 fd，它们语义完全不同，极易搞反：

事件 来源 fd 含义 触发的动作
TX_QUEUE_EVENT TX queue eventfd（ioeventfd 来） guest 在 TX 队列放好了要发的包 process_tx：从 TX 队列取包写 TAP
RX_QUEUE_EVENT RX queue eventfd guest 给 RX 队列提供了空描述符 开始/继续监听 TAP 可读
RX_TAP_EVENT TAP fd 的 EPOLLIN host 有包进来了（TAP 可读） process_rx：从 TAP 读包填进 RX 描述符
RX/TX_RATE_LIMITER_EVENT rate limiter fd 限速恢复 继续被限速阻塞的处理

最大误读：TX_QUEUE_EVENT 不是"host 在发包"，而是"guest 把要发的包交出来了"；RX_TAP_EVENT 才是"host 有包进来"。详见 §5。

CubeVS eBPF 程序（TC 程序）

CubeSandbox 用 eBPF TC（Traffic Control）程序挂在 TAP/host NIC 上做策略、NAT、重定向。三个入口程序：

程序 挂载点 作用
from_cube sandbox TAP ingress 处理出站包（guest 发出的）：SNAT、端口映射、重定向到 nodenic/cubegw0
from_world host NIC ingress 处理入站外部流量：TCP/UDP/ICMP NAT，端口映射回 guest
from_envoy cube-dev egress 处理本地代理（envoy）回包：DNAT→mvm_inner_ip、SNAT→mvm_gateway_ip、重定向到目标 TAP

三者都用 bpf_redirect(ifindex, ...) 把包送到目标 TAP（按 ifindex 定位）。

1. 核心结论

网络链路两个方向：

  • 出站：guest eth0 → virtio-net TX 队列 → VMM 写 TAP → from_cube 做策略/NAT → nodenic/cubegw0。
  • 入站：host 流量 → from_world/from_envoy → bpf_redirect 回 TAP → VMM 从 TAP 读包写 RX 队列 → MSI-X/irqfd 唤醒 guest。

这条链不是单纯的 VMM 数据面。它要求 host TAP、CubeVS map、virtio-net 队列、guest 内接口/路由/ARP/DNS 全部收敛。"VM 网卡可见"只证明设备模型通了，不证明网络通了。

2. 总体分层

控制面先把每段资源备好（TAP、CubeVS map、队列、guest 接口配置）；运行时数据面才在这些已接好的 fd/map/队列间流动。

3. 控制面前置条件

步骤 动作 锚点
network-agent 建资源 createStateLocked() 分配/复用 TAP、配端口映射、registerCubeVSTap() 注册到 CubeVS local_service.go:275/700
写 CubeVS map cubevs.AddTAPDevice() 把 ifindex→mvm metadata、mvm ip→ifindex 写入 pinned map 并应用策略 tap.go:42
CubeVS 关键 map mvmip_to_ifindex、ifindex_to_mvmmeta、remote_port_mapping、local_port_mapping、egress_sessions、ingress_sessions map.h:15
CubeShim 下发 guest 配置 create_sandbox() 把 interfaces/routes/ARPNeighbors/dns 放进 CreateSandboxRequest sb.rs:462
guest agent 配置内核 先更新接口、再路由、再 ARP 邻居 rpc.rs:1227、netlink.rs:90

guest 看到 virtio-net 设备 ≠ 网络 ready。还必须等 cube-agent 用 MAC 找到网卡，把地址/名字/MTU/ARP/路由真正写进内核。

4. host TAP 如何接进 virtio-net

Net::activate() 为每对 RX/TX 队列建 NetEpollHandler，把 TAP fd 塞进 NetQueuePair（net.rs:646）。handler 的 run() 把四类 fd 加进同一个 epoll——这一段是本文的核心代码，因为它直接定义了四类事件的语义：

// hypervisor/virtio-devices/src/net.rs:266
fn run(&mut self, paused: Arc<AtomicBool>, paused_sync: Arc<Barrier>) -> Result<(), EpollHelperError> {
    let mut helper = EpollHelper::new(&self.kill_evt, &self.pause_evt)?;
    helper.add_event(self.queue_evt_pair.0.as_raw_fd(), RX_QUEUE_EVENT)?;  // RX 队列 eventfd
    helper.add_event(self.queue_evt_pair.1.as_raw_fd(), TX_QUEUE_EVENT)?;  // TX 队列 eventfd
    if let Some(rl) = &self.net.rx_rate_limiter {
        helper.add_event(rl.as_raw_fd(), RX_RATE_LIMITER_EVENT)?;
    }
    if let Some(rl) = &self.net.tx_rate_limiter {
        helper.add_event(rl.as_raw_fd(), TX_RATE_LIMITER_EVENT)?;
    }
    // 若 RX 队列已有可用描述符，立刻开始监听 TAP 可读
    if /* used_idx < avail_idx 表示有可用 desc */ {
        helper.add_event(self.net.tap.as_raw_fd(), RX_TAP_EVENT)?;         // TAP fd 可读
        self.net.rx_tap_listening = true;
    }
    self.net.epoll_fd = Some(helper.as_raw_fd());
    helper.run(paused, paused_sync, self)?;
    Ok(())
}

看这四行 add_event 就能分清事件语义：前两个是 queue eventfd（来自 ioeventfd，guest kick），RX_TAP_EVENT 是 TAP fd（host 有包）。guest 写 PCI notification BAR → KVM ioeventfd → queue eventfd → worker 醒来——数据面入口不是普通 MMIO write handler，热路径是 queue eventfd + TAP fd。

5. 出站链路：guest eth0 → host 网络

guest 应用发包 → guest eth0 → virtio-net driver 把描述符放 TX virtqueue → 写 notification BAR → KVM 触发 TX_QUEUE_EVENT 对应 queue eventfd：

NetEpollHandler::handle_event() 收到 TX_QUEUE_EVENT → handle_tx_event() → process_tx() → NetQueuePair::process_tx() 把 guest descriptor 内容写进 TAP（net.rs:309/222、queue_pair.rs:386）。

包进 TAP 后命中挂在 TAP ingress 的 from_cube（注释明确：附在 sandbox TAP ingress 做 SNAT + 重定向，mvmtap.bpf.c:436）。主要分支：

分支 动作
ARP 请求 走 handle_arp()，网关 MAC 代理应答
目的 = mvm_gateway_ip 改写到 cubegw0 并 bpf_redirect(cubegw0_ifindex, BPF_F_INGRESS)
TCP 源端口命中 local_port_mapping 重写为 host port，重定向到 nodenic_ifindex
其余 egress policy 检查 → TCP/UDP/ICMP NAT → 按 dst_ifindex 重定向

（mvmtap.bpf.c:440）

6. 入站链路：host 网络 → guest eth0

两类入口都靠 bpf_redirect(...ifindex...) 把包送回目标 TAP：

入口 挂载点 处理 锚点
from_world host NIC ingress 只处理 IPv4，按 TCP/UDP/ICMP 进 NAT；TCP 查 remote_port_mapping 做端口代理重写 nodenic.bpf.c:224
from_envoy cube-dev egress DNAT→mvm_inner_ip、SNAT→mvm_gateway_ip，按 mvmip_to_ifindex 找目标 TAP 重定向 localgw.bpf.c:18

包回到 TAP → TAP fd 可读 → NetEpollHandler 收到 RX_TAP_EVENT → handle_rx_tap_event() → process_rx() → NetQueuePair::process_rx() 把 frame 拷进 guest RX descriptor（net.rs:251、queue_pair.rs:445）。完成后按 needs_notification() 决定是否触发 RX used queue interrupt。

7. 中断唤醒如何与数据面闭环

worker 完成 TX/RX 后不直接碰 IOAPIC/GIC，只调 signal_used_queue()，再由 VirtioInterruptMsix::trigger() 按 queue index 选 vector：

// hypervisor/virtio-devices/src/net.rs:183
fn signal_used_queue(&self, queue_index: u16) -> result::Result<(), DeviceError> {
    self.interrupt_cb.trigger(VirtioInterruptType::Queue(queue_index))
        .map_err(|e| { /* ... */ DeviceError::FailedSignalingUsedQueue(e) })
}

trigger() 选 vector → 未 mask 则 interrupt_source_group.trigger(vector) 写 irqfd（pci_device.rs:795/820，完整见 trace 文档 §11）。

数据面与中断面的三个结合点：

  1. guest 发包时，用 queue notify 把 TX 工作交给 host；
  2. host 收包时，用 TAP readable 把 RX 工作交给 worker；
  3. host 完成队列消费后，用 used queue interrupt 把完成状态交还 guest。

restore 细节：driver_awake 初始 false（net.rs:176），restore 后要先强制发中断，避免 TAP 事件在 driver 尚未就绪时丢失。这也是 restore 后首包唤醒 必须验证的点。

8. 容易说反的方向

误读 正解
TX_QUEUE_EVENT = "host 发包" 是 guest 在 TX 队列放好了要发到 TAP 的包
RX_QUEUE_EVENT = "host 有包进来" 是 guest 给 RX 队列提供了可填充 descriptor（net.rs:193）
真正表示 host 有包的事件 是 RX_TAP_EVENT（来自 TAP fd 的 EPOLLIN）
from_world/from_envoy/from_cube 混为一谈 分别是 host NIC ingress / cube-dev egress / sandbox TAP ingress

9. 能力边界

CubeSandbox 的 virtio-net 路径本身只保证"guest 队列 ↔ TAP fd"搬运。真正网络能力边界还取决于：CubeVS map 是否正确、策略是否放行、port mapping 是否登记、guest 是否完成接口配置。

这就是为什么 CubeSandbox 的 network ready 比一般 VMM 更重——VM 网卡可见只证明设备模型通了，不能证明 guest eth0、host eBPF 策略、端口重写一起通了。

10. ARM64 与 x86_64 差异

高层逻辑共享（TAP、epoll、queue eventfd、MSI-X 触发、guest netlink 都不分叉）。ARM64 三个额外风险点：

  1. CubeVS 复用 x86 对象：ARM64 不重生成 arm64 wrapper，而是经 bpf_arm64.go 复用 *_x86_bpfel.o（bpf_arm64.go:1）。关注点不在 Go API，而在内核 verifier、TC attach、helper 支持、对象兼容性。
  2. 中断控制器分叉：x86_64 落 IOAPIC/APIC/MSI；ARM64 落 GICv3/ITS/MSI。
  3. 设备发现路径：x86_64 多走 ACPI/PCI；ARM64 还要验证 FDT、GIC、guest 网卡枚举顺序与 MAC 匹配逻辑一致。

11. 与 restore 的关系

snapshot restore 没有发明新的网络数据面——它恢复的是 virtio-net 设备状态和 host backend 绑定关系。真正跑包时仍走同一条 TAP → epoll → process_rx/process_tx → used queue interrupt 热路径。

这解释了为什么 restore 路线必须额外处理 driver_awake、TAP backend 替换和网络元数据恢复（详见 中断状态恢复链路）。
