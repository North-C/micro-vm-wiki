    CubeSandbox VMM Snapshot Restore 状态恢复链路

    本文展开 CubeSandbox 快照路线，聚焦 CubeShim 之后的 CubeHypervisor / VMM 内部恢复机制。

    结论只来自当前仓库源码，不把上游 Cloud Hypervisor 的通用说明当作依据。

    设备恢复细节见 VMM Device Restore 设备恢复链路；virtio-net/fs 内部状态见 Virtio Net/Fs Restore 链路；中断状态恢复见 中断状态恢复链路。

    0. 术语与背景

    Snapshot 与 Restore 的关系

    CubeSandbox 的 restore 不是按新配置重创一台 VM，而是把一台之前 Paused 的 VM 从快照"复活"。快照存两样东西：

    快照面 文件 内容
    状态面 config.json + state.json VM 配置 + 各 manager/设备的序列化状态（device tree、内存布局、vCPU 寄存器、GIC/ITS、MSI-X table…）
    数据面 memory-ranges 或外部 memory volume guest 内存内容

    关键概念

    • RestoreConfig：恢复请求的覆盖配置。restore 端先读快照 config.json，再用 RestoreConfig 覆盖已有设备的后端（disk path / tap / fs shared_dir / vsock socket / pmem file），而不是新增设备。
    • Migratable / Snapshot trait：Cloud Hypervisor 抽象（CubeSandbox 继承）。每个可快照设备实现 snapshot()/restore()/pause()。restore() 恢复运行时状态。
    • fast restore vs slow restore：内存恢复的两条路径。fast = 把 memory blob 整个 mmap 成 guest 内存（无 shared memory、无 hotplug virtio-mem 时）；slow = 先建内存区域，再把 blob 内容拷回各 GPA。
    • 两阶段设备恢复：① 先按快照拓扑重建设备对象（create_devices），② 再恢复每个设备内部状态（restore_devices）。
    • memory_vol_url：CubeSandbox 加强点——允许内存内容从独立 volume 读，而非固定读 source_url/memory-ranges。

    核心约束：restore 是"同一机器拓扑下换后端恢复"。跨架构、跨 CPU 特性、跨设备拓扑的迁移不是这条路径的目标。

    1. 核心结论

    restore 先读 config.json/state.json，用 RestoreConfig 覆盖已有设备后端，再按快照状态恢复内存、设备、vCPU、中断控制器。RestoreConfig 边界很窄——只替换、不新增（如 update_nets() 只按已有 net id 替换 tap）。

    ARM64 与 x86_64 最大差异在架构状态：x86_64 有 CPUID 兼容性检查、VM clock 恢复、TSC MSR 重设；ARM64 要额外保存/恢复 GIC/ITS 并在恢复后启用中断路由。

    2. 入口链路

    CubeShim 构造 restore 请求（从 snapshot metadata 校验 CPU/memory/kernel/disk/pmem，生成覆盖配置，sb.rs:946）→ 发 ApiRequest::VmRestore（cube_hypervisor.rs:173）→ VMM control loop 匹配后调 self.vm_restore()（lib.rs:1996）。

    sequenceDiagram participant Shim as CubeShim participant Vmm as VMM control loop participant VM as Vm participant MM as MemoryManager participant DM as DeviceManager participant CPU as CpuManager Shim->>Vmm: ApiRequest::VmRestore(RestoreConfig) Vmm->>Vmm: recv_vm_config + update backends Vmm->>Vmm: recv state.json Vmm->>VM: Vm::new_from_snapshot VM->>MM: MemoryManager::new_from_snapshot Vmm->>VM: restore(snapshot) VM->>DM: restore / create devices VM->>CPU: restore / create vCPUs VM->>Vmm: resume

    3. RestoreConfig 的真实能力

    RestoreConfig 字段：source_url、prefault、disks、net、fs、vsock、pmem、dirty_log、memory_vol_url（config.rs:2095）。source_url 是快照目录，恢复端从它读 config.json/state.json（migration.rs:92）。

    覆盖边界一目了然：

    覆盖项 实际行为 能力边界
    disk 按 id 替换 path 和 rate limiter 不能添加快照外 disk
    net 按 id 替换 tap 和 rate limiter 不能改变 net 设备数量
    fs 按 id 替换 shared_dir/allowed_dirs/cache/rate limiter 依赖快照内已有 fs id
    vsock 替换 socket 依赖快照内已有 vsock
    pmem 按 id 替换 file 不能改变 pmem 拓扑
    memory_vol_url 替换内存 blob 来源 必须是绝对路径、普通文件或块设备

    update_nets() 的代码最能说明"只替换、不新增"——它只遍历已有 vm_config.net，命中同 id 才替换 tap：

    // hypervisor/vmm/src/config.rs:2287
pub fn update_nets(&mut self, net_cfgs: &Vec<NetConfig>) {
    if let Some(nets) = &mut self.net {
        // 先把 RestoreConfig 里的 net 按 id 收成 map
        let mut devices: HashMap<String, String> = HashMap::default();
        for net_cfg in net_cfgs.iter() {
            if net_cfg.id.is_none() { continue; }
            if net_cfg.tap.is_some() {
                devices.insert(net_cfg.id.as_ref().unwrap().clone(),
                               net_cfg.tap.as_ref().unwrap().clone());
            }
            // ... rate_limiter 同理 ...
        }
        // 再遍历【已有】net，命中同 id 才替换
        for net in nets.iter_mut() {
            if let Some(id) = &net.id {
                if let Some(tap) = devices.get(&id.clone()) { net.tap = Some(tap.clone()); }
                // ...
            }
        }
    }
}

    看这段循环就懂边界：外层遍历的是快照里已有的 nets，RestoreConfig 里多余的 net id 会被静默忽略。所以 restore 不能新增网卡。memory_blob_to_path() 还会校验 memory blob 路径（拒绝目录/相对路径/未知 scheme，migration.rs:38）。

    4. Vmm::vm_restore 的阶段

    // hypervisor/vmm/src/lib.rs:653
fn vm_restore(&mut self, restore_cfg: RestoreConfig) -> result::Result<(), VmError> {
    if self.vm.is_some() || self.vm_config.is_some() {
        return Err(VmError::VmAlreadyCreated);          // (1) 只允许空 VMM 恢复
    }
    let vm_config = Arc::new(Mutex::new({
        let mut vm_config = recv_vm_config(source_url)?; // (2) 读 config.json
        if let Some(disks) = &restore_cfg.disks { vm_config.update_disks(disks); }
        if let Some(nets)  = &restore_cfg.net   { vm_config.update_nets(nets); }
        if let Some(vsock) = &restore_cfg.vsock { vm_config.update_vsock(vsock); }
        if let Some(fses)  = &restore_cfg.fs    { vm_config.update_fses(fses); }
        if let Some(pmems) = &restore_cfg.pmem  { vm_config.update_pmem(pmems); }
        vm_config.memory.dirty_log = restore_cfg.dirty_log;
        vm_config
    }));
    // ... 读 state.json, x86_64 检查 CPUID 兼容性 ...
    let mut vm = Vm::new_from_snapshot(/* ... */)?;      // (3) 建框架（内存已映射）
    vm.restore(snapshot)?;                               // (4) 恢复设备/vCPU/中断
    vm.resume()?;                                        // (5) 进入 Running
}
    flowchart TD A["VmRestore request"] --> B{"vm or vm_config exists?"} B -->|yes| E["VmAlreadyCreated"] B -->|no| C["recv config.json"] C --> D["apply RestoreConfig backend overrides"] D --> F["recv state.json"] F --> X86{"x86_64 + KVM?"} X86 -->|yes| CPUID["check CPUID compatibility"] X86 -->|no| N["skip CPUID check"] CPUID --> G["Vm::new_from_snapshot"] N --> G G --> H["Vm::restore(snapshot)"] H --> I["Vm::resume()"]

    Vm::new_from_snapshot() 返回的 VM 尚未完全恢复运行态——它已有 hypervisor VM、内存映射、DeviceManager/CpuManager 框架，但设备状态和 vCPU 状态要靠后面的 vm.restore(snapshot) 继续。

    5. 内存恢复机制

    内存先于设备和 vCPU 恢复。Vm::new_from_snapshot() 取 MEMORY_MANAGER_SNAPSHOT_ID 调 MemoryManager::new_from_snapshot()（vm.rs:821）。MemoryManagerSnapshotData 保存内存布局（ranges、guest_ram_mappings、device area、boot/current RAM、arch mem regions、hotplug slot，memory_manager.rs:2891）。

    fast vs slow 两条路径的关键判断在 support_fast_restore_check（无 shared memory、无 hotplug virtio-mem 时为 fast）：

    // hypervisor/vmm/src/memory_manager.rs:1319  (fast restore)
let fast_restore = Self::support_fast_restore_check(config);
let memory_file = if fast_restore {
    info!("restore non-shared map, speed up restore by share map memory file");
    let file = memory_file_target.open_read()?;       // 直接打开 memory blob
    Some(file)
} else { None };
let mm = MemoryManager::new(vm, config, Some(prefault), phys_bits, /*...*/,
                            Some(&mem_snapshot), None, memory_file, /*...*/)?;

    // hypervisor/vmm/src/memory_manager.rs:1349  (slow restore)
if !fast_restore {
    info!("restore shared map, fall back to slow restore");
    mm.lock().unwrap()
      .fill_saved_regions(memory_file_target.path, mem_snapshot.memory_ranges)?;  // 把 blob 拷回各 GPA
}

    fast vs slow 的本质：fast 把整个 memory blob mmap 成 guest 内存（O(1)，按需缺页）；slow 先建内存区域，再逐 range 拷贝 blob 内容回对应 GPA。shared memory 或 hotplug virtio-mem 会破坏"整块映射"前提，只能走 slow。

    flowchart LR M1["MemoryManager snapshot data"] --> M2["guest_ram_mappings"] M1 --> M3["memory_ranges"] M2 --> R["restore regions and zones"] M3 --> Blob["memory blob"] Blob --> Fast{"fast restore allowed?"} Fast -->|yes| Map["map memory file (mmap)"] Fast -->|no| Copy["fill_saved_regions (copy)"] Map --> Ready["GuestMemory ready"] Copy --> Ready

    6. 设备与 vCPU 恢复

    Vm::restore() 要求能迁移到 Paused，然后按严格顺序恢复。源码骨架最能说明顺序：

    // hypervisor/vmm/src/vm.rs:2772
fn restore(&mut self, snapshot: Snapshot) -> std::result::Result<(), MigratableError> {
    current_state.valid_transition(VmState::Paused)?;                     // 必须能迁到 Paused

    self.device_manager.lock().unwrap()
        .restore(/* device_manager_snapshot */)?;                         // ① DeviceManager: set_state + create_devices
    self.cpu_manager.lock().unwrap()
        .restore(/* cpu_manager_snapshot */)?;                            // ② vCPU 状态
    // [aarch64] ③ restore_vgic_and_enable_interrupt()  ← GIC/ITS 恢复(见 interrupt-state-restore-chain)
    self.device_manager.lock().unwrap()
        .restore_devices(/* snapshot */)?;                                // ④ 每个设备内部状态
    self.cpu_manager.lock().unwrap()
        .start_restored_vcpus()?;                                         // ⑤ 最后才启动 vCPU
}

    顺序是硬约束：start_restored_vcpus() 最后才调——vCPU 不能在设备和中断状态完整前运行。缺 DEVICE_MANAGER_SNAPSHOT_ID 或 CPU_MANAGER_SNAPSHOT_ID 都直接报错。aarch64 的 ③（GIC/ITS restore）在 ① ② 之后、④ 之前，详见 中断状态恢复链路。

    CpuManager restore 为每个 vCPU 调 create_vcpu(..., Some(snapshot))，x86_64 还重设 TSC MSR（cpu.rs:2135）。

    7. x86_64 与 ARM64 差异

    维度 x86_64 ARM64
    CPU 兼容性 restore 前检查 CPUID（vm.rs:2685、lib.rs:1773） 当前无对应 CPUID 检查
    VM clock snapshot/restore VM clock（vm.rs:2245） 无该 x86 clock 分支
    vCPU 补偿 restore 后重设 TSC MSR 依赖 ARM vCPU state 和 GIC 状态
    中断控制器 IOAPIC/MSI 随设备模型恢复 显式 snapshot/restore GIC/ITS（vm.rs:2256/2286）
    pause 行为 主要 pause vCPU 和设备 还要 pause GIC flush pending/ITS table（device_manager.rs:4784）
    失败边界 CPUID 不兼容会拒绝恢复 缺 GIC/ITS snapshot 会拒绝恢复

    8. Snapshot 与 restore 的对称关系

    snapshot 要求 VM 已 Paused，否则 Vm::snapshot() 直接报错（vm.rs:2678）。snapshot 聚合 VM/CPU/MemoryManager/DeviceManager，ARM64 额外加 VGIC section（vm.rs:2715）。MemoryManager transport 阶段写 memory blob：full 写所有 range，incremental/soft-dirty 走各自脏页选择（memory_manager.rs:3023）。

    因此 VMM 层 restore 依赖两个文件面：状态面（state.json/config.json）+ 数据面（memory-ranges 或外部 memory volume）。CubeSandbox app snapshot/commit 把 memory_vol_url 传给 snapshot，restore 再用 RestoreConfig.memory_vol_url 读回。

    9. 能力边界

    VMM restore 的强约束：

    • VMM 内不能已有 VM 或 VM config。
    • source_url 必须可转换为快照目录路径。
    • 快照必须含 MemoryManager/DeviceManager/CpuManager snapshot。
    • restore 覆盖只能更新快照内已有设备的后端。
    • x86_64 KVM 必须通过 CPUID 兼容性检查。
    • ARM64 必须有可恢复的 GIC/ITS snapshot。

    这解释了为什么 CubeShim 进入 VMM 前要先校验 snapshot metadata（sb.rs:947），把当前节点的 rootfs/tap/virtiofs/pmem/vsock 映射成 restore 覆盖配置。
