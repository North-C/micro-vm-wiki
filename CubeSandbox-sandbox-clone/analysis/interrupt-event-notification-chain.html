    CubeSandbox 中断与事件通知链路

    本文承接 CubeHypervisor API Request 内部调度链路、TAP FD 与 NetworkInfo 闭环 和 CubeVS eBPF 数据面链路。

    CubeSandbox 里有好几样东西都叫"事件"或"通知"，极易混淆。本文把它们分层讲清：eventfd、NotifyEvent、virtio queue notify、irqfd/MSI-X、TAP fd passing 各是哪条链、哪个方向、解决什么问题。

    源码基线：当前仓库工作树。

    virtio MSI-X / irqfd 的函数级细节见 Virtio 中断注入函数级链路；网络包 RX/TX 热路径见 网络数据面与中断唤醒链路。

    0. 术语与背景：CubeSandbox 的"事件"到底有几种

    先把容易混的几类"事件"一次性分开。它们方向不同、承载不同、解决的语义不同：

    类别 名字 方向 承载 语义
    ① 控制面唤醒 API EventFd + mpsc channel CubeShim → VMM 线程 Linux eventfd + Rust mpsc "执行这个 VM 操作"
    ② 状态通知 NotifyEvent guest/VMM → CubeShim Rust mpsc channel "VM 生命周期变了（started/ready/shutdown）"
    ③ 设备中断 ioeventfd / irqfd / MSI-X guest ↔ virtio 设备 KVM eventfd virtio 队列工作通知
    ④ 资源交接 TAP fd passing network-agent → Cubelet → VMM Unix socket + SCM_RIGHTS 把宿主 TAP fd 交给 VMM

    几个关键概念：

    • eventfd：Linux 轻量事件 fd，write(1) = signal 一次，read() 取累计次数。CubeSandbox 用它做线程间唤醒（如 API EventFd 唤醒 VMM epoll loop）。
    • mpsc channel：Rust 的多生产者单消费者通道，传结构化消息（如 ApiRequest、NotifyEvent）。eventfd 只负责"叫醒"，真正数据走 mpsc。
    • epoll control loop：VMM 线程的主循环，用 epoll 等待多种 fd（API event、ioeventfd 触发的 queue event、设备 event…），按 token 分发。
    • SysCtrl 设备：CubeSandbox 自定义的 guest→host 通知设备。guest 往它写一个 code（如"我启动了"/"vsock 服务好了"），VMM 据此发 NotifyEvent。这是 ② 的来源。
    • SCM_RIGHTS：Unix domain socket 的辅助消息机制，可以在进程间传递文件描述符（不传数据，传 fd 的"副本"）。TAP fd passing 就靠它（④）。
    • ioeventfd / irqfd / MSI-X：见 trace 文档 §0，是 ③ 的机制，本文只在 §7 概要。

    一句话：① ② 是控制面/生命周期事件（CubeShim 和 VMM 之间），③ 是数据面中断（guest 和设备之间），④ 是宿主资源交接（TAP fd）。把它们混成一团是读这套代码最常见的障碍。

    1. 核心结论

    四类事件各走各的链：

    1. 控制面唤醒：CubeShim 调 VmmInstance::send_request() → 写 mpsc request + 写 API EventFd → 唤醒 VMM epoll loop。
    2. 状态通知：guest 写 SysCtrl 设备 → VMM 用 event_notify! 把 NotifyEvent 发回 CubeShim。
    3. 设备中断：virtio PCI notification BAR 由 ioeventfd 处理；设备完成后经 VirtioInterruptMsix → interrupt group → irqfd 注入 guest。
    4. TAP fd passing：network-agent → Cubelet → hypervisor，经 Unix socket + SCM_RIGHTS 传宿主 TAP fd（不是 guest interrupt）。

    3. 控制面事件：CubeShim → VMM（ApiRequest 唤醒）

    CubeShim 要 VMM 做事（create/boot/restore/snapshot/add_device）时，不直接调函数，而是发一个请求并"敲门"。敲门的就是 API EventFd：

    // hypervisor/vmm/src/api/service.rs:85
pub fn send_request(&self, request: ApiRequest) -> Result<ApiResponse, Error> {
    self.api_sender.send(request).map_err(Error::RequestSend)?;  // (1) 数据走 mpsc
    self.api_evt.write(1).map_err(Error::EventFdWrite)?;          // (2) 敲门：写 eventfd
    self.res_receiver.recv().map_err(Error::ResponseRecv)         // (3) 等响应
}

    VMM 线程的 control loop 用 epoll 等 API event，收到后按 eventfd 计数从 mpsc 取出同等数量的请求：

    // hypervisor/vmm/src/lib.rs:1927
EpollDispatch::Api => {
    for _ in 0..self.api_evt.read().map_err(Error::EventFdRead)? {      // 按 eventfd 计数
        let api_request = api_receiver.recv().map_err(...)?;            // 从 mpsc 取请求
        match api_request {
            // 分发到 vm_create / vm_boot / vm_restore / vm_snapshot / vm_add_device ...
        }
    }
}

Loop-->>Svc: ApiResponse Svc-->>Shim: result

    为什么 eventfd + mpsc 两件套？ eventfd 只能传"次数"（叫醒），mpsc 才传结构化请求。两者配合：eventfd 保证 VMM 线程被及时唤醒，mpsc 保证请求不丢、有序。这个 API EventFd 不是 guest IRQ，不进 IOAPIC/GIC。

    4. 状态通知：guest SysCtrl → NotifyEvent → CubeShim

    guest 启动完成、vsock 服务就绪时，需要告诉外面的 CubeShim。CubeSandbox 用自定义的 SysCtrl 设备承载这个语义（CubeShim 默认开 sys_ctrl，config.rs:138）：

    // hypervisor/devices/src/legacy/sys_ctrl.rs:70
fn write(&mut self, _base: u64, _offset: u64, data: &[u8]) -> Option<...> {
    let code = data[0];
    if sys_start(code) && !sys_start(self.sys_state) {
        self.sys_state |= SYS_START;
        event_notify!(NotifyEvent::SysStart);                    // guest 启动
    }
    // ...
    if (code & SYS_VSOCK_SERVER) == SYS_VSOCK_SERVER {
        info!("vsock server ready");
        event_notify!(NotifyEvent::VsockServerReady);            // vsock 服务就绪
    }
    None
}

    event_notify! 宏把事件塞进一个全局 channel（CubeShim 在 launch_vmm() 时创建并注册的 sender）：

    // hypervisor/event_notifier/src/lib.rs:52
pub fn send_event(event: NotifyEvent) {
    let mut guard = NOTIFIER.lock().unwrap();
    guard.send(event);                       // 发到 CubeShim 的 NotifyEvent channel
}
#[macro_export]
macro_rules! event_notify { ($event:expr) => { $crate::send_event($event) }; }

    SysCtrl 的暴露方式按架构分（device_manager.rs:1665/1782）：x86_64 放 I/O port 0x680，aarch64 没有 PIO port space，插到 MMIO bus。

    NotifyEvent 是生命周期状态通道，服务 CubeShim 的 ready/shutdown/restore 语义，不是 virtio queue notification。VsockServerReady 表示 guest 内 vsock 服务写过了 sys_ctrl，但网络接口仍要由 agent RPC 配置（见 网络数据面）。

    5. CubeShim 等待 ready 与 stale event drain

    SandBox::start_vm() 先 launch_vmm()，普通 boot 完成后等 NotifyEvent::VsockServerReady；收到 VmShutdown 视为异常，超时则 fallback vsock probe（sb.rs:781/810）。restore 路径构造 RestoreConfig（fs/net/disk/pmem/vsock/memory volume URL）后调 restore_vm()（sb.rs:946）。

    stale event 陷阱：rollback 前会先 VmDelete，而 VmDelete 会向 event queue 推 VmShutdown（sb.rs:1375）。所以恢复新 VM 前必须 drain 掉旧事件，否则新 monitor 会把旧 VM 的 shutdown 误判成新 VM 崩溃。

    注：NotifyEvent::RestoreReady 当前只见枚举和注释掉的等待代码，未见实际 event_notify! 生产点（event_notifier/src/lib.rs:16、sb.rs:997），不能当作现行同步闸门。

    6. VM shutdown 通知

    Vm::shutdown() 关 signal handler → 唤醒 device manager 线程 → 关 CPU manager → 等线程退出 → 发 NotifyEvent::VmShutdown（vm.rs:1311/1335）。它表达 VM 生命周期变化，被 CubeShim monitor 或 rollback drain 消费，不是 guest 内设备中断。

    7. 设备中断与 queue notify（概要）

    ③ 这条链的完整函数级细节在 Virtio 中断注入函数级链路。这里只给方向：

    • guest → host（kick）：guest 写 notification BAR → KVM ioeventfd → queue eventfd → NetEpollHandler worker 醒来。
    • host → guest（完成中断）：worker 完成 → signal_used_queue() → VirtioInterruptMsix::trigger() → interrupt group → irqfd → IOAPIC/GIC 注入 guest。

    一句话：③ 是 guest 与 virtio 设备之间的数据面工作通知，与 ① ② 的控制面/生命周期事件完全不同链路。

    8. TAP fd passing（不是中断）：network-agent → Cubelet

    network-agent 把宿主 TAP 的 fd 经 Unix socket + SCM_RIGHTS 交给 Cubelet。先看 network-agent 的 fd server（Go）：

    // network-agent/internal/fdserver/server.go:87
func handleConn(conn *net.UnixConn, provider service.TapFDProvider) error {
    // ... 读 {sandboxId, name} 请求 ...
    file, err := provider.GetTapFile(req.SandboxID, req.Name)   // 取 TAP fd
    // ...
    return writeResponse(conn, []byte(`{"errCode":"0",...}`), file)
}

func writeResponse(conn *net.UnixConn, payload []byte, file *os.File) error {
    var rights []byte
    if file != nil {
        rights = syscall.UnixRights(int(file.Fd()))             // SCM_RIGHTS：fd 作为辅助消息
    }
    _, _, err := conn.WriteMsgUnix(payload, rights, nil)        // 数据 + fd 一起发
    return err
}

    GetTapFile() 校验 sandbox id 与 TAP name；内存 state 没 fd 就 restoreTap() 重取（tap_fd_provider.go:18）。

    Cubelet 侧 requestNetworkAgentTapFile() 连 socket、读响应 + oob data，用 ParseUnixRights() 把 fd 解出来：

    // Cubelet/network/plugin_tap.go:1042
oob := make([]byte, 1024)
n, oobn, _, _, err := conn.ReadMsgUnix(buf, oob)                 // 读数据 + 辅助消息
// ...
msgs, _ := syscall.ParseSocketControlMessage(oob[:oobn])
for _, msg := range msgs {
    fds, _ := syscall.ParseUnixRights(&msg)                      // 从 SCM_RIGHTS 取 fd
    if len(fds) == 0 { continue }
    return os.NewFile(uintptr(fds[0]), "/dev/net/tun"), nil
}

    随后 registerNetworkAgentTapForPool() 把 fd 装进 Name2MvmNet（按 TAP name + sandbox id 索引，plugin_tap.go:972）。

    SCM_RIGHTS 在传什么？ 不是数据，是文件描述符的副本——内核帮接收进程复制一个指向同一 TAP 的 fd。所以 network-agent 和 VMM 最终操作的是同一个 TAP。

    9. TAP fd passing：Cubelet → hypervisor

    Cubelet 起一个 cubetap socket server（CUBE_TAP_SERV_PATH，默认 /data/cubelet/cubetap.sock，main.go:391/503）。tapProvider 收到请求后按 name+sandbox id 查 Name2MvmNet，再用 WriteMsgUnix + UnixRights 把 fd 发出（tap_provider.go:48/138）：

    // Cubelet/services/server/tap_provider.go (run)
mvmNet, exist := network.Name2MvmNet.Load(req.Name)             // 按 TAP name 查
// ... 校验 sandbox id ...
var fds []int
if retFile != nil { fds = append(fds, int(retFile.Fd())) }
data := syscall.UnixRights(fds...)                              // 包成 SCM_RIGHTS
conn.WriteMsgUnix(b, data, nil)                                 // 发 fd

    hypervisor 侧的 fast path：单队列 + 已有 TAP name + sandbox id 时，优先走 Tap::lookup_from_pool() 向 cubetap socket 要 fd，而不走普通 /dev/net/tun 打开：

    // hypervisor/net_util/src/open_tap.rs:77
if num_rx_q == 1 {
    if let Some(name) = if_name {
        if let Some(sandbox_id) = sandbox_id {
            match Tap::lookup_from_pool(name, sandbox_id) {     // 向 cubetap 要 donated fd
                Ok(tap) => { taps.push(tap); return Ok(taps); }
                Err(e) => info!("Fast request tap failed {:?}, fall back to slow path", e)
            }
        }
    }
}

    Tap::lookup_from_pool() 内部连 CUBE_TAP_SERV_PATH、用 recv_with_fds 收 fd、F_DUPFD_CLOEXEC 复制（tap.rs:198/221）。

    这条 fd 链决定 virtio-net 绑哪个 host TAP，但不触发 guest interrupt。 中断仍由 virtio queue + ioeventfd + MSI-X + irqfd 完成。TAP 的可读/可写只代表 host I/O readiness。

    10. ARM64 与 x86_64 差异

    ①②④（API eventfd、mpsc、NotifyEvent、TAP fd passing）都是同一套 Linux 机制，无架构分叉。差异落在 ③ 的载体和 guest 描述：

    维度 x86_64 aarch64
    SysCtrl 暴露 I/O port 0x680 MMIO（ARM 无 PIO port space）
    kernel cmdline console=hvc0 + no_timer_check 等 console=ttyAMA0,115200
    CubeShim seccomp 放行 SYS_mkdir 放行 SYS_mkdirat
    中断控制器 IOAPIC / APIC / MSI-X GIC / FDT / MPIDR / vGIC restore
    flowchart LR Common["common: ApiRequest, EventFd, NotifyEvent, TAP fd"] --> X86["x86_64"] Common --> ARM["aarch64"] X86 --> Port["SysCtrl PIO 0x680"] X86 --> Ioapic["IOAPIC / APIC / MSI-X"] ARM --> Mmio["SysCtrl MMIO"] ARM --> Gic["GIC / FDT / MPIDR / vGIC"]

    因此 ARM64 验证不能只看 send_request() 能否返回——还要验证 SysCtrl MMIO ready、GIC/ITS 注入、virtio-net queue notify、CubeVS eBPF、snapshot restore state。

    11. 能力边界与常见误读

    各组件的职责边界：

    组件 负责 不负责
    CubeShim 经 ApiRequest 下发 VM/device 操作，经 NotifyEvent 等生命周期事件 不直接实现 queue notify / irqfd
    network-agent TAP、CubeVS、port mapping、fd 暴露 不参与 virtio 中断
    Cubelet workflow、网络配置、TAP fd 池、cubetap server 不处理 guest IRQ
    CubeHypervisor/VMM virtio PCI notification BAR、ioeventfd、MSI-X、interrupt group、irqfd、IOAPIC/GIC —

    五个常见误读：

    1. API EventFd 不是 guest IRQ——只唤醒 VMM control loop 消费 mpsc request。
    2. NotifyEvent::VsockServerReady 不是 virtio-net ready——是 guest 内 vsock 服务写过了 sys_ctrl，网络接口仍要 agent RPC 配置。
    3. TAP fd passing 不是 queue notify——只交 host TAP fd，后续包传输仍靠 virtio queue eventfd + worker。
    4. VmDelete 产生的 VmShutdown 可能成 stale event——rollback drain 是为避免旧生命周期事件污染新 VM。
    5. ARM64 差异不在 VMM_SERVICE，而在 SysCtrl MMIO、GIC/ITS、FDT/MPIDR、kernel cmdline、snapshot device state。

    ready 不等于 boot 完成：CubeSandbox 需要 VMM boot + SysCtrl ready + vsock server ready + agent RPC CreateSandbox 都收敛，才进入平台可用状态。
