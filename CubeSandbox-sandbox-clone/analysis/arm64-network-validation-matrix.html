    CubeSandbox ARM64 网络验证矩阵

    本文承接 ARM64 与 x86_64 架构差异链路、CubeVS eBPF 数据面链路 和 网络数据面与中断唤醒链路。

    目标不是重复解释 ARM64 原理。

    目标是把 ARM64 网络路径中真正需要核验的前置条件、观测点和失败边界整理成一份源码驱动的验证矩阵。

    源码基线：当前仓库工作树。

    1. 核心结论

    CubeSandbox 的 ARM64 网络不是“virtio-net 能启动”就算通过。

    它至少要同时满足五层条件：

    1. guest ARM64 kernel 具备 TUN、virtio-net、GICv3 ITS、BPF 和 TC 相关能力。
    2. CubeVS 能在 ARM64 上加载 eBPF object，并把 TC filter attach 到指定接口。
    3. VMM 能用 FDT/GICv3/ITS 把 virtio-net 和 MSI 路由正确暴露给 guest。
    4. guest cube-agent 能按 MAC 找到网卡，并完成地址、路由和 ARP 配置。
    5. snapshot/restore 后，GIC/ITS 和 virtio-net 唤醒链不能丢失。

    因此 ARM64 网络验证的重点不是“有没有 arm64 代码分支”。

    重点是这五层在一次真实 sandbox 生命周期里能否连续闭环。

    2. 验证矩阵总览

    层级 必要条件 关键源码依据 失败时的典型表现
    guest kernel CONFIG_BPF、CONFIG_NET_SCH、CONFIG_TUN、CONFIG_VIRTIO_NET、CONFIG_ARM_GIC_V3_ITS mvm.config VM 能启动，但 eBPF、TAP 或 virtio-net 某一层不可用
    CubeVS loader ARM64 build tag 走 bpf_arm64.go，直接加载嵌入的 *_x86_bpfel.o bpf_arm64.go LoadCollectionSpec、verifier 或 map pin 失败
    TC attach Init() 和 AttachFilter() 通过 clsact + tc.Filter.Replace 挂载 BPF cubevs.go，tc.go host 有 TAP，但 from_cube/from_world/from_envoy 未生效
    VMM 暴露 aarch64 走 configure_vcpu()、FDT、GICv3 ITS、MSI compatible aarch64/mod.rs，gic/mod.rs guest 设备枚举异常，或中断不达 guest
    guest 配网 cube-agent 先等 PCI path，再 update_interface、update_routes、add_arp_neighbors rpc.rs，netlink.rs 网卡可见但 eth0 没地址、没路由、无法连通
    restore snapshot 带 gic-v3-its section，restore 时重建 VGIC 并重新 enable vm.rs，gic.rs restore 后首包不醒、MSI 丢失、网络僵死

    3. 第一层：guest ARM64 kernel 前置条件

    ARM64 guest kernel 配置已经给出了一组明确前提。

    mvm.config 打开了 CONFIG_BPF、CONFIG_BPF_SYSCALL 和 CONFIG_BPF_JIT。

    源码依据：mvm.config。

    同一个配置还打开了 CONFIG_NET_SCHED 和 CONFIG_NET_SCH_INGRESS。

    源码依据：mvm.config。

    网络设备侧，配置里有 CONFIG_TUN、CONFIG_TAP、CONFIG_VIRTIO_NET、CONFIG_VIRTIO_PCI 和 CONFIG_VIRTIO_MMIO。

    源码依据：mvm.config，mvm.config。

    中断控制器侧，配置里有 CONFIG_ARM_GIC_V3 和 CONFIG_ARM_GIC_V3_ITS。

    源码依据：mvm.config。

    这组条件可以转成最小检查项：

    1. guest kernel 至少要具备 virtio-net、TUN/TAP 和 GICv3 ITS。
    2. host/guest 两侧都要允许 BPF 与 TC ingress 路径。
    3. ARM64 cmdline 也必须保持 console=ttyAMA0,115200，避免把 x86-only 参数带进 agent 用户态。

    源码依据：mvm.cmdline。

    4. 第二层：CubeVS 在 ARM64 上怎么加载

    ARM64 的 CubeVS 不是重新生成一套 arm64 专属 bpf2go wrapper。

    它走 bpf_arm64.go，用 ebpf.LoadCollectionSpecFromReader() 直接加载嵌入对象。

    源码依据：bpf_arm64.go。

    源码注释写得很清楚。

    ARM64 复用的是仓库里的 little-endian eBPF object，而不是复用 x86 CPU 指令。

    源码依据：bpf_arm64.go。

    因此 ARM64 下真正该验证的是：

    1. loadLocalgw/loadMvmtap/loadNodenic 是否成功。
    2. verifier 是否接受对象中的 helper、map 和程序布局。
    3. map 是否能按预期 pin 到 /sys/fs/bpf。

    这里最容易误判。

    编译通过只说明 Go 层 wrapper 没问题。

    真正的风险在运行时 LoadCollectionSpec 和 NewCollectionWithOptions。

    5. 第三层：TC attach 能否在 ARM64 host 上完成

    CubeVS Init() 会加载三个对象，再把 from_envoy 挂到 cubegw0 egress，把 from_world 挂到 node NIC 和 lo ingress。

    源码依据：cubevs.go。

    单个 TAP 的 from_cube 由 AttachFilter() 负责挂载。

    它先创建 clsact qdisc，再用 tc.Filter.Replace 把 BPF 程序挂到指定方向。

    源码依据：cubevs.go，tc.go。

    因此 ARM64 host 的最小验证项是：

    1. tc.Open() 可用。
    2. Qdisc().Add(clsact) 成功。
    3. Filter().Replace(bpf) 成功。
    4. TAP、node NIC 和 cubegw0 上都能看到对应 filter。

    如果这一层失败，现象通常不是 VMM 启动失败。

    更常见的表现是 guest 看得到网卡，但没有真正的数据面转发。

    6. 第四层：ARM64 VMM 如何暴露网络和中断

    aarch64 的 configure_vcpu() 会把 kernel entry 和 FDT_START 写入寄存器，再读取 MPIDR_EL1。

    源码依据：aarch64/mod.rs。

    configure_system() 再根据 MPIDR、device info、PCI space 和 GIC 生成 FDT。

    源码依据：aarch64/mod.rs。

    中断控制器不是 IOAPIC，而是 Gic。

    create_default_config() 会按 layout 计算 distributor、redistributor 和 MSI 区域。

    源码依据：gic.rs。

    更底层的 KVM GICv3 ITS 设备会显式创建 ITS device，并暴露 arm,gic-v3 与 arm,gic-v3-its 兼容字符串。

    源码依据：gic/mod.rs，gic/mod.rs。

    这层应该关注三个观测点：

    1. guest 是否能按 FDT 枚举到 virtio-net 和 GICv3 ITS。
    2. virtio-net 队列完成后，MSI 能否通过 GIC/ITS 注入 guest。
    3. guest 内网卡顺序是否和 cube-agent 的 MAC 匹配逻辑一致。

    如果这里失败，常见现象是：

    网卡在 host 已创建，TAP 和 eBPF 也都正常，但 guest 内中断不通，RX/TX 卡死或设备枚举异常。

    7. 第五层：guest 内接口配置是否真正完成

    cube-agent 的 create_sandbox() 在处理接口时，会先检查 pciPath。

    如果有 PCI path，它会先 wait_for_pci_net()，再调用 update_interface()。

    源码依据：rpc.rs。

    update_interface() 本身并不是按名字找接口。

    它先按 MAC 地址找 link，再删旧地址、加新地址、设 MTU、改名字并拉起接口。

    源码依据：netlink.rs。

    随后 update_routes() 会删旧路由再加新路由。

    源码依据：netlink.rs。

    这说明 ARM64 下 guest 配网的最小验证项不是“virtio-net driver loaded”。

    真正需要确认的是：

    1. PCI path 或 MAC 地址能稳定定位目标网卡。
    2. eth0 重命名与地址配置成功。
    3. route 和 ARP 更新没有因为设备顺序差异而落到错误接口。

    8. 第六层：restore 后网络还能不能醒

    ARM64 的 snapshot 明确额外保存了 VGIC snapshot section。

    源码依据：vm.rs。

    Gic 的 snapshot id 是 gic-v3-its。

    它在 pause() 时会把 pending tables 和 ITS tables flush 到 guest RAM。

    源码依据：gic.rs。

    restore 时，VMM 会重新创建 VGIC，初始化 PMU IRQ，再用保存的 vCPU state 重建 GICR_TYPER，恢复 gic-v3-its section，最后重新 enable() interrupt routing。

    源码依据：vm.rs。

    所以 ARM64 网络 restore 的验证重点必须包括：

    1. snapshot 中是否存在 gic-v3-its section。
    2. restore 后是否执行了 set_gicr_typers()。
    3. restore 后首个 TAP 可读事件能否重新唤醒 guest。

    如果这里失败，通常表现为 restore 前网络正常，restore 后设备还在，但首包后不再触发 RX 中断。

    9. 推荐的验证顺序

    按源码依赖关系，建议顺序如下。

    第一步：验证 guest kernel 和 host 能力。

    重点看 /dev/kvm、ARM64 guest kernel config、TUN/TAP、BPF、TC 和 GICv3 ITS 前置条件。

    第二步：验证 CubeVS load 和 TC attach。

    重点看 loadObject()、Init()、AttachFilter() 是否都成功。

    第三步：验证正常启动链。

    重点看 VM boot、virtio-net 枚举、guest eth0 配置和 host/guest 互通。

    第四步：验证策略与端口路径。

    重点看 from_cube、from_world、from_envoy 三个入口都能形成完整路径。

    第五步：验证 snapshot/restore。

    重点看 gic-v3-its、GICR_TYPER 和 restore 后首包唤醒。

    10. 最小检查表

    flowchart TB Host["host /dev/kvm + tc + bpffs"] --> CubeVS["CubeVS load + attach"] CubeVS --> VMM["FDT + GICv3 ITS + virtio-net"] VMM --> Guest["guest MAC match + eth0 + routes"] Guest --> Data["from_cube / from_world / from_envoy"] Data --> Restore["snapshot/restore wakeup"]

    建议把 ARM64 网络最小检查表固定为这十项：

    1. guest kernel 启用了 BPF、NET_SCHED、TUN/TAP、VIRTIO_NET 和 ARM_GIC_V3_ITS。
    2. CubeVS ARM64 loader 能成功解析三个嵌入对象。
    3. cubegw0、node NIC、lo 和 TAP 上都能挂上正确 TC filter。
    4. guest 能通过 FDT 枚举 virtio-net。
    5. GICv3 ITS 可用于 MSI 注入。
    6. cube-agent 能按 MAC 找到目标 NIC。
    7. eth0、IP、route、ARP 和 DNS 都能落地。
    8. 出站 from_cube 路径可通。
    9. 入站 from_world/from_envoy 路径可通。
    10. restore 后首包仍能触发中断唤醒。

    11. 结论

    CubeSandbox 的 ARM64 网络问题，本质上不是单点问题。

    它是一条跨 guest kernel、host eBPF/TC、VMM FDT/GIC、guest netlink 和 restore 中断状态的组合链。

    所以最靠谱的研究方式不是再写一篇泛泛的 ARM64 介绍。

    而是按这份矩阵逐层收证据，确认每一层成功时上一层的假设才成立。

    源文件: CubeSandbox-sandbox-clone/analysis/arm64-network-validation-matrix.md
