    context_switch finish 阶段流程分析

    本文总结 sbench 定制 sched:sched_context_switch_cost 插桩下，一次 context_switch() 的整体执行流程，并重点解释 finish_cycles 所覆盖的 finish_task_switch(prev) 阶段。

    分析对象：

    • 实验环境：openEuler 24.03 LTS-SP3、arm64、6.6.0-132.0.0.111.oe2403sp3.aarch64。
    • 插桩说明：context-switch-cost-experiment.zh.md。
    • 插桩补丁：0001-sched-arm64-add-context-switch-cost-tracepoint.patch。
    • 内核源码参考：openEuler OLK-6.6 分支的 kernel/sched/core.c， 与实验内核同属 openEuler 6.6 调度器代码路径。

    观测窗口

    实验插桩在 context_switch(prev, next) 内读取四类时间段：

    context_switch(prev, next)
|
|  T0 = core_start_cycles
|  prepare_task_switch()
|  ...
|  switch_mm_irqs_off()
|  switch_mm_cid()
|  prepare_lock_switch()
|
|  T1 = arch_start_cycles
|  switch_to(prev, next, prev)
|  barrier()
|  T2 = after_switch_cycles
|
|  finish_task_switch(prev)
|  T3 = after_finish_cycles
|
return rq

    其中：

    core_pre_finish_cycles = T2 - T0
arch_switch_cycles     = T2 - T1
finish_cycles          = T3 - T2
total_cycles           = T3 - T0

    finish_cycles 的关键边界是：

    • 起点 T2：switch_to(prev, next, prev) 返回后，已经处在 next/current 任务上下文。
    • 终点 T3：finish_task_switch(prev) 返回后，tracepoint 写事件之前。

    因此，finish_cycles 不包含 tracepoint 写入本身，但包含 T2 读数之后到 T3 读数之前的收尾路径，包括 finish_task_switch(prev) 中打开中断后可能 执行的 IRQ handler 时间。

    context_switch 主流程

    openEuler 6.6 的 context_switch() 主体结构如下，省略了部分注释：

    static __always_inline struct rq *
context_switch(struct rq *rq, struct task_struct *prev,
               struct task_struct *next, struct rq_flags *rf)
{
        prepare_task_switch(rq, prev, next);
        arch_start_context_switch(prev);

        if (!next->mm) {
                enter_lazy_tlb(prev->active_mm, next);
                next->active_mm = prev->active_mm;
                if (prev->mm)
                        mmgrab_lazy_tlb(prev->active_mm);
                else
                        prev->active_mm = NULL;
        } else {
                membarrier_switch_mm(rq, prev->active_mm, next->mm);
                switch_mm_irqs_off(prev->active_mm, next->mm, next);
                lru_gen_use_mm(next->mm);

                if (!prev->mm) {
                        rq->prev_mm = prev->active_mm;
                        prev->active_mm = NULL;
                }
        }

        switch_mm_cid(rq, prev, next);
        prepare_lock_switch(rq, next, rf);

        switch_to(prev, next, prev);
        barrier();

        return finish_task_switch(prev);
}

    按执行语义拆开：

    1. prepare_task_switch() 做切换前的调度器准备。
    2. arch_start_context_switch() 做架构相关切换准备。
    3. 根据 next->mm 处理 kernel thread / user task 的地址空间切换。
    4. 对 user task 路径执行 switch_mm_irqs_off()，即在 IRQ 关闭状态下切换地址空间。
    5. switch_mm_cid() 维护 mm context id。
    6. prepare_lock_switch() 把 runqueue lock 的释放责任转交给切入后的任务上下文。
    7. switch_to() 切换寄存器和内核栈。
    8. finish_task_switch(prev) 在新任务上下文中完成收尾。

    这说明 arch_switch_cycles 更贴近第 7 步的寄存器/栈切换；而 finish_cycles 观察的是第 8 步以及其周边尾部开销。

    finish_task_switch 源码结构

    openEuler 6.6 中 finish_task_switch(prev) 的主体步骤如下：

    static struct rq *finish_task_switch(struct task_struct *prev)
        __releases(rq->lock)
{
        struct rq *rq = this_rq();
        struct mm_struct *mm = rq->prev_mm;
        unsigned int prev_state;

        if (WARN_ONCE(preempt_count() != 2*PREEMPT_DISABLE_OFFSET,
                      "corrupted preempt_count: %s/%d/0x%x\n",
                      current->comm, current->pid, preempt_count()))
                preempt_count_set(FORK_PREEMPT_COUNT);

        rq->prev_mm = NULL;

        prev_state = READ_ONCE(prev->__state);
        vtime_task_switch(prev);
        perf_event_task_sched_in(prev, current);
        mem_sampling_sched_in(prev, current);
        finish_task(prev);
        tick_nohz_task_switch();
        finish_lock_switch(rq);
        finish_arch_post_lock_switch();
        kcov_finish_switch(current);
        kmap_local_sched_in();

        fire_sched_in_preempt_notifiers(current);

        if (mm) {
                membarrier_mm_sync_core_before_usermode(mm);
                mmdrop_lazy_tlb_sched(mm);
        }

        if (unlikely(prev_state == TASK_DEAD)) {
                if (prev->sched_class->task_dead)
                        prev->sched_class->task_dead(prev);

                put_task_stack(prev);
                put_task_struct_rcu_user(prev);
        }

        return rq;
}

    这个阶段包含几类工作。

    第一类是切换后状态校验与清理：

    • 重新取 this_rq()。switch_to() 已经切换到新任务内核栈，不能继续假设普通局部状态仍代表旧任务上下文。
    • 检查 preempt_count() 是否符合调度器切换后的预期。
    • 清空 rq->prev_mm，为后续 delayed mm drop 做准备。
    • 读取 prev->__state，后面判断 prev 是否已经进入 TASK_DEAD。

    第二类是调度、性能和时间 accounting：

    • vtime_task_switch(prev)：虚拟 CPU 时间 accounting。
    • perf_event_task_sched_in(prev, current)：perf sched-in accounting。
    • mem_sampling_sched_in(prev, current)：openEuler 6.6 源码中的内存采样 sched-in 处理。

    第三类是完成 prev 从 CPU 上切出的状态发布：

    static inline void finish_task(struct task_struct *prev)
{
#ifdef CONFIG_SMP
        smp_store_release(&prev->on_cpu, 0);
#endif
}

    prev->on_cpu 清零后，其他 CPU 上的 wakeup 路径可以观察到 prev 已经不再 运行在当前 CPU 上。这一步必须发生在读取 prev->__state 之后，避免和并发 wakeup / task dead 状态转换发生乱序。

    第四类是 tick/nohz 和 runqueue lock 收尾：

    static inline void finish_lock_switch(struct rq *rq)
{
        spin_acquire(&__rq_lockp(rq)->dep_map, 0, 0, _THIS_IP_);
        __balance_callbacks(rq);
        raw_spin_rq_unlock_irq(rq);
}

    这是理解 finish_cycles 尖峰的核心位置：

    • prepare_lock_switch() 之前仍在旧任务上下文中持有 runqueue lock。
    • switch_to() 之后，新任务上下文继续持有这个 lock。
    • finish_lock_switch(rq) 在新任务上下文中释放 runqueue lock。
    • raw_spin_rq_unlock_irq(rq) 不只是 unlock，还会重新打开本地中断。

    也就是说，从 finish_lock_switch() 执行到 finish_task_switch() 返回之间， 已经进入了一个 IRQ 可执行的窗口。如果此时本 CPU 有 pending IRQ，或刚好有 新 IRQ 到达，硬中断处理会发生在 finish_cycles = T3 - T2 的观测窗口内。

    第五类是打开 runqueue lock 之后的后置清理：

    • finish_arch_post_lock_switch()：架构相关 post-lock 收尾，未定义时为空。
    • kcov_finish_switch(current)：kcov 上下文切换收尾。
    • kmap_local_sched_in()：恢复 local kmap 状态。
    • fire_sched_in_preempt_notifiers(current)：触发 preempt notifier 的 sched-in 回调。

    第六类是延迟释放 mm 和死亡任务清理：

    • 如果 rq->prev_mm 非空，执行 membarrier_mm_sync_core_before_usermode(mm) 和 mmdrop_lazy_tlb_sched(mm)。这是前面 context_switch() 中 kernel thread / user task 切换路径延迟下来的 mm 引用释放。
    • 如果 prev_state == TASK_DEAD，执行调度类的 task_dead 回调，并释放 task stack 和 task 引用。

    这些路径并非每次都会发生，但它们都属于 finish_cycles 的合法覆盖范围。

    插桩实现对 finish 的实际计量

    补丁在 switch_to() 返回后读取 T2，并记录：

    switch_to(prev, next, prev);
barrier();

if (trace_sched_context_switch_cost_enabled()) {
        struct sched_cs_cost_sample *cost = this_cpu_ptr(&sched_cs_cost);
        u64 now = __arch_counter_get_cntvct();

        cost->core_pre_finish_cycles = now - cost->core_start_cycles;
        cost->arch_switch_cycles = now - cost->arch_start_cycles;
}

rq = finish_task_switch(prev);

if (trace_sched_context_switch_cost_enabled()) {
        total_cycles = __arch_counter_get_cntvct() - cost->core_start_cycles;
        finish_cycles = total_cycles - cost->core_pre_finish_cycles;
        trace_sched_context_switch_cost(...);
}

    由此可知：

    • finish_cycles 的数学含义是 T3 - T2。
    • tracepoint 调用发生在 T3 之后，不计入 finish_cycles。
    • T2 之后到 finish_task_switch() 调用前的少量插桩赋值会计入 finish_cycles，但这是固定小开销，不足以解释大幅尖峰。
    • 大幅尖峰更可能来自 finish_task_switch() 内部的条件路径、lock 释放后的 IRQ/softirq 扰动，或二者叠加。

    为什么 IRQ 会主要放大 finish 阶段

    context_switch() 前半段仍在调度器临界区内，尤其 switch_mm_irqs_off()、 prepare_lock_switch()、switch_to() 附近与 IRQ-off / rq lock 语义紧密相关。 这部分更接近调度器和架构切换本体。

    进入 finish_task_switch() 后，流程发生变化：

    T2: switch_to 返回，已经是 next/current
 |
 |  finish_task_switch(prev)
 |    vtime / perf / mem sampling
 |    finish_task(prev)
 |    tick_nohz_task_switch()
 |    finish_lock_switch(rq)
 |      __balance_callbacks(rq)
 |      raw_spin_rq_unlock_irq(rq)  <-- 释放 rq lock，并打开本地 IRQ
 |        [pending IRQ 可在这里开始执行]
 |    finish_arch_post_lock_switch()
 |    kcov / kmap / preempt notifier
 |    delayed mm drop
 |    TASK_DEAD 清理
 |
T3: finish_task_switch 返回后读取时间

    如果 IRQ 在 raw_spin_rq_unlock_irq(rq) 打开本地中断之后执行，CNTVCT 看到的是 elapsed cycles，而不是只统计 C 函数自身指令。因此 IRQ handler 消耗的时间会直接进入 finish_cycles。

    这解释了两个观测现象：

    • finish_cycles 比 arch_switch_cycles 更容易出现长尾。
    • 当 CPU irq% 的时间窗口升高时，finish_cycles 更容易出现同步尖峰。

    如果 hard IRQ 后又触发 softirq，且 softirq 在返回路径中被处理，那么 softirq 时间也可能成为同一类尾部扰动。是否归入 hard IRQ 还是 softirq，需要结合 irq_handler_entry/exit、softirq_entry/exit 或 sar -u ALL 的 irq/soft 字段进一步拆分。

    对当前实验现象的推断

    实验设置是在单节点机器上按 {1, 100, 500, 1000, 1500} 增加沙箱数量， 并始终观察第一个沙箱进程的 context-switch 数据。已确认的数据事实是：

    • 随着中断占据 CPU 时间增长，context-switch 数据出现尖峰。
    • 尖峰主要体现在 finish_cycles。
    • finish_cycles 与 CPU irq% 在时间窗口上存在相关性。

    结合上面的源码路径，可以形成如下推断：

    1. 沙箱数量增加后，系统中 VMM、虚拟设备、timer、IPI、网络/块设备等相关 事件变多，导致 CPU 的 IRQ 压力上升。
    2. 第一个沙箱进程虽然固定不变，但它每次被调度回来时面对的是更拥挤的系统 状态，而不是一个隔离的单进程环境。
    3. arch_switch_cycles 主要覆盖 switch_to() 附近的寄存器和栈切换，仍然 更接近 context switch 的架构本体成本。
    4. finish_cycles 覆盖 finish_task_switch()，其中 finish_lock_switch() 会通过 raw_spin_rq_unlock_irq(rq) 释放 rq lock 并重新打开本地中断。
    5. 当打开本地中断时存在 pending IRQ，或 IRQ 在这个窗口内到达，IRQ handler 的 elapsed cycles 会被计入 finish_cycles。
    6. 因此，finish_cycles 的尖峰更像是“context switch 收尾窗口被 IRQ 放大 的尾延迟”，而不是 switch_to() 本身随着沙箱数量增加而线性变慢。

    更准确的报告表述应为：

    在 openEuler 6.6 的 context_switch() 路径中，finish_cycles 覆盖 switch_to() 返回后到 finish_task_switch(prev) 返回前的收尾窗口。 该窗口包含 finish_lock_switch() 中释放 runqueue lock 并重新打开本地中断 的步骤。因此，当沙箱规模增大导致 CPU IRQ 时间上升时，pending IRQ 或新到达 IRQ 可能在 finish_task_switch() 返回前执行，并被计入 finish_cycles。 当前数据中 finish_cycles 与 CPU irq% 存在时间窗口相关性，支持将尖峰 解释为 IRQ 放大的 context-switch finish 尾延迟，而不是架构级 switch_to() 本体成本的稳定退化。

    后续验证建议

    为了把相关性进一步拆成具体来源，需要把问题拆成三层：

    1. 哪些 IRQ / softirq 在尖峰窗口增长。
    2. 这些 IRQ 对应哪些设备、handler 或内核子系统。
    3. 它们是否插入到目标进程的 finish_cycles 观测窗口内。

    第一层：用计数器定位增长来源

    先用 /proc/interrupts 和 /proc/softirqs 做低成本窗口采样：

    while true; do
  date '+%s.%N'
  cat /proc/interrupts
  cat /proc/softirqs
  sleep 1
done > /tmp/irq-softirq.log

    分析时按相邻两个时间点做 delta，优先找：

    • 某个 IRQ 号的计数是否在 finish_cycles 尖峰窗口同步增加。
    • softirq 中 TIMER、NET_RX、NET_TX、BLOCK、SCHED、HRTIMER、 RCU 哪些类型增长最快。
    • 增长是否集中在目标沙箱进程所在 CPU，还是分散到多个 CPU。

    IRQ 号可以从 /proc/interrupts 直接回查 handler 名称，也可以继续查看：

    cat /proc/irq/<IRQ>/smp_affinity_list
cat /proc/irq/<IRQ>/effective_affinity_list
find /sys/kernel/irq/<IRQ> -maxdepth 1 -type f -print

    如果 handler 名称指向网卡、NVMe、virtio、vhost、GIC timer、IPI 等，就可以把 问题先归类到网络、块设备、虚拟设备、timer 或跨核通信方向。

    第二层：用 trace-cmd 对齐事件时间线

    /proc/interrupts 只能告诉我们哪个 IRQ 在涨，不能证明它是否落在 finish_cycles 的 T2 到 T3 窗口。需要用 ftrace/trace-cmd 采集事件时间线：

    trace-cmd record \
  -e sched:sched_context_switch_cost \
  -e sched:sched_switch \
  -e irq:irq_handler_entry \
  -e irq:irq_handler_exit \
  -e irq:softirq_entry \
  -e irq:softirq_exit \
  -e timer:hrtimer_expire_entry \
  -e timer:timer_expire_entry \
  sleep 10

trace-cmd report > /tmp/irq-finish-trace.txt

    如果怀疑 IPI 或跨核调度唤醒，可以增加：

    trace-cmd record \
  -e sched:sched_context_switch_cost \
  -e sched:sched_switch \
  -e sched:sched_wakeup \
  -e irq:irq_handler_entry \
  -e irq:irq_handler_exit \
  -e irq:softirq_entry \
  -e irq:softirq_exit \
  -e timer:hrtimer_expire_entry \
  -e timer:timer_expire_entry \
  -e ipi:* \
  sleep 10

    看 trace 时重点检查：

    • sched_context_switch_cost 中 next_pid 是否为目标沙箱进程。
    • 该事件附近是否紧邻 irq_handler_entry/exit。
    • IRQ handler 名称和 /proc/interrupts 中增长最快的 IRQ 是否一致。
    • hard IRQ 后是否跟随 softirq_entry/exit，从而把尾部时间继续拉长。
    • timer、hrtimer、ipi 事件是否集中出现在高沙箱数量实验窗口。

    如果目标机器没有安装 trace-cmd，可以用 tracefs 直接采集：

    TRACE=/sys/kernel/tracing

echo 0 > $TRACE/tracing_on
echo > $TRACE/trace
echo > $TRACE/set_event

echo sched:sched_context_switch_cost >> $TRACE/set_event
echo sched:sched_switch             >> $TRACE/set_event
echo irq:irq_handler_entry          >> $TRACE/set_event
echo irq:irq_handler_exit           >> $TRACE/set_event
echo irq:softirq_entry              >> $TRACE/set_event
echo irq:softirq_exit               >> $TRACE/set_event
echo timer:hrtimer_expire_entry     >> $TRACE/set_event
echo timer:timer_expire_entry       >> $TRACE/set_event

echo 1 > $TRACE/tracing_on
sleep 10
echo 0 > $TRACE/tracing_on

cat $TRACE/trace > /tmp/irq-finish-trace.txt

    第三层：用 bpftrace 聚合 IRQ 时间

    当 trace 文本量太大时，可以先用 bpftrace 聚合每秒 hard IRQ 耗时：

    bpftrace -e '
tracepoint:irq:irq_handler_entry
{
  @ts[args->irq, cpu] = nsecs;
}

tracepoint:irq:irq_handler_exit /@ts[args->irq, cpu]/
{
  @irq_time[args->irq, cpu] = sum(nsecs - @ts[args->irq, cpu]);
  @irq_count[args->irq, cpu] = count();
  delete(@ts[args->irq, cpu]);
}

interval:s:1
{
  print(@irq_time);
  print(@irq_count);
  clear(@irq_time);
  clear(@irq_count);
}
'

    softirq 可以按 vector 聚合：

    bpftrace -e '
tracepoint:irq:softirq_entry
{
  @ts[args->vec, cpu] = nsecs;
}

tracepoint:irq:softirq_exit /@ts[args->vec, cpu]/
{
  @softirq_time[args->vec, cpu] = sum(nsecs - @ts[args->vec, cpu]);
  @softirq_count[args->vec, cpu] = count();
  delete(@ts[args->vec, cpu]);
}

interval:s:1
{
  print(@softirq_time);
  print(@softirq_count);
  clear(@softirq_time);
  clear(@softirq_count);
}
'

    常见 softirq vector 含义：

    0 HI
1 TIMER
2 NET_TX
3 NET_RX
4 BLOCK
5 IRQ_POLL
6 TASKLET
7 SCHED
8 HRTIMER
9 RCU

    结果归因规则

    结合以上三层数据，可以按下面规则归因：

    • NET_RX / NET_TX 高：优先检查 tap/veth/物理网卡、虚拟网络设备和 ethtool -S <iface>、ip -s link、/proc/net/softnet_stat。
    • BLOCK 或 NVMe IRQ 高：优先检查镜像、日志、块设备队列和 iostat -x 1。
    • TIMER / HRTIMER 高：优先检查高密度沙箱带来的 timer tick、hrtimer 和 runtime 轮询。
    • IPI 高：优先检查跨核 wakeup、TLB shootdown、RCU、负载均衡和 CPU 亲和性。
    • virtio、vhost、KVM、GIC 相关 handler 高：优先检查微 VM 虚拟设备、eventfd、 vCPU 线程、I/O 线程和宿主机中断亲和性。

    最终需要把这些事件和 sched_context_switch_cost 中的高 finish_cycles 样本按时间戳对齐。如果 IRQ 或 softirq 总是在高 finish_cycles 样本前后贴近 出现，就可以把“finish 尖峰来自中断窗口扰动”的推断从窗口相关性推进到事件级 证据。

    推荐最小采集组合

    当前问题最小推荐采集组合是：

    trace-cmd record \
  -e sched:sched_context_switch_cost \
  -e sched:sched_switch \
  -e irq:irq_handler_entry \
  -e irq:irq_handler_exit \
  -e irq:softirq_entry \
  -e irq:softirq_exit \
  -e timer:hrtimer_expire_entry \
  -e timer:timer_expire_entry \
  sleep 10

    分析时建议把 arch_switch_cycles、core_pre_finish_cycles、finish_cycles 分开呈现。arch_switch_cycles 用于描述较纯的架构切换本体；finish_cycles 和 total_cycles 用于描述包含调度器收尾、IRQ 扰动和条件清理路径的尾延迟。
