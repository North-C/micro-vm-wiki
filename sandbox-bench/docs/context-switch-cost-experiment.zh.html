    Context Switch 内核切换开销观测设计与实现方案

    本文说明 sbench context switch 开销专项实验的设计、内核插桩实现、RPM 编译部署、验证方法和采样结果解释。当前已验证环境为 openEuler 24.03 LTS-SP3、arm64、6.6.0-132.0.0.111.oe2403sp3.aarch64，验证主机为 root@192.168.25.61。

    该方案不是测进程 off-CPU 时长，也不是测 runqueue latency，而是尽量贴近 Linux 内核执行一次 context_switch() 的切换动作成本。它应作为显式 opt-in 的定制内核实验指标使用，不建议作为 sbench 默认常规指标长期打开。

    设计目标

    目标口径：

    • 观测单次任务切换在内核中的执行成本，覆盖 context_switch() 内部关键路径。
    • 单次样本保留 raw counter cycles，避免热路径中做 ns 换算。
    • 支持按 prev_pid / next_pid 过滤目标进程，避免全系统长期逐事件采集。
    • tracepoint 默认关闭，未启用时只承担 tracepoint static key 判断开销。
    • 启用后优先用于短窗口采样，正式压力场景优先使用 eBPF/perf 聚合而不是 tracefs 文本输出。

    非目标口径：

    • 不测调度等待时间，即任务从 runnable 到实际运行之间的 runqueue latency。
    • 不测阻塞时间，即任务被切出后到再次切入之间的 off-CPU latency。
    • 不把 schedule() 外层函数耗时作为 context switch 本体开销，因为它包含较多调度器路径和调用场景。
    • 不依赖动态 kprobe 覆盖 __schedule、context_switch() 或 cpu_switch_to()，这些点在当前内核上不可稳定动态观测。

    插桩方案对比

    动态 eBPF/kprobe/function graph

    动态方案的优点是不需要改内核，适合快速探索函数调用结构。但在当前 openEuler arm64 内核上存在关键限制：

    • context_switch() 是 static __always_inline，没有独立可 probe 的稳定符号。
    • __schedule 有符号，但在当前环境中不在 ftrace 可过滤函数集合中，kprobe/kretprobe 不稳定。
    • cpu_switch_to 是更底层的寄存器和栈切换点，但源码显式 NOKPROBE(cpu_switch_to)。
    • schedule() 外层可被 function graph 观测，但口径过宽，不能等价为一次 context switch 本体开销。
    • function graph 在高频切换微基准中扰动很大，更适合短时结构分析，不适合输出精确低扰动数值。

    结论：动态工具可作为前期验证和结构辅助，不作为主采集方案。

    内核 tracepoint + local_clock()

    local_clock() 直接返回 ns，语义接近 scheduler/ftrace 的 sched clock，通用性较好。但它通常包含 sched clock 换算、seqcount retry、preempt disable/enable 等逻辑。对于几十到几百 ns 的短路径，时间戳读取本身更容易影响测量值。

    结论：local_clock() 可作为 ns 口径对照，不作为本实验主时间源。

    内核 tracepoint + 裸 mrs cntvct_el0

    裸读 cntvct_el0 指令数最少，理论开销最低。但它缺少 arm64 内核封装中的 ordering 处理、ECV alternative 和平台兼容逻辑。对于极短路径，裸 mrs 可能得到更低的数值，但测量边界语义弱，容易受乱序或 speculative system register read 影响。

    结论：裸 mrs cntvct_el0 只适合作为估计时间戳读取下界的对照实验，不作为正式数据来源。

    内核 tracepoint + __arch_counter_get_cntvct()

    __arch_counter_get_cntvct() 是 arm64 内核读取 virtual counter 的 inline 封装。它仍读取 CNTVCT，但比裸 mrs 多了内核期望的同步与 ordering 语义：

    asm volatile(ALTERNATIVE("isb\n mrs %0, cntvct_el0",
                         "nop\n" __mrs_s("%0", SYS_CNTVCTSS_EL0),
                         ARM64_HAS_ECV)
             : "=r" (cnt));
arch_counter_enforce_ordering(cnt);

    该方案的特点：

    • 比 local_clock() 更接近硬件 counter，避免热路径 ns 换算和 sched clock 额外逻辑。
    • 比裸 mrs 更稳健，保留 isb、ECV self-synchronizing counter 路径和 ordering 处理。
    • 输出 raw cycles，可在用户态或 eBPF 侧按 cntfrq 换算为 ns。
    • arm64 专用，不作为通用上游 ABI 设计。

    结论：本方案选择 __arch_counter_get_cntvct() 作为主时间源。

    详细设计

    内核 patch 路径：

    patches/linux/0001-sched-arm64-add-context-switch-cost-tracepoint.patch

    patch 修改两个文件：

    • include/trace/events/sched.h：新增 sched:sched_context_switch_cost tracepoint。
    • kernel/sched/core.c：在 context_switch() 内读取 CNTVCT 时间戳，并通过 per-CPU scratch slot 跨过 switch_to() 保存样本。

    新增 tracepoint：

    sched:sched_context_switch_cost

    事件字段：

    prev_pid
next_pid
core_pre_finish_cycles
arch_switch_cycles
finish_cycles
total_cycles
cntfrq

    关键实现点：

    • 使用 trace_sched_context_switch_cost_enabled() 判断 tracepoint 是否启用；未启用时只走 static key 快路径。
    • 使用 DEFINE_PER_CPU(struct sched_cs_cost_sample, sched_cs_cost) 保存跨 switch_to() 的中间时间戳。
    • 不在热路径做 ns 换算，只输出 cycles 和 cntfrq。
    • 在样本字段完整时才输出 tracepoint，避免 tracepoint 在切换中途打开时产生脏样本。
    • 仅在 CONFIG_ARM64 下启用该插桩逻辑。

    选择 per-CPU scratch slot 的原因是 switch_to(prev, next, prev) 返回后已经切换到 next 任务的内核栈，不能把跨切换样本依赖在普通局部变量上。per-CPU slot 与当前 CPU 上的一次切换路径绑定，适合保存 t0/t1/prev_pid/next_pid。

    观测指标说明

    插桩读取四个时间点：

    context_switch(prev, next)
|
|  T0 = core_start_cycles
|  prepare_task_switch()
|  ...
|  switch_mm_irqs_off()
|  switch_mm_cid()
|  prepare_lock_switch()
|
|  T1 = arch_start_cycles
|  switch_to(prev, next, prev)
|  barrier()
|  T2 = after_switch_cycles
|
|  finish_task_switch(prev)
|  T3 = after_finish_cycles
|
return rq

    各指标覆盖区间：

    core_pre_finish_cycles = T2 - T0

T0 |---------------- prepare + mm + lock + switch_to ----------------| T2

arch_switch_cycles = T2 - T1

T1 |-------------------------- switch_to -----------------------------| T2

finish_cycles = T3 - T2

T2 |-------------------- finish_task_switch --------------------------| T3

total_cycles = T3 - T0

T0 |--------- prepare + mm + lock + switch_to + finish_task_switch ---| T3

    字段语义：

    字段 含义 主要用途
    prev_pid 被切出的任务 PID 过滤目标进程
    next_pid 被切入的任务 PID 过滤目标进程
    core_pre_finish_cycles context_switch() 入口到 switch_to() 返回后的周期数 观测 finish 前的核心切换路径
    arch_switch_cycles 紧贴 switch_to() 前到 switch_to() 返回后的周期数 更接近架构态寄存器/栈切换成本
    finish_cycles switch_to() 返回后到 finish_task_switch() 返回后的周期数 观测收尾路径和长尾
    total_cycles context_switch() 入口到 finish_task_switch() 返回后的周期数 完整 context_switch() 口径
    cntfrq arm64 generic timer 频率 cycles 到 ns 的换算因子

    注意：finish_task_switch() 会释放 rq lock 并重新打开中断，finish_cycles 和 total_cycles 可能出现中断或其他尾部扰动导致的离群值。因此报告中应优先看 p50/p90/p99 和直方图，max 只作为异常观察值。

    使用 eBPF/bpftrace 做聚合采样

    tracefs 文本输出不适合高频长期采集。正式压力测试建议使用 eBPF 聚合，按周期读取直方图或分位数。示例：

tracepoint:sched:sched_context_switch_cost
/args->prev_pid == 23903 || args->next_pid == 23903/
{
  @arch = hist(args->arch_switch_cycles);
  @core = hist(args->core_pre_finish_cycles);
  @finish = hist(args->finish_cycles);
  @total = hist(args->total_cycles);

}

{
  print(@count);
  print(@arch);
  print(@core);
  print(@finish);
  print(@total);
  exit();
}'

    后续接入 sbench collector 时，建议默认读取聚合结果：count、sum、min、max、p50、p90、p99 或 histogram bucket，而不是长期落每一条事件文本。

    结果内容说明

    单条事件字段示例：

    prev_pid=23969
next_pid=23903
core_pre_finish_cycles=53
arch_switch_cycles=37
finish_cycles=71
total_cycles=124
cntfrq=100000000

    解释：

    • prev_pid=23969 表示这次切换中被切出的任务。
    • next_pid=23903 表示这次切换中被切入的任务。
    • core_pre_finish_cycles=53 表示从 context_switch() 入口到 switch_to() 返回后的耗时，当前机器约 530ns。
    • arch_switch_cycles=37 表示紧贴 switch_to() 的架构切换段耗时，当前机器约 370ns。
    • finish_cycles=71 表示 switch_to() 返回后到 finish_task_switch() 返回的耗时，当前机器约 710ns。
    • total_cycles=124 表示完整 context_switch() 观测段耗时，当前机器约 1240ns。
    • cntfrq=100000000 表示 CNTVCT counter 每秒 tick 数为 100 MHz。

    本次短采样统计：

    指标 min p50 p90 p99 max
    core_pre_finish_cycles 18 46 52 59 69
    arch_switch_cycles 13 34 39 44 51
    finish_cycles 3 73 83 94 25682
    total_cycles 34 120 131 147 25723

    ns 换算方法

    事件输出的是 raw counter cycles，不是 ns。统一换算公式：

    duration_ns = cycles * 1000000000 / cntfrq

    当前验证机器：

    cntfrq = 100000000
1 cycle = 1000000000 / 100000000 ns = 10 ns

    因此当前机器可快速换算：

    duration_ns = cycles * 10

    脚本实现时不要硬编码 10ns，应使用每条事件中的 cntfrq 字段。跨机器或跨平台时，generic timer 频率可能不同。

    awk 换算示例：

    awk '
/sched_context_switch_cost:/ {
  for (i = 1; i <= NF; i++) {
    split($i, a, "=")
    if (a[1] == "arch_switch_cycles") arch = a[2] + 0
    if (a[1] == "total_cycles") total = a[2] + 0
    if (a[1] == "cntfrq") cntfrq = a[2] + 0
  }
  printf("arch_ns=%.1f total_ns=%.1f\n",
         arch * 1000000000.0 / cntfrq,
         total * 1000000000.0 / cntfrq)
}' /tmp/sbench_cscost_sample.txt

    损耗控制建议

    高频 context switch 机器上，不应长时间打开逐事件 tracefs 文本输出。推荐策略：

    • 默认关闭 sched:sched_context_switch_cost。
    • 采样前先设置 prev_pid/next_pid filter，避免采集全机切换。
    • tracefs 文本输出只用于 1-5 秒冒烟验证。
    • 正式压测使用 eBPF/perf ring buffer 聚合，周期性读取统计结果。
    • 每次报告同时记录 workload 基线吞吐和开启采集后的吞吐，用于量化观测扰动。
    • 对 finish_cycles 和 total_cycles 保留长尾分析，避免把中断扰动误判为稳定切换成本。

    当前结论

    __arch_counter_get_cntvct() + 定制 tracepoint 是当前环境下更合适的主方案。它在测量边界上比裸 mrs cntvct_el0 更稳健，在热路径开销上比 local_clock() 更低，并绕开了 context_switch() inline、__schedule notrace、cpu_switch_to NOKPROBE 等动态观测限制。

    当前 192.168.25.61 已完成 RPM 构建、安装、手动重启和 tracefs 短采样验证。tracepoint 可用，数据字段完整，cycles 到 ns 的换算链路已验证。
