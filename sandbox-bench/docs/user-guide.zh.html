    SBench 用户指南

    SBench 帮助你完成三件事：启动虚拟机 → 采集性能数据 → 可视化展示。本指南覆盖从环境准备到查看 Dashboard 的完整流程。

    当前能力范围

    • 支持通过 Firecracker 启动虚拟机，也支持导入外部启动的虚拟机进程。
    • 所有性能采集都在主机侧完成，不需要在虚拟机内部安装额外工具。
    • 虚拟机采用长驻模式：启动后持续运行，可以对其反复执行不同的采集任务。
    • 支持自动调度：Agent 可以按配置定期自动采集，无需手动操作。

    环境准备

    安装目录

    mkdir -p /opt/sbench/{bin,images,tools,results,state}

    构建 sbench

    go build -o /opt/sbench/bin/sbench ./cmd/sbench

    必要组件

    • sbench 放入 /opt/sbench/bin/ 或加入 PATH
    • Firecracker 二进制放入 /opt/sbench/bin/ 或加入 PATH
    • 虚拟机镜像放入 /opt/sbench/images/
    /opt/sbench/images/vmlinux            # 内核
/opt/sbench/images/initramfs.cpio.gz  # initramfs（可选）
/opt/sbench/images/rootfs.ext4        # rootfs

    构建镜像参考 microvm-image-build.md。

    可选组件

    工具 安装方式 用途
    perf 系统包管理器 采集 cache/TLB miss 等硬件事件
    FlameGraph 脚本 已随仓库 vendoring 到 third_party/FlameGraph/ 将 perf script 渲染为 SVG 火焰图
    Kunpeng DevKit 放入 /opt/sbench/tools/devkit/devkit TopDown 分析、内存带宽、miss 热点
    iostat / pidstat / sar 安装 sysstat 包 磁盘 I/O、进程资源、系统活动统计
    Docker / Docker Compose 系统包管理器 Prometheus/Grafana 可视化

    子命令详解

    sbench host probe — 探测主机环境

    扫描当前机器的硬件配置和工具可用性。在开始测试前运行一次，确认环境就绪。

    sbench host probe --root /opt/sbench

    输出一份 JSON 文件（默认写入 <root>/state/host-probe.json），包含：

    • CPU 核心数、在线 CPU 列表
    • NUMA 节点拓扑
    • 可用工具路径（firecracker、perf、devkit 等）
    • 内核版本和操作系统信息

    sbench deployment create — 启动虚拟机

    根据配置文件启动一批 Firecracker 虚拟机。每个 VM 独享一份 rootfs 副本，可指定 CPU 绑核策略。

    sbench deployment create \
  -c configs/deploy/firecracker-json-parse-2vm-quick.yaml \
  --root /opt/sbench

    启动成功后会输出 deployment_id，后续所有操作都通过这个 ID 关联。

    查看运行状态：

    sbench deployment status <deployment-id> --root /opt/sbench

    可用的部署配置示例：

    配置文件 说明
    firecracker-json-parse-quick.yaml 1 个 VM，快速验证
    firecracker-json-parse-2vm-quick.yaml 2 个 VM，标准测试
    firecracker-32-single-numa.yaml 32 个 VM，单 NUMA 节点
    firecracker-json-parse-1000-idle.yaml 1000 个 VM，高密度空闲测试

    sbench deployment import — 导入外部虚拟机

    当虚拟机由其他工具启动时，用此命令导入当前机器上正在运行的 Firecracker 进程。导入后可以像 sbench 自己启动的 VM 一样进行采集。

    # 自动扫描所有 Firecracker 进程
sbench deployment import --name external-sandbox --root /opt/sbench

# 只导入命令行包含特定关键字的进程
sbench deployment import --name json-parse-sandbox --pattern json-parse --root /opt/sbench

# 指定只扫描 Firecracker 进程
sbench deployment import --hypervisor firecracker --root /opt/sbench

    导入后会生成 deployment state 文件，包含每个 VM 的 PID、线程 ID、CPU 亲和性等信息。

    注意事项： - 导入的 deployment 在 destroy 时不会停止原始进程，只更新 sbench 的状态记录 - 适合临时采集场景——对外部管理的虚拟机做一次性性能分析

    sbench deployment status — 查看部署状态

    显示指定 deployment 的详细信息。

    sbench deployment status <deployment-id> --root /opt/sbench

    sbench deployment destroy — 销毁部署

    停止 deployment 中的所有 Firecracker 进程，释放资源。已采集的性能数据不会被删除，仍可用于后续分析。

    sbench deployment destroy <deployment-id> --root /opt/sbench

    sbench workload start — 登记负载会话

    为 deployment 创建一个 workload session，并生成 phase 文件和宿主机侧 metrics_dir。该命令不会进入虚拟机或 E2B sandbox 执行任务；任务仍需由 guest init、E2B sandbox exec、SDK commands.run() 或外部调度器启动。

    sbench workload start <deployment-id> \
  -c configs/workload/json-parse.yaml \
  --root /opt/sbench

    命令会同时输出 metrics_dir。对于支持 Terminal-Bench/E2B task_completion JSON 的负载，只有当这个目录对任务侧和 sbench agent 都可见时，agent 才能直接解析其中的完成事件并在 Overview 中展示沙箱任务吞吐量。 本地容器可以通过 volume 挂载该目录；远端 E2B sandbox 需要把事件文件同步回 这个目录，或通过宿主机可读的共享 metrics 目录写入。

    如果 E2B 任务需要在一批已存在的 sandbox 中持续运行，可以使用 Python SDK 辅助脚本按 template 名称/id 或 sandbox id 选择目标：

    python3 -m pip install e2b
export E2B_API_KEY=<your-e2b-api-key>

scripts/e2b-tbench-sdk.py list --template <template-name> --json

scripts/e2b-tbench-sdk.py start-loop \
  --template <template-name> \
  --rows 1000000 \
  --run-id-prefix tbench

scripts/e2b-tbench-sdk.py pull \
  --sandbox-id <sandbox-id-a> \
  --sandbox-id <sandbox-id-b> \
  /opt/sbench/results/workload-sessions/<session-id>/metrics

    start-loop 会在 sandbox 内安装 /tmp/sbench-tbench-loop.sh 并通过 SDK commands.run(..., background=True) 启动后台循环。默认情况下如果远端 pid 文件显示循环仍在运行，它不会重复叠加新的无限循环；需要强制替换时加 --restart。pull 会把远端 /tmp/sbench-task-metrics/completions.ndjson 增量拆分成宿主机 metrics_dir/e2b-<sandbox-id>-00000001.json 这样的单条 JSON 文件。 start-loop 默认会先校验并运行 E2B 镜像中安装的 /usr/local/bin/tbench-large-scale-text-editing；如果 template 使用不同路径， 通过 --task-bin <path-or-command> 覆盖。

    sbench workload stop — 停止负载

    将当前 workload session 标记为已停止。

    sbench workload stop <deployment-id> --root /opt/sbench

    sbench collect run — 采集性能数据（附带模式）

    绑定到已有的 deployment，对其中的虚拟机进程采集性能数据。每次执行会生成一个独立的采集目录。

    # 基础采集：CPU 使用率、进程资源占用、上下文切换
sbench collect run <deployment-id> \
  -c configs/collect/baseline-quick.yaml \
  --root /opt/sbench

# 硬件事件：cache miss、TLB miss 等
sbench collect run <deployment-id> \
  -c configs/collect/perf-stat-vmm-quick.yaml \
  --root /opt/sbench

# TopDown 性能分析
sbench collect run <deployment-id> \
  -c configs/collect/devkit-topdown-quick.yaml \
  --root /opt/sbench

# miss 热点分析
sbench collect run <deployment-id> \
  -c configs/collect/devkit-miss-event-vmm-quick.yaml \
  --root /opt/sbench

# 系统工具：iostat、pidstat、sar
sbench collect run <deployment-id> \
  -c configs/collect/sysstat-tools-vmm-quick.yaml \
  --root /opt/sbench

# 中断指标：sar + /proc/interrupts
sbench collect run <deployment-id> \
  -c configs/collect/interrupts-vmm-quick.yaml \
  --root /opt/sbench

    每个采集配置文件可以包含一个或多个采集器，通过 enabled 字段单独开关。

    sbench collector run — 采集性能数据（独立模式）

    不需要启动虚拟机，直接对指定的 CPU、进程或整个主机采集。适合调试和快速测试。

    # 主机 CPU 统计（30 秒）
sbench collector run -c configs/collector/proc-stat-standalone.yaml --root /opt/sbench

# 指定 CPU 核心的硬件事件（5 秒）
sbench collector run -c configs/collector/perf-stat-quick.yaml --root /opt/sbench

# 生成 perf 火焰图（SVG + HTML）
sbench collector run -c configs/collector/perf-flamegraph-quick.yaml --root /opt/sbench

# TopDown 分析
sbench collector run -c configs/collector/devkit-topdown-quick.yaml --root /opt/sbench

# 内存带宽统计
sbench collector run -c configs/collector/devkit-memory-quick.yaml --root /opt/sbench

# miss 热点分析
sbench collector run -c configs/collector/devkit-miss-event-quick.yaml --root /opt/sbench

    独立模式的配置以 collector_run 为顶层字段，所有采集目标（CPU、PID、设备）都需要在配置中显式指定。详细说明参考 standalone-collector.zh.md。

    sbench agent serve — 启动指标服务

    启动 HTTP 服务，将采集数据转换为 Prometheus 格式，供 Grafana 读取和展示。

    # 基本用法
sbench agent serve --root /opt/sbench --listen 127.0.0.1:8888

    命令行参数

    参数 默认值 说明
    --root .sbench 数据根目录
    --listen 127.0.0.1:8888 监听地址
    --refresh 1s 数据刷新间隔
    --no-proc 否 不读取本机 /proc，用于离线可视化
    --schedule 无 调度配置文件，自动定期执行采集任务

    离线可视化

    将采集结果拷贝到另一台机器上查看时，使用 --no-proc 避免读取不相关的本机进程数据：

    # 在非采集机器上启动 agent
sbench agent serve --root /opt/sbench --listen 0.0.0.0:8888 --no-proc

    自动调度

    通过 --schedule 指定调度配置，Agent 会在后台按配置自动执行采集：

    sbench agent serve --root /opt/sbench --listen 127.0.0.1:8888 \
  --schedule configs/agent/schedule-quick.yaml

    调度配置示例：

    agent:
  scheduler:
    enabled: true
  proc:
    # 可选：限制实时 sbench_vmm_* 指标只读取指定 deployment/PID。
    # 如果不配置，Agent 会读取 deployment state 中的全部 VMM PID。
    deployment_id: fc-json-parse-2vm-quick-20260513-135837
    target:
      type: pid_group
      pids: [12345]

jobs:
  # 附加到指定 deployment，每 60 秒采集一次 perf 数据
  - name: perf-stat
    enabled: true
    mode: attached
    deployment_id: fc-json-parse-2vm-quick-20260513-135837
    config: configs/collect/perf-stat-vmm-quick.yaml
    interval: 60s
    concurrency_policy: skip

  # 独立模式，每 30 秒采集一次主机 CPU 数据
  - name: host-cpu
    enabled: true
    mode: standalone
    config: configs/collector/proc-stat-standalone.yaml
    interval: 30s
    concurrency_policy: skip

    调度任务字段说明：

    字段 说明
    mode attached 绑定 deployment，standalone 独立运行
    deployment_id attached 模式下必填，必须写明确切 deployment ID
    config 采集配置文件路径
    start_delay 相对 Agent 启动的首次延迟，可用于控制任务首次进入调度窗口的相位
    interval 执行间隔
    concurrency_policy skip 表示上一次未完成则跳过本轮
    resource_lock 资源锁名称，相同锁名的任务不会同时运行（如 perf 和 devkit 共用 PMU）
    target 可选的 scheduler 级目标覆盖；会覆盖引用 collector 配置中相同类型的 target，例如覆盖 proc_pid / pidstat 的 pid_group
    collector_targets 可选的按 collector 名称覆盖 target，用于同一个 job 内不同 collector 需要不同目标时

    调度状态通过 Agent 的 /metrics 端点暴露，可在 Grafana 中监控任务执行情况。

    对于严肃实验使用的 configs/agent/schedule-density-experiment.yaml，其中 density-procfs-pidstat-by-pid 这一项现在会触发：

    • proc_stat：主机 /proc/stat
    • proc_pid：目标 VMM PID 的 /proc/<pid>
    • pidstat：目标 VMM PID 的 CPU/内存/I/O/上下文切换

    目标 PID 可以直接在 agent schedule 中配置，不必再修改 collector 配置文件：

    jobs:
  - name: density-procfs-pidstat-by-pid
    mode: attached
    deployment_id: fc-json-parse-2vm-quick-20260513-135837
    config: configs/experiments/density-procfs-pidstat-by-pid.yaml
    target:
      type: pid_group
      pids: [12345]

    而主机级中断/CPU 状态采集已拆成独立的 density-sar-host job，便于单独控制刷新周期， 不再等待整组 procfs/pidstat 串行完成。该 job 使用 configs/experiments/density-interrupts-host.yaml， 其中 interrupts 是组合 collector，运行时会展开为 sar 和 proc_interrupts。

    这样启用后：

    • density-procfs-pidstat-by-pid 提供 Target Process CPU Usage
    • density-sar-host 提供 Host CPU State Breakdown、Host Interrupt Rate、IRQ SoftIRQ CPU Time Share 和 IPI Scheduler Interrupt Rate

    当多个 DevKit 任务共用 resource_lock: pmu 时，Agent 现在会在同一把锁下建立串行队列，并按照 jobs: 中的声明顺序轮转执行。例如，把 topdown、miss-event、memory 依次写在配置中，就会形成固定顺序：

    jobs:
  - name: topdown
    enabled: true
    mode: attached
    deployment_id: fc-json-parse-2vm-quick-20260513-135837
    config: configs/experiments/density-devkit-topdown-by-pid.yaml
    start_delay: 0s
    interval: 300s
    resource_lock: pmu
    concurrency_policy: skip

  - name: miss-event
    enabled: true
    mode: attached
    deployment_id: fc-json-parse-2vm-quick-20260513-135837
    config: configs/experiments/density-devkit-miss-event-by-pid.yaml
    start_delay: 40s
    interval: 300s
    resource_lock: pmu
    concurrency_policy: skip

  - name: memory
    enabled: true
    mode: attached
    deployment_id: fc-json-parse-2vm-quick-20260513-135837
    config: configs/experiments/density-devkit-memory-by-cpu.yaml
    start_delay: 80s
    interval: 300s
    resource_lock: pmu
    concurrency_policy: skip

    这样会形成 topdown -> miss-event -> memory 的固定调度顺序，不会再因为简单抢锁而让后面的任务长期饥饿。start_delay 在这里是可选项，只用于调整首次启动时各任务进入队列的时间点，不再是定义顺序的唯一手段。

    如果你需要在同一个 agent 中同时采集“单 VMM PID topdown”和“全核心 topdown”，可以直接基于：

    configs/agent/schedule-density-mixed-topdown.yaml

    这个模板已经把 PMU 队列顺序定义为：

    1. 单 VMM PID topdown
    2. 全核心 topdown
    3. 单 VMM PID perf stat
    4. 全核心 perf stat
    5. 单 VMM PID miss-event
    6. CPU range memory

    同时，这个 mixed 模板会把主机 CPU 状态拆成独立的 density-sar-host job。

    在 Prometheus 指标层面，这两类 topdown 会通过通用目标标签区分：

    • target_type=pid_list + target_pids=...
    • target_type=cpu_range + target_cpus=...

    Dashboard 的 Topdown 面板已经拆成两组固定视图：

    • VMM PID Topdown ...
    • All CPU Topdown ...

    Perf Stat 面板也对应拆成两组固定视图：

    • VMM PID Perf Stat ...
    • All CPU Perf Stat ...

    用于直接区分 PID 视角和全核心视角的 PMU 数据。

    DevKit Memory 面板已拆成独立视图：

    • L1/L2 Average Cache Miss Rate：各级 L1/L2 cache 平均 miss 率
    • Total DDR Bandwidth / DDR Read Write Bandwidth：系统级 DDR 总带宽和读写拆分
    • Average Access Bandwidth / Average Hit Rate：L1/L2/TLB 访问带宽与命中率，CPU=All 时对 CPU 维度求平均
    • Average TLB Miss Rate：由 TLB hit rate 派生的 miss rate，默认展示 L2D_TLB 数据访问视图
    • L3 Read Bandwidth / L3 Read Hit Rate：L3 读带宽与命中率
    • DDRC Controller Bandwidth：按 DDRC 控制器拆分的读写带宽

    注意：DevKit tuner memory 只支持 host/CPU range 目标，不能按 PID 直接采集。需要单个 VMM 进程的 TLB miss 热点时，使用 devkit_miss_event 并设置 devkit.metric: 2，例如 configs/collect/devkit-tlb-miss-event-vmm-quick.yaml 或 configs/experiments/density-devkit-tlb-miss-event-by-pid.yaml。

    Overview 面板中的 LLC Miss Rate Table 按函数/模块展示 devkit_miss_event 的 LLC Miss Rate 热点；使用 configs/collect/devkit-llc-miss-event-vmm-quick.yaml 或 configs/experiments/density-devkit-llc-miss-event-by-pid.yaml 采集。

    同时，Dashboard 顶部还提供多组目标选择器：

    • VMM PID Topdown Target：按 target_pids 选择具体 VMM PID 视角结果
    • Pidstat PID Target：按 target_pids 选择 Target Process CPU Usage / Target Process Context Switch Rate 的 pidstat 结果
    • All CPU Topdown Target：按 target_cpus 选择具体 CPU 区间 / 全核心结果
    • VMM PID Perf Target：按 target_pids 选择具体 VMM PID 的 perf stat 结果
    • All CPU Perf Target：按 target_cpus 选择具体 CPU 区间 / 全核心的 perf stat 结果
    • Memory CPU Target：在 DevKit Memory Dashboard 中按 target_cpus 选择具体 CPU 区间

    这样当同一个 deployment_id 下同时保留多次 PID topdown 或多组 CPU range topdown 历史结果时，不会把不同目标范围的曲线混在一起。

    采集结果

    每次采集会生成一个独立目录：

    /opt/sbench/results/collections/<collection-id>/
├── manifest.json              # 采集元数据
├── config.original.yaml       # 原始配置
├── config.resolved.json       # 解析后的配置
├── raw/collectors/            # 原始数据（工具输出、CSV、报告等）
└── normalized/                # 结构化数据（供 Agent 转为 Prometheus 指标）
    • raw/ 保留所有外部工具的原始输出，可用于后续离线分析
    • normalized/ 包含解析后的结构化数据，Agent 读取此目录生成 Prometheus 指标

    查看实际执行的采集命令

    每次采集时，sbench 会把实际执行的命令记录到 command*.json 中。当你需要确认采集参数、排查问题或复现采集场景时，可以在这里查阅。

    # 查看某次采集中 perf_stat 执行的命令
cat /opt/sbench/results/collections/<collection-id>/raw/collectors/perf_stat/command.json

# 查看某次采集中 perf_flamegraph 的分阶段命令
find /opt/sbench/results/collections/<collection-id>/raw/collectors/perf_flamegraph \
  -name 'command*.json' -exec echo "=== {} ===" \; -exec cat {} \;

# 查看某次采集中所有采集器执行的命令
find /opt/sbench/results/collections/<collection-id>/raw \( -name command.json -o -name 'command*.json' \) \
  -exec echo "=== {} ===" \; -exec cat {} \;

    command.json 包含完整命令、退出码和执行耗时：

    {
  "command": "perf stat -d -d -d -e l2d_cache_refill,l2i_cache_lmiss -x , -o .../perf-stat.csv -p 12345,12346 -- sleep 5",
  "exit_code": 0,
  "duration_ms": 5201
}

    不同采集器的原始数据文件：

    采集器 command.json 其他文件
    perf_stat 有 perf-stat.csv（原始 CSV）
    perf_flamegraph 有（command.record.json 等） perf.data、perf.script、out.folded、flamegraph.svg、index.html
    devkit_topdown 有 stdout.txt、stderr.txt
    devkit_memory 有 stdout.txt、stderr.txt
    devkit_miss_event 有 stdout.txt、stderr.txt、miss_report.tar
    iostat / pidstat / sar 有 stdout.txt、stderr.txt
    proc_stat / proc_pid 无（直接读 /proc） .ndjson（原始文本记录）

    故障排查

    虚拟机启动失败

    • 检查 /opt/sbench/bin/firecracker 是否存在并可执行
    • 检查 kernel/rootfs 镜像路径是否与配置文件一致
    • 查看日志：/opt/sbench/results/deployments/<deployment-id>/hypervisor/<vm-id>/firecracker.stderr
    • 确认磁盘空间足够（每个 VM 需要复制一份 rootfs）

    perf 采集失败或显示 <not counted>

    • 确认以 root 运行
    • 检查 /proc/sys/kernel/perf_event_paranoid 是否为 0 或 -1
    • 用 perf list 确认平台支持的事件名称
    • 尝试改用 CPU range 模式（对整个 CPU 采集而非指定 PID）
    • 减少同时采集的事件数量

    DevKit 采集失败

    • 确认 DevKit 路径正确：/opt/sbench/tools/devkit/devkit
    • 确认目标 CPU 上有活跃的负载
    • 检查采集时长是否足够（建议至少 3 秒）

    Prometheus/Grafana 无数据

    • 确认 sbench agent serve 正在运行：curl http://127.0.0.1:8888/healthz
    • 检查 Agent 是否有数据：curl http://127.0.0.1:8888/metrics | head
    • 在 Prometheus 的 /targets 页面确认 sbench target 状态为 UP
    • 确认采集任务已执行：检查 results/collections/ 下是否有数据
