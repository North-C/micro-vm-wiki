    Quickstart

    This quickstart defines the V1 operator flow. For a fuller Chinese user guide covering prerequisites, CLI commands, collection, metrics conversion, and Prometheus/Grafana visualization, see user-guide.zh.md.

    1. Host Preparation

    Run on the Kunpeng host.

    mkdir -p /opt/sbench/{bin,images,tools,results,state}

    Expected host baseline:

    • openEuler 24.03 LTS-SP3
    • aarch64 kernel 6.6
    • root access
    • Firecracker installed
    • DevKit Tuner CLI installed under /opt/sbench/tools/devkit
    • optional tools installed: perf, pidstat, sar, iostat, numastat

    The local repository currently contains the DevKit package:

    DevKit-Tuner-CLI-26.0.RC1-Linux-aarch64.tar.gz

    Suggested install location:

    mkdir -p /opt/sbench/tools/devkit
tar -xf DevKit-Tuner-CLI-26.0.RC1-Linux-aarch64.tar.gz -C /opt/sbench/tools/devkit

    2. Probe Host Capability

    Probe host topology, kernel interfaces, PMU/SPE devices, cgroup version, and external tool availability.

    sbench host probe --output /opt/sbench/state/host-probe.json

    The probe output is referenced by every later deployment and collection.

    Minimum information:

    • OS and kernel
    • CPU topology
    • NUMA topology
    • SMT sibling map
    • cgroup version and mounted controllers
    • PMU devices, including armv8_pmuv3_0
    • SPE devices, including arm_spe_0
    • DevKit version and path
    • perf, iostat, pidstat, sar, and numastat availability

    3. Prepare Images

    Place Firecracker kernel and rootfs images under /opt/sbench/images.

    /opt/sbench/images/vmlinux
/opt/sbench/images/rootfs.ext4

    The rootfs should contain the guest runner:

    /opt/sbench/guest-runner

    The guest runner must support the json-parse workload and emit structured progress records.

    4. Create A Deployment

    Create a long-running Firecracker deployment.

    sbench deployment create -c configs/deploy/firecracker-32-single-numa.yaml

    Example deployment config:

    deployment:
  name: fc-32-single-numa
  hypervisor: firecracker
  sandbox_count: 32

image:
  kernel: /opt/sbench/images/vmlinux
  rootfs: /opt/sbench/images/rootfs.ext4

placement:
  numa_policy: single_numa
  numa_nodes: [0]
  smt_policy: physical_core_preferred
  cpu_policy: pinned
  cpus: "0-95"

    Expected output:

    deployment_id: fc-32-single-numa-20260513-001
state_file: /opt/sbench/state/deployments/fc-32-single-numa-20260513-001.json

    The deployment state must include a target registry with:

    • sandbox IDs
    • VMM PIDs
    • VMM thread IDs
    • assigned CPU list
    • assigned NUMA node
    • cpuset or cgroup paths when configured
    • guest runner connection information

    If MicroVMs are started by another tool, import the existing VMM processes instead of creating them through SBench:

    sbench deployment import --root /opt/sbench --name external-sandbox --hypervisor auto

    The imported deployment can be used by sbench collect run <deployment-id>. Destroying an imported deployment only updates SBench state and does not stop external VMM processes.

    5. Register The Workload Session

    Create an SBench workload session for the existing deployment. This records the expected workload phases and creates a host-side metrics directory; it does not execute code inside a VM or E2B sandbox.

    sbench workload start fc-32-single-numa-20260513-001 -c configs/workload/json-parse.yaml

    Example workload config:

    workload:
  id: json-parse
  mode: duration
  duration: 180s
  params:
    document_size_kb: 256
    nesting_depth: 4
    arrays: true
    threads: 1
    report_interval: 1s

phases:
  - name: warmup
    duration: 30s
  - name: run
    duration: 180s
  - name: cooldown
    duration: 10s

    Expected output:

    workload_session_id: json-parse-20260513-001
phase_file: /opt/sbench/results/workload-sessions/json-parse-20260513-001/phases.ndjson
metrics_dir: /opt/sbench/results/workload-sessions/json-parse-20260513-001/metrics

    For Terminal-Bench/E2B-style workloads that emit task completion events, the agent can parse *.json files in metrics_dir only when that directory is visible to the host running sbench agent. For local containers, mount the printed directory and pass it through --metrics-dir or TBENCH_METRICS_DIR:

    sbench workload start <deployment-id> \
  -c configs/workload/large-scale-text-editing.yaml \
  --root /opt/sbench

TBENCH_METRICS_DIR=/opt/sbench/results/workload-sessions/<session-id>/metrics \
TBENCH_RUN_ID=worker-001 \
/usr/local/bin/tbench-large-scale-text-editing --mode run --rows 1000000

    For remote E2B sandboxes, sbench workload start does not run e2b sandbox exec and the agent cannot read files that remain inside the E2B sandbox filesystem. Use E2B CLI/SDK to run the task, and either write completion events to a host-readable shared metrics directory or copy the generated JSON files back into the printed metrics_dir before expecting dashboard throughput data.

    For a long-running E2B sandbox, SBench includes helper scripts that keep tbench-large-scale-text-editing running inside the sandbox and periodically pull completed task records back to the host:

    scripts/e2b-start-tbench-loop.sh <sandbox-id> --rows 1000000

while true; do
  scripts/e2b-pull-tbench-metrics.sh \
    <sandbox-id> \
    /opt/sbench/results/workload-sessions/<session-id>/metrics
  sleep 10
done

    For batches of existing E2B sandboxes, the Python SDK helper can select sandboxes by template name/id or by explicit sandbox id:

    python3 -m pip install e2b
export E2B_API_KEY=<your-e2b-api-key>

# Inspect running sandboxes, optionally filtered by template.
scripts/e2b-tbench-sdk.py list --template <template-name> --json

# Start the infinite task loop in every matching sandbox. Re-running this
# command is idempotent unless --restart is set.
scripts/e2b-tbench-sdk.py start-loop \
  --template <template-name> \
  --rows 1000000 \
  --run-id-prefix tbench

# Later, pull metrics only from selected sandboxes into the SBench metrics_dir.
scripts/e2b-tbench-sdk.py pull \
  --sandbox-id <sandbox-id-a> \
  --sandbox-id <sandbox-id-b> \
  /opt/sbench/results/workload-sessions/<session-id>/metrics

    The SDK helper writes the same task_completion JSON records as the CLI helper and keeps an incremental cursor in metrics_dir/.e2b-<sandbox-id>.line. By default start-loop verifies and runs the task binary installed by the E2B image at /usr/local/bin/tbench-large-scale-text-editing. If a template uses a different path, pass --task-bin <path-or-command>.

    6. Run Baseline Collection

    Run baseline collectors while the workload session is active.

    sbench collect run fc-32-single-numa-20260513-001 -c configs/collect/baseline.yaml

    Example collection config:

    collection:
  name: baseline-host
  attach_to:
    workload_session: latest

collectors:
  - name: proc_stat
    enabled: true
    interval: 1s
    target:
      type: host
    trigger:
      phase: run
      delay: 0s
      duration: 180s

  - name: proc_pid

    6a. Run A Standalone Collector

    Collectors can also run without a deployment.

    sbench collector run -c configs/collector/proc-stat-standalone.yaml

    Standalone collectors must provide explicit targets and use collector_start triggers.

    collector_run:
  name: proc-stat-standalone

collectors:
  - name: proc_stat
    enabled: true
    interval: 1s
    target:
      type: host
    trigger:
      at: collector_start
      delay: 0s
      duration: 30s

    7. Run DevKit Topdown Collection

    Run a profiling collection over a CPU range or cpuset.

    sbench collect run fc-32-single-numa-20260513-001 -c configs/collect/devkit-topdown-node0.yaml

    Example:

    collection:
  name: devkit-topdown-node0
  attach_to:
    workload_session: latest

collectors:
  - name: devkit_topdown
    enabled: true
    target:
      type: cpu_range
      cpus: "0-95"
    trigger:
      phase: run
      delay: 30s
      duration: 60s

    The collection result must preserve:

    • DevKit command line
    • DevKit stdout
    • DevKit stderr
    • DevKit report directory or archive
    • normalized topdown summary when parser support exists

    8. Run DevKit Miss Collection

    Run a profiling collection over VMM PIDs or a CPU range.

    sbench collect run fc-32-single-numa-20260513-001 -c configs/collect/devkit-miss-vmm.yaml

    Example:

    collection:
  name: devkit-miss-vmm
  attach_to:
    workload_session: latest

collectors:
  - name: devkit_miss
    enabled: false
    target:
      type: pid_group
      selector: vmm
    trigger:
      phase: run
      delay: 30s
      duration: 60s

    9. Stop Workload And Destroy Deployment

    sbench workload stop fc-32-single-numa-20260513-001
sbench deployment destroy fc-32-single-numa-20260513-001

    Destroying the deployment must not delete results. It only stops Micro-VMs and updates deployment state.

    10. Inspect Results

    Deployment state:

    /opt/sbench/state/deployments/<deployment-id>.json

    Workload results:

    /opt/sbench/results/workload-sessions/<session-id>/
  manifest.json
  phases.ndjson
  workload_results.ndjson
  guest_logs/

    Collection results:

    /opt/sbench/results/collections/<collection-id>/
  manifest.json
  config.original.yaml
  config.resolved.json
  raw/
  normalized/

    The manifest.json file is the entry point for every collection. It links the collection back to the deployment, workload session, host probe, resolved targets, collector config, and tool versions.
